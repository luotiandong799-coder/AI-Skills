# wb-skill-authoring（技能层：写得能被触发、能被执行）

来源：WaytoAGI 精选 2026-09-01《Agent Skill 100 问》（skill 描述写法、触发排查、脚本/参考文件拆分、跨工具迁移、安全审查）。
核心判断：**skill 的价值 = 能否在该触发时被触发 + 读到的内容是否够执行。** 写得好但没人触发 = 不存在。

**与相邻技能的分工**（防抢触发）
| 场景 | 走谁 |
|---|---|
| 从零新建一个技能 | 平台内置 `skill-creator`（官方结构 / frontmatter / 脚本规范） |
| 改造 / 体检**已有**技能（触发不准、描述过宽、去重合并、安装后接线、触发评测、安全审查） | **本技能** |
| 长内容（书 / 长视频 / 播客 / 课程）蒸馏成技能 | `cangjie-skill`（本技能只管蒸馏产物落地后的写法与验收） |

## 设计原则（动手写之前先定）
来源：mattpocock/skills 的 README（"技能设计小巧、易于适应和组合，适用于任何模型，基于数十年的工程经验"）+ 本库实践。
- **单一职责**：一个技能解决一个功能位的问题；同一功能位出现第二个技能＝重复（走下面的去重合并流程）
- **小巧可组合**：正文能被一次读完；需要跟别的技能串起来时，用"与相邻技能的分工"表写清接口，**不复制对方的规则**
- **不重造流程**：已有成熟方法论（SDD / TDD / 诊断循环 / 代码评审）时，只补本地化差异与触发条件，不复述一遍通用流程——复述出来的部分会跟上游漂移
- **渐进披露**：description（常驻，只写"何时用"）→ SKILL.md（判断与步骤）→ `references/`（长清单/模板按需读）
- **只写跑过的**：没实际执行过的流程不写进技能，否则变成假规则

## 写"什么时候不该跑"：STOP / WAIT / PROCEED 快速路径表

来源：GitHub `william-london/ownframework-loop` `.agents/skills/of-loop-{build,review}/SKILL.md`（2026-09-14 增量）。好的技能不只写"怎么用"，还在**最前面**用一张表声明**当前状态下该做什么**：

| 状态 | 动作 |
|---|---|
| 已经完成 / 已阻塞 / 已停止 | **STOP**——别重复做 |
| 前置物还没产生（上一环没交付） | **WAIT**——别自己造前置物，更别替别人启动 |
| 前置就绪 | **PROCEED** |

- **STOP 分支最重要**：技能被反复触发是最大的隐性浪费，"已经做完了"时必须能直接退出，而不是再跑一遍。
- **WAIT ≠ 自己动手补**：缺前置物时**不要自己创建它**（评审技能不得自己去创建构建产物），否则两个角色变成同一个角色，独立性没了。
- 声明"不该跑"比声明"该跑"更能防止误触发，也是**负向边界的可执行版**（不只是"不适用于…"，而是"遇到 X 就 STOP / WAIT"）。

## 技能是"指令 + 所需工具"的打包，不是一段文字

来源：n8n Docs《Build and manage agents》（2026-09-14 实访 Markdown 原文）：*Skills = reusable behavior bundles that package instructions with the tools needed for a specific task.*

- **一个技能 = 一类任务的指令 + 完成它所需的工具**，二者一起交付。只给指令不给工具，执行时还得现找；只给工具不给指令，模型不知道何时用、怎么用。
- **因此写技能时要同时回答两个问题**：① 怎么做（步骤/规则）② 用什么做（脚本 / 命令 / 依赖）。缺第二个，技能就是不完整的。
- **可复用的判定在"任务"这一层**：按"一类任务"打包，不按"一次操作"、也不按"一个领域"打包——太细会碎片化，太粗会变成什么都往里塞的杂物间。
- 与「文件拆分」配套：指令进 `SKILL.md`，工具进 `scripts/`、资料进 `references/`，**打包的是同一件事的三种形态**。

## description 怎么写（决定触发的唯一因素）
- **写"何时用"，不写"是什么"**：description 是路由器，不是简介。开头就给触发场景（"当用户要求 X / 出现 Y 场景时使用"），其次才是能力范围
- **把用户的原话写进去**：用户会说的说法（含中英文、口语、错拼）都列进触发词——模型靠语义匹配，不靠理解你的命名
- **具体 > 宽泛**：`"修 bug"` 会被误触发到所有排错场景；`"涉及编码任务时"` 才收得准。宁可窄，触发太窄时再补
- **边界写进描述**：明确"不适用于什么"（如 ponytail 写"非代码任务不套用"），防误触发比补充触发词更省事
- **负向边界声明成段**（来源：阿里云 Skills / ModelScope 生态的通用写法）：能力封装类技能在描述或正文开头写显式的 `不适用于：…` 段（如支付宝 skill 写"不用于微信支付、银联支付、对账、红包等非收单场景"）——把最容易误触发的一批相邻场景**点名排除**，比只写正向触发词收得准得多
- **一处修改即可生效**：description 是唯一被常驻加载的字段，正文只在触发后才读——所以约束的第一层防线必须在 description 里

## 描述的两条硬规格与一条写法纪律（来源：agentskills.io 官方 Specification / Optimizing descriptions，2026-09-15 实拉新站）
`agentskills.io` 是 Agent Skills 的**官方开放规范站**（原在 `anthropics/skills/spec/`，现为独立站，`/llms.txt` 有全量索引）。它给 description 定了可机检的边界，另有一条反直觉的写法纪律：
- **硬规格**：`name` 1–64 字符、只能小写字母/数字/连字符、**不得以连字符开头或结尾、不得出现连续连字符、必须与父目录同名**；`description` **上限 1024 字符**且非空。名称不与目录同名是巡检能直接抓的静默故障。
- **写法用祈使句，不要用陈述句**：写"**当用户要 X 时使用**"，不写"本技能做 X"。agent 是在决定**要不要行动**，所以描述要告诉它**何时行动**；能力介绍句不触发。
- **倾向强势（err on the side of being pushy）**：显式列举适用场景，**包括用户没有直接点出领域词的情形**（"即使他没说'CSV'或'分析'"）。宁可多列，触发不足比过宽更难发现。
- **面向用户意图，不写实现机制**：agent 拿用户原话去匹配，匹配的是用户想达成什么，不是技能内部怎么实现。
- **反直觉事实：简单请求可能根本不查技能**（来源：同上《Optimizing descriptions》）。agent 通常只对**超出自身能力**的任务去翻技能库——"读一下这个 PDF"这类单步请求，即使描述完美匹配也可能不触发，因为基础工具就能做。**该触发却没触发时，这是第 0 层原因**，先排除它再改描述。

## 该触发却没触发：按序排查
0. **这个任务是否本来就不需要技能？**（超出模型自身能力的任务才会去查技能库——单步简单请求没触发不等于描述有问题，见上节末条）
1. 描述里有没有用户实际会说的那几个词？
2. 触发条件是否写得太抽象（"处理复杂任务" 这类）？
3. 文件位置对不对（用户级 `~/.workbuddy/skills/` vs 工作区 `.workbuddy/skills/`）？
4. frontmatter 语法是否合法（`name` / `description` 必填，YAML 缩进别错）？
5. 改完 skill 后会话没重开 → 读的仍是旧版本

## 不该触发却触发
- description 过宽（写成了"所有 AI 相关任务"）
- 多技能触发词打架 → 显式写出优先级，或收窄其中一条
- 名字太泛（`helper` / `utils`）→ 改成能被语义区分的名字

## 双路由防呆：原生路由存在时，不要常驻 meta-router（来源 addyosmani/agent-skills #557）
宿主已能按 description 原生发现并激活技能（渐进披露）时，**不要再把"技能路由表 / meta-skill"整份常驻进 system prompt / 规则文件**——同一任务被两套路由器处理：多耗常驻上下文 + 路由结果可能打架。二选一：
- 原生路由在 → 各技能写好 description 即可，meta 层只做"接线表"（指向谁管什么，一行一个），不复制路由逻辑
- 原生路由不在 → 才用 meta-skill / 常驻路由表兜底
- 反模式：装了原生渐进披露的宿主，又把 25 个技能的索引塞进 always-on 上下文"图省事"；或同一任务在技能内和规则文件里各写一套分流逻辑
- 自反检查：本库技能靠 description 原生触发 → 任何新技能**只写 description + 分工表一行**，禁止再造一份"何时用哪个技能"的常驻长清单

## 触发评测：发布前盲测（新技能 / 改过 description 必做）
来源：GitHub `kangarooking/cangjie-skill`（★9.8k，MIT）阶段 4「压力测试」——把"description 能不能被触发"从**事后排查**升级为**发布前可测**。写得再好，没测过就是碰运气。

**用例三类，缺一不可**（写成 `test-prompts.json` 放技能目录，与 darwin-skill 格式兼容）
| 类型 | 条数 | 测什么 |
|---|---|---|
| `should_trigger` | 3–5 | 该调用时是否调用 |
| `should_not_trigger`（诱饵） | 2–3 | 不该调用时是否忍住 |
| `edge_case` | 1–3 | 边界模糊场景判断是否合理 |

- **没有诱饵用例的技能一律打回**：只测正例，每个技能都"看起来很好"，上线后乱触发
- **诱饵里至少 1 条必须是"应该触发另一个相邻技能"的 prompt**——技能间抢触发是上线后最常见的真实故障，只测"完全无关场景"发现不了

**盲测做法（优先独立 sub-agent）**
- 给 sub-agent 只给：技能清单（全量 name + description）+ 用户 prompt；**不给**预期答案 / 用例类型 / 判断
- **写时自检（20 条混检法）**（来源：Anthropic《构建 Agent Skills 五条工程准则》，2026-09-16 实拉）：盲测之前的轻量自检——把你写的 description **单独拿出来，混进另外 20 条描述里**，问自己：只看描述，一个从没见过项目的人能否在真实用户话术下挑中它？**挑不中 = 还没写完**。判据：自检在写的时候做（便宜、随时可跑），盲测在上线前做（严格、要 sub-agent）；自检都过不了的 description 不值得进入盲测。
- 让它做**选择题**（该激活哪一个），而不只是"要不要激活这一个"——否则测不出抢触发
- 要求输出 `would_trigger` / `reason` / `if_triggered_action`，主流程再逐条对答案
- 无 sub-agent 能力时才退回自测，并在结果里标注这是 fallback、可信度低于盲测

**评测任务四元组：写"评测任务"必须四件齐全，缺一不可**（来源：Stanford CS329Z《Engineering AI Agents》HW2 评估套件，2026-09-16 实拉）：`request`（请求/任务描述）+ `environment`（环境/前提状态）+ `stopping criteria`（停止条件，什么时候算结束）+ `scorer`（评分器，怎么打分）。判据：**任何评测用例缺四元组之一 = 测不了或测不准**——没有 environment 用例不可复现、没有 stopping criteria agent 会跑飞、没有 scorer 结果不可比。写 eval 用例时逐条核对四元组，跟"用例三类缺一不可"并列作为发布前必检。

**分环节评估矩阵：每个中间环节一个指标，指标必须对应它抓的失败**（来源：OurToken《Agentic RAG: Build Retrieval Loops That Decide》2026-09-16 实拉）：评估不能只看端到端结果——agentic 流程的每个中间环节都该有自己的指标，且**每个指标都要能说出"它抓住的失败是什么"**：
| 评估目标 | 示例指标 | 抓到的失败 |
|---|---|---|
| 查询改写 | 意图保留率 | 改写改变了用户原意 |
| 任务分解 | 子查询覆盖率 | 漏掉比较的一侧 |
| 工具选择 | 正确工具率 | 用向量检索查实时状态 |
| 证据充分性 | 证据覆盖+冲突检测 | 用不完整/矛盾证据作答 |
| 停止行为 | 每查询类型迭代次数 | 无限检索或过早停止 |
| 端到端答案 | 忠实度+相关性 | 流畅但无证据支持 |
判据：**指标与失败一一对应**——说不出"这个指标防哪种失败"的指标不设；只设端到端指标会漏掉中间环节的坏行为（与四元组互补：四元组管任务结构，本条管指标设计）。

**通过率门槛**
- 100% → 接受
- ≥80% → 分析失败用例：description 有歧义 → **修技能**；用例设计过狠 → 修测试，但必须记下理由
- <80% → **回炉重写 description**，不做表面修补；诱饵用例容错为 0

**回归保护三件套：发布后防退化，与发布前盲测互补**（来源：ECC Eval Harness CSDN 2026-09-07 / Fiddler《Automating EDD》2026-06-29 / XYZBytes《EDD: Why Evals Are the New Unit Tests》2026-06-28 实拉）——盲测管"上线前能不能触发"，这三条管"上线后每次改动别把已好的弄坏"：
- **pass@k 度量**：`pass@1`（首试成功率，直接可靠性）+ `pass@3`（3 次尝试内至少成功一次，容错上限）。典型目标 **pass@3 > 90%**；报告成绩必须写 k，不写 k 的通过率不可比。
- **变更触发 + 自动回滚**：每次实质变更（模型版本 / prompt / description / 检索策略 / 工具列表）后跑全量 eval 套件，与 best-seen 基线比聚合分；**跌破基线自动恢复上一版本**（版本控制兜底），不靠"我觉得没变差"。
- **eval 是 CI 门不是信息面板**：回归阻断在合入前生效——套件只报告不拦截 = 事后诸葛亮。判据：改了 skill 却说不清"哪条 eval 验证了它没退步"，等于没测。

### 用例怎么挑才有分辨力：正例要"连接不明显"，负例要 near-miss（来源：agentskills.io《Optimizing descriptions》2026-09-15 实拉）
用例条数够不代表测得出东西——**挑错用例等于没测**：
- **最有价值的正例是"技能会有帮助、但从 prompt 表面看不出来"的**。若一条 prompt 已经明确要求了技能所做的事，**任何合理描述都能触发它**——这条用例对"描述写得好不好"零分辨力，只测了显然的事。
- **最有价值的负例是 near-miss（近失）**：**共享关键词或概念，但实际需要的是别的东西**。例：给"CSV 分析"技能设负例，弱例是"写个斐波那契函数"（明显无关，什么都测不出）；强例是"帮我改一下 Excel 预算表里的公式"（共享表格/数据概念，实际要的是 Excel 编辑）与"写个脚本把 CSV 每行传到 postgres"（含 CSV，但任务是 ETL 不是分析）。**"显然无关"的负例是假诱饵，删掉或换掉。**
- **正例要沿四个轴变化**：措辞（正式/口语/错拼缩写）、**显式度**（点名领域 vs 只描述需求，如"老板要我把这个数据文件做成图"）、细节度（一句话 vs 带路径列名与背景）、复杂度（单步 vs 埋在长链路里）。
- **负例不能只有一条"应触发相邻技能"的**（本技能上表已有此硬要求）——**再补近失类**，两类诱饵测的是不同的东西：前者测抢触发，后者测描述精度。
- **真实感要素**：带文件路径（`~/Downloads/report_final_v2.xlsx`）、个人语境（"我经理让我…"）、具体列名/公司名/数值、口语缩写与偶发错别字。用"处理这个数据"这类空泛 prompt 测不出任何东西。
- **触发率口径（与通过率门槛并用）**：模型行为非确定，**同一 query 至少跑 3 次**，算**触发率**（被调用的运行占比）；应触发用例看触发率是否 **≥0.5**，不应触发用例看是否 **<0.5**。20 条用例 × 3 次 = 60 次调用，应脚本化。**只跑一次就下结论 = 拿单次样本当分布**（与 §指标有噪声同源）。

### 上线后度量：触发率 × 有效性（防评测自身失效）
来源：GitHub `trailofbits/skills` 的 property-based-testing eval 方法论（测量 skill 触发率与有效性，防评测自身漂移）。盲测只是发布前门槛；上线后的技能还要回答"真被用了没、用了真有用没"：
- **触发率（recall）**：该触发的场景里实际触发的比例——从真实会话里数，不从测试集里数；长期 0 触发的技能要么改 description 接线，要么按去重流程处理
- **有效性（effectiveness）**：触发后结果是否真的比不触发好——只统计"触发了"不看结果，会把抢触发的噪声技能当成功
- **防评测自身失效**：固定评测参数会让各档扫描结果全部等价（测了个寂寞）；评测脚本本身也要防漂移——检查器查到零样本必须报错（与 `wb-spec-driven` 三·八反空洞守卫同源），**评测里"0 次触发"先查是不是评测坏了，再下"技能没用"的结论**
- **用真实触发数据找描述词表缺口**（来源：addyosmani/agent-skills #434，实测触发 rank-1 86%→100%）：正例把技能排到第 2–3 名而不是第 1 名 = 描述缺了用户真实会说的词——包括**不共词干的近义词**（`docs` 与 `documentation` 词干不同，只写一个就漏匹配）、场景口语（"昨天还好好的" = regression 词表）。修完词表后把触发率地板按**棘轮**调高（只升不降），防止质量回退。

### Rubric 生成与归因：评分标准别手写硬造（来源：RubricForge arXiv 2608.13564 / AdaRubric arXiv 2603.21362，2026-09-16 实拉）
手写 rubric 常见两个病：标准定得不贴近真实好坏（过宽/过窄）、维度互相重叠（一条过其他条必挂）。两个可落地做法：
- **RubricForge：从标注轨迹演化出 rubric**——拿少量带 ground-truth 结果的轨迹，让 rubric 通过反思式演化迭代，最大化与真实奖励的一致性，冻结后直接用于留出集；**产物是人类可读文本，每个判定可归因到命名标准**。判据：评测 rubric 若从"我感觉该看什么"手写 → 先收集 10~20 条带真实好坏标签的轨迹，让 rubric 从轨迹里"长"出来，再人工审一遍。
- **AdaRubric：评估维度是任务的函数，不是评估器的固定属性**——按任务生成 N 个**任务特定、正交**的评估维度 + 校准的 5 点评分标准。判据：同一套 rubric 套所有任务 = 维度必然错位；新任务先问"这个任务的好坏由哪几个互不重叠的维度决定"。
- **评分尺度按判据性质选，不默认量表**（来源：DecodingAI《How EDD Works》2026-06-23 实拉，与 AdaRubric 的 5 点量表互补合并）：**能确定性判的一律用二元分类（verified / not）**——结构性判据（调没调工具、格式对不对、字段在不在）用代码指标服务器端判，免费且不抖；只有主观质量判据（完整性、准确性、排序质量）才上 LLM judge / 校准量表。判据：同一维度的判定若"既是又不是"模棱两可 → 先拆维度，别靠 1–5 分的中间档吸收模糊；评分器在中间档抖动 = 该维度的二元判据没设计出来。
- **rubric 校准：人工抽查回测一致性**（来源：ilyaisaev《EDD: The New TDD for the Agentic Era》2026-04-27 实拉）：rubric 定稿后，让人工专家定期抽查少量输出（如 5%）与自动评分对答案，**一致性 <90% 说明 rubric 太主观、需细化到可判定条目**，而不是调自动评分器去凑人工。判据：rubric 上线前至少回测一轮，把"专家判 A、评分器判 B"的条目挑出来改写。

### 评测集配方：别拿"随便攒的 50 条"当评估（来源：aipromptshub 2026-06-27 + FutureAGI Golden Set 2026-05-16 + FutureAGI Playbook 2026-05-14 实拉，与 RubricForge/AdaRubric 互补——那条管"怎么打分"，本条管"拿什么打"）
- **尾部过采样**：质量失败集中在低频尾部查询（底部 20% 频次产生 60–80% 失败）——评测集必须**故意多放低频/长尾用例**，只放高频常见问题测不出真实弱点。
- **canary 保留集**：留 20–50 个**永不用于提示迭代**的 held-out 用例，每次改动后先跑 canary——**防止提示词对评测集过拟合**（改着改着评测集分数涨、真实世界没涨）。
- **四桶配比**：生产采样 60%（真实流量分层覆盖）+ 对抗 15%（jailbreak/红队）+ 专家边界 15%（手工长尾）+ **失败重放 10%**（过去事故/错误簇——已付过钱的 bug 不许回归）。
- **双集结构**：固定回归集（每次发布必跑）+ 滚动对抗集（每两周轮换，≥10% 对抗覆盖）；规模 50–200/任务起步，<50 统计噪声会翻转胜者。

### 效果归因：必须设 no-skill 对照组（来源：腾讯 SkillHub TRACE 评测体系，腾讯科技 × 玄武实验室）
"有 Skill"≠"Skill 有用"——**有 Skill 不一定效果更好**。技能质量最终要看 E 维度（效果增益）：同一任务分别跑"启用 Skill"与"仅原生模型"两组，只有 Skill 组**显著更好且代价合理**才算合格。
- **为什么必须对照**：模型本身能力一直在涨，不设 no-skill 参照组，就会把模型自己变强误判为技能贡献——技能库被灌进一堆"看起来有用、实测无增益"的技能，白占常驻上下文与路由位
- **代价合理性**：增益要扣掉成本（常驻 token、加载延迟、维护负担）再算——小增益 + 高常驻成本 = 负资产
- **红线维度前置**：TRACE 五维（Trust 可信任 / Reliability 可靠 / Adaptability 适用 / Convention 规范 / Effectiveness 有效）中 **T 是红线**——触碰安全红线的技能直接淘汰，不看其他维度得分（与本技能 P0 分级同构）
- **自反检查**：本库技能每季抽测——挑 2–3 个技能做 no-skill 对照，无显著增益的按去重流程处理，不为"数量"保留
- **同一方法两用：技能消融 & 工具消融**（候选池收口，来源：Make best practices）——对照法不仅可以把技能抽走，也可以把**某个工具/MCP 禁用**后重跑同一任务，对比执行轨迹差异来归因"这个工具贡献了什么"。禁用前后轨迹无差异的工具 = 常驻上下文纯开销，砍。
- 五维可并进审计评分表（与 darwin-skill 8 维互补：TRACE 管"该不该留"，8 维管"哪里能改"）

### 指令迭代：用**执行轨迹**当输入，不靠手改/感觉（来源：Make AI Agent 帮助中心《Best practices》）
技能 / agent 指令改写的输入应是**真实运行过的证据**，不是"我觉得不够好"。官方口径：**多数错误或异常结果来自指令不清或有误导**，而修法是把下面三样一起交给 LLM 让它改，**不要手工逐字改**：
1. **当前指令**（改前原文）
2. **实际执行步骤**（这次跑出来的步骤序列、调了哪些工具、每步输入输出）
3. **每步的推理**（若模型/工具能给出 thinking 或 reasoning 视图，一并给）

改完再跑一次，循环到表现符合预期为止。
- **为什么不能只凭感觉手改**：手改无法归因（下次变好/变坏都不知道是哪句起的作用），也无法验证（与本技能 §效果归因的 no-skill 对照组联动）
- **顺序**：先看轨迹定位歧义与漏项 → 再定向改（指出具体缺陷、保留其余部分）→ 重跑 → 对比；**一次只改一个变量**（与 `wb-max-token-saver` 换挡顺序联动，一次改多处 = 归因失败）
- **定向改 > 让模型自动改**：需求/缺陷明确时给方向；无明确方向时才留空让模型自己改（自动改的结果也要重跑验证）
- **轨迹读不到时**：先补可观测（把"中间步骤 + 工具名 + 输入输出"打出来）再谈改指令——没有轨迹的迭代就是猜
- **配套联动**：指令里点名的工具**改了名就要把指令里所有出现处同步改**（Make 同页明说"匹配工具名"），与 §重命名必须全链路同步同一纪律

### 指标有噪声：单次差异不是信号，靠重复采样看趋势

来源：n8n Docs《Fix common issues》"Dealing with inconsistent results"（2026-09-14 实访 Markdown 原文）。

**同一份东西、同一套评估，跑两次指标也可能不一样**——被测方本身有随机性，用模型打的分数自身也在波动。**把一次指标的涨跌当成改进/退化的证据，是最常见的自欺。**

- **重复采样平滑**：把同一条用例在数据集里放多份，一次评估中同一输入被跑多次，用均值/分布代替单点。
- **判定改的是"趋势"不是"一次的值"**：只在多次重复后仍同向变化，才认它为真信号。
- **先分清噪声来源**：是产出本身不稳定（被测方问题），还是评分器在抖（度量问题）。**评分器不稳时，先修评分器，别拿它去改被测方**——否则你在追一个随机游走的目标。
- 反向用法：如果同一输入的多次结果差异很大，**这本身就是最重要的发现**（不一致 > 平均表现差），应优先处理稳定性而不是平均分。
- 适用于本技能所有量化度量：触发率、通过率、检出率、no-skill 对照组的增益。

### 评测套件契约：能力评测 vs 回归评测，先定目的再选用例（来源：edonadei/caliper `evaluate-skill`，skills.sh /hot 实拉 2026-09-15）

写一个技能的评测（`.eval.yaml` 一类规格）前，先回答四个问题——它们决定用例怎么选、结果怎么读：

1. **先点名目标行为**：这个技能应当比**裸 agent** 做得好在哪里？（答不出来 = 还没到写评测的时候）
2. **先决定套件性质：能力评测（capability）还是回归评测（regression）。** 两者目的不同、用例选法不同——能力评测探"能不能做到"（要刻意挑技能该赢的场景）；回归评测守"别退化"（锁定已通过的真实场景）。**混在一套里会导致两边都不准。**
3. **行为重要时，覆盖正常 / 边界 / 对抗三类**（与 §触发评测盲测的三类用例同构，但这里评的是**效果**不是触发）。
4. **打分产物优先于打分转录**：能打分产物（文件、git 状态、命令输出、精确数值）时**必打分产物**；**只有"行为本身"才是被评对象时，才评判转录**。转录评分易受表述影响，产物是硬证据——与 `wb-artifact-verification`「验证要能脚本化」同源。

**完成判据（Done when，五条全满足才算做完）**：
- 每个任务有**可观察**的成功标准
- 至少一条**确定性断言**（不是纯语言判断）
- 相对**消融对照**（`--ablate` 后与裸 agent 比）有**正增益**——与 §效果归因 no-skill 对照组是同一方法的两用（技能消融 / 工具消融）
- 规格本身**通过校验器**（`validate` / lint 类）
- **已提示用户把规格提交**（明确告知，不默认对方知道）

### 评测要跑在两个执行体上：文件级 runner 与 agent 级 runner 必须分开（来源：GitHub `FrancyJGLisboa/agent-skills-platform`·`LEARNINGS.md`，gh search repos 2026-09-16 实拉）
两套 runner 回答的是**两个不同的问题**，合并成一套会同时毁掉两者的诊断力：

| | **文件级 runner** | **agent 级 runner** |
|---|---|---|
| 怎么跑 | 拿 golden cases 直接跑技能里的脚本 / 管线，**不启动 agent** | **真起一个 agent**、装上这个技能，跑真实任务 |
| 回答什么 | 产物对不对（脚本/管线是否正确） | **找不找得到（discovery）/ 读没照做（instruction following）/ 多次一不一致（repeat consistency）** |
| 成本 | 秒级、可上 CI | 每次几分钟 + token，**不能上交付门** |

- **核心失败模式（真实案例）**：某技能**通过了全部文件级 eval**，而实际使用时 agent 读了技能、**直接忽略它的管线、自己把指标算了一遍**。→ **文件级全绿不构成"agent 会正确使用这个技能"的证据**；这两件事必须分别取证。
- **不许合并成一个 runner**：合并后一条"评测挂了"分不出是哪一半挂——**`description` 写得差（根本没被找到）、正文写得差（读了但不照做）、脚本写得差（照做了但跑不对）三者的修法完全不同**，合成一条就丢掉了修哪个的信息。
- **成本约束决定放置位置**：agent 级保持**手工 + 本地**跑，结果喂给认证/评审（**走工具生成，不许手抄结论**）；**CI 只做离线能完成的**（规格语法校验、静态检查）。
- 与上一节 §能力评测 vs 回归评测 的分工：**那条按目的分**（探上限 vs 守退化），**本条按执行体分**（脚本直跑 vs 真 agent 跑）。两个维度正交——一套评测要同时标明"**目的是什么**"和"**在哪个执行体上跑**"。

**调试与测量的档位**：先用 `k=1` **调规格本身**（跑通、看输出形态），再用 **`k=3` 或更高测可靠性**（`pass@k`：同一任务跑 k 次看通过率）。**用 k=1 的结果谈可靠性 = 拿单次样本当分布**（与 §指标有噪声同一条纪律）。

**引擎与规格解耦**：评测规格里**不写** backend / model；运行时**分别独立选**——`--model` 选被测技能的引擎、`--judge-model` 选评判者的引擎。理由：规格是**可复现的资产**（谁 clone 都能跑同一评测），引擎是**当时的成本/能力选择**；写死在一起 → 换个模型就得改规格，规格立刻失去可比性。
- **规格与 `SKILL.md` 同仓提交**（在技能旁边），**运行结果 JSON 可 gitignore**——前者是可复现资产，后者是随时间对比用的中间物。

## 内容从哪来：喂真实专长，不要叫模型自造（来源：agentskills.io《Best practices》2026-09-15 实拉）
**最常见的失败做法**：给 LLM 一句话需求就让它生成技能，全靠它自己的通用训练知识。产出必然是"妥善处理错误""遵循认证最佳实践"这类**空泛通用流程**，而不是真正有价值的 API 细节、边界情况与项目约定。技能的价值全在**喂进去的领域上下文**里。
两条素材路径：
1. **从一次真实动手任务里提取**——先带着 agent 真做完一件事（过程中给上下文、纠偏、说偏好），再把可复用模式抽出来。重点记录四类：**走通的步骤序列 / 你做过的纠偏**（"用 X 库别用 Y""检查 Z 边界"）/ **输入输出格式** / **你补充的项目特有事实与约束**。
2. **从已有项目资料合成**——喂给 LLM 的项目特有材料优先于"某领域最佳实践"文章。高价值来源：内部文档、runbook、风格指南；API 规格、schema、配置文件；**代码评审意见与 issue 跟踪**（捕捉反复出现的关注点与评审者预期）；**版本控制历史，尤其是补丁与修复**（**通过"实际改了什么"揭示模式**）；真实失败案例与其处置。

## 用真实执行精修：三件事（来源：同上）
- **把跑出来的结果全部回灌，不只是失败**。只喂失败会漏掉"侥幸成功但过程有病"的情形。回灌后问三个问题：**什么触发了误报？漏了什么？能砍掉什么？**
- **读执行轨迹（trace），别只看最终输出**。agent 在无产出的步骤上浪费时间时，常见归因只有三条——① **指令太含糊**（agent 试了好几种才找到能用的）② **指令不适用于当前任务**（agent 照做了）③ **给了太多并列选项而没有明确默认**。这三条各自对应不同修法，先定因再改，与 §指令迭代（用执行轨迹当输入）同一纪律。
- **过度全面反而有害**：内容越多，agent 越难**提取**相关内容，且**会被那些不适用于当前任务的指令带偏到不产出的路径上**。多数边界情况交给 agent 自己的判断更好。判据："**没有这一条，agent 会做错吗？**"——答"不会"就砍；不确定就去测；若 agent 根本没这个技能也能把整件事做好，**这个技能可能没在增加价值**。

## 调指令是缓解，不是修复：失败若发生在"指令被正确遵循之后"，改指令无效（来源：GitHub `thedotmack/claude-mem`·`docs/merge-rubric.md`，2026-09-16 实拉）
- 原文硬判据：`nudging a model's behavior with stronger instructions is mitigation, not a fix`——**用更强的措辞去推模型行为属于缓解，不算修复**；这类改动自己往往承认"`won't eliminate the problem`"。（同源另一句：**加固不是修复**——`armor for a wound nobody has`，没有哪个行为今天是错的，加的只是盔甲。）
- **判定顺序**：先看失败发生在哪一步——**指令没被正确遵循**（没读到、读不懂、触发不对）→ 归指令，走 §用真实执行精修 改写法；**指令被正确遵循了，照做之后仍然失败**（工具返回错、脚本有 bug、数据本身不对、宿主能力缺失）→ **归实现**，去改脚本 / 工具 / 数据 / 宿主配置，**不要在 SKILL.md 里加粗再写一遍**。
- **自查信号**：连续两轮改同一条指令措辞而现象不变 → 你正在把修复预算花在缓解上；**此时应停止改写法，去读执行轨迹定位真正的失效点**（与 §指令迭代"用执行轨迹当输入，不靠手改/感觉"同一条纪律的判据版）。
- **允许改指令的三种情形**（其余一律先查实现）：① 措辞含糊导致多种理解；② 缺了必要的约束或边界；③ 给了并列等权选项而没有默认。
- 与 §rule 生命周期（成文/磨尖/退役）的分工：**那条管规则什么时候该写、该走**，本条管**遇到失败时别默认往规则层推**——把实现缺陷写成一条新规则，等于给同一个洞加第二层盔甲。
- 与 `wb-debug-loop` §二·五·六 的分工：那条管**代码修复**不得由容错装置构成，本条是同一判据在**指令层**的对应物（"再加一句必须……"就是指令层的兜底）。

## 控制度：按脆弱性逐段校准，不是全文一个强度（来源：同上）
不是每一段都该同样强硬。**匹配具体度与任务的脆弱程度，逐段独立校准**：
- **给自由度**（多种做法都行、任务容忍变化）：**解释"为什么"比硬性指令更有效**——理解目的的 agent 能做更好的情境判断。典型：代码评审技能描述"要看什么"（查 SQL 注入、验每个端点的鉴权、找并发竞态、确认报错不泄漏内部细节），不规定具体步骤。
- **必须强硬**（操作脆弱、一致性要紧、顺序不能变）：写死命令并明说"不要改这条命令、不要加额外旗标"。
- **给默认，不给菜单**：多种工具都可能work时，**选一个默认 + 一句话提替代**，不要并列成等权选项（并列选项正是上面"trace 归因第③条"的成因）。
- **写过程，不写答案**：教"怎么处理这一类问题"，不是"这个具体实例该产出什么"。具体细节（输出模板、硬约束如"绝不输出 PII"、特定工具用法）可以有，但**方法本身要能泛化**。

## 四个高价值实操模式（来源：同上）
- **Gotchas 段（很多技能里价值最高的内容）**：写**环境特有、违背合理假设**的具体纠正，不是通用建议。例：`users` 表用软删除，查询必须带 `WHERE deleted_at IS NULL`；user ID 在库里叫 `user_id`、在 auth 服务叫 `uid`、在计费 API 叫 `accountId`；`/health` 只要 web server 活着就返回 200，即使数据库已断，查全量健康要用 `/ready`。**放在 SKILL.md 里**（agent 遇到前就先读到）；放独立文件也行但**必须说清何时加载**——非显然的问题 agent 认不出触发条件。**迭代法：每次你不得不纠正 agent 的一个错误，就把这条纠正写进 Gotchas**，这是最直接的改进路径。
- **输出格式给模板，不要用散文描述**：agent 对**具体结构**做模式匹配远比理解格式描述可靠。短模板内联在 SKILL.md；长模板或只在特定情况用的放 `assets/` 并在正文指明加载条件。
- **多步流程给显式 checklist**：`- [ ]` 勾选式（步骤名 + 该跑的命令/该改的文件），尤其是步骤间有依赖或验证关卡时，防跳步。
- **validation loop / plan-validate-execute**：① 干完活 → 跑校验器（脚本、参考清单或自检）→ 有错就修 → 再跑，**通过才继续**；② 批量或破坏性操作先产出**结构化中间计划**（如字段映射 JSON），**对源真相校验**（如"表单可用字段清单"），校验通过才执行——**第 ② 步的校验才是关键**：错误信息要具体到能自纠（"'signature_date' 不存在——可用字段：customer_name, order_total, signature_date_signed"）。
- **打包脚本的信号**：对比多个用例的执行轨迹，**若发现 agent 每次都在独立重造同一段逻辑**（画图、解析某格式、校验输出）→ 说明该写一个**测过的脚本**放进 `scripts/`，一次写好反复用。（与 §文件拆分"能被代码写死的用脚本"同一判据，这里是**发现时机**。）

## 评测执行纪律：干净上下文 / 快照基线 / 记 timing（来源：agentskills.io《Evaluating skills》2026-09-15 实拉）
本技能 §触发评测、§效果归因讲"测什么"；这里补"**怎么跑才作数**"：
- **每次运行必须从干净上下文开始**——不能带上一轮的残留状态，也不能带技能开发过程的上下文。否则**无法确定 agent 是按 SKILL.md 做的还是被前面的痕迹带的**，整个对照失效。支持子 agent 的宿主天然隔离（每个子任务全新）；否则**每次运行单开会话**。
- **改已有技能时，基线指向旧版本快照**：编辑前先 `cp -r <技能目录> <workspace>/skill-snapshot/`，基线跑指向快照、结果落 `old_skill/` 而非 `without_skill/`。**只跟"无技能"对比，测不出这次改动是改善还是退化。**
- **起步只要 2–3 条用例**：**在看到第一轮结果之前不要过度投入**，用例集随迭代扩张。
- **断言在看到第一轮结果之后再定**：第一轮只写 prompt + 期望输出（人类可读的"成功长什么样"）+ 可选输入文件；看到实际产出再补具体断言，避免凭空设计考纲。
- **用例结构与存放**：每条 = prompt / expected output / input files；存技能目录下 `evals/evals.json`；结果按 `iteration-N/<用例>/with_skill|without_skill/{outputs,timing,grading}.json` 组织，顶层 `benchmark.json` 做聚合。
- **必须记 timing（token 数 + 耗时）**：**"质量大幅提升但 token 翻三倍"和"既更好又更便宜"是两种完全不同的取舍**——只测质量不测代价，等于把负资产当成绩（与 §效果归因"增益要扣掉成本"同源）。
- **边界用例至少一条**：畸形输入、异常请求，或技能说明本身可能含糊的场景。


- **脚本放 `scripts/`**：能确定性执行的逻辑不要写成"让模型照着做"——脚本每次结果一致，描述性步骤每次可能不同
- **参考料放 `references/`**：长清单、模板、映射表按需读取，不常驻上下文
- **模板 / 素材放 `assets/`**
- 判据：**能被代码写死的用脚本，需要判断的留给 SKILL.md**
- **加载契约：只有路由加载，子文件互不加载**（来源：trailofbits/skills·mutation-testing SKILL.md，2026-09-15 实拉）——workflow 与 reference 由 SKILL.md 的路由表**成对指定**（选了哪个 workflow → 一并加载它列出的 references），子文件内部不写"另请参见 X"让加载决策层层扩散；**加载决策收敛在路由一处**，否则上下文涨多少不可控。配套判据：reference 按条件加载的（如"仅 Solidity 目标加载 blockchain-patterns"）在路由表里写明触发条件
- **跨工具调用间 shell 状态不持久**（来源：同上 second-opinion v2）：每次工具调用是独立 shell——本轮定义的变量下一轮就没了；后一轮要用，就**重新赋值到落盘路径再读**，不假设"刚才 export 过还在"

## 脚本通道纪律：stdout 是数据通道，日志必须走 stderr（来源 MCP 官方《Build an MCP server》2026-09-15 实访）
- **STDIO 型进程的 stdout 是协议/数据通道**：往 stdout 里 print 日志会**静默污染**协议流（MCP JSON-RPC 因此直接坏掉）；HTTP 型进程没这个约束。
- 正确姿势：日志统一走 `logging`（默认 stderr），每模块一个 logger（`getLogger(__name__)`）；**`print()` 在这类脚本里整个禁用**。
- 迁移到技能脚本：技能自带脚本若被其他程序/agent 以管道方式调用（读 stdout 当结果），同样适用——**调试信息、进度提示一律 stderr，stdout 只放交付数据**；否则调用方拿到的"结果"里混着日志，静默解析错位。
- 体检项：`grep -n "print(" scripts/*.py`——凡出现在管道调用脚本里的 print，先问"这是数据还是日志"，是日志就改 stderr。

## 组合三平面：展示 / 行为 / 知识严格分离（来源 GPT Store 构建方法论）
一个可部署的 agent / skill = 三个**正交**平面，把三者混用是最常见坏味道：
1. **展示配置（presentation）**：名称 / 描述 / 开场提示 / 图标——只影响"被发现、被怎么启动"，**不参与推理**；改这些不会让行为变聪明。
2. **行为（behavior）**：指令 / 规则 / 语气 / 工作流——定义"怎么思考、怎么回应、什么不做"，是真正的逻辑层；必须常驻且可查。
3. **知识（knowledge）**：上传的参考文件 / 外部语料——**只是被检索引用的源材料，永远不定义行为**。"把规则写进知识文件"是典型错配：知识文件不控行为，只供引用。
- **硬规则**：规则 / 语气 / 流程放行为层；参考素材放知识层；不要把参考材料当指令灌进行为核心（污染决策且难以审计）。
- **怎么分**：问一句"这条内容改了，会不会改变 agent 的推理？"——会→行为层；不会、只是被引用→知识层；只影响门面→展示层。
- 反模式：把长文档整篇塞进 system prompt（既撑爆上下文又模糊行为边界）；用知识文件当"隐藏指令"；展示字段写成长篇能力介绍却从不触发（见「description 怎么写」）。

## 另一种切法：按"谁来控制"分三积木（动作 / 数据 / 指令）

来源：MCP 官方《Understanding MCP servers》（2026-09-14 实访）。与上一节「展示/行为/知识三平面」互补——那是按**用途**分，这里是按**控制权**分：

| 积木 | 是什么 | **谁决定用不用** |
|---|---|---|
| **Tools（动作）** | 可执行的操作，**会产生副作用**（写库 / 调外部 API / 改文件 / 触发流程） | **模型**（它根据上下文自行决定调用） |
| **Resources（数据）** | 被动只读数据源（文件内容 / 库表结构 / API 文档） | **应用**（由程序决定给什么上下文） |
| **Prompts（指令）** | 预置的指令模板，说明如何配合特定工具与资源工作 | **用户**（人选/触发） |

- **关键在"谁控制"那一列**：**有副作用的那一类恰好是模型自己决定的**——所以才必须有"能拒绝的人"（见 `wb-spec-driven` §七·11）。**只读数据反而由应用控制**，因为那里没有不可逆风险。
- 落地判据：**给技能配能力时，先问"这项能力会不会改变外部状态"**——会，归 Tools，必须配可见性与拒绝通道；不会，归 Resources，可以放心常驻上下文。
- **一个工具只做一件事，输入输出类型明确并用 schema 校验**：动作面越窄，模型选错的空间越小。
- 与「指令 + 工具打包」合用：一个技能 = 指令（Prompts 层）+ 动作（Tools 层）+ 参考资料（Resources 层），三层各自的归属不同，别混在一起写。

## 版本号编码"兼容性"，废弃必须给迁移路径

来源：MCP 官方《Versioning》与 feature lifecycle（2026-09-14 实访）。

**1. 版本号该表达的是"这次改动会不会破坏现有用法"，不是"改了几次"。**
- MCP 的做法：版本号 = **最后一次不兼容变更的日期**；**只要保持向后兼容，就不递增**。
- 落到技能/脚本：**破坏性变更才动主版本**，措辞补充、新增可选小节、修错别字都不算破坏。否则版本号会变成一个只涨不说明任何事的计数器。
- 判据：**依赖它的东西不改代码还能正常用吗？** 能 → 不算破坏；不能 → 主版本 +1，并写清"什么变了、怎么改"。

**2. 兼容性按次协商，不是全局一次定死。**
- 每个请求自带版本标识，对端**按请求独立接受或拒绝**，明确返回"不支持该版本"而不是含糊失败。
- 允许同时支持多个版本——**过渡期里新旧并存是常态**，一刀切换才是事故来源。

**3. 废弃 ≠ 删除，是一段有承诺的过渡期。**
- 被标记废弃的东西**必须继续存在一段时间**（MCP 规定至少 12 个月，加速移除例外至少 90 天），给依赖方留出迁移窗口。
- **废弃时必须给出迁移路径，或者明确写"无需迁移"**——两条都不给就删，等于把成本全推给使用者。
- 与 `wb-ponytail`「删前先查它为什么在那」配套：**查完确认为废弃后，仍要走"标记 → 给路径 → 留窗口 → 才删"**，不能查完当天就删。

## 显式写出"不做什么"（non-scope），职责才不会膨胀

来源：MCP 官方《Architecture overview》（2026-09-14 实访）：*"MCP focuses solely on the protocol for context exchange—it does not dictate how AI applications use LLMs or manage the provided context."*

一份规范/技能最容易被侵蚀的地方，是**边界没人写、于是谁都可以往里加**。MCP 把"不管什么"写进正文第一屏，就是这个用途。

- **写技能时同样要写 non-scope**：本技能管 X，**不管** Y（Y 归谁）。例如本技能管"技能的写法与体检"，**不管**"从零新建（归 skill-creator）"、"长内容蒸馏（归 cangjie-skill）"。
- **判据**：下次想往里加内容时，先问"它落在 scope 里还是 non-scope 里"；落在 non-scope 但确实需要 → **指向负责它的那个技能**，而不是就地扩写。
- **负向边界（不适用于）是 non-scope 的用户面版本**：non-scope 说"不管什么"，负向边界说"什么情况别触发"。两个都要写。
- 反模式：技能越写越长，最后变成一个"什么都提一句"的杂物间——那不是全面，是失去了边界。

## 技能编码的是"选择依据"，不是操作步骤

来源：MCP 官方《Build with Agent Skills》（2026-09-14 实访）：*"they encode the design decisions (deployment model, tool patterns, auth) so your agent can interrogate your use case and scaffold a server that fits."*

**写"先点这里再点那里"的技能价值最低**——那种信息看文档就有。**技能真正该编码的是"什么时候该选哪一个"**：不同情况分别走哪条路、判断依据是什么、代价是什么。

- 自检：**把技能里的步骤全删掉，它还剩有价值的东西吗？** 只剩空壳 → 你在写操作手册，不是写技能。
- 写法：给出**选项 + 适用条件 + 代价**，让执行方按需情选择，而不是给一条唯一路径（唯一路径在情况一变就失效）。
- 与「STOP/WAIT/PROCEED 快速路径表」同源：那张表也是"选择依据"的一种形态。
- 反模式：技能写满 UI 操作步骤（换个版本就全错）；只给一条路不给判据（遇到边缘情况只能硬套）。

## 区分"谁写的内容"与"谁决定何时用"

来源：MCP 官方《Prompts》User Interaction Model（2026-09-14 实访）：*"Prompts are user-controlled… This refers to who decides when the prompt is used, not who authors its content. Prompt content is defined by the server."*

- **写内容的人和决定用它的人，经常不是同一个**。技能内容由我（或技能作者）写，但**何时触发由用户/路由机制决定**——不要因为"这是我写的"就认为"我可以决定何时执行"。
- **落到触发设计**：技能要能被**显式选中**（如斜杠命令 / 点名调用），而不只依赖模型自己判断要不要用。**用户能直接点名，触发才可控**；只靠语义匹配，就永远存在"该触发没触发"的灰区。
- 配套：每个请求自带元信息（我是谁、我支持什么、我用哪版），**不依赖握手时的一次约定**——这样任何一次调用单独看都是自解释的，排查时能直接定位"这次调用是什么环境发起的"。

## 换行符：技能文件必须 LF（跨平台的静默故障）
来源：agency-agents（279 个 agent 人设库）用 `.gitattributes` 强制 LF 的工程实践。
- **为什么**：技能靠 YAML frontmatter（`---` 包裹的 `name` / `description` / `version`）被发现和加载。CRLF 会让部分解析器读不到 frontmatter → **技能静默不加载、不报错、只是永远不触发**。这是最难排查的一类故障：文件在、内容对、就是不生效。
- **Windows 上的成因**：`core.autocrlf=true` 时，git 在 checkout 会把 `.md` 转成 CRLF。仓库若无 `.gitattributes`，下次 git 触碰该文件就会被转换（git 会明确警告 `LF will be replaced by CRLF`）——**此时文件往往仍是 LF，风险是预期性的，别等它炸**。
- **硬要求**：托管技能的仓库根目录放 `.gitattributes`，写入 `*.md text eol=lf`（需要时加 `*.yml` / `*.json`），让换行符不受本地 autocrlf 影响。
- **体检项**（并入「审计已启用技能」）：`git ls-files --eol <skill.md>` 看 `w/` 字段，`w/crlf` 即隐患。发现 CRLF 就地转 LF 再提交，不要只改内容。
- 反模式：只在自己这台机器上改好内容，不锁换行符 → 换机 / 重装 / 换工具后技能凭空不触发，且毫无报错可循。

## 改技能文件后：必须复核结构与版本（不只看 diff）
来源：2026-09-14 实际踩坑（在 `wb-context-compressor` 插入新段落时，`old_string` 只填了下一节的标题行，结果**把那个标题一起替换掉了** —— 正文变成上一节的一部分，节标题消失，肉眼不看目录根本发现不了）。

- **插入新段落时 `old_string` 必须带上下文**：不要只用"下一节的标题行"当锚点，要么把标题**写回 new_string 末尾**，要么连带上一节最后一行一起匹配。
- **改完固定跑一次结构复核**：`grep -nE '^## |^### ' <file>`，比对改动前后章节数；少一节就是删标题事故。改 description/frontmatter 的还要 `grep '^version:'` 确认版本号与内容同一次改完（**版本号与文件必须同一次编辑落地**，别事后补）。
- **改完再跑一次内容复核**：新段的标题、关键规则词要在磁盘上真的找得到（`grep` 一次），不靠"我记得写进去了"。
- 同一纪律适用于 AGENTS.md、报告、任何靠标题层级组织的长文档——**结构化文件的结构本身就是接口，静默丢失比内容写错更难发现**。

## 重命名必须全链路同步（改了名 ≠ 改完了）
来源：Make Help Center 的工具改名规则（2026-09-14 经代理实访）+ 本机真实故障样本。

**只要还有一处引用旧名，旧名就还在生效。** 本机实测：`claude-context-compressor` → `wb-context-compressor` 改名后，**长期报告表格里一直写着旧名**（还连带"插件"这个错口径留了很久），直到 2026-09-14 用户拿截图来问才发现——**改名漏同步可以潜伏两周以上**。

改名清单（逐项 **grep 打勾**，不靠记忆）：
- 目录名 + frontmatter `name`
- **引用它的其它技能**：分工表、description 里的"走 X / 转 X"
- `AGENTS.md`、用户级 `MEMORY.md` 的默认清单
- **长期文档**（如 `plugin-watch-report.md` 这类被反复读的文件）
- **自动化 prompt** 里的点名清单
- 记忆文件（automation memory、日记）

复核命令（命中数**必须为 0** 才算改完）：
```bash
grep -rn "<旧名>" ~/.workbuddy/skills /c/Users/26719/.workbuddy/AGENTS.md "D:/AI技能仓库"
```
- **判定：「改名」的完成标志不是新名生效，是旧名再也搜不到。**
- 旧名要留历史痕迹时，**紧挨着写"现名 = X"**——历史记录可以提旧名，但读者要能一眼对上，否则下一个人会照着旧名去找。
- 同理适用于：技能合并（被合掉的旧技能名要在原引用处改成新名）、接口 / 参数 / 环境变量改名（改完必须回头同步文档与调用点）。

## 跨工具迁移
- 核心约束（触发条件、硬性规则、收尾动作）必须写在 SKILL.md 内，不依赖某个工具的插件 / hook 机制——换工具就失效的约束等于没写
- 工具特有的能力（如某工具的专属工具调用）在正文里显式标注为“仅 X 下适用”，并给出降级做法
- 迁移后必查：路径分隔符、命令是否跨平台、编码是否 UTF-8、**换行符是否 LF**

## 安装前安全审查（第三方 skill）
按 P0 / P1 / P2 分级，先审 `SKILL.md` 再审 `scripts/`：
- **P0（拒绝安装）**：读取 / 外发凭证或密钥、`rm -rf` 或等价的无确认删除、向未知域名上传本地文件、静默改系统配置
- **P1（警告后确认）**：外部网络请求、写用户目录之外、调用 shell 执行下载内容、`sudo` / 提权、**破坏性操作缺守卫**（`rmtree` / 覆盖前不校验目标是否为该技能自己的产物目录，`--target` 传错即可删掉任意目录）
- **P2（可安装）**：纯本地读写、只读查询、明确作用域内的文件操作
- 审查只看**实际会执行的代码**，不采信 SKILL.md 里的自我声明
- **先看注册表侧信号**（来源：ClawHub 注册表机制）：市场类来源安装前查平台公开的**安全扫描摘要、版本历史、changelog 与下载量/星标**——扫描被 hold 或被 block 的包会从公开目录消失但可能仍可装；发布门禁（如要求账号年龄）的说明也是供应链信任信号之一
- **单技能过检 ≠ 安全：必须做组合链审查**（来源：arXiv 2608.16246《CompoSkill: Compositional Skill Chain Attacks from Individually Scanner-Passing LLM Agent Skills》，2026-09-16 实拉）：恶意技能的常见形态是**每个技能单独过扫描器、组合成链才成为攻击**——CompoSkill 在 OpenClaw/Nanobot 上 5 类威胁、6 场景、1140 条长程工作流中，风险链形成率高达 83.3%（白盒）/80.6%（黑盒），而现有单技能扫描器只拦下有限比例的组合风险。判据：**批量安装/让 agent 调用多个技能时，除单技能 P0/P1/P2 审查外，必须跑一遍"组合链"检查**——把同批技能串起来读，看 A 技能的输出是否变成 B 技能的注入/逃逸输入（如：A 抓取网页内容 → B 无条件执行其中命令；A 读文件 → B 把内容外发），形成"单点无害、串联有害"的链就按 P0 处理。
- **纵深三原则（来源：PostHog 攻防实录，latestllm.com 2026-09-15 实拉）**：① **系统提示词不是安全边界**——注入可经"无辜"文件（如 PR 里的 markdown）进入上下文，任何安全要求都必须在工具/执行层有确定性兜底，不能只靠 prompt 措辞；② **确定性工具优先于概率性判断**——扫描/校验类用 YARA 式确定性规则，不用 LLM 猜（与"护栏执行化"同构）；③ **安全层"建议"而非"强制"，且必须 fail closed**——拿不准就拒绝执行/停止，不默认放行。
- **高风险动作 human-in-the-loop 批准（来源：AI Buzz《Prompt Injection Explained》2026-09-10 实拉）**：发邮件、写文件、外部 API 调用、金融交易等**不可逆现实动作**必须人工批准——这是 agentic AI 最有效的爆炸半径控制，防止注入指令自动触发不可逆操作。配套：**记录全部工具调用带完整上下文**（哪个工具、什么参数、由什么输入触发），无此日志事后无法取证。

**发现 P1 且能用几行代码消掉风险时，就地修掉再装，不要只写警告**（2026-09-12 实测：`cangjie-skill` 的 `apply_skill_patch.py` / `cangjie.py rollback` 会对 `--target` 直接 `rmtree`，已补 `assert_safe_skill_target()` 守卫——拒绝盘根 / 用户主目录 / 顶层无 `SKILL.md` 的目录，并附行为测试）。留痕写一行，标明是本地补丁，避免把改动误当成上游行为。

## 审计已启用技能（定期体检清单）
用户 2026-09-12 强制要求：定期审计用户级 `skills/` 下每个已启用技能，找出并修正——**拼写错误 / 乱码 / 过时信息 / 失效工具名 / 与新环境不匹配的描述**。复用本清单（每项具体动作）：
- **拼写 / 乱码**：逐文件扫 frontmatter 与正文；控制台 GBK 误显示的"鑱旂綉"类乱码是**显示问题不是文件损坏**，用 Read 复核 UTF-8 原文，别把显示乱码当文件损坏去"修"
- **失效工具名**：检查 `allowed-tools` 与正文指令里的工具 / 命令名是否本环境真实存在（`command -v <x>` 验；如 `read_file` / `write_file` 在本环境不存在，应用 `Read` / `Write` / `Edit`；`openclaw` 等第三方 CLI 本环境无 = 环境不匹配，加注"本环境不可用"而非删命令）

**凭据硬编码扫描**（来源 `workbuddy-health-check` 唯一独有维度）：审计时**必跑**——全库 grep 所有 `SKILL.md` 与 `scripts/` 找 `api_key` / `token` / `secret` / `password` / `cookie` / `AKID` 等硬编码；发现即清除或转环境变量，**绝不入仓**（`.gitignore` 已排除 `~/.ssh/` 与 12306 cookies，不得移除该排除）。
- 评分维度（来源 `darwin-skill`，只取评分部分，不装整包）：触发准确率 / 描述质量 / 实际调用率 / 覆盖完整性 / 时效性 / 安全 / 可维护性 / 复用价值——按**棘轮**原则只升不降地改进（本地追踪），评分不是为了好看，是为了决定"该保留 / 该删 / 该并"。

## 技能归属权：一个技能同一时刻只有一个 owner 可写（来源：OpenClaw 2026.9.3「Persistent skills have an owner / Skill Workshop」，2026-09-16 实拉）
多 agent / 多 workspace 共享技能库时，**每个技能必须声明 owner（归属）**——谁是唯一可修改者；无主技能 = 人人可写 = 并发覆盖事故（对应 WorkBuddy 同时工作问题：同文件双写互踩）。
- **判据**：技能 frontmatter 或治理表里显式写 owner（agent / 用户 / 组）；修改前先确认"我是这个技能的 owner 吗"；**同一文件同一时刻只有一个写者**，非 owner 只能提改动建议、由 owner 合入。
- 与 §审计的配合：审计时顺带核对 owner 声明是否还在、是否与当前分工一致。
- 反模式：两人同时 Edit 同一 SKILL.md（后写覆盖先写、无锁无提示）；或技能无主、谁都能改，改了没人知道。
- **并行写隔离的工程化实现：git worktree（来源：Orca 59K★，agentconn.com 2026-09-01 实拉）**——多 agent 需要同时推进同一仓库时，**给每个 agent 建独立 worktree**（`git worktree add ../repo-<agent> <branch>`），各 agent 在自己的分支/工作树里写，互不产生 index.lock 与覆盖冲突，完成后再逐分支合并回主干。判据：**并发写同一仓库时 worktree 隔离 > 同目录轮流写**；单写者时不需要 worktree，直接主线写。与"同一文件单写者"配合：worktree 解决文件系统级冲突，owner 声明解决逻辑级归属，两者都要。

## 知识库编译为可导航技能目录树：用导航替代检索（来源：arXiv 2604.14572《Don't Retrieve, Navigate: Distilling Enterprise Knowledge into Navigable Agent Skills》，2026-09-16 实拉）
文档语料不一定要"检索"，可以**离线编译成层级技能目录树**：聚类文档 → 每层生成 LLM 摘要 → 物化成树形技能文件。服务时 agent 先看鸟瞰图、按分支渐进钻取更细摘要、需要全文才按 ID 取——**导航替代向量检索**。
- **判据**：面对大知识库（手册/语料/资料库），优先把库编译成"技能树"（目录节点=摘要技能、叶节点=文档 ID），让 agent 导航式访问，而不是每次全量向量检索；技能树的每个节点都应是可独立调用的技能文件。
- 与 §技能文件拆分的配合：文件拆分是"单个技能怎么拆"，本条是"整个知识库怎么组织成技能层"——上层鸟瞰、中层摘要、底层全文 ID。
- 反模式：把整库塞进一个技能/一个上下文（导航时找不到）；或坚持向量检索但库大、检索噪声高（导航树的确定性强于 embedding 相似度）。

## 技能/插件更新治理：隔离彩排 → 兼容验证 → 可回滚（来源：OpenClaw 2026.9.3「isolated candidate-state rehearsals」+ 2026.9.4「safe rollback from compatible failed updates」，2026-09-16 实拉）
更新技能/插件不能"改完就上线"：
- **隔离彩排（candidate-state rehearsal）**：更新先在隔离候选态跑一遍验证（核心功能在副本上跑通），通过才正式切换。
- **兼容性验证**：更新前核对破坏性变更（版本号语义、接口/工具签名变化），按"按次协商版本"既有规则处理。
- **可回滚**：更新失败要能安全回滚到可用版本——更新动作与旧版本快照解耦，失败即回退。
- 与用户偏好"更新须授权且不损原有优点"的配合：授权在切换前拿，彩排+回滚保证切换后能兜底。
- 反模式：改完直接覆盖上线（坏版本污染所有后续使用）；或更新失败后无回滚路径、只能手动返工。

## 技能质量硬杠（VoltAgent 策展标准）
来源：GitHub `VoltAgent/awesome-agent-skills` 的 README 内联质量条款（1000+ 官方 Skills 策展清单）。本库写 skill / 审计时逐项打勾；不满足不上线：
- **description 约 100 token 以内**：常驻字段，必须一次读完；太长会吃常驻上下文，触发时也抓不住重点
- **三句描述**：何时用 / 做什么 / 边界或不做什么；禁止写小作文或能力介绍
- **SKILL.md body ≤ 500 行**：正文必须能被一次读完；超过 → 拆 `references/` 长清单、`scripts/` 确定性逻辑、`assets/` 模板；禁止正文里塞参考资料
- **禁绝对路径**：正文 / 脚本里不写 `C:\` / `/Users/` / `~/.x` 等硬编码绝对路径；必须走相对路径、环境变量或技能约定目录，否则换机器/换账号失效
- **tools 作用域化**：`allowed-tools` 与正文只声明本技能真实会用的工具；禁止罗列"可能用到"的全局工具；`scripts/` 里不得调用超出 skill 自解释范围的系统命令
- **提示词质量评分维度**（来源：LobeHub `afrexai/prompt-engineering` 技能评分卡，2026-09-16 实拉）：写提示词/技能正文时按以下加权自查，逐项打勾，不满足不上线——**示例 ≥2 组 input→output 对（15）**、**错误处理有明确失败路径（10）**、**输出格式结构已指定（10）**、**语气一致（10）**、**无冗余或矛盾指令（5）**；余下为上下文/边界等维度。判据：**"至少 2 组输入输出示例"是硬门槛**——1 组太少（只覆盖一条路径），0 组是许愿式提问。

## 安装前安全审查：补查"身份与授权的作用域"

来源：MCP 官方《Security Best Practices》Confused Deputy（2026-09-14 实访）。

审第三方技能/工具时，除了看它读写什么，还要问**它拿谁的身份在做事**：

- **它是否用共享/固定的身份替多方执行动作？** 是 → 存在混淆代理风险，要求它按调用方区分授权。
- **它的同意/授权是一次性的还是按次取得的？** 缓存的同意会被后来的调用方搭便车。
- **凭据作用域**：拿到的是"能读能执行"还是"连配置都能改"？能只读+执行就不该给可改配置（与 `wb-context-compressor`「授权范围也属于暴露面」同构）。
- **它会不会把某次成功的授权复用到别的用途上？** 授权是有范围的，"同意过一次"不等于"什么都可以"。

## 安装后必须接线（用户 2026-09-12 强制：**装了不调用 = 没装**）
技能装完 / 写完**不算完成**，必须当轮让它"下次会被扫到并真被用上"：
1. **写相邻分工**：在职责最接近的既有技能里加一行路由（例："长内容蒸馏 → `cangjie-skill`"）。不写 → 任务来了仍走旧路径
2. **触发词互补**：新技能 description 覆盖用户的实际说法；若旧技能也会被同一说法触发，在旧技能里注明"此类转 X"，避免抢触发
3. **验证扫得到**：`ls -1 ~/.workbuddy/skills/` 复核目录在 + 读 SKILL.md 前 20 行确认 frontmatter 的 `name` / `description` 完整（缺 `---` 分隔或 name 拼错 = 系统清单里扫不到）
4. **留痕一行**：装了什么 → 接到了哪里（写进当日 memory）
- **反模式**：装完只更新记录、不写路由 → 下次任务照旧走老路，等于没装（实测教训：`cangjie-skill`、`wb-debug-loop` 都曾被"装了但没接线"）

## 去重与合并流程（用户 2026-09-11 强制：「重复的都删」「去坏存好结合」）
发现两个技能同一功能位重叠时，**按固定顺序走完，不能只删不并**：

1. **先查同类**：在全量技能里按"功能"而非"名字"找同类（名字不同、干同一件事的就是同类）
2. **列各自的好与坏**：逐条列出两边**独有的好点**（能力/触发词/脚本/边界判断）与**坏点**（依赖不可用服务、过时、空泛、被更优实现取代）
3. **合并成新的**：新建一个技能，**把双方的好点都装进去**——被删方的好点必须显式落进新技能（写清来源，便于回溯），不能"删了就没了"
4. **触发词取并集**：两边 description 里的触发词合并，否则原来的用户说法会失配
5. **删掉被覆盖的**：旧目录直接删，**不额外备份**（本地 git 历史即可回溯）
6. **删后查引用**：全库搜被删名字，修掉悬空引用（技能正文、规则文件、自动化 prompt）
7. **留痕**：一行记录（合并了谁+谁 → 新技能名 / 删了什么 + 理由）

**硬判据**
- **同轮完成**（用户 2026-09-12 强调）：合并与删除必须在**同一轮内一起做完**。写下"已被 X 吸收 / 待删 / 暂不视为独立技能"却留着目录 = 没做；做完必须 `ls` 复核。
- **不确定是否重复时按重复处理**：先合后删，不要两个并列。
- **不并列保留**：同一功能位只允许一个技能。哪怕"各走不同服务"也是并列——应做成同一技能内的多条路径
- **不动**平台内置与插件市场纳管的技能（各有管家），但可向用户指出其重叠
- **非同类不合并**：只要不干同一件事，即使风格相近也不碰（如确定性图像编辑 vs AI 生成式修图）

## 反模式
- description 写成能力介绍（"这是一个帮助用户处理文件的技能"）→ 不触发
- 把长流程塞进 description → 常驻上下文被白白占掉
- 能确定性执行的步骤写成"让模型自行判断" → 每次结果不一致
- 约束只写在正文、不写 description → 该拦的没拦住
- 装 skill 只看名字不看脚本 → 引入 P0 风险
- 两个 skill 职责重叠还并列保留 → 触发时二选一，行为不稳定（应合并）

## 规则（技能条目）的生命周期：成文、磨尖、退役都要带出处（2026-09-15 来源 principal-engineer principal-engineering）
技能里的规则不是只进不出的存货：**咬两次 → 成文**，且必须记录出处（发生了什么事故、何时、如何避免）；**持续触发 → 磨尖**（表述收紧、触发词补全）；**根因已修 → 退役删除**。出处记录是关键：它同时防止两条失败——没出处的规则被 cargo-cult 照抄（不知为何存在、不敢动），以及根因消失后规则被误删前没人知道它当初为什么写。退役时同样留一行"已修根因"的变更记录，便于回溯。

## 信任标签不可自封：保留词一律拒绝（来源：OpenClaw 官方 docs.openclaw.ai·clawhub/publishing，2026-09-15 实拉）
注册中心会**保留一批信任词**（approved / audited / certified / verified / trusted / official / featured / staff-pick / curated / endorsed 一类），作者不得把它们写进名称、标签或描述。
- 校验在**归一化之后**做：大小写、空格、连字符变体一样拒绝（`Official`、`staff pick` 与 `official` 同判）。
- 判据：**信任是第三方授予的，不是自我声明的**；允许自封等于让"已审计"这个信号失效。
- 迁移到自有技能库：给技能打"已验证 / 已审计"标记时，必须写明**谁在什么时候用什么判据验的**；没有这一行的标记不许出现。
- 同类规则：分类标签必须取自**受控词表**（未知值直接失败），自由标签走另一个字段；**受控词表与自由标签混在一个字段里，迟早会被当成受控词表来读**。

## 预览不做全部校验：dry-run 通过 ≠ 真的能过（同源）
`--dry-run` 一类的预览**只覆盖一部分校验**（例：不校验受控词表取值，真实发布时才校验）。
- 判据：**预览是给"会不会被发现改动"看的，不是给"会不会被接受"背书**。要确认能否通过，必须走真实通道或明确指出"哪些规则在预览阶段不跑"。
- 与 `wb-execute-discipline`「预览不是计划」分工：那条管**预览不落地**，这条管**预览不保真**。

## 审计结论看"一致性"，不看"有没有用危险能力"（来源：OpenClaw 官方 docs.openclaw.ai·clawhub/security-audits，2026-09-15 实拉）
审查第三方技能时，主问题是 **coherence**：名称、摘要、元数据、申请的权限、实际内容，是否彼此对得上、是否符合用户合理预期。
- **强力行为不等于恶意**：需要凭证、能跑命令、能调外部 API 的技能照样可以正当；判据是**是否披露、是否目的相符、是否与声明用途相称**。
- 结论按**双轴**读：**权力有多大**（影响面）× **该拿它怎么办**（处置）。`Pass` 只是"没发现高于低危的问题"，**不替代自己的判断**——尤其对能发内容、能改数据、能跑命令的技能。
- 低置信发现不进公开汇总：汇总只留有把握的证据，**噪声会淹没信号**，但这不意味着被隐藏的那部分"不存在"。

## 安全审查进阶：攻击链推理与静态指标库（来源：腾讯朱雀实验室 A.I.G / OWASP Agentic Skills Top 10，2026-09-15 实拉）

`skill-scanner`（朱雀实验室 A.I.G 出品）对 5 万+ Skill 的全量扫描，把"安装前安全审查"从一份分级清单升级成**攻击链推理**——这是本技能 P0/P1/P2 之外的关键增量，只取独有点：

- **组合风险 ≠ 单点风险之和**：单个动作（远程拉取、反序列化、多层编码解码）各自都"合理"，但拼起来就是完整 RCE 链路。**判据：不只看每个动作危不危险，要看多个高风险动作能否拼成一条攻击链**（`curl|bash` 下载即执行 + 读 `.ssh`/`.env` + `eval` 动态构建命令 + 反连通道 = 投毒）。
- **静态指标库（直接补进 P0/P1 清单）**：`curl | bash` / 下载即执行、读 `~/.ssh` `~/.aws` `.env`、base64 解码后执行、`eval` 动态拼命令、反向 shell 模式、SKILL.md 里**伪装成正常描述的隐藏指令**、权限组合（文件读 + 网络外传 = 完整数据外泄路径）。这些线索只是"参考信号"，最终结论交给语义推理。
- **核心审计问题**："这个技能**实际做的**，和它**声称要做的**，一不一样？"（M3 Skill-Scan 的灵魂一问）——比 coherence（一致性）更深一层：声明用途合理 ≠ 实现没越界。
- **流行度 ≠ 安全**（流行度-安全性悖论）：高下载量 Skill 的安全性并不优于低下载量；ClawHavoc 曾 1184 个恶意 Skill 获 24.7 万次安装。**判据：不因为"很多人装"就跳过审查，下载量不是信任信号。**

## 装载侧的宽容与边界（来源：agentskills.io《Adding skills support》，2026-09-15 实拉）
- **宽容校验**：名称与目录名不一致、名称超长 → **告警但仍加载**（为跨客户端兼容）；描述缺失/为空、YAML 完全不可解析 → **跳过并记日志**。判据：**缺了"何时用"的技能无法被正确触发，必须跳过；长得不规范但能用，不该拦。**
- **被过滤的技能整条隐藏**，不要列出来再在激活时拦截——模型会反复尝试加载它，白白烧轮次。
- **没有技能时不显示空目录、不注册无选项的工具**：空壳会让模型以为自己漏看了什么。
- 激活工具的 `name` 参数用**枚举约束到实际存在的技能名**，防幻觉出不存在的技能。
- **项目级技能来自可能不可信的仓库**：加载前做信任门禁，否则"克隆一个开源项目"就等于"允许它向 agent 上下文注入指令"。
- 同名冲突按**项目级覆盖用户级**处理，并**记一条告警告诉用户哪个被遮蔽了**（遮蔽不可见 = 排障噩梦）。

## 断言的质量：能验证、能观察、能计数（来源：agentskills.io《Evaluating skill output quality》，2026-09-15 实拉全文）
- 好断言三特征：**可程序化验证**（"输出是合法 JSON"）/ **具体可观察**（"图表两个轴都标了"）/ **可计数**（"至少 3 条建议"）。
- 弱断言两种：**太模糊**（"输出不错"——没法判）/ **太脆**（"必须出现字符串 'Total Revenue: $X'"——换个说法就误判 FAIL）。脆断言会惩罚正确输出，比没有断言更糟。
- **PASS 必须附可引用证据**（引用输出本身：找到哪个文件、哪句话、缺了什么），**不给宽限**：标题是 "Summary" 但只有一句空话 = FAIL（标签在，实质不在）。
- **不是所有东西都配断言**：写作风格、视觉观感、"感觉对不对" 拆不成通过/失败 —— 这些留给人工复核，硬写断言只会得到一堆噪声。**断言只留给能客观核对的项**。

## 断言本身也要评审：先修考纲，再改技能（同源）
聚合之后的四类信号，处理动作各不相同：
- **两边都过的断言 → 删掉或换掉**：它对衡量技能价值毫无贡献，只会虚高通过率（与 `wb-artifact-verification`「指标必须带口径」同源）。
- **两边都挂的断言 → 先查断言**：是断言错了（要求了模型做不到的事）、用例太难、还是查错了东西，修完再跑。
- **只有带技能才过的断言 → 这是技能真正的价值所在**：反查是哪条指令/哪个脚本起的作用，把它写稳、写清楚。
- **跨轮结果不稳（stddev 高）→ 收紧指令消歧义**，别急着加规则；**耗时/token 离群 → 去读该轮执行 transcript** 找瓶颈（慢在哪里，一看就知道）。
- 注：**stddev 只在同用例跑多次时才有意义**；早期 2–3 条用例、每轮单跑时只看原始通过数与 delta，别拿统计量装样子。

## 两版对比用盲评：断言打不平的差距靠它（同源）
- **盲评（blind comparison）**：把两个版本的输出同时交给评委，**不透露哪个来自哪个版本**，让它按自己的标尺评组织/格式/可用性/完成度。
- 它补的是断言的盲区：**两份输出可能全过断言，整体质量却差一大截**；反过来断言能抓住盲评说不细的机械项。两者是互补不是替代。

## 迭代的停止条件（同源）
三类信号收敛后再决定停不停：**失败断言**（具体缺口）/ **人工反馈**（方向性问题）/ **执行 transcript**（为什么会走偏）。
- 停止信号：**反馈持续为空**、或**相邻两轮没有实质改善** —— 继续迭代只是在烧轮次和制造波动。
- 人工反馈要**可行动**："X 轴没标、月份按字母序排了" 是能改的；"看着不太行" 不是。空反馈即通过（不用脑补意见）。

## 复盘发现先分型：机械型建检查，判断型才写规则（来源：GitHub `mattpocock/skills` PR #1083「retro: push mechanical coding-standards findings toward deterministic checks」，2026-09-15 实拉 commit message）
- 复盘/评审出一条发现时，**先判它是固定句法模式（机械型）还是需要人判断（判断型）**：
  - **机械型 → 默认去建一条确定性检查**（lint / CI / 测试），一次付费，之后每个 diff 自动判；
  - **判断型 → 才写进规则文档**（CODING_STANDARDS / SKILL.md）。
- 反例就是"每发现一次就加一行规则"：那是让未来的评审者**每次重新推一遍同一个结论，永远重复付费**。
- **没有自动检查设施本身就是一条发现**（仓库既无 pre-commit 也无跑 lint/typecheck/test 的 CI），不要等它导致具体错误才算 —— 与 `wb-artifact-verification`「未扫描是一等状态」同源。
- 分型表述要**保持语言中立**（不写成 ESLint/ts 专有说法），否则换个语言栈就失效。

## 分发到多个 CLI：一份工作树 + 非破坏安装（来源：GitHub `simota/agent-skills` README，skills.sh /hot 本轮新源，2026-09-15 实拉）
- **单一真源**：一份 git 工作树，symlink 到各 CLI 的技能目录；一次 `git pull` 全平台同步，避免 N 份副本各自漂移。
- **非破坏**：目标里**已存在的同名技能 → 报告并跳过，绝不覆盖**（覆盖等于悄悄毁掉用户已有的东西）；目标 CLI 没装 → 跳过该平台，不报错中断。
- **卸载只删自己建的链接**，别人的技能与自定义别名保持原样 —— 清理动作的作用域必须等于安装动作的作用域。
- **全局 vs 项目本地分层**：仓库专属的"操作型"技能**不进全局花名册**（否则每个项目都被塞进无关能力），放在项目本地目录并单独计数。

## 生态清理：审计只出提案，执行要分离（来源：同源 `Prune` agent 定义）
- 审计技能生态（重叠 / 冗余 / 长期不活跃）的产出是**提案**：含合并候选、下线计划、**证据**、以及归档说明。
- **审计者不自己执行删除**（propose-only）—— 让同一个角色既判"该删"又动手删，误判就没有第二次检查。
- 执行删除前走 `wb-execute-discipline` 的确认与留痕；删完 `ls` 复核（本文件 §去重与合并流程 已强制）。

## 技能生命周期五层管理：本机目录按状态分层，装完不等于在用（来源：OoderAgent，MIT，内置 137+ 技能，2026-09-14 学习轮实拉）

技能在本机不该只有一个"装没装"的布尔状态。OoderAgent 把技能目录按生命周期显式分五层，状态可见、审计可数：

| 层 | 含义 | 该层里的技能什么状态 |
|---|---|---|
| `downloads/` | 下载暂存 | 已拉下来、**还没审**（未过安装前安全审查 P0/P1/P2，不许进 installed） |
| `installed/` | 已安装 | 已审、已落盘，**但未激活**（description 不被路由加载） |
| `activated/` | 已激活 | 正在用（description 参与路由，触发即执行） |
| `dev/` | 开发中 | 自己正在写/改的技能（未到发布标准，不占路由位） |
| `cache/` | 缓存 | 运行时缓存与临时产物（随时可清，不入版本管理） |

- **核心判据**：目录结构本身就是状态机。`installed` 与 `activated` 分离解决了"装了但没接线"（本技能 §安装后必须接线）的不可见性——**装完只放 installed = 审计时一眼看出没激活**，不必靠翻记忆。
- **与相邻条目的分工**：§分发到多个 CLI（simota）管**跨 CLI**怎么同步一份工作树；本条管**本机单侧**技能目录怎么按状态分层。§安装前安全审查管"能不能装"，本条管"装完放哪层"。三者互补不重叠。
- **落地判据**：给技能库做体检时，按层计数（downloads 有几个没审、installed 有几个没激活、activated 有几个长期零触发）——把"技能堆积"变成可数的数字；activated 里长期零触发的按 §触发率×有效性处理。
- **回滚/升级有据**：dev 与 cache 分离后，改技能期间旧版本仍在 activated，改完再替换——天然是"先备后切"。

## 技能结构体检：目录里的每一样东西都要有存在理由（来源：GitHub `richtabor/agent-skills`·`skill-review`，2026-09-15 实拉）
- **`references/` 只一层深**，不做嵌套引用链（A 引 B 引 C = 模型要跑三段才拿到内容，且断链不可见）。
- **技能目录不塞杂物**：`README.md` / `CHANGELOG.md` / 安装说明这类文件不进技能目录 —— 它们会被当可选资源列出，既占目录又诱发幻觉式加载。
- **正文里写的脚本路径必须真实存在**（`scripts/foo.py` 要能在目录里找到）；**用到外部二进制必须写明依赖**（否则换个环境就是静默失败）。
- **路径一律正斜杠**，不写 Windows 反斜杠（与 §换行符 同源：跨平台的静默故障）。
- **信源分歧（如实记录）**：description 的人称，官方 agentskills 倾向**祈使/强势动作表述**，第三方实践（本源）要求**第三人称**、禁止 "I can / You can"。**两者共同且无争议的部分**：必须同时说清「做什么」和「什么时候用」，并带具体触发短语与用户同义说法——按这条执行，人称按所用平台的校验器要求定。

## 处理外部评审意见：先核当前状态，再分三类（来源：同源 `review-pr`，2026-09-15 实拉）
- **评审意见本身也要先验证**：意见常引用**过期行号 / 已被后续提交改掉的代码 / 误读的逻辑**。动手前先读当前代码，核对"这条意见说的还是不是真的"。
- 三类处置，每条都要给理由：
  1. **已处理（Already addressed）**：后续提交已修，或评审者看错了 → 回复时说明代码实际在做什么；
  2. **要改（Fix）**：当前代码里确实存在的缺陷/安全问题/笔误 → 改；
  3. **不改（Won't fix）**：过度设计、纯风格偏好、属于新需求、或改了会破坏既有一致性 → 写清原因，**不默默跳过**。
- 判据：**"不改"必须留下可被复核的理由**，否则下一次评审还会再提一遍同样的意见（与 §规则生命周期「成文、磨尖、退役都要带出处」同源）。

## 体检项/检查规则自身要按误报率校准（来源：GitHub `simota/agent-skills` 的 `gauge`，2026-09-16 实拉）
写了一套检查清单或自动体检规则之后，**规则本身会随时间失真**——把"规则还在跑"当成"规则还有效"是最常见的自欺。
- **逐条规则监控误报率与漏报率**，任一条误报率超过阈值（该源取 15%）就**重校或退役该条**，不是加个例外绕过。判据：**一条老误报的规则会训练使用者忽略所有规则**，损失的是整份清单的可信度。
- **漂移用稳定度指数分级**：同一对象两次扫描的合规分差异 **<10% 视为稳定 / 10–20% 排查 / >20% 介入**。为什么看差值不看绝对值：**绝对值低可能一直是低（稳定的差），差值大才是"刚刚变坏了"**，后者才有信息量。
- **正文质量用"显而易见密度"衡量**（该源 CQ1）：技能/文档正文里**读者不看也知道的内容占比**越高，性价比越低——把篇幅让给"不看就不知道"的部分。配合 CQ2：**description 里有没有真正的触发词**（用户的同义说法），没有就等于技能不会被调用。
- **体检者只出建议不改文件**（该源原则：绝不直接编辑 SKILL.md）——**测量与修改分离**，否则既当裁判又当运动员，规则会被自己的改动带偏。
- 与 §规则生命周期「成文、磨尖、退役都要带出处」配套：那条管**规则从哪来**，这条管**规则什么时候该走**。

## 官方口径补四点：命名、跨模型测试、时效信息、双实例迭代（来源：Anthropic 官方 `docs.claude.com/.../agent-skills/best-practices`，经 VPN 实拉 1.17MB 原文，2026-09-16）
与 agentskills.io 规范互补，取本地尚未收录的四条：
1. **命名用动名词（-ing），并避开平台保留词**（如 `anthropic` / `claude`）：动名词直接说明"这是一项什么活动"，**命名一致才能被引用、被检索、被讨论**——同一套技能里混用名词/动词/形容词，会让人（和模型）无法凭名字判断用途。
2. **同一技能要在"计划支持的每个模型档"上各测一遍，且每档问不同的问题**：**小模型问"够不够细"**（它缺的是指引）、**中档问"清不清楚、省不省"**、**强推理模型问"有没有过度解释"**。同一份指令在一种模型上完美、在另一种上可能完全不够用——**没跨模型测过就宣称通用，是没测**。
3. **会腐烂的信息不进正文，降级到"旧模式/legacy"区**：不写"2025 年 8 月前用旧 API"这类**以当前时间为参照**的句子（今天对、明天错，且错得毫无提示）。改为正文只讲当下做法，历史做法进 legacy 区并**标注废弃时间**。参考文件**超过 100 行要加目录**——模型可能只读到一部分，没有目录它就看不到后面还有什么。
4. **开发与试用拆成两个实例（A 写、B 用）**：一个实例当**作者**（据此改技能），另一个**全新实例当使用者**在真实任务里跑；**观察 B 的实际行为 → 把具体现象带回 A**（"B 出区域报表时忘了过滤测试账号"）→ A 改 → B 再跑。判据：**迭代依据必须是 B 的真实行为，不是 A 的想象**；A 既写又用会一直觉得自己写的很清楚。抽取技能的正确顺序也是**先真做一次任务，再回头抽可复用模式**，不是凭空写文档。
- **description 人称分歧收口（补充 §信源分歧）**：本官方页明确要求**一律第三人称**（"Processes Excel files…"，禁 "I can / You can"），理由是 description 被注入系统提示、人称不一致会影响发现。此前记录的"官方祈使/强势 vs 第三方第三人称"至此有了一手出处——**按所用平台校验器的要求定人称，"做什么 + 何时用"这条共识不变**。

## 用真实历史会话给技能打分，且语料不许出本机（来源：GitHub `warpdotdev/common-skills` 的 `skill-doctor`，2026-09-16 实拉）
评估技能不要只造测试题——**最真实的评测语料是你自己过去那批真会话**。
- 做法：从本地会话历史里抽取近期任务，按**效率**（有没有走弯路、重复读同一份东西、绕远路）与**产出质量**两套 rubric 打分，再据此起草具体的技能改动与一份报告。判据：**"装了但没被用上""用了但没帮上忙"这两类失效，只有在真会话里才看得见**，人造用例测不出来。
- **隐私硬约束**：会话记录、transcript、任何片段**一律只在本机处理，绝不上传**；**唯一可以外发的只有聚合后的报告**，且由用户自己决定发不发。
- **不污染用户仓库**：评测产物**不写进被测项目**；**每次运行新建一个无碰撞的临时目录**当工作区（不是"用完再删"的承诺，是从一开始就不落在别人的地盘上）。

## 脚本给 agent 用的接口设计：非交互 / --help 即契约 / 输出体积可预测（来源：agentskills.io《Using scripts in skills》，2026-09-16 实拉）
`scripts/` 里的脚本不是给人敲的，是给 agent 调的——agent 靠 stdout、stderr、退出码和 `--help` 决定下一步，接口设计的每一处都直接变成它的行为。
- **禁止交互式提示（硬要求）**：agent 跑在非交互 shell 里，**等 TTY 输入 = 永久挂起**（不报错、不超时，就那么卡住）。所有输入走命令行 flag / 环境变量 / stdin；**缺参数要给"错在哪 + 可选值 + 用法"**（`Error: --env is required. Options: development, staging, production.` + Usage 行），不是空等也不是一句 `invalid input`。
- **`--help` 就是接口契约**：agent 学一个脚本怎么用，主要靠 `--help`。必须含**一句话描述 / 全部 flag 及默认值 / 用法示例**；同时**要短**——它和别的东西一起进上下文，长篇手册等于挤掉真正的任务信息。
- **错误信息三要素**：错在哪、期望是什么、试什么（`Error: --format must be one of: json, csv, table. Received: "xml"`）。判据：**错误信息的读者是下一轮的模型，写得好不好直接决定它会不会第二次就修对**。
- **退出码分型并在 `--help` 里写明**：not found / invalid arguments / auth failure 用**不同的码**，别一律 `exit 1`——调用方要靠码分流（重试 / 改参数 / 换凭据）。
- **幂等优先**：agent 会重试，**"不存在才创建" 优于 "创建，重复则失败"**；破坏性操作给 `--dry-run` 与显式确认 flag。
- **工具形状阈值：3 次合并、8 参数拆分**（来源：AWS《MCP strategies》2026 实拉）：流程里**常用 ≥3 次独立调用才完成的操作 → 合并成单个工具**（省 token/延迟/认知负担）；**参数 >8 个 → 拆成多工具**（LLM 对复杂参数选择失败率随数量上升）。判据：设计工具前先数"这活儿要几趟调用、几个必填参数"，超线就重构形状，别让模型现场凑。
- **幂等性显式标注进描述**（来源：arXiv 2603.13417《Design Patterns for Deploying AI Agents with MCP》2026 实拉）：agent 重试工具是常态，**描述里显式写清"重复调用是否安全"**（idempotent / retry-safe），调用方据此决定恢复策略（直接重试 vs 先查状态）。与「幂等优先」设计原则配套：那条管"怎么设计"，这条管"怎么告诉模型"。
- **幂等落地三件：幂等键 → 重试前副作用检查 → 标识符职责分离**（来源：GitHub MCP Scripts 规范 2026-08-28 + CSDN《MCP 无状态核心之后：身份、任务、幂等与审计状态》2026-08-06 实拉）——"设计成幂等/标注幂等"还只是声明，这三条是让声明成立的具体实现：
  1. **幂等键**：带副作用的工具接受调用方传入的唯一稳定标识（如 UUID，**派生自原请求**而非每次新生成），工具侧据此去重重复提交（idempotency key / request dedup）。
  2. **重试前副作用检查（read-before-write）**：重试破坏性操作前，先查询外部系统确认上次尝试确实没产生效果（创建类先确认资源不存在再创建），不盲重试。
  3. **标识符职责分离**：幂等键 ≠ 追踪 ID ≠ 业务对象 ID——`Trace ID` 关联执行路径（可随链路变化）、`operation_id` 标识同一次业务尝试（重试保持）、`taskId` 寻址持久任务；**幂等键不能兼作授权凭据，审计证据不可只用幂等键**。判据：工具文档说不清"重试时哪个 ID 保持不变" = 幂等没落地。
- **输出体积要可预测**：多数 harness 会截断超长工具输出（10–30K 字符量级），**超出即静默丢尾部**。大输出默认给摘要或限额，配 `--offset` 翻页；实在不适合分页的，要求显式传 `--output <file>` opt-in，而不是默认喷到 stdout。
- **拒绝含糊输入，不要猜**：用枚举与闭集，收到集合外的值报错退出——**猜对了没人记得，猜错了静默污染结果**。
- 与 §脚本通道纪律（stdout 数据 / stderr 日志）配套：那条管"往哪写"，这条管"写成什么样 agent 才好用"。

## 触发器归技能，策略归文件（来源：GitHub `inkeep/open-knowledge-skills` 的 `cadence-and-logs`，2026-09-16 实拉）
技能不该把"具体怎么做"的策略全写死——**它只负责在正确的时机喊一嗓子，规则由现场的文件自己带**。
- 做法：技能只带**触发条件**（"本轮改了知识库/记忆文件 → 去找项目日志文件"）；日志的**条目形状、节奏、分类**由那个文件自己的 frontmatter / 注释说明。
- 为什么：**同一个动作在不同项目里策略不同**（有的当审计流水，有的当变更记录，有的当决策日志），写死就等于在每个不匹配的场景里强制执行错的格式。
- **文件不存在就没有这条纪律**：找不到对应文件 → 不套用默认策略，也**不要替用户造一个**。
- 判据：**技能的职责是"别忘记看"，不是"规定看到什么"**；把策略留在数据侧，技能才能跨项目复用。

## 入口点四要素 + description 瘦身的边界（来源：GitHub `ccheney/robust-skills`·`docs/skill-authoring-audit.md` v4.0.0 实拉；其评审依据为 OpenAI《Rethinking skills and prompts for GPT-6 Astra》与 Build skills 指南，2026-09-16）
一次真实的 11 技能改造给出了可量化的尺度：**入口点行数 2,851 → 510（-82%），description 总长 7,368 → 2,312 字符（-69%）**，而 77 个参考文件一个没删。
- **每个入口点必须声明四件事**：**输入上下文 / 相关约束 / 输出 / 完成预期**。缺哪一项，agent 就得猜——猜的部分就是每次跑都不一样的那部分。
- **提问只绑定"影响结果的缺失事实"**，不做笼统的批准关卡：**问"这份数据用哪个时区"，不问"我可以开始了吗"**。判据：**问句的价值 = 不问会做出不同结果吗**，不会就别问。
- **瘦身有边界**：缩短 description 时**只能删套话，不能删区分性用例**；**不要往里堆关键词目录**（"也支持 X/Y/Z"），也不要设一个任意的长度目标去凑——**长度的敌人是冗余，不是信息**。本次改造后单条 description 落在 **178–229 字符**区间（不是硬指标，是结果）。
- **指令支持具体结果，但不规定不必要的行程**：写"产出什么、满足什么"，不写"先点这里再点那里"；**把行程（itinerary）写得越细，换个宿主就越容易失效**。
- **区分"项目约定"与"技术要求"**：约定是可以改的（换个项目就不成立），要求是不改就会坏的；**把约定写成要求会让技能在别处误报，把要求写成约定会让人不当回事**。
- 与 §description 怎么写的分工：那条给写法，这条给**改造时的取舍边界与实测尺度**。

## 技能优先级：流程类先于实现类；路由类元技能在子 agent 里自我豁免（来源：GitHub `obra/superpowers`·`using-superpowers`，2026-09-16 实拉）
- **多个技能同时命中时，先跑"管方法"的，再跑"管实现"的**：流程类技能（怎么拆解、怎么排障、怎么验收）决定**做法**，实现类技能（用什么框架、怎么写代码）负责**落地**；反过来会让实现细节把方法挤掉。例："修这个 bug" → 先排障流程，再域技能。
- **路由类 / 元技能要在被派为子 agent 时立刻自我豁免**（该文件用 `<SUBAGENT-STOP>` 显式声明）：**子 agent 已经带着父级给定的任务进来，再走一遍全局技能路由只会递归消耗上下文**。判据：**这条规则只对"接收用户原始请求的那层"成立**。
- **优先级链的末位是用户指令**：用户显式要求 > 技能指引 > 默认工作流（与全局规则 0.9 同源，这里补的是**技能之间的相对次序**）。

## 评测集四类样本 + 留出集：断言过窄时改断言，不为迎合检查器改技能（来源：GitHub `ccheney/robust-skills` 的 `evals/VALIDATION.md` / `evals/COVERAGE.md`，2026-09-16 实拉）
一份能用的技能评测集**不是一堆用例，而是四类各司其职的样本**，且必须有一部分永远不许拿来调参。
- **四类样本，缺一类结论就偏**：① **产物任务**（给了输入要产出什么，判结果对不对）；② **正例控制**（应当通过的参考实现，用来证明评分器不是恒挂）；③ **语义反例**（应当失败的变体，用来证明评分器不是恒过）；④ **路由请求**（不判产出，只判"该不该加载这个技能"，含跨技能的混合请求）。**只做①的评测集测不出触发问题，只做④的评测集测不出内容质量。**
- **每个技能留 2–4 条 holdout，不参与任何调参**：调参用的是 development 拆分。理由：**断言和技能一起调，最后得到的是"断言刚好过这个技能"，不是"技能变好了"**。本次实测 112 个产物任务按 8/2、7/3、6/4 等比例拆 development/holdout。
- **首次通过暴露的"过窄假设"要变成新控制项，而不是改技能去迎合检查器**。实测四条：答案用了有效强调但没套外层 `<p>/<div>`（评分器改为量"有没有强调内容"而非"标签在第几位"）；空通配导出写成 `[]` 而请求没要求布尔（两种表示都接受）；直接返回表格块而请求没要求消息信封（两种都接受）；缺失字段叫 `user_id` 而不是 `slack_user_id`（指同一个缺失身份，接受）。**原文硬规则：`No skill was changed merely to satisfy these checker preferences.`**
- **判据（谁改）**：**放宽的是"等价表示" → 改断言**；**放宽的是"真实要求本身" → 不许改**，只能改技能并写明为什么原来的要求是错的。分不清时先改断言，再单独记一条待办去核要求。
- **评分材料不得进入模型可见的工具面**：断言、参考答案、预期标签、反例设计**不随任务一起下发给被测方**——见到答案的被测方会去拟合答案（与 §盲评对比 同源：那条讲人评，这条讲机评）。
- **证据强度要分层，不许互相顶替**：人工盲选 40 条请求全选中预期技能 = **支持"描述清晰度"**，**不是实测激活率**；API 配额没跑完的 comparison 一律**不声称通过**。**写结论时必须标明是哪一档证据。**
- 与 §用例分辨力（near-miss 负例）/ §触发率阈值 0.5 的分工：那两条管**单条用例怎么挑**，这条管**整个评测集怎么组织与怎么防止自我迎合**。

## 落地前查重必须双键检索：来源标识 + 概念关键词（本条来自 2026-09-16 r78-A 的真实事故，不是外部信源）
- **事故**：r78-A 从 `2dmurali/review-loop-skill` 提炼 5 点落进 `wb-artifact-verification`，落地后才发现**该源早在 r60（2026-09-15）已被消费并分散落进 spec §5 / max-token-saver「换挡检测信号」/ context-compressor「历史反馈随每轮重发」**——5 点全中重复，整段回滚。
- **根因**：查重只搜了**概念词**（"停滞""复核者能力""截断"），没搜**来源标识**。同一批源会通过 skills.sh 榜单轮换**反复出现在视野里**（本轮就是隔了 18 轮再次撞上同一个仓库），概念词查重对"同一来源被二次消费"完全无防御力。
- **硬规则**：任何落地动作之前，**至少跑两次检索**——① `grep "<owner>/<repo>" 全库`（或页面 URL 的域名 + 路径关键词，如 `cli/policy`）；② 概念关键词。**任一命中即进"已落"判定**，命中后只允许做相邻扩展（补一条互补判据并在正文写明与既有条目的分工），不允许整段重写。
- **判据**：**"我这次读到的角度不一样"不算新**——角度不同但结论相同，应写成对既有条目的一句话补充；**只有判据本身不同（换了个可机械执行的条件）才算新点**。
- **回滚纪律**：发现重复后**整段回滚并把版本号退回**（本例 av 1.21.0 → 1.20.0），不许"留着也无妨"——留着就是给下一轮埋同一颗雷。

## 评估要看真实使用表现：zero-shot CoT 提示 + SimpleQA 式事实性抽检（来源：GitHub `openai/simple-evals`，2026-09-16 实拉）
评估（模型或技能输出）时**提示格式本身会决定分数**——不要沿用 base model 时代的评估法。
- **评估指令微调模型/agent 用 zero-shot + chain-of-thought 的简单指令**（"Solve the following multiple choice problem"），**不用 few-shot 或角色扮演提示**（"You are an expert..."）——后者是评估 base model 的遗留做法，对 instruction-tuned 模型会虚高，不反映真实使用。
- **事实性用 SimpleQA 式抽检**：一组**短问题 + 短答案**（可判对错），衡量"短形式事实性"（编造率）。判据：**长答案能藏幻觉，短答案藏不住**；个人场景可定期抽检自己的输出/技能答案，用可判对错的短问句集量化"有没有编"。
- 与 §评测集四类样本/§断言过窄的分工：那些管**评测集组织与评分器校准**，本条管**评测时用什么提示格式 + 怎么低成本测事实性**。

## 改进既有 Skill 的四条信号（来源：办公场景 Agent Skills 方法论，CSDN 2026-09-13 实拉）
改技能不是凭感觉改，以下四条是可机械执行的信号：
- **反馈泛化，拒绝过拟合少数样本**：一条反馈只证明了一个用例 → 不要为它改技能。判据：**改动要让技能可复用百万次，不是让眼前这单次通过**（与 §评测留出集同源：防过拟合评分器，这里防过拟合单条反馈）。
- **精简 prompt 要看 transcript，不只看产出**：判断技能"啰不啰嗦"要读完整对话记录，不是看最终产出好看就完事。
- **解释 why，不用全大写 MUST**：规则/指令里出现全大写强调（MUST/ALWAYS）是黄灯信号——**优先写清"为什么这么做"，而不是用大写强调"必须做"**；原因清楚的指令模型才会真正执行。
- **3 个用例重复同一脚本 = 收编信号**：若发现三个不同用例各自写了同一段脚本/同一套操作，就是把它收编成技能内 bundled script 的时机——**重复出现三次才收编，一次两次先忍着**。

## SKILL.md 三要素检查：触发条件 / 指令正文 / 边界（来源：GitHub 高星 Agent Skills 生态综述，CSDN 2026-02 实拉；与入口点四要素互补）
写或审一个 SKILL.md，按三要素逐项查，缺哪个补哪个：
- **触发条件**：什么时候该用这个技能（"当用户要求 X 时"）——与 §description 写法、渐进式披露 Discovery 段同源，这里落成**正文首段必须有显式触发句**。
- **指令正文**：Agent 该做什么（可执行步骤）。
- **边界（not-to-do 禁区）**：什么**不该**做（"严禁编造数据、严禁越权修改、禁止执行 X"）——**独立于输入约束**：约束管"怎么做受限"，边界管"哪些动作碰都不许碰"。判据：**技能没有 not-to-do 节 = 越界风险**；执行类/有副作用的技能（改文件、发消息、调外部 API）必须写边界，纯生成类可省略。

## 护栏执行化：把声明式规则编译成运行时前置检查（来源：Langflow 1.11 Policies 功能，2026-09-16 实拉）
"边界"写好之后还要能**拦住**——声明式规则（自然语言写的 not-to-do / 业务规则）要编译成**工具调用前的确定性检查**，违规在发生前被拦截，而不是事后靠模型自觉。
- **做法**：把技能/agent 的规则（"不要碰 X""只允许 Y"）写成**人可读的策略**，执行时编译成**机械可判的守卫**（参数枚举 / 路径白名单 / 调用前置条件），挂到对应动作的入口。
- **判据**：**拦截必须发生在副作用动作之前**——规则只有在"调用工具那一步"前置校验才叫护栏；写在正文里的提醒只是装饰。
- **与 §三要素边界的分工**：那条管**写不写边界**（静态声明），本条管**边界怎么变成拦得住的动作**（运行时执行）。两边各有长处 → 合并使用：先写 not-to-do，再把它编译成前置守卫，缺一不可。
- 反模式：把护栏写成"事后检查"（先执行再看是否违规）——副作用已发生，检查只是追认。

## 边做边沉淀：三个触发信号立即记技能，不等重复三次（来源：Hermes Agent skills system，nousresearch/hermes-agent，2026-09-16 实拉）
与 §3 用例重复才收编互补：那条管**重复后收编**（保守），这条管**成功后立即沉淀**（主动）——遇到以下任一信号就记录技能，不必等第三次：
1. **摸索出一条值得重复的多步工作流**（今天解了一个坑、跑通了一条流程，且以后还会做）→ 立即记；
2. **撞了错误/死胡同后找到可行路径**（失败→修复的经验本身是技能）→ 立即记；
3. **用户纠正了你的做法**（用户教了你更好的方式）→ 立即记，这是用户亲手给的规则。
- 判据：**可复用的验证标准是"以后还会遇到"，不是"已经遇到几次"**——一次踩坑+修复就值得沉淀，因为重踩概率高；单纯一次性任务不记。
- 记录形态：**轻量条目**（一段方法说明即可入库/进记忆），不用一上来就写完整 SKILL.md；**条目复用 3 次再升级成独立技能文件**（与 §3 用例收编衔接：轻记 → 复用 → 成技能）。

## 技能规范三件套：allowed-tools 白名单 / 触发分类 / 上下文成本治理（来源：agentskills.io Specification + mattpocock/skills CHANGELOG + Anthropic Claude Code /skill-doctor + OpenClaw creating-skills，2026-09-16 实拉）
写/审技能时，除三要素外再查这三条：
- **allowed-tools 白名单（agentskills.io spec 字段）**：技能 frontmatter 声明**允许使用的工具集**（只声明它完成任务所需的那几个工具）。判据：**白名单 = 正面的最小工具面**，与 not-to-do 禁区互补——禁区管"哪些动作碰都不许碰"，白名单管"**任务只允许碰这几样**"；写指令时不要让技能鼓励 agent 去用清单之外的工具（"只需要 git 就别写顺带可以上网查"）。
- **触发分类：user-invoked vs model-invoked（mattpocock/skills）**：技能分两类——**用户显式调用型**（只有用户输入命令才可达，用于编排）与**模型自动调用型**（任务匹配时自动可达）。层级规则：**user-invoked 技能可以调用 model-invoked 技能，但绝不能调用另一个 user-invoked 技能**（防止未授权链式编排）。判据：写技能时先声明它是"用户点名才跑"还是"自动匹配就跑"，自动型 description 必须写成触发短语。
- **上下文成本治理（Anthropic /skill-doctor + OpenClaw）**：**每个已加载技能都在消耗上下文**——SKILL.md 控制在 ~500 词内（"A 500-word SKILL.md is fine"）；定期做**技能加载审计**：统计哪些技能被加载却从未被调用，按上下文成本禁用条目（/skill-doctor 做的事：追踪每个技能是否被调用+显示成本，报告后禁用浪费项）。判据：**"加载但从不调用"= 纯上下文税**，审计信号是"装了没用/每轮都注入却没触发"。
- 与 §三要素边界/§护栏执行化分工：边界管"写不写禁区"、护栏管"怎么拦住"，本条管"**声明工具面 + 声明触发类别 + 控制加载成本**"——技能从编写到加载的规范侧闭环。

## 技能级溯源元数据与发布分级（来源：GitHub `affaan-m/ECC`·`docs/SKILL-PLACEMENT-POLICY.md` + `continuous-learning-v2`，经 gh API 实拉，2026-09-16 学习轮 r82-B · 用户本轮新增「GitHub 优质开源仓库也要作为学习来源」）

与 §「规则生命周期要带出处」(rule-level 出处) 互补：那里要求每条规则标来源；这里要求**整个技能文件带一份机器可读的溯源元数据块**，让「这个技能从哪来、何时习得、可信度多高、谁/什么产出」可被脚本检索，直接堵住 r78-A「同一源被二次消费」事故在文件级复发。

### 1. 技能级 provenance 块（每个被本机习得/导入的技能都要有）
落地/导入一个技能时，在技能目录放一份 provenance 记录（写进 SKILL.md 顶部 frontmatter 扩展字段，或独立 `.provenance.json`），至少含四字段：
- `source`：来源 URL / 仓库 / 标识（如 `github.com/affaan-m/ECC`），与 §双键检索的「来源标识」同一值；
- `learned_at`：ISO-8601 日期（如 `2026-09-16`）；
- `confidence`：0–1，本机对该技能效用的当前置信（初学 0.3–0.5，多轮验证后升）；
- `producer`：产出方——哪个信源/仓库/agent 提炼的。

理由：① 满足用户反复要求的「来源标识」落到文件级、可审计；② 与 §双键检索共用 `source` 值，落地前 `grep source` 即可秒判是不是已消费过的源；③ confidence 让「候选池→已学」的晋升有数字依据，不靠感觉。

### 2. Curated(发布) vs Learned/Imported(本机-only) 分级
- **Curated（发布库）**：进 `D:\AI技能仓库`、随 GitHub push 发布的技能；必须经双键查重 + 多轮验证，且 provenance.confidence ≥ 0.8。
- **Learned / Imported（本机-only）**：从某次会话/某源临时习得或导入、尚未验证的技能；**默认不进发布库、不 push**；只在本机 `~/.workbuddy/skills/` 待用，带 provenance 块。
- 边界：发布库里只放「验证过、可复用、非临时」的技能；任何「本轮从 X 源提了一点」先落本机-only，别直接进发布库污染版本历史。

### 3. 晋升门槛（本机-only → 发布库）
满足全部才并入 Curated：
- provenance.confidence ≥ 0.8；**且**
- 在 **≥2 个独立上下文/项目**中被实际使用并确认有效（对应 ECC「project → global 当且仅当在 2+ 项目见到」的晋升规则）；
- 已通过 §双键检索确认不是对已发布技能的重复。
未达则留在本机-only，继续累积证据；禁止为了「凑数」把未验证技能直接发版（呼应「不硬凑 / 不编造 idle commit」铁律）。

## 引用前先验证生产者真的产出它；保留名字不等于保留契约（来源：neolabhq/context-engineering-kit·`grounded-instruction-references.md` + `stable-name-changed-shape.md`，2026-09-17 实拉）
原文：`When an instruction tells an agent to take a value from a named file, section, or field, first open the producer of that format and confirm it actually emits that value. An instruction pointing at a source that never exists leaves the agent with no defined behaviour — worse than stating no rule at all, because it suppresses the fallback that would otherwise apply. ... port its structure, never its assumptions about what the input contains.`
`When you change the SHAPE of a block but deliberately keep its NAME so consumers can still locate it, grep those consumers for assertions about the BODY, not just for lookups of the name. A consumer that validates the old shape under the stable name does not fail loudly — it silently rejects every correct artifact the new shape produces.`

- **引用一个来源之前，先打开"生产者"确认它真的产出那个值**：技能里写"取 X 文件的 `#### Verification` 段"，就要先 `grep` 那个文件确认它真有这一段。→ 判据：**指向不存在的来源，比不写这条规则更糟**——不写时还有默认兜底；写了却指空，把兜底也一并抑制了，agent 进入"无定义行为"。
- **移植模式时，只移植结构，绝不移植"输入里有什么"的假设**：从参考实现搬一套模板/流程过来，最容易顺手把"上游一定会给出 Y"这个假设一起搬过来。→ 判据：**结构是可移植的，输入契约不是**；每个取值点都要对新环境的生产者重新取证一次。
- **兜底链必须以"总能解析的来源"收尾**：`A if set — otherwise B — otherwise C` 这条链里，C 必须是确定存在的。→ 判据：链上任何一环指空，整条链在那一支上失效，而且失效时没有报错。
- **改了块的"形状"却故意保留"名字"时，要 grep 消费者对主体的断言，不只是对名字的查找**：只查"谁按这个名字找它"会漏掉最危险的那类——**按旧形状做校验的消费者不会大声失败，它会静默拒绝新形状产出的每一个正确产物**。→ 判据：**名字稳定 ≠ 契约稳定**；形状变更的排查面是"谁断言了内容"，不是"谁引用了标题"。这类消费者即使本轮不改，也要在报告里逐条列出。
  - 与 §结构体检（脚本路径真实存在）的分工：那条查**路径存在**；本条查**路径里有没有你说的那个字段/段落**，以及**形状变了之后谁会静默失效**。
- 反模式：写"见 XX 文件的 Y 段"但从没打开过该文件；从别处搬模板时连取值假设一起搬；兜底链最后一环是个不存在的值；保留旧标题改写内容后只 grep 标题引用就宣布兼容。
- **提升层**：可复用 Skill（引用完整性 / 变更影响面）。
