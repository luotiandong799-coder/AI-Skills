# wb-skill-authoring（技能层：写得能被触发、能被执行）

来源：WaytoAGI 精选 2026-09-01《Agent Skill 100 问》（skill 描述写法、触发排查、脚本/参考文件拆分、跨工具迁移、安全审查）。
核心判断：**skill 的价值 = 能否在该触发时被触发 + 读到的内容是否够执行。** 写得好但没人触发 = 不存在。

**与相邻技能的分工**（防抢触发）
| 场景 | 走谁 |
|---|---|
| 从零新建一个技能 | 平台内置 `skill-creator`（官方结构 / frontmatter / 脚本规范） |
| 改造 / 体检**已有**技能（触发不准、描述过宽、去重合并、安装后接线、触发评测、安全审查） | **本技能** |
| 长内容（书 / 长视频 / 播客 / 课程）蒸馏成技能 | `cangjie-skill`（本技能只管蒸馏产物落地后的写法与验收） |
| 学到的东西**要不要**写成技能 | `wb-loop-engineering`（写入前的三道门）；确定要写之后回本技能 |

## 设计原则（动手写之前先定）
来源：mattpocock/skills 的 README（"技能设计小巧、易于适应和组合，适用于任何模型，基于数十年的工程经验"）+ 本库实践。
- **单一职责**：一个技能解决一个功能位的问题；同一功能位出现第二个技能＝重复（走下面的去重合并流程）
- **小巧可组合**：正文能被一次读完；需要跟别的技能串起来时，用"与相邻技能的分工"表写清接口，**不复制对方的规则**
- **不重造流程**：已有成熟方法论（SDD / TDD / 诊断循环 / 代码评审）时，只补本地化差异与触发条件，不复述一遍通用流程——复述出来的部分会跟上游漂移
- **渐进披露**：description（常驻，只写"何时用"）→ SKILL.md（判断与步骤）→ `references/`（长清单/模板按需读）
- **只写跑过的**：没实际执行过的流程不写进技能，否则变成假规则

## description 怎么写（决定触发的唯一因素）
- **写"何时用"，不写"是什么"**：description 是路由器，不是简介。开头就给触发场景（"当用户要求 X / 出现 Y 场景时使用"），其次才是能力范围
- **把用户的原话写进去**：用户会说的说法（含中英文、口语、错拼）都列进触发词——模型靠语义匹配，不靠理解你的命名
- **具体 > 宽泛**：`"修 bug"` 会被误触发到所有排错场景；`"涉及编码任务时"` 才收得准。宁可窄，触发太窄时再补
- **边界写进描述**：明确"不适用于什么"（如 ponytail 写"非代码任务不套用"），防误触发比补充触发词更省事
- **一处修改即可生效**：description 是唯一被常驻加载的字段，正文只在触发后才读——所以约束的第一层防线必须在 description 里

## 该触发却没触发：按序排查
1. 描述里有没有用户实际会说的那几个词？
2. 触发条件是否写得太抽象（"处理复杂任务" 这类）？
3. 文件位置对不对（用户级 `~/.workbuddy/skills/` vs 工作区 `.workbuddy/skills/`）？
4. frontmatter 语法是否合法（`name` / `description` 必填，YAML 缩进别错）？
5. 改完 skill 后会话没重开 → 读的仍是旧版本

## 不该触发却触发
- description 过宽（写成了"所有 AI 相关任务"）
- 多技能触发词打架 → 显式写出优先级，或收窄其中一条
- 名字太泛（`helper` / `utils`）→ 改成能被语义区分的名字

## 触发评测：发布前盲测（新技能 / 改过 description 必做）
来源：GitHub `kangarooking/cangjie-skill`（★9.8k，MIT）阶段 4「压力测试」——把"description 能不能被触发"从**事后排查**升级为**发布前可测**。写得再好，没测过就是碰运气。

**用例三类，缺一不可**（写成 `test-prompts.json` 放技能目录，与 darwin-skill 格式兼容）
| 类型 | 条数 | 测什么 |
|---|---|---|
| `should_trigger` | 3–5 | 该调用时是否调用 |
| `should_not_trigger`（诱饵） | 2–3 | 不该调用时是否忍住 |
| `edge_case` | 1–3 | 边界模糊场景判断是否合理 |

- **没有诱饵用例的技能一律打回**：只测正例，每个技能都"看起来很好"，上线后乱触发
- **诱饵里至少 1 条必须是"应该触发另一个相邻技能"的 prompt**——技能间抢触发是上线后最常见的真实故障，只测"完全无关场景"发现不了

**盲测做法（优先独立 sub-agent）**
- 给 sub-agent 只给：技能清单（全量 name + description）+ 用户 prompt；**不给**预期答案 / 用例类型 / 判断
- 让它做**选择题**（该激活哪一个），而不只是"要不要激活这一个"——否则测不出抢触发
- 要求输出 `would_trigger` / `reason` / `if_triggered_action`，主流程再逐条对答案
- 无 sub-agent 能力时才退回自测，并在结果里标注这是 fallback、可信度低于盲测

**通过率门槛**
- 100% → 接受
- ≥80% → 分析失败用例：description 有歧义 → **修技能**；用例设计过狠 → 修测试，但必须记下理由
- <80% → **回炉重写 description**，不做表面修补；诱饵用例容错为 0

## 文件拆分
- **SKILL.md 只放判断规则与步骤**，控制在能被一次读完的长度；超过后遵循度下降
- **脚本放 `scripts/`**：能确定性执行的逻辑不要写成"让模型照着做"——脚本每次结果一致，描述性步骤每次可能不同
- **参考料放 `references/`**：长清单、模板、映射表按需读取，不常驻上下文
- **模板 / 素材放 `assets/`**
- 判据：**能被代码写死的用脚本，需要判断的留给 SKILL.md**

## 跨工具迁移
- 核心约束（触发条件、硬性规则、收尾动作）必须写在 SKILL.md 内，不依赖某个工具的插件 / hook 机制——换工具就失效的约束等于没写
- 工具特有的能力（如某工具的专属工具调用）在正文里显式标注为"仅 X 下适用"，并给出降级做法
- 迁移后必查：路径分隔符、命令是否跨平台、编码是否 UTF-8

## 安装前安全审查（第三方 skill）
按 P0 / P1 / P2 分级，先审 `SKILL.md` 再审 `scripts/`：
- **P0（拒绝安装）**：读取 / 外发凭证或密钥、`rm -rf` 或等价的无确认删除、向未知域名上传本地文件、静默改系统配置
- **P1（警告后确认）**：外部网络请求、写用户目录之外、调用 shell 执行下载内容、`sudo` / 提权、**破坏性操作缺守卫**（`rmtree` / 覆盖前不校验目标是否为该技能自己的产物目录，`--target` 传错即可删掉任意目录）
- **P2（可安装）**：纯本地读写、只读查询、明确作用域内的文件操作
- 审查只看**实际会执行的代码**，不采信 SKILL.md 里的自我声明

**发现 P1 且能用几行代码消掉风险时，就地修掉再装，不要只写警告**（2026-09-12 实测：`cangjie-skill` 的 `apply_skill_patch.py` / `cangjie.py rollback` 会对 `--target` 直接 `rmtree`，已补 `assert_safe_skill_target()` 守卫——拒绝盘根 / 用户主目录 / 顶层无 `SKILL.md` 的目录，并附行为测试）。留痕写一行，标明是本地补丁，避免把改动误当成上游行为。

## 审计已启用技能（定期体检清单）
用户 2026-09-12 强制要求：定期审计用户级 `skills/` 下每个已启用技能，找出并修正——**拼写错误 / 乱码 / 过时信息 / 失效工具名 / 与新环境不匹配的描述**。复用本清单（每项具体动作）：
- **拼写 / 乱码**：逐文件扫 frontmatter 与正文；控制台 GBK 误显示的"鑱旂綉"类乱码是**显示问题不是文件损坏**，用 Read 复核 UTF-8 原文，别把显示乱码当文件损坏去"修"
- **失效工具名**：检查 `allowed-tools` 与正文指令里的工具 / 命令名是否本环境真实存在（`command -v <x>` 验；如 `read_file` / `write_file` 在本环境不存在，应用 `Read` / `Write` / `Edit`；`openclaw` 等第三方 CLI 本环境无 = 环境不匹配，加注"本环境不可用"而非删命令）
- **过时信息**：脚本调用的服务 / API / 路径是否仍有效（如旧平台名 `Clawdbot`、`~/.claude` 跨宿主文档属第三方技能自身、不改）
- **与新环境不匹配**：frontmatter 占位垃圾（如 `author: "你的合作方名称"`）、指向已删技能 / 已迁目录的路径

**凭据硬编码扫描**（来源 `workbuddy-health-check` 唯一独有维度）：审计时**必跑**——全库 grep 所有 `SKILL.md` 与 `scripts/` 找 `api_key` / `token` / `secret` / `password` / `cookie` / `AKID` 等硬编码；发现即清除或转环境变量，**绝不入仓**（`.gitignore` 已排除 `~/.ssh/` 与 12306 cookies，不得移除该排除）。
- 评分维度（来源 `darwin-skill`，只取评分部分，不装整包）：触发准确率 / 描述质量 / 实际调用率 / 覆盖完整性 / 时效性 / 安全 / 可维护性 / 复用价值——按**棘轮**原则只升不降地改进（本地追踪），评分不是为了好看，是为了决定"该保留 / 该删 / 该并"。

## 技能质量硬杠（VoltAgent 策展标准）
来源：GitHub `VoltAgent/awesome-agent-skills` 的 README 内联质量条款（1000+ 官方 Skills 策展清单）。本库写 skill / 审计时逐项打勾；不满足不上线：
- **description 约 100 token 以内**：常驻字段，必须一次读完；太长会吃常驻上下文，触发时也抓不住重点
- **三句描述**：何时用 / 做什么 / 边界或不做什么；禁止写小作文或能力介绍
- **SKILL.md body ≤ 500 行**：正文必须能被一次读完；超过 → 拆 `references/` 长清单、`scripts/` 确定性逻辑、`assets/` 模板；禁止正文里塞参考资料
- **禁绝对路径**：正文 / 脚本里不写 `C:\` / `/Users/` / `~/.x` 等硬编码绝对路径；必须走相对路径、环境变量或技能约定目录，否则换机器/换账号失效
- **tools 作用域化**：`allowed-tools` 与正文只声明本技能真实会用的工具；禁止罗列"可能用到"的全局工具；`scripts/` 里不得调用超出 skill 自解释范围的系统命令

## 安装后必须接线（用户 2026-09-12 强制：**装了不调用 = 没装**）
技能装完 / 写完**不算完成**，必须当轮让它"下次会被扫到并真被用上"：
1. **写相邻分工**：在职责最接近的既有技能里加一行路由（例："长内容蒸馏 → `cangjie-skill`"）。不写 → 任务来了仍走旧路径
2. **触发词互补**：新技能 description 覆盖用户的实际说法；若旧技能也会被同一说法触发，在旧技能里注明"此类转 X"，避免抢触发
3. **验证扫得到**：`ls -1 ~/.workbuddy/skills/` 复核目录在 + 读 SKILL.md 前 20 行确认 frontmatter 的 `name` / `description` 完整（缺 `---` 分隔或 name 拼错 = 系统清单里扫不到）
4. **留痕一行**：装了什么 → 接到了哪里（写进当日 memory）
- **反模式**：装完只更新记录、不写路由 → 下次任务照旧走老路，等于没装（实测教训：`cangjie-skill`、`wb-debug-loop` 都曾被"装了但没接线"）

## 去重与合并流程（用户 2026-09-11 强制：「重复的都删」「去坏存好结合」）
发现两个技能同一功能位重叠时，**按固定顺序走完，不能只删不并**：

1. **先查同类**：在全量技能里按"功能"而非"名字"找同类（名字不同、干同一件事的就是同类）
2. **列各自的好与坏**：逐条列出两边**独有的好点**（能力/触发词/脚本/边界判断）与**坏点**（依赖不可用服务、过时、空泛、被更优实现取代）
3. **合并成新的**：新建一个技能，**把双方的好点都装进去**——被删方的好点必须显式落进新技能（写清来源，便于回溯），不能"删了就没了"
4. **触发词取并集**：两边 description 里的触发词合并，否则原来的用户说法会失配
5. **删掉被覆盖的**：旧目录直接删，**不额外备份**（本地 git 历史即可回溯）
6. **删后查引用**：全库搜被删名字，修掉悬空引用（技能正文、规则文件、自动化 prompt）
7. **留痕**：一行记录（合并了谁+谁 → 新技能名 / 删了什么 + 理由）

**硬判据**
- **同轮完成**（用户 2026-09-12 强调）：合并与删除必须在**同一轮内一起做完**。写下"已被 X 吸收 / 待删 / 暂不视为独立技能"却留着目录 = 没做；做完必须 `ls` 复核。
- **不确定是否重复时按重复处理**：先合后删，不要两个并列。
- **不并列保留**：同一功能位只允许一个技能。哪怕"各走不同服务"也是并列——应做成同一技能内的多条路径
- **不动**平台内置与插件市场纳管的技能（各有管家），但可向用户指出其重叠
- **非同类不合并**：只要不干同一件事，即使风格相近也不碰（如确定性图像编辑 vs AI 生成式修图）

## 反模式
- description 写成能力介绍（"这是一个帮助用户处理文件的技能"）→ 不触发
- 把长流程塞进 description → 常驻上下文被白白占掉
- 能确定性执行的步骤写成"让模型自行判断" → 每次结果不一致
- 约束只写在正文、不写 description → 该拦的没拦住
- 装 skill 只看名字不看脚本 → 引入 P0 风险
- 两个 skill 职责重叠还并列保留 → 触发时二选一，行为不稳定（应合并）
