# wb-ponytail（决策阶段：少写代码）

## 前置分流（先判任务类型，再选阶梯）

| 任务类型 | 走哪条 |
|---|---|
| 单次小改动、修 bug、加小特性 | 下方决策阶梯 + 验证阶梯（本 skill 全程覆盖） |
| **3 步以上 / 跨会话 / 要自主跑到交付的实现任务** | 本阶梯走完定方案后 **转 `wb-spec-driven`**：先立规约（目标 / 验收标准 / 范围内外）→ 计划-实现-检查 → 独立验证 → 交付 |
| 生成类视觉任务（生图 / 改图 / 视频 / 3D / AI 做网页） | **转 `wb-visual-gen`**：先定验收标准 → 备料 → prompt → 生成 → 对照清单自评 → 定向迭代。**禁止直接开生成碰运气** |
| 写作 / 文档 / 研究 / 数据分析 | 不套用本 skill，按内容完整度交付 |

写代码前先走决策阶梯，停在第一个成立的台阶：

1. 这事真的需要存在吗？投机需求 → 跳过并一句话说明（YAGNI）
2. 代码库 / 已有方案里能复用吗？先找后写，不重复造轮子
   - **顺带盘一次执行环境的能力基线**（文件读写 / 子 agent 对话 / 任务协作 / 缓存保留；来源：WaytoAGI 09-10 DeepSeek V4.1 Flash harness 清单）。**环境不支持的方案别硬上**：以"能开子 agent 并行"或"能持久化中间态"为前提的设计，在窄 harness 里必然卡死；缺哪项就在方案里补人工环节，或退回更简单的做法
3. 标准库能做吗？用标准库
4. 平台原生功能覆盖吗？（如 `<input type="date">` 代替日期库、CSS 代替 JS）
5. 已安装依赖能解决吗？绝不为几行代码引入新依赖
6. 能一行搞定吗？一行
7. 最后才写最简可用代码

## 实现前：先核对真实来源，别凭记忆编接口
来源：marketplace `source-driven-development` 独有条目（整包与 `wb-spec-driven` 重叠 >60%，只取这一条并入，不安装）。
**编造 API / 参数名是幻觉最高发的部位，且编译期常常查不出来。**
- 动手前先取证据：**官方文档** > **本地真实源码**（该库在本仓库的现有调用点、`node_modules`/site-packages 里的实现）> 记忆。**记忆只能用来定位，不能用来确认签名**
- 涉及外部库 / 接口 / 命令行参数时，至少找到一处真实来源再写；**找不到证据就在代码注释或交付说明里标"未核对"，不要编一个看着合理的**
- 版本敏感项（API 行为随版本变）先确认本机装的版本，再按该版本的文档写
- 已核对的来源在交付摘要里留一句出处，便于后续复查
- **会增长的枚举不许硬编码**（来源 riekelt/mutation-testing 实拉 2026-09-15）：命令/算子/类别清单"随每次发布增长"（如 `mewt print mutations`），权威清单在运行时可查就每次现查，不把枚举写死在代码或技能里——写死的清单第一次遇到新条目就变成静默漏判

## 能力边界：声明"能力"，不声明路径；权限来自授权，不来自探测

来源：GitHub `william-london/ownframework-loop` `docs/architecture/HOST_CAPABILITIES.md` + `ADAPTER_CONTRACT.md`（2026-09-14 增量）。

- **声明可移植的能力名，不写主机路径 / 凭据 / 供应商位置**：写"需要浏览器能力"，不写 `C:\...\chrome.exe`。路径是环境细节，写进方案就等于把方案钉死在一台机器上。
- **解析失败要在启动前 fail-closed**：能力不可用就**停在动手之前**，不要让执行过程自己想办法（"模型不能扩大自己的主机权限"）。靠运行时兜底 = 兜底的人正好是最想继续跑的那个。
- **"命令在 PATH 里找得到" ≠ "被允许使用"**：PATH 探测只是"存在性证明"，不是"授权证明"。可用性的来源应是**授权清单 / 白名单**，不是"我 which 到了"。同理，"上次能跑"也不是这次能跑的证据。
- **特权能力要证明，不要声明**：容器、本地端口监听这类能力，必须由一次**可复核的验证（canary / 摘要 / 已登记的中间人）**证明可用，且**自证的声明无效**——"我把指纹抄进配置里"不叫验证。拿不出证据的权限 = 没有该权限。
- **第一个实现不是参考实现**：某个平台/工具是"第一个跑通的"，不代表它是规范、更不代表后来者该照抄它。**新东西从与实现无关的接口契约起步，只加自己能证明的部分**。
- **能力要在建立连接时显式声明，并且"清单会变"本身也要声明**（来源：MCP 官方规范，服务器须声明 `capabilities.tools.listChanged`）：**缓存下来的能力视图会过期**。只声明"我有哪些能力"不够，还要声明"这个清单会不会变、变了怎么通知"——否则对端拿着一份旧的清单做决策，失败时看起来像随机故障。
- 反模式：方案里硬编码本机路径；`which` 到就当能用；探测失败后在脚本里加 `|| true` 绕过；把"某工具的实现方式"当"这件事该怎么做"；**只声明能力不声明变更**，让对端的缓存悄悄失效。

## 改动 / 删除前：先查它为什么在那（Chesterton's Fence）
来源：GitHub `addyosmani/agent-skills`（85k★，Google 工程纪律 24 个技能包）中的 Chesterton's Fence 原则。
**"看着没用"和"真的没用"是两件事——先证明后者，再动手。**
- 要删 / 要改任何已存在的东西（代码、配置、脚本、技能、自动化的某一步），先花一分钟找它存在的原因：`git log`/`blame` 看提交信息 → 全库 grep 找引用点 → 看注释与相邻文档 → 问一句"谁会依赖这个行为"
- **查不出原因 = 不能删**，改成先标注（`TODO: 疑似无用，原因待查`）+ 保留；查得出来才可动
- 改动后用**原场景回归**一遍，确认没把别人依赖的行为顺手改掉（Hyrum's Law：任何可观察行为都可能已被依赖）
- 反例（真实踩过）：记忆里写着"已删"，本机其实没删 —— **删完必须 `ls` 复核**，写记录不算删除动作完成

## 改现有代码：外科手术式，不顺手改无关
来源：GitHub `multica-ai/andrej-karpathy-skills`（Karpathy 对 LLM 编码四大坑的观察，只取本地缺的两条并入库，其余 Simplicity/Goal-Driven 已由本 skill 与 `wb-spec-driven` 覆盖）。
**"顺手改进"是 diff 里最常见的污染，也是最难回滚的部分。**
- 只碰**必须**碰的：不"改进"邻近代码、注释、格式；不顺手重构没坏的东西；风格照现状走，即使我本来会写另一种
- **每行改动都要能追溯到用户的这次请求**；追溯不到的，就是混进去的私货
- 顺手发现无关死代码 / 别处的问题 → **只提及，不删不改**（要不要动由用户定，另见下面 Chesterton's Fence）
- 只清理**我这次改动造成的**孤儿（import / 变量 / 函数）；改动前的死代码不碰

## 有界 ≠ 最小：别为了"改动小"把该改的改薄

来源：GitHub `william-london/ownframework-loop` `.agents/skills/of-loop-build`（2026-09-14 增量）：*"A bounded build pass is not required to be minimal… The operator MUST NOT collapse or thin the change set to keep the pass small."*

- **"最小改动"说的是别越界顺手改无关的，不是该改的也分批改**。当问题的修复面本身就跨多个文件（同一抽象要一起动、同一个契约要一起改），**一次改完整是更小风险的做法**——分批改会让中间每个版本都是不一致状态。
- 判据：**这个改动单独存在时，代码库是否处于自相矛盾 / 半迁移状态？** 是 → 它必须和同伴一起上，拆开才是真风险。
- 与「外科手术式」的分工：那条管**横向**（不要碰与本次请求无关的东西），本条管**纵向**（本次请求本身要求改到的范围，不要纵向削薄）。两条一起才完整：**不越界，也不欠改**。
- 反模式：为了"diff 好看"把一个跨文件的重命名拆成 5 次提交，中间 4 次都跑不起来；把接口与其全部调用点分开改，留下中间态。

## 不确定就问，别静默替用户选一种解释
来源：同上（Karpathy「Think Before Coding」）。
**模型最爱做的错事不是理解错，是理解有多种可能时悄悄挑一个往下跑。**
- 有歧义就**列出可能的解释并让用户选**，不要默默假设一个然后一路做完——做完才发现理解错，代价远大于问一句
- 拿不准的假设**显式写出来**（"我按 X 理解，如果不是告诉我"），让它可被纠正
- 自己有困惑就**停下来指名困惑点**；有更简单的路就直说，不要因为用户点了头就硬上
- 反例：同一段需求有两种合理读法，我选了难的那种写了 300 行 → 返工；选前问一句成本几乎为零

## 取舍清单：先说出按什么标准权衡
来源：The Batch issue-368（2026-08-28）软件工程基本功对 agentic coding 的作用。
**vibe 编码的失效点通常不是"写不出来"，是不知道该权衡什么 → agent 只能自己瞎选，选完你还看不出来选错了。**
动手前显式声明本次的优先级（选 1–2 个主目标，其余明确让位）：
| 维度 | 常见冲突 |
|---|---|
| 延迟 / 吞吐 | 快速响应 vs 批量处理 |
| 可用性 | 简单可靠 vs 高可用冗余 |
| 一致性 | 强一致（慢、简单）vs 最终一致（快、要处理冲突） |
| 可靠性 | 快糙猛 vs 容错、不崩、可恢复 |
| 可维护性 | 临时方案 vs 可读、可测、可改 |
| 简洁性 | 通用抽象 vs 直接实现（**默认站简洁**） |
| 成本 | 省算力/省 token vs 效果 |

不做的事：**不替用户默认全部都要**。冲突不可兼得时，说明"这次优先 X，代价是 Y"，而不是默默选一个。

## agent 架构：默认单一工具调用 agent，不追类型动物园
来源：n8n 在 v1.82 把多种 agent type 全部收敛为 **Tools Agent**（唯一的工具调用原语 + memory + tool 子节点）。信号：绝大多数场景不需要"反思型 / 规划型 / 多角色"等特化 agent 类型，一个能调工具 + 带记忆的 agent 就够了。
- **默认**：先上**一个**工具调用 agent（LLM + 记忆 + 需要的工具节点），把它跑通；只有当它稳定做不好某类子任务，才拆出专门的子 agent / 工作流（与「取舍清单」的"默认站简洁"同构）。
- **工具以子节点 / 子技能挂接**（可插拔），不把工具逻辑写死进主 agent 行为；记忆独立配置。
- **配工具时先分清"子 agent"还是"普通工具"**（来源：Make Help Center《Make AI Agent best practices》，2026-09-14 经代理补访，此前 403）：**这一步需要"自己的推理 + 自己的工具"才做成子 agent；其余一律用普通工具**（一次调用 / 一个模块 / 一个 MCP 工具）。**子 agent 要多花额度买它自己那份额外推理**——省下的编排复杂度是用推理成本换的，不划算就别拆。判定问一句：这一步是"想一下再决定调谁"吗？不是 → 普通工具。
#### 工具挂两档：固定操作的内建工具 vs 开放选择的 MCP 服务器

来源：n8n Docs《MCP servers》《Build and manage agents》（2026-09-14 实访 Markdown 原文）。

同一个外部能力，可以以两种形态挂给 agent，**选哪个取决于你知不知道它要用哪个动作**：

| | 内建工具（固定操作） | MCP 服务器（开放选择） |
|---|---|---|
| **用在哪** | 你明确知道 agent 需要哪个动作 | agent 需要一系列动作，或事先不知道用哪个 |
| **范围** | 一个操作（如"发一条 Slack 消息"） | 该服务器暴露的**全部**工具 |
| **你固定什么** | 任意参数（频道 / 类型 / 模板），只把需要模型填的字段留空 | 允许/排除哪些工具 |
| **模型决定什么** | 只填你留开的字段 | 调哪个工具 + 全部参数 |

- **开放度是拿控制力和上下文换的**：越开放，模型每次要读的工具定义越多、走偏的空间越大。**能固定就固定**——把一个常用动作固化成"只留两个字段"的工具，比丢一整个 MCP 服务器给它便宜也稳。
- **暴露范围默认用白名单**（只给需要的那几个），而不是"全部"或"除了这几个之外全部"。后两种叫黑名单，**新工具一上线就自动进了它的能力集**——你没授权过的东西被授权了。
- **路径校验要做两次：归一化之后一次，符号链接/最深祖先解析之后再一次**（来源：OpenClaw Docs《The trust boundary》，2026-09-15 经自启 VPN 实访）：只在上层做一次校验，是路径逃逸类漏洞的经典成因——**校验时看到的路径和实际打开的路径不是同一个**。判据：**校验完到使用之间，路径还会被解析吗？** 会 → 解析完必须再校验一次。
- **"显式要求的安全环境不存在"必须报错，不能静默降级**（同源：显式 `host=sandbox` 但未配置沙箱运行时 → **失败**，而不是悄悄在宿主机上跑）：**静默降级把一次配置错误变成一次安全事故**，而且当事人毫不知情。判据：用户明确指定了更严的环境，那环境不可用时的正解是**停下来告诉他**，不是退回到更松的环境。
- **变更通知有两个粒度，要分开声明**（来源：MCP 能力声明：`listChanged` 清单级 + `subscribe` 单项级，可各自独立开启）：**"清单变了"和"某一项的内容变了"是两件事**——前者要重新拉取目录，后者只需刷新那一条。只声明一个，对端要么漏更新，要么为一条变动去拉全量。
- **认证方式要匹配部署形态，别硬套**（来源：MCP 官方授权指南）：OAuth 那套浏览器跳转流程是**为远程 HTTP 服务设计的**；**跑在本机的东西不必套 OAuth**——它本来就在用户环境里，用环境凭据或第三方库自带的凭据机制更自然，也更少出错。**把为远程设计的方案套在本地上，会凭空多出一堆"为什么要跳浏览器"的复杂度。**
- **形态决定并发与生命周期，别选错**（来源：MCP 架构：本地 STDIO 服务通常只服务一个客户端，远程 HTTP 服务服务多个）：**本地/进程内的东西天然是 1:1**（一个实例对一个调用方），**远程/长连接的东西天然是 1:N**。按 1:1 写的组件被多个调用方同时使用，状态会互相踩；按 1:N 写的组件只有一个调用方，则白白付了并发成本。
- **一个外部服务一个专职通道，由统一层协调**（来源：MCP host/client 分离）：host 是用户看到的那一层，负责整体协调；**每个 client 只跟一个 server 说话**。好处是失败的 blast radius 被限制在一条连接内，权限也能逐连接授予和回收。**别做一个"万能连接器"同时对接所有服务**——它会同时成为权限黑洞和故障放大器。
- **先分清"这是动作还是数据"**（来源：MCP 三积木）：会改变外部状态的 = 动作（Tools），只读的 = 数据（Resources）。**动作面要窄（一个工具一件事）并配拒绝通道；数据面可以宽（常驻上下文）**。把数据当动作暴露会产生无谓风险，把动作当数据常驻会让人失去对副作用的感知。
- **agent 每轮的下一步只有四类**：调工具 / 检索知识 / 交给另一个 agent / 追问一句；循环直到产出最终响应。**把"追问"列为合法出口**很重要——不会追问的 agent 会用猜测填满不确定性。

#### 子 agent 嵌套限一层，且对外只暴露"名字 + 一句话描述"

来源：Make Help Center《Create your first AI agent》（2026-09-14 实访）。**agent 嵌套限一层**：父可以有子，**子不能再有孙**。

更要紧的是接口侧：**父 agent 只拿到子 agent 的`名字`和`描述`，看不到它的指令和工具**（平台是有意这么设计的，不是限制）。迁移到本地：

- **描述即契约**：子 agent / 子技能对外只暴露"它做什么、什么时候该用它"这两句；**它的内部指令、工具清单不要倒进父的上下文**——父会用"看起来更强"的方式去依赖子的内部实现，改子必炸父。
- 描述写不好 = 父根本不会调用它。**调用不上的根因常在描述，不在能力**（与 `wb-skill-authoring` 的触发词工程同源）。
- **层级上限是调试预算**：两层以上时，一个问题要穿过整条链才能定位，而每层都在消耗额外推理额度。
- 反模式：三层嵌套（父→子→孙）；把子的完整 system prompt 贴进父的提示词"让它调度得更准"；为了省事让父直接引用子的内部工具名。
- 反模式（架构级）：一上来就搭"主管 agent + 3 个专家 agent + 评审 agent"的复杂编排（过度设计，是 YAGNI 的反面）；为不存在的需求预设 agent 类型动物园；把一次性调用包成子 agent 只为"看起来像多智能体"。

## 拆子流程的抽取契约：单入口单出口 + 类型显式声明 + 上下文表达式逐个重验（来源 n8n《Convert to sub-workflows》2026-09-15 实访）
- n8n 对"把一段流程抽成可复用子流程"规定了硬性边界条件，逐条可迁移到"把一段代码/一段链路拆成子 agent 或子任务"：
  1. **单入口单出口**：抽取段对外只有一条入边、一条出边（多分支汇入/分出的节点不能当边界）——不满足就先理顺再抽，硬抽等于把耦合搬进接口。
  2. **触发器不进抽取段**：入口语义（何时启动）留在父层，子层只管"给什么就处理什么"。
  3. **输入输出类型必须显式声明**：默认"什么类型都收"是隐患——不声明类型，调用方传错要等运行时才炸。
  4. **上下文相关表达式不平移**：`first()` / `last()` / `all()` / `itemMatching(i)` 这类"依赖在父上下文里的位置"的引用，抽出去后语义会悄悄变（n8n 的做法是加 `_firstItem` 等后缀保留原信息 + 要求人工重验）——**拆分清单里必须有一项：逐个列出依赖外部上下文的引用，逐个重验**。
- 判据：抽出去的部分如果"离开父上下文就无法自解释"，说明还没到可抽取的边界，先补显式接口再拆。

## 验证阶梯（写完代码后，与决策阶梯配套）
验证强度匹配任务风险，不做一刀切：
1. 先跑廉价信号：编译 / 冒烟 / lint / 单测，能自动化就自动化，让结果可自查
2. 设定"够用"的判定阈值：什么算通过、什么必须停下修（阈值先想清楚，别边跑边改）
3. 廉价信号越过阈值才升级到重型验证：人工走查、LLM-as-judge、安全/架构审计、端到端流程验证
4. 危险操作（删除、覆盖、外发、权限变更）不论任务大小，一律过人工确认，不进自动化

## 约束
- 不写投机性抽象、样板代码、留待未来的脚手架；删除优于添加；最短可用 diff 优先
- 复杂需求：给最简版本，并说明"做了什么、覆盖了什么、需要完整版就说"
- 绝不偷懒砍：输入校验、防数据丢失的错误处理、安全措施、无障碍基础、用户明确要求的内容
- 先完整理解问题（读相关代码、追调用链），再决定偷懒——理解环节不能省
- 非代码任务按内容完整度交付，不套用"少写代码"

## 状态建模三律（来源：gbasin/clanker-discipline）

AI agent 写状态类型时的典型病：乱加 boolean 旗标、optional 字段大杂烩、变更方式含糊，最后复合成谁都没打算要的状态。每个 boolean 让理论状态空间翻一倍。

### 一、派生不存储
能从已有数据算出来的值，不存——最佳派生源是**事件流**（"发生了什么"的日志）。四个旗标回答一个问题 = 四处 mutation 点在同步。派生写法的调试红利：bug 变成"数据进、答案出"，拿事件 fixture 断言纯函数即可，不用 mock 和复现时序。
**不派生的三例外**：领域真是有序状态机（checkout 步骤本身就是状态）；含不可再生的外部/时序数据（异步时间戳、下游要用的 API 响应）；派生逻辑比存储更复杂。可变状态必须存在时，用**闭包**圈进最小作用域（closure 优于类字段——类字段全类可见，闭包外面碰不到）。

### 二、让非法状态不可表示
- **判别联合替代 optional 大杂烩**：`status` 为 idle 时 gateway/transactionId 该不该存在？optional bag 答不了；改成一个 status 一个形态，各形态只带自己需要的字段。
- **分阶段组合替代 20+ optional 平铺**：identity?: {…全必填} 一个 optional 替八个——identity 在则字段全在。
- **null 优于哨兵值**：`'none'` 不是动作，是动作的缺席；哨兵（'none'/'unknown'/-1）会被误当真值处理。
- **同形异义的原语要 brand**（UserId ≠ TeamId，同是 string 会串）。**死变体删掉**：从未被构造的 status 变体说明那个生命周期不存在。

### 三、变更契约二选一
改输入就返回 `void`；要返回值就先克隆返回新对象。**禁止改输入又返回同一引用**——调用方无法判断该用返回值还是原对象。纯函数悄悄长出副作用时，把副作用抽到独立的编排函数里去。

## 引依赖：先榨干已有的，再 vet、pin、记退出条件（来源：riekelt/principal-engineer·adding-dependencies，2026-09-15 实拉）

> 判重留痕：与「外科手术式」（管不顺手改）、「有界≠最小」（管该改不削薄）、「状态建模三律」（管数据建模）均不重叠——本条管"要不要把一个包领进树"。上游整包 11 个 skill 与本地重叠 >60%，不装，只取本条。

**依赖是一次招聘，不是一段代码**：招进来的是它的缺陷、发布节奏、传递树和维护者的精力。

### 七级阶梯（逐级往下，停在最先够用的层级）
1. **需求本身**——投机需求不是需求，一句话说清并跳过
2. **本代码库**——几个文件外已有 helper / 类型 / 模式就复用；仓库已有东西的第二份拷贝是缺陷
3. **标准库**——装包前先读它的索引，看是否已覆盖
4. **平台**——数据库约束优于应用代码、原生控件优于 widget 库、运行时原语优于包装层
5. **项目已带的依赖**——它的传递树已经付过钱了。**两条边界**：①你开始直接 import 的传递依赖 = 新直接依赖，要显式声明并 pin 到已解析版本；②dev 工具的传递依赖被提升进 runtime，成本转移到每个消费者的安装
6. **自己写二十行**——二十行真的够时，拥有自己的二十行胜过拥有别人的仓库
7. **过了六级才引新的**——按下面 vet

### vet 招进来的人
- **算整笔账**：传递树、安装/构建重量、许可证冲突、安全历史
- **摸脉搏**：最近发布、issue 响应、可合并人数——承载关键路径的包只有一个耗尽的维护者，是你主动选的风险
- **读你要调用的那部分**：API 面和失败模式，不是 README 的承诺
- **要只做一件事的工具**，不要四十个功能的框架——另外三十九个照样跟着来（重量 + 攻击面）
- **记录决策**：用途、权衡过什么、**它在什么条件下离开**（退出条件）

### 姿态、pin 与删除
- **依赖姿态是项目要声明的**（全自禁 / 白名单 / 审后加）；没人能回答时按"声明的假设姿态"走并记下假设 + owner，不是默默放行
- commit lockfile、pin 版本；CI 或基础镜像里的裸 `latest` = 别人调时的定时炸弹；大版本升级单独一个 commit（blame 可读），patch 可打包
- **依赖的用途消失时，依赖在同一变更里一起走**；"留着以防万一"= 第 1 级投机需求的反向版；只剩一个小调用点时考虑改为拥有那几行
- 常见反射病：树不是被大决策养大的，是一次一个"小而合理"的包喂大的——**为绕开读现有代码而装包 = 跳过了第 2 级**

## 依赖的调用面：只用公开入口，弃用路径只在声明的兼容窗口内存活（来源：OpenClaw 官方 docs.openclaw.ai·plugin-validation-fixes / agent-runtime-architecture，2026-09-15 实拉）

> 判重留痕：§引依赖 管"**要不要把一个包领进树**"（选型与全生命周期）；本条管"**已经在树里之后，从哪个门进去、旧门留多久**"。与 §135「描述即契约」（子 agent 之间）不同层：那条管 agent/技能边界，本条管**代码 import 边界**。

- **只从公开入口进，不 import 内部路径**：用文档化的公开子路径（`pkg/public-x`），**不 import 包的内部目录**（`src/**`）。内部路径没有兼容承诺，一次小版本就能把你的构建打断——**"能跑"不等于"被支持"**。
- **两种被禁的入口**要能识别：①**已弃用的根 barrel**（全量导出的大入口，体积与耦合都最大），换成窄的公开子路径；②**保留给内置/内部兼容的路径**——不是给你用的，即使现在 import 得到。
- **行为没有公开 API 时，两个正当出路**：把那段 helper **留在自己的包里**，或者**去上游申请公开 API**。**不要靠内部路径"先用着"**——那是把未声明的依赖伪装成正常引用。
- **弃用路径只在显式声明的兼容范围内存活**：保留旧 helper / 旧钩子的**唯一合法理由**是"我声明的兼容范围仍要支持老版本"，且必须**同时**写清（a）兼容范围到哪结束（b）替代入口是什么（c）退出条件。**没有这三个的"暂时留着"就是永久留着**（与 §捷径债务台账 同一纪律）。
- **兼容范围与你自己的版本号是两件事**，分别声明：一个说"我这个包发布到哪一版"，一个说"我依赖的上游契约范围"。写混会让升级决策无法判断该动哪个。
- **元数据声明与实际行为必须一致**：声明了要用某环境变量/某二进制，就必须真用；真用了就必须声明。不一致会被静态校验标为缺陷（"声明漏了"和"引用了没声明的"是同一枚硬币）。**声明不是装饰，是可被机械核对的契约**（与 §约束 段同源）。
- **不要用尚未定义契约的声明式文件假装安全**：上游还没有发布版本化 schema 时，**删掉那个自制清单文件**，把安全敏感行为写进公开文档，而不是先造一份没人校验的 JSON 看着像治理。**契约不存在时的"声明"只是仪式**。

## 收益数字必须有可减的真实基线：没写出来的那个版本不是基线（来源：dietrichgebert/ponytail·`ponytail-gain`，2026-09-16 实拉）

> 判重留痕（sa 双键检索）：`dietrichgebert/ponytail` 这个仓库名在本库已命中——`ponytail-debt` 于 2026-09-15 落地为下节 §捷径债务台账。本条取自**同仓库的另一个子技能 `ponytail-gain`**，判据不同（那条管"偷的懒记没记"，本条管"收益怎么报"），按相邻扩展落地，不重写既有条目。

- **"省了多少"是差额，差额要有两个真实端点**。原文硬边界：`NEVER print a per-repo savings number`——被省掉的那个版本**从来没被写出来**，它不构成基线，减不出数字。**"没做的实现"不是对照组，是反事实**。
- 能报的三类数字，各自带口径：① **基准中位数**——必须同时写"这是基准上测的，不是本项目"；② **计数台账**——来自真实 grep / 真实提交（下节债务台账的 N 条标记属此类）；③ **两侧都真跑过的对照组差值**。
- 禁止的写法：把基准或估算说成"你这次省了 X 行 / X token / X 元"；用"本来要写 N 行"的反事实当分母。
- 判据：**问一句"这个差额的另一端，是哪一次真实运行？"答不出来就不许报**——宁可写"没有基线，不给数"。
- 与 `wb-skill-authoring` §效果归因（no-skill 对照组）的分工：**那条管"要不要设对照才能说技能有用"**；本条管**没设对照时数字能不能报**——不能，且必须标明口径。与 `wb-artifact-verification` §声明边界写在数字旁边 是同一纪律的两种场景。

## 捷径债务台账：偷的懒要留升级触发器，否则延期会静默变永久（来源：dietrichgebert/ponytail·ponytail-debt，2026-09-15 实拉）
凡是"先简单做、以后再改"的捷径，落地时**在代码里留结构化注释**：`ponytail: <天花板——这个简化撑到哪>, <触发条件——什么信号出现就该回来重做>`。只写"待优化"没有触发器的债务 = **no-tag 腐烂债**，九成永远不会被还。收割：定期 grep 注释标记聚成一张台账（文件:行、简化了什么、天花板、触发条件），**没有触发条件的那几行单独标出来**——它们才是真风险。这条与「引依赖·退出条件」同源：**借的东西都要写清什么时候还**，无论是引的包还是偷的懒。

## 被要求绕开规则时：报一次、不纠缠、把例外写成文档（来源：openai/skills `security-best-practices` SKILL.md，2026-09-15 实拉）
项目文档或用户的明确要求可能与通用最佳实践冲突。处理顺序固定：
1. **说明一次**（这条实践是什么、绕开它意味着什么）→ 2. **不争论**（说第二遍就不是告知，是施压）→ 3. **照做** → 4. **把这次例外连同原因写进项目文档**，后续照此一致执行。
- 判据：**例外不落文档，就会在下次被当成"上次怎么没做"重新吵一遍**；落了文档，它就从"某次妥协"变成"已声明的决策"。
- 与 AGENTS.md 0.9（用户指令优先）分工：那条决定**听谁的**，这条决定**留下了什么**。

## 修复本身可能引入故障：按部署环境区分，一次只改一处（同源）
- **通用建议在错误的环境里就是破坏**：例如要求"cookie 必须带 secure"在纯 HTTP 的本地/测试环境会**直接让应用不可用**；强制 HSTS 一旦回滚困难会造成长时间不可用。给建议前先问**目标是什么环境**，不要用生产标准去套开发态，也不要反过来。
- **不安全的代码常常是有理由才活到今天的**：改之前先想清楚它现在被谁依赖、改动会不会造成回归、二阶影响是什么。**一次只改一个发现**；不要把多个无关发现塞进同一个提交（出问题时无法二分，回滚时被迫全退）。
- **最小有效修复**：先确定这段代码**必须强制的不变量**，然后在**最后一个可信的决策点**做**最窄**的改动；优先给出仓库相关的具体改动 + 回归测试，而不是"建议加强输入校验"这类通用加固。
- 与 §改现有代码：外科手术式 配套：那条管**范围**，这条管**位置与粒度**。

## 抽象不出来说"抽不出来"之前，先把例外变成数据；形状相似 ≠ 主体相同（来源：GitHub `edonadei/caliper`·`docs/adr/0020-a-backend-declares-its-chores-rather-than-performing-them.md`，2026-09-17 实拉）

- **"我这个情况特殊"不是保留私有副本的理由**：四个后端各自手写了同样的三件杂活（播种隔离 home / 定位 CLI 二进制 / 组装环境）。**它们之所以重复了那么久，是因为每个后端都有一个例外，而例外看起来像是保留自己那份的正当理由** —— 结果逐个检查下来，**每一个例外都能表达成数据**：`seed_files` 给一份 `(real, isolated)` 清单、`cli_name` + `cli_path_env_var` + `cli_candidates()` 给名字和候选路径、`env_passthrough` 给要透传的变量。
  - 判据：准备说"这个抽象做不了，因为我们情况特殊"之前，先问**"我的特殊之处能不能写成一行配置/一张表"**。能写成数据就别留副本 —— 基类做动作，各家只提供**那一个不同的事实**。
- **三份里的两份近似，不构成共享实现**：用户会在失败那一刻读到三句提示，它们共享"形状"但不共享"主体"（一句讲 API 计费且不命名环境变量，另两句命名安装命令与 `*_CLI_PATH`）。套模板会把这段散文压平，原文说这是 `the wrong thing to economize`。
  - 判据：**面向人读的失败文案不为省代码而模板化**。抽象看的是主体是否同一个，不是文字是否像 —— 两条近似不算共享实现。
- **顺序是契约的一部分，要写明，不能留给发现**：`_seed_home` 必须跑在 `_prepare` 之前，因为要重写配置的后端必须看到已经就位的逐字副本；**反过来看不出错，只会静默破坏两处**。
  - 判据：抽出模板方法之后，**步骤顺序要显式写进流程与文档**。抽得越干净，顺序越容易被后人调换，而调换是不报错的。
- **改了默认行为就记下来**：统一后 claude-code 从只透传 `TMPDIR`（还只在 macOS）变成和大家一样透传 `LANG`/`LC_ALL`/`TERM`/`TMPDIR`。原文给的理由是"一个后端和它的兄弟们不同、却没有任何记录的原因，正是这篇记录要反对的东西"。→ 统一带来的行为变化要**逐条写出来并说明理由**，否则下次排查时它会变成"看起来一直是这样的"。
