# wb-doc-writing（技术文档写作与评审）

来源：GitHub `riekelt/technical-writer`（同作者另有 `principal-engineer` / `multi-agent-review`，均已在前轮落地）——其 9 个技能里取 4 个方法论点：`technical-writing` 核心纪律 / `reviewing-technical-prose` / `writing-design-docs` / `recording-decisions`。整包不装，只取独有点（2026-09-15 实拉）。

**为什么单独立技能**：全库有"做事前的规约"（`wb-spec-driven`）、"教人"（`wb-teaching`）、"验生成物"（`wb-artifact-verification`），**没有"写给人看的文档 / 评审别人的文档"**——而写报告、写方案、审材料是高频真实需求。

## 〇、AI 写作工作流强化（来源：AIUnpacker《10 Prompts for Writing》2026-07-15 + EyeSift《Writing Prompts》2026-04-30 + aipromptshub《AI Content Workflow》2026-06-15 + PromptNest《Reescribe para que no parezca de IA》2026-06-05 + Toolin《内容创作实操》2026-04-17 实拉，与下文各节互补——本条管"初稿怎么生成/怎么迭代"，下文管"成稿怎么改/怎么评"）
- **文风锁定（voice-lock）**：让 AI 续写/改写前，贴 200-300 字**你自己以前的文字**做风格样本——这是保持"你的声音"的最低保障，其他技巧都是杠杆。
- **三阶段迭代，不一轮求完美**：第一轮出**结构**（大纲/子标题）→ 第二轮填**内容** → 第三轮**润色**；每一轮只做一件事，别让一轮 prompt 同时干三件事。
- **两遍编辑法**：①**结构事实遍**——有没有回答问题、每个主张真假、缺漏/重复（事实必须人验，模型不得 assert 未查证的统计/研究）；②**行编辑遍**——精简与声音。
- **去 AI 味清单（改稿时逐项查）**：句长均匀（要有长短变化）、AI 套话 tics（"不只是 X，是 Y"、三点并列清单、"在当今世界"、滥用长破折号、硬塞的总结段）。
- **精修只做减法**：让 AI 修稿时只删不增（删冗余、删套话），新增内容会导致原文失准。
- 判据：**AI 输出是初稿不是成品**——省 20-30% 时间合理，宣称省 80% 是营销话术；读出声检查开头、结尾与关键判断句，必须人来把关。

## 〇·一、AI 写作工作流强化二：精确任务 / 反思循环 / 过关四连（来源：PANACHES《Hybrid Workshop 2026》2026-08-24 + AppliedAI《Recursive Reflection》2026-05-15 + AI Tools《Writing Assistant》2026-05-17 + BuildFast《Claude Prompts》2026-06-20 + GPT Uncensored《Content Workflow》2026-07-18 实拉，与〇节互补——〇管"初稿怎么生成"，本条管"改稿用哪些具体动作"）
- **AI 只做精确任务，不整篇代写**：缩短一段 / 加强过渡 / 建议标题变体 / 简化句子 / 改错——每次都指名精确动作；整篇"帮我写"是最后手段。
- **反思循环三阶段**：Draft → **Critique**（按指定标准与视角，只列**具体编号缺陷**，禁"这能改进"式模糊语）→ **Rewrite**（逐条对应缺陷修改，保留原本在起作用的语气与结构，只动有问题的部分）。
- **诊断与动手分离**：critique 时不重写（模型诊断，人做删除决定）；润色时要选项（"3 个标题变体 / 3 个开头变体"）和损失问句（"删掉 X 段会损失什么"）。
- **修订先问后改**：给草稿后先指 3 个最大结构弱点（不是语法），问 2 个澄清问题，**答完才动笔**。
- **草稿过关四连**：①每个事实陈述对照源集，不支持就删或改；②删填充式确定性（AI 爱完美结论，真专业更条件化精确）；③每节加一个具体东西（观察/轶事/真实短语/有用反驳）；④收紧开头结尾（AI 开头过度解释、结尾硬总结）。

## 一、编辑即诊断（第一原理）
**编辑就是诊断。每一次编辑都要点名它修的那个具体缺陷；能修好它的最小编辑胜出。**

- **没有具名缺陷就改写自然或已批准的语言，这本身就是缺陷。** 看着"还能更好"不是缺陷；说不出改的是哪条问题，就不要改。
- 一次编辑只修一个具名缺陷，不顺手重排、不顺手改风格。
- **只改正文**：代码块、前言区（frontmatter）、表格数据、链接目标原样保留。
- **改写必须保持内容完全一致**——只许改表达，不许改事实。

### 控制三问（改写他人文本后必答）
1. **哪一句还像语言模型写的？**（语感自查）
2. **这次改写增加或丢掉了哪个事实、数字、日期、名称、来源、主张？**
3. **改写是否用新的修辞形式把刚删掉的模式又建了一遍？**

然后**把改写后的段落当源文本再扫一遍**（视角切换，防自证）。
> **增和删都算错，即使读起来更好。** 需要补事实才能把句子写完 → 去问作者，或换一句更简单的话。
> 同一句改两次还是僵硬 → 围绕该段主旨重写整段，不要继续磨单句。

### 逐字对照与评审语言
- **作者可达时，diff 就是提案**：先给改写稿再覆盖原文。不可达（仓库无人值守）时，commit 就是提案，评审做同样的事。
- **改写保持原文档语言**：荷兰语文档回荷兰文；英文特有的词表检查换成该语言自己的清单。

## 二、缺口标记法：删除 + 留洞，优于编造

三类标记，用途不同，都**不能**用编造或静默省略替代：

| 标记 | 用在哪 | 语义 |
|---|---|---|
| `**[source wanted: <该主张>]**` | 数字 / 事实**没有来源** | 事实保留，来源待补——**绝不编造引用，也绝不静默丢弃这个事实** |
| `**[input wanted: <该句应作出的主张>]**` | 源文本**没有可恢复的主张**（铺垫句、释义句、意义句） | 正确改法是**删除该句 + 留下标记缺口**，不是硬凑一句 |
| `**[DRAFT - input wanted]**` | 段落**未完成** | 显式声明未完成，而不是省略不写 |

- **一篇满是标记缺口的改写，"无主张源文本"场景下是预期结果，不是失败。**
- 未被标记的缺口才是缺陷；标记过的缺口是刻意的。

## 三、不受理清单：误报防护（评审纪律的另一半）

**"禁用构造清单"本身不证明任何东西**——这些模式在好的人类写作里同样出现。**只有当同一段落中多个迹象同时出现时，才标记。**

以下**不报**（除非同段落多处并发）：
- 抛光过的语法与一致的格式
- **一次**重复的句子开头（只在重复毫无增益时才修）
- **一个**用于强调的短句（只有成排的碎片才是问题）
- 一般性的正式词汇（清单点名的是**特定词**，不是所有正式词都该简化）
- **事实性对比**："流水线设标签，开发者不设"是陈述，不是对偶修辞
- **读者会真正权衡的严肃替代方案**——它属于文档
- **起限定作用的修饰**：范围、假设、安全与法律说明要留，只有**堆叠**才砍
- 迁移文档 / 发版说明里**对上一版情况的引用**——在那里"变化"本身就是主题
- **引号内的词**：引用、标题、讨论该词的例句里，一律不改
- **解释性的隐喻**：只砍它周围的装饰
- 刻意的笨拙：清晰的碎片句或不对称句，不因为"能被抛光"就成为缺陷

## 四、评审报告格式

- **判决写在第一行**，发现按最严重优先排序。
- **严重度词汇必须在使用它的报告里定义**：
  - **BLOCKER**：不能继续（硬规则违反；**任何所引来源不支持、或追溯不到任何来源的主张**）
  - **WARNING**：很可能返工（禁用构造、结构性缺陷：问句标题 / 结论被埋 / 段落可任意重排；主张只有松散支撑）
  - **OBS**：歧义、缺抛光、细心作者大概率自己会抓到的
- **每条发现**：一句话说明缺陷 + 位置（`file:line` / 章节 / 任务 ID）+ **建议修法** + **置信度**。
- **命名空情况**：无发现就明确写 `FINDINGS: none`，不留空。
- **文档主张被代码反驳 → 是文档的缺陷**，报出来并附上冲突来源；顺手看到的不相关 bug 不算你的发现（另开）。
- **重审只列剩下的问题**（已修的不复述）。
- **认可写得好的部分**——不只是挑错。
- 评审**全文**，不看摘要；不用评审去重开已定的决定、扩范围、或把文档改成自己的口味。

## 五、设计文档（提案类）

**设计文档 = 一份可以讨论的提案**：结论先行，每个非平凡选择进 Why & What 框，成本紧挨收益，事实与提案可区分。

### 骨架
```
# 标题：这份文档做什么
**一句话钉住范围的小标题**
| Status | Draft / Request for comments |
| Owner | [团队或角色] |
| Scope | [明确写出，含"什么不在范围内"] |
| Related | [同目录兄弟文档链接] |
| Audience | [谁必须读] |
---
1. Summary            ← 结论立刻给出（不是缘由，不是方法）
2. 背景 / 分析了什么
3. 分析（按问题拆章）
n. 开放问题            ← 每条要有 owner：人名、角色，或显式"待 X 填"
n+1. 收益与成本        ← 两者都要；只有收益 = 推销稿
n+2. 残留风险与"不要做什么"  ← 当设计把工作交给别的团队时才写
---
*收尾行：哪部分事实、哪部分提案、哪里需要输入*
```

### 结构规则
- **章节编号**，引用写 `ch. 7.1`。
- **目标与**非目标**都写**：非目标段说明什么保持不变。
- **有歧义的术语先定义后使用**（先把"已响应""符合条件""过期"钉死再往下写）。
- **一个 grounding 段**钉住设计依赖的事实：事实/来源表 + 对着**具名 commit** 核对过的标记；把已验证事实与将要构建的东西分开。
- **事实只住一处**：链接过去，绝不重复——同仓库跨文档也不重复。
- **开放问题要有 owner**；**残留风险与"不要做什么"**收尾（当设计把工作交出去时）。
- **没有行数预算**，但因重复或强调产生的长度要砍；**超过约 800 行就拆分**，主文档链接到各分册。
- 附录用字母编号（Appendix A/B），放会埋掉正文的东西：配置样例、术语表、清单。

### Why & What 框（每个非平凡选择一个）
```markdown
> **Why & What - [四个词概括这个选择]**
>
> **What:** [选择本身，一句话，不加论证]
>
> **Why:** [理由。同时写明这个选择**不解决**什么]
>
> **Alternatives considered:**
> - *[替代方案]:* [它最强的论点，以及为何仍然落选]
>
> **Fallback:** [这个方案不成立时，什么还活着]
```
- **被驳回却不给最强论点的替代方案 = 稻草人。** 那条最强论点必须写出来。
- **承认"这个选择不解决什么"会让文档更可信。**
- **没人会争的选择不设框**——那是噪音。
- **文档别处从未出现的替代方案，不属于这个框**（读者根本不会考虑它）。偶尔一个可以理解，**连着好几个短的 = 这个框在凑数**。

### 语气
- 文档**保持提案身份**："我们提议""是否信服由你判断"，不是"这将成为工作方式"。它定方向，把细节选择留开。
- **点名代价**：收益章节要以下面这些收尾——什么变难了、谁必须改掉旧习惯、哪项自由消失了。
- 无最高级、无承诺式语言；要具体数字与可验证陈述。
- **预期结果可以是否定的，而且要写在前头**："预期结果是当前队列打败提议的重写，这也是有用的结果。"

### 完备性检查（交给评审者/执行者之前查五类含糊缺陷）
| # | 缺陷 | 判据 |
|---|---|---|
| 1 | **未解决的占位符** | 任何字面 TBD / TODO / "稍后补" / 明显不完整的句子（**带标记的 `[DRAFT - input wanted]` 块是刻意的；未标记的缺口才是缺陷**） |
| 2 | **缺验收标准** | 有要求，但没有具体、可独立验证的成功条件 |
| 3 | **未定义的引用** | 提到了某类型 / 端点 / 组件 / 表，但全文没有定义 |
| 4 | **无可验证产物** | 这个任务产不出评审者能检视的东西（无文件路径、无命令、无可观察行为） |
| 5 | **有 what 无 how** | 有结果、无实现方向（"妥善处理错误"而没定义什么叫妥善） |

> 第 1–3 项与 `wb-spec-driven` §三·十「执行前评审·完整性镜头」同源，那边管**动手前的 spec**；本节管**要给人看的文档**。**第 4、5 项是本技能补的增量**（那边没有）：任务必须产出可检视的东西，且"what"必须带可实现的"how"。
> 执行计划类文档额外按任务列：目标、确切文件、改动展示、带具体场景的测试、验证命令。**任何让人困惑的遗留物**（怪异的目录名、旧别名）要解释，不要留着让人猜。

## 六、记录决策：ADR 与决策日志

**两种格式按重量分**：有架构级后果的决定写完整 ADR；日常小决定的流水写决策日志条目。**两者都是 append-only**：已接受的决定不可变，新情况写新条目覆盖旧条目。

- **先记录再引用**：聊天不是持久来源。把带日期的实质内容写进台账 → 引用决策者原话（措辞重要时）→ 提交条目 → 然后才引用它。**记录最小的完整决定，不是转录。**
- **主动捕捉"正在溜走的未记录决定"**：出现"我们决定用 X 不用 Y""就这么定吧"、在 PR 评论或聊天里解决掉的权衡、**有人已经解释过第二遍的理由** → 提议记录下来。
- 不适用于"还在争论中的决定"（那是设计文档；它的 Why & What 框在决定被接受后就变成 ADR）。

### ADR（Nygard 格式，一决定一 ADR）
```markdown
# ADR-[编号]: [决定的短标题]
| Status | Proposed / Accepted / Superseded by ADR-XXX |
| Date   | YYYY-MM-DD |
| Deciders | [参与的人] |

## Context
[起作用的力：技术、组织、政治。要解决什么。陈述事实，不提前泄露决定。]

## Decision
[决定了什么。主动语态："我们在 tag 上发版"，不是"据说决定…"]

## Consequences
**Positive:** [什么变容易]
**Negative:** [什么变难，我们接受哪个权衡]
**Neutral:**  [什么变了但无所谓好坏]

## Alternatives considered
**[替代方案]** - For: [...] Against: [...] Why not chosen: [...]

## References
[证据、相关决定、度量]
```

- **Negative 是强制的，且不得为空。**
- **每个替代方案都要带"它最强的一条支持理由"**，没有它的驳回就是稻草人。
- **已接受 ADR 唯一允许的编辑，是 Status 行加上 "Superseded by ADR-XXX"。**
- **被提出但从未被回答的反对意见，要以全强度写进 Negative 后果，并指定具名 owner**：作者**永不**自己编造反驳，**永不**隐瞒 owner 已宣布的决定。（"owner 已决定，我们照办"也是一种记录，不要美化。）
- **写的时候还不知道的人名要标成"归档前补"**——归档记录承载的是真人。
- 当**书面规则与已上线现实已经分叉**，记录团队意图的是哪一个。
- 每份教义文档声明**它拥有什么、它留给别人什么**（scope guard，例："产品想法住 ROADMAP.md；本文件只放工程决定"）。

### 决策日志（轻量流）
```markdown
## YYYY-MM-DD
### [用祈使句陈述的决定]
[一段话：规则是什么。]
Why:
- [理由]
Instead of: [被否掉的选项] - [为何不选]
```
- **append-only**：写错的那条**新增一条带日期的条目去覆盖它，永不编辑**；**相对日期一律转成绝对日期**。
- **记录 why，不只 what。**
- **负面结果与未知要显式捕捉**："四个理论、四个被证伪，原因没找到"**是结果**；"检索无结果"**也是结果**。

## 七、交付前清单（压缩版）

- [ ] **与同目录既有文档匹配**，且已加进 `README.md` 索引（若有）
- [ ] **结论先行**（文档、章、段三层都是）
- [ ] **标题命名内容**：不用问句形式、不用"What X 意味着"、标题不在它的第一句里重复
- [ ] **术语一致**、首次使用处定义；一个概念一个词
- [ ] **每个带数字的主张都能追到文档里点名的来源**
- [ ] **引用逐条跟着点开验证**：章号、相对链接、文件名确实存在（"看过"不算，**点开过**才算）
- [ ] **事实与提案可区分**；估算有标签；未知显式写成未知
- [ ] **提出或决定之处**：每个非平凡选择都有理由、有严肃替代方案，且**成本在内不只收益**
- [ ] **去名测试**（开头与摘要）：删掉产品名，陌生人仍能看出这份文档在讲什么
- [ ] **冷读、整读**：对从没看过这场对话或这些反馈轮次的人读得通；全文一个声音，无拼接缝，**没有哪句话在解释"这份文档为什么要这么写"**
- [ ] 改写稿：**没有增加或丢失任何事实、数字、日期、来源**

## 八、页面是检索面，不是文章（来源：fission-ai/openspec `write-openspec-docs` SKILL.md，2026-09-15 实拉）
- **结构决定读者能不能找到答案，文笔只决定读起来如何**。每一节**以答案开头**，永远不要用一段铺垫把它引出来。
- **一槽一事实**：一句一个事实，列表引导句只负责预告列表；相关的事实**自己另起一槽**，不搭别人的车。
- **承重事实必须落在扫描锚点上**：代码围栏、编号加粗引导、`**术语**：事实` 条目、表格、文件树——**绝不能只出现在段落中间**。
- **先写最短可答的版本**：扩展一篇薄的便宜，删一篇臃肿的是重写。多数人会跳过的深度内容放到链接后面。
- 两个收尾自测：① **可检索性**——每个问题或确切名称，光靠扫视能不能找到？② **一眼成形度**——把渲染后的页面当形状看，像"能读完的"还是"像一堆活儿"？表格改动的桌面与窄宽都要看。

## 九、事实核查走干净上下文，且默认只报不改（来源：fission-ai/openspec `verify-openspec-docs` SKILL.md，2026-09-15 实拉）
- **为什么必须是干净上下文**：核查者**没有亲眼看着这篇文字被写出来**，所以不会被作者的假设带跑。独立性的本质是"没接触作者推理"，不是"必须开子代理"。
- 子代理**不继承技能**，所以提示词必须把材料**按绝对路径**全部交待清楚，不留占位符。
- **核查要复跑**：只读命令照跑；会改状态的只在临时目录跑或干脆不跑；跑不了的命令（如聊天面指令）**对照源码核名字与行为**。**文档里的输出块必须与命令真实输出逐字一致**——写了没跑过的输出，等于给读者一个假的锚。
- **便宜核实不了的事实照样写，但要标"未核实"**；**绝不用一句听起来合理的句子把洞补上**（与 §二 缺口标记同源）。
- **默认报告、不重写**：每条发现给"引用原句 + 错在哪 + 一行修法"，并说明**你验了什么、怎么验的、哪些没验成**。
- **核查者也会错**：被你驳回的意见要**连理由一起写进报告**，让用户可以推翻你。
- 改过事实性主张 → **按变更范围再验一遍**（拼写措辞不用）；**两轮不收敛就停下来交给人**。

## 十、按"读者任务"分页，拆分时保留旧锚点（来源：OpenClaw 官方 docs《QA overview》，2026-09-16 实拉）
长文档拆成多页时，两条硬规则：
- **分页维度是"读者要干什么"，不是"内容怎么归类"**。原文：整节拆成 8 页，**one page per reader job**（要看命令 → Command surface；要跑 lane → Operator flow；要读报告 → QA reporting）。按内容结构分页的结果是所有人都得翻完全部页面。
- **搬走的内容必须保留旧锚点**：原文明确"每个旧小节标题的 anchor 都留在原处，旧链接仍可解析"。**文档一拆，外部链接、历史回答、别人记的笔记同时失效**——留锚点是拆分的成本，不是可选优化。
- 配套：索引页只做**任务 → 页面**的路由表（一句话说清"什么时候看这页"），不要在索引页里重复正文内容（与 §八 页面是检索面 同源：重复两份必然过期一份）。

## 反模式
- 说不出改的是哪个具名缺陷就动手改 → 违反 §一
- 为了句子好读悄悄补了一个事实 → 违反 §一（增和删都算错）
- 事实查不到来源 → 删掉或编一个 → 违反 §二（正确做法是 `[source wanted]`）
- 看到破折号 / "不仅仅是"就判 AI 味 → 违反 §三（要同段落多迹象同现）
- 替代方案只写"被否了"不给最强论点 → 违反 §五（稻草人）
- ADR 的 Negative 写"无" → 违反 §六
- 接受了 ADR 又去改正文 → 违反 §六（只许改 Status 行）
- 决策日志改错条目而不是新增覆盖条 → 违反 §六
- 引用链接没点开就写"已验证" → 违反 §七

## §十 复制来的断言要在新目标上重新取证；逐字搬移要保住块形态（来源：neolabhq/context-engineering-kit·`reground-transplanted-doc-claims.md` + `verbatim-move-keeps-block-form.md`，2026-09-17 实拉）
原文：`When documenting a second command, agent, or module by mirroring the structure of its sibling's page, re-verify each transplanted sentence against the NEW target's own source file before keeping it. A claim that is true for the sibling reads as authoritative on the target's page and is indistinguishable from a verified fact, so a false transplant is worse than an omission.`
`When an instruction says to move or inline content **without summarising or rephrasing**, copy every block in its original form — tables stay tables, fences stay fences — even when a block restates something already stated elsewhere in the destination. Judging a block redundant and folding it into prose is an edit, not a move ... If a block really is duplicated, report the duplication and let the reviewer decide; do not resolve it inside the move.`

- **从兄弟文档/模块镜像结构时，每一句复制过来的断言都要对新目标自己的源文件重新取证**：原文档说"这个命令会暂存输出"，搬到兄弟命令的页面上就必须 `grep` 那个命令的实现，确认它真的有这一步。→ 判据：**假移植比遗漏更糟**——遗漏只是少一条信息，假移植在新页面上读起来和已核实的事实一模一样，没人会去怀疑它。
- **镜像写法的正确顺序是"先取证，再落笔"**：照着结构写是允许的，**照着结论写不允许**。→ 判据：只有**目标文件本身**能支撑的句子才留下，其余删掉或改正。
- **"逐字搬移/内联"是形态保全令，不是内容整理许可**：要求不改写地搬一段内容时，**表格还是表格、代码块还是代码块**，哪怕它和目标处的另一段重复。→ 判据：**把表格折成一句散文 = 把"读者扫一眼能找到的表"改没了**，而且这个改动藏在一份"看起来忠实搬运"的 diff 里；**判断冗余并合并是编辑，不是搬移**。
- **真重复要上报，不在搬移里顺手解决**：发现重复就写进报告，让评审决定留哪份。→ 判据：**去重是需要授权的取舍**；搬运者替评审合并掉，等于在"什么都没改"的表象下改了东西。
  - 与 §九（干净上下文核查）的分工：那条管**核查已写内容**的纪律（核完只报不改）；本条管**从别处复制内容**时的取证义务与形态保全。
- 反模式：照抄兄弟页面的描述句；把"另一处已经写过"当作可以折成散文的理由；搬移后在报告里写"内容未改动"却改了块形态；发现重复直接合并而不告知。
- **提升层**：可复用 Skill（文档复用 / 内容搬运）。

## §十一 术语表与决策记录：两类产物两套门槛；膨胀的修法是删不是拆（来源：GitHub `mattpocock/skills`·`docs/engineering/domain-modeling.md`，2026-09-17 实拉，★263k）

- **ADR 准入三门槛，缺一就不写 ADR**：① 难逆转（hard to reverse）② 没有上下文会让人意外（surprising without context）③ 是真实取舍的结果（result of a real trade-off）。反着看：易逆转的决定会被直接逆转，写它没用；不意外的没人会问；没有真实备选的，记录的只是"你做了显而易见的事"。
- **一个文件只允许装一种产物**：术语表只装术语——"它是什么"一两句，加一组 `_Avoid_` 拒用同义词；不装实现细节、不装 spec、不做草稿本、不收通用编程概念。与 ADR 混同是这类文档最主要的故障源。
  - 具体失效模式：**模型把"写入术语表"当成"把每个答案都持久化下来"的许可**，文件于是变成一份滚动的 spec。原文称这是跨多个模型报告最多的问题。
- **膨胀是症状不是病因**：术语表长到几千行，病因是它吸收了实现细节和本不属于它的决定。**先删到 lean，再谈拆**——拆分一个臃肿文件只会得到几个臃肿文件。拆分的正当理由只有一个：lean 之后仍覆盖两个读者不愿同时持有的域。
- **内联写，不批量写**：术语在对话里**确定的那一刻**写进去，不攒到收尾时产出整洁的术语表。批量版是"会话的摘要"，内联版是"会话的真实产出"。
