# wb-loop-engineering（循环阶段：越跑越好）

来源：WaytoAGI 精选 2026-09-03《人人都能学会的自进化 Agent 搭建指南》。
核心判断：**周期性任务的价值不在单次结果，在于下一轮比这一轮更准。**

## 四段循环
1. **采集**：定时拉取固定信源，范围固定、可复现，不靠临时起意
2. **沉淀**：把结果写进文件（记忆目录 / 表格 / 知识库），不留在上下文里——上下文会丢，文件不会
3. **反馈**：三类信号必须捕获，且写回文件，不是只在当前会话生效
   - 用户纠正 / 批注 / 否决
   - 环境变化（站点改版、命令失效、依赖升级）
   - 重复命中（同一内容连续多轮出现 → 说明筛选规则过宽，收窄它）
   - **用真实反馈驱动收敛，而非自评**（来源 WaytoAGI 精选 2026-09-10《Grok Bot 产品负责人：几人 30 天做出产品》）：改进方向优先来自**真实用户 / 真实运行结果**的陪跑与反馈（哪一步真卡住、哪个界面真被弃用），而不是 agent 自己的"我觉得哪里能优化"。自评容易自洽地绕开真问题；真实反馈会撕开它。落到本循环：每轮先收集外部信号（用户纠正、运行失败、复用语料的偏离），再据此改模板/阈值，**不靠主观判断凭空收敛**。
4. **迭代**：每轮结束时更新筛选逻辑、模板、阈值；候选池只增不减，用掉的划掉

### 硬规则：用户指定信源清单必须全量实拉（零省略）（用户 2026-09-13 强制，原话"我让你打开的都必须全部学完 一个都不能少"）
> 细则（路径阶梯 / 失败根因诊断 / 反模式）已独立成 **`wb-execute-discipline`**，本节为循环场景的应用摘要；两者冲突时以 `wb-execute-discipline` 为准。
- 用户点名过的**每一个**信源站点 / 仓库，每轮循环都必须**真实访问、真实评估**，**一个不能少**：不得用"每轮抽 ≥2 个轮换"代替全表；不得用"上轮已访问 / 已评估过"代替本轮实拉；不得以"该站无方法论深度"为理由跳过访问（结论必须来自本轮实拉）。
- 访问失败（被墙 / Cloudflare / 403 / 超时）**不等于放弃**（用户 2026-09-13 追加，原话"失败了你要继续进去学习 不能失败了就放弃"）：必须**逐级换路径继续攻**——① WebFetch 换镜像/备用域名/API 端点 → ② 浏览器渲染通道（agent-browser / playwright，可过部分 bot 检查）→ ③ 该站点的公开镜像或替代入口。每级都试过仍失败才标注"本轮未达"留待下轮，**不算学完**；只要有一条路没试，就不许写"放弃/跳过"。
- **同一目标失败 ≥2 次必须先停手诊断根因**（用户 2026-09-13 强制，原话"如果失败2次以上要思考为什么错 不能一直错误的方式进行下去"）：写出"为什么错的假设"（缺依赖？被沙箱杀子进程？路径本身不可达？参数/顺序错？），先用最小探针验证假设（查安装态 / 查进程 / 单独测可达性），**纠正后再试新路径**；禁止对同一命令原样重试、禁止在未诊断前加超时硬冲。根因结论写进留痕（可复现根因=环境结构性限制，标注"非重试可解"+解法归属（如需用户开 VPN / 手动装 Chromium））。
- "学完"的判定 = 本轮实拉 → 逐条评估 → 有独有点就落地 / 无独有点记录判据。任何省略、抽访、以旧代新，都算违反本规则。

### 沉淀什么：记忆三分法
来源：deeplearning.ai short-course《Long-Term Agentic Memory With LangGraph》（LangChain, Harrison Chase）。
"沉淀到文件"不是把一切都写下来——**分三类写，位置不同、更新频率不同**：
| 类型 | 内容 | 落到哪 | 更新时机 |
|---|---|---|---|
| **语义记忆**（事实） | 用户偏好、项目约定、环境事实（路径、命令、坑） | 记忆文件 / 知识库 | 发现即写 |
| **情景记忆**（案例） | 具体一次的对错示例、用户纠正的原话场景 | 记忆文件里的"案例"段 / few-shot | 发生后写 |
| **程序记忆**（规则） | 该怎么做事的流程与约束（skill、AGENTS.md、自动化 prompt） | skill / 长期指令文件 | 同类问题重复出现才升级写入 |

**两种写入时机，别混**：
- **热路径**：交互当下就写（用户刚纠正你、刚发现命令失效）——**不能省**，会话一断就丢
- **后台**：一轮/一天结束时批量整理（去重、合并、升格为规则）——**只做整理，不产生新信息**

判断升格的信号：**同一类事实/案例出现 2 次以上 → 从语义/情景记忆升格为程序记忆（写进 skill 或长期规则）**。只出现一次的留在记忆里别动，写进规则就是噪声。

**四层记忆扩展（来源 DeepSeek 插件 `MemOS` #5）**：上面的三分法是"按内容性质"分；当记忆量变大，可改用 MemOS 的四层——**轨迹（L1，每次操作的原始记录）/ 策略（L2，做事方法）/ 世界模型（L3，对外部系统/工具/环境的认知）/ 技能（L4，可被直接调用的能力单元）**。世界模型层补了"agent 对工具与环境怎么运作的认知"这一维，技能层补了"能直接复用的能力单元"。两套可叠加：三分法决定"该不该写规则"，四层决定"写进哪一层"。

### 长期知识库：三层 + 三种操作
来源：合并自旧 skill `llm-wiki`（Karpathy 模式）+ WaytoAGI 精选 2026-09-04《2026 我的 Obsidian 完整分享》。
当资料量大到"记不住、每次重读"时，用**持久 wiki** 替代每次检索（RAG）：

**三层，权限各不相同**
| 层 | 内容 | 谁写 |
|---|---|---|
| **原始层 raw** | 原文、论文、截图、数据文件 | **不可变**，只读，是事实验证的最终依据 |
| **整理层 wiki** | 摘要页、实体页、概念页、对比页、综述 | **agent 独占写入**，人来读 |
| **规则层 schema** | 目录结构、页面模板、交叉引用规则、分类 | 人与 agent 共同演进 |

**三种操作**
1. **Ingest（摄入）**：读一份新资料 → 写摘要页 → 更新索引 → 回改受影响的实体/概念页 → 追加一条日志。一份资料常牵动 10+ 页；**一次只摄一份**，保证质量
2. **Query（提问）**：先读索引定位相关页 → 综合回答并附引用 → **好答案要归档回 wiki**（对比、分析、新关联不能烂在对话里）
3. **Lint（体检）**：定期查——页面间矛盾 / 被新资料推翻的旧结论 / 无入链的孤儿页 / 反复提及却没有独立页面的概念 / 缺失的交叉引用 / 可补的数据缺口

**硬要点**
- 日志用统一前缀，可 grep：`## [YYYY-MM-DD] operation | Title` → `grep "^## \[" log.md | tail -5`
- 知识是**复利资产**：每摄入一份、每问一次，都应该比上一次更厚
- 目录本身就是一个 git 仓库 → 免费获得版本历史；图片要**下载到本地**，不留外链（外链会失效）
- 三层落点：`raw/` 只增不改，`wiki/` agent 全权维护，`WIKI-SCHEMA.md` 记录约定

**落地细节（合并自 llm-wiki 的独有条目）**
- **默认落点**：`~/.workbuddy/wiki-knowledge/`。用户提到"我的知识库/wiki"时**先查这个路径**，若已存在 `WIKI-SCHEMA.md` 就直接用、不要问路径；只有用户明确要另建时才问
- **初始化四步**：① 建结构 `raw/`（含 `assets/`）+ `wiki/`（含 `index.md`、`log.md`）+ `WIKI-SCHEMA.md`；② `index.md` 是目录，每页一行（链接 + 一句话摘要 + 元数据），每次摄入后更新；③ `log.md` 只追加；④ `WIKI-SCHEMA.md` 与用户共同演进
- **页面模板**：frontmatter 写 `title / type(entity|concept|source-summary|comparison|synthesis) / created / updated / sources / tags`；正文用 `[[wiki-links]]` 交叉引用，末尾固定 `## See Also` 列出关联页
- **查看与产出**：Obsidian 当查看器（graph 看连接、Dataview 查 frontmatter）；Marp 可从 wiki 生成幻灯片；Obsidian Web Clipper 把网页转 markdown 便于 ingest；图片下载到固定附件目录
- **适用场景**：个人（日记/播客笔记 → 目标与自省）、研究（论文/报告 → 实体与演进论点）、读书（章笔记 → 主题与线索）、业务（会议记录/文档 → 内部知识库）、竞品分析（报道/新闻 → 对手档案与对比）、课程（讲义 → 概念图）

> 区别于本技能上面的「记忆三分法」：三分法是**按内容性质**分（事实/案例/规则），这里是**按加工深度**分（原文/整理/规则）。两者叠加用——raw 对应原文，wiki 对应语义+情景记忆，schema 对应程序记忆。

## 经验固化：从轨迹到可复用技能
来源：deeplearning.ai short-course《Building Adaptive AI Agents》（Oracle）。
**每轮跑完只更新筛选逻辑是不够的——踩过的坑如果不固化成技能，下一轮照样踩。**

- **轨迹 → 技能**：一次成功的非平凡操作（绕过某个坑、找到某种可行路径）跑完立刻固化：写进 skill / 脚本 / 记忆文件，附触发条件。**同一类问题手工解决第二次，就说明第一次白解决了。**
- **代码知识图谱 / 索引 > 全量重读**：长期项目维护一份结构索引（模块职责、入口、依赖、已知雷区），每轮只读相关切片，不要每轮从零把代码读一遍。
- **三个改进杠杆，按顺序用，别跳级**：
  1. 改**技能/提示词与流程**（最便宜，先试）
  2. 改**检索与上下文**（agent 找不到东西，多半不是笨，是没喂到）
  3. 才考虑换/调**模型本身**（最贵，且常常掩盖前两步的问题）
- **写入前的三道门（可迁移自 `cangjie-skill` 阶段 1.5 三重验证）**：不是所有学到的都配写进技能，先过三问——
  1. **跨源（V1）**：同一方法在**不同来源 / 不同场景**出现过 ≥2 次？同一案例换个说法不算（这与上面"出现 2 次以上才升格为程序记忆"是同一条线）
  2. **预测力（V2）**：能用它推出原文**没直说**的问题的答案吗？只能复述原文例子 = 那是描述不是方法
  3. **独特性（V3）**：抹掉出处与作者名，还是"聪明人都会说的常识"？是 → **不写**，模型本来就会，写进去只占上下文
  - 三问有一条不过是常态；**通过率过高反而说明门槛太松**。没过门的留在候选池，不直接写成规则
- **写完必须验触发**：新技能 / 改过 description 的，走 `wb-skill-authoring` 的「触发评测盲测」（正例 + 诱饵 + 跨技能混淆），没测过不算可用
- **固化前先查同类**：新能力若与已有 skill 相近 → 合并成更强的那一个，再删被完全覆盖的；并列堆叠同类 skill = 下次不知道该用谁。
- **源头是长内容时走专用通道**：要把**书 / 长视频转写 / 播客 / 课程 / 访谈**这类长材料蒸馏成一组可执行 skill，用已装的 `cangjie-skill`（RIA-TV++ 流水线：整书理解 → 并行提取 → 三重验证 → 晋级门 → 能力卡 → 压力测试 → 编译交付），不要用手写的临时拆解流程。

## 多步链路：角色 + 交接介质 + 关卡
来源：WaytoAGI 精选 2026-09-08《用 Grok Bot 搭建自媒体团队》（情报 → 选题 Brief → 写稿 → 事实审校 → 人工发布 → 数据复盘）。
单次会话塞下全流程 = 每步都打折。按以下拆：
- **固定角色，不临时起意**：每步一个明确角色（采集者 / 选题者 / 执行者 / 审校者 / 发布者），角色职责写死在 prompt 或 skill 里
- **共享文件是唯一交接介质**：上一角色的产出落成文件（brief / 草稿 / 表格），下一角色只读文件，不依赖"同一个会话还记得"
- **审校关卡**：交付/发布前必过一道独立校验——事实、数据、引用是否站得住；审校者不自己改稿，只标记问题退回
- **人工放行关卡**：对外动作（发布、发信、push 到共享分支、下单）必须停在人工确认点，链路不自动跨过
- **多角色写同一文件必须带入口戳**（来源：addyosmani/agent-skills #546「name the entry point when several write to one log」）：调度器、重放、手动补跑等多条路径写**同一个**共享文件/日志时，每条记录开头标**写入者 + 入口**（谁、从哪条链路来），并随交接向下传播——不标的话事后无法归因某条记录出自谁，只能靠排除法对着外部记录倒推（调度历史、进程表……碰巧还在才能查）。与"共享文件是唯一交接介质"配套：**介质共享，署名不能共享**。
- **复盘指标固定**：每轮记 1–3 个可量化指标（命中率、返工次数、耗时），用指标判断链路是否变好，不靠感觉

### 多 Agent 协作：依赖图驱动 + 工具策略
来源：DeepSeek 插件 `dsh-agent-teams`(#27) / `Wegent`(#25) / `Polaris`(#69)。
- **依赖图驱动推进**：多角色链路不是固定线性顺序——把任务写成 DAG（谁依赖谁的产物），无依赖的并行跑，被阻塞的等上游完成再启动；比"固定顺序逐个跑"省时且不会因某一步卡死而全链停摆
- **每 Agent 工具 allow-list**：每个角色只声明它真实需要的工具集合，超出即拒——写稿角色不需要 shell，审校角色不需要写权限；最小权限防误操作也防角色越界
- **跨 agent 共享记忆/交接**：本机多个 AI 工具栈（WorkBuddy / Claude Code / Codex）需要共享身份、规则、记忆与交接消息时 → **`agent-guild`**（`~/.agent-guild/`，纯本地 Markdown/JSON；`ag bootstrap` 读全量、`ag send` 交接、`ag learn` 跨 agent 学习台账）。**与现有记忆分层不替换、不双写**：AGENTS.md 三层仍是单 agent 权威源，guild 只放跨 agent 交接与共享事实

## 收尾分支（硬性）
任何周期性任务都要显式列出收尾动作，且**成功 / 失败 / 跳过 / 中断 四个分支都必须走到**：
- 释放外部资源：进程、代理、临时目录、锁
- 还原环境：代理设置、环境变量、工作目录
- 落痕迹：一行记录（学了什么 → 改了什么 → 版本 hash）
- 校验：确认释放与还原真的生效（查进程、探活 URL），不假设成功

## 优化前先分型：策略问题 / 能力问题 / 模型问题
来源：Dify 插件市场（2026-09-13 实访）把 **Agent Strategy** 与 Tools 拆成并列的两类一等公民插件（分类为 Models / Tools / Data Source / **Agent Strategy** / Triggers / Extensions）——**"怎么决策"和"能用什么"是两个可独立替换的层**，不是一回事。

三类问题对应三个不同修法，混着改等于白改：
- **策略问题**（怎么决策/怎么迭代）：一次性直出该改成"生成 → 自评 → 迭代"；线性该改成"先规划再执行"；缺复核关卡 → **换策略，通常零新增工具**
- **能力问题**（能做什么）：缺工具 / 缺数据 / 缺检索源 → 补工具或补检索，**不要去动流程**
- **模型问题**：换模型能解决的极少，且最贵 → 前两类排查完再考虑

判据：**同一套工具换个跑法结果就变好 = 策略问题；工具齐了仍然做不到 = 能力问题。** 先做这个判断，再决定动哪一层。
反模式：表现不好就先加工具 / 加参考文档 / 换大模型 → 工具越堆越多，真正的瓶颈（决策流程）始终没被碰到。

## 反模式
- 每轮从零开始、不读上一轮记录 → 重复踩同一个坑
- 只在会话内记住用户纠正 → 下一轮照犯
- 没新东西时硬凑改动 → 改为回溯候选池挑旧的落地
- 收尾只写在成功路径 → 失败时留下僵尸进程
- 全流程塞进一个会话、靠上下文传递中间产物 → 中途一断全盘重来
- 审校和执行是同一个角色 → 自查永远查不出自己的盲点
- 只复盘"这次感觉如何" → 没有指标，链路不会真的变好
- 坑只在当前会话解决、不固化成技能 → 下一轮原样再踩一遍
