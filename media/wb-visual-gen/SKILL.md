# 生成类视觉任务工作流

核心原则：**先定验收标准，再生成**；出错时**定向改**，不重抽卡碰运气。

## 一、五步流水线

| 步 | 动作 | 产出 |
|---|---|---|
| 1 定标 | 把模糊需求拆成可检查项（主体/场景/光线/构图/文字/用途/尺寸），与用户对齐 | 验收清单（见第三节） |
| 2 备料 | 收集参考图、品牌色、文案原文、真实地名/人名；**没有参考就先问或先找，不脑补** | 素材清单 |
| 3 写 prompt | 按通用公式 + 取案例库骨架；默认英文，中文场景保留中文原词 | prompt + 负向约束 |
| 4 生成 | 一次出 1–4 张候选，参数与 prompt 一并记录 | 候选 + 生成记录 |
| 5 验收迭代 | 逐条对照清单自评 → 定位到具体哪一项不达标 → 只改对应变量/参数 → 重生成 | 通过 / 明确卡点 |

**改图（图生图 / 局部编辑）比重新生成高效**：整体构图对、局部不对 → 走局部编辑；整体跑偏 → 才重生成并改 prompt。

## 一·五、输出形态：可控性与灵活性成反比
来源：deeplearning.ai short-course《Build Interactive Agents with Generative UI》（CopilotKit, Atai Barkai）。
**先选产物形态，再选生成方式。** 三档，越往右越灵活、越不可控：
| 档 | 做法 | 可控性 | 什么时候用 |
|---|---|---|---|
| **受控** | 自己造固定组件（图表 / 卡片 / 表单模板） | 最高，样式与字段完全掌握 | 结构固定、要品牌一致、要能长期复用 |
| **声明式** | agent 从一套可复用积木里组合布局 | 中，组合自由但积木受控 | 内容结构多变但要素有限（如报告页、看板） |
| **开放式** | 从零生成界面 / 图形 | 最低，最容易跑偏 | 探索性、一次性、无既有模板可用 |

判断口径：
- **能用受控/声明式解决的，不要上开放式**——开放式看似方便，返工与验收成本最高
- **用户要"能看见、能操作"的产物时，别只给纯文字长段**：该出表格出表格、该给图给图、该做可交互页面就做（这也是 `show_widget` 存在的原因）
- 用开放式生成时，必须先有验收清单（本 skill 第三节），否则无法判断"生成得好不好"

## 二、通用 prompt 公式（生图）

```
主体（人/物 + 具体特征：脸型、发型、肤质、服装）
+ 场景（地点 + 时间 + 环境细节）
+ 光线（光源类型 + 方向 + 色温/色偏）
+ 镜头（焦段/画幅/景别/构图比例 9:16 或 16:9）
+ 材质与质感（胶片颗粒、皮肤毛孔、布料褶皱）
+ 风格参考（35mm film / watercolor / studio photobook）
+ 负向约束（no plastic skin, no airbrushing, no watermark, no text）
```

硬性写法：
- **只替换变量，保留句式结构**——句式是可迁移骨架，改句式 = 丢效果
- 画面有文字：写明「字迹清晰完整 / no watermark」**并重复强调**（最易出乱码字）
- 多图一致：必须带 `100% consistency in ..., identity across all frames`

## 三、验收清单（生成后逐条过，不过就改）

| 检查项 | 不通过的表现 | 定向改法 |
|---|---|---|
| 主体对不对 | 人物/产品特征错、数量错 | 改主体描述，细化到脸型/服装/数量词 |
| 文字对不对 | 乱码、缺字、多字、错字 | 减少画面文字量 + 重复强调清晰；长文改后期排版叠加 |
| 构图/尺寸 | 主体被裁、比例不符 | 显式写画幅比例 + 景别（wide/close-up） |
| 风格一致性 | 多张风格漂移 | 固定风格参考词 + 一致性约束句 |
| 光影质感 | 塑料感、过曝、脏 | 加负向 `no plastic skin / no airbrushing` + 光源描述 |
| 用途适配 | 好看但不能用（无留白、无安全区） | 补用途约束（留白/横竖版/印刷尺寸） |
| 合规 | 伪造截图、真实人物代言、无 AI 标识 | 见第五节红线 |

**"什么算做完"**：清单全过 + 用途可交付（尺寸/格式/标识齐全）。用户没说用途 = 未定标，先问。

## 三·五、网页 / UI 生成：反 AI 味设计基线

来源：GitHub `Leonxlnx/taste-skill`（Anti-Slop Frontend Skill，AI TELLS 禁令 + 62 项 Pre-Flight）。
**适用：交付的网页/前端页面，以及 `show_widget` 输出的内联 HTML/SVG 视觉**——同样的"AI 默认审美"在这里一样会犯。
判据：**模型默认的不是设计选择，是没做选择。** AI 味的本质是把"生成器最常输出的样子"当成了方案。

### 硬禁（见到即改，不要等用户提）
| 类别 | 禁 |
|---|---|
| 配色 | AI 紫渐变、霓虹外发光、纯 `#000000`/纯 `#ffffff`、过饱和强调色；**全页最多 1 个强调色，饱和度 <80%** |
| 布局 | **三等分 feature 卡片横排**（最高频 tell）→ 改 2 列 zig-zag / 非对称网格 / bento；同一布局家族全页最多用一次；zigzag 不得连续 3 个 section |
| 字体 | 默认 Inter（+ slate-900 中性色）；`Fraunces`/`Instrument_Serif` 作 display serif；sans 标题里插随机 serif 单词（强调用同族的 bold/italic） |
| 假内容 | `John Doe`/`Acme`/`Nexus`、SVG 蛋形头像、`99.99%`/`50%` 完美数字 → 用有语境的真名与"有机"数字（如 `47.2%`） |
| 假截图 | **用 div 矩形拼的假终端 / 假 dashboard / 假任务列表 = 头号 tell**，宁可不做预览 |
| 装饰垃圾 | section 编号 eyebrow（`001 · Capabilities`）、hero 版本标签（`V0.6`/`BETA`）、滚动提示（`Scroll ↓`）、装饰彩点、图片上叠 pill、照片版权 caption、hero 底部装饰文字条、每行都 `border-t`+`border-b` 的长表 |
| 文案 | 营销填充动词（Elevate / Seamless / Unleash / Next-Gen）；英文文案里 **禁用 em-dash `—` 作分隔符**（改用句号/逗号/换行） |

### 硬做（默认就该对）
- **Hero 装得下首屏**：标题桌面 ≤2 行，副文本 ≤20 词，CTA 不滚动可见；`min-h-[100dvh]`，**不用 `h-screen`**
- **bento 格子数 = 内容条目数**（3 项→3 格），不留空格；至少 2–3 格有真实视觉变化（图/渐变/纹理），不要全是白底白字卡
- **eyebrow 节制**：每 3 个 section 最多 1 个（hero 算 1 个）；能删就删
- **动效只动 `transform` / `opacity`**，禁 `window.addEventListener('scroll')`；`MOTION>3` 必须 honor `prefers-reduced-motion`；**说要做动效就得真做出来**，做不了就把档位降下来发干净的静态页
- **深色/浅色同时定**，同页只锁一个主题，不在中段反色；两种模式都实际打开看过
- 图标只用现成图标库，**不手写装饰 SVG**；图片用真实资源或 `picsum.photos/seed/{描述}/{w}/{h}`，不用坏掉的 Unsplash 链接
- 多列布局显式写 `<768px` 折叠（`w-full` / `px-4`），不假设框架自动处理

### 交付前自查（任一不过 = 没做完，先修）
1. 上面"硬禁"表里有没有残留？
2. 全页强调色是否唯一？按钮文字是否过 WCAG AA？CTA 标签桌面端是否单行？
3. 布局家族是否 ≥4 种（8 个 section 的页面）？
4. 有没有 div 假截图 / 手写装饰 SVG / 纯文字极简凑版面？
5. 每个动效能否一句话说清它在传达什么（层级/叙事/反馈/状态）？说不清就删
6. 移动端与深色模式实际看过？

## 五、合规红线

第 5、6 类本质是伪造截图/伪造内容：
- **不得**用于造谣、诽谤、诈骗、伪造证件/票据/官方公告、捏造真实人物言论
- 仅限虚构/娱乐/创意演示，**必须主动加可见标识**（水印 "AI 生成" / 图注）
- 用户要求生成可能被误认为真实的截图 → 先提示风险并加标识，不默默生成
- 真实在世人物形象：避免虚假言论/代言场景

## 六、反模式

- 没定验收标准就连抽 10 张，靠"看起来还行"挑 → 返工率最高
- 结果不对就整段重写 prompt → 荡掉原本对的部分；应逐项定位后改对应变量
- 只给一句"帮我画个好看的图"就开工 → 缺素材必返工
- 视频/网页：跳过"对照原稿逐帧/逐区块检查"，直接交付
- 开工前就推销视觉方案 → 来源：obra/superpowers·brainstorming「Visual Companion 即时提议」（2026-09-15 实拉）——**视觉辅助按需提议，不预先打包**：① 等到真遇到"画出来比说清楚更快"的具体问题（布局对比/示意图/mockup）才提议，且提议独立成一条消息、等答复；② 用户接受了也**逐题再判**：视觉内容用图，概念/取舍/清单类问题留在文字——**"话题涉及 UI"≠"这题适合画图"**；③ 从没出现视觉问题就全程不提议。

## 七、与相邻技能的分工

| 场景 | 走谁 |
|---|---|
| 生成图片 / 视频 / 3D / 网页 | **本技能**（生成方向） |
| **读取 / 取证**已有视频画面（抖音链接、逐帧分析、无字幕视频里有什么） | `wb-media-forensics`（反向链路，别混） |
| 确定性图像编辑（裁剪 / 压缩 / 水印 / 格式转换） | `image-processor` |

## 结构图交付走"可编辑源文件"，不走位图：让模型驱动绘图工具出 .drawio/.mermaid，改图=改文件再生成（来源：WaytoAGI 知识库《Codex 实战系列｜零代码画出复杂架构图》2026-09-11 实拉，豆包 r183-B 报送并核验）
- **画复杂架构图/PPT 图的最高效路径不是手绘，也不是让模型直接吐图片**：把结构描述交给绘图工具（Draw.io MCP 一类），产出**可编辑的源文件**（.drawio / .mermaid / 可编辑矢量），之后要改结构只改文件再生成，不用整张重画。
- **判据：这张图以后会不会改？** 会改（方案评审迭代、迁移图、PPT 复用）→ 必须产出可编辑源文件；一次性且不求改（氛围插图）→ 才直接出位图。
- **模块数越多越应该走这条路**：几十个模块的多层大图，位图每改一次就要重生成一次，可编辑文件只改对应节点。
- **与"生图"能力的分工**：生图/改图管**画面本身**（风格、质感、构图）；本条管**结构关系**（谁连谁、分层、依赖），结构关系用可编辑源文件承载，不要用像素承载。
- 提升层：工作流。

## 图表契约先行：结论→证据逻辑→导出需求→评审风险，图是论证载体不是装饰（来源：GitHub `jing1312/nature-figure-skill` ★151 官方 README，2026-09-26 r189-C 独立实拉首读，清单外新发现信源）

原文工作流：`图表契约 → 后端门禁 → 单后端绘制 → 布局与 QA → 独立导出 → 交付清单`；三条工作流规则：独立图集导出、标注不遮挡数据、语义角色配色。

- **先签图表契约再动笔**：动手前定义这张图要支撑的结论、证据逻辑、导出需求与评审风险。判据：**图是论证的载体不是装饰，先有结论再有图**——先画出来再想它证明什么，改的到底是图还是结论永远说不清。
- **独立图集导出：N 张图就是 N 张图，禁止静默拼成一张**。判据：**合并是作者的决定，不是渲染器的决定**——静默合并会让读者以为自己看到的是一个证据而不是 N 个。
- **整套图共享字体、轴措辞、颜色语义与统计精度**。判据：**跨图一致性是"同一篇论证"的证据**——各图各画一套，等于在暗示数据来自不同来源。
- **标注不得遮挡数据点；配色按语义角色分配而不是按好看**。判据：**遮挡与装饰性配色都在降低信息密度**；标注的位置和颜色都是论证的一部分，不是排版细节。
- **导出是独立环节且带投递格式约束**（矢量 PDF 文字可选中、TIFF 含 dpi 元数据、分辨率 1×–4× / 300·600 dpi）。判据：**交付格式是需求不是后处理**——投稿/印刷场景不接受"导出时再看看"。
- 反模式：先出图再补结论；把多张图合成一张凑版面；同一篇里字号/轴名/色义各图不一；标注压在数据点上；最后一步才想导出格式。
- 提升层：工作流 / 可复用 Skill。
