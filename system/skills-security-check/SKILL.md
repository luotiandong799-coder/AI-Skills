## 学习轮章节（已下沉 references/knowledge-base.md，正文留指针）

- 🏛️ 平台级技能准入参考模型 → 

- Skill 安全风险九类分层（T01–T09）：审查要按"攻击面层级"过，不按文件顺序过 → 

- 审查别拿"符合性代理"当技术证据：记录面要按三类缺陷主动查，不看厂商标签 → 

- 控制门的延迟会诱发绕过：安全开销本身就是合规率的一部分 → 

- 审阅/验证第三方技能这一步本身不得引入运行期副作用：Staging 不跑 install/build/postinstall，按对象类型选扫描器 → 

- 内容可读与代码可执行必须分两档：远端技能包可全文下发、强校验，但包内脚本永不执行；同步排除清单把可信钩子挡在不可信沙箱外 → 

- 风险分层按「是否含可执行资产」，不按文本扫描结论；技能文件本身就是注入载荷 → 

- 本地小模型审计技能包要走"证据引导两段式"，不能让 compact LLM 直接判 → 

- 信任信号要逐维度报覆盖率，不能只给一个总通过率；单维 100% 可能掩盖其他维几乎为零 → 

- 门控资格与分诊资格是两档：一个检测配置有没有「门控资格」由它对良性样本的标记率单独判定，召回提升换不来门控权 → 

- 允许集与校验集是两个集合：字段被接受不等于字段被检查，名字像安全承诺的字段尤其危险 → 

- 审查结论要有一个显式的「不处置」档位，且误报形态可枚举：不是每条读数都要整改，关闭必须带理由 → 

- 出站副作用要在 frontmatter 里声明成契约，审计器不执行也能判：外发字段与失败姿势必须可静态读 → 

- 来源要分两个锚：registry 上的 owner 只是分发渠道标签，不等于发布者密码学证明 →

- 扫描判级三原则（能力≠滥用、云端判定缓冲、Safe 模板禁无证据默认✅）：扫描器判定要区分「能力存在」与「能力被滥用」——敏感原语（bash/子进程/读密钥/env）若属声明功能所需且有文档，只报能力不判恶意；云端 risky 不默认高危，按实际影响二次映射，unknown/请求失败必须降级本地审计并记「云情报不可用」；Safe 输出模板禁止无证据默认✅，须附「静态分析不覆盖后续更新风险」免责（来源：matrix.tencent.com/clawscan/skill.md 46,622B，2026-10-07 独立 curl 实拉逐串命中 `ability vs Abuse`/`can do dangerous`/`base64`/`zero-width`/`ROT13`；与 §审查结论要有「不处置」档位 互补——那条管误报形态枚举，本条管扫描判级的总原则）
- **判据**：① **「能做事」与「在做坏事」是两层判定**：扫描器若一见危险原语就标 Medium+，会把"声明功能需要的敏感能力"误判为恶意 ⇒ 判定逻辑要先问"这个能力是否为该技能声明功能所必需且已文档化"，是则不升恶意、只作能力登记。② **云端分级结论要带缓冲**：risky 类结果默认不映射到高危，必须按本地实际影响二次判定；云端情报不可用（unknown/请求失败）时降级到本地审计并留痕，不许假装云端结论存在。③ **Safe 模板的✅必须基于证据**：无证据不得默认给通过章，且强制附"静态分析不覆盖后续更新"免责，防止"扫过=安全"的错误暗示。④ 与既有「审查结论要有显式不处置档 + 误报形态可枚举」构成"判级原则 + 误报枚举"双层，本条是原则层。
- 提升层：可复用 Skill / 工具。触发词：能力-滥用二分、声明功能所需才报能力、risky 不默认高危、云端降级本地审计、Safe 模板禁无证据默认✅、静态分析不覆盖后续更新。

- 漏洞类别全清单（17 类 / 68 模式）作扫描规则覆盖度对照表，Triage 处置动词表五档（阻断至修或正式接受 / 发布前移除 / 欠声明→改权限或删行为 / 有漏洞依赖→升级-pin-文档化豁免 / 描述-行为失配→改描述或改代码），报告格式含 SARIF 入 CI（来源：docs.nvidia.com/skills/scanning-agent-skills.md 4,822B，2026-10-07 独立 curl 实拉逐串命中 `Memory poisoning`/`Trigger abuse`/`Taint tracking`/`YARA`/`MCP least privilege`/`MCP tool poisoning`；与 §审查九类 T01–T09 互补——九类是自家分层，本条是 NVIDIA 公开 17 类全清单，可作覆盖度对照）
- **判据**：① 自家九类分层要对照公开 17 类找覆盖盲区（如 memory poisoning / trigger abuse / taint tracking / YARA / MCP least privilege / MCP tool poisoning 等是否已在自家判级里）。② **处置动词要可机检**：每条发现对应一个明确动作（修 / 删行为 / 文档化豁免 / 改描述），含糊的"建议注意"不算处置。③ **SARIF 入 CI** 使扫描结果可进流水线条件，不只是给人看的报告。
- 提升层：工具。触发词：17 类漏洞清单、68 模式、Triage 五档处置动词、SARIF 入 CI、覆盖度对照。

- 信任徽标必须自带「负向适用范围」声明：徽标/扫描结论若只报"已覆盖的项"，要同时写明它**不裁定**的那一面（如 AIPM Registry 明示 "metadata checks, not a malware verdict"——元数据校验≠恶意裁决）（来源：aipm-registry.com/research/state-of-agent-skills-2026 43,058B，2026-10-07 独立 curl+UA 实拉逐串命中 `metadata checks`/`not a malware verdict`/`1%`/`Organization`；与 §信任信号要逐维度报覆盖率 互补——那条管"维度覆盖率要分别报"，本条管"结论要明示不裁定面"）
- **判据**：① 任何对外展示的信任信号（徽标/扫描通过章/评分）都要写清它**不证明**什么，否则读者会把"部分覆盖"读成"整体安全"。② 与覆盖率倒挂同族但机制不同：覆盖率倒挂管"各类信号实际占比要公开"（1% 组织审查伪装成 100% 安全感），本条管"每个信号本身要声明否定式适用范围"。
- 提升层：可复用 Skill。触发词：信任徽标负向适用范围、metadata checks not a malware verdict、声明不裁定面。

## r436A-r436A2（全文已下沉 references/knowledge-base.md §r436A-r436A2；2026-10-09 r484 正文预算下沉）
## 技能「形态」应在内容审查之前先定权限档：是否捆绑可执行脚本是可静态判定的事实，直接决定权限下限——实测 bundling executable scripts 使漏洞风险 2.12×（来源：arxiv.org/html/2602.12430v4 169,999B，2026-10-08 独立 curl 实拉逐串命中 `Skills bundling executable scripts are 2.12` / `An unvetted community skill (T1) receives instructions-only access with full tool isolation` / `T1 and T2 skills are never granted script execution` / `Level 3 executable scripts require T3 or T4 trust`；与 §恶意产能按发布者聚合熔断 互补——那条管封禁的作用域单位，本条管单个技能安装前的权限先验档）
- **判据**：① **形态先于内容**：有无 `scripts/`、frontmatter 是否声明可执行资源，是零成本可判的事实；把它作为权限档输入，可在读第一行代码前就把默认权限压到 instructions-only（T1/T2 永不授予脚本执行），审查资源优先投给含脚本者。② **2.12× 是分诊权重不是罪名**：倍数是排队依据（含脚本优先深审、加行为回归），不是「含脚本即恶意」。③ **与行为定档串联而非替换**：既有按沙箱观察后定档是事后校验，本条是事前先验，串成「先验给下限、行为校验再升降档」。④ 数字须连原文位置引：2.12× 出 Sec 6.2 实测、T1–T4 出 Sec 6.4 权限映射，混引会造出不存在的因果。（细则见 references/knowledge-base.md §r437A）
- 提升层：可复用 Skill（准入策略 / 权限先验）。触发词：形态先验权限档、2.12×、T1/T2 不授予脚本执行、Level 3 脚本需 T3/T4、含脚本优先深审、先验档与行为定档串联。

## 风险档位只由「可能性 × 影响」决定，不得按「偏离清单的条目数」打分；判定三态中未确认项被显式剥夺 severity，且检查者不得是发现者（来源：github.com/cloudflare/security-audit-skill 295,484B，2026-10-08 独立 curl 实拉逐串命中 `Severity requires impact.` / `Likelihood x impact, not deviation from a checklist.` / `confirmed, needs_validation, and rejected` / `The agent that checks a finding is never the agent that found it.`；与 §扫描判级三原则 互补——那条管能力≠滥用，本条管定级的算术与判定者分离）
- **判据**：① **符合度不是风险**：偏离清单条目多不等于风险高，只有 likelihood×impact 才是定级输入；把「不符合项计数」当风险分会让清单越长风险越高。② **三态各带约束**：`confirmed` 需 complete source trace + bounded observed result；`needs_validation` 只记未决事实、**禁带 severity**（未证实的候选不得预先打分）；`rejected` **显式记录被证伪的候选**（不静默丢弃）。③ **检查者≠发现者**：验最终源主张要用 fresh agent，不复用原 detector。（细则见 references/knowledge-base.md §r437C-4）
- 提升层：可复用 Skill。触发词：Likelihood x impact、not deviation from a checklist、needs_validation 禁 severity、rejected 记录被证伪候选、检查者不等于发现者。

## 运行期可执行面的允许清单，声明权归「部署运营方」而非技能作者：作者侧管字段可见性，运营方管命令可执行性——两个声明者要分别检查（来源：github.com/FlowiseAI/Flowise/releases/tag/flowise@3.1.4 213,716B，2026-10-08 独立 curl 实拉逐串命中 `Fix Flowise 709 Make Custom MCP stdio command allowlist operator-controlled by @yau-wd in #6578`；与 §出站副作用声明成契约 互补——那条管作者声明外发面，本条管谁有权定义可执行命令面）
- **判据**：① 审计允许清单时先问「这份清单是谁写的」：作者随包提交的允许清单是**自证**，运营方在部署期注入的才是外部约束；二者同名但约束方向相反（作者想放宽以便运行 vs 运营方要收紧以便管控）。② 同一技能可以两面都有，审计报告须分列两个声明者，不许合并成「已配置允许清单」。③ 运行期命令面（stdio 命令、可执行路径）属运营方所有权，作者无权自授。（细则见 references/knowledge-base.md §r437C-5）
- 提升层：可复用 Skill。触发词：允许清单声明权、operator-controlled allowlist、作者自证 vs 运营方约束、运行期命令面所有权、两个声明者分列。

## 批准不是权限本身，而是「派生关联」：每次使用都要对活的授权行再验证，且批准绑定的是规范化执行上下文（cwd + 精确 argv + env 绑定 + 固定可执行路径），启动前重解析重检查（来源：docs.openclaw.ai/tools/exec-approvals 一手 363,977B，2026-10-08 r438B 独立 curl 实拉逐串命中 `a grant is derivative correlation, revalidated against the live approval row, automation row, and revocation state on every use` / `bind canonical execution context: cwd, exact argv, env binding when present, and pinned executable path` / `re-check it before launch` / `not a per-user auth boundary or filesystem read-only policy`；全库 grep `revalidated` / `exact argv` 均 0 命中）
- **① 授权状态不能缓存**：批准记录是**对另一行授权状态的派生关联**，不是一份自足的权限；每次使用都要拿活授权行 + 自动化行 + 吊销状态三者重新对一遍。判据：**审计"有没有权限"时，看的是再验证的动作，不是批准记录的存在**；只查"批过没有"等于把可撤销的引用当成了既得权限。
- **② 批准要钉到可执行身份，不能钉到命令名**：批准的粒度是规范执行上下文——cwd、精确 argv、env 绑定、固定可执行文件路径；网关侧在评审前绑定每个解析出的命令段可执行文件，**启动前再检查一次**。原文同时给出边界声明：这只降低误执行风险，**不构成按用户的认证边界，也不构成文件系统只读策略**。判据：审查批准/白名单机制时问三件事——绑的是名字还是 argv+路径？启动时重不重查？文档有没有把"批准过"说成"有权"？三者任一答错即判缺陷。
- 提升层：可复用 Skill（权限模型）/ 工作流（运行期授权复核）。触发词：批准不是授权边界、derivative correlation、revalidated on every use、exact argv、pinned executable path、re-check before launch、授权不能缓存、批准粒度、per-user auth boundary

## 审批校验要验「记录的签发者是否有权为本动作签发」，不能只验记录存在：跨技能链把伪造审批藏在单技能扫描的盲区（来源：arxiv.org/abs/2610.01564 + /html/2610.01564v1 293,934B，2026-10-08 一手实拉）
- **实证**：APEX 全链攻击成功率 **84.3%**，而把同样的两步合并进**单个技能**只有 **17.4%**；512/690 attempts＝**74.2%**；提示层防御把良性 verifier 通过率从 **86.7%** 压到 **56.3%**。原文机制：「an agent-written record of genuine task progress can carry a false claim of user approval across skills」「an upstream skill induces the agent to create the record, and a downstream skill ...」。
- **判据**：① **风险藏在链上，不在件上**——单技能静态扫描对本类攻击天然高漏（84.3% vs 17.4% 的差值就是链带来的增量），审计必须按**调用序列**而非单包取证；② 消费侧见「已批准」记录时，要回溯**该记录的签发者是否被授权签这一类动作**，只验存在性等于把上游诱导当授权；③ **防御代价必须与攻击成功率并列报告**（86.7%→56.3% 的可用性损失不是免费的），只报拦截率的防御方案不可验收。
- **与既有能力分工**：r437C「允许清单声明权归运营方」管**谁有权写清单**；本条管**跨技能传递的审批声明由谁签发**——两处都是「声明者身份」，但一在授权面一在传递面，须分别检查。
- 提升层：工具（取证面）/ 工作流（审计序列）。触发词：链式审批伪造、84.3 vs 17.4、agent-written record、跨技能链、签发者权限、防御代价并列报告。

## 技能根目录是「容纳边界」：装载时对越根软链一律跳过并留原因位，共享靠显式白名单目录而非隐式跟随（来源：docs.openclaw.ai `/gateway/troubleshooting/skills-and-model-providers` 247,412B，2026-10-08 一手实拉）
- **实证**：官方日志形态「Skipping escaped skill path outside its configured root: ... **reason=symlink-escape**」；定性原句「**Every skill root is a containment boundary**」——`~/.agents/skills`、`<workspace>/.agents/skills`、`<workspace>/skills`、`~/.openclaw/skills` 下的越根软链一律 skip；放行须同时具备显式 `extraDirs` + `allowSymlinkTargets`，且 `~`、`/` 这类宽目标被禁。
- **判据**：① **复用技能不许用软链"借道"**——把外部目录链进技能根等价于让该目录绕过一次准入审查；共享只能走显式登记的额外目录白名单；② **跳过必须留原因位**（`reason=symlink-escape`），静默跳过会让"技能没生效"变成无痕失败，排查时看不到被拒的那一次；③ **白名单目标是路径精度问题**：`~`、`/` 这类宽目标一旦开了等于边界失效。
- **与既有能力分工**：r437A「形态先验权限档」管**有没有脚本决定权限下限**；本条管**技能根之外的内容能不能被带进来**——前者是权限档，后者是容纳面。
- 提升层：工具（装载面）/ 工作流（准入）。触发词：容纳边界、symlink-escape、越根软链、extraDirs、allowSymlinkTargets、技能没生效无痕失败。

## 复审的记分对象是「新增」不是全量；LLM 语义阶段只升不降置信，未确认项须显式打 `llm-unconfirmed`（来源：api.github.com/repos/NVIDIA/SkillSpector/contents/README.md 53,632B 全解，2026-10-08 一手实拉）
- **实证**：官方原文「Scan against the baseline — **only NEW findings are reported and scored**」；「Findings the model reviews but does not confirm (disputed, low-confidence, or unaddressed) are tagged **`llm-unconfirmed`** in JSON and SARIF output」。
- **判据**：① **跨轮扫描必须区分三态：新增 / 已被 baseline 抑制 / 未确认**——把全量重贴当"本轮发现"会让同一个 finding 在每轮报告里重复计分，风险趋势图上看到的是基线漂移而非真实新增；② **模型没确认的东西不许当已确认**：语义阶段只升不降置信 ⇒ 未确认项要单独留标签位，混进 confirmed 会让"AI 复核过"变成虚高可信度；③ baseline 是记分口径的一部分，**换基线等于换量纲**，跨基线比较前必须先对齐基线版本。

- 提升层：工作流（扫描口径）/ 工具（报告契约）。触发词：only NEW findings、llm-unconfirmed、基线记分、重复计分、跨轮三态、换基线换量纲。

## 漏洞情报源要带「自动离线回退」，且模式库规模必须给出「类别数 × 模式数」双层粒度作为覆盖基准的分母（来源：api.github.com/repos/NVIDIA/SkillSpector/readme 53,566B 解码全文，2026-10-08 一手 curl 逐串命中 `71 vulnerability patterns` across `17 categories` / `SC4 | Known Vulnerable Dependencies | HIGH | Dependencies with known CVEs (live OSV.dev lookup)` / `real-time CVE data with automatic offline fallback`；与 §r435C 17 类漏洞清单 + Triage 五档处置 + SARIF 入 CI 互补——那条落"检出来怎么处置与怎么进 CI"，本条落"情报从哪来、断网时朝哪个方向失败、覆盖够不够怎么量"）
- **实证**：原文「**71 vulnerability patterns** across **17 categories**: prompt injection, data exfiltration, privilege escalation, supply chain, excessive agency, output handling, system prompt leakage, memory poisoning, tool misuse, rogue agent, anti-refusal, trigger abuse, dangerous code (AST), taint tracking, YARA signatures, MCP least privilege, and MCP tool poisoning」；「**Live vulnerability lookups**: SC4 queries [OSV.dev](https://osv.dev) for real-time CVE data with **automatic offline fallback**」；「**Multiple output formats**: Terminal, JSON, Markdown, and **SARIF** reports」；阶段与基线「Two-stage analysis: Fast static analysis + optional LLM semantic evaluation」「Baseline / false-positive suppression … so re-scans surface only *new* issues」。
- **判据**：① **依赖实时情报的检查必须显式声明离线时的方向**：SC4 命中 CVE 靠在线查询，官方明写"自动离线回退" ⇒ 联网检查的默认失败方向如果是"查不到=没有漏洞"，断网期间的扫描会静默降级成"全部安全"；正确写法是把"情报源不可用"作为可观测状态（与"扫过且无 CVE"区分）。② **模式库规模要分两层报（类别数 × 模式数）**：17 个类别是目录、71 个模式是条目 ⇒ 只报"覆盖 17 类"会让人以为只有 17 项检查；覆盖率的分母是模式数，归类方式由类别数决定，两者缺一都无法判断"这个扫描器是否够用"。③ **类别清单本身就是威胁面清单**：17 类里既有注入/外传/提权这类经典面，也有 memory poisoning、rogue agent、anti-refusal、trigger abuse、MCP tool poisoning 这类 agent 特有的面 ⇒ 审自己的技能库时，先拿这份清单对一遍"哪些面我根本没有检查项"。④ **两阶段（快速静态 + 可选语义）意味着第二阶段可缺席**：LLM 语义评估是 optional ⇒ 报告里必须标注本次是否跑了语义阶段，否则同一份结果可能是两种强度的产出。⑤ **与处置链串成完整闭环**：模式库（覆盖什么）→ 情报源（依赖是否已知有洞，含离线回退）→ 基线（只报新增）→ SARIF（进 CI）⇒ 任何一环缺席，扫描结论都只能当线索不能当裁决。
- **与既有能力分工**：r435C「17 类清单 + Triage 五档 + SARIF 入 CI」管**检出之后的处置与集成**；本条管**情报来源的失败方向与覆盖度的计量基准**。
- 提升层：工具（扫描器接入三要素）/ 治理（覆盖度分母）。触发词：71 模式 17 类别、模式库规模双层粒度、OSV.dev 实时 CVE、automatic offline fallback、离线回退方向、两阶段可选语义、类别清单即威胁面、覆盖度分母。

## 扫描覆盖的是「检查面」，执行面可被随包字节码缓存替换：扫描对象须含 __pycache__/.pyc 并与源码做行为一致性比对，且防御代价必须与检出率并列（来源：arxiv.org/abs/2610.10612（PyCache Trap）43,017B，2026-10-09 一手 curl 逐串命中 `Python may execute a bundled bytecode cache with different behavior` / `Across 100 skills and seven scanners, PyCache Trap achieves 94-100% attack success, with no semantic recognition of the cache-resident behavior` / `detects all 100 evaluated source-present cache substitutions and reaches 92.8% Recall at 10.0% FPR across five attack families and 200 benign skills`；r472B 落地）

- **判据**：① **检查面 ≠ 执行面**：静态扫描默认只覆盖可见源码，运行时却可能加载随包字节码缓存 ⇒ 准入只看源码等于放行执行面（与 r445B / r448-Q-C 已落的「预编译字节码绕过」同机制；本条补的是**一手规模数值**与**防御侧代价**）。② **不是个别扫描器失手，是全行业面失效**：100 技能 × 7 扫描器 94–100% ASR、对缓存内行为零语义识别 ⇒ 单换扫描器不构成缓解。③ **防御的误报率必须与检出率并列报告**：EAV 100/100 检出的代价是 **92.8% Recall @ 10.0% FPR**（200 个良性里约 20 个误报）⇒ 只报 100/100 的防御方案不可采信（沿用 ssc 既有「防御代价须与攻击成功率并列报告」纪律）。④ **可操作增量**：扫描对象清单必须显式包含 `__pycache__/` 与 `*.pyc`，并与源码做**行为一致性比对**（而非仅存在性检查 / 仅源码扫描）。⑤ **措辞层面的相似性比对无效**：攻击靠 scanner-guided rewriting 改措辞保留工件本体 ⇒ 检测必须落到工件级（字节码/代码对象归一化后比对），不能落在文本级。

## 技能「选择阶段」存在不需要任何注入痕迹的攻击面：用户提示与技能描述单看都良性，靠语义关系塑形即可把选择率从 15.2% 推到 63.5%，而人工评审只拦住 2.9%、五个 LLM 检查器平均放行 82.9%（来源：arxiv.org/abs/2609.02035（ISM）42,386B，2026-10-09 一手 curl HTTP 200 逐串命中 `increases the average target-selection rate (TSR) from 15.2% to 63.5%` / `73.5% TSR, only 9.8 percentage points below Explicit Steering` / `Human reviewers block ISM in only 2.9% of judgments, versus 91.4% for Explicit Steering` / `five LLM-based inspectors pass ISM at an average rate of 82.9%, versus 37.4%`）
- **实证**：① 攻击定义「even when the user prompt and skill description appear benign **in isolation**, their **semantic relationship** can still be strategically shaped to favor an attacker-chosen skill」；② 三阶段策略「broaden semantic coverage, strengthen target distinctiveness, and preserve natural prompt wording」；③ 跨度「Across four task domains and eight selector models, ISM increases the average TSR from **15.2%** to **63.5%**」；④ 与显式操纵的对照「In a matched comparison, ISM achieves a **73.5%** TSR, **only 9.8 percentage points below** Explicit Steering」；⑤ **人审几乎无效**「Human reviewers block ISM in only **2.9%** of judgments, versus **91.4%** for Explicit Steering」；⑥ **机审同样失效且方向相反**「five LLM-based inspectors **pass ISM at an average rate of 82.9%**, versus **37.4%** for Explicit Steering」。

## r485C · 目录「有无安全标记」要先问「扫不扫」：无标记有两种成因；多家扫描源可并列且允许结论冲突；第三方目录的限流窗口可能是「日」（来源：skillsmp.com/docs/api 503,097B + skillsmp.com 302,679B + www.skills.sh/anthropics/skills/pdf 122,581B，2026-10-10 r485C 一手 curl 实拉逐串命中 `We don't scan for malware (yet)` / `not a live ranking, quality certification, or safety review` / `DAILY_QUOTA_EXCEEDED`×3 / `X-RateLimit-Daily-Limit`×6 / `Gen Agent Trust Hub`×2 / `Socket`×2 / `Snyk`×2）

## r488C · 多源审计「可并列但不可归并」：三家词表不同构，折叠成单一 verdict 必然失真；同时更正 r485C 的通道结论——不入账的是「统一判级」而非「判级值」（来源：www.skills.sh/audits 387,367B，2026-10-10 一手 curl 逐串命中 `Combined security audit results from Gen Agent Trust Hub, Socket, and Snyk.` 与 `Safe`×23 / `Low Risk`×17 / `Med Risk`×12 / `alerts`×52 / `Pending`×72 / `Socket`×29 / `Snyk`×29；r488C 落地）

- **判据**：① **不同词表不可比，聚合只能并列不能归并**：形容词级与计数级之间没有映射函数 ⇒ 把三源折成一个"是否通过"会丢掉"Snyk 说中风险但 Socket 说零告警"这类最关键的分歧；报告须**逐源保留原形态**，并允许并列冲突。② **`Pending` 是第三态，既非通过也非失败**：把它填成"通过"（默认）会虚增覆盖率，填成"失败"会污染阳性率 ⇒ 未扫描必须单独成态并在覆盖率分母中显式扣除。③ **更正 r485C**：r485C 因「`PASS/WARN` 0 命中（JS 渲染）」判「判级值不入账」——本轮一手核验表明 raw HTML **机读可得**（387KB 全文含三源异构词表），**真正的结论应是"统一判级不可入账，各源原值可入账"**；把"没有统一词表"误记成"取不到判级"，属于把取证失败与对象性质混为一谈。④ **"多源并列"的实现前提是有源可列**：r485C 只立了"允许冲突"的形态，本条补齐"各源值怎么取、Pending 怎么算" ⇒ 二者合起来才是可用的多源聚合判据。

- 提升层：可复用 Skill（安全校验）/ 工具（多源聚合）。触发词：Combined security audit results、Safe / Low Risk / Med Risk、alerts 计数、Pending 第三态、词表不同构不可归并、逐源列原形态、判级值可入账但统一判级不可。

## r492C · 安装器「假成功」是三层结构的复合故障：计数变量活不到汇总行、落盘结果被硬编码成功吞掉、汇总口径与成功无关审计时必须逐层各验一次（来源：www.modelscope.cn/skills/install.sh 27,039B + github.com/prompt-security/clawsec README 8,314B，2026-10-10 r492C 一手 curl 实拉）

- 提升层：工具 / 安全边界（授权面审查）。触发词：read 与 write 不是梯度、作用域落点机器、stdio 在成员本机、connectors:write 等于执行代码、只授予只读。


## 作用域覆盖是**加法**且重复声明必须单调收紧：更弱的重复声明被显式拒绝，能否下放由「证据可归因性」决定（来源：docs.openclaw.ai `cli/policy/scopes.md` 4,160B，2026-10-11 r516A 一手 curl 取 `.md` 原文通道实拉、逐串命中）
- **实证（逐串）**：`Overlays are additive: the global rule still runs, and the scoped rule can add its own finding against the same evidence`（作用域规则**不替换**全局规则，可对同一证据再加一条 finding）；`A repeated scoped field for the same agent must be equally or more restrictive; a weaker duplicate claim is rejected (allow-lists are subsets, deny-lists are supersets, required booleans are fixed)`（同一字段的重复声明**必须等严或更严**，更弱者被拒——allow 列表必须子集、deny 列表必须超集、required 布尔固定）；`is not channel-attributable evidence, so it cannot be scoped by`（`session.dmScope` 不是渠道可归因证据 ⇒ 该项**只能保持全局**）；`evaluates the scoped rule against inherited global/default posture for that runtime agent id instead of skipping it`（作用域引用了不存在的 agent id 时**不跳过**，改用继承的全局/默认姿态评估）；`Every scope present in policy.jsonc must be valid and enforceable`。
- **判据**：① **叠加是加法不是替换**——给某一类对象"加严"不会抵消全局规则，审计时两条 finding 可能同时落在同一份证据上，不能当成重复项去重。② **"更严"必须是可判定方向**：同一字段被两个作用域各自声明时，系统不是取并集或取最后一条，而是要求单调收紧并把更弱的那条**拒掉**——配置里有冲突不是"谁在后面谁赢"，而是直接失败。③ **能否下放到某一级，取决于证据能不能归因到该级**：证据不可归因（这是会话级还是渠道级说不清）时强制保持全局，不得为了配置好看而下放。④ **引用了不存在的对象不算空配置**——按继承默认姿态评估而不是跳过，否则"写错一个 id"会静默变成"这条规则没生效"。
- 提升层：工具 / 工作流（安全策略与配置审计）。触发词：作用域叠加、加法不替换、更弱重复被拒、单调收紧、证据可归因性、不可下放的维度、不存在的 id 不跳过。

## 密钥「未配置」不是「没有密钥」，而是落到一个可猜的或另一个信任域的值上：回落会把两个本该独立的信任域合成一个（来源：docs.flowiseai.com `configuration/authorization/app-level.md` 7,734B，2026-10-11 r516B 一手 curl 取 `.md` 原文通道实拉、逐串命中）
- **实证（逐串）**：`Secret for refresh tokens (defaults to auth token secret if not set)`（刷新令牌密钥未设时**复用**访问令牌密钥）；`Session encryption secret (default: 'flowise')`、`Token validation audience claim (default: 'AUDIENCE')`、`Token validation issuer claim (default: 'ISSUER')`（未设时落到**写在文档里的常量**）；`otherwise, default values will be used, which could increase the chances of attackers to forge valid tokens and impersonate users`（官方明示：不配即用默认值，攻击者可**伪造有效令牌并冒充用户**）。
- **判据**：① 审计"这一项没配"时，结论**不能停在"未设置"**，必须继续追"运行时落到了什么值"——落到文档公开的常量，等于签名密钥已经公开。② **回落复用另一个密钥比常量默认更隐蔽**：`refresh` 未设则复用 `auth` 的密钥，于是"短期访问令牌域"与"长期刷新令牌域"合并成一个域，攻破短令牌即可续出长会话——两个信任域退化成一个，而配置面看起来"只少设了一项"。③ **"没配"要按有效密钥计入资产清单**，不能按"无密钥"从清单里剔除；默认值的安危判据仍是"它单独能不能构成授权"，但它构成的授权要**按默认值的可预测性**升级。
- 提升层：工具 / 工作流（凭据与密钥面审计）。触发词：默认值可伪造、回落复用另一密钥、信任域合并、未配置不等于没有、JWT 默认密钥、刷新令牌复用。

## 「读 / 写」不是同一能力的两档：作用域的危险度由**副作用落在谁的机器上**决定，不看动词（来源：pipedream.com/docs/conduit/use/api/scopes.md 3,110B，2026-10-11 r516C 一手 curl 取 `.md` 原文通道实拉、逐串命中）
- **实证（逐串）**：`A stdio connector launches a command on each workspace member's own machine (through the conduit CLI), not on the server`（`stdio` 连接器在**每个成员自己的机器**上启动命令，不在服务器）；`granting it is effectively granting the ability to run code on your members' machines`；`grant connectors:read alone where a client only needs to inspect connectors`；`This is the same trust boundary that makes connector management a workspace-admin operation`。
- **判据**：① **名字只差一个动词的两个作用域，可能是两个完全不同的信任域**——判断危险度要追到"副作用落在哪台机器、哪个进程"，不要靠 `read`/`write` 字眼分级；本例 `connectors:write` 的实质不是"能改配置"，而是"能在成员本机执行代码"。② **"只读"是唯一能显著降权的那一档**：只要需求是查看/盘点，就应显式只授予 read，而不能用"反正都要接 API 就一起给 write"。③ **权限面要给出"为什么这一档这么高"的落点说明**，否则使用者会把命名相近的作用域当成梯度。④ 与 ssc「运行期可执行面的声明权归运营方」互补：那条管**谁有权声明清单**，本条管**被授予的能力最终落在谁的机器上**。
- 提升层：工具 / 安全边界（授权面审查）。触发词：read 与 write 不是梯度、作用域落点机器、stdio 在成员本机、connectors:write 等于执行代码、只授予只读。

## 技能自带的展示文本是不可信输入：宿主须做「去控制字符＋转义尖括号防仿冒内部格式」两级消毒，且该消毒绑定客户端版本下限（来源：code.claude.com/docs/en/skills.md 107,130B，2026-10-12 r528C 一手 curl 200 逐串命中 `Claude Code sanitizes the display text the skill supplies, such as its description. It removes control characters, and in text that reaches Claude, such as the description, it also escapes angle brackets so the text can't imitate Claude Code's internal formatting. This sanitization requires Claude Code v2.1.228 or later.` / 同页 `A skill can grant itself broad tool access, so review the allowed-tools of skills checked into a repository before you run Claude Code there.`；r528C 落地）
- **实证**：宿主对技能自带的显示文本（例举 `description`）做两级处理——**一律移除控制字符**；**对会进入模型上下文的文本再做尖括号转义**，官方给的理由是 `so the text can't imitate Claude Code's internal formatting`。该消毒**要求客户端 v2.1.228 或更高**。
- **判据**：① **技能包里的文本字段要按"陌生人的上传"对待，不是按"作者自己的说明"对待**：description / 名称 / 展示文案都能被作者任意填写 ⇒ 审查清单里"文本字段"是与"代码/脚本"并列的受审面，不能因为"只是描述"就跳过。② **两级消毒防的是两类不同攻击**：控制字符防的是**显示层欺骗**（不可见字符、覆盖、伪造排版），尖括号转义防的是**拟人层欺骗**（让技能文本长得像宿主的格式化输出/系统提示）。只做前者，技能仍可用伪标签冒充系统消息 ⇒ 审查时要分别问"控制字符清了没有"与"会不会被读成内部格式"。③ **"进不进模型上下文"是分级依据**：官方只转义**会到达模型的那部分文本**，说明分级维度是**读者**而不是字段类型 ⇒ 建立分级规则时先标"这段给谁看（人/模型/两者）"，再决定处置强度；按字段类型分级会漏。④ **消毒能力有版本下限**：`requires Claude Code v2.1.228 or later` ⇒ "宿主会消毒"这个前提在旧客户端上不成立；审查结论若依赖宿主侧消毒，必须写明"仅当宿主 ≥ 该版本"，否则等于给未打补丁的环境发了通过。⑤ **与"技能可自我授予宽权限"同页并列**：同一份文档既警告技能能给自己批工具、又说明宿主在消毒它的文本 ⇒ 审查一个技能包时，**代码/权限声明/展示文本三面要一起过**，只审代码会把"用描述骗模型"这一路整条漏掉。⑥ 与 §公钥信任方向按用途判、§豁免带指纹可复查 互补：那两条管**凭据与处置**，本条管**包内自带文本的注入面**。
- 提升层：工具（包内文本消毒）/ 工作流（上架审查三面）。触发词：技能描述消毒、控制字符移除、尖括号转义防仿冒、消毒版本下限、展示文本不可信、包名/描述注入面。

## 扫描结论必须带「完备性」一等字段：`is_complete`/`scope_exclusions`/`analyzer_statuses`/`limitations` 四件套入账，「扫不完备」与「扫出问题」是两条独立退出理由，覆盖率高不等于扫全了（来源：raw.githubusercontent.com/NVIDIA/SkillSpector/main/docs/scan-completeness.md 17,670B，2026-10-12 r541C 一手 curl 200 逐串命中 `analysis_completeness.status` / `is_complete` / `scope_exclusions` / `analyzer_statuses` / `limitations` / `The report raises an otherwise SAFE recommendation to CAUTION for incomplete analysis while retaining the actual score and severity` / `default CLI exit 0 is not an installation-safety verdict` / `component coverage can still read 100% ... Consumers must use is_complete and the ledger, not the coverage percentage alone`；提名 Qoder r538-Q-C ①）
- **实证**：SkillSpector 的完备性文档把「扫全了没有」做成了结构化字段而不是报告里的一句话：JSON/MCP 输出暴露 `analysis_completeness.status`、`is_complete`、`ledger_exceptions`、`scope_exclusions`、`analyzer_statuses`、`limitations` 与 `execution_successful`；异常条目带 reason/message/path/fatality/可用源码行数/适用限额指标。三条硬规则：① **完备性不足时把原本 `SAFE` 的结论强制升为 `CAUTION`**（实际分数与严重级保留，不改分只改结论档）；② **默认 CLI exit 0 不是安装安全裁决**——MCP 侧另要求执行成功、分析完整、零个完全未检文件、分数 ≤50；③ **组件覆盖率可以显示 100% 而系统事件仍记录未解的解释项** ⇒ 消费方必须读 `is_complete` 与 ledger，不能只看覆盖率。
- **判据**：① **「扫不完备」与「扫出问题」必须分设两条退出理由**：前者是证据不足（未知），后者是证据确凿（阴性/阳性）⇒ 混为一条会让「没扫到」伪装成「扫了没问题」；退出码与结论档都要能区分这两种情况。② **完备性四字段是扫描报告的最小必备集**：`is_complete`（总判）/ `scope_exclusions`（哪些没进范围）/ `analyzer_statuses`（每个分析器干了没有）/ `limitations`（已知限制）——缺任何一个，「已扫描」的声明就不可审计；对不完备的结论**强制降档**（SAFE→CAUTION）且不做乐观的分数修正。③ **覆盖率 100% 是过程指标不是结论指标**：每个文件都被分析器碰过，仍可能有未解释项 ⇒ 判断「扫全了没有」的唯一依据是完备性字段与 ledger，不是覆盖率数字。④ **默认退出码不是安全语义**：exit 0 只说明命令跑完 ⇒ 把「退出码为 0」当「可以安装」是通道误用；安装门控必须显式消费完备性字段与分数阈值。⑤ 与 §扫描覆盖三轴（av KB r322A）分工：那条管**覆盖面怎么声明**（输入格式 × 被读字段 × 结构深度三轴逐项标注查了/没查），本条管**不完备时结论怎么降档与退出**——一个在声明面、一个在裁决面。

## 计划与执行分离时，权限与取消必须在执行前最后一刻重验：规划期验过不算数，计划做出后到落盘前世界可能已经变了（来源：docs.openclaw.ai/agent-runtime-architecture.md 10,069B，2026-10-12 r542C 一手 curl 200 逐串命中 `File-tool workers perform pure edit matching, Unicode normalization, and diff computation. One prepared patch supplies both display and unified-patch receipts, including previews.` / `The file-tool caller keeps the mutation queue, filesystem access, persisted-byte verification, and authority checks; it revalidates authority and cancellation after planning before changing files.` / `Write receipts retain their existing size and edit-distance limits.`；r542C 落地）
- **实证**：OpenClaw 的文件工具把「计划」与「执行」拆开： planning worker 只做纯编辑匹配、Unicode 归一与 diff 计算，一份准备好的补丁同时供展示与 unified-patch 回执（含预览）；而变更队列、文件系统访问、落盘字节验证与权限检查留在调用方。关键一句：调用方「**revalidates authority and cancellation after planning before changing files**」——规划完成之后、真正改文件之前，重新验证权限与取消状态。
- **判据**：① **计划期验证≠执行时有效**：计划做出到执行之间存在时间窗，窗内权限可被撤、文件可被改、取消可被发出 ⇒ 任何「先规划后执行」的两段式结构，第二段开头必须重验第一段验过的东西（TOCTOU 面）。② **重验的集合=执行面依赖的全部事实**：本例是 authority + cancellation 两样 ⇒ 枚举「执行会依赖哪些外部状态」，逐个在执行前复查，而不是只重验最显眼那个。③ **预览/回执不承载权限语义**：同一份 prepared patch 供展示与回执 ⇒ 给人看的预览通过不代表执行被授权，验收要区分「计划正确」与「允许执行」。④ 与 §allow/deny 按名字过滤不检查副作用（dl KB r513A）分工：那条管**过滤维度**（名字 vs 副作用），本条管**重验时机**（计划后执行前）。
- 提升层：工具（文件改写执行面）/ 工作流（计划-执行分离的验收）。触发词：revalidates authority and cancellation after planning before changing files、计划期验证不等于执行时有效、TOCTOU、执行前重验、预览不承载权限。

## 隐式选择的触发条件必须精确匹配：只有「精确官方路由 + 无作者覆盖」才隐式选路由，provider/model 前缀永不单独触发选择，明文 HTTP 端点硬拒（来源：docs.openclaw.ai/agent-runtime-architecture.md 10,069B，2026-10-12 r542C 一手 curl 200 逐串命中 `auto selects a registered plugin harness that supports the effective provider route, otherwise the built-in OpenClaw runtime. - **实证**：OpenClaw 运行时选择：`auto` 选支持有效 provider 路由的已注册插件 harness，否则用内置 openclaw 运行时；**provider 或 model 前缀永不单独选中 harness**。OpenAI 可能隐式选 `codex`，但只在「精确的官方 HTTPS Platform Responses 或 ChatGPT Responses 路由 + 无作者请求覆盖」时发生；Completions 适配器、自定义端点、带作者请求行为的路由都留在 `openclaw`；**明文官方 HTTP 端点被拒**。旧别名 `pi` 归一为 `openclaw`、`codex-app-server` 归一为 `codex`。
- **判据**：① **隐式选择的条件要逐条钉死且用精确匹配**：官方把隐式选 codex 的条件写成「exact official route + no authored request override」两个合取 ⇒ 设计任何「不显式配置时自动选 X」的机制时，触发条件必须是可枚举的精确谓词，不能是「看起来像」的前缀/近似匹配。② **前缀不触发选择**：provider/model 前缀永不单独选中 harness ⇒ 按名字前缀做的自动路由会把未验证的路由选进执行路径；选择依据必须是完整路由身份而非名称片段。③ **明文端点硬拒**：plaintext official HTTP endpoints are rejected ⇒ 隐式/自动路径上的传输安全要有硬失败，不能降级。④ **别名归一是显式契约**：legacy alias 有明确定的归一目标 ⇒ 归一表要显式维护并随版本声明，隐式「猜归一」会让旧配置静默换轨。⑤ 与 §名称解析宽容度按副作用分面（ssc 1.57.0）分工：那条管**名称到实体的解析宽容度**（只读可模糊/写面严格），本条管**隐式路由/运行时选择的匹配精度**（精确谓词、前缀不触发、明文硬拒）。
- 提升层：工具（路由与选择面）/ 工作流（隐式选择设计审计）。触发词：A provider or model prefix alone never selects a harness、exact official HTTPS route with no authored request override、Completions adapters stay on openclaw、Plaintext official HTTP endpoints are rejected、legacy alias normalizes。

## 角色映射的三模式语义：显式关闭不求值、供给时事务前解析、持续解析每次重评；角色写入与身份事务分离（来源：api.github.com/repos/n8n-io/n8n/pulls/40809，2026-10-12 merged，一手 curl + 逐串命中）
- **实证**：n8n identity 服务按 source 的 `identity.roleMapping` 三模式应用：`off` 不求值；`on-provision` 在事务前解析，校验实例角色（block access / owner / 非全局角色 / 无许可角色全部 `no-role` 拒绝）后同事务建 JIT 用户；`continuous` 每次解析都评，无结果在 `lastSeenAt` 盖章前以 `no-role` 拒绝，写入只对非 owner 的 jit 绑定且在身份事务提交后经 `applyResolvedRoles`（因 `changeUserRole` 自开事务）；`claim-match` 绑定只评不写；项目规则只解析团队项目（规则不能授权个人项目）；链接路径先查 continuous 映射再写绑定（被拒的解析不许留行）；`$claims` 传原始 token claims，同一 `RoleMappingProxyService` + provider 标签让既有 SSO 规则原样复制。
- **判据**：① 「关闭」要显式——off 模式明写 evaluates nothing，别用默认值隐含关闭语义；② 映射解析放在事务前（先解析后建用户），解析失败不污染身份事务；③ 角色写入与身份事务分离——写角色走独立事务且在身份事务提交后，失败不回滚身份；④ 只评不写的绑定类型要标出（claim-match），别把「评估过」当「生效」；⑤ 授权规则的作用域要有边界（项目规则只到团队项目），链接路径先验证再落行（被拒不留残留）。
- 提升层：工具（身份映射治理）/ 工作流（授权链路审计）。触发词：roleMapping 三模式、off 不求值、on-provision 事务前解析、continuous 每次重评、no-role 拒绝、applyResolvedRoles 独立事务、claim-match 只评不写、团队项目作用域、链接路径先验后写、原始 claims 直传。

## 技能产物跨会话传播是攻击面：指令传播/数据边界违反/证据投毒三机制，防御靠恢复工件来源上下文+执行前 advisory（来源：arxiv.org/abs/2610.13227，2026-10-12 一手实拉摘要逐串命中）
- **实证**：skill 执行中产出/修改的工件（文件、配置、缓存数据）会被后续会话的其他 skill 复用；工件跨会话持久且被其他 skill 访问，构成新攻击面。三机制：Instruction Propagation（IP，指令经工件传播）、Data Boundary Violation（DBV，数据边界被跨域读写打破）、Evidence Poisoning（EP，证据被投毒影响后续判定）。SkillRelayBench：270 对抗用例、30 个跨会话技能组合场景、10 领域；7 个模型 × Codex CLI/Gemini CLI/Claude Code 实测攻击成功率 ASR 46.7%–77.4%、攻击链成功率 ACSR 35.6%–61.1%，成功链覆盖全部五类目标安全后果。SkillRelayGuard 防御：恢复工件来源上下文（provenance）+ 执行前 advisory 评审，最终执行决策留给 agent；ASR 69.5%→10.9%、ACSR 54.8%→10.0%，合法任务完成率 79.6%→87.5%。
- **判据**：① 准入审查不能只审 skill 自身声明——它在后续会话会读到别人留下的工件，工件即跨会话输入信道；② 攻击分三机制建模：指令经工件传播（IP）/ 数据边界被跨域读写打破（DBV）/ 证据被投毒（EP）——分别对应「工件内容被当指令」「工件被越界读写」「工件被当证据」；③ 防御形态=来源上下文恢复 + 执行前 advisory（不接管决策）——把最终执行权留给 agent 的 advisory 比硬拦更保合法完成率；④ 实测攻击成功率近七成说明「技能各自干净」不构成组合安全。
- 提升层：工具（技能安全审查）/ 工作流（多技能组合治理）。触发词：跨会话组合攻击、Instruction Propagation、Data Boundary Violation、Evidence Poisoning、persistent artifact 攻击面、SkillRelayBench、SkillRelayGuard、工件来源上下文恢复、执行前 advisory、ASR/ACSR、组合安全。

## 滥用门覆盖按 denylist：只豁免平台自管 provider，未来公共 provider 默认受检；验证信号有证明范围；判定宽容度按副作用分面（来源：api.github.com/repos/activepieces/activepieces/pulls/15591，2026-10-12 merged 12:22Z，一手 gh api 逐串命中）
- **实证**：`signUp` 只在 `provider === EMAIL` 时跑 ZeroBounce 滥用门。Google 登录是 Cloud 的公共门且**不经任何邮件即铸造 verified 身份**（`verified: isFederatedProvider`，`sendVerificationOrAutoVerify` 什么都不发）——门被整体跳过。2026-09-16，曾在邮件路径被打掉的数据农场（1,458 个 `emalupe.com` 账号）经 Google 回归：一次性 `.shop` 域名靠 `google-site-verification` TXT 记录过 Google 验证、**无 MX**，36 个 Cloud Identity 账号（`user`、`user01`…`user35`），20 条流 5 秒内先后触发，HK/TW/JP IP 轮换。PostHog：36/36 有 `federated.login.started`（provider: google）早于 `signed.up` 20–55s，`email.code.*` 与 `signup.submitted` 零事件。**Google 的 `email_verified: true` 只意味着"此人控制该 Google 账户"，不说明该地址或域名能收信**——ZeroBounce 对这些地址的 `invalid`/`no_dns_entries` 判定正确却从未被咨询。修复三件：① 门按 provider **denylist** 化——`requiresSignUpAbuseCheck` 只跳过 `PLATFORM_CONTROLLED_PROVIDERS`（JWT 托管认证嵌入、SAML），EMAIL 与 GOOGLE 都查，**未来公共 provider 默认受检而非静默豁免**；denylist 项配测试钉住（不花 credit）。② **domain 级 invalid 判定拒绝**（`no_dns_entries`/`does_not_accept_mail`/`unroutable_ip_address`）——不能收信的域名拒掉的是本也完不成注册者，且不泄漏任何单邮箱信息；**mailbox 级 invalid 保持允许**（`mailbox_not_found`/`possible_typo`/`mailbox_quota_exceeded`）——拒绝它等于把公共端点变成 mailbox 存在性 oracle 并惩罚 typo（决策 000032）；`failed_syntax_check` 在 `EmailType` 后不可达，钉为允许而非留死代码。③ **被拒的 Google 注册伪装**：抛无参 `INVALID_CREDENTIALS`——与 Google token 交换失败的既有响应完全同形；诚实的 `DOMAIN_NOT_ALLOWED` 先试后回滚——攻击者读响应体，"domain not allowed" 恰好告诉他该补哪条 DNS 记录。缓存按信号稳定性分面：dead-domain 判定**不按域名缓存**（DNS 瞬变、列表无 TTL），disposable 缓存不变且现覆盖 Google 路径（同一一次性域第二个账号不花 credit）。诚实声明局限：修掉今天这个配置（无 MX 的 Google 租户）修不掉这一类——一条免费 MX 记录（Cloudflare Email Routing）就把判定翻成 `catch-all` 或 `mailbox_not_found`（均允许），最便宜一级转化成本近零、六行代码、每层买周级时间；持久解是信任分层计算（年轻/无 MX/免费邮域可自由构建测试，生产运行与 AI 额度前需 $0 卡认证；`domain_age_days`/`mx_found`/`free_email` 已在 ZeroBounce 响应里，Autumn 已暴露 `paymentMethod`）——单独 PR。
- **判据**：① **门禁覆盖按 denylist 设计**：只列平台自管 provider（JWT/SAML），其余默认受检——未来新增公共入口自动纳入，不会"静默豁免"；denylist 每项配测试钉住行为。② **验证信号有证明范围**：federated 的 `email_verified=true` 只证明"控制该账户"，不证明"域名可收信"——把登录验证当邮件能力证据是范畴错误；门禁判据要按信号的证明范围取，不按信号强度取。③ **判定宽容度按副作用分面**（承 ssc 1.57.0 同原则新实例）：domain 级拒绝（不误伤本可完成的注册、不泄漏单邮箱信息），mailbox 级允许（免 oracle + 不惩罚 typo）。④ **拒绝响应防泄漏**：诚实错误消息会告诉攻击者该补哪条 DNS 记录 ⇒ 伪装成与既有失败（token 交换失败）完全相同的通用响应；对合法用户的信息量与对攻击者的信息量是两条设计线。⑤ **缓存按信号稳定性分面**：瞬变信号（DNS）不缓存，稳定信号（disposable 名单）缓存并跨路径复用。⑥ **诚实声明防线层级**：修掉当前配置≠修掉类——最便宜一级转化成本近零，每层只买周级时间；持久解单独排期，不在本条里假装完备。
- 提升层：工具（注册/滥用治理）/ 工作流（门禁覆盖面审计）。触发词：滥用门 denylist、未来公共 provider 默认受检、PLATFORM_CONTROLLED_PROVIDERS、email_verified 证明范围、domain 级拒绝 mailbox 级允许、mailbox 存在性 oracle、拒绝响应防泄漏、INVALID_CREDENTIALS 同形、缓存按信号稳定性、trust-tiered compute、数据农场经 federated 回归。

## 维护/暂停态放行面不能按 HTTP 方法推断——GET 也会写；用枚举测试把"新路由未分类"变成构建失败（来源：api.github.com/repos/langflow-ai/langflow/pulls/15633，2026-10-11 merged 17:56Z，一手 gh api 逐串命中）
- **实证**：该测试列出 Langflow 自家代码服务的每个 GET/HEAD 路径——今天 172 条（含 feature flag 挂载的）。合并后，**新增 GET 路由的 PR 测试不过**，直到作者把路径加进 `READS` 或给路由 `dependencies=[Depends(changes_the_instance)]`；失败消息说明该做什么。守卫的东西：迁移暂停把每个 GET 当读放行——而**两个 GET 路由照样写数据**：OAuth 流程的两个浏览器路由，暂停期间回来的 consent 在数据库拷贝之后写 token；二者现声明 `changes_the_instance`，暂停期被拒。清单在 PR 开放期间就已干活：审计迹加了五个 GET 路由、数据主体功能七个，每个都被读到尽头——九个只读，三个往审计日志写"谁读了某人的数据"一行（现也声明 `changes_the_instance`）。**没有什么会告诉下一个这样的路由何时被加**——有了这个测试，每个新 GET 路由都必须有人明确归类。清单上方注释命名"一个读仍然会写什么、为何暂停期放它过"：登录算什么、开着的授权审计日志、被重新算出的值、活在进程或缓存里的东西、把行与 provider 对齐的 deployments 路由。测试只问 handler 定义在 `langflow`/`lfx` 的路由（API 文档与插件挂载的不在范围）；deployments 路由虽仅 flag 挂载也在清单上，测试自带那 10 条 ⇒ flag 开关同答。若代价太高，本 PR 可无其他改动关闭——pause endpoints PR 的描述本就写明"没有什么检查一个在 GET 上写的新路由"。
- **判据**：① **维护/暂停态放行面按真实副作用逐路由判定，不按 HTTP 方法推断**——GET ≠ 只读（OAuth 浏览器路由暂停期写 token；审计读路由写"谁读了"的行；重算值、进程/缓存内状态、deployments 行对齐都是"读的写"）。② **枚举测试=分类强制机制**：新增 GET 路由不过测试直到作者显式归类（进 `READS` 或声明 `changes_the_instance`）——"未分类"从无声状态变成构建失败，且失败消息给出动作。③ **放行清单须带"读仍写什么"的注释台账**：每类放行写明它写什么、为何暂停期可放——否则清单随时间腐烂成噪音。④ **覆盖边界诚实声明**：只枚举自家 handler 定义的路由，插件挂载不在范围；flag 门控路由两面同答（自带那 10 条）。⑤ 与 ssc 1.60.0（OAuth 钩子时机枚举）分工：那条管钩子调用时机，本条管维护态放行面的副作用分类。

## 策略引擎的形状：合成策略按评估序展开、写入时报告遮蔽、版本乐观并发、自有与合成分离、floor/priority 附件唯一、先解绑再删、delegate 仅实例域（来源：docs.n8n.io/connect/n8n-api/credential-type-policy.md 34,957B + node-type-policy.md 34,501B，2026-10-12 r546B 一手 curl 200 实拉逐串命中）
- **实证**：n8n 公共 API 的凭据类型/节点类型策略。**合成策略按评估序返回**："its default action and the rules of every attached policy document in evaluation order"；从未配置的实例报 `scopeId: null`、无规则、`defaultAction: allow`、`version: 0`。**写入带版本乐观并发**：`version` must equal the version last read，陈旧值 409；规则 id 在清单内唯一。动作三态 `allow`/`deny`/`delegate`——**`delegate` 在项目作用域不接受**，且文档被挂到项目作用域时其中 delegate 规则被拒（委派是实例域专有动作）。**写入时报告遮蔽**：`warnings` 列出 `[{ruleId, shadowedByRuleId}]`——被更早规则遮蔽的规则在写时 surfaced，不静默排序。**自有与合成分离**：项目 GET 返回"the project's own composed policy, **not the result of combining it with the instance policy**"。**附件模型**：策略文档可复用并挂多作用域；替换作用域附件时每个 `policyId` 与每个 `(isFloor, priority)` 对必须唯一，last write wins 且作用域版本 bump；替换文档规则会 bump 它所挂的每个作用域的版本。**先解绑再删**：删除仍被挂载的文档 409，须先 detach。**共享文档冲突**：项目文档与另一作用域共享时替换该项目策略 409。选择器按 `name` 或 `package`。
- **判据**：① **策略的"生效结果"与"自有配置"是两个读**：项目读自己、实例读合成——混为一个读会让"我没配"与"我配了被上层覆盖"不可分辨。② **规则顺序即语义，遮蔽必须在写入时可见**：后写同名/同选择器规则 silently 吃掉先前的，是策略腐化的主通道；`warnings[{ruleId, shadowedByRuleId}]` 把隐式顺序变成显式告警。③ **策略写入要乐观并发**：version 必须等于上次读到的值，陈旧 409——策略是低频高危写，丢更新比拒绝写入贵。④ **共享文档=耦合版本面**：一个文档挂 N 个作用域，改它 bump 全部 N 个——传播面=被挂面（与 rm 1.121.0 共享文件 bump 同构）。⑤ **删除前置解绑**：挂载中删除 409——防止出现"文档没了但附件还指向它"的悬空引用。⑥ **动作分级按作用域收窄**：`delegate` 仅实例域——越权委派在窄作用域没有意义，按作用域裁动作集比全局统一更安全。⑦ **未配置=显式默认值+version 0**：defaultAction allow 与 version 0 一起报，"没配过"是一等状态而非缺失。

## 强制面的形状：脱敏 floor 是跨实例下限而非每域可选值；只读计数为收紧决策而存在；整对象替换忽略只读字段；强制按认证通道分界且放松不追溯（来源：docs.n8n.io/connect/n8n-api/security-policy.md 8,860B + deploy/host-n8n/configure-n8n/security/manage-security-policies.md 8,773B，2026-10-12 r546B 一手 curl 200 实拉逐串命中）
- **实证**：安全策略含个人空间发布/共享开关、**执行数据脱敏强制 floor**（`redactionEnforcement.floor` 枚举 `off`/`production`/`all`，原文"Minimum execution-data redaction level enforced across the instance"）与 UI 只读计数（`publishedPersonalWorkflowsCount` 等，"shown for awareness before tightening the policy"）。写入语义：**整对象替换**——"Every writable field must be sent. Read-only usage counts from GET are ignored if included, so a GET response can be sent back as a PUT body"，且"takes effect exactly as it would from the UI, using the same validation"（API 与 UI 同一校验）。2FA 强制：**只对邮箱密码登录生效**——"Users signing in through SSO (SAML or OIDC) aren't affected by this setting"（SSO 用户由 IdP 管）；**放松不追溯**：关掉开关后"Users who already set up 2FA keep it enabled but new users are no longer required to configure it"。个人空间策略控制成员能否从个人空间发布/共享工作流与凭据。
- **判据**：① **floor 与每域可选值是两种设置**：floor 是跨实例下限（枚举 off/production/all），域级配置只能在其上收紧不能穿透——把 floor 当普通开关会让人以为"某项目配 off 就能全局关脱敏"。② **只读计数为决策而存在**：收紧前先展示"将影响多少已发布/已共享"——收紧类开关必须配影响面读数，否则管理员在信息不全时做不可逆决定。③ **整对象替换的读写对称**：GET 响应可直接回填为 PUT body（只读字段被忽略）——替换语义 + 只读豁免让 round-trip 无损；缺字段即清空是该形态的代价，须明文"每个可写字段都必须送"。④ **强制面按认证通道分界**：同一"强认证"要求对密码登录强制、对 SSO 用户不适用——因为 SSO 侧的强制点在上游 IdP，本地再套一层是重复且可被绕过；设计强制项先问"这个通道的权威强制点在哪"。⑤ **放松不追溯**：关闭强制只影响新用户，已 adopt 的用户保留——回滚类操作默认不剥夺已获得的安全态，避免"关一次开关全体裸奔"。

## harness 塑形信念：终端成功看不见跨 harness 信念分叉；用 belief-rollout 诊断（预期世界状态+未来决策）测，立即分歧与长程分歧分离（来源：arxiv.org/abs/2607.04528v2，2026-10-12 r546B 一手实拉摘要逐串命中）
- **实证**：论文证明执行 harness 会塑形 agent 对环境的演化信念——**任务、环境、基础 LLM 全部固定，仅换 harness**。方法：belief-rollout 诊断，"traces how an agent's anticipated world state and future decisions evolve under alternative harnesses"；并"separate immediate divergence introduced by the interface from divergence that develops over longer horizons"。在 HIBench-Code、SWE-bench Verified、Terminal-Bench 上实测：跨 harness 信念分叉显著，"often invisible from terminal success alone and can propagate into different downstream actions"。提出 Belief-Invariant World-Modeling（BIWM）："exposes evidence hidden or compressed by harness execution and aligns the resulting belief trajectories across different harnesses"。
- **判据**：① **终端成功不是 harness 等价性的证据**：同模型同任务，harness 不同 ⇒ 信念轨迹分叉且下游动作不同——"都跑通了"证明不了"理解一样"，换 harness 复跑实验前先想这条。② **诊断要 rollout 不要终态**：测"预期的世界状态 + 未来决策"的演化，而不是只看最后输出——分叉常在中途形成、终态巧合地收敛。③ **立即分歧与长程分歧分离定位**：接口层引入的即时差异 vs 长程演化差异，修法与归因都不同。④ **harness 会隐藏/压缩证据**：跨 harness 比对结论前，先确认两边证据面对齐（BIWM 的核心动机）——否则比的是"harness 让你看到了什么"不是"世界是什么"。⑤ 与 §评测冻结 harness（av KB:1073/1074：同题冻结 harness/模型/温度）分工：那条管"同题比对时冻结变量"，本条管"harness 本身既是测量面也是干扰源，且其干扰可以不可见"。

## 稳定证明哈希必须排除时间戳：同一状态重复检查必须得到同一 attestationHash，否则时间差把"没漂移"判成漂移；证据面随功能启用而增长，启用后须复审并刷新接受值（来源：docs.openclaw.ai/cli/policy/attestation.md 5,742B，2026-10-12 r546B 一手 curl 200 实拉逐串命中）
- **实证**：openclaw policy attestation。审计四元组：`policy.hash`（已创作的规则制品）、`evidence`（检查所用实测状态）+ `workspace.hash`（该证据载荷）、`findingsHash`（确切发现集）、`attestationHash`（稳定声明）。关键设计：`attestationHash` identifies the stable claim (policy hash, evidence hash, findings hash, and clean/dirty state) and **deliberately excludes `checkedAt`**, so the same policy state always produces the same attestation hash；`checkedAt` stays in JSON output for audit logs but is not part of the stable hash。生命周期：干净检查后同时接受两个 hash 作 `expectedHash` / `expectedAttestationHash`；**策略规则变→两个都更新；仅工作区设置变→通常只更新 expectedAttestationHash**；启用/升级 `agents.workspace` 或工具姿态规则会把 `agentWorkspace`/`toolPosture` 新证据加进 workspace hash 与 attestation hash ⇒ 须复审新证据并刷新已接受 hash。`policy watch` 重跑检查、当前证据不再匹配 `expectedAttestationHash` 即报漂移；`--once` 供 CI；默认每 2 秒轮询；间隔大于 2,147,000,000 ms 被截断以防计时器溢出。
- **判据**：① **稳定身份哈希排除时间戳**：drift 检测判的是"状态变没变"，时间进哈希会让同一状态每次检查都换 hash——"没漂移"被时间差异判成漂移，检测器失去意义；时间戳只进审计日志。② **接受值分两种保鲜期**（承 rm r516A 两把 hash 锁）：制品 hash 只在文件改时失效，证明 hash 随环境/证据集变——本条补"什么进稳定哈希"的构成判据：证据哈希+发现哈希+干净/脏状态进，时间不进。③ **证据面随功能启用而增长是特性**：开新规则域=新证据进哈希，旧接受值失效不是误报——启用后必须复审新证据再刷新接受值，否则要么漏审要么永假漂移。④ **轮询间隔设 int32 上限**：可配置间隔必须截顶防计时器溢出（2,147,000,000 ms）——"用户传多大都收"是把溢出当配置。
- 提升层：工具（证明/漂移检测设计）/ 工作流（合规接受值管理）。触发词：attestationHash 排除 checkedAt、同状态同哈希、审计四元组、证据哈希+发现哈希+干净脏状态、启用新规则域须复审刷新、policy watch 漂移、--once CI、间隔截顶防计时器溢出、2,147,000,000 ms。

## 组合风险经工具效果-前置依赖图发现：让 LLM「想哪里有害」偏训练分布；执行反馈驱动扩样（来源：arxiv.org/abs/2610.13886v1 X-AgentRed，2026-10-12 r546B 一手实拉摘要逐串命中）
- **实证**：个人 agent 跨服务用工具，**效果会跨服务累积与交互**，良性请求也可能产出 unintended/harmful 结局。现有红队方法要么直接让 LLM 从任务/环境描述里想潜在有害路径，要么把人/LLM 指定的有害目标拆成看似良性的动作组合——**生成偏训练学到的模式**，"potentially favoring familiar tool combinations and leaving novel cross-service interactions underexplored"。X-AgentRed：分析每个工具的效果、潜在危害与执行前置，**构造有向依赖图**——"captures how one tool's effects can satisfy another's execution preconditions"；从图中采样 recipe 并实例化为 agent 能产出有害结局的真实场景；**执行反馈自改进**——"diversifying paths that pr[ove harmful]"（跑过的降权、未探的升权）。
- **判据**：① **组合风险不能靠"让模型想哪里有害"**：自由生成偏训练分布——熟悉工具组合被高估、新颖跨服务交互被低估，红队覆盖面对齐的是模型先验不是系统真实面。② **可达性=效果满足前置**：把工具间"效果→前置"依赖显式建图，组合枚举从"想"变成图采样——只有效果能填上前置的边才是真可达路径。③ **红队也要防局部最优**：执行反馈驱动扩样（有害证明过的降权、新路径升权），否则红队在同一族组合里反复挖。④ 与 §跨会话组合攻击（ssc 1.64.0 IP/DBV/EP）分工：那条管"工件作为跨会话信道的组合风险"，本条管"跨服务工具组合的可达性枚举方法"。

## 收紧型作用域必须是「叠加」不是「替换」；被指名对象找不到时按继承值继续求值，不跳过（来源：docs.openclaw.ai/cli/policy/scopes.md 4,160B，2026-10-13 r547C 一手 curl 200 实拉逐串命中）
- **实证**：openclaw 用 `scopes.<scopeName>` 让特定 agent/通道受比全局基线更严的策略。三条明文设计：① **叠加语义**——"Overlays are additive: **the global rule still runs, and the scoped rule can add its own finding against the same evidence**"；② **名字只是标签，匹配靠 selector**——"The scope name is just a label; matching uses the selector inside the scope"，`agentIds` 只对 `tools`/`agents.workspace`/`sandbox`/`dataHandling.memory`/`execApprovals` 五节生效，`channelIds` 只对 `ingress.channels` 生效；③ **指名缺失的默认方向**——"If an `agentIds` entry is not present in `agents.entries.*`, OpenClaw evaluates the scoped rule against **inherited global/default posture** for that runtime agent id **instead of skipping it**"。文档中 `release-lockdown` 一例对单个 agent 同时收紧 `tools.exec.allowHosts`/`denyTools`/`sandbox.requireMode`/`dataHandling.memory.denySessionTranscriptIndexing`，而全局 `tools.exec.allowHosts: ["sandbox","node"]` 与 `sandbox.requireMode: ["all","non-main"]` 仍然跑。页面 `read_when` 还列了一条病症："A scoped container posture rule reports **unobservable evidence**"。
- **判据**：① **收紧类 overlay 取交集（叠加），不是替换**：替换语义会让"给某作用域单独收紧"变成"该作用域只剩这条收紧规则"，基线规则在此静默失效——收紧一处同时放宽其余是最常见的配置事故。② **同一证据允许多条 finding 并存**：全局一条 + 作用域一条，不允许"一个证据只留一个结论"——结论去重会吃掉其中一方的判据。③ **指名错误的默认方向是"继续求值"不是"跳过"**：用继承的全局/默认姿态继续判，而不是当这条规则不存在——**跳过会让"写错一个 agent id"等价于静默放宽该 agent**，且没有任何信号。④ **作用域 selector 的作用节要显式枚举**：`agentIds` 只在五节生效、`channelIds` 只在一节生效——selector 与节的适用范围不声明，写错位置的人会以为自己收紧了实际上没有。⑤ **"作用域规则报出不可观察证据"要当作检查项写进 read_when**：作用域求值依赖的证据若取不到，规则本身的可信度就降级——**规则的可观察性是其结论可采信的前提**。

## 声明键缺失的缺省方向按"误置代价"定，不按一致性定；删除键不等于设为 false；声明的合法性必须在产出之前校验（来源：windmill-labs/windmill#11703 一手 gh api 2026-10-13 r548A 实拉正文逐串命中）
- **实证**：git 托管的应用可在 `raw_app.yaml` / `app.yaml` 声明 `sandbox` 与 `frontend_api` 作用域。缺省方向是刻意不对称的："**The file has no `sandbox` key**: the deployed isolation and scopes carry over, as before this change. ## 数据进入特权子进程的边界要按「公开契约」白名单校验：字符串 split 再 splat 进命令行 = 把数据通道变成参数通道（来源：api.github.com/repos/PrefectHQ/prefect/pulls/21916，2026-10-13 r551A 一手 gh api 200 逐串命中 `Validate each dependency line in execute_bundle_in_subprocess() before passing to uv pip install` / `Rejects flag-shaped tokens — any line starting with - (e.g. --index-url, --extra-index-url, --find-links, --target) raises ValueError before the subprocess call is made` / `currently splits a dependency string on newlines and splats the resulting tokens directly into subprocess.check_call()` / `It does not alter the happy-path behavior for well-formed inputs and does not rely on any single downstream control`；r551A 落地）
- **实证**：`execute_bundle_in_subprocess()` 把依赖字符串按换行 split 后直接 splat 进 `subprocess.check_call()`；含标志形 token 的依赖表被原样转发给 `uv pip install`。修法四步：剥离空行、**拒绝一切以 `-` 开头的行**（`--index-url` / `--extra-index-url` / `--find-links` / `--target`）、用 `packaging.requirements.Requirement` 逐行按 PEP 508 解析、把**校验后的列表**（而非原始 split 结果）交给子进程。官方动机写明是 defense-in-depth，且「不依赖任何单一下游控制」。
- **判据**：① **「按换行切分再展开成 argv」把数据面升级成了参数面**：只要某一行长得像标志，它就是在**下指令**（改索引源、改安装目标）而不是在声明依赖 ⇒ 任何"把用户字符串变成命令行参数"的通道都必须显式拒绝标志形 token，净化（转义/加引号）不如拒绝可靠。② **校验点要在「进入特权执行」的边界上**：本例卡在 subprocess 调用之前，而不是指望 `uv` 或下游某一道控制来兜 ⇒ 纵深防御的判据是「如果下游那道控制被关掉，我还能不能拦住」。③ **白名单按格式解析优于黑名单穷举标志**：PEP 508 解析器判定"这是不是一个合法的依赖声明"，黑名单却要预判未来所有标志名 ⇒ 输入有公开格式时，优先用格式解析做准入。④ **拒绝依据要能引用公开契约**（"the documented contract of the parameter"），这样误拒可申诉、放行有出处，且不至于为了兼容而放宽从未被支持的输入。⑤ **空行先剥离**：空 token 会变成畸形 argv，属于"格式化副作用"而非"恶意输入"，两类都要处理。⑥ **兼容声明要写出"谁会开始失败"**：本例明确「含标志 token 或语法非法的 bundle 现在会显式报 ValueError —— 这些从未被文档支持过」⇒ 收紧类改动的交付物包含受影响面清单。
- 提升层：工具（子进程调用与参数边界）/ 安全（参数注入面）。触发词：flag-shaped token、splat 进 argv、PEP 508 准入、特权子进程边界校验、不依赖单一下游控制、收紧改动要列受影响面。


## 签名密钥可以「只可用不可读」：外部签名器不得留本地回退，签发审计日志永不携带被保护物（含旁路通道），签名器故障与容量不足要分码（来源：api.github.com/repos/windmill-labs/windmill/pulls/11614，2026-10-13 r551B 一手 gh api 200 逐串命中 `Lets the key that signs Windmill's OIDC tokens live in an HSM or KMS that Windmill can ask for a signature but never read` / `there is no fallback to a local key` / `An invalid configuration, or OIDC_SIGNER_URL together with OIDC_SIGNING_KEY_FILE, stops the server at startup` / `the listing (pending / active / retired) is cached, refreshed periodically and on a 409, validated as a whole, and served in the JWKS without calling the signer` / `It never carries the token, sub, email or username, including through the request span and the OTEL log bridge` / `A job token shed for capacity gets 429 with Retry-After; a signer outage gets 503` / `local verification of every signature`；r551B 落地）
- **实证**：签名密钥迁到 HSM/KMS，Windmill 只能请求签名、永不读取；服务器经 mTLS 对小适配器说话（`GET /v1/keys`、`POST /v1/sign`），claims/issuer/endpoints 不变，**无本地密钥回退**——配置无效、或与 `OIDC_SIGNING_KEY_FILE` 同时配置，服务器**启动时停机**。密钥列表（`pending`/`active`/`retired`）缓存、定期与遇 `409` 刷新、**整体校验**、JWKS 由缓存提供而不回调签名器；`kid` 用 RFC 7638 指纹。签名链路：单次超时 + 总 deadline、进程内限流（内部刷新优先于 job token）、`409` 刷新后重试一次、`429` 暂停并减半、对 502/503/504/超时抖动重试、熔断器、**每份签名本地校验**。新增 `OIDC token minted` 一行日志（含 `caller`/`aud`/`kid`/`exp`，job token 另含 `job_id`/`root_job_id`/`jti`/`signer_request_id`），**永不携带 token / sub / email / username，包括 request span 与 OTEL log bridge**。
- **判据**：① **「能用」与「能读」是可分离的**：把密钥放进 HSM/KMS 后应用只持有签名能力 ⇒ 密钥泄露面的判据是「持有这个进程能导出什么」，能导出多少决定了轮换与审计的紧迫度。② **纵深安全特性不能留静默降级通道**：无本地回退、配置冲突即启动停机 ⇒ 若同时允许本地密钥，「外部签名器已启用」这句话就不再保证任何事；安全开关的默认值必须是「配置错=不起」。③ **验证链不能依赖签名器在线**：密钥列表缓存 + 整体校验 + JWKS 由缓存供应 ⇒ 签发方短暂不可用不应让已签发令牌的验证一起失效，签发与验签的可用性要求不同，要分开设计。④ **审计日志的价值取决于它不含什么**：一行 mint 日志要覆盖 `caller`/`aud`/`kid`/`exp`/`jti`，但**绝不能**带 token/sub/email/username，且要逐条堵住旁路（request span、OTEL 桥）⇒ 声明「日志不含敏感字段」时必须枚举所有出口，主出口干净不等于旁道干净。⑤ **故障码要按「客户端该做什么」分**：签名器故障 = 503（可重试、需熔断），容量不足 = 429 + `Retry-After`（退避）⇒ 混成一个错误会让客户端对不可重试的做重试、或对该退避的放弃。⑥ **外部依赖返回成功不等于产物正确**：`local verification of every signature` ⇒ 把密码学正确性交出去时，至少要自验结果，否则外部签名器的静默错误会产出无法验证的凭据。
- 提升层：安全（密钥托管与凭据签发）/ 工具（外部依赖的故障语义）。触发词：HSM/KMS 外部签名器、只可用不可读、无本地回退、配置冲突停机、JWKS 由缓存供、mint 日志不含身份、request span 与 OTEL 旁路、429 容量 vs 503 故障、每份签名本地校验。
