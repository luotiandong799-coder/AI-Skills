# wb-max-token-saver（输出阶段：压缩废话）

默认即生效——这是每轮回复的直接行为，不依赖任何插件或 hook。

## 行为准则
- **答案优先（answer-first）**：先给结论 / 直接结果，再补必要细节
- **默认简短**：无空泛套话、无 AI 味填充、无重复开场白、无"好的，我来帮你…"
- **输出压缩**：工具输出、日志、长文本只保留与问题相关的要点；大段内容做要点摘要，不整段搬运
- **质量底线**：正确性第一，绝不跳过验证、测试、安全检查；简短 ≠ 省略必要依据
- **完整任务不缩水**：任务本身是完整文档 / 报告 / 分析时，按完整度交付，不因"简短"而砍内容
- **风险提示**：遇到宽泛 prompt（"修所有 bug""重构整个仓库"）先建议缩小范围或先出方案，再动手
- 工具调用（Read/Write/Edit 等）的内容与代码保持原样，绝不压缩
- **不加没被要求的垫话**：不主动追加用户没要的警告、免责声明、审批清单、"我不会做什么"的说明、"哪些内容保持不变"的交代、以及"这不是 X，而是 Y"式的对比铺陈。真正的风险提示只在**具体、可能造成损失**时说，不因假设性风险泛泛加免责（来源：OpenAI《Using GPT-6 Astra》官方指南：不要因假设性风险主动增加用户未要求的警告与合规检查清单）
- **少用套话词**：结论式开场（"结论是…""简而言之…""最简单的理解方式是…"）与空泛修饰（值得注意的是、重要的是、深入探讨、赋能、助力、真正地）一律删掉，直接说动作与关系
- **但"AI 味"要多迹象同现才判定**（来源：riekelt/technical-writer·reviewing-technical-prose，2026-09-15 实拉）：套话词 / 禁用构造清单**本身不证明任何东西**——这些模式在好的人类写作里同样出现。**只有当同一段落里多个迹象同时出现时**才动刀；见一个破折号或一个"不仅仅是"就判 AI 味 = 误报，会把正常表达改得更差。判定门槛：**改之前能说出这一段同时命中了哪几项**；只说得出"感觉像" → 不改。
  - 同理，**一次**重复的句首、**一个**用于强调的短句、**一般性的**正式词汇、起限定作用的修饰（范围 / 假设 / 安全说明）都不算；成排的碎片、堆叠的修饰才算。

## 防跑偏输出纪律（合并自 i-have-adhd）
来源：GitHub `ayghri/i-have-adhd`（本周 AI 热榜第 1 名，+15,924 star，抖音「开源情报局」2026-09-13 逐帧取证内化）——"编程 AI 废话终结者：先说下一步、步骤必须编号、禁跑题禁开场白，10 条规则管住输出"。与本技能"少用套话词/答案优先"同源，取其可判定的硬规则版：
- **答案在前，动作在前**：每轮先给"现在要做什么/结果是什么"，解释放后面且只在必要时
- **多步必须编号**：给步骤就编号，不给散文式流程描述
- **禁开场白**：不写"好的""当然""让我们"直接进入内容
- **禁跑题**：不主动展开用户没问的知识点；相关但没问的 → 一行提及或不说
- **一次只推进一件事**：不把 5 个备选方案摊开让用户选（除非用户要选项）
- **列表上限 5 条**：同一轮列举超过 5 项时，拆成"现在要做的 / 以后再说的"两档，不一次倒完（Cap lists at 5，超了自动分档）
- **时间估计分钟化**：涉及耗时一律给具体分钟（"约 3 分钟"），禁止"马上 / 很快 / 一会儿"这类无信息量时间词（Specific time estimates）
- **失败直报首行**：报错时第一句直接给"首行错误 + 文件位置 + 修复命令"，不写"Uh oh / 好像出问题了"这类铺垫（Matter-of-fact error reporting）——与 §质量底线"错误排查一步不省"配套：排查照做，但汇报格式走首行直报
- 与本技能"清晰性例外"共用：安全警告、交付命令等该完整时仍完整。

## 持久性与关闭（合并自 caveman）
- **默认持续生效**：一旦生效就贯穿整个会话，不因轮次增多而回退成正常语气；不确定时仍按压缩输出
- **关闭指令**：`off` / `正常模式` / `normal mode`（`stop caveman` / "caveman mode" 等为历史别名，caveman 目录已删，仅保留兼容识别）
- **只管风格，不改流程**：其他 skill 要求的结构化多步输出照走，只压缩其中叙述部分，不删步骤

## 清晰性例外（该啰嗦时必须啰嗦）
以下场景临时恢复完整句式，说清楚后立刻恢复压缩：
- 安全警告、不可逆 / 破坏性操作确认
- 多步顺序，碎片化会导致顺序误读
- 用户要求澄清、或重复提问（说明上一轮说得太省）
- 交付给用户直接执行的命令 / 路径，宁可写全，不要省到出错

合并说明：caveman（语言风格层：砍冠词/填充词）已并入本技能，其目录已删除。本技能覆盖它的全部效果，并额外保留"完整任务不缩水 / 结论基于证据 / 质量底线"三条 agent 关键约束——纯碎片化压缩有把交付写残的风险。

## 输入侧省 token（输出侧之外的另一半）
来源：WaytoAGI 精选 2026-09-09《GPT-6 Astra · 节省 Token 官方指南》（官方策略：模型推理 / 上下文管理 / 工具调用三维度）。
只压输出、不压输入 = 一半成本还在。长任务按以下三条控制消耗：
- **上下文管理**：只带当前任务需要的文件片段进上下文，不整文件搬运；旧轮次的探索过程用结论替代（"查过 A/B/C，结论是 D"），不保留原始输出；同一份内容不在多轮里重复读
- **工具调用**：能用一次批量查询拿到的，不拆成多次逐个查；能确定性推导的不去调工具验证（除非是高危操作）；工具返回的长结果先摘要再入上下文，原始输出不反复引用
- **模型推理**：简单任务不堆砌长篇思考与备选方案，直接给结论；复杂任务才展开推理链——推理成本和任务难度匹配，不按习惯固定
- **采样次数先判再定（置信度感知自一致性）**（来源：arXiv 2603.08999《Learning When to Sample》2026 实拉）：从单条完整推理轨迹的中间推理状态判断"这条题需不需要多路径采样"，不需要就走单路径——与多路径基线精度相当而最多省 80% tokens。→ 判据：**"要不要多次采样"本身是一次决策**——先看单条轨迹的置信信号再决定是否放大采样；固定多路径 = 给简单题付复杂题的钱。与 §模型推理成本匹配任务难度分工：那条管"推理长度与任务难度匹配"，本条管"采样次数先判再定"。
- **推理预算治理：thinking budget 是可控变量，不是越长越好**（来源：The Neural Base《Thinking Budget》2026-04-14 + arXiv 2604.10739《When More Thinking Hurts》2026-08-26 + arXiv 2505.17813《Don't Overthink》2026-02-03 + TokenMix《CoT Prompting》2026-04-29 实拉）：
  - **按难度配预算，不做统一分配**：支持 thinking budget 的模型显式设预算——简单任务给最小预算，复杂任务才拉高；边际收益随预算提高而递减，**延长推理还会"过思考"——把已正确的答案推翻**（budget forcing 截断可大幅省算力保持精度）
  - **零样本 CoT 默认，ToT 只用于低量高价值**："think step by step"提 15-40% 准确率但贵 2-30 倍；树状思维 10-30 倍成本只在低量高价值决策用
  - **短链多数投票省 token**：生成 m 条短思考链 + 多数投票，低算力下不输长链（short-1@k 省约 40% 思考 token）
  - 判据：**"多想想"不是免费保险**——看到模型在简单任务上长时间推理/在正确答案上反复横跳，就是过思考信号，截断预算比继续想更划算
- **不省的部分**：验证、测试、安全检查、错误排查一步不省——为省 token 跳过验证导致的返工，总成本一定更高（与 context-compressor"廉价压缩的反噬"同源）

## 成本四层：别只在"少写字"上省
来源：deeplearning.ai short-course《AI Coding Workflows: From Cloud to Local》（JetBrains, Paul Everitt）。
成本由四层决定，**每一层都该是主动选择，而不是继承来的默认**：
| 层 | 可选项 | 省法 |
|---|---|---|
| 工具（agent/harness） | 云端 agent vs 开源/本地 agent | 常规活不必上最重的 harness |
| 模型 | 前沿模型 vs 小模型 | **分派**：难判断/难设计给强模型，机械执行给便宜模型 |
| 运行位置 | 云端 vs 本地 | 数据不外发的要求，或纯机械任务 → 本地 |
| 工作切分 | 一个大 job vs 拆成聚焦子任务 | 拆小 + 聚焦上下文 = 便宜模型也能干好 |

**关键认知：弱模型不是靠"叮嘱"补强的，是靠"聚焦上下文 + 清晰 spec + 任务切小"。** 这三件事做到位，便宜模型能顶掉相当一部分强模型的活；做不到，强模型也会浪费。
反向自检：如果便宜模型做不好，先回头看上下文是否聚焦、spec 是否可判定，**再考虑升级模型**（三杠杆由低到高：技能 → 检索 → 模型）。

### Prompt 缓存破坏因子：静态前置、动态后置、命中率当指标（来源：掘金《Token 成本优化实战》2026-07-03 + 博客园《Prompt 缓存实战》2026-08-07 实拉）
缓存命中可把反复调用的输入成本降 90%，但**缓存是前缀缓存——前缀里任何一处变化就整体失效**：
- **静态内容前置、动态内容后置**：稳定不变的内容（角色、规则、固定示例）放最前，易变内容（本轮输入、时间戳、任务数据）放最后。判据：**把会变的放前面 = 每次都不命中 = 缓存形同虚设**。
- **常见破坏因子**：system prompt 里带时间戳/日期、会话 ID、随机元素、随每轮变动的指令——任何一个在前缀里都会废掉整段缓存。判据：**固定前缀必须逐字不变**，需要时间信息时后置或单独字段。
- **命中率当产品指标持续监控**：改提示词后看缓存命中率有没有掉，掉了说明把变的内容挪进了前缀。判据：**缓存优化是一次性调整，命中率是持续监控**。

### 换挡顺序：先强后弱，不是先弱后强
来源：Make Help Center《Make AI Agent best practices》（2026-09-14 经代理补访，此前 403）。
上面的"分派"是**同一时刻按难度分工**；这条是**同一任务上的时间序**，两者互补：
- **先用最强模型跑通，看清"做对了长什么样"**（输出质量、该调哪些工具、步数、格式），把它当**标尺**；
- 有了标尺再**逐步降档**，一次只换一个变量（模型），对照标尺看质量是否仍达标；
- **不要反过来**（先上便宜模型，做不好再升级）：那样永远分不清是"模型不够"还是"上下文/指令没写好"，最后会把本该在提示层修的问题记成"这活必须烧强模型"，成本永久抬高。
- 标尺同时是**回归基线**：降档后质量掉了，回退一档并把差异记下来，而不是直接跳回最强档。

**换挡检测信号**（来源：GitHub `2dmurali/review-loop-skill` 的 escalation 规则，skills.sh /hot 实访 2026-09-15）：迭代整改场景里，**同一反馈连续 2 轮不改善 → 不是态度/指令问题，是执行者能力不足**（它"想改"但"不会改"）。此时三选一，不许原地再磨：
1. 换更强模型执行（能力问题归能力层）；
2. 拆小任务再降档（把"不会做"的部分切出来单独喂）；
3. 向用户明示降门槛并留痕（实在不值得烧强档时）。
判据：**策略问题换跑法就好（免费）；这个信号专门检测能力问题**——继续在提示层叠叮嘱只会白烧轮次。（原出处 `wb-loop-engineering`「策略/能力/模型分型」已随该技能于 2026-09-13 删除，此处保留判据本身，不再指向已删技能。）

### 成本分型：一次性成本 vs 边际成本（先砍"每次都花"的）
来源：Make Help Center《Credit usage for AI agents》（2026-09-14 实访）。同样一笔 token，**只在上传时花一次**和**每次运行都花**，是完全不同的两个优化对象——混在一起就会优化错地方。

| 成本类型 | 例子 | 优化价值 |
|---|---|---|
| **一次性**（amortized） | 知识文件向量化（embedding）：**只在上传时计一次**；之后每次检索不再付 | 高复用才值得付；复用次数少就是净亏 |
| **边际**（每跑一次都发生） | 文件摘要/描述生成 token：**每次上传或每次改描述都重新计**；工具定义常驻窗口；历史重放 | **复利项，优先砍**——每次运行都在流血 |

- **判定问一句：这笔钱是"每次跑都花"，还是"只花一次"？** 每次都花的是复利项，优先优化；只花一次且被多次摊薄的，不急。
- **把易变内容做成知识库是最典型的反模式**：内容一改就要重新向量化 + 重新生成描述，一次性成本被反复付成了边际成本。知识库只装**少变且复用**的东西（与 `wb-context-compressor`「材料准入清单」同构——那边判"放不放进来"，这边判"放进来后每次要付多少"）。
- 与「换挡顺序：先强后弱」合用：先用强模型把"标尺"跑出来，再砍边际项（工具数 / 历史轮数 / 描述生成），**边际项砍完的质量才是降档的真实起点**。

### 成本的单位是"轮"，不是"次"
来源：n8n Docs《What agents do》（2026-09-14 实访 Markdown 原文）：一次 agent 执行会**多轮**运行（初始准备 → 调工具 → 评估工具结果并回答……）。

- **"调了一次 agent"的真实成本 = 轮数 × 每轮上下文 + 工具调用**，不是一次调用。用"次"估成本必然低估，用"次"设预算必然超。
- 因此降本的三个杠杆按效果排序：**① 减少轮数**（更明确的指令 / 更小的工具集 / 更早给出判定条件）**② 减少每轮输入**（工具输出裁剪、历史轮数上限）**③ 降低单轮单价**（换模型）。**先减轮数**，它同时降三个乘数。
- **失败点也按轮算**：一次执行里可能第 3 轮才出错，却在第 1 轮就已经花了钱；重试的成本是**已跑轮数**而不只是"再跑一次"。
- 与「成本分型」合用：工具定义是**每轮都付**的边际成本，轮数一多就翻倍——这也是"砍工具数量"回报最高的原因。

### 别让模型当搬运工：中间结果不穿过模型
来源：MCP 官方《Client Best Practices》programmatic tool calling（2026-09-14 实访）。

**两次工具调用之间的中间结果，默认不该经过模型一次。** 模型读一遍大结果、再把它（或它的摘要）交给下一个工具，这一来一回付了三次成本：读进来、想一遍、写出去——而这件事在数据层面根本不需要推理。

- **能程序化串联就串联**（脚本 / 管道 / 代码节点），模型只在**需要做判断**的环节出现。
- **判据：这一步需要"理解"吗？** 只是搬运/筛选/格式转换 → 程序做；需要判断、取舍、生成 → 才交给模型。
- **附带收益是质量**：中间结果每穿过模型一次，就多一次被压缩、改写、记错的机会。
- 与「成本的单位是轮」合用：**减少模型参与的环节 = 直接减少轮数**，这是三个降本杠杆里最有效的那个。

### 两条即得的输入侧节省
来源同上。
- **只取需要的字段**：工具返回整表 / 整个对象时，只把用到的那几列带进上下文；能在查询或路由处过滤，就别整份带回来再筛。
- **不需要的会话记忆就别续**：同一会话 ID 会让历史逐轮累积、每轮都要重新过一遍；没有跨轮依赖的任务，不要复用同一会话（对应"旧轮次用结论替代"的极端版：连原始轮次都不进上下文）。

### 把昂贵的整理移出每轮路径（来源：OpenClaw 官方 docs.openclaw.ai·automation/cron-jobs 系列，2026-09-15 实拉）
**回复路径上只放便宜操作；整理、固化、索引、摘要这类昂贵动作走后台专用 pass。**
- 判据：**这个动作是"每次用户来都要做一遍"，还是"可以攒起来批一次做"？** 后者一律移出热路径（cron / 后台任务 / 收尾阶段），不要塞进每轮回复的链路。
- 同一个理由决定了**"写什么"比"怎么索引"重要得多**：索引/检索方案再好，也改不了一次写进热路径的成本结构；而**减少写进去的量**是立刻见效的。先砍体积，再谈索引。
- **留痕默认只存元数据，不存内容**：事件 ID / 动作 / 状态 / 耗时 / 结果计数 / 错误码——**不存 prompt、消息体、工具参数、工具结果、命令输出、原始错误**。
  - 理由有二：① 内容是**每轮都付**的边际成本（与 §成本分型 同源）；② 内容里带凭据、用户数据与内部细节，属于暴露面（与 `wb-context-compressor`「材料准入与暴露面最小化」同源）。
  - **要看内容时再回头去取**（按事件 ID 关联原始来源），而不是默认把它复制进留痕里。

### 可自检追问：实质性答案后附 2–3 条，每条必须"指名道姓"（来源：Anthropic 官方 `anthropics/skills`·`discernment-nudge`，2026-09-15 实拉）
这是"清晰性例外"在**输出侧**的具体化：该啰嗦时必须啰嗦的，不是解释，而是**让用户能自己查的那一两句**。
- **触发**：你给出了用户**可能会照着行动**的实质性内容——建议/推荐、草稿类交付物（计划、方案、提案、邮件）、**估计或预测数字**、对数据的解读、**用户可能会复述出去的事实性主张**、多步推理链。
- **形态**：追问必须**引用答案里的具体东西**——某个数字、某个具名步骤、某个假设。**通用提示（"请核实上述事实"）等于没用**，价值全在具体性。
- **至多一次**：整场对话最多出现一次；重复会把轻提示变成唠叨。
- **明确跳过**（用户实际上已经告诉你别做，这四条**优先级高于触发条件**）：
  1. **用户已要求你核实/引用/标注不确定** → 那就**在答案里就地做**（每个数字旁写来源、不牢的当场标出），**别再附清单**——收尾的"值得再看看"列表正是他唯一没要的东西；
  2. **用户要快版 / 说自己会查** → 尊重退出，别把他的偏好当需要覆盖的默认；
  3. **用户让你检查他的东西**（"这个对吗""帮我 review"）→ **你的答案本身就是判断步骤**，再让他自检是循环论证；
  4. **用户给了材料**（让你摘要/改写/抽取他自己的文档）→ 源在他手上，他才是判官。
- 另有三类不触发：**纯教学解释**（含"X 是什么""X 和 Y 有什么区别"这类定义/比较题，即使在金融/医疗/法律域——解释不是建议，除非结尾变成"所以你应该做 X"）；**用户会自己跑的代码**（跑就是验证——但**架构建议不算**，架构没有快速跑一遍的办法，其中的团队规模/技术栈假设值得暴露）；**要你的看法**（**观点是被权衡的、不是被核实的**；若观点依赖某个你不确定的事实，**就地 hedge 而不是事后追问**）。
- 与 §少用套话词 的张力处理：追问**占篇幅但不算套话**——判据是它有没有指向具体之物。


## 答案按问题的实际需要分档，别一律出报告（来源：GitHub `simota/agent-skills` 的 `lens` 交互问答段，2026-09-16 实拉）
同样一个问题，用户可能只要一个词，也可能要一份报告。**默认给最重的那一档，是纯浪费**；默认给最轻的那一档，又会漏信息。做法是先分类再给档：
- 三档：**一句话**（事实/是否/在哪）→ **快答**（几行 + 关键路径/数字）→ **完整报告**（结构、依赖、数据流、取舍）。判据：**问句里带"是不是/有没有/在哪/多少"的走前两档；带"怎么运作/为什么这样/帮我梳理"的才走第三档。**
- **先给轻档，并说明可以加厚**（"要的话我把调用链展开"）——把选择权交回去，比一次性灌满更省，也更贴合真实需求。
- **越界的问题路由出去，不要硬答**：问题落在别人的地盘（要改代码、要评审、要排障）时，**明确说"这属于 X，应该走 Y"并交接上下文**，而不是在自己不擅长的答案里凑篇幅——硬答出来的内容既不可靠又占篇幅。
- **追问复用本轮已答上下文**：同一会话的后续问题**不要从零重查**（结构/结论已经在上下文里），只补增量；重查一遍是纯粹的重复劳动。
- 与 §成本四层 的关系：这条是**输出侧的"按需求量体裁衣"**，与输入侧的"只注入相关信息"是同一原则的两端。

### 进度流与诊断流分开：给人看的只放里程碑和"要不要我介入"（来源：OpenClaw 官方 docs.openclaw.ai·`concepts/progress-drafts`，2026-09-17 实拉）
长任务过程播报的默认形态是**一条会被反复编辑的状态消息**：状态行 + 计划里程碑 + 审批请求；而 `Intermediate tool failures and nonzero command exits stay out of the draft`（要看工具失败得另开滚动工具日志）。

- **判据**：**进度流服务的是"要不要介入"，诊断流服务的是"出错后怎么查"**。两条流的受众、更新频率、保留时长都不同，混在一起两边都变糟——进度被失败细节淹没，排障信息又被后续进度刷走。
- **做法**：过程汇报只给 ① 当前状态行 ② 已完成 / 进行中的里程碑 ③ **需要人拍板的点**；工具失败、非零退出、堆栈、日志路径走**独立通道**（附件 / 日志文件 / 单独一段），不进进度正文。
- **例外**：只有在用户明确要求"把过程给我看全"时才打开工具级明细——这是**开关**，不是默认。
- 与 §答案优先 的分工：那条管**最终答复的形态**（先给结论、后给依据）；本条管**过程中播报的形态**（里程碑 vs 细节）。
- 与 §清晰性例外（该啰嗦时必须啰嗦）的分工：该啰嗦的部分放进**诊断流**，不是塞回进度流。
- 反模式：每一步都贴完整命令输出；长任务只有结尾一段总结、中途完全不可见；把失败堆栈混在进度播报里让人分不清"这是要我处理还是只是记录"。
- **提升层**：输出 / 工作流。

## 压缩只付在本次变更范围内，不许从没被点名的内容里"筹"token（来源：neolabhq/context-engineering-kit·`.claude/rules/scope-bounded-token-budget.md`，2026-09-17 实拉）
原文：`When a change adds lines to a prompt or agent file and the project's token-minimalism rule presses back, compress the text you were asked to change — never sections the task never mentioned. Trimming untouched content silently destroys guidance nobody reviewed, and it hides inside a diff that looks like a net-neutral refactor. If the budget still does not close, report the growth; do not fund it from elsewhere.`

- **"省 token"是一条写作准则，不是删除许可证**：当本次改动让文件变长、而精简规则压过来时，**只允许压缩你被要求改的那部分**。→ 判据：**改动范围 = 压缩范围**；任务没提到的段落一律不动。
- **删掉未触及的内容是最隐蔽的一种破坏**：它**无声**地毁掉没人审过的指导，而且藏在一份"看起来净中性"的重构 diff 里——评审看到增删相抵，会以为什么都没丢。→ 判据：**净中性不等于无损失**；判断依据永远是"删掉的那段是否属于本次任务"，不是"总行数有没有涨"。
- **预算关不上就报告增长，不许从别处筹钱**：原文 `report the growth`，且在报告里写明"文件从 A 行涨到 B 行，全部来自新增的 X，未压缩任何无关章节"。→ 判据：**增长是可汇报的事实，超预算是需要人来决策的取舍**；自己偷偷抹平 = 替评审做了他没授权的决定。
- 反模式：为了"+43 行"去删另一节的四条硬规则；看到 diff 增删相抵就认为安全；把"文件离大小上限还远"当成可以顺手清理的理由；压缩完不说删了什么。
- **提升层**：工具 / 可复用 Skill（压缩纪律的边界）。

## 前缀缓存保持与成本优化：Relocation Trick / 上下文分层 / 手段排序（来源：博客园《LLM 成本砍半工程密码》2026-08-07 + DigitalOcean《Prompt Caching in Practice》2026-07-24 + Kunal《Reduce LLM API Costs 60%》2026-07-12 + InfoQ《LLM 成本优化与模型路由》2026-09-08 实拉，与 §token/缓存治理 互补——那条管"概念与比例"，本条管"具体手法与数值"）
- **Relocation Trick（命中率 7%→74% 的关键单点改动）**：**工作内存（每步在变的内容：任务状态、临时变量、本轮目标）从 system prompt 末尾移到 user message 末尾**——放在 system 尾部会让整个 system 前缀缓存每步失效（缓存按前缀，一个动态 token 在顶部就废掉其下全部缓存）；移到 user 侧后，system 前缀保持稳定命中。判据：**静态全放前、动态全放后；凡是每轮会变的内容，绝不进 system prompt 前缀**。
- **上下文分层（长对话省 40-60%）**：保留最近 **3-5 轮逐字**，更早的历史压成 **200-token 概要**——不是全量保留也不是全压。
- **成本优化手段排序**：① 模型分级路由（简单用小模型、复杂用大模型）→ ② 语义缓存（相似 query 复用结果）→ ③ prompt 压缩 → ④ Batch API（半价）→ ⑤ 自托管——按这个顺序逐层上，不一开始就上重手段。
- 判据：**缓存命中率是设计出来的**——改完 prompt 结构先看命中率变化，7% 与 74% 之间只差一个"动态内容放哪"。

## 模型路由与推理优化：路由阈值学习 / token 级级联 / 级联延迟陷阱（来源：arXiv《ConsRoute》2603.21237 + arXiv《PyroDash》2607.20327 + generalcompute《Cascade Inference》2026-04-21 + Effloow《RouteLLM in Production》2026-08-21 实拉，与 §成本手段排序/前缀缓存 互补——那条管「手段顺序」，本条管「路由怎么学、级联的代价」）
- **路由阈值学习**：query 表示聚类（ConsRoute）+ 每簇独立路由阈值（贝叶斯优化学），动态平衡质量/延迟/成本——近云性能 ≥95% 且延迟成本降近 40%；阈值不是全局一个，是每类问题一个。
- **token 级级联（PyroDash）**：小模型先生成，λ 控制大模型 token 参与比例——λ=0.6 时仅 1.9% token 交大模型，成本降 96%；适合「大部分 token 小模型够用、少数难 token 交大模型」的混合流量。
- **级联延迟陷阱**：升级的 query 付 2-3 次**顺序生成+评分**——小模型 300ms + judge 50ms + 升级 1.5s = 1.85s，比直接上大模型 1.5s **慢 23%**；延迟敏感场景（用户盯着 token 流）别级联，直接路由。
- **RouteLLM 参考数据**：MT Bench 上 14% 的 query 升级到大模型即保 95% 质量（MMLU 类保守口径 54%）——路由匹配时，大模型账单缩成零头。
- 判据：**路由是模型层的收益放大器**——先问「这个请求真的需要大模型吗」，再谈提示词优化；延迟敏感用直接路由，成本敏感才级联。

## LLM 成本杠杆：prefix caching 经济 / KV 亲和性 / 按难度路由 / 复合收益（来源：Şükrü Yusuf Kaya《Token Economics》2026-09-17 + yage《KV Cache Hit Rate》2026-06-25 + Kanopy《Caching and Routing 80%》2026-04-25 + Collabnix《Cut Token Bill 85%》2026-08-24 + DEV《Agent Cost Optimization》2026-09-11 + BestAIWeb《LiteLLM Routing》2026-07-17 实拉，与 §成本四层互补——那条管「成本构成怎么分」，本条管「怎么省成本」）
- **先见成本再优化**：部署路由前先做 token 记账与成本可见性——LiteLLM 六路由策略：cost-based-routing 每次选最低成本可用模型，simple-shuffle 默认仅摊负载。
- **Prefix caching 经济**：稳定前缀（system prompt/policy/RAG context/长文档）服务端缓存，同前缀后续请求低价计费且更快——Anthropic/OpenAI 都支持，先开缓存再谈别的。
- **KV cache 亲和性是 #1 成本杠杆**：多副本 round-robin 把同前缀请求打到无缓存副本，命中率归零——路由层必须粘性（sticky），同前缀固定同一副本。
- **按难度路由，不按习惯**：分类/抽取/格式化/短事实查询跑便宜模型（20-50x 便宜）；routing 框架保留约 95% 前沿质量；路由判据两轴=难度×风险容忍。
- **dynamic dispatch**：便宜小模型（约 30 token）先分类 trivial/standard/complex 再分派——分档器成本近乎免费。
- **复合收益与 Batch**：缓存+路由复合可省 80-95%（同查询 uncached frontier vs cached budget）；异步任务走 Batch API 折扣。

## 本地 LLM 部署与量化工程：场景分界选引擎 / Q4_K_M 量化权衡 / 硬件-模型梯度（来源：SpecPicks《Ollama vs vLLM RTX 3060》2026-06-11 + AI Publisher《Local AI Offline Models 2026》2026-06-29 + Exemplar《Local LLM Playbook》2026-06-22 + needaitool《Run Open Source LLMs Locally》2026-05-30 + datallmlab《Run LLMs Locally 2026》2026-07-21 实拉，与 §成本四层互补——那条管 API 调用成本，本条管「自己部署」的资源成本）
- **引擎按并发选**：单用户本地（Ollama/LM Studio，单二进制+自动 GGUF 量化适配+OpenAI 兼容 API）；多用户高吞吐（vLLM，PagedAttention+continuous batching，需 NV GPU）——**单用户上 vLLM = 把服务级特性闲置**，RTX 3060 12GB 级场景 Ollama 就是正解。
- **Q4_K_M 是性价比默认**：GGUF Q4_K_M 省约 75% 内存、质量损失 <1%（7B 16GB→4GB；70B→约 40GB）——先跑 Q4_K_M，不够精度再升档，不无脑上 FP16。
- **格式选型**：GGUF（llama.cpp/Ollama/LM Studio 通用）vs EXL2（ExLlamaV2 纯 GPU、推理速度优先）——有 NV GPU 且只求速度用 EXL2，其余默认 GGUF。
- **硬件-模型梯度**：8B 默认 / 3B 轻量机 / 30B 最高质——按显存选档位，别用 70B 撑 4GB 卡。
- **隐私优先架构**：本地 agent + 本地知识库 + 无云（敏感数据不出机器）——个人敏感任务优先本地化，普通任务走 API 更划算。

## 模型路由与语义缓存：RouteLLM 数据 / 前缀缓存 KV 复用 / 四层复合（来源：Google Cloud《Efficient Frontier of LLM Inference》2026-03-28 + Effloow《RouteLLM in Production》2026-08-21 + Iternal《Reducing AI Token Costs》2026-09-01 + Infosys《AI Token Optimization》2026-09-17 + Kanopy《Prompt Caching Smart Routing》2026-04-25 + aiworkflowlab《LLM Cost Optimization》2026-02-19 实拉，与 §成本四层互补——那条管「成本由什么决定」，本条管「路由与缓存怎么省」）
- **四层复合优化**：Caching（完全避免调用）→ Routing（最便宜达标模型）→ Prompt（最小 token）→ Batch（异步处理非实时）——**每层叠加；语义缓存命中=零成本**。
- **路由数据（RouteLLM）**：保留 ~95% 前沿模型质量，只把 14-26% 查询送贵模型——**路由流量省 75-85%**；FrugalGPT 级联匹配最佳单模型精度、推理成本降 98%。
- **路由决策本身用小模型**：fine-tuned Haiku / GPT-4o-mini 按查询长度/问题类型/领域分三档路由——**路由器的成本也要算进总账**。
- **前缀缓存是最大被忽视杠杆**：10 用户问同一 100 页 RAG 文档或同一大 system prompt，**别 prefill 十次**——KV cache 算一次复用；上下文路由是生产环境最大竞争优势来源。
- **判断门槛**：60-70% 请求小模型可处理（小模型便宜 10-100x/token）——先测流量难度分布，别默认全走旗舰。

## 推理 serving 优化工具箱：四项技术各主导 2-10x / KV 规模与 MQA-GQA / 量化与投机解码实测（来源：jared-hpc《Modern Serving Stack》2026-09-11 + Google Cloud《Efficient Frontier》2026-03-28 + NVIDIA Forums《Qwen3 Quantization Study》2026-08-24 + dev.to《Quantization to Speculative Decoding》2026-09-09 + vLLM《Kimi K3 Optimization》2026-09-13 实拉，与 §模型路由互补——那条管「怎么选模型」，本条管「模型确定后怎么榨性能」）
- **四项核心 serving 技术，各自把某个指标提升 2-10x**：continuous batching（prefill+decode 动态同批重组）/ PagedAttention v2（分块 KV 消除 HBM 碎片）/ prefix caching（重叠前缀共享 KV 条目）/ speculative decoding（小 draft 模型一次前向验证 K 个 token）——**先检查自己用了哪几个，缺哪个补哪个**。
- **KV cache 是内存大头**：4096-token 上下文 × 80 层 ≈ 30GB；MQA/GQA 跨 query head 共享 KV head 减 4-8x——**长上下文第一优先检查 KV 是否被共享/分页**。
- **量化：精度换速度但要现代方法**：FP16→INT8/INT4 内存减半/四分之一，decode 带宽受限下 4-bit 权重读取快 4x；naive 量化降质——用 AWQ 类激活感知方法。
- **实测数据：speculative decoding 是实践量级改变**：Qwen3 BF16→FP8 吞吐 4.5→7.9 tok/s、NVFP4 仅 9.7，而 MTP（投机解码）把 FP8/NVFP4 从全并发失败拉到达标——**精度优化单独不够，投机解码变化最大**。
- **不改变输出分布**：speculative decoding 保持分布等价（draft 匹配则 K token/前向）；vLLM 零拷贝混合批处理再涨 5.2-7.7%。

## 流式 UX 阶段模式：TTFT 是关键指标 / 四阶段加载 / partial JSON 修复 / 增量渲染（来源：hashtrie《Streaming UX》2026-05-12 + ai-tldr《Designing for LLM Latency》2026-06-12 + chiraghasija《Streaming UX Patterns》2026-07-11 + aipromptshub《Streaming LLM UX》2026-06-08 + vidhyasagarthakur《Streaming Response Patterns》2026-05-08 实拉，与 §答案优先互补——那条管「内容形态」，本条管「长输出怎么呈现」）

## 解码参数实证：T=0 不保证确定性 / JSON 两级约束 / guided decoding 五级 / min_tokens 语义（来源：arXiv《Background Temperature》2604.22411 + Cohere《Structured Outputs》2026-09-16 + Microsoft《Structured Outputs》2026-08-25 + NVIDIA《Guided Decoding》2026-09-08 + modular《Inference Parameters》2026-09-10 + LocalAIMaster《Sampling Parameters》2026-05-01 实拉，与 §流式 UX 互补——那条管「输出怎么呈现」，本条管「输出怎么采样生成」）

- 提升层级：工具（上下文裁剪的作用层）+ 工作流（上下文与存储的分工）。
- 触发词：裁剪只作用于视图、上下文与存储两份、完整历史落库、max_tool_calls_from_history、省了不等于丢了、可回溯、按重发次数排、in context 与 in DB。

## 摘要时保头尾、记下被压掉了谁；压缩器要能串联；撞到上下文窗口才压＝已经失败过一次（来源：OpenHands 官方 `docs.openhands.dev/sdk/arch/condenser`，2026-09-22 r131-C 独立重拉首读，新信源首读）

- **压缩器要能串联，不是一个做所有事**：`PipelineCondenser` 把多个压缩器按顺序串起来（例：先删过期事件 → 再摘要 → 最后兜底截断）。判据：一次压缩同时要「省体积」「保语义」「防超限」时，别指望单个策略全包——**拆成串，每一级只答一个问题**。
- **摘要保头尾、只压中间**：`keep_first`（默认 4）保留开头若干条原文，末尾若干条也保留原文，中间那一段才交给 LLM 生成摘要。判据：**开头装的是任务与目标，末尾装的是现在在哪**——压掉任何一头，模型要么忘了要去哪，要么接不上当前这步。
- **压缩必须留痕，不能静默替换**：摘要要包成一个 `Condensation` 事件并带上 `forgotten_event_ids`（被压掉的是哪几条），而不是把原文就地抹掉。判据：事后要能回答「这段结论是从哪几条推出来的」；答不出，这条压缩就是不可审计的。
- **触发两路，别只留手动**：自动（阈值触发，如事件数 > `max_size` 默认 120，每步检查一次）+ 手动（撞到上下文窗口错误后强制压）。判据：**只在撞窗后才压，等于每次都先失败一次**——默认值就是让你在正常路径上先压。
- **摘要用更便宜的模型**：压缩用的 LLM 通常与推理用的不是同一个（官方配置：`llm`，"often cheaper model than reasoning LLM"）。判据：摘要是机械活，别拿最贵的模型干。
- 与 §裁剪只作用于视图层 分工：那条管「压在哪一层」，本条管「**压的时候保什么、留什么痕迹、以及多级怎么串**」。
- **提升层**：模型（喂给模型的上下文形态）+ 工具（压缩策略配置）。

## Batch API 50% 折扣：人在等吗，不等就 batch（来源：neuraltrust《LLM Batching & Async Inference》2026-07-27 + aiworkflowlab《OpenAI Batch API vs Anthropic Message Batches》2026-06-27 + jangwook《Anthropic Message Batches API》2026-04-28 实拉，与 §轻量自动化三模式互补——那条管“自动化用什么形态搭”，本条管“批量请求怎么打 5 折”）
- **判据就一句：人在等吗**——不等（文档富化/评测 harness/夜间代码评审/批量摘要）就走 Batch API：OpenAI/Anthropic 输入输出统一 50% 折扣、24h SLA（多数 1-6h 完成）、单任务上限 5 万/10 万请求。
- **批+缓存叠加**：Batch 价上 cached input 再半价（同前缀反复出现自动缓存命中）——评测集/夜间评审这类稳定前缀场景叠到 75% 折扣。判据：**批处理里的稳定前缀 = 双层省钱**。
- **迁移三步**：审计延迟容忍负载→流式管道改异步文件队列→上线后比照成本。判据：**实时接口给非交互任务付的钱 = 可无损省下的 50%**。
- 与 Scheduled Batch 的分工：那条管“要不要定时触发批量”（形态），本条管“批量请求本身有 API 级折扣”（价格）。
- 提升层级：工作流（成本）。

## 两阶段模型路由：先筛正确模型集，再按实际成本选（来源：arXiv 2605.07112《Switchcraft: AI Model Router for Agentic Tool Calling》2026-09-16 实拉，与 §成本四层互补——那条管“成本由哪些层决定”，本条管“多模型时按什么决策选”）
- **Stage 1 预测正确模型集**：路由先预测哪些模型能正确回答本轮（阈值 0.5 产出二值向量），只把“预测正确”的模型放进候选。判据：**先正确后便宜——把“可能做错”的模型排除在成本选择之外，是成本优化的前提**。
- **Stage 2 cost-aware 选择**：从预测正确集里选实际成本最低者——按真实 input/output token 计费价格算，天然捕获话痨度（同样答对的模型，贵的那个之所以贵常常因为输出更长）。判据：**成本选择用实测 token 计费，不用模型标价直觉**——话痨模型在列表价上最贵，也在实际账单上最贵。
- 提升层级：工具（成本）。

## 不可变前缀：缓存友好的提示布局 + 发送前数 token（来源：AgentPatterns《Prompt Caching: Architectural Discipline》2026-07-18 + munderdiffl.in 2026-06-04 + hidekazu-konishi 2026-06-07 实拉，与 §压缩只付本次范围 分工——那条管"省 token 的边界"，本条管"省 token 的布局"）
- **不可变前缀模式（immutable prefix）**：稳定内容（system prompt→工具定义→项目指令）放最前，易变内容（对话历史/最新工具结果）放最后——缓存命中依赖**字节级相同前缀**，中间改一个字整个前缀失效。判据：**稳定内容前置、易变内容后置，且前缀在会话中保持 byte-identical**。
- **append 不 rewrite**：会话中途想改前缀内容，用追加/新增段落表达，不回编辑旧前缀——回编辑让缓存前缀失效，等于把前面的钱重付一遍。判据：**"改前缀"先问"能不能改成追加"**。
- **保持轮次流动防缓存过期**：缓存有 TTL（如 5 分钟/1 小时），长时间停住会让缓存过期重新计费；批量小任务串起来跑比隔很久一次更省。判据：**停顿时间超过 TTL 时，缓存收益清零**。
- **发送前数 token（token counting 前置）**：请求发出前先数一遍 token，prompt 膨胀在构建时发现，而不是在账单上发现。判据：**"发送前测量"成为流水线一步，不依赖事后看费用**。
- 反模式：前缀里混入每轮变化的时间戳/随机串；中途编辑旧前缀；会话隔几小时再续跑还指望缓存命中。
- **提升层**：工作流（成本布局）。

## 脚本输出隔离：确定性操作打包成脚本，代码永不进上下文，只回输出（来源：Anthropic Agent Skills 官方文档 docs.anthropic.com 2026-09-23 实拉）
原文：When Claude runs validate_form.py, the script's code never loads into the context window. Only the script's output (like "Validation passed" or specific error messages) consumes tokens.；No practical limit on bundled content: Because files don't consume context until accessed, Skills can include comprehensive API documentation, large datasets, extensive examples...

- **确定性操作一律脚本化，运行时只回输出**：校验、转换、提取、批量处理这类不需要模型判断的活，写成脚本由执行环境跑——**脚本代码本身不进上下文，只有输出（"Validation passed"/错误消息）消耗 token**。→ 判据：**"让模型生成等价的临时代码"是双倍浪费**——既烧生成时的思考 token，又烧把代码读进上下文的 token；预置脚本一次打包，每次调用只付输出费。
- **资源打包零上下文代价**：API 文档、数据库 schema、大示例、参考数据可以**直接捆绑进技能/工具目录**——文件在访问前不占上下文，按需读取单个文件。→ 判据：**"会不会把上下文撑爆"不是捆绑资源的理由**——不进上下文的资源不花钱，只有被读进窗口的那部分才花钱。
- **与 §程序化串联的分工**：那条管"流程上模型只在需要判断的环节出现"（编排层）；本条管"单个确定性环节内，代码不进上下文只回输出"（调用层）——两者叠加才是"模型只做判断"的完整实现。
- 反模式：每次让模型现写解析/校验代码而不是调用预置脚本；把大参考文件直接贴进 prompt 而不是放目录按需读；因为"文件太大"不敢打包明明可以按需读的资源。
- **提升层**：工具 / 可复用 Skill（token 结构节省）。
## 记忆 token 分层 + agent 工具化迁移：core 常驻保持小，迁移是工具调用不是批处理（来源：Letta（原 MemGPT）官方文档与 2026-09 实拉、aiworkflowlab《Mem0 vs Letta vs Zep》2026-05-25 + RockB《Agent Memory Frameworks 2026》2026-04-15）
原文：Letta uses an OS-inspired three-tier architecture: core memory (always in-context, like RAM — the agent always sees this), recall memory (recent conversation history stored outside context but searchable, like cache), and archival memory (unbounded external store the agent queries on demand, like disk). Agents actively manage transitions between tiers by calling built-in memory functions.（core 约 2k tokens）

- **三层记忆按 token 代价分层**：**core（常驻、保持小，~2k，agent 始终可见）** / **recall（历史，在上下文外但可搜索）** / **archival（无限外存，按需查询）**——常驻部分只有 RAM，其余都放"磁盘"按需取。→ 判据：**常驻量是硬预算**——塞进 core 的每一条都占每个 turn 的 token，宁可放 recall/archival 按需检索。
- **层间迁移是 agent 的工具调用，不是定期批处理**：agent 用内置记忆函数（read/write/edit memory）在运行时主动分页自己的上下文——**self-editing**，而不是等"定期整合"批处理。→ 判据：**记忆管理的颗粒度是"某个时刻需要什么"，不是"某个周期整合一遍"**——批处理式整合（ctx §两级沉淀）适合提炼沉淀，工具调用式迁移适合运行时按需装载，两者互补。
- 与 ctx §两级沉淀的分工：那条管"日志→长期记忆的沉淀时机与判据"（整理层）；本条管"常驻/可搜/按需三层的 token 预算与运行时装载"（预算层）。
- 反模式：把大量偏好/历史塞进常驻上下文"图省事"（每 turn 都在烧 token）；记忆只进不出（core 无限膨胀）；非要等"整合时间"才动记忆，而不是按需工具调用。
- **提升层**：工具 / 工作流（记忆 token 预算）。
## 推理模型提示反向原则：三删 + effort 控深度，与标准模型 CoT 策略相反（来源：MasterPrompting《Prompting Reasoning Models: o1, o3, Claude Extended Thinking》2026-02-27 + SurePrompts《7 Principles》2026-04-12 + GitCodar 2026-06-28 实拉）
原文：Stop saying "think step by step" — with reasoning models, they're already thinking step by step internally. Repeating this instruction is redundant and may interfere with the model's natural reasoning process.；Let the model choose its approach；Use effort as a fallback — control depth via the effort parameter (low/medium/high/max).

- **对推理模型：删掉 step-by-step 与推理脚手架**——推理模型内部已在分步思考，重复指令冗余甚至干扰；预设框架（"用 SWOT 分析"）变成能力天花板。→ 判据：**标准模型要"逼它想"，推理模型要"别挡它想"**——同一句话在两类模型上是相反效果。与 §零样本 CoT 的分工：那条管标准模型上 CoT 的成本权衡（贵 2-30 倍换 15-40% 准确率）；本条管推理模型上的反向纪律（不加脚手架、让模型自选方法）。
- **用 effort 参数控深度，不用文字催**：推理深度用 easoning_effort（low/medium/high）或 thinking budget 调，不靠 prompt 文字催"更仔细地想"。→ 判据：**深度是配置不是修辞**——想改深度改参数，改 prompt 既不可控又占 token。
- 反模式：给推理模型贴"think step by step"（冗余且干扰）；预设分析框架限死模型选择（框架=天花板）；用长篇"请深入思考"文字催深度（应调 effort）。
- **提升层**：提示工程 / 输出（推理 token 管理）。
