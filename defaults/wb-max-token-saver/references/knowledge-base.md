## 成本四层：别只在"少写字"上省
来源：deeplearning.ai short-course《AI Coding Workflows: From Cloud to Local》（JetBrains, Paul Everitt）。
成本由四层决定，**每一层都该是主动选择，而不是继承来的默认**：
| 层 | 可选项 | 省法 |
|---|---|---|
| 工具（agent/harness） | 云端 agent vs 开源/本地 agent | 常规活不必上最重的 harness |
| 模型 | 前沿模型 vs 小模型 | **分派**：难判断/难设计给强模型，机械执行给便宜模型 |
| 运行位置 | 云端 vs 本地 | 数据不外发的要求，或纯机械任务 → 本地 |
| 工作切分 | 一个大 job vs 拆成聚焦子任务 | 拆小 + 聚焦上下文 = 便宜模型也能干好 |

**关键认知：弱模型不是靠"叮嘱"补强的，是靠"聚焦上下文 + 清晰 spec + 任务切小"。** 这三件事做到位，便宜模型能顶掉相当一部分强模型的活；做不到，强模型也会浪费。
反向自检：如果便宜模型做不好，先回头看上下文是否聚焦、spec 是否可判定，**再考虑升级模型**（三杠杆由低到高：技能 → 检索 → 模型）。

### Prompt 缓存破坏因子：静态前置、动态后置、命中率当指标（来源：掘金《Token 成本优化实战》2026-07-03 + 博客园《Prompt 缓存实战》2026-08-07 实拉）
缓存命中可把反复调用的输入成本降 90%，但**缓存是前缀缓存——前缀里任何一处变化就整体失效**：
- **静态内容前置、动态内容后置**：稳定不变的内容（角色、规则、固定示例）放最前，易变内容（本轮输入、时间戳、任务数据）放最后。判据：**把会变的放前面 = 每次都不命中 = 缓存形同虚设**。
- **常见破坏因子**：system prompt 里带时间戳/日期、会话 ID、随机元素、随每轮变动的指令——任何一个在前缀里都会废掉整段缓存。判据：**固定前缀必须逐字不变**，需要时间信息时后置或单独字段。
- **命中率当产品指标持续监控**：改提示词后看缓存命中率有没有掉，掉了说明把变的内容挪进了前缀。判据：**缓存优化是一次性调整，命中率是持续监控**。

### 换挡顺序：先强后弱，不是先弱后强
来源：Make Help Center《Make AI Agent best practices》（2026-09-14 经代理补访，此前 403）。
上面的"分派"是**同一时刻按难度分工**；这条是**同一任务上的时间序**，两者互补：
- **先用最强模型跑通，看清"做对了长什么样"**（输出质量、该调哪些工具、步数、格式），把它当**标尺**；
- 有了标尺再**逐步降档**，一次只换一个变量（模型），对照标尺看质量是否仍达标；
- **不要反过来**（先上便宜模型，做不好再升级）：那样永远分不清是"模型不够"还是"上下文/指令没写好"，最后会把本该在提示层修的问题记成"这活必须烧强模型"，成本永久抬高。
- 标尺同时是**回归基线**：降档后质量掉了，回退一档并把差异记下来，而不是直接跳回最强档。

**换挡检测信号**（来源：GitHub `2dmurali/review-loop-skill` 的 escalation 规则，skills.sh /hot 实访 2026-09-15）：迭代整改场景里，**同一反馈连续 2 轮不改善 → 不是态度/指令问题，是执行者能力不足**（它"想改"但"不会改"）。此时三选一，不许原地再磨：
1. 换更强模型执行（能力问题归能力层）；
2. 拆小任务再降档（把"不会做"的部分切出来单独喂）；
3. 向用户明示降门槛并留痕（实在不值得烧强档时）。
判据：**策略问题换跑法就好（免费）；这个信号专门检测能力问题**——继续在提示层叠叮嘱只会白烧轮次。（原出处 `wb-loop-engineering`「策略/能力/模型分型」已随该技能于 2026-09-13 删除，此处保留判据本身，不再指向已删技能。）

### 成本分型：一次性成本 vs 边际成本（先砍"每次都花"的）
来源：Make Help Center《Credit usage for AI agents》（2026-09-14 实访）。同样一笔 token，**只在上传时花一次**和**每次运行都花**，是完全不同的两个优化对象——混在一起就会优化错地方。

| 成本类型 | 例子 | 优化价值 |
|---|---|---|
| **一次性**（amortized） | 知识文件向量化（embedding）：**只在上传时计一次**；之后每次检索不再付 | 高复用才值得付；复用次数少就是净亏 |
| **边际**（每跑一次都发生） | 文件摘要/描述生成 token：**每次上传或每次改描述都重新计**；工具定义常驻窗口；历史重放 | **复利项，优先砍**——每次运行都在流血 |

- **判定问一句：这笔钱是"每次跑都花"，还是"只花一次"？** 每次都花的是复利项，优先优化；只花一次且被多次摊薄的，不急。
- **把易变内容做成知识库是最典型的反模式**：内容一改就要重新向量化 + 重新生成描述，一次性成本被反复付成了边际成本。知识库只装**少变且复用**的东西（与 `wb-context-compressor`「材料准入清单」同构——那边判"放不放进来"，这边判"放进来后每次要付多少"）。
- 与「换挡顺序：先强后弱」合用：先用强模型把"标尺"跑出来，再砍边际项（工具数 / 历史轮数 / 描述生成），**边际项砍完的质量才是降档的真实起点**。

### 成本的单位是"轮"，不是"次"
来源：n8n Docs《What agents do》（2026-09-14 实访 Markdown 原文）：一次 agent 执行会**多轮**运行（初始准备 → 调工具 → 评估工具结果并回答……）。

- **"调了一次 agent"的真实成本 = 轮数 × 每轮上下文 + 工具调用**，不是一次调用。用"次"估成本必然低估，用"次"设预算必然超。
- 因此降本的三个杠杆按效果排序：**① 减少轮数**（更明确的指令 / 更小的工具集 / 更早给出判定条件）**② 减少每轮输入**（工具输出裁剪、历史轮数上限）**③ 降低单轮单价**（换模型）。**先减轮数**，它同时降三个乘数。
- **失败点也按轮算**：一次执行里可能第 3 轮才出错，却在第 1 轮就已经花了钱；重试的成本是**已跑轮数**而不只是"再跑一次"。
- 与「成本分型」合用：工具定义是**每轮都付**的边际成本，轮数一多就翻倍——这也是"砍工具数量"回报最高的原因。

### 别让模型当搬运工：中间结果不穿过模型
来源：MCP 官方《Client Best Practices》programmatic tool calling（2026-09-14 实访）。

**两次工具调用之间的中间结果，默认不该经过模型一次。** 模型读一遍大结果、再把它（或它的摘要）交给下一个工具，这一来一回付了三次成本：读进来、想一遍、写出去——而这件事在数据层面根本不需要推理。

- **能程序化串联就串联**（脚本 / 管道 / 代码节点），模型只在**需要做判断**的环节出现。
- **判据：这一步需要"理解"吗？** 只是搬运/筛选/格式转换 → 程序做；需要判断、取舍、生成 → 才交给模型。
- **附带收益是质量**：中间结果每穿过模型一次，就多一次被压缩、改写、记错的机会。
- 与「成本的单位是轮」合用：**减少模型参与的环节 = 直接减少轮数**，这是三个降本杠杆里最有效的那个。

### 两条即得的输入侧节省
来源同上。
- **只取需要的字段**：工具返回整表 / 整个对象时，只把用到的那几列带进上下文；能在查询或路由处过滤，就别整份带回来再筛。
- **不需要的会话记忆就别续**：同一会话 ID 会让历史逐轮累积、每轮都要重新过一遍；没有跨轮依赖的任务，不要复用同一会话（对应"旧轮次用结论替代"的极端版：连原始轮次都不进上下文）。

### 把昂贵的整理移出每轮路径（来源：OpenClaw 官方 docs.openclaw.ai·automation/cron-jobs 系列，2026-09-15 实拉）
**回复路径上只放便宜操作；整理、固化、索引、摘要这类昂贵动作走后台专用 pass。**
- 判据：**这个动作是"每次用户来都要做一遍"，还是"可以攒起来批一次做"？** 后者一律移出热路径（cron / 后台任务 / 收尾阶段），不要塞进每轮回复的链路。
- 同一个理由决定了**"写什么"比"怎么索引"重要得多**：索引/检索方案再好，也改不了一次写进热路径的成本结构；而**减少写进去的量**是立刻见效的。先砍体积，再谈索引。
- **留痕默认只存元数据，不存内容**：事件 ID / 动作 / 状态 / 耗时 / 结果计数 / 错误码——**不存 prompt、消息体、工具参数、工具结果、命令输出、原始错误**。
  - 理由有二：① 内容是**每轮都付**的边际成本（与 §成本分型 同源）；② 内容里带凭据、用户数据与内部细节，属于暴露面（与 `wb-context-compressor`「材料准入与暴露面最小化」同源）。
  - **要看内容时再回头去取**（按事件 ID 关联原始来源），而不是默认把它复制进留痕里。

### 可自检追问：实质性答案后附 2–3 条，每条必须"指名道姓"（来源：Anthropic 官方 `anthropics/skills`·`discernment-nudge`，2026-09-15 实拉）
这是"清晰性例外"在**输出侧**的具体化：该啰嗦时必须啰嗦的，不是解释，而是**让用户能自己查的那一两句**。
- **触发**：你给出了用户**可能会照着行动**的实质性内容——建议/推荐、草稿类交付物（计划、方案、提案、邮件）、**估计或预测数字**、对数据的解读、**用户可能会复述出去的事实性主张**、多步推理链。
- **形态**：追问必须**引用答案里的具体东西**——某个数字、某个具名步骤、某个假设。**通用提示（"请核实上述事实"）等于没用**，价值全在具体性。
- **至多一次**：整场对话最多出现一次；重复会把轻提示变成唠叨。
- **明确跳过**（用户实际上已经告诉你别做，这四条**优先级高于触发条件**）：
  1. **用户已要求你核实/引用/标注不确定** → 那就**在答案里就地做**（每个数字旁写来源、不牢的当场标出），**别再附清单**——收尾的"值得再看看"列表正是他唯一没要的东西；
  2. **用户要快版 / 说自己会查** → 尊重退出，别把他的偏好当需要覆盖的默认；
  3. **用户让你检查他的东西**（"这个对吗""帮我 review"）→ **你的答案本身就是判断步骤**，再让他自检是循环论证；
  4. **用户给了材料**（让你摘要/改写/抽取他自己的文档）→ 源在他手上，他才是判官。
- 另有三类不触发：**纯教学解释**（含"X 是什么""X 和 Y 有什么区别"这类定义/比较题，即使在金融/医疗/法律域——解释不是建议，除非结尾变成"所以你应该做 X"）；**用户会自己跑的代码**（跑就是验证——但**架构建议不算**，架构没有快速跑一遍的办法，其中的团队规模/技术栈假设值得暴露）；**要你的看法**（**观点是被权衡的、不是被核实的**；若观点依赖某个你不确定的事实，**就地 hedge 而不是事后追问**）。
- 与 §少用套话词 的张力处理：追问**占篇幅但不算套话**——判据是它有没有指向具体之物。

## 前缀缓存保持与成本优化：Relocation Trick / 上下文分层 / 手段排序（来源：博客园《LLM 成本砍半工程密码》2026-08-07 + DigitalOcean《Prompt Caching in Practice》2026-07-24 + Kunal《Reduce LLM API Costs 60%》2026-07-12 + InfoQ《LLM 成本优化与模型路由》2026-09-08 实拉，与 §token/缓存治理 互补——那条管"概念与比例"，本条管"具体手法与数值"）
- **Relocation Trick（命中率 7%→74% 的关键单点改动）**：**工作内存（每步在变的内容：任务状态、临时变量、本轮目标）从 system prompt 末尾移到 user message 末尾**——放在 system 尾部会让整个 system 前缀缓存每步失效（缓存按前缀，一个动态 token 在顶部就废掉其下全部缓存）；移到 user 侧后，system 前缀保持稳定命中。判据：**静态全放前、动态全放后；凡是每轮会变的内容，绝不进 system prompt 前缀**。
- **上下文分层（长对话省 40-60%）**：保留最近 **3-5 轮逐字**，更早的历史压成 **200-token 概要**——不是全量保留也不是全压。
- **成本优化手段排序**：① 模型分级路由（简单用小模型、复杂用大模型）→ ② 语义缓存（相似 query 复用结果）→ ③ prompt 压缩 → ④ Batch API（半价）→ ⑤ 自托管——按这个顺序逐层上，不一开始就上重手段。
- 判据：**缓存命中率是设计出来的**——改完 prompt 结构先看命中率变化，7% 与 74% 之间只差一个"动态内容放哪"。

## 模型路由与推理优化：路由阈值学习 / token 级级联 / 级联延迟陷阱（来源：arXiv《ConsRoute》2603.21237 + arXiv《PyroDash》2607.20327 + generalcompute《Cascade Inference》2026-04-21 + Effloow《RouteLLM in Production》2026-08-21 实拉，与 §成本手段排序/前缀缓存 互补——那条管「手段顺序」，本条管「路由怎么学、级联的代价」）
- **路由阈值学习**：query 表示聚类（ConsRoute）+ 每簇独立路由阈值（贝叶斯优化学），动态平衡质量/延迟/成本——近云性能 ≥95% 且延迟成本降近 40%；阈值不是全局一个，是每类问题一个。
- **token 级级联（PyroDash）**：小模型先生成，λ 控制大模型 token 参与比例——λ=0.6 时仅 1.9% token 交大模型，成本降 96%；适合「大部分 token 小模型够用、少数难 token 交大模型」的混合流量。
- **级联延迟陷阱**：升级的 query 付 2-3 次**顺序生成+评分**——小模型 300ms + judge 50ms + 升级 1.5s = 1.85s，比直接上大模型 1.5s **慢 23%**；延迟敏感场景（用户盯着 token 流）别级联，直接路由。
- **RouteLLM 参考数据**：MT Bench 上 14% 的 query 升级到大模型即保 95% 质量（MMLU 类保守口径 54%）——路由匹配时，大模型账单缩成零头。
- 判据：**路由是模型层的收益放大器**——先问「这个请求真的需要大模型吗」，再谈提示词优化；延迟敏感用直接路由，成本敏感才级联。

## LLM 成本杠杆：prefix caching 经济 / KV 亲和性 / 按难度路由 / 复合收益（来源：Şükrü Yusuf Kaya《Token Economics》2026-09-17 + yage《KV Cache Hit Rate》2026-06-25 + Kanopy《Caching and Routing 80%》2026-04-25 + Collabnix《Cut Token Bill 85%》2026-08-24 + DEV《Agent Cost Optimization》2026-09-11 + BestAIWeb《LiteLLM Routing》2026-07-17 实拉，与 §成本四层互补——那条管「成本构成怎么分」，本条管「怎么省成本」）
- **先见成本再优化**：部署路由前先做 token 记账与成本可见性——LiteLLM 六路由策略：cost-based-routing 每次选最低成本可用模型，simple-shuffle 默认仅摊负载。
- **Prefix caching 经济**：稳定前缀（system prompt/policy/RAG context/长文档）服务端缓存，同前缀后续请求低价计费且更快——Anthropic/OpenAI 都支持，先开缓存再谈别的。
- **KV cache 亲和性是 #1 成本杠杆**：多副本 round-robin 把同前缀请求打到无缓存副本，命中率归零——路由层必须粘性（sticky），同前缀固定同一副本。
- **按难度路由，不按习惯**：分类/抽取/格式化/短事实查询跑便宜模型（20-50x 便宜）；routing 框架保留约 95% 前沿质量；路由判据两轴=难度×风险容忍。
- **dynamic dispatch**：便宜小模型（约 30 token）先分类 trivial/standard/complex 再分派——分档器成本近乎免费。
- **复合收益与 Batch**：缓存+路由复合可省 80-95%（同查询 uncached frontier vs cached budget）；异步任务走 Batch API 折扣。

## 本地 LLM 部署与量化工程：场景分界选引擎 / Q4_K_M 量化权衡 / 硬件-模型梯度（来源：SpecPicks《Ollama vs vLLM RTX 3060》2026-06-11 + AI Publisher《Local AI Offline Models 2026》2026-06-29 + Exemplar《Local LLM Playbook》2026-06-22 + needaitool《Run Open Source LLMs Locally》2026-05-30 + datallmlab《Run LLMs Locally 2026》2026-07-21 实拉，与 §成本四层互补——那条管 API 调用成本，本条管「自己部署」的资源成本）
- **引擎按并发选**：单用户本地（Ollama/LM Studio，单二进制+自动 GGUF 量化适配+OpenAI 兼容 API）；多用户高吞吐（vLLM，PagedAttention+continuous batching，需 NV GPU）——**单用户上 vLLM = 把服务级特性闲置**，RTX 3060 12GB 级场景 Ollama 就是正解。
- **Q4_K_M 是性价比默认**：GGUF Q4_K_M 省约 75% 内存、质量损失 <1%（7B 16GB→4GB；70B→约 40GB）——先跑 Q4_K_M，不够精度再升档，不无脑上 FP16。
- **格式选型**：GGUF（llama.cpp/Ollama/LM Studio 通用）vs EXL2（ExLlamaV2 纯 GPU、推理速度优先）——有 NV GPU 且只求速度用 EXL2，其余默认 GGUF。
- **硬件-模型梯度**：8B 默认 / 3B 轻量机 / 30B 最高质——按显存选档位，别用 70B 撑 4GB 卡。
- **隐私优先架构**：本地 agent + 本地知识库 + 无云（敏感数据不出机器）——个人敏感任务优先本地化，普通任务走 API 更划算。

## 模型路由与语义缓存：RouteLLM 数据 / 前缀缓存 KV 复用 / 四层复合（来源：Google Cloud《Efficient Frontier of LLM Inference》2026-03-28 + Effloow《RouteLLM in Production》2026-08-21 + Iternal《Reducing AI Token Costs》2026-09-01 + Infosys《AI Token Optimization》2026-09-17 + Kanopy《Prompt Caching Smart Routing》2026-04-25 + aiworkflowlab《LLM Cost Optimization》2026-02-19 实拉，与 §成本四层互补——那条管「成本由什么决定」，本条管「路由与缓存怎么省」）
- **四层复合优化**：Caching（完全避免调用）→ Routing（最便宜达标模型）→ Prompt（最小 token）→ Batch（异步处理非实时）——**每层叠加；语义缓存命中=零成本**。
- **路由数据（RouteLLM）**：保留 ~95% 前沿模型质量，只把 14-26% 查询送贵模型——**路由流量省 75-85%**；FrugalGPT 级联匹配最佳单模型精度、推理成本降 98%。
- **路由决策本身用小模型**：fine-tuned Haiku / GPT-4o-mini 按查询长度/问题类型/领域分三档路由——**路由器的成本也要算进总账**。
- **前缀缓存是最大被忽视杠杆**：10 用户问同一 100 页 RAG 文档或同一大 system prompt，**别 prefill 十次**——KV cache 算一次复用；上下文路由是生产环境最大竞争优势来源。
- **判断门槛**：60-70% 请求小模型可处理（小模型便宜 10-100x/token）——先测流量难度分布，别默认全走旗舰。

## 推理 serving 优化工具箱：四项技术各主导 2-10x / KV 规模与 MQA-GQA / 量化与投机解码实测（来源：jared-hpc《Modern Serving Stack》2026-09-11 + Google Cloud《Efficient Frontier》2026-03-28 + NVIDIA Forums《Qwen3 Quantization Study》2026-08-24 + dev.to《Quantization to Speculative Decoding》2026-09-09 + vLLM《Kimi K3 Optimization》2026-09-13 实拉，与 §模型路由互补——那条管「怎么选模型」，本条管「模型确定后怎么榨性能」）
- **四项核心 serving 技术，各自把某个指标提升 2-10x**：continuous batching（prefill+decode 动态同批重组）/ PagedAttention v2（分块 KV 消除 HBM 碎片）/ prefix caching（重叠前缀共享 KV 条目）/ speculative decoding（小 draft 模型一次前向验证 K 个 token）——**先检查自己用了哪几个，缺哪个补哪个**。
- **KV cache 是内存大头**：4096-token 上下文 × 80 层 ≈ 30GB；MQA/GQA 跨 query head 共享 KV head 减 4-8x——**长上下文第一优先检查 KV 是否被共享/分页**。
- **量化：精度换速度但要现代方法**：FP16→INT8/INT4 内存减半/四分之一，decode 带宽受限下 4-bit 权重读取快 4x；naive 量化降质——用 AWQ 类激活感知方法。
- **实测数据：speculative decoding 是实践量级改变**：Qwen3 BF16→FP8 吞吐 4.5→7.9 tok/s、NVFP4 仅 9.7，而 MTP（投机解码）把 FP8/NVFP4 从全并发失败拉到达标——**精度优化单独不够，投机解码变化最大**。
- **不改变输出分布**：speculative decoding 保持分布等价（draft 匹配则 K token/前向）；vLLM 零拷贝混合批处理再涨 5.2-7.7%。

## 缓存工程与批处理成本杠杆：静态前缀/动态后缀 / 一个动态 token 失效整个缓存 / Batch 50% 折扣（来源：Collabnix《Cut Your Token Bill by 85%》2026-08-24 + Şükrü《Token Economics》2026-09-17 + dev.to《Token Accounting Cache》2026-09-11 + Kinda Technical《Caching and Batching》2026-09-17 + Kunal《Reduce Costs 60%》2026-07-12 + Stochastic Sandbox《Token Costs》2026-08-10 实拉，与 §成本四层互补——那条管「四层成本选型」，本条管「缓存与批处理的具体参数」）
- **缓存结构铁律：静态全放前面、动态全放后面**——缓存作用于前缀，**靠近顶部的一个动态 token 使下方整个缓存失效**；稳定指令/示例/工具定义在前，变量内容在后。
- **缓存定价实证（Anthropic 2026-05）**：cache write（首次写缓存）1.25x 输入价、cache read 约 90% off、min cacheable 1024 tokens、TTL 5min 自动续、cached reads 不占 ITPM——**前缀要够长够稳才值得缓存**。
- **Batch API 是离线负载的 50% 折扣**：50k 请求/批、24h 窗口——适合夜间 evals/批量分类/enrichment/离线摘要/大规模内容生成/周期报告；**非时间敏感才用**。
- **语义缓存**：embedding 余弦相似度匹配请求，重复语义请求免推理——RAG 重复问题场景适用。
- **提示压缩（LLMLingua-2 类）**：2-5x 输入 token 减少、质量损失最小——长固定上下文可用。
- **模型路由（RouteLLM threshold）**：查询复杂度匹配模型能力，2x+ 成本降低——先路由再生成。

## 成本可观测性：贵的不是输出是那一大坨 input / 三通道分开看 / 长时自主任务是成本大头（来源：cxuanAI《Agent 上下文工程完整笔记》第 19 章 2026-09-18 用户提供，与 §成本四层互补——那条管「成本由哪几层决定」，本条管「怎么观测、最吓人的是哪一项」）
- **反直觉实证**：某天约 2 亿 token 中 **90%+ 是 cached input**（/goal 不间断跑近 20 小时）——**最吓人的往往是 input 是一大坨上下文，不是输出很长**。
- **分开看 input / cached input / output，不要只看总量**——只看 total 会误以为每次全量烧，实际可能大部分是 cache 命中；也看不见长时任务悄悄吃掉大头。
- **长时自主任务是成本大头**：/goal 跑 20 小时烧 2 亿 token——「不要一个 goal 一路走到黑」不只是效率问题，**也是成本问题**。
- **成本可观测是优化前提**：没有度量就无法判断优化是否有效——先能分开看三通道，再谈省。
- 反模式：只看总量以为输出贵；长任务挂机不管烧 token；省 token 但没度量导致优化前后无法对比。

## Batch API 50% 折扣：人在等吗，不等就 batch（来源：neuraltrust《LLM Batching & Async Inference》2026-07-27 + aiworkflowlab《OpenAI Batch API vs Anthropic Message Batches》2026-06-27 + jangwook《Anthropic Message Batches API》2026-04-28 实拉，与 §轻量自动化三模式互补——那条管“自动化用什么形态搭”，本条管“批量请求怎么打 5 折”）

## 两阶段模型路由：先筛正确模型集，再按实际成本选（来源：arXiv 2605.07112《Switchcraft: AI Model Router for Agentic Tool Calling》2026-09-16 实拉，与 §成本四层互补——那条管“成本由哪些层决定”，本条管“多模型时按什么决策选”）

- **Stage 2 cost-aware 选择**：从预测正确集里选实际成本最低者——按真实 input/output token 计费价格算，天然捕获话痨度（同样答对的模型，贵的那个之所以贵常常因为输出更长）。判据：**成本选择用实测 token 计费，不用模型标价直觉**——话痨模型在列表价上最贵，也在实际账单上最贵。
- 提升层级：工具（成本）。
