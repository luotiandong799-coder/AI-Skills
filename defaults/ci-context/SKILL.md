# CI · 上下文工程与预算（Context Intelligence）

> 本技能是 13 模块中 **CI（上下文智能）** 的载体。完整经验日志在 D 盘：`D:\腾讯AI\WorkBuddy数据\module-memory\CI\MEMORY.md`。关联子技能（长期默认运行）：`defaults/wb-context-compressor`、`defaults/wb-max-token-saver`、`defaults/wb-ponytail`。

## 一、核心认知

- 有效上下文窗口是任务复杂度的函数，非标称容量：检索类可扛几千 token，排序 / 摘要类 400–1200 即崩；退化静默无报错（实测 ~40% fill 开始跳过旧规则）⇒ 预算须显式告警、按最重操作测窗口。
- 规则上限按条数不按行数：~200 条 ceiling（system prompt 已占 ~50），超出后遵守率约 70% 且与文件长度无关；**必须每次成立的约束放确定性 hook 而非 advisory context file**；规则增退役成对。

## 二、触发与协作

- 何时加载：长上下文任务开工前估预算；调 prompt caching 命中率异常时；要不要把某规则改成 hook 时；多 agent 并发设计缓存策略时。
- 与 EI（执行）：预算约束影响计划拆解粒度；与 OI（编排）：缓存税是 agent 调度成本项。

## 三、窗口退化与规则上限方法论（实拉 r710A，2026-11-08）

> 来源：`dotex.org/epic/meta-programming/context-engineering` 一手 WebFetch；arXiv 2602.11988 经 dotex 回读原文（p=.87 / +20% cost）。

- **（r710A-1）窗口是任务复杂度的函数**：检索类可扛几千 token，排序 / 摘要类 400–1200 即崩；退化**静默无报错**（实测 40% fill 开始跳过旧规则）。⇒ 预算须显式告警，且按"最重操作"测窗口，不能只看平均。
- **（r710A-2）规则上限按条数不按行数**：~200 条 ceiling（system prompt 已占 ~50），超出后遵守率约 70% 且与文件长度无关。⇒ 必须每次成立的约束放**确定性 hook**而非 advisory context file；规则增 / 退役**成对**进行，避免 orphan。
- **（r710A-3）多 agent 隔离自带 cache tax**：14 子代理 700K cache_create / 0 cache_read，TTL 5 分钟、缓存键含 model id。⇒ 并发须贴近 TTL 窗口、顺序管线共享上下文落成文件、换模型即缓存清零。

## 四、提示缓存方法论（实拉 r715B，2026-11-08）

> 来源：OpenAI 官方 `platform.openai.com/docs/guides/prompt-caching`（Cloudflare 拦，3 独立域交叉补足）+ aiwiki 厂商表；intuitionlabs 2026-09 五家定价表；落地 `defaults/wb-max-token-saver/references/knowledge-base.md` §r715B-1/2/3 → 1.102.0。

- **（r715B-1）缓存键 = 渲染后的完整前缀**：不是用户可见提示词。隐藏 system 指令、tools 定义与顺序、`parallel_tool_calls`、`text.format` schema、`reasoning.effort`、`context_management` 压缩都参与匹配，任一变化自断点后失配。⇒ 排查 miss 先查**不可见渲染层**。
- **（r715B-2）最小可缓存长度按模型档位分裂**：GPT-5.6+ 1024 / 更老 2048，隐藏 system 内容不计入门槛，命中按 128-token 增量。⇒ "请求总长够" ≠ "可缓存前缀够"——整体超阈值但稳定前缀不足仍 `cached_tokens=0`；同一应用跨型号升级会静默改变可缓存性，参数族须标型号与日期。
- **（r715B-3）缓存是三档计费不是开关**：写 1.25x / 读 0.1x / 未读未写原价，一写一读 1.35x vs 2x、一写九读 2.15x vs 10x；每请求最多 4 写断点、读回溯最近 50 断点取最长匹配、TTL 30m 从写入或复用起算且刷新不另收费。`cache_write_tokens` 高而 `cached_tokens` 低 = 断点前混入变化内容的可机检信号。

## 五、注意力预算的架构根因与上下文可恢复性（实拉 r732C，2026-11-11）

> 来源：Anthropic 官方《Effective context engineering for AI agents》（`anthropic.com/engineering/effective-context-engineering-for-ai-agents`，WebFetch 200 全文逐字）；Anthropic 官方《Scaling Managed Agents: Decoupling the brain from the hands》（WebFetch 200 全文逐字）；Chroma《Context Rot: How Increasing Input Tokens Impacts LLM Performance》（Kelly Hong / Anton Troynikov / Jeff Huber，2025-07-14）经 13labs.au / masterprompting.net / qatronic.com / adroit.io 四独立域交叉回读；Liu et al.《Lost in the Middle》TACL 2024 经 13labs.au 逐字引用。

- **（r732C-1）退化是连续梯度不是悬崖，根因在 n² 注意力与训练分布**：Anthropic 逐字 "This results in **n² pairwise relationships** for n tokens"、"models develop their attention patterns from training data distributions where **shorter sequences are typically more common** than longer ones"、"These factors create a **performance gradient rather than a hard cliff**"。⇒ "窗口没满"**不构成**继续堆料的理由：每引入一个 token 都在消耗有限的 attention budget（"Every new token introduced depletes this budget by some amount"），收益递减先于容量上限出现。目标是 "the **smallest possible** set of high-signal tokens"，且官方明确 "minimal does not necessarily mean short" ⇒ 判据是**信号密度**不是字符数；调参顺序为先最大召回、再按失败模式提精度（compaction prompt 亦然）。与 §三 r710A 分工：那条给"按最重操作测窗口"的工程口径，本条给为什么会这样 + 为什么不能等告警才动手。
- **（r732C-2）干扰项比噪声更毒，结构连贯反而更差；位置效应是任务依赖不可照抄**：Chroma 在固定任务复杂度、只加无关内容的 18 模型实验里，单个 **topically-related distractor** 即把表现压到 needle-only 基线之下、四个复合加剧；低 needle-question 相似度随长度退化更快；**"shuffled haystacks did better across all 18 models"**（结构连贯的噪声反而更抢注意力）；11 个 needle 位置**无显著变化**，与《Lost in the Middle》多文档 QA 的 U 型曲线结论并列 ⇒ 位置效应依赖任务类型，"把关键放首尾"是**待验证假设不是通用定律**，须在本域跑位置探针。⇒ 检索 top-20 不是 20 条证据，而是 1 条答案 + 19 个近似干扰；裁剪动作应按"与问题语义相似度"筛掉近义命中，而非按长度截断。LongMemEval 306 prompts 全量 ~113k tokens vs 聚焦 ~300 tokens，所有模型聚焦版更好 ⇒ **包装形状与信息量同等重要**。
- **（r732C-3）压缩是不可逆决定，正解是把上下文做成窗口外的可查询对象**：Anthropic 逐字 "the standard ways to address this all involve **irreversible decisions** about what to keep"、"It is difficult to know which tokens the future turns will need"、"these are **recoverable only if they are stored**"。Managed Agents 把 context 从"窗口内容"改为**持久化的 session log 对象**，`getEvents()` 让 brain 按位置切片、回退若干事件看前因、重读特定动作前的上下文；harness 负责变换（含为 prompt cache 命中率做重排），**存储与变换分离**——理由是不能预测未来模型需要哪种上下文工程。⇒ 压缩前先把原始轨迹落盘可检索，压缩产物只是**视图**而非唯一真相；验收问"被压掉的内容还能按位置取回吗"。同一架构解耦 brain/hands 后 p50 TTFT 降约 60%、p95 降超 90%（不得混同为压缩收益）。与 §一「必须每次成立的约束放 hook」互补：那条防规则静默丢失，本条防原始上下文不可逆丢失。

## 六、工具面上下文压力先按来源分四路，别把四种手段当四个开关（CI · r738B 2026-11-11 实拉，四独立域交叉）

前几节处理"窗口里装什么"（注意力预算、干扰项、压缩可逆性）。工具面是另一条独立压力源：工具定义与累积的 `tool_result` 块在任务开始**之前**就在占窗口。Claude 官方把这一面拆成四条互不替代的路径，选哪条取决于 token 去了哪里，不是"全开更好"。

- **（r738B-1）四种手段各减一样东西，组合前先定位压力源**。官方逐字表：Tool search → "Tool definitions loaded upfront"，适合 "Many tools (10+), most of which aren't needed every turn"；Programmatic tool calling → "`tool_result` roundtrips"，适合 "Chains of tool calls that can run as a single script"；Prompt caching → "Token cost of repeated tool definitions"，适合 "Stable tool definitions across many requests"；Context editing → "Old `tool_result` blocks in history"，适合 "Long conversations where early results are no longer relevant"。官方结论："each approach targets a different source of context pressure" / "Pick the one that matches where your tokens are going."。判据：① 工具定义膨胀 ≠ 工具结果堆积，减前者用 defer、减后者用脚本化或旧结果裁剪，混用会"开了但没省到地方"；② 组合允许（"You can use these approaches together, because each solves a different part of the problem"），但起步顺序按瓶颈来，不是一次全上。
- **（r738B-2）缓存不减少上下文，只减少重复付费；与 §四的计费口径互补不重复**。官方逐字："Prompt caching doesn't reduce the number of tokens in context, but it reduces what you pay for them on subsequent requests."；"Cache writes carry a 25 percent markup over base input pricing, which pays back on the second request that hits the cache." ⇒ 把 cached_tokens 上升读成"窗口压力下降"是口径错：窗口里那批工具定义仍在，退化风险（§五 n² 梯度、干扰项）一分未减。判据：① 报上下文健康度时把"占窗口的 token 数"与"计费 token 数"分两栏；② 工具集大而**固定**才是缓存主场，工具集频繁变动要回到 r715B 的渲染前缀失配问题；③ 10 个工具以下、每轮都要用全，别为了省基线引入额外一轮检索。
- **（r738B-3）省上下文要付延迟，脚本化改变的是"中间结果进不进历史"**。官方逐字："This trades a small amount of latency (one extra turn to look up a tool) for a large reduction in baseline context usage."；程序化调用把多次 `tool_use`/`tool_result` 往返折叠成一段在沙箱里跑的脚本，"The intermediate results never enter the conversation history."。判据：① 工具搜索的收益要用"基线占用下降"减"多一轮的时延"来算，低延迟交互场景不必然划算；② 判断该不该脚本化，看的是"中间结果有没有资格进历史"，不是"调用次数多不多"；③ 旧结果裁剪是不可逆动作，与 §五 r732C 的正解配套：裁剪前先把原始轨迹存成窗口外可查询对象。

**判非（重要）**：`defer_loading` / `Tool Search Tool` / `Programmatic Tool Calling` / `Tool Use Examples` 的**机制本体**已由豆包自留地学过（`defaults/wb-max-token-saver/references/knowledge-base.md` §788 r206-A 可见工具衰减量化、`defaults/wb-ponytail/references/knowledge-base.md` §193 Tool Use Examples、`engineering/wb-execute-discipline/KB` §7467/10225/13478 tool_choice 与 programmatic 判据），WB **0 落地**这些文件、不复述机制数字（134K / 8.7K / 85% / 49%→74% 均不搬）。本轮只取官方《Manage tool context》一页的**分流判据**：四压力源、缓存不减窗口 token、延迟代价、按瓶颈起步。窄串 `25 percent markup` / `10 or more tools` / `one extra turn` / `four approaches` / `context pressure` 全库 0 命中（本批机检）。

## 八、有效上下文长度必须按基准族测，"窗口没满"从来不是安全声明（CI · r742B 2026-11-14 实拉，三独立域交叉）

§五给退化的架构根因（n² 注意力）与压缩可逆性，§六给工具面四条压力源。本节补的是**验收口径**：标称窗口是"能接受多少输入"，有效长度是"能可靠用上多少"，两者必须分开度量；而一个绿色的单针热力图几乎不能证明任何下游能力。

### r742B-1 ★claimed length ≠ effective length，且两者差距是常态不是例外
Compile N Run《Long Context in Practice》逐字："A config.json that says `max_position_embeddings: 131072` tells you **the largest position the model will accept. It does not tell you whether the model can find, use or reason over a fact that sits 100,000 tokens back**."；RULER（Hsieh et al., NVIDIA, COLM 2024）**effective context length** 定义逐字："the largest tested length at which a model's average score over the 13 tasks stays above a fixed threshold, chosen as **Llama2-7B's score at 4K tokens (85.6%)**"；实测"**Almost every model passes vanilla NIAH at its claimed length and fails RULER's threshold well before it**"：GPT-4 128K→64K、Llama3.1 70B 128K→64K、Qwen2 72B 128K→32K、Mistral-v0.2 7B 32K→16K。Futurecraft《Context Rot》独立逐字："In the authors' words, **'only half of them can maintain satisfactory performance at the length of 32K'**"（17 个声称 32K+ 的模型）；NoLiMa 有效长度表（保持短输入基线 ≥85% 的最长输入）：GPT-4o 声称 128K / 有效 8K、Gemini 2.0 Flash 声称 1M / 有效 4K，"The claimed window is **16x the effective length for GPT-4o and roughly 250x for Gemini 2.0 Flash**"。
- 判据：① 上下文预算按**有效长度**定，不按 model card 的窗口数；② "窗口没满"在 §五 已被判为不构成堆料理由，本条给出可测量的判据——自己任务上按长度扫一遍并定保持率阈值，而不是看 fill 百分比；③ 换型号/换推理配置后有效长度会变，预算表须标型号、基准与日期。与 §三 r710A-1「按最重操作测窗口」分工：那条给工程测法，本条给公开基准对"标称 ≠ 可用"的量化证据与阈值定义方式。

### r742B-2 ★绿色 NIAH 热力图只证明两件事；基准族彼此不可代替
Compile N Run 逐字："**A green heatmap shows that positions work and copying works, nothing more.** Add distractors, multi-hop and non-literal variants."；HELMET（Yen et al., ICLR 2025）逐字："argues that synthetic tests and small task subsets give **noisy, inconsistent rankings**… Across 59 models, it found that **NIAH-style synthetic tasks do not reliably predict downstream performance**, that **categories correlate weakly with each other**, and that open models lag closed ones most on tasks requiring full-context reasoning"；NoLiMa（Modarressi et al., ICML 2025）去掉词面重叠后"at 32K, **11 of the 13 models fell below 50% of their own short-context baseline**, and even GPT-4o dropped from **99.3% to 69.7%**"。Futurecraft 独立交叉："Of 13 models claiming at least 128K, 'at 32K, for instance, 11 models drop below 50% of their strong short-length baselines.' GPT-4o went from 99.3% on short input to 69.7% at 32K."
- 判据：① 基准按"它抓什么"分开记（NIAH＝位置/复制；Lost in the Middle＝位置偏置；RULER＝干扰项/多跳/聚合/QA 的有效长度；NoLiMa＝依赖关键词匹配；HELMET＝应用级下游排名），**不能用 A 的通过给 B 背书**；② 需求若含"跨多段材料推理"或"问题与证据无字面重叠"，单针检索通过率与它无关，必须换对应基准；③ 位置效应按 §五 r732C-2 是任务依赖的待验证假设，基准间的弱相关正好说明"换个任务排名就变"。与 §六 r738B-1「四种手段各减一样」同构但不同面：那条分流**工具面压力**，本条分流**评测能力**。

### r742B-3 ★评估有固定顺序，且配置错误会伪装成"上下文能力差"
Compile N Run 官方《A Checklist for Evaluating an Extended Model》逐字七步：1. **Short-context regression**（≤4K 重跑常规基准，"Static scaling methods can cost some short-context quality"）→ 2. **Perplexity sanity check**（"A blow-up means the configuration is wrong; **a flat curve proves little**"）→ 3. **NIAH grid**（"Anything less than near-perfect here usually means a **configuration error**"）→ 4. **RULER** 按自己业务阈值算 effective length → 5. **Position sweep** 在自家任务上把关键文档从首移到尾 → 6. **语义非字面测试**（NoLiMa 或 HELMET/LongBench/自家长文档任务）→ 7. **Cost and latency**（prefill 与 KV-cache 随长度增长，"Sometimes retrieval over a shorter context beats a long one on both quality and cost"）。《Common Mistakes》逐字："**Equating claimed and effective length**"、"**Reporting only vanilla NIAH**"、"**Using the chat model without its chat template**… which **looks like a context failure but is not**"、"**Forgetting to enable scaling at inference**… measures **extrapolation, not the advertised capability**"、"**Ignoring tokenization in length targets**… build haystacks by **token count**, not by characters"。
- 判据：① 顺序不可跳——先短上下文回归再谈长，否则把配置退化误判成模型能力退化；② 症状"长上下文掉分"先排三个非能力因（chat template / rope_scaling / 字符数当 token 数），排完才归到 §五 的注意力预算；③ 报数字必须带长度口径、分词器、基准名与阈值，跨基准的分数不可比。Futurecraft 明确代际边界："Almost all the work below uses synthetic tasks and models from 2023-2025. **You can't carry its numbers over to current** … no comparable published tables for these models could be found."、"No such table exists for the late-2026 generation" ⇒ 本轮所有数值只作**方法示例**，落地时以自测为准，禁止写死成通用阈值。

## 九、上下文工程是「每次请求重新装配的 payload」：分层定位、逐级留痕、检索评估先于答案（CI · r746B 2026-11-14 实拉，四独立域交叉）

> §3–§8 分别处理窗口退化、缓存计费、注意力预算、工具面压力、有效长度；本轮补的是**装配这一层本身**：谁在改 payload、每次改动在哪一级、以及"答错了"该归因到哪一级。

### r746B-1 ★ 五种实践控制不同对象，质量下降先定位变了哪一层
Braintrust《What is context engineering?》（2026-09-20）逐字定义："the practice of designing and managing everything a language model receives for a single request. It covers how each context source is **selected, ordered, compressed, and fitted within the context window**"；"Prompt engineering focuses on the instructions themselves, whereas context engineering governs the information assembled around those instructions **at request time**"。官方五列对照表逐字：context engineering 控制 "The complete payload assembled for each request: selection, ordering, freshness, compression, and token budget"，**每个请求都变**，衡量 "Context precision and recall, groundedness, utilization, token share, plus task outcome"；prompt engineering 只在刻意编辑时变、用固定数据集上的分数变动衡量；RAG 控制"文档如何索引检索排序"、memory 控制"跨会话持久化什么"，两者逐字 "**supply candidates that context engineering then selects from, so improving either one does not guarantee a better payload**"；fine-tuning 是 "the only practice in this list that changes the model rather than its input"。
- **判据**：答错先问"这一轮相对上一轮变了哪一层"——候选集（RAG/记忆）、装配策略（选择/顺序/截断/压缩）、指令文本、还是模型权重；四层的修复动作互不等价。报告健康度按 **context precision / recall（选对没）+ groundedness / utilization（用上没）+ token share（占了多少）+ task outcome** 分栏，不许只报端到端一个分。与 §六 r738B「四压力源」分工：那条按**来源**分（定义／往返／重复计费／旧结果），本条按**实践层**分。

### r746B-2 ★ 装配流水线九级，每一级必须记下"丢了什么、为什么丢"
同一官方原文："Filtering, conflict resolution, compression, ordering, and truncation can each change what survives into generation, so **each stage should log what it dropped and why**." 九级逐字：① 广收候选（"before applying the final token budget"）② 过滤排序 ③ 去重与冲突按显式优先规则（"Recency, source authority, or application-defined priority"）④ 按预算压缩（"**a shorter payload can still fail if summarization removes a critical detail**"）⑤ 排序与格式化 ⑥ 强制预算（"apply a defined truncation order that removes the lowest-value material first and **records exactly what was dropped**"）⑦ 执行并记 token/latency ⑧ trace 装配上下文（"source IDs, their order, age, token share, any filtering or truncation decisions"）⑨ 打分并把低分生产用例回灌回归集。官方失败表逐字八类各配探测信号，其中 **Silent truncation**＝"Quality drops with **no application error**, usually losing whichever component lands last"、检测靠 "Log the truncation decision per request and alert on truncation frequency"；**Relevant evidence ignored**＝"High context precision paired with low utilization"；**Permission leakage** 用确定性 scorer 断言每个入选源都在当前用户权限内。
- **判据**：装配流水线每一级留结构化 trace（谁被丢、丢弃理由、该级前后 token 数），回归时按级定位而不是"整体质量掉了"。**"没有报错"不构成上下文健康证据**——静默截断、历史挤掉证据、权限越界三类都产出流畅答案。与 §五 r732C-3「压缩不可逆、原始轨迹先落盘」分工：那条保证可取回，本条保证**可归因**。厂商工具（Braintrust span/scorer）仅作实现示例，不绑定。

### r746B-3 ★ 检索评估与答案评估分开；k 取生成器实际收到的条数，块要保住"规则+例外"
PEI Learn《Evaluate retrieval before evaluating the answer》（Updated Aug 2026）逐字："Evaluate retrieval and generation **separately**. Otherwise prompt changes may hide an indexing, ranking, or permission problem."；四指标 recall@k / precision@k / rank / coverage，且 "**Choose k from the amount of context the generator actually receives. Evidence ranked twentieth is not useful if only five passages enter the prompt.**"；用例须含 "**questions whose answer is absent**"、"Retrieval should not be rewarded for returning a related passage when no source establishes the answer"；**chunk integrity** 六项清单（标题与节上下文／表头／定义／**a rule with its exception**／日期版本管辖元数据／原文链接）："A semantically relevant fragment may be unusable if the qualification was split into another chunk."；权限过滤逐字 "**A permission failure is critical even when the answer is factually correct**"；诊断序按 原问题→改写→过滤元数据→嵌入/词法→重排→分块→索引新鲜度，"**Adding prompt detail to the generation stage cannot retrieve a document that was filtered out incorrectly**"。Data AI Hub《RAG Evaluation Guide》（2026-07-21 复核）独立逐字："**Never optimize generation when context recall is low**; attribute metric drops to retrieval vs prompt vs model before changing anything."；"Combined scores hide root cause"；误诊表含 "Correct by lucky parametric guess → 常被误判 Success → 实为 Unfaithful，will fail next query"；"**Calibrate judges on your domain before CI trust**"。
- **判据**：① 评估记录含「问题+权限上下文／所需证据与权威／期望相关与误导段落／检索器版本／recall·precision·rank·coverage／实际交付的上下文／答案忠实度与引证」八项；② k 按**实际进 prompt 的段数**定，不按检索返回条数；③ 分块验收要检查「规则与其例外、表头、版本元数据」是否同块，语义相关但被切断的片段判无效；④ 必备无答案用例与权限用例，权限失败即使答案事实正确也判 critical；⑤ 指标下降先归因（低 recall→分块/嵌入/过滤；recall 好而 faithfulness 低→提示/模型），**禁止用换模型修检索问题**。与 §八 r742B「七步评估顺序」分工：那条测的是**长上下文能力上限**，本条测的是**本次装配有没有把证据送到位**。

## 十、前缀缓存是块级链式哈希 + 有序驱逐 + 隔离维度（CI · r751B 2026-11-15 实拉，四独立域交叉）

> **换道说明**：豆包自留地 `defaults/wb-context-compressor`、`engineering/wb-execute-discipline` 已有「能缓存就缓存／SGLang KV cache+RadixAttention 更快更便宜」等**口号级**命中；本轮不重复性能口号，改取**推理引擎块级机制层**（哈希构成／驱逐顺序／隔离维度／精确前缀硬边界），与 §四 r715B「API 计费层提示缓存」、§六 r738B「cached_tokens 不减窗口压力」分工。

### r751B-1 ★ 缓存键是「块内 token + 全部前缀 token」的链式哈希，中间插一个字后面全失效
vLLM 官方逐字「每个 KV 块可以通过**块内的标记以及块前缀中的标记**唯一标识」「`hash(prefix tokens + block tokens) <--> KV Block`」「将逻辑 KV 块映射到它们的哈希值，并维护一个包含所有物理块的**全局哈希表**」「此设计实现了自动前缀缓存，**而无需在 KV 块之间维护树结构**」；infra.bea.ai 逐字 "Standard prefix caching has a strict limitation: **only exact token-by-token matches from the beginning can be reused**. If shared text appears in the middle, or prompts are similar but not identical, **no reuse happens**"（并给 `[System]+[Doc]` 与 `[Doc]+[System]` 换序即零复用的例子）。
- **判据**：① 稳定公共内容**必须前置且连续**，动态内容（时间戳／用户 ID／检索结果）只能放末尾；在稳定块**中间**插入任何变化内容，自断点起所有后续块哈希全变，命中率归零。② 「前缀看起来一样」不构成命中证据，验收按**实际 cached_tokens／命中块数**记，并连前缀深度一起报。③ 与 §四 r715B 分工：那条是 **API 计费侧**「渲染后完整前缀」，本条是**引擎侧块级哈希**；同向但层级不同，不可互相替代。

### r751B-2 ★ 驱逐是有序三级策略，命中率不是「前缀相同就一直命中」
vLLM 官方逐字「当没有空闲块时，我们将驱逐**引用计数**（即，当前使用该块的请求数量）**等于 0** 的 KV 块」「如果有多个引用计数等于 0 的块，我们优先驱逐**最近最少使用的块（LRU）**」「如果有多个块的最后访问时间相同，我们优先驱逐**位于最长前缀末尾的块**（即，其前面有最大数量块的块）」「此驱逐策略有效实现了与 [RadixAttention] 中**完全相同的策略**，该策略优先驱逐前缀树中引用计数为零和最近最少使用的**叶节点**」；infra.bea.ai 逐字 "Shared blocks use **reference counting** — they're only freed when **no request or cache entry** references them" / "When GPU memory is full, evict the **least recently used** (LRU) cached prefixes"。
- **判据**：① 三级顺序是硬的（refcount=0 → LRU → 最长前缀尾块），**在飞请求持有的块不可驱逐**；由此命中率由「在飞请求数 × 显存水位 × 公共前缀深度」共同决定，而非纯前缀相似度。② 报缓存健康度须连 **refcount／内存水位／命中块数／前缀深度** 一起报，单报百分比不可归因。③ 最深的个性化尾块优先被淘汰是设计选择——公共前缀天然留存；与 §六 r738B「cached_tokens 上升≠窗口压力下降」分工（那条管计费 vs 上下文窗口，本条管命中率的物理成因）。

### r751B-3 ★ 复用与隔离是同一套哈希策略的两面：键里必须带身份/权限维度
vLLM 官方逐字「**多 LoRA 服务**：我们可以简单地让每个 KV 块的哈希值也**包含请求查询的 LoRA ID**」「**多模态模型**：我们可以使用不同的哈希方法来处理不同模态输入的缓存。例如，对图像使用**感知哈希**来缓存**相似**的输入图像」；AIInfraGuide 快照逐字「要留意**多租户环境下的隔离**——vLLM 提供 **cache_salt** 等机制，避免不同租户/权限的请求意外命中彼此的缓存**造成信息泄露**」「把公共内容前置才能命中」。
- **判据**：① 缓存键必须包含**会改变 KV 的身份维度**（LoRA ID／adapter／租户／权限），漏一个就是跨租户误命中＝信息泄露面；启用前缀缓存前先列全这些维度。② 多模态**感知哈希是近似匹配**，与离散 token 的精确哈希语义不同 ⇒ 图像侧「命中」不能按文本侧等价性验收，须单定相似度阈值与误命中检测。③ 精确前缀是硬边界；CacheBlend（重算分歧 token）／Prompt Cache（预定义模块固定位置编码）／语义缓存（整响应跳过推理）是各自的近似复用，**不得混用命中口径**；与 §九 r746B「检索评估与答案评估分开」同构（不同层的命中不可互相背书）。

**提升层**：上下文工程 / 缓存治理。触发词：块级链式哈希、hash(prefix+block)、全局哈希表、refcount=0 才驱逐、LRU、最长前缀末尾块、RadixAttention 叶节点等价、公共内容前置、精确前缀硬边界、cache_salt、LoRA ID 入哈希、感知哈希、命中率不可单报。

## 十一、服务端 context editing 的运行期语义：清除不是压缩，验收要带预览与回执（CI · r755B 2026-11-15 实拉，四独立域交叉）

> **换道说明**：豆包自留地 `defaults/wb-context-compressor` §4753 已有「服务端清除优先于本地修剪」+ `trigger = max(50000, floor(contextWindow*0.3))` / `keep=3` / `clear_at_least` / `clear_tool_inputs:false` 的**参数推导式与缓存口径**，`engineering/wb-execute-discipline` §3789 有「context editing=选择性移除 stale 上下文」口号。WB **0 落地**这两个文件、不搬参数推导式；本轮取**运行期语义与验收协议层**：removal 与 summarization 是两种不同动作、五个参数各改不同的面、清除破缓存的预览/回执三件套、型号代际默认分裂。与 §四 r715B（API 计费层提示缓存）、§六 r738B（工具面四压力源分流）、§十 r751B（引擎侧块级链式哈希）分工明确。

### r755B-1 ★ removal ≠ summarization：官方把 compaction 定为主策略，editing 只是「需要细粒度控制删哪些」的场景
Anthropic 官方《Context windows》逐字「For long-running conversations and agentic workflows, **server-side compaction is the primary strategy for context management**」；官方《Context editing》德文页（WebSearch 快照逐字）「Für die meisten Anwendungsfälle ist **serverseitige Compaction die primäre Strategie** … Die Strategien auf dieser Seite sind nützlich für **spezifische Szenarien**, in denen du eine **feinere Kontrolle darüber benötigst, welche Inhalte gelöscht werden**」。两策略带日期版本：`clear_tool_uses_20250919`（清工具结果）与 `clear_thinking_20251015`（清 thinking 块），beta header `context-management-2025-06-27`，「每策略可以独立配置」；清除机制逐字「Bei Aktivierung löscht die API automatisch **die ältesten Tool-Ergebnisse in chronologischer Reihenfolge**. Die API ersetzt **jedes gelöschte Ergebnis durch einen Platzhaltertext**, damit Claude weiß, dass es entfernt wurde」；certsafari 教材快照逐字「**Context editing works by removal, not summarization.** You set rules, and once a threshold is crossed the API clears specific content **before the prompt reaches Claude**」。对照 compaction：官方《Context editing》同页把客户端 SDK compaction 定义为「**Generiert eine Zusammenfassung und ersetzt den vollständigen Gesprächsverlauf**」，而服务端清除「**wird angewendet, bevor der Prompt Claude erreicht**」，且「Your client keeps the **full unmodified history** — there is **no client state to synchronise**」（GitHub 一手整合逐字）。
- **判据**：① 先按 §六 r738B-1 定位增长来源，再判「这次能不能用 removal 而非 summarization」——removal 只动被规则命中的那些块，未命中部分保持**原文与原有前缀**；summarization 把整段历史改写成摘要，**丢失面不可预测**。两者都不可逆，但 removal 的丢失面**可枚举**（哪几个 tool_use/result、哪个时间段），验收可按枚举项逐条核对；② 「清除」与「压缩」不是同义词，把 clear 当 compact 配置会预期错恢复行为；③ 客户端保留完整历史、服务端在 prompt 到达模型前清除 ⇒ 「模型说没看到、但我本地还在」是**设计不是 bug**，排查这一层再查检索或截断；④ 官方把 compaction 定为主策略 ⇒ 只在「工具结果占增长且需按工具粒度保住一部分」时上 editing，不要反过来把 editing 当默认。与 §五 r732C-3「压缩不可逆、原始轨迹先落盘」分工：那条给可恢复性正解，本条给运行期策略分层与丢失面可枚举性。

### r755B-2 ★ 清除是带触发条件的规则，五个参数各改不同的面；默认值随型号代际分裂
GitHub 一手整合《Compaction & Context Editing Reference》（标注 facts verified against platform.claude.com and anthropic.com **2026-08-30**）逐字参数表：`trigger` 默认 **100,000 input tokens**（阈值，单位 `input_tokens` 或 `tool_uses`）、`keep` 默认 **3 tool uses**（「Most recent tool-use/result pairs preserved」）、`clear_at_least` 默认 **none**（「Minimum tokens cleared per activation — **the cache-economics knob**」）、`exclude_tools` 默认 none（「Tools whose results are never cleared」）、`clear_tool_inputs` 默认 **`false`**（「Also clear the tool *call parameters*, not just results」）。Go 库 `dive/llm` 类型定义（WebSearch 快照逐字）补运行期硬语义：「**If the API can't clear at least the specified amount, the strategy will not be applied.** This helps determine if context clearing is worth breaking the prompt cache」；`keep` 单位随策略分（tool_uses / thinking_turns，`"all"` 可保留全部 thinking）；`clear_tool_inputs` 逐字「By default (**false**), only the tool **results** are cleared **while keeping the original tool calls visible**」。组合顺序是硬约束：「When **combining strategies, thinking-block clearing must be listed first**」。默认行为按型号代际分裂：「**Opus 4.5+ and Sonnet 4.6+ keep all prior thinking; earlier Opus/Sonnet and all Haiku models keep only the last turn**」；certsafari 教材快照补「On Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, **server-side context management never invalidates thinking blocks**」而「**Editing earlier turns yourself on the client can invalidate the thinking in every later assistant turn**」。LangChain 官方 `ClearToolUsesEdit` reference（**WebFetch 200 全文逐字**）给出第三方镜像实现：「This strategy **mirrors Anthropic's `clear_tool_uses_20250919` behavior** by replacing older tool results with a **placeholder text** … **preserves the most recent** tool results and can **exclude specific tools**」，并支持 `trigger: {fraction: 0.8}` / `keep: {fraction: 0.3}` 按模型上限比例配置。
- **判据**：① 配置不能只写 `type`，`trigger / keep / clear_at_least / exclude_tools` 四项须显式声明并各配一条回归用例——`keep=3` 是最小上下文连续性保障（指代「那个文件」「第二次」的最近几轮），`exclude_tools` 应至少含记忆 / 权限相关工具；② `clear_tool_inputs` 决定被清的是「结果」还是「结果+调用参数」，两者对后续可追溯性差别很大，默认 false 时调用参数仍在历史里，**别把它当成整条调用已消失**；③ 换型号会**静默改变 thinking 保留默认值**，参数族必须标型号与日期（与 §四 r715B-2「同一应用跨型号升级会静默改变可缓存性」同构，此处落到清除面）；④ `clear_at_least` 不达标则策略整体不应用 ⇒ 「配了没生效」先查是不是最小清除量没满足，而不是查阈值；⑤ 官方原文提示 `clear_tool_inputs` 的真实类型可接受布尔**或指定工具名数组**（docs 散文只写布尔形态）⇒ 跨实现移植时先核类型契约，别照抄散文。

### r755B-3 ★ 清除破缓存：上线前预览、上线后读回执，把「省下的 token」与「一次 cache write」并报
GitHub 一手整合逐字：「**Clearing invalidates the cached prefix from the clear point onward. Each activation costs a cache write on the next request.** Therefore **set `clear_at_least`**. Without it, a trigger can fire and clear a trivial amount, **paying a full cache re-write to save a few hundred tokens**」；「Thinking-block clearing is the mirror image: **keeping** thinking preserves the cache; **clearing** it invalidates at the clearing point. `"all"` is the cache-optimal setting」。验收三件套逐字：① **回执**「Responses report what was applied: `{"context_management": {"applied_edits": [{"type": "clear_tool_uses_20250919", "cleared_tool_uses": 8, "cleared_input_tokens": 50000}]}}`」，Go 类型定义另给 `OriginalInputTokens`（「useful for calculating token savings」）；② **预览**「`count_tokens` **accepts the same `context_management` block** and returns both the post-clearing `input_tokens` and `context_management.original_input_tokens`」（例 70,000 → 25,000）；③ **配对 memory tool**「Claude is **warned as context approaches a clearing threshold**, and can **write the durable conclusion to memory before the raw material is cleared**. **Clearing without memory throws information away**; clearing with memory demotes it from tier 1 to tier 2」。同页把「compaction is not the default」做成三约束（A 窗口上限 / B 成本上限 / C 延迟目标）与 remedy 顺序：cap tool output → 外移文件留路径 → server-side clearing → summarising compaction，**前两者保缓存、后两者破缓存**；其引用的一单研究（Gemini 3.5 Flash / 660 turns）给出 keep-everything 在 recall/cost/TTFT 三轴同时优于 clear+summarise，但**逐字标注为该研究的数值、非 Claude 基准**，只作机制示意。Anthropic 内部 agentic-search 评测 +29%（仅 context editing）/ +39%（加 memory tool）/ 100-turn web-search 少 84% tokens，同页**明确限定范围**：「the gains are on **long-horizon agentic search**, where Constraint A is genuinely binding. It is **not evidence that clearing helps a twelve-turn conversation**」。
- **判据**：① 上线前用 `count_tokens` 带同一 `context_management` 预览清除前后差值，别靠估算；② 上线后逐请求读 `applied_edits`，把「清了多少 tool_use / input_tokens」与「下一次请求的 cache write 成本」**并报两栏**——单报 input_tokens 下降是把成本挪走，不是省掉（与 §六 r738B-2「占窗口 vs 计费两栏」同构，本条把缓存重写成本加进来）；③ 「清除没生效」排查顺序：阈值未到 → `clear_at_least` 未达标 → `exclude_tools` 命中 → 型号默认 thinking 保留差异；④ 清除前须有落盘/外移路径（§五 r732C-3 的窗口外可查询对象、或 memory tool），否则是把不可逆动作伪装成例行清理；⑤ 所有收益数字只在**其声明的负载形状**内使用，长时域 agentic search 的 +29%/84% 不得迁移到十几轮对话，也不得迁移成跨厂商通用值。与 §四（计费层）、§十（引擎侧块级哈希）分工：本条给 API 运行期清除策略与验收协议。

## r759B · 注意力汇聚（attention sink）：常数内存流式推理的硬约束，不是可省略的缓存优化（来源：Xiao et al.《Efficient Streaming Language Models with Attention Sinks》arXiv:2309.17453 / ICLR 2024，MIT News 官方报道全文逐字 + aiwiki.ai / edgechat.ai / devinfo.dev 多域交叉，2026-11-16 实拉）

> 与 §六/§七/§九/§十（cached_tokens 不减窗口压力·RULER 有效长度·NIAH 证明不了什么·前缀块哈希驱逐）分工：那些管「窗口内 token 怎么计费/怎么评估/怎么复用」，本节管「流超过训练长度后，缓存里必须钉住哪几块才不崩」——一条缓存驱逐的**硬正确性约束**，误删 sink 不是变慢而是困惑度断崖。

- **softmax 归一把残余注意力压到首 token，sink 是算术必然不是语义重要**：MIT News 逐字「The Softmax operation requires all attention scores to sum up to 1. Since most tokens aren't strongly related, their attention scores are very low. The model dumps any remaining attention score in the first token. The researchers call this first token an "attention sink"」；Han 逐字「We need an attention sink, and the model decides to use the first token as the attention sink because it is globally visible — every other token can see it. We found that we must always keep the attention sink in the cache to maintain the model dynamics」。devinfo 逐字「They are not semantically important. They are arithmetically necessary」。**判据：驱逐策略必须把 sink 位置特判钉住**——通用「删最旧/删低注意力」策略会静默删掉 sink（aiwiki 逐字「Heavy-hitter and sliding-window schemes that drop low-attention or old tokens will silently delete sinks unless they special-case them」），这与 §十「驱逐 refcount→LRU」是不同层：§十管普通 KV 块，本节管不可驱逐的锚点块。
- **驱逐 sink = 困惑度悬崖，不是渐进退化**：MIT News 逐字「researchers employ a "sliding cache" that bumps out the oldest tokens ... However, the model's performance often plummets as soon as that first token is evicted」；edgechat 逐字数字「Llama-2-7B with zero initial tokens kept reaches perplexity 3359.95」而保留四个 initial tokens 后「falls from 3359.95 to 9.59」。StreamingLLM 方案逐字「retaining four initial tokens is enough to recover full performance whereas one or two are not」（aiwiki）、「having four attention sink tokens at the beginning of the sliding cache leads to optimal performance」（MIT News）。**判据：验收要测「超过窗口那一刻」而非窗口内**——窗口内指标全绿不能外推到流式场景；sink 数量是模型族属性（预训练模型 4 个、sink-trained 1 个），不可拍脑袋设 1。
- **位置编码必须相对缓存固定 + sink 与量化/速度三面**：MIT News 逐字「the positional encoding of each token must stay the same, even as new tokens are added and others are bumped out. If token 5 is bumped out, token 6 must stay encoded as 6, even though it is now the fifth token in the cache」；edgechat 逐字 RoPE 实现「keys are cached before rotation and re-rotated to their cache positions at each decoding step ... ## r763B · 输入侧提示压缩（LLMLingua）：删掉目标模型最不需要的 token，与 KV 压缩是两个面（来源：Jiang et al. LLMLingua EMNLP 2023 / LongLLMLingua ACL 2024，Microsoft Research 官方项目页全文逐字 + Belgavi.AI Lab 深度解读 2026-10-03 全文逐字 + devinfo.dev《Prompt Compression Is Not KV Compression》逐字 + 微软博客/CSDN 交叉，2026-11-18 实拉）

> 与 §六/§七/§九/§十/§十一（tool context 四来源·cached_tokens 不减窗口·NIAH 证明不了什么·前缀块哈希驱逐·清除≠压缩）分工：那些管「窗口内 token 怎么计费/复用/评估/清除」或「KV 缓存侧」，本节管「**请求发出前，在输入侧永久删掉 token**」——压缩发生在模型读到之前，目标模型是黑盒也能用，与缓存/驱逐是不同层；误删否定词/数字/名字会让答案自信地错。

- **提示压缩 ≠ KV 压缩：一个在模型前（应用侧），一个在解码期（引擎侧）**：devinfo 逐字「One shrinks the KV cache the model holds during decoding. The other shrinks the prompt itself, before the model ever reads it」；「KV compression is a serving concern, inside the engine. Prompt compression is an application concern, in front of any model - including black-box APIs you cannot modify. You compress the input, then send it. The cheapest token is the one you never send」。微软官方逐字「employs a well-trained small language model after alignment, such as GPT2-small or LLaMA-7B, detects unimportant tokens in the prompt and enables inference with the compressed prompt in black-box LLMs, achieving up to 20x compression with minimal performance loss」；「a format that is difficult for humans to understand but can be well interpreted by LLMs」。**判据：本节手段不减 cached_tokens、不动 KV 块，它减的是「发送量/预填等待」**——与 §四/§十（计费与引擎侧复用）并报而不互顶；压缩后的 token 数须用**目标模型的 tokenizer 重数**（Belgavi 逐字库返回的是 GPT-3.5 tiktoken 口径），否则预算错配。LLMLingua-2 换成「从 GPT-4 标签蒸馏出的 keep/drop 分类器，一个编码器 pass，task-agnostic」，与基于困惑度的因果 LM 压缩器是两条路（前者快、后者 question-aware）。

- **三组件 = 预算控制器 + 迭代 token 级压缩 + 分布对齐；独立打分会整段误删**：Belgavi 逐字 Selective Context 两弱点「It treated every part of the prompt the same way, so an instruction was as likely to be cut as filler in a document. And it scored each unit independently, ignoring that once you delete one token, the surprise of the next one changes」。LLMLingua 三件逐字「① budget controller ... instruction and question are short and dense, while demonstrations are long and redundant. The controller assigns a higher keep-rate to the instruction and question and compresses the demonstrations harder ... ranks whole demonstrations by perplexity」；「② iterative token-level compression ... splits the text into segments and compresses them in order, scoring each segment conditioned on the already-compressed text before it. That way, the score of a token reflects what the target model will actually see, not what was in the original」；「③ distribution alignment ... a token that surprises the small model might be obvious to the large one or the reverse. The authors instruction-tuned the small model on text generated by the target model」。信息论口径逐字「self-information ... negative log of its probability. Perplexity over a span is the same quantity averaged and exponentiated ... a rare name, a figure or a domain term, carries a lot」。**判据：① 分段差异化保留率——指令/问题高保留、示例/文档狠压；② 必须按「已压缩后的上文」逐段重打分，一次性独立打分会把重复出现的短语整段抹掉**（do-not-panic 可视化逐字反例：同一短语在 8 个 demo 都出现，独立打分下每个都显得「可预测」而全删）；③ 换目标模型须重做小模型对齐，否则 surprise 分布错配。

- **question-aware（LongLLMLingua）+ 只在「长、可变、检索调好后仍必需」的段落压；具体数字只是论文口径**：Belgavi 逐字「Plain perplexity is question-blind ... a passage can be full of surprising tokens and still irrelevant to the user's question. LongLLMLingua (ACL 2024) makes every stage question-aware ... improving RAG performance by up to 21.4% while using about a quarter of the tokens」；粗粒度「ranks documents by how much each one makes the question likely: roughly, the perplexity of the question conditioned on the document」、细粒度「contrastive perplexity, the change in a token's surprise when the question is present ... reorders documents so the most relevant appear first, countering the lost-in-the-middle effect」「dynamic compression rates」「subsequence-recovery step that maps spans in the model's answer back to the original uncompressed text, so names and figures the compressor mangled can be restored」。**落地纪律逐字**：「Apply it only to long, variable context, never to a cached prefix, structured data or the question, and choose the rate from an evaluation on your own traffic rather than from paper figures」；先「Tune retrieval and turn on prefix caching first, then measure again」；「Compression often holds up on summary-style questions and fails first on questions whose answer is a specific number, date or identifier, because those are exactly the tokens a general-purpose scorer is least sure about」；保护手段 force_tokens/占位符/排除结构化段。do-not-panic 逐字拆穿口径：20× 里「Much of '20×' is dropping redundant demonstrations」（hand-picked 1-shot 422 tok 得 77.10 vs 方法 446 tok 79.08，无需压缩器）、GSM8K 79.08 vs 78.85 仅 0.23 分≈1319 题里约 3 题「nowhere near the noise line」。微软官方 insights 逐字「GPT-4 can recover all the key information from a compressed prompt-emergent ability」「trade-off between language completeness and compression ratio」。**判据：先用重排/前缀缓存等更便宜手段，仍不够才压；rate 用自有流量 sweep（准确率 vs token 曲线 + p95 压缩延迟）定，不抄 20×/21.4%；对数字/日期/ID 类问题优先保护或跳过压缩**。
