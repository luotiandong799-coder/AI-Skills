# wb-ponytail（决策阶段：少写代码）

## 前置分流（先判任务类型，再选阶梯）

| 任务类型 | 走哪条 |
|---|---|
| 单次小改动、修 bug、加小特性 | 下方决策阶梯 + 验证阶梯（本 skill 全程覆盖） |
| **3 步以上 / 跨会话 / 要自主跑到交付的实现任务** | 本阶梯走完定方案后 **转 `wb-spec-driven`**：先立规约（目标 / 验收标准 / 范围内外）→ 计划-实现-检查 → 独立验证 → 交付 |
| 生成类视觉任务（生图 / 改图 / 视频 / 3D / AI 做网页） | **转 `wb-visual-gen`**：先定验收标准 → 备料 → prompt → 生成 → 对照清单自评 → 定向迭代。**禁止直接开生成碰运气** |
| 写作 / 文档 / 研究 / 数据分析 | 不套用本 skill，按内容完整度交付 |

写代码前先走决策阶梯，停在第一个成立的台阶：

1. 这事真的需要存在吗？投机需求 → 跳过并一句话说明（YAGNI）
2. 代码库 / 已有方案里能复用吗？先找后写，不重复造轮子
   - **顺带盘一次执行环境的能力基线**（文件读写 / 子 agent 对话 / 任务协作 / 缓存保留；来源：WaytoAGI 09-10 DeepSeek V4.1 Flash harness 清单）。**环境不支持的方案别硬上**：以"能开子 agent 并行"或"能持久化中间态"为前提的设计，在窄 harness 里必然卡死；缺哪项就在方案里补人工环节，或退回更简单的做法
3. 标准库能做吗？用标准库
4. 平台原生功能覆盖吗？（如 `<input type="date">` 代替日期库、CSS 代替 JS）
5. 已安装依赖能解决吗？绝不为几行代码引入新依赖
6. 能一行搞定吗？一行
7. 最后才写最简可用代码
## 实现前：先核对真实来源，别凭记忆编接口
来源：marketplace `source-driven-development` 独有条目（整包与 `wb-spec-driven` 重叠 >60%，只取这一条并入，不安装）。
**编造 API / 参数名是幻觉最高发的部位，且编译期常常查不出来。**
- 动手前先取证据：**官方文档** > **本地真实源码**（该库在本仓库的现有调用点、`node_modules`/site-packages 里的实现）> 记忆。**记忆只能用来定位，不能用来确认签名**
- 涉及外部库 / 接口 / 命令行参数时，至少找到一处真实来源再写；**找不到证据就在代码注释或交付说明里标"未核对"，不要编一个看着合理的**
- 版本敏感项（API 行为随版本变）先确认本机装的版本，再按该版本的文档写
- 已核对的来源在交付摘要里留一句出处，便于后续复查
- **会增长的枚举不许硬编码**（来源 riekelt/mutation-testing 实拉 2026-09-15）：命令/算子/类别清单"随每次发布增长"（如 `mewt print mutations`），权威清单在运行时可查就每次现查，不把枚举写死在代码或技能里——写死的清单第一次遇到新条目就变成静默漏判
## 能力边界：声明"能力"，不声明路径；权限来自授权，不来自探测

来源：GitHub `william-london/ownframework-loop` `docs/architecture/HOST_CAPABILITIES.md` + `ADAPTER_CONTRACT.md`（2026-09-14 增量）。

- **声明可移植的能力名，不写主机路径 / 凭据 / 供应商位置**：写"需要浏览器能力"，不写 `C:\...\chrome.exe`。路径是环境细节，写进方案就等于把方案钉死在一台机器上。
- **解析失败要在启动前 fail-closed**：能力不可用就**停在动手之前**，不要让执行过程自己想办法（"模型不能扩大自己的主机权限"）。靠运行时兜底 = 兜底的人正好是最想继续跑的那个。
- **"命令在 PATH 里找得到" ≠ "被允许使用"**：PATH 探测只是"存在性证明"，不是"授权证明"。可用性的来源应是**授权清单 / 白名单**，不是"我 which 到了"。同理，"上次能跑"也不是这次能跑的证据。
- **特权能力要证明，不要声明**：容器、本地端口监听这类能力，必须由一次**可复核的验证（canary / 摘要 / 已登记的中间人）**证明可用，且**自证的声明无效**——"我把指纹抄进配置里"不叫验证。拿不出证据的权限 = 没有该权限。
- **第一个实现不是参考实现**：某个平台/工具是"第一个跑通的"，不代表它是规范、更不代表后来者该照抄它。**新东西从与实现无关的接口契约起步，只加自己能证明的部分**。
- **能力要在建立连接时显式声明，并且"清单会变"本身也要声明**（来源：MCP 官方规范，服务器须声明 `capabilities.tools.listChanged`）：**缓存下来的能力视图会过期**。只声明"我有哪些能力"不够，还要声明"这个清单会不会变、变了怎么通知"——否则对端拿着一份旧的清单做决策，失败时看起来像随机故障。
- 反模式：方案里硬编码本机路径；`which` 到就当能用；探测失败后在脚本里加 `|| true` 绕过；把"某工具的实现方式"当"这件事该怎么做"；**只声明能力不声明变更**，让对端的缓存悄悄失效。
## 改动 / 删除前：先查它为什么在那（Chesterton's Fence）
来源：GitHub `addyosmani/agent-skills`（85k★，Google 工程纪律 24 个技能包）中的 Chesterton's Fence 原则。
**"看着没用"和"真的没用"是两件事——先证明后者，再动手。**
- 要删 / 要改任何已存在的东西（代码、配置、脚本、技能、自动化的某一步），先花一分钟找它存在的原因：`git log`/`blame` 看提交信息 → 全库 grep 找引用点 → 看注释与相邻文档 → 问一句"谁会依赖这个行为"
- **查不出原因 = 不能删**，改成先标注（`TODO: 疑似无用，原因待查`）+ 保留；查得出来才可动
- 改动后用**原场景回归**一遍，确认没把别人依赖的行为顺手改掉（Hyrum's Law：任何可观察行为都可能已被依赖）
- 反例（真实踩过）：记忆里写着"已删"，本机其实没删 —— **删完必须 `ls` 复核**，写记录不算删除动作完成
## 改现有代码：外科手术式，不顺手改无关
来源：GitHub `multica-ai/andrej-karpathy-skills`（Karpathy 对 LLM 编码四大坑的观察，只取本地缺的两条并入库，其余 Simplicity/Goal-Driven 已由本 skill 与 `wb-spec-driven` 覆盖）。
**"顺手改进"是 diff 里最常见的污染，也是最难回滚的部分。**
- 只碰**必须**碰的：不"改进"邻近代码、注释、格式；不顺手重构没坏的东西；风格照现状走，即使我本来会写另一种
- **每行改动都要能追溯到用户的这次请求**；追溯不到的，就是混进去的私货
- 顺手发现无关死代码 / 别处的问题 → **只提及，不删不改**（要不要动由用户定，另见下面 Chesterton's Fence）
- 只清理**我这次改动造成的**孤儿（import / 变量 / 函数）；改动前的死代码不碰
## 有界 ≠ 最小：别为了"改动小"把该改的改薄

来源：GitHub `william-london/ownframework-loop` `.agents/skills/of-loop-build`（2026-09-14 增量）：*"A bounded build pass is not required to be minimal… The operator MUST NOT collapse or thin the change set to keep the pass small."*

- **"最小改动"说的是别越界顺手改无关的，不是该改的也分批改**。当问题的修复面本身就跨多个文件（同一抽象要一起动、同一个契约要一起改），**一次改完整是更小风险的做法**——分批改会让中间每个版本都是不一致状态。
- 判据：**这个改动单独存在时，代码库是否处于自相矛盾 / 半迁移状态？** 是 → 它必须和同伴一起上，拆开才是真风险。
- 与「外科手术式」的分工：那条管**横向**（不要碰与本次请求无关的东西），本条管**纵向**（本次请求本身要求改到的范围，不要纵向削薄）。两条一起才完整：**不越界，也不欠改**。
- 反模式：为了"diff 好看"把一个跨文件的重命名拆成 5 次提交，中间 4 次都跑不起来；把接口与其全部调用点分开改，留下中间态。
## 不确定就问，别静默替用户选一种解释
来源：同上（Karpathy「Think Before Coding」）。
**模型最爱做的错事不是理解错，是理解有多种可能时悄悄挑一个往下跑。**
- 有歧义就**列出可能的解释并让用户选**，不要默默假设一个然后一路做完——做完才发现理解错，代价远大于问一句
- 拿不准的假设**显式写出来**（"我按 X 理解，如果不是告诉我"），让它可被纠正
- 自己有困惑就**停下来指名困惑点**；有更简单的路就直说，不要因为用户点了头就硬上
- 反例：同一段需求有两种合理读法，我选了难的那种写了 300 行 → 返工；选前问一句成本几乎为零
## 取舍清单：先说出按什么标准权衡
来源：The Batch issue-368（2026-08-28）软件工程基本功对 agentic coding 的作用。
**vibe 编码的失效点通常不是"写不出来"，是不知道该权衡什么 → agent 只能自己瞎选，选完你还看不出来选错了。**
动手前显式声明本次的优先级（选 1–2 个主目标，其余明确让位）：
| 维度 | 常见冲突 |
|---|---|
| 延迟 / 吞吐 | 快速响应 vs 批量处理 |
| 可用性 | 简单可靠 vs 高可用冗余 |
| 一致性 | 强一致（慢、简单）vs 最终一致（快、要处理冲突） |
| 可靠性 | 快糙猛 vs 容错、不崩、可恢复 |
| 可维护性 | 临时方案 vs 可读、可测、可改 |
| 简洁性 | 通用抽象 vs 直接实现（**默认站简洁**） |
| 成本 | 省算力/省 token vs 效果 |

不做的事：**不替用户默认全部都要**。冲突不可兼得时，说明"这次优先 X，代价是 Y"，而不是默默选一个。
## agent 架构：默认单一工具调用 agent，不追类型动物园
来源：n8n 在 v1.82 把多种 agent type 全部收敛为 **Tools Agent**（唯一的工具调用原语 + memory + tool 子节点）。信号：绝大多数场景不需要"反思型 / 规划型 / 多角色"等特化 agent 类型，一个能调工具 + 带记忆的 agent 就够了。
- **默认**：先上**一个**工具调用 agent（LLM + 记忆 + 需要的工具节点），把它跑通；只有当它稳定做不好某类子任务，才拆出专门的子 agent / 工作流（与「取舍清单」的"默认站简洁"同构）。
- **工具以子节点 / 子技能挂接**（可插拔），不把工具逻辑写死进主 agent 行为；记忆独立配置。
- **配工具时先分清"子 agent"还是"普通工具"**（来源：Make Help Center《Make AI Agent best practices》，2026-09-14 经代理补访，此前 403）：**这一步需要"自己的推理 + 自己的工具"才做成子 agent；其余一律用普通工具**（一次调用 / 一个模块 / 一个 MCP 工具）。**子 agent 要多花额度买它自己那份额外推理**——省下的编排复杂度是用推理成本换的，不划算就别拆。判定问一句：这一步是"想一下再决定调谁"吗？不是 → 普通工具。
#### 工具挂两档：固定操作的内建工具 vs 开放选择的 MCP 服务器

来源：n8n Docs《MCP servers》《Build and manage agents》（2026-09-14 实访 Markdown 原文）。

同一个外部能力，可以以两种形态挂给 agent，**选哪个取决于你知不知道它要用哪个动作**：

| | 内建工具（固定操作） | MCP 服务器（开放选择） |
|---|---|---|
| **用在哪** | 你明确知道 agent 需要哪个动作 | agent 需要一系列动作，或事先不知道用哪个 |
| **范围** | 一个操作（如"发一条 Slack 消息"） | 该服务器暴露的**全部**工具 |
| **你固定什么** | 任意参数（频道 / 类型 / 模板），只把需要模型填的字段留空 | 允许/排除哪些工具 |
| **模型决定什么** | 只填你留开的字段 | 调哪个工具 + 全部参数 |

- **开放度是拿控制力和上下文换的**：越开放，模型每次要读的工具定义越多、走偏的空间越大。**能固定就固定**——把一个常用动作固化成"只留两个字段"的工具，比丢一整个 MCP 服务器给它便宜也稳。
- **暴露范围默认用白名单**（只给需要的那几个），而不是"全部"或"除了这几个之外全部"。后两种叫黑名单，**新工具一上线就自动进了它的能力集**——你没授权过的东西被授权了。
- **路径校验要做两次：归一化之后一次，符号链接/最深祖先解析之后再一次**（来源：OpenClaw Docs《The trust boundary》，2026-09-15 经自启 VPN 实访）：只在上层做一次校验，是路径逃逸类漏洞的经典成因——**校验时看到的路径和实际打开的路径不是同一个**。判据：**校验完到使用之间，路径还会被解析吗？** 会 → 解析完必须再校验一次。
- **"显式要求的安全环境不存在"必须报错，不能静默降级**（同源：显式 `host=sandbox` 但未配置沙箱运行时 → **失败**，而不是悄悄在宿主机上跑）：**静默降级把一次配置错误变成一次安全事故**，而且当事人毫不知情。判据：用户明确指定了更严的环境，那环境不可用时的正解是**停下来告诉他**，不是退回到更松的环境。
- **变更通知有两个粒度，要分开声明**（来源：MCP 能力声明：`listChanged` 清单级 + `subscribe` 单项级，可各自独立开启）：**"清单变了"和"某一项的内容变了"是两件事**——前者要重新拉取目录，后者只需刷新那一条。只声明一个，对端要么漏更新，要么为一条变动去拉全量。
- **认证方式要匹配部署形态，别硬套**（来源：MCP 官方授权指南）：OAuth 那套浏览器跳转流程是**为远程 HTTP 服务设计的**；**跑在本机的东西不必套 OAuth**——它本来就在用户环境里，用环境凭据或第三方库自带的凭据机制更自然，也更少出错。**把为远程设计的方案套在本地上，会凭空多出一堆"为什么要跳浏览器"的复杂度。**
- **形态决定并发与生命周期，别选错**（来源：MCP 架构：本地 STDIO 服务通常只服务一个客户端，远程 HTTP 服务服务多个）：**本地/进程内的东西天然是 1:1**（一个实例对一个调用方），**远程/长连接的东西天然是 1:N**。按 1:1 写的组件被多个调用方同时使用，状态会互相踩；按 1:N 写的组件只有一个调用方，则白白付了并发成本。
- **一个外部服务一个专职通道，由统一层协调**（来源：MCP host/client 分离）：host 是用户看到的那一层，负责整体协调；**每个 client 只跟一个 server 说话**。好处是失败的 blast radius 被限制在一条连接内，权限也能逐连接授予和回收。**别做一个"万能连接器"同时对接所有服务**——它会同时成为权限黑洞和故障放大器。
- **先分清"这是动作还是数据"**（来源：MCP 三积木）：会改变外部状态的 = 动作（Tools），只读的 = 数据（Resources）。**动作面要窄（一个工具一件事）并配拒绝通道；数据面可以宽（常驻上下文）**。把数据当动作暴露会产生无谓风险，把动作当数据常驻会让人失去对副作用的感知。
- **agent 每轮的下一步只有四类**：调工具 / 检索知识 / 交给另一个 agent / 追问一句；循环直到产出最终响应。**把"追问"列为合法出口**很重要——不会追问的 agent 会用猜测填满不确定性。

#### 子 agent 嵌套限一层，且对外只暴露"名字 + 一句话描述"

来源：Make Help Center《Create your first AI agent》（2026-09-14 实访）。**agent 嵌套限一层**：父可以有子，**子不能再有孙**。

更要紧的是接口侧：**父 agent 只拿到子 agent 的`名字`和`描述`，看不到它的指令和工具**（平台是有意这么设计的，不是限制）。迁移到本地：

- **描述即契约**：子 agent / 子技能对外只暴露"它做什么、什么时候该用它"这两句；**它的内部指令、工具清单不要倒进父的上下文**——父会用"看起来更强"的方式去依赖子的内部实现，改子必炸父。
- 描述写不好 = 父根本不会调用它。**调用不上的根因常在描述，不在能力**（与 `wb-skill-authoring` 的触发词工程同源）。
- **层级上限是调试预算**：两层以上时，一个问题要穿过整条链才能定位，而每层都在消耗额外推理额度。
- 反模式：三层嵌套（父→子→孙）；把子的完整 system prompt 贴进父的提示词"让它调度得更准"；为了省事让父直接引用子的内部工具名。
- 反模式（架构级）：一上来就搭"主管 agent + 3 个专家 agent + 评审 agent"的复杂编排（过度设计，是 YAGNI 的反面）；为不存在的需求预设 agent 类型动物园；把一次性调用包成子 agent 只为"看起来像多智能体"。
## 拆子流程的抽取契约：单入口单出口 + 类型显式声明 + 上下文表达式逐个重验（来源 n8n《Convert to sub-workflows》2026-09-15 实访）
- n8n 对"把一段流程抽成可复用子流程"规定了硬性边界条件，逐条可迁移到"把一段代码/一段链路拆成子 agent 或子任务"：
  1. **单入口单出口**：抽取段对外只有一条入边、一条出边（多分支汇入/分出的节点不能当边界）——不满足就先理顺再抽，硬抽等于把耦合搬进接口。
  2. **触发器不进抽取段**：入口语义（何时启动）留在父层，子层只管"给什么就处理什么"。
  3. **输入输出类型必须显式声明**：默认"什么类型都收"是隐患——不声明类型，调用方传错要等运行时才炸。
  4. **上下文相关表达式不平移**：`first()` / `last()` / `all()` / `itemMatching(i)` 这类"依赖在父上下文里的位置"的引用，抽出去后语义会悄悄变（n8n 的做法是加 `_firstItem` 等后缀保留原信息 + 要求人工重验）——**拆分清单里必须有一项：逐个列出依赖外部上下文的引用，逐个重验**。
- 判据：抽出去的部分如果"离开父上下文就无法自解释"，说明还没到可抽取的边界，先补显式接口再拆。
## 验证阶梯（写完代码后，与决策阶梯配套）
验证强度匹配任务风险，不做一刀切：
1. 先跑廉价信号：编译 / 冒烟 / lint / 单测，能自动化就自动化，让结果可自查
2. 设定"够用"的判定阈值：什么算通过、什么必须停下修（阈值先想清楚，别边跑边改）
3. 廉价信号越过阈值才升级到重型验证：人工走查、LLM-as-judge、安全/架构审计、端到端流程验证
4. 危险操作（删除、覆盖、外发、权限变更）不论任务大小，一律过人工确认，不进自动化
## 约束
- 不写投机性抽象、样板代码、留待未来的脚手架；删除优于添加；最短可用 diff 优先
- 复杂需求：给最简版本，并说明"做了什么、覆盖了什么、需要完整版就说"
- 绝不偷懒砍：输入校验、防数据丢失的错误处理、安全措施、无障碍基础、用户明确要求的内容
- 先完整理解问题（读相关代码、追调用链），再决定偷懒——理解环节不能省
- 非代码任务按内容完整度交付，不套用"少写代码"
## 引依赖：先榨干已有的，再 vet、pin、记退出条件（来源：riekelt/principal-engineer·adding-dependencies，2026-09-15 实拉）

> 判重留痕：与「外科手术式」（管不顺手改）、「有界≠最小」（管该改不削薄）、「状态建模三律」（管数据建模）均不重叠——本条管"要不要把一个包领进树"。上游整包 11 个 skill 与本地重叠 >60%，不装，只取本条。

**依赖是一次招聘，不是一段代码**：招进来的是它的缺陷、发布节奏、传递树和维护者的精力。

### 七级阶梯（逐级往下，停在最先够用的层级）
1. **需求本身**——投机需求不是需求，一句话说清并跳过
2. **本代码库**——几个文件外已有 helper / 类型 / 模式就复用；仓库已有东西的第二份拷贝是缺陷
3. **标准库**——装包前先读它的索引，看是否已覆盖
4. **平台**——数据库约束优于应用代码、原生控件优于 widget 库、运行时原语优于包装层
5. **项目已带的依赖**——它的传递树已经付过钱了。**两条边界**：①你开始直接 import 的传递依赖 = 新直接依赖，要显式声明并 pin 到已解析版本；②dev 工具的传递依赖被提升进 runtime，成本转移到每个消费者的安装
6. **自己写二十行**——二十行真的够时，拥有自己的二十行胜过拥有别人的仓库
7. **过了六级才引新的**——按下面 vet

### vet 招进来的人
- **算整笔账**：传递树、安装/构建重量、许可证冲突、安全历史
- **摸脉搏**：最近发布、issue 响应、可合并人数——承载关键路径的包只有一个耗尽的维护者，是你主动选的风险
- **读你要调用的那部分**：API 面和失败模式，不是 README 的承诺
- **要只做一件事的工具**，不要四十个功能的框架——另外三十九个照样跟着来（重量 + 攻击面）
- **记录决策**：用途、权衡过什么、**它在什么条件下离开**（退出条件）

### 姿态、pin 与删除
- **依赖姿态是项目要声明的**（全自禁 / 白名单 / 审后加）；没人能回答时按"声明的假设姿态"走并记下假设 + owner，不是默默放行
- commit lockfile、pin 版本；CI 或基础镜像里的裸 `latest` = 别人调时的定时炸弹；大版本升级单独一个 commit（blame 可读），patch 可打包
- **依赖的用途消失时，依赖在同一变更里一起走**；"留着以防万一"= 第 1 级投机需求的反向版；只剩一个小调用点时考虑改为拥有那几行
- 常见反射病：树不是被大决策养大的，是一次一个"小而合理"的包喂大的——**为绕开读现有代码而装包 = 跳过了第 2 级**
## 依赖的调用面：只用公开入口，弃用路径只在声明的兼容窗口内存活（来源：OpenClaw 官方 docs.openclaw.ai·plugin-validation-fixes / agent-runtime-architecture，2026-09-15 实拉）

> 判重留痕：§引依赖 管"**要不要把一个包领进树**"（选型与全生命周期）；本条管"**已经在树里之后，从哪个门进去、旧门留多久**"。与 §135「描述即契约」（子 agent 之间）不同层：那条管 agent/技能边界，本条管**代码 import 边界**。

- **只从公开入口进，不 import 内部路径**：用文档化的公开子路径（`pkg/public-x`），**不 import 包的内部目录**（`src/**`）。内部路径没有兼容承诺，一次小版本就能把你的构建打断——**"能跑"不等于"被支持"**。
- **两种被禁的入口**要能识别：①**已弃用的根 barrel**（全量导出的大入口，体积与耦合都最大），换成窄的公开子路径；②**保留给内置/内部兼容的路径**——不是给你用的，即使现在 import 得到。
- **行为没有公开 API 时，两个正当出路**：把那段 helper **留在自己的包里**，或者**去上游申请公开 API**。**不要靠内部路径"先用着"**——那是把未声明的依赖伪装成正常引用。
- **弃用路径只在显式声明的兼容范围内存活**：保留旧 helper / 旧钩子的**唯一合法理由**是"我声明的兼容范围仍要支持老版本"，且必须**同时**写清（a）兼容范围到哪结束（b）替代入口是什么（c）退出条件。**没有这三个的"暂时留着"就是永久留着**（与 §捷径债务台账 同一纪律）。
- **兼容范围与你自己的版本号是两件事**，分别声明：一个说"我这个包发布到哪一版"，一个说"我依赖的上游契约范围"。写混会让升级决策无法判断该动哪个。
- **元数据声明与实际行为必须一致**：声明了要用某环境变量/某二进制，就必须真用；真用了就必须声明。不一致会被静态校验标为缺陷（"声明漏了"和"引用了没声明的"是同一枚硬币）。**声明不是装饰，是可被机械核对的契约**（与 §约束 段同源）。
- **不要用尚未定义契约的声明式文件假装安全**：上游还没有发布版本化 schema 时，**删掉那个自制清单文件**，把安全敏感行为写进公开文档，而不是先造一份没人校验的 JSON 看着像治理。**契约不存在时的"声明"只是仪式**。
## 收益数字必须有可减的真实基线：没写出来的那个版本不是基线（来源：dietrichgebert/ponytail·`ponytail-gain`，2026-09-16 实拉）

> 判重留痕（sa 双键检索）：`dietrichgebert/ponytail` 这个仓库名在本库已命中——`ponytail-debt` 于 2026-09-15 落地为下节 §捷径债务台账。本条取自**同仓库的另一个子技能 `ponytail-gain`**，判据不同（那条管"偷的懒记没记"，本条管"收益怎么报"），按相邻扩展落地，不重写既有条目。

- **"省了多少"是差额，差额要有两个真实端点**。原文硬边界：`NEVER print a per-repo savings number`——被省掉的那个版本**从来没被写出来**，它不构成基线，减不出数字。**"没做的实现"不是对照组，是反事实**。
- 能报的三类数字，各自带口径：① **基准中位数**——必须同时写"这是基准上测的，不是本项目"；② **计数台账**——来自真实 grep / 真实提交（下节债务台账的 N 条标记属此类）；③ **两侧都真跑过的对照组差值**。
- 禁止的写法：把基准或估算说成"你这次省了 X 行 / X token / X 元"；用"本来要写 N 行"的反事实当分母。
- 判据：**问一句"这个差额的另一端，是哪一次真实运行？"答不出来就不许报**——宁可写"没有基线，不给数"。
- 与 `wb-skill-authoring` §效果归因（no-skill 对照组）的分工：**那条管"要不要设对照才能说技能有用"**；本条管**没设对照时数字能不能报**——不能，且必须标明口径。与 `wb-artifact-verification` §声明边界写在数字旁边 是同一纪律的两种场景。
## 被要求绕开规则时：报一次、不纠缠、把例外写成文档（来源：openai/skills `security-best-practices` SKILL.md，2026-09-15 实拉）
项目文档或用户的明确要求可能与通用最佳实践冲突。处理顺序固定：
1. **说明一次**（这条实践是什么、绕开它意味着什么）→ 2. **不争论**（说第二遍就不是告知，是施压）→ 3. **照做** → 4. **把这次例外连同原因写进项目文档**，后续照此一致执行。
- 判据：**例外不落文档，就会在下次被当成"上次怎么没做"重新吵一遍**；落了文档，它就从"某次妥协"变成"已声明的决策"。
- 与 AGENTS.md 0.9（用户指令优先）分工：那条决定**听谁的**，这条决定**留下了什么**。
## 抽象不出来说"抽不出来"之前，先把例外变成数据；形状相似 ≠ 主体相同（来源：GitHub `edonadei/caliper`·`docs/adr/0020-a-backend-declares-its-chores-rather-than-performing-them.md`，2026-09-17 实拉）

- **"我这个情况特殊"不是保留私有副本的理由**：四个后端各自手写了同样的三件杂活（播种隔离 home / 定位 CLI 二进制 / 组装环境）。**它们之所以重复了那么久，是因为每个后端都有一个例外，而例外看起来像是保留自己那份的正当理由** —— 结果逐个检查下来，**每一个例外都能表达成数据**：`seed_files` 给一份 `(real, isolated)` 清单、`cli_name` + `cli_path_env_var` + `cli_candidates()` 给名字和候选路径、`env_passthrough` 给要透传的变量。
  - 判据：准备说"这个抽象做不了，因为我们情况特殊"之前，先问**"我的特殊之处能不能写成一行配置/一张表"**。能写成数据就别留副本 —— 基类做动作，各家只提供**那一个不同的事实**。
- **三份里的两份近似，不构成共享实现**：用户会在失败那一刻读到三句提示，它们共享"形状"但不共享"主体"（一句讲 API 计费且不命名环境变量，另两句命名安装命令与 `*_CLI_PATH`）。套模板会把这段散文压平，原文说这是 `the wrong thing to economize`。
  - 判据：**面向人读的失败文案不为省代码而模板化**。抽象看的是主体是否同一个，不是文字是否像 —— 两条近似不算共享实现。
- **顺序是契约的一部分，要写明，不能留给发现**：`_seed_home` 必须跑在 `_prepare` 之前，因为要重写配置的后端必须看到已经就位的逐字副本；**反过来看不出错，只会静默破坏两处**。
  - 判据：抽出模板方法之后，**步骤顺序要显式写进流程与文档**。抽得越干净，顺序越容易被后人调换，而调换是不报错的。
- **改了默认行为就记下来**：统一后 claude-code 从只透传 `TMPDIR`（还只在 macOS）变成和大家一样透传 `LANG`/`LC_ALL`/`TERM`/`TMPDIR`。原文给的理由是"一个后端和它的兄弟们不同、却没有任何记录的原因，正是这篇记录要反对的东西"。→ 统一带来的行为变化要**逐条写出来并说明理由**，否则下次排查时它会变成"看起来一直是这样的"。
## 工具粒度按工作流切、不按端点切；工具返回只回高信号（来源：Anthropic《Writing effective tools for agents — with agents》2026-09-18 实拉）
- **不要按后端端点 1:1 包工具**：最常见的一类错误就是"这个 API 有，就给它包一个工具"，**不管这个形状 agent 用起来顺不顺手**。原因是 agent 的"可供性"和传统软件不同——计算机内存便宜，可以一条条扫；**agent 的上下文有限，让它读全量再逐 token 过一遍，是在烧它最贵的资源**（原文地址簿例子：`list_contacts` 让 agent 从头翻到尾，正解是 `search_contacts`）。
  - 判据：**问一句"这两个动作之间的中间结果，还要不要回灌上下文"。** 要 → 它们该合成一个工具；不要 → 才值得分开。
  - 三个合并样板：`list_users` + `list_events` + `create_event` → `schedule_event`；`read_logs` → `search_logs`（只回相关行 + 少量上下文）；`get_customer_by_id` + `list_transactions` + `list_notes` → `get_customer_context`。
- **"一个工具一件事"不等于"一个工具一个端点"**：原文同时要求每个工具有"清晰、独立的目的"，两条不冲突——**目的按"人拿到同样这些资源会怎么分解这个任务"来定**，不是按后端有哪些接口。工具重叠或过多会**把 agent 从高效策略上引开**，这是纯损失，不是"多给点选择没坏处"。
- **返回字段：高信号优先于灵活**：`uuid` / `256px_image_url` / `mime_type` 这类低层技术标识，不如 `name` / `image_url` / `file_type` 能直接驱动下一步动作；**把任意 UUID 解析成语义名（哪怕退化成 0-indexed ID）能显著降低检索类任务的幻觉**。
  - 但别顺手砍掉下游要用的 ID：给 `response_format: concise|detailed` 之类的枚举让调用方自选（concise 约 1/3 token，但缺了 `thread_ts` 就再也拿不到回复）。判据：**省掉的那一档必须能明确说出"省掉的是哪个能力"**，说不出就是在静默削功能。
- **错误响应和截断也是指令**：校验失败时回"具体该怎么改"，而不是错误码 / 堆栈；截断时顺带引导"改多次小而定向的检索，别一次大而宽的检索"。→ **工具的错误通道是它能改 agent 行为的最便宜的地方**，别浪费在 traceback 上。
- 与既有条目的分工：§内建工具 vs MCP 开放度 管**给不给它选择权**；本条管**决定给之后，每个工具长什么样**。§接口最小化 管**露多少**；本条管**按什么切、返回什么**。
## 工具契约有两条：schema 管"什么合法"，示例管"怎么用"（来源：Anthropic《Advanced tool use》·Tool Use Examples 章，2026-09-18 实拉）
JSON Schema 只表达**结构合法性**（类型、必填、枚举），表达不了**用法惯例**。写一个工具/接口时，先问："合法的输入是否仍然可能用错？" 是 → 必须补示例，因为那一类信息 schema 天然装不下：

- **格式约定**：`due_date` 是 `2024-11-06` 还是 `Nov 6, 2024` 还是带时区的完整时间戳——schema 全是 `string`。
- **ID 约定**：`reporter.id` 是 UUID、`USR-12345` 还是裸数字——schema 全是 `string`。
- **嵌套结构何时填**：`reporter.contact` 什么时候该给、什么时候该省。
- **可选参数之间的相关性**：critical 工单 = 完整 contact + escalation + 紧 SLA；feature request = 只有 reporter；内部任务 = 只有一个 title。**这是"带不带"的模式，不是"对不对"的校验**，validators 同样表达不了（与 ed §业务规则放 validators 不放 schema 互补：那条讲"对错"归谁，本条讲"惯例"归谁）。
- 判据：**"合法 JSON ≠ 正确用法"** 是补示例的唯一理由；简单单参工具、URL/email 这类模型已经懂的标准格式、能用 schema 约束解决的，都不要加——示例是有 token 成本的。
- **示例要按复杂度递减给三条**，不是给三条一样全的：最全的一条教"格式 + 嵌套 + 参数相关性"，中间一条教"哪些可以省"，最简一条教"最小调用长什么样"。三条全量示例只教了一种形态。
- **相似命名的工具靠示例区分该用哪个**（`create_ticket` vs `create_incident`、`notification-send-user` vs `notification-send-channel`）——名字相近是选错工具的主要来源，光靠描述改字眼不如一条示例直接。
- 分工：与 §错误响应与截断也是指令 互补——那条管**返回侧**也是契约，本条管**入参侧**的第二条契约通道。
## 元提示与防锚定排序：prompt 编译器 / 承诺步骤放最后 / 显式禁止跳步（来源：arXiv《Meta-Prompting Protocol》2512.15053 2026-08-24 + AI Engineer Lab《Meta Prompts》2026-09-08 + RockB《Advanced Prompt Techniques 2026》2026-04-15 + PromptCraft《Meta-Prompting》2026-06-23 + eWeek《Cheat Sheet》2026-04-23 实拉，与 §工程化指令互补——那条管「提示词结构」，本条管「谁写提示词+步骤怎么排序」）
- **meta-prompting（prompt 编译器）**：用高能力推理模型编写/迭代生产系统提示词，部署到更小更快模型（如 GPT-5.4 写、mini/Haiku 跑）——**把推理花在写提示词上，运行成本落在小模型**。
- **防锚定排序（最高价值结构规则）**：**承诺答案的步骤必须放最后**——「先收集约束再提方案、先评估备选再选择」；步骤 2 推荐方案、步骤 3 列约束 → 模型会先锚定推荐再挑约束来合理化。
- **显式禁止跳步**：加「Do not skip or combine steps / 不要跳过或合并步骤」——跳过=自己选了步骤，约束名存实亡。
- **对抗三元组**：Generator-Auditor-Optimizer（生成-审计-优化）自优化回路，把文本批评当梯度迭代提示词——**适合高频复用的生产提示词，值得多轮打磨**。
- **context engineering 视角**：prompt 只是多层上下文栈的一层（system 身份/动态检索文档/相关历史/工具定义/结构化示例）——**先设计上下文架构，再写 prompt 文本**。
- 反模式：让模型先给结论再补理由（锚定）；一条 prompt 里塞 5 个任务又不准它排序（跳过）。
## 开关的三种状态：没设过 / 设成关 / 设成开，必须存成三个不同的值（来源：docs.openclaw.ai `concepts/usage-tracking`·Three distinct session states，2026-09-18 实拉）

与 §声明即契约 / §兼容范围与版本号分开 分工：**那两条管"声明出去的契约长什么样"，本条管"一个可覆盖的开关该怎么存、默认值与用户意图谁赢"**。

- **"没设过"和"设成关"不是一回事，却最常被存成同一个值**：`unset`（缺席 → 落到配置默认值）与 `off`（显式关闭 → 字面值 `"off"` 存下来）必须可区分。判据：**一旦把"用户明确关掉"存成"没设过"，任何非 off 的配置默认值都会把它静默重新打开**——用户以为关了，其实只是没人替他记着。这是"改了配置，用户设置就失效"这类幽灵 bug 的标准成因。
- **显式关闭要能压过默认值**：优先级固定为 `会话显式值 → 环境/渠道配置 → 默认值 → 关`，显式 `off` 之后**非 off 的默认值不得重新启用它**。判据：**默认值的职责是"用户没表态时怎么办"，不是"覆盖用户已经表过的态"**；把它写成"默认值优先"等于让配置文件的作者替每个使用者做决定。
- **"关掉"和"重置"是两个不同的动作，别合成一个按钮**：`off` 是把值**钉死**在关（并持久化，跨会话重置仍保留）；`reset`（/ inherit / clear / unpin）是**清掉覆盖、回到继承**。判据：**合成一个动作之后，用户就没有任何办法表达"我现在不要，但你以后改默认值我认"**——而这恰恰是最常见的真实意图。
- **轮转式开关要从"当前生效值"起步**：循环切换（关 → 简 → 全 → 关）的起点必须取**当前实际生效的模式**（会话值缺失时先落到配置默认），否则"按一下"的结果和用户屏幕上看到的不一致。判据：**开关的下一个状态相对用户此刻所见计算**，不是相对内部存储的那个字段。
- 与 `wb-context-compressor` §条件注入的失败方向 的边界：那条管"谓词失效时往哪边倒"（安全方向），本条管"用户/配置的覆盖关系怎么存"（谁说话算数）。
## 先问"有没有一层免费的复用托底"，再决定要不要为省而加复杂度（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/caching.md` 实测数字，2026-09-18 实拉）

与 §YAGNI 决策阶梯 分工：**那条按"是不是真需要"取舍，本条补一条可量化的兜底判据**——存在一层自动复用机制时，"更浪费但更简单"的实现可能只贵 17%，这时复杂度不值得加。

- **同一任务的三种装配方式实测**（10 技能 / 18 工具 agent，live API）：不做任何门控、18 个原始工具 schema 直给 = 40,563；**智能门控**（按需绑定、每轮重算）= 28,404，开复用后降到 6,535（−77%）；**塞满再靠复用扛**（10 份技能正文常驻）= 约 140,000，开复用后 7,640（−95%）。
- **没有复用层时，"省"是唯一经济解，复杂度必须加**：此时裸给比门控多付 43%，不门控就是纯浪费。
- **有复用层时两者都成立，简单实现只贵 17%**：7,640 vs 6,535。判据：**先看有没有托底，再谈要不要优化**——把"没托底时的必要性"当成"有托底时的最佳实践"，是过度设计最常见的来源之一；此时该按团队偏好（代码更简单 vs 每轮更省）选，不必默认"越省越好"。
- **代价是搬了家，不是消失了**：塞满方案的首轮要付一次写入成本（延迟更差），之后才便宜。判据：**冷启动变贵、稳态变便宜的优化，要按"这个任务会跑几轮"来算账**——只跑一两轮的场景，塞满方案是净亏；与 §别为一两次调用上基础设施 同向，本条给了具体算账口径。
## 库里有 ≠ 能用：选择存在容量上限时，"落选"不是"不合格"（来源：OpenClaw `docs.openclaw.ai/tools/skills`「Revisions and session selection」2026-09-20 实拉，与 §清点资产按"真的用上了"计 互补——那条管"做取舍时分子用哪个计数"，本条管"**分子的上限在哪里**"）
- 实测：新会话最多选中 **64** 个已启用库技能，顺序为 personal 优先、组内按稳定 ID 排序；库超过上限时由用户拆掉一个再挂另一个；且启用不绕过 agent allowlists、必需二进制、操作系统限制等前置条件；托管包另有 256 文件 / 单文件 1 MiB / 合计 8 MiB 的硬上限。
- 判据：**"我有多少能力"要按上限之后的数量算，不是按库里的数量算**；库里 200 个、会话里只进得去 64 个时，多出来的 136 个不是"冗余资产"而是"本轮用不上的资产"，按库容量做的删留取舍会砍错对象。
- **落选与不合格必须分开报**：超限落选由排序规则（personal 优先 + 稳定 ID 序）决定，与质量无关；把"没进会话"读成"被判不合格"，是把一条排序事实误当成一次质量裁决（与 §过滤来源等于过滤答案 同族：被过滤掉的原因必须能被说清是哪一种）。
- **容量上限要写成数字而不是形容词**：知道"最多 64"才能回答"再装一个会不会挤掉谁、挤掉的是谁"；只有"别装太多"这种表述，等于把取舍交给运气。
- **提升层**：工作流（资产取舍 / 容量预算）+ 工具（装配上限）。
## 互斥 / 不兼容的能力必须显式取舍，不让一条静默关掉另一条（来源：topaiskills.com `azure-aigateway-procedural`（2026-09-17）2026-09-20 实读，与 §按产物存活期选型 / §库里有≠能用 互补——那两条管"一次性基础设施从哪来 / 分子上限在哪"，本条管"**两个都要但互相打架时怎么选**"）

## 删除键归人，改名是全仓操作：能过测试能过编译 ≠ 没人在用（来源：topaiskills.com「ai-agent-refactoring-experience」（Vercel `vercel-react-best-practices` + `improve-codebase-architecture` 双 agent 实测复盘）2026-09-21 独立重拉实读，与 §按产物存活期选型、§一次只改一处 互补——那两条管"选什么资源"与"一次动多少"，本条管"**删除与改名这两类特殊动作由谁按下**"）

- **原文事实**：一次真实事故——agent 用静态分析判定五个工具函数是"死代码"并删掉，**测试仍过、编译仍过、一切看起来正常**；实际上其中两个是被**动态调用**（一个 agent 无法静态追踪的遗留模块里的 eval 式调用）用的，**生产上静默影响了约 5% 的用户**，最后是靠错误监控的尖峰发现的。作者的结论写成了规则：**"Do not let agents delete code. Flag it, mark it in a review, but make a human hit delete."** 同一个实验里的第二处：agent 依据"React 惯例事件处理器用 `on` 前缀"把 `handleRowClick` 全局改名为 `onRowClick`，**但这个标识同时也是下游组件的 prop 名**，改名没有传播到所有引用处，**三个组件静默坏掉，而 TypeScript 抓不到运行时的这处不匹配**。作者给的修法只有一条：**every rename needs a full grep check**。另有一条作用域结论：**窄作用域（"只重构这个目录" / "只动 hooks"）产出明显更好**，让 agent 自由漫游是那次事故的前提之一。
- **判据**：
  1. **静态分析能证明"没找到调用者"，证明不了"没有调用者"**。判据：**删除的举证责任在删除方，而静态可达性不构成举证**；凡是"能过测试、能过编译"就当作没人用的删除，都是把不可证当成已证（与 §重来不是解法 同向：那条管冲突里的信息代价，本条管**删除这个不可逆动作的信息代价**）。
  2. **agent 只标记，人来按删除键**。判据：**删除要作为一条待确认项进入评审，不由执行方直接落地**；这不是保守，是因为撤销一次删除的成本与写出它时不对称。
  3. **改名不是文件内编辑，是全仓一致性操作**。判据：**任何按"惯例/风格"发起的改名，落地前必须全量搜索该标识的每一种身份（本地名 / 导出名 / prop 名 / 配置键 / 字符串引用），并逐个确认已传播**；类型系统只覆盖它能看见的边界，跨边界的那部分不匹配会静默跑到运行时。
  4. **给 agent 的自由度按作用域收，不按信任度收**。判据：**与其判断"这个 agent 可不可信"，不如把范围写窄**——窄作用域同时降低爆炸半径和评审成本。
- 提升层级：工作流（不可逆动作的归属）+ 工具（改名/删除的前置检查）。
- 触发词：删除键归人、make a human hit delete、死代码误删、动态调用、静态可达性不是举证、every rename needs a full grep、全量 grep、改名是全仓操作、prop 名不匹配、窄作用域、自由漫游。

## 测试投入按"这段代码碰什么"分档，不按信仰；方法要写明自己的失效条件（来源：topaiskills《I Tried TDD With an AI Assistant and It Caught a Bug》2026-05-31，2026-09-21 r125-A 独立实拉，此前未读）

- **原文事实**：作者的取舍判据是"碰什么"而不是"重不重要"——"I use this approach for anything that touches money, permissions, or external APIs. ## 自动化的准入三条件里"可预测"是硬门槛；选平台把"出错时能不能看清内部"当一等指标（来源：topaiskills《How to Build Your First AI Automation Workflow》2026-07-23，2026-09-21 r125-B 独立重拉实读，此前未读）

- **原文事实**：① 作者给的准入判据叫 One-Task Rule，三条同时成立才值得自动化：**Repetitive**（每周至少做两次）、**Predictable**（每一轮都是同样的输入、同样的流程、同样的输出格式）、**Boring**（人做会走神的事）。原文对最常见的失败形态的判断是 "The single biggest mistake is trying to automate everything at once"——一次碰五个系统、三个条件分支、每种失败各自处理的，会耗掉几周去建和调。② 平台三档（AI agent / 低代码 n8n-Make / 自定义代码）的对照表里，作者额外点出一条不在规格行里的代价："Low-code builders are great for business users, but **the abstraction can make debugging harder when something goes wrong**."同一张表把 Monitoring 单列一行（内置终端输出 / 可视化执行日志 / 自建）。

## 先判"这次是找答案还是找选项"，再选检索/研究工具（来源：topaiskills《I Replaced Google with an AI Search Agent for a Week》2026-08-01，2026-09-21 r125-C 独立重拉实读，此前未读）

- **原文事实**：作者七天实验的对照表里，除了"答题速度/质量/成本"这些意料之中的行，还有两行给出了反向结论——**Serendipity / discovery：Google High、AI 搜索代理 Low**；**Learning the material：Google High、AI 搜索代理 Low**。原文结论："a pure AI-search workflow is **great for answers and terrible for discovery**. When I knew what I was looking for — an SDK method, a pricing detail, a config flag — the agent was strictly better. ## 重来不是解法：冲突回溯一手来源的意图，不自创第三个版本，验收按结构→行为→噪声（来源：topaiskills.com「resolving-merge-conflicts-procedural」（Matt Pocock `resolving-merge-conflicts`，347.8K installs）2026-09-21 实拉）

- **原文事实**：技能的教义是一句话——**resolve 每一个 hunk，永不 `--abort`，保留双方意图**，且"这段代码太难解 / 分支差太远"**没有例外条款**。理由：`--abort` 丢掉的不只是 merge state，还有**已解决的 hunk、已经做过的决定、以及你为什么开始这次合并**；"合并状态是一次工作会话，放弃它等于把问题归零，下一次从同样的无知开始"。流程：① `git status` + `git log --oneline` 一起读，先知道有几个 hunk ② **为每个冲突找回一手来源**（commit message / PR / 原始 issue），因为 "diff 只给你两个版本，只有一手来源告诉你产生它们的意图" ③ 逐 hunk 解，**尽可能保留双方意图**，真不兼容时挑符合合并目标的一侧并**把取舍写进解决结果**；两条硬禁令：**不发明新行为**、**绝不 abort** ④ 跑项目自带检查，**顺序固定：typecheck → tests → format**（分别抓结构损伤 / 行为损伤 / 噪声）。
- **判据（可迁移，不限于 git）**：
  - **把"重来 / 重置 / 弃权"当逃生舱，是最贵的一种省事**：它同时销毁已完成的部分、已做出的决定与动机。判据：**遇到卡点先问"还差什么信息"，只有在信息已经不可能拿到时才允许归零**，且归零前必须把已有结论留痕（与 §"关掉"和"重置"是两个动作 同向：那条管开关语义，本条管**放弃动作的信息代价**）。
  - **只解表面文本不解意图 = 偷工减料**：两个方案冲突时，区别不在字符在那两行背后的目的。判据：**每解一处冲突都要能说出"这两边各自想达成什么"**；说不出就是还没查够，不是可以随便挑一边。
  - **两边都不对时，这是要上报的发现，不是写第三个版本的许可**。判据：**"我来提一个更好的方案"在冲突现场默认是越权**——没人要求过这个版本，它还会把两边的意图一起埋掉。
  - **验收顺序有方向：结构 → 行为 → 噪声**。判据：**先 typecheck 再 tests 再 format**，反过来会把格式问题当成功能问题查，也会让结构性损伤藏在测试红里分不清。
- 提升层级：工作流（冲突处理与验收顺序）+ 决策（放弃的代价）。
触发词：重来不是解法、abort 禁令、一手来源、双方意图、不发明新行为、验收顺序、typecheck 先行、结构性决策才确认。
## 判断「要不要加」之前先分清能力与补偿：别为一个会消失的短板加永久结构（来源：MCP 官方 `modelcontextprotocol.io/community/design-principles` 设计原则八条，2026-09-22 r129-A 独立实拉，新信源首读）

- **原文事实（八条原则，全库零命中）**：
  1. **Capability over compensation**：*"Models improve faster than protocols evolve. We avoid adding permanent structure to work around limitations that are likely temporary — the limitation fades, but the complexity remains."* 但并非无视现状：*"Optional context that weaker models lean on and stronger ones ignore costs nothing."*
  2. **Stability over velocity**：*"Adding to a protocol as widely adopted as MCP is easy. Removing from it is nearly impossible. Every addition is a permanent commitment and a cost for client implementers to support... 'no' today leaves the door open while 'yes' closes it forever."*
  3. **Convergence over choice**：*"There should be one way to solve a problem... Rather than supporting multiple approaches that fragment the ecosystem, we choose a single well-designed path."*
  4. **Composability over specificity**：*"We don't add protocol features for use cases that can be constructed from these existing building blocks."*
  5. **Demonstration over deliberation + Interoperability over optimization**：跑得起来的实现压过理论论证；特性要能优雅降级，能力靠显式协商而不是假设对手一样强。
- **判据（可迁移，落在「先判再加」的决策阶梯上）**：
  - **先问「这个限制会消失吗」**：要加的东西如果主要在补一个**很可能临时**的短板（当前模型不够强、当前工具缺个字段），默认不加——限制消失那天，复杂度留下来。**唯一例外**：做成"弱者能靠、强者能忽略"的**可选上下文**（零成本），而不是把它变成结构的一部分。
  - **加法与减法的代价不对称，所以默认答案偏向不加**：加一项 = 永久承诺 + 每个下游都要为它付实现与维护成本；"今天说不"只是留着门，"说是"就是把门永久焊死。判据：**评估「加这个」时把「将来能不能拆掉」当一等属性写进取舍清单**，拆不掉的就得按永久负债计价。
  - **「两种写法都支持」不是兼容，是把选择成本转嫁给每一个后来者**：多方案并存即生态分裂。判据：**同一问题只留一条官方路径；试验性的放"扩展区"，收敛了的才进"标准区"**——先证明再收编，别同时发两个正式答案。
  - **能用现有原语拼出来的，不新增特性**：判据：**提新能力之前先回答"用已有三件套能不能拼出来"**；能拼就写清拼法，拼不出来才谈新增。每加一个原语，后面的组合空间就要重新算一遍。
  - **有可跑实现压过理论论证**：判据：**争不下来的设计争议，交一个能跑的最小实现来裁决**，别继续在文档里辩论。
- 提升层级：决策（加与不加的判断）+ 工作流（取舍清单里新增"可撤销性"这一列）。
- 触发词：能力与补偿、补偿性设计、永久结构、临时短板、限制会消失、加法不可逆、可撤销性、一条路径、收敛优于选择、组合优于特化、跑得起来压过理论。
## 给模型用的工具，参数边界由宿主夹紧：不接受模型可构造的昂贵模式，元工具要自豁免（来源：Pydantic AI 官方 `pydantic.dev/docs/ai/harness/tool-output-limits`（`Spill` / `read_tool_result` 设计，引 pydantic-ai issue #4352），2026-09-22 r129-B 独立重拉实读，新信源首读）

- **原文事实**：大工具返回会常驻历史、之后每次请求都重发，所以 `ToolOutputLimits` 在**返回产生的那一刻**减容一次并把减容后的形态持久化——*"This capability intercepts a return when it is produced, reduces it once, and lets the reduced form persist -- the reduction is not recomputed per request."* 无损档 `Spill` 落盘后，模型通过注册的 `read_tool_result(handle, offset, limit, from_end, pattern)` 回读，而该工具是**有界的**：*`offset >= 0`*、*`limit` clamped to a built-in line cap*、*the joined output capped*、且 *`pattern` is a literal substring (not a regex), so a model-supplied value cannot hang the host with catastrophic backtracking*。另外 *"Its own returns are exempt from reduction."*
- **判据**：
  - **凡是让模型传"模式/表达式"的接口，先问最坏情况下它能不能把宿主打死**：正则、glob、深度递归、无界 limit 这类参数一旦由模型自由构造，灾难性回溯 / 全量扫盘就成了"一次普通调用"的形状。判据：**对外暴露的检索类工具，模式类参数默认收成字面量；数值类参数由宿主 clamp，不靠模型自觉**。与 §工具契约有两条（schema 管合法、示例管用法）分工：那条管**模型怎么理解这个工具**，本条管**宿主怎么防这个工具被用成武器**。
  - **元工具必须显式豁免于它自己参与的治理规则**：回读工具的返回不再过减容，否则治理会作用在治理工具本身上，形成自指循环。判据：**写"对所有输出统一施加 X"这类规则时，先列出"哪些输出是 X 机制自己产生的"并把它们排除**，漏掉这一条的表现是自引用递归而不是报错。
  - **减容只做一次，减完的形态才落历史**：减容若每次请求重算，成本随轮数线性增长且结果可能逐轮漂移。判据：**上下文里的内容按"还会被重发多少次"计价，不按"这一次多大"计价**；处理时机选在**产生时**而不是**每次发送前**。
- **重型 agent 框架 / workflow boilerplate 会随模型变强成技术债**（来源 Strands Agents "one year of production agents"）：最小架构（system prompt + model + tools）先解决 80%，再按需加 scaffolding；模型能力提升后，为已不成立的难处过度铺垫的框架最先过时。判据：**先最小架构跑通，框架 / 状态机只在最小架构真不够时才加**。
- 提升层级：工作流（架构选型判据）。

## 并行不是模型自己悟出来的：接口要拆成多个具体调用，描述里要写明"可并行"（来源：Google ADK 官方 `adk.dev/tools-custom/performance`，2026-09-22 r140-A 独立重拉首读，新信源首读）
- **原文事实**：官方专节 "Write parallel-ready prompts and tool descriptions"，要求提示里明示并行并给示例：*"When users ask for multiple pieces of information, always call functions in parallel... 'Compare cities A and B' → Call get_weather, get_population, get_distance in parallel"*，并给工具描述加一句 *"This function is optimized for parallel execution - call multiple times for different cities."*，附一条通吃规则 *"Always prefer multiple specific function calls over single complex calls."*
- **判据**：
  - **串行常常是接口形状造成的，不是模型笨**：把多个查询塞进一个 `cities: list` 参数，模型只能一次调用、内部循环。判据：**一次调用能不能只做一件事**——能拆成 N 个具体调用就别合成一个"批量调用"，后者既不能并行也不能只对失败的那一个重试。
  - **可并行要写进描述，不能指望模型推断**：描述里补一句"为并行执行优化，多个 X 可同时调用"，比在提示里反复催促管用。判据：**这个工具/技能被连续调用多次时，调用方知不知道它其实可以同时发**；不知道就会排队，表现为"明明显然独立的事一件件做"。
  - **给"一问多查"的示例比给规则有效**：官方示例是"问伦敦天气 + USD/EUR 汇率 → 两个函数同时调"。判据：**在提示/技能正文里放一个"用户一句话里含两个独立诉求"的示例**，模型更容易泛化出并行，而不是靠"请尽量并行"这类祈使句。

- **提升层**：工具（接口形状与描述）+ 模型（行为引导方式）。

## 快捷路径有准入条件：省掉的那一步承担了什么保障，就得先确认那些保障你不需要（来源：Temporal 官方《Local Activity》`docs.temporal.io/local-activity` 2026-09-23 r144-C 独立重拉首读，此前未读）

- **原文事实**：Local Activity 在同一 Worker 进程内直接执行，**不走任务队列、不经服务端**，换来"significantly lower latency and fewer Event History entries"。官方同时给了**五条准入条件**，并明说 "Local Activities help with performance optimization and **are not a replacement** for regular Activities"，"For most production workloads, regular Activities remain the **recommended default**"：① 短命（含重试在几秒内完成）② 能在同一份二进制里执行 ③ 不需要路由到特定 Worker / 任务队列 ④ 不需要全局限流 ⑤ **必须幂等**。
- **判据**：
  - **先列"被省掉的那一步在替你做什么"**：队列给了独立调度与重试留痕、服务端给了全局限流、事件史给了审计。**每省一层，就少一层保障**；五条准入条件本质上就是逐条确认"这层保障我不要了"。
  - **幂等是快捷路径的硬门票**：不走队列意味着重放/重来时这一步会被再跑一次，不幂等就是副作用翻倍。
  - **快捷路径默认关，不为"看起来更快"开**：判据＝**这一步是不是真的高频短小到值得**；不是就走常规路径。
  - **可观测性会被一起省掉**：只记最终标记、不记中间步骤，出事后可查的东西变少——**省历史等于省审计**，要在结论里说清。
- 与 §最小架构优先 分工：那条管"要不要上重型框架"，本条管"**已有常规路径时，能不能走更短的旁路**"。
- 反模式：为了少几行代码/少一次调用改走进程内；旁路里做不幂等的写操作；为了日志干净把中间步骤的留痕一起删了；把旁路当默认路径。
- **提升层**：工具（执行路径选择）+ 工作流（保障层的取舍）。
- 触发词：走不走旁路、进程内执行、省一次往返、快捷路径、要不要队列、限流还要不要、幂等才敢省、省了审计、默认走哪条
## 能写成规则的分支就别用模型路由；用模型路由必须闭域（来源：Flowise 官方 `docs.flowiseai.com/using-flowise/agentflowv2` 中 Condition Node 与 Condition Agent Node 的并列设计，2026-09-23 r146-B 独立重拉首读，此前未读）

- **官方把分支做成两个不同的节点，不是一种节点的两种配置**：`Condition Node` 走**确定性比较**（`String`/`Number`/`Boolean` × `equal`/`notEqual`/`contains`/`larger`/`isEmpty`，结果就是 true/false 两条出口）；`Condition Agent Node` 走 **LLM 分类路由**（需要 `Instructions` + `Scenarios`）。判据：**这条判断写不写得成一条规则**——写得成就别让模型掷骰子（与 §判定要确定性 同源，本条补的是**分支这个具体位置怎么落地**）。
- **语义路由必须闭域：每个 Scenario 对应一个出口锚，场景是配置出来的枚举，不是模型自由发挥的结果**。判据：**模型只能在"你列出来的几条路"里选，不能走出第五条**——没有枚举的语义路由等于把控制流交给了不可枚举的输出空间。
- **Instructions 只描述"分类任务"，不描述"怎么走"**：官方示例是 "Determine if the user's request is about sales, support, or general inquiry"。判据：**指令写判据，出口写行为**——把"选完该怎么办"塞进路由指令，会让分类与执行耦在一次调用里，改行为就得重测分类。
- **两种分支的失败形态不同，别用同一套兜底**：确定性分支失败是**配置错误**（可静态查）；语义路由失败是**分类漂移**（要评测量）。判据：**先分清是"规则写错了"还是"模型判偏了"**，两者修法完全不同。
- 触发词：确定性条件优先、语义路由闭域、场景枚举即出口、路由要不要用模型、条件分支。
## 能描述就别编程：默认走声明式，只给四条例外（来源：n8n 官方 `docs.n8n.io/connect/create-nodes/plan-your-node/choose-a-node-building-style` + `.../reference/code-standards`，2026-09-23 r149-B 独立实拉首读，清单外新信源）

- **默认路径是"描述请求"，不是"写执行代码"**：官方的默认风格用一份 JSON 描述请求（`routing` 键），不需要 `execute()` 方法——官方理由是 "less code to write and maintain"；并明写"如果不确定，从声明式开始"。→ 判据：**能用配置描述行为时就用配置**，因为配置只有一份，代码要维护两处（描述与实现）。**例外清单要穷举**，官方只给四条：① 触发器类；② 非 REST（GraphQL、需要外部依赖）；③ 需要做超出描述能力的数据变换；④ 需要按特性在代码里分支。不在清单上就回到默认。
- 例外里有一条很说明问题：**"需要按特性在代码里分支"本身就是升级理由**——同一份特性声明，配置层能控显示、代码层能控执行；只有必须写分支时才落代码（与 `wb-release-maintain` §版本区间声明 合用，能让配置层覆盖大多数场景）。
- **标识与文案分离：改文案不该丢用户已填的数据**。参数有两个名字——对外显示的名字与内部标识（`value`）；**跨操作复用同一个内部标识**，用户在 A 操作填的值切到 B 操作时不会丢；代价是**必须保证同一时刻只有一个字段可见**（显示条件互斥），否则两个字段抢同一个值。
- 与 §不要用尚未定义契约的声明式文件假装安全 分工：那条管**契约不存在时别造一份没人校验的声明文件**（声明 ≠ 治理）；本条管**契约存在时能描述就别落代码**（配置优先于实现）。两条方向相反但对象不同：前者的对象是"自制的治理清单"，后者的对象是"官方的行为描述格式"。
- 触发词：能描述就别编程、默认声明式、例外清单要穷举、不确定就从声明式开始、需要代码分支才落代码、标识与文案分离、改文案不丢数据、复用内部标识、可见性互斥。
## 共享知识放一个仓库，各 agent 引用、不复制（来源：Letta 官方 `docs.letta.com/concepts/shared-memory/index.md`，2026-09-23 r151-B 独立实拉首读，清单外新信源）

- **多个 agent 要同一份知识，给它一个共享仓库，让各 agent 去读，而不是每人复制一份进自己上下文**：官方 shared memory repository「give multiple agents access to the same files」，团队约定、产品知识、研究结论都放一处。
- 判据：**「这个知识会被多个 agent 用到吗」→ 是就外置成共享仓库 + 引用，不是每个 agent 各存一份**（存多份＝漂移、不一致、占更多 token）。
- 与 §能描述就别编程 分工：那条管「能用声明式就别写实现」；本条管「能被多 agent 共享的知识，外置成引用源而非各自复制」，是知识复用层面的 YAGNI。
## 跨档位比「贵和快」是选择偏差；而「不设参数」拿到的是别人的默认，不是中性值（来源：Browser Use 官方 `docs.browser-use.com/cloud/choosing-an-agent.md` 与 `cloud/agent/thinking-levels.md`，2026-09-23 r154-C 独立实拉首读，清单外新信源）
- **★跨档比平均数会得出反因果的结论**：官方公布了三档的每任务成本与耗时（V2 $0.70 / 约 1 分钟、V3 $0.87 / 约 2 分钟、V4 $1.64 / 约 5 分钟），但紧接着自己拆掉这个比较：`V4 costs more per task because customers use it for more complex work, and V2's tasks run shortest only because it gets the simplest ones.`（V4 更贵是因为客户拿它干更复杂的活，V2 跑得最短只是因为它接到的是最简单的活）。官方给的正确读法是**只在相同难度上比**——在**同一批难任务**上，V3 最快（约 6 分钟，V2 与 V4 各约 10 分钟）。→ 判据：**"贵档=浪费钱""快档=更高效"这类结论，多半是接活分布造成的**；比较两个方案前先问一句「它们各自被用在什么难度的活上」，没有同难度对照就别下结论。（与 `wb-artifact-verification` §对照实验 分工：那条管**实验装置怎么搭**，本条管**在真实使用数据上做横向比较时会踩的分布陷阱**。）
- **★不设参数 ≠ 拿到中性值**：官方写明推理深度这个"同一件事"在三家 provider 上**参数名与取值集都不同**（OpenAI 走 `reasoning.effort`、Anthropic 走 `output_config.effort` + `thinking.type`、Google 走 `thinkingConfig.thinkingLevel`），且**一批模型根本不接受这些参数**；更关键的是——`Omitting modelParams applies Browser Use's defaults for that V4 model`（省略参数＝应用**该模型**的默认），官方举例 `gpt-5.6-luna` 与 `gpt-6-astra` **默认就是 `xhigh`**，而 `Astra does not accept none or minimal`。想真正交还给 provider 默认，得**显式发一个空对象**。→ 判据：**「我不设置」等于「接受别人替我设的那个值」**，而且不同目标上的那个值还不一样；涉及成本/深度的旋钮**必须显式写出来**，否则你以为的中性配置会静默变成一个高档位（贵、慢、且没人知道为什么）。
- 与 §取舍清单：先说出按什么标准权衡 分工：那条管**权衡的维度要显式列出来**；本条管**横向比数字时的分布陷阱，以及"不填"这个动作实际选了什么**。
- **提升层**：决策（选型与默认值）。
- 触发词：跨档比较、选择偏差、贵是因为接了不同的活、同难度对照、不设参数、默认值不是中性、省略等于别人替你选、档位默认高档。

- **★「推理强度」是模型专属枚举，不是全局旋钮，换模型会静默重置**：Windmill AI Agent 官方写明 `Reasoning effort is model-specific: changing the model resets the selected effort.`；可选档位**随模型变**（有的只有 `low/medium/high`，有的到 `minimal/xhigh/max`），`An off option is available where the provider can genuinely disable reasoning`——**只有 provider 真能关的时候才有 `off`**；更反直觉的是**「默认」这个词在两家上意思相反**：`For models that only reason when asked (such as Claude), the default option is already labelled off` vs `For models that reason by default (such as Gemini or OpenAI o-series / GPT-5), a Model default option keeps the provider's built-in behavior`。→ 判据：①**换模型＝这一档被清空重选**，配置里留着的旧值不是"沿用"而是"被重置为新的默认"，而新默认可能是**开着的推理**（多花钱、多耗时，且不报错）；②**「off」不是普遍可用的三态之一**（与 §开关三态 分工：那条管一般开关的中间态，本条管**这一档位的能力边界由模型决定**）；③推理消耗额外 token 且**计入该步用量**，所以"要不要推理"首先是个**成本决策**不是质量决策。与 §不设参数 ≠ 拿到中性值 分工：那条管**省略参数＝接受别人的默认**；本条管**切换对象时这份默认会被悄悄换掉**。
- **提升层**：模型 / 决策（成本与深度旋钮的模型依赖性）。
- 触发词：推理强度、reasoning effort、换模型重置、模型专属档位、off不可用、默认就是off、推理要花钱、思考预算。
## 缺能力时先「声明要什么」，再去找：把全量预载换成按需请求（来源：arXiv 2506.01056《MCP-Zero》2026-06-01，2026-09-24 豆包 r156-C 实拉取证，同轮 WB 审计独点属实后落地）
- **★反转顺序**：不是先把整个工具/技能目录塞进上下文让模型挑，而是**让模型在发现自己缺某个能力时，主动发出一条结构化的能力请求**（「我需要一个能把 PDF 转 Markdown 的东西」）。判据：**先描述缺口、后检索目录**——缺口描述比"从一百个里挑一个"省得多，也更准。
- **匹配分两级再合成**：先按**服务聚合能力**描述匹配出候选服务（server 级），再在该服务内按**工具描述**语义排序（tool 级），最终分由两级分数合成（乘积再乘两者较大者），**并对原始描述与增强摘要各匹配一次取高分**。判据：**「这个服务大概是干这个的」和「这个工具具体是干这个的」是两个不同的判据，合成时不要让一级吃掉另一级**。
- 与本技能既有阶梯的关系：**"有没有现成方案"这一步，靠声明缺口去检索，而不是靠把候选全列出来肉眼扫**。判据：**目录大到列不完时，检索才是默认姿势**。
## 单方法不够就组合，但先评估再定（来源：Haystack 官方 cookbook/sparse_embedding_retrieval + using_hyde_for_improved_retrieval，2026-09-24 r161-C 独立实拉首读）
- 别教条选单一方案：稠密检索吃语义但吃算力、对新领域和精确措辞差；稀疏检索反之。常需组合（hybrid = dense + sparse），但"组合"本身不是默认，要先评估再决定。

## 先按频率解耦再谈换模型：一次昂贵决策 + 多次廉价类型化执行（来源：arXiv 2609.30186《Jev-Mobile: Jev as an Executor for Mobile GUI Agents》，2026-09-27 独立实拉 export.arxiv.org 摘要原文）

- 原文：`low-frequency VLM planning and high-frequency lightweight execution: the VLM specifies local goals, the accessibility tree defines a structured executable action space, and a fast typed decision model repeatedly selects actions within this space. This design allows multiple GUI actions to be executed under a single VLM decision` —— 成功轨迹上端到端时延 **−32.7%**、模型 API 成本 **−73.4%**。
- → 判据：**省成本的第一刀是"降调用频率"，不是"换便宜模型"**。把昂贵模型从"每一步都要问"降到"只定局部目标"，中间若干步交给轻量类型化执行器连续跑完；一次决策覆盖 N 步。
- **前提是先有结构化动作空间**：该方案的轻量执行器能成立，是因为 `the accessibility tree defines a structured executable action space`——动作不是自由文本而是有限类型集。→ 判据：**没先把动作空间收敛成有限类型，就上不了轻量执行器**；这一步做不到时，别指望换模型能拿到同等降本。
- **诚实的折让**：该方案成功率 79%，低于逐步 VLM 基线的 84%（**−5pp**）。→ 判据：**频率解耦是成本 / 延迟机制，不是质量提升机制**；只在任务对延迟与成本敏感、且能接受这点成功率折让时才用，别当通用加速手段推广。
- 反模式：为了省钱把每一步都换成小模型（降的是单步质量而非调用次数）；动作空间还是自由文本就上"快速执行器"；只报 −73.4% 成本不报 −5pp 成功率。
- **提升层**：模型 / 工作流。
## 长链路任务优先拆 subagent，内联 skill 只在短小/无契约时（来源：arXiv 2609.09233《Subagents vs Skills》2026-09-07 + Anthropic 官方 Skill-vs-Subagent 对比，2026-09-27 r203-A 实拉核验）
- **★路由判据看"契约清晰度"而非"技能 vs 子代理"标签**：当技能包暴露**清晰的输入/输出契约**、且指令里编码了完成该契约所需的过程知识时，把任务交给一个**隔离上下文的子代理**执行，效果优于把技能整段加载进主上下文；代价是**协调通信 token**。
- **★长任务上下文堆积会退化**：标准 skill 注入在长任务里因上下文越积越多导致推理质量退化；子代理带独立上下文、只回蒸馏摘要（官方：约 1000–2000 token），主上下文不被污染。→ 判据：**任务长 + 会产生大量中间产物 → 走 subagent**；**任务短、无清晰 I/O 契约、就调一下现成能力 → 内联加载 skill**。
- **★半官方背书**：Anthropic 官方认可「需要上下文隔离、或主上下文快满时走 subagent」原则；但「契约路由」本身是 arxiv 学术贡献，官方未直说"按契约选"。→ 判据：用契约清晰度当路由开关，不是无脑"子代理总优于技能"。
- **反模式**：为省事把所有长任务都塞进一个越来越长的主上下文（靠 skill 重复加载）；或反过来——明明一步能调的现成 skill 也起一个子代理，白付协调开销。
- **提升层**：工作流 / 可复用 Skill（路由决策）。

## 采用第三方产物（模板 / 技能 / 代码）的准入门槛：先算改动率，再过供应链四查（来源：n8n 模板生态多篇独立实拉取证 xuro.net《Best n8n Workflow Templates in 2026》+ stacksheriff《n8n Templates: Find, Import and Vet Workflows (2026)》+ samautomation《Template Requirements Before You Buy》+ synkrai《Why Most n8n Templates Fail》+ nordflux《why a community template rarely suffices》，2026-09-27 r206-C 独立实拉；与 §引依赖七级阶梯 互补——那条管「要不要引一个库」，本条管「要不要接一整份别人的实现」）
- **40% 改动阈值**：需要改掉的部分超过约 40% 就重建，别改。判据：**改到 40% 时你已经承担了读懂别人逻辑的成本，却没拿到自己写的可维护性。**
- **供应链四查**（接之前逐项过）：① 第三方节点/插件是否拥有全量数据与宿主机权限（n8n 社区节点即如此）；② 导出物里是否残留作者的认证头/凭据（HTTP 节点常带）；③ 作者与最近更新时间（超过 12 个月未动 = 接口可能已变）；④ 凭据一律改用本地凭证引用，不在代码节点硬编码。
- **沙箱先跑，且要故意失败一次**：用沙箱账号/日志-only 出口跑一遍；再插一个模拟失败节点（4xx/5xx）看它怎么处理——**只看 happy path 的模板等于没验。**
- **生产四缺必补**：幂等键 / 退避重试 / 结构化错误路由到运维收件箱 / 每次运行带时间戳与状态码的日志。缺任一项就不是「省下的时间」，是「延后的事故」。
- 判据：**把模板当陌生人提交的代码评审，不当你自己的实现接受。**

## 采纳平台前的四个治理控制点 + agent 与 flow 必须共享单一状态面（来源：Activepieces 官方文档首页 2026-09-28 r208-B 独立实拉，第 3 次探活达标）
- **选平台先过四问，不是先比功能数量**：官方自述治理为四个可决策项——① 谁能构建（who can build）；② 他们能触达哪些应用（which apps they can reach）；③ 哪些模型能看到你的数据（which models see your data）；④ 凭据存在哪（where credentials live）。判据：**功能表能抄，这四个控制点抄不来；它们决定的是"出事后你能否追责与收口"，不是"能做多少"。**
- **数据与模型的可见性是独立控制点，不能被"接了哪个模型"掩盖**：第三问单独列出，说明平台把"模型看到什么数据"当作与"用哪个模型"不同的权限面。判据：**选型时若供应商只答模型名、答不出 data-facing 的模型清单，等于这条控制点不存在。**
- **agent 与 flow 双向调用，且必须读写同一张状态表**：官方架构为 agent 可调 flow、flow 可调 agent、双方读写同一 Tables。判据：**状态存两份（agent 一份、编排一份）必然漂移，且漂移点会出现在双方都认为是对方负责的那一块。** 落自研时同理：把共享状态收进单一可查询表，而不是各留一份内存。
- **平台若提供嵌入分发，租户级裁剪是必查项**：Embed builder 之外还有按 token 预置用户（免二次登录）、预置客户凭据、按客户裁剪可见应用列表。判据：**把构建器嵌给别人用，"每个租户能看到什么"必须可配置；不可配置就等于把所有集成暴露给所有租户。**
- 提升层：工具 / 工作流。触发词：平台选型、治理控制点、谁能构建、模型看数据、凭据存哪、共享状态表、agent 调 flow、状态漂移、嵌入分发、租户裁剪。

## 选自托管 / 开源 agent 栈时，把「模型强度」当安全控制项、把「治理结构」当信任信号（来源：docs.openclaw.ai 首页与 Quick start 2026-09-28 r209-C 独立实拉；原文 "For best quality and security, use the strongest latest-generation model available"，并声明 MIT / OpenClaw Foundation 501(c)(3) / 无付费层 / 默认无遥测仅一个可关闭的版本检查；与 §第三方产物准入门槛 互补——那条管"第三方产物进门前查什么"，本条管"整个栈选不选"）
- **"用你能拿到的最强最新一代模型"是官方的安全建议，不是性能炫技**：自托管栈把请求路由到弱模型，等价于放宽了自己的安全边界（弱模型更容易被注入、更容易误调工具）。判据：**选型表里的"省钱选小模型"在自托管场景下是一条安全降级，不只是质量降级**；涉及工具权限与凭据的环节不要为省 token 换弱模型。
- **治理结构是可核验的信任信号，优先级高于宣传语**：非营利基金会主体、无付费层、默认无遥测（仅一个可关闭的版本检查）——三项都是**可被第三方复核的事实**，而不是"我们重视隐私"这类声明。判据：**评估一个 agent 栈时先问"它的钱从哪来、默认往哪发数据、能不能关"，答不上来的按不可信处理**；与 wb-skill-authoring §持久声明纪律 一致——能被检查的声明才算声明。
- **同一套代码同时覆盖个人与团队部署，差别只在配置**：官方明示个人助手与团队部署是同一个 Gateway，配置是唯一差别。判据：**选型时不要为"以后可能要团队协作"另选一套栈**，先确认它是否只是配置差异，避免为不存在的分叉重复投入。
- 判重：`sudosubin/agents.nix`（Nixpkgs overlay 分发 skills.sh 技能）本轮实拉，属"多渠道分发"的第 N 个渠道实例，与 wb-skill-authoring §技能家族与多渠道分发 重叠 >60%，不落。
- 提升层：模型 / 工具。触发词：自托管选型、开源 agent 栈、模型强度、弱模型安全、默认遥测、无付费层、基金会治理、个人与团队同栈。

## 编码 agent 栈的迁移要按三笔账算：成本 / 速度 / 用量，可迁移性是选型前提（来源：deeplearning.ai 短期课程《AI Coding Workflows: From Cloud to Local》JetBrains，1h32m，2026-09-28 r210-C 独立实拉）
- **课程主张**：从一个云端编码 agent 基线出发，**切换编码 agent、接入不同模型/提供商**，并**评估云 → 混合 → 本地三种工作流的 cost / speed / usage 权衡**。
- **判据**：① **可迁移性先测后选**——「能不能换 agent / 换模型」是选型时的**前置条件**，不是用久之后的补救；把工作流焊死在单一 agent 或单一提供商上，等于放弃议价与降级能力。② **迁移不是二值判断，是三笔账**：**成本**（token/订阅）、**速度**（往返延迟、本地推理吞吐）、**用量**（上下文与请求配额）；三笔要分开记，混成一个「感觉更快/更便宜」就没有决策价值。③ **云→本地是连续谱不是开关**：混合态（本地检索/执行 + 云端推理）通常是先落点，全本地只在三笔账同时改观时才成立。
- 与 §自托管栈选型（模型强度=安全控制项、治理结构=可核验信任信号）互补——那条管「要不要自托管」，本条管「从托管迁出去要算哪几笔账」。
- 提升层：工作流 / 可复用 Skill。触发词：编码 agent 选型、云到本地、混合工作流、成本速度用量、可迁移性、模型提供商切换。
