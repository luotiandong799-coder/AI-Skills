## 三、本轮 3 个独有点（完整判据见技能正文 §13.1–13.3）

1. **触发器决定权限面，危险动作不是 checkout 而是「下一步执行了检出的代码」**：`pull_request` 跑 merge commit、只读 token、无 secrets、有 fork 审批；`pull_request_target` 跑 base 默认分支、读写 token + 全部 secrets、绕审批。官方 MUST「only ever inspected as data and never executed」；`make test` 跑 PR 里的 Makefile，`npm install`/lifecycle scripts/配置文件/依赖都算执行且**不需要显式 build 步**。⇒ 门禁三问「谁能触发 × 拿到什么 × 检出物是否被执行」，并按能力等价集枚举绕过（`git fetch` / `gh pr checkout` / 下载 fork 工件），不按命令名点杀。
2. **常见缓解各有失效面，正解是工作流拆分**：`permissions: {}` 挡不住缓存投毒（缓存作用域挂默认分支 SHA、低信任写 → `push`/`schedule` 恢复 → 横向移动）；TOCTOU 让「审批后改 PR」绕过（`head.ref` 可变 vs `head.sha` 不可变，用 commit SHA 不用 HEAD）；漏洞常残留非默认分支；repo check 对 `workflow_run` 无效、actor/date check 对 `issue_comment` 无效（触发者≠利用者、commit date 可伪造）。⇒ 逐条撞失效面，禁止「配了 permissions:{} 就算加固」；正确形态是 `pull_request` 无密钥处理 + `workflow_run` 高信任只消费经验证元数据。
3. **平台默认值本身是安全边界，且随生效日期变化**：2026-06-26 起「不可信触发 ∧ 默认分支 SHA 作用域」两条件 AND 才发 read-only cache token；save 失败仅 warning、job 继续、restore 不受影响；7 类触发与非默认分支作用域（`pull_request`/`release`）保留读写；填缓存须另起 `push` 工作流。Docs 载 2026-12-02 起公开仓默认策略强制阻断 `pull_request_target`，**当前 evaluate 模式、私有/内部仓不适用**。⇒ 门禁按「触发事件 × 作用域」二维表判，声明带生效日期/仓型/模式；「CI 全绿」不证明缓存写入成功，别把「平台会拦」写成已生效。
