## 实拉证据（关键原文）
- zylos 社区阈值：「Trip to OPEN: 5 consecutive failures, or >15% error rate over a 60-second window. Cooldown: 60 seconds (longer for LLM APIs — they recover slowly). HALF-OPEN probe: use a lightweight low-stakes request; never re-send the original failing prompt.」
- truefoundry：「Token buckets handle volume. Circuit breakers handle pattern. An agent that obeys the 100-rpm bucket but makes 100 identical calls per minute in a tight loop is still a runaway, just a slower one.」
- opennash：「Most frameworks let you set timeouts on individual tool calls. That is necessary but not sufficient…The fix is a timeout budget for the entire agent turn.」
- dailyaiworld：预算到限时「the circuit breaker freezes the agent, checkpoints its state to Temporal, and sends a human-in-the-loop approval request」——不是直接杀。
- openlegion：「Never retry non-rate-limit 4xx errors (400, 401, 403, 422) — these require operator intervention.」

## 独点清单（3 个真独点）

### 独点1：熔断阈值具体数字 + half-open 探测不重发原 prompt（工具层）
- 判据：5 连续失败或 60 秒窗口 >15% 错误率触发 open；冷却 60 秒（LLM API 恢复慢要更长）；half-open 用**轻量低风险请求**探测，绝不把原来失败的 prompt 再发一遍（那会重复触发同样的问题）。
- 独有增量：r166B 讲 transport 重试退避；本条给了熔断的**具体阈值与 half-open 探测纪律**，是生产部署可直接抄的数字。
- 提升层：工具。

### 独点2：速率桶管量、熔断管模式——慢失控也是失控（工作流层）
- 判据：token bucket 只管每分钟多少请求；一个遵守 100rpm 但每分钟发 100 次相同调用的 agent 是"慢失控"——它没超桶但在死循环烧钱。网关必须同时看**流量模式**（连续 429/相同调用重复率）触发熔断。
- 独有增量：点出"合规的死循环"——限速到了不代表没失控，模式检测是另一层。
- 提升层：工作流。

### 独点3：整轮超时预算不只单步 + 4xx 不重试（工作流层）
- 判据：每工具超时必要但不够——模型可能串行调 6 个工具每个 3-4 秒，用户盯 spinner 25 秒。必须给整个 agent turn 设总超时预算。重试只针对 429/5xx 退避；400/401/403/422 是客户端错误（参数错/权限错），重试无意义，直接转人工。
- 独有增量：总 turn 超时预算 + 4xx 不重试的二分，与单步超时互补。
- 提升层：工作流。
