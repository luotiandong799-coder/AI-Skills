# r176-B MCP 服务器生产安全：tool manifest pinning、无状态化、四控制层

实拉时间：2026-09-24 20:25
信源：Secure MCP Server Development 2026-02 / DEV auth authz 2026-09 / Microsoft Foundry build MCP 2026-07 / developertoolkit hardening 2026-08 / DEV 7 controls 2026-09 / InfoQ MCP gateway 2026-07 / entrans dev guide 2026-08 / AWS stateless MCP 2026-09 / mcpgee security checklist 2026-09 / SecAppDev MCP security PDF（MCP 安全组，满 10 站）

## 实拉证据（关键原文）
- InfoQ：「Address MCP security as four control layers: execution, management infrastructure, outbound trust, semantic integrity. Use a gateway for authz/audit — do not expect it to detect semantic abuse. Pin tool manifests at registration to avoid post-approval schema drift and rug-pull.」
- DEV：「Never do token passthrough. Derive tenant from verified claims, not request params. Map tools to explicit scopes. New tools denied by default.」
- AWS：MCP 2026-07-28 spec 转无状态——issuer validation（RFC 9207）、client type declaration。
- SecAppDev：manifest.json pruning 减攻击面；输出过滤（JSON schema）防模型-工具输出注入；进程隔离跑工具。

## 独点清单（3 个真独点）

### 独点1：tool manifest pinning——防止审批后 schema 漂移（工作流层）
- 判据：MCP server 注册时把工具 manifest（name/description/schema）钉死。server 升级后偷偷改工具描述或加字段（rug-pull：你审批时它是只读搜索，更新后变成能删库）。diff-based review 而不是二进制 allow/deny。
- 独有增量（与 r164C MCP 服务器区别）：那条讲怎么搭 MCP；本条讲**生产部署后怎么防 MCP server 自己变坏**。
- 提升层：工作流。

### 独点2：网关只管 authz/audit，不管语义滥用——四层控制分开（工具层）
- 判据：别指望一个 MCP gateway 解决所有安全。四层各有执行点：执行层（工具权限/隔离）、管理基础设施层（注册/审批）、出站信任（server 能连哪）、语义完整性（输出内容校验）。网关做认证审计，但模型被诱导用合法工具做坏事（语义滥用）网关抓不到。
- 独有增量：点出"网关不是安全银弹"，语义滥用是另一层。
- 提升层：工具。

### 独点3：无状态化 + token 不 passthrough（工具层）
- 判据：MCP 2026-07 spec 转无状态。OAuth 2.1/OIDC、短时效 token、每次调用校验；tenant 从 verified claims 推不从请求参数取（防伪造租户）；新工具默认拒绝、读写分离、敏感操作要确认。
- 独有增量：2026-07 spec 的具体变化（issuer validation/client type declaration）。
- 提升层：工具。

## 判非重复理由
- r164C 讲 MCP 服务器搭建；本条讲生产安全与 schema 漂移，增量 >40%。
- 与 r172-C 间接注入互补（那讲 prompt 侧，这讲 server 侧）。
