# r176-A Agent 生产监控：p95 不按均值、延迟拆四层、token 除以被接受结果

信源：valuestreamai 2026-05 / mlflow production management 2026-06 / mlflow latency 2026-07 / aurametrics token efficiency 2026-06 / agentic-ai observability 2026-09 / futureagi 12 metrics 2026-05 / openlit victoria metrics 2026-07 / futureagi monitoring glossary / 阿里云 CMS AI 监控 2026-06（监控组，满 10 站）

## 实拉证据（关键原文）
- futureagi：「Always p95, never the mean; the mean hides the 1-in-20 user who waits four seconds and hangs up.」
- aurametrics：「AI agent latency has to separate model time, tool time, queue time, and human-review time. One slow retriever can masquerade as the model being slow.」+「tokens per accepted outcome: approved PR / resolved ticket / completed workflow.」
- mlflow：「P99 latency reveals tail behavior averages hide. An agent calling three external tools in sequence can spike P99 even when P50 looks healthy.」
- agentic-ai：MTTD（Mean Time to Detection）= 从失败到检测的时间，衡量告警覆盖质量。

## 独点清单（3 个真独点）

### 独点1：延迟告警按 p95/p99 不按均值（工作流层）
- 判据：均值隐藏尾延迟——agent 串行调三个外部工具，P50 健康但 P99 爆。SLO 写 p95 end-to-end（RAG ≤2s、简单 chat ≤500ms），5 分钟滚动窗口超阈值才 page。TTFT（首 token 时间）单独盯，流媒体 UX 感知全在这。
- 独有增量（与 r157B 可观测性区别）：那条讲 trace 四支柱；本条讲**具体盯哪些数字、按什么分位、怎么配告警**。
- 提升层：工作流。

### 独点2：agent 延迟拆四层——模型/工具/队列/人工（工作流层）
- 判据：端到端延迟不能只看一个数。拆成模型时间、工具时间、队列时间、人工审核时间分别计时。一个慢检索器会伪装成"模型慢"——不拆层就去优化模型，方向错了。
- 独有增量：点出"慢在哪一层"必须拆开，否则优化打偏。
- 提升层：工作流。

### 独点3：token 效率除以"被接受的结果"，不是每次调用（工作流层）
- 判据：tokens per call 没意义；tokens per accepted outcome（批准的 PR / 解决的工单 / 完成的工作流）才是效率指标。同时盯 input/output/cached/reasoning 四类 token。成本按 per successful task 算（不是 per run）——失败的 run 也烧钱但没产出。
- 独有增量：把成本分母从"调用次数"换成"成功结果数"，和 r170-B 成本工程呼应但更具体。
- 提升层：工作流。
