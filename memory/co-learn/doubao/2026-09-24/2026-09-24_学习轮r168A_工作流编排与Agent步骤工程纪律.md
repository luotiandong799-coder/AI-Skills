# r168-A 工作流编排与 Agent 步骤工程纪律

实拉时间：2026-09-24 18:42-18:44（本地）
实拉信源（10 站，全量逐站）：Dify / n8n / LangFlow / Activepieces / Make / Pipedream / Anthropic Skills / skills.sh / SkillsMP / Full Stack Skills

## 实拉证据（逐站）

1. **Dify**（dify.ai/blog/the-human-input-node + deepwiki/langgenius/dify）：Human Input 节点是画布一等公民，执行到该节点即 yield pause event，表单+决策按钮后沿对应分支继续；v1.13 起支持自定义按钮（不止 Approve/Reject，可加 Escalation/条件批准，各接不同 workflow path）；支持超时处理。
2. **n8n**（blog.n8n.io/production-ai-playbook-complex-agent-patterns + deterministic-steps-ai-steps）：「Deterministic pipeline with one agent step is the right answer most of the time」——大部分工作流 = 普通节点（trigger/HTTP/Set/IF/DB 写）+ 单个 AI Agent 节点只放在需要判断的那一点；只有动作序列真的依赖输入才用自主 Agent；分类用快便宜模型、生成用强模型；复制粘贴的预处理/校验/后处理抽成 sub-workflow 一次更新处处生效；把 workflow 包成工具（Call n8n Workflow Tool）让父 agent 调。
3. **LangFlow**（langflow.org/blog/how-to-build-a-deep-research-multi-agent-system + paiteq.com orchestration patterns）：deep research = 子问题→Summary agent 抽事实→Reviewer agent 扫覆盖度、标缺口、提新子问题→Professional Writer 成报告；最终 writer 跑大模型、前面节点保持 lean 控成本。Supervisor vs Swarm 对比：token 成本线性 vs 对等广播二次方；可调试性一条 trace 树 vs 交接手环图；失败模式 supervisor 上下文 OOM vs 无限 handoff 循环。
4. **Activepieces**（activepieces.com 首页 + resources/automation-for-ai-agents）：「Approval where it counts: Gate the steps that touch money, customers, or production, and let the rest run」；Tables 存结构化上下文（prior prompts/entity IDs/validation flags）支持有状态分支；MCP 把 workflow 暴露成可调用工具。
5. **Make**（help.make.com/make-ai-agents-new-best-practices + academy agent-engineering/02-building）：工具靠 name+description 选（描述模糊→agent 忽略或误用）；测试四检查：Request（缺信息也理解意图）/Configuration（正确查知识、备齐数据再调工具）/Execution（正确工具+参数填全）/Result（目标系统产出正确）；每模块 Break/Ignore 错误处理+错误路由 Slack 告警。
6. **Pipedream**（pipedream.com/docs/build-with-ai + privacy-and-security/best-practices）：AI 生成代码要写清具体指令（"给 HTTP 步骤加 429 时退避重试 3 次"而非"修错误处理"）；安全最佳实践要求审计 workflow 内代码——连平台自带 prebuilt 组件也要审。
7-10. **Anthropic Skills / skills.sh / SkillsMP / Full Stack Skills**：官方规范（SKILL.md<500 行、name≤64 字符小写连字符、description 含做什么+何时用、渐进披露）与 npx skills add owner/repo 安装器、SkillsMP 35 万+聚合——与已有 wb-skill-authoring 规范/CLI 管理偏好重叠>60%，纯重复不落。

## 独点清单（3 个真独点，双键查重后落地）

### 独点1：确定性优先 + 快慢模型分工（工作流层）
- 原文判据：「Deterministic pipeline with one agent step is the right answer most of the time」+「fast cheap model for classification, more capable model for generation」。
- 独有增量（与已有「多 agent 协作纪律·大多数系统不需要多 agent」的区别）：那条管「要不要拆成多个 agent」，本条管**单条流程里节点类型怎么混**——默认普通节点写死流程，只在真正需要判断的那一个点插 AI 节点；判断类前置步骤（分类/路由/提取）用快模型，生成/综合类用强模型；深度研究里中间节点保持 lean、只有最终 writer 上大模型。
- 提升层：工作流。

### 独点2：Human Input 一等公民节点 + 按风险设闸门（工作流层）
- 原文判据：Dify Human Input 是画布节点（不是外挂审批系统），执行到即暂停-恢复，自定义决策按钮接不同分支、有超时兜底；Activepieces：只给 touch money/customers/production 的步骤设批准，其余放行。
- 独有增量（与已有「请求批准画面怎么写/风险五类触发索引」的区别）：已有管**批准内容怎么写**和**触发哪五类**，本条管**机制形态**——等待人工应做成流程里的一等节点（可暂停/恢复/分支/超时），不是事后补审批弹窗；闸门按步骤风险设，不整条流程一刀切要人盯。
- 提升层：工作流。

### 独点3：Agent 集成三层架构 + debug output 原始输出留痕（工作流/可复用 Skill 层）
- 原文判据：三层 = Input（触发）→ Processing（AI agent，**内含 debug output 模块记录 agent 原始输出**）→ Execution（子流程/API 真正执行）；agent→子流程数据传丢时，先看 debug output 的原始输出——数据在 agent 输出里就是 prompt 问题，不在就是映射层问题。配套 Make 测试四检查（Request/Configuration/Execution/Result）。
- 独有增量（与已有「工具结果断言层/verify-before-retry」的区别）：那两条管调用后校验和重试，本条管**排障入口**——agent 与下游之间必须留一份原始输出快照，故障先定位「模型层还是映射层」，再决定改 prompt 还是改参数映射。
- 提升层：工作流。
