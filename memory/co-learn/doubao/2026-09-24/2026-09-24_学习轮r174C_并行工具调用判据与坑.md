# r174-C 并行工具调用：无依赖才并行、并行要显式提示、有副作用操作不并行

## 独点清单（3 个真独点）

### 独点1：并行判据——"call B 的参数能在 call A 返回前写出来吗"（工作流层）
- 判据：两工具无数据依赖（A 输出不是 B 输入）就并行。一句话测试：写 call B 的参数时需不需要等 call A 的结果？不需要→并行。典型安全并行：独立数据源查询、同参数不同值的批量查（订单1001和1002同时查）、只读操作。
- 独有增量：给了一个可直接判断的测试问句，不是抽象的"无依赖"。
- 提升层：工作流。

### 独点2：模型不会自动并行，必须在 prompt 里显式说"同时调这几个"（可复用 Skill 层）
- 判据：光在工具定义里写"可以并行"模型不会自己推断；必须在提示词里明说"call all three tools"或"fetch all..."。否则模型串行调用，延迟白白增加。三个 800ms 串行=2.4s，并行=0.8s。
- 独有增量：点出"并行不是模型默认行为，是提示词指令"——和 r172-A 工具描述工程呼应。
- 提升层：可复用 Skill。

### 独点3：有副作用/幂等敏感操作不并行；strict 模式与并行互斥（工具层）
- 判据：支付、发邮件、写共享状态的工具不并行（并发重复请求）；有顺序要求的不并行。OpenAI strict schema + parallel_tool_calls=true 会静默降级成非 strict——二选一。模型把有依赖的调用并行了会用过期/错误参数白跑，结果还要丢掉。
- 独有增量：两个坑——幂等敏感 API 不并行、strict 与并行互斥，都是生产坑。
- 提升层：工具。
