### 独点判据原文（逐条，不缩水）

- **r738B-1 ★四种手段各减一样东西，组合前先定位压力源**：官方逐字表把工具面拆成四条互不替代的路径——工具定义（预加载）、`tool_result` 往返（调用链）、重复定义的 token 成本（计费）、历史里的旧 `tool_result`（长对话）；官方结论「Each approach targets a different source of context pressure」/「Pick the one that matches where your tokens are going.」。判据：① 工具定义膨胀 ≠ 工具结果堆积，减前者用 defer、减后者用脚本化或旧结果裁剪，混用会「开了但没省到地方」；② 组合允许（「You can use these approaches together, because each solves a different part of the problem」），但起步顺序按瓶颈来，不是一次全上；③ Anthropic 官方同向「Not every agent needs to use all three features for a given task. Start with your biggest bottleneck」。与 §三/§五分工：那两条管窗口里装什么，本条管工具面这条独立压力源。
- **r738B-2 ★缓存不减少上下文，只减少重复付费；与 §四计费口径互补不重复**：官方逐字「Prompt caching doesn't reduce the number of tokens in context, but it reduces what you pay for them on subsequent requests.」；「Cache writes carry a 25 percent markup over base input pricing, which pays back on the second request that hits the cache.」 ⇒ 把 cached_tokens 上升读成「窗口压力下降」是口径错：窗口里那批工具定义仍在，退化风险（§五 n² 梯度、干扰项）一分未减。判据：① 报上下文健康度时把「占窗口的 token 数」与「计费 token 数」分两栏；② 工具集大而**固定**才是缓存主场，工具集频繁变动要回到 r715B 的渲染前缀失配问题；③ 10 个工具以下、每轮都要用全，别为省基线引入额外一轮检索。
- **r738B-3 ★省上下文要付延迟，脚本化改变的是「中间结果进不进历史」**：官方逐字「This trades a small amount of latency (one extra turn to look up a tool) for a large reduction in baseline context usage.」；程序化调用把多次 `tool_use`/`tool_result` 往返折叠成一段在沙箱里跑的脚本，「The intermediate results never enter the conversation history.」。判据：① 工具搜索的收益要用「基线占用下降」减「多一轮的时延」来算，低延迟交互场景不必然划算；② 判断该不该脚本化，看的是「中间结果有没有资格进历史」，不是「调用次数多不多」；③ 旧结果裁剪是不可逆动作，与 §五 r732C 的正解配套：裁剪前先把原始轨迹存成窗口外可查询对象。
