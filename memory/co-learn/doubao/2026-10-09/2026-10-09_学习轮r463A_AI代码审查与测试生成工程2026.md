## 落地 5 独点（每点标注提升层）

### 1. AI 代码审查架构原则：独立审查 agent + 证据要求 + reviewer skills 版本化（可复用 Skill/工作流）
来源：7-practices-roi / machinebrain / designveloper / ai-tldr
- **写代码的 agent 不审自己的代码**：Anthropic 工程团队实证——把编码 agent 与独立验证 agent 分离能得到更诚实的评估（自我评估的 agent 会自信地夸奖平庸结果）；独立审查 agent 能抓到作者 agent 抓不到的另一类问题。
- **评论必须指向证据**：AI 审查评论须指向失败测试、静态分析结果、运行时信号、策略规则或显式需求——"合理推测不是证据"（plausible explanation is not evidence）。
- **reviewer skills 版本化入库**：把仓库约定、架构决策、测试要求、安全规则放进版本控制的 reviewer skill 文件，而不是每次在 prompt 里反复粘贴；长而不维护的规则书会让 AI 审查又吵又脆。
- **恶意框架化（malicious framing）降低检测率**：把补丁描述为安全会显著降低 LLM 的漏洞检测率——高影响变更（认证/支付/基础设施/数据处理）必须保留人工审查预算。
- 提升层：可复用 Skill（审查架构）/ 工作流（证据要求）。

### 2. PR review prompt 六要素与七阶段 pipeline（可复用 Skill/工具）
来源：aitoolsguidebook-pr-prompts / sevenlabs / softwaretestpilot-llm-review
- **PR 审查 prompt 六要素**：Role（谁在审：release captain/QA lead/SRE/staff engineer）+ Context（repo/框架/运行时/分支/diff/失败日志）+ Goal（一个具体交付物：checklist/plan/测试文件/审查笔记/根因/工单列表）+ Constraints（MUST NOT：不自动修复/不静默重写/不猜版本）+ Output format（结构化）+ 示例；bug 聚焦审查 prompt=Role（staff engineer 审 PR，只查正确性 bug 与安全，风格交给 linter）+ 每条 bug 带严重级（P0-P3）+ 类别（null/boundary/race/auth/injection/missing-test/error-handling）+ 文件行号。
- **七阶段 pipeline**：scope（按 PR 大小缩放分析）→prompt→evaluate（LLM 按 JSON schema 输出结构化结果）→format→validate（解析校验；AI 评论映射到 diff 具体行号；**幻觉行号直接丢弃**）→publish（经 GitHub API 以非阻塞评论发布）——格式/验证阶段是"有用审查 vs 自动噪音生成"的分水岭。
- 提升层：可复用 Skill（prompt 模板）/ 工具（pipeline 阶段）。

### 3. 变异评分黄金标准：阈值与五步流水线（工具/工作流）
来源：scaled2c / augmentcode-mutation / softwaretestpilot-genai-unit / mervcodes
- **变异评分是黄金标准**：行覆盖只报"哪些代码被执行"，变异评分报"注入的缺陷是否被测试检测到"——AI 生成套件能高覆盖却杀不死几个变异体，制造虚假信心。
- **量化阈值**：AI 生成套件首过变异分通常 55-65%，人工审查存留变异体后升到 70%+；**≥70-75% 才算真正有保护力的测试**；用 Stryker-JS（JS/TS）/PIT（Java）/mutmut（Python）；**每月跑一次 mutation pass 抓假覆盖**。
- **五步流水线**：①仓库上下文生成测试（候选含 setup/依赖/断言）②构建执行（只留能编译能通过的）③变异测试（弱断言以存留变异体形式浮出）④存留变异体喂回 agent 做针对性断言修复 ⑤被接受的修复进团队记忆与审查规则（仓库特定测试模式持续传承）。
- 提升层：工具（变异测试器）/ 工作流（五步流水线）。

### 4. 对抗式测试生成：双 agent 框架与 feedback-directed 重 prompt（工具/可复用 Skill）
来源：arxiv-advertest / franktip-llmutantkiller / aitoolsguidebook-test-workflow / codingfleet
- **AdverTest 双 agent 对抗**：Test Case Generation Agent（造高质量套件抓 bug）vs Mutant Generation Agent（造变异体逃逸）——把变异测试织进测试生成过程本身。
- **feedback-directed 重 prompt**（LLMutantKiller）：测试没杀死目标变异体时，带场景化反馈（语法错误/依赖违规/失败断言执行日志）重新 prompt LLM 重试，最多 N 次——执行反馈是测试生成的最大杠杆，其次才是模型选择。
- **对抗式生成流程**：直接"给这个函数加测试"产出的是镜像实现的测试（永远通过、抓不到任何东西）——正确顺序=先向模型要 edge cases 清单→再写测试→然后变异函数确认测试真的会失败（预算 15-30 分钟/非平凡函数）。
- 提升层：工具（双 agent 框架）/ 可复用 Skill（对抗式生成流程）。

### 5. 编码 agent 形态选型与 TDD 工作流（工作流/工具）
来源：sureprompts / qaskills-cursor-vs-claude / cursor-agent-best-practices / dev-dublecc / thepromptshelf
- **三形态选型**：Claude Code=终端原生自主循环（写测试→终端跑→读失败→修→重复，全程免手把手，最适合驱动完整红-绿周期）；Cursor=chat-with-diff 布局（每个改动以 diff 呈现、接受/拒绝后才落地，适合 review 与 red/refactor 阶段，但每步确认会拖慢 green）；Cline=plan/act 分离（先计划讨论后执行）。
- **设计锁定→实现**：先让 agent 审设计文档并 push back，设计锁定后把文档作为上下文导入再实现（@docs/webhooks-design.md Implement the migration from this design... Match the schema exactly as specified）。
- **测试先行 prompt 四要素**（Anthropic 实证）：命名文件 + 命名场景 + 命名约束 + 命名一个 agent 能运行的检查（"write a validateEmail function. example test cases: user@example.com is true, invalid is false... run the tests after implementing"）——模糊 prompt 让 agent 猜，四要素让它直接跑；显式声明在做 TDD 时 agent 不会预写模拟实现。
- 提升层：工作流（选型与 TDD）/ 工具（prompt 四要素）。
