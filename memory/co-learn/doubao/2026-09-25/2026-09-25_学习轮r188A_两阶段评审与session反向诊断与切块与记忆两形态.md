## 独点（5 个）
### A1：代码评审分两阶段——先 spec compliance 再 code quality（来源：obra/superpowers）
- subagent-driven-development 里每块任务做完，先问"做的是不是计划要的"（spec compliance），再过代码质量。Critical 问题 block 前进。
- 判据：**一把评代码会把"方向错"和"写得烂"混在一起**——方向错了代码再好也白做；先对计划再审代码，与 wb-artifact-verification 分工：那条管产物对错，本条管"是否对题"。
- **提升层**：工作流/可复用 Skill。

### A2：skill 系统本身要可诊断——反向读 transcript 行级定位（来源：同上 diagnosing-superpowers）
- session 出问题（skill 误触发/该响没响/agent 偏离计划/重复干活）时，反向读 transcript，给行级证据报告"哪一步哪个 skill 做错了什么"，可打包 scrubbed bundle 报 bug。
- 判据：**路由/触发类技能本身也要 debug 入口**——不能只靠"好像没触发"；与 wb-skill-authoring 闭合邻域评测互补：那条管离线测，本条管线内复盘。
- **提升层**：可复用 Skill。

### A3：任务切 2-5 分钟一块，每块带 exact file paths + verification steps（来源：同上 writing-plans）
- 计划拆成 2-5 分钟的小块，每块写死改哪个文件、完整代码、怎么验证；计划写给"没品味没判断没项目上下文的 junior"看。
- 判据：**拆块粒度以"一个 junior 不费脑就能照做"为准**；不是按文件模块切，是按可验证的最小动作切。
- **提升层**：工作流。

### A4：记忆两形态权衡——profile JSON vs document collection（来源：LangGraph memory）
- profile=单条 JSON key-value，信息统一好喂，但模型每次要 reconcile 新旧值易出错、膨胀后崩；collection=文档集合，recall 高、新增比对账容易，但要自己管删/改/搜。
- 判据：**用户画像这种"全局一致"的用 profile，零散事实用 collection**；默认别一把塞一个 JSON 里。与 r186-C 三支柱打分、r187-C 记忆六类互补。
- **提升层**：记忆。

### A5：procedural memory 靠 reflection——把当前 prompt + 反馈喂回让 agent 自己改指令（来源：同上）
- procedural memory（怎么做事的规则）在 agent 侧靠"把当前 system prompt + 近期对话/用户反馈喂回去，让模型产出新版指令写回 store"——难一次性写对的 prompt 靠反馈迭代出来。
- 判据：**别一次追求完美指令**；用户 critique 输出 → agent 改写自己指令 → 存回，比静态写死更稳。与 r187-A trace 沉淀 skill 同源。
- **提升层**：可复用 Skill / 记忆。
