## 独点（4 个）
### A1：上下文窗口可视化面板——把"压了多少/怎么压的"亮给用户（来源：deepseek-plugin collections · dsh-context，★600）
- 面板显示当前窗口组成、历史 token 趋势、压缩与剪枝事件。
- 判据：**上下文压缩不能是黑盒**——用户看不见窗口被什么占满、什么时候被压，就不会信任压缩；与 wb-context-compressor（怎么压）互补，本条管"压缩过程的可见性/可审计性"。
- **提升层**：可复用 Skill / 输出。

### A2：@文件提及只注入"存在性引用"，不读全文（来源：dsh-at-file，★438）
- 在编辑器选 @ 文件路径后，只把"这个文件存在"引用进上下文，**不读文件内容**；模型需要时再决定读哪段。
- 判据：**提及 ≠ 注入全文**——用户 @ 一个 5000 行文件不该瞬间占满窗口；这是渐进披露在"用户主动引用"场景的落地，与 metadata→body→resources 三层是同一原则。
- **提升层**：工具/工作流。

### A3：错误通知节流 vs 错误事件流不去重（来源：pipedream errors 文档）
- 默认邮件：**同一错误每 workflow 每 24h 最多 1 封**——高频错误不刷屏；但订阅 `$errors` 事件流的自定义 workflow **每条错误事件都收**，不去重。
- test mode 错误不发通知/live event 才发；REST 可拉最近 100 错误 + `original_event`，程序化重放。
- 判据：**通知层要节流（防人被淹没），事件层要完整（供程序消费/重放）**——两层不能用同一去重策略。与 wb-debug-loop 错误签名索引互补：那条管"错误来了怎么记"，本条管"错误怎么通知/重放不刷屏"。
- **提升层**：工作流/可观测性。

### A4：节点级 retry 硬边界 + fail 分支不中断主流程（来源：dify code node）
- 节点 retry 上限 10 次、间隔上限 5000ms（平台硬边界，不是无限退避）；开 Error Handling 后异常走 fail 分支，主流程不中断。
- 判据：**retry 次数和间隔必须有硬顶**，fail 分支把异常当一条可走的路而不是终止点；与既有 transport/tool 重试分工——那条管代码内重试分类，本条管可视化编排节点的 retry 边界与分支。
- **提升层**：工作流。
