## 独点（5 个）
### K1：settings 硬强制 vs CLAUDE.md 软引导的权威分工表 + claudeMdExcludes + add-dir 开关（来源：docs.anthropic.com/en/docs/claude-code/memory 全文）
- **分工映射表（权威）**：Block 工具/命令/文件路径→managed settings `permissions.deny`；强制沙箱隔离→`sandbox.enabled`；环境变量/API provider 路由→`env`；认证方法与组织锁→`forceLoginMethod`/`forceLoginOrgUUID`——**settings 由客户端强制，Claude 无法绕过**。而代码风格/数据处理/合规提醒/行为引导→Managed CLAUDE.md——**塑造行为但不是硬执行层**。
- **Managed policy CLAUDE.md 位置**：macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`、Linux/WSL `/etc/claude-code/CLAUDE.md`、Windows `C:\Program Files\ClaudeCode\CLAUDE.md`——**个体设置无法排除**（组织强制）。
- **claudeMdExcludes**：monorepo 中跳过其他团队不相关的 CLAUDE.md（大仓库防指令污染）。
- **--add-dir + CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1**：额外目录默认不加载其 CLAUDE.md，显式开关才加载（含 rules）。
- 判据：**硬约束放 settings（防绕过），软引导放 CLAUDE.md（省 context）**；组织级文件用个体无法排除的位置。
- **提升层**：工具 / 可复用 Skill。

### K2：skill-comply 行为合规率测量：三档提示严格级别 + 工具调用时间线合规率（来源：skillsmp #1422，affaan-m/ECC）
- **技能/规则/代理定义是否被实际遵循可以量化**：自动生成 **3 种提示严格级别的场景**（宽松/标准/严格）→ 运行代理 → 分类行为序列 → **报告完整工具调用时间线的合规率**。
- 与 caliper 评测互补：caliper 管"该不该触发/做没做对"（闭合邻域激活测量）；skill-comply 管"**规则被遵循到什么程度**"（时间线合规率 + 严格级别梯度对比）。
- 判据：**规则有效性 = 在不同提示严格度下的合规率曲线**，不是单点测试；输出按时间线（哪个工具调用违反哪条规则）而非总分。
- **提升层**：可复用 Skill（技能评测 / 行为审计）。

### K3：autoresearch 自主实验循环：目标→指标→范围约束→自动变更-测试-测量-保留/丢弃（来源：skillsmp #1413，github/awesome-copilot）
- **Karpathy 式自主迭代**：先定义目标、**可测量指标**与范围约束 → 自动循环（代码变更 → 测试 → 测量 → **保留/丢弃结果**）→ 直到收敛。
- **DO NOT USE 边界显式化**：一次性任务、简单 bug 修复、代码审查、**无可测量指标的任务**——明确不适用（防止把简单任务拖进无限实验循环）。
- 与"事前可验证成功标准"互补：那条管动手前定标准；这条管**自动迭代循环的结构与丢弃机制**。
- 判据：**没有可测量指标就不开实验循环**；每轮必须有保留/丢弃决策，不能无限叠加变更。
- **提升层**：工作流。

### K4：多流派评审团结构化打分：Pydantic Signal 输出（来源：skillsmp #1428，wbh604/UZI-Skill investor-panel）
- **66 位投资者评审团按 9 大流派**（经典价值/成长/宏观对冲/技术趋势/中国价投/A股游资/量化系统/科技领袖/AI 卡位）各自方法论打分，**统一输出 Pydantic Signal：signal/confidence/score/verdict/comment**。
- 与 marketing-council（名人顾问团）同族但增量：**结构化打分 schema（confidence+score+verdict）+ 流派维度覆盖**——同一份输入数据给多方法论并行打分，结论可聚合可对比。
- 判据：**多视角评审要有统一结构化输出 schema**，否则无法聚合；流派覆盖要显式声明（避免视角盲区）。
- **提升层**：工作流 / 可复用 Skill。

### K5：Pipedream component API：dedupe 三策略 + async options 分页契约 + props 四类（来源：pipedream.com/docs/components/api/ 全文）
- **dedupe 策略三选**：unique / greatest / last——事件去重是组件声明式配置，不是手写逻辑；**用 dedupe 必须给每个事件传 id**。
- **async options 分页契约**：`options(page, prevContext)`——prevContext 返回 `{options, context:{nextPageToken}}`（token 分页）；page 返回 0 起始页码（数字分页）——**动态下拉选项的官方分页协议**。
- **props 四类**：User Input（部署时收参数）/ Interface（HTTP/timer 触发面）/ Service（内置 key-value 状态库）/ App（托管 OAuth）——组件按 props 类型分工，不是全塞进 run。
- 判据：**事件去重与下拉分页是声明式契约，写进组件结构而非 run 逻辑**；props 类型决定触发面与状态面。
- **提升层**：工具 / 可复用 Skill。
