## 独点：2 条
**D8：高频策略编译成确定性守卫代码，挂在工具边界，不用 LLM 每次现判断**（来源：LangFlow Policies/ToolGuard，2026-05-20 官方 blog + docs）
- 机制：自然语言策略 → buildtime 编译成验证逻辑（guard code）→ 附加到工具 → 运行时任何 guarded tool 调用先过策略检查才执行；guard code 缓存提升性能。
- 关键区别：**把策略执行从"软指令"（LLM 提示语，每次现判断、可能不一致）变成"工具边界的确定性控制点"（编译代码，可缓存、可复现、零 LLM 成本）**——业务风险真正发生的地方是工具边界，守卫就放那里。
- 与 ctx §guardian pattern 互补：guardian 用 LLM 动态审计划动作（灵活但慢贵）；D8 把**稳定高频策略**编译成确定性代码（快而一致）。判据：**同一个策略每次都要 LLM 重新判断=浪费且漂移；稳定策略进编译层，动态情况才留给 LLM 审**。
- 提升层：工具/工作流。重叠：guardian 30%（都是执行前检查，一动态一确定性）、ed §工具结果断言层 20%（断言管结果后，D8 管调用前）——独立成立。

**D9：安装技能/工具时区分"来源自述"与"服务端解析验证"，只有后者提升为可信源**（来源：OpenClaw docs/tools/skills + cli/skills.md，2026-09 实拉）
- 机制：openclaw skills verify @owner/slug 请求 clawhub.skill.verify.v1 信任信封；已装技能按 .clawhub/origin.json 记录的版本+注册表验证；服务端解析的源才产出 commit-pinned verifiedSourceUrl，**不可用或自声明的 source URL 只留在原始信封、不被提升**。
- 关键区别：**验证来源≠相信来源自述**。自声明"我是官方"的 URL 不被提升；只有服务端独立解析到的才标记已验证。
- 与 sa"来源形态决定复现性"（git 源钉死 commit）互补：那条管复现性，D9 管信任升级规则；与 D5 三层审计互补：D5 审内容，D9 验来源身份。判据：**装第三方技能/工具后，核对其来源是否经过独立解析验证；"来源声称"与"来源已验证"是两个状态，不得混用**。
- 提升层：工具/工作流。重叠：sa 来源形态 20%、D5 20%——独立成立。
