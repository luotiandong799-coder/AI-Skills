## 独点（10）

**1. 并行工具调用五件套（多调用回合/有界扇出/按 ID 键控结果/合并器/限速守卫）**（来源：AgentPatternsCatalog 2026-06-01 + AI-TLDR 2026-06-13 实拉）：provider 支持的多调用 assistant turn 消息格式携带几个独立工具调用→host fan-out executor 在有界并发限制下并发运行→per-tool adapter 调用并返回按 call id 键控的 tool-message 结果→result joiner 收集全部 tool messages 进下一轮 assistant turn 上下文→rate-limit guard 对严格每秒限制的工具做退避+排队；快速测试=能在 call A 返回前写出 call B 参数吗？能→并行（B 输入不依赖 A 输出）。判据：**并行工具调用=五件套（多调用回合/有界并发扇出/调用 ID 键控结果/结果合并器/限速守卫）；依赖判据=参数可在前序返回前写出**。提升层：工作流/可复用 Skill。

**2. 并行化四判据（独立收集→并行；fan-out/fan-in→扇出并行聚合串行；投机→浪费算力<串行延迟；依赖链→串行）**（来源：Zylos 2026-04-23 + AI-TLDR 2026-06-13 实拉）：independent data gathering（无数据依赖的多 API/DB/搜索）总是并行化；fan-out/fan-in=查询分解为子查询后聚合——并行化扇出、串行化聚合；speculative execution=多个可能下一步只有一个结果被用——浪费算力比串行探索延迟便宜才并行化；dependent chains=每次调用需前序输出——不可并行化；并行扇出显著降总延迟（独立子任务 N× 提速）。判据：**并行化四判据（独立→并行/扇出并行聚合串行/投机按算力-延迟权衡/依赖链串行）**。提升层：工作流。

**3. fan-in 三种合并策略（拼接/黑板键结构化合并/归约）+合并幂等**（来源：OpenLegion 2026-07-01 + AgentPatterns.ai LLM map-reduce 2026-06-13 实拉）：concatenation=合并全部 N 结果成列表；structured merge=每个子任务写到 distinct blackboard key、collector 读全部键；reduction=sum/consensus/LLM synthesis 聚合 N 输出；合并必须与 checkpointing 一起幂等——同输入跑两次合并产出相同输出；map-reduce 选 reduce 策略（single-pass/hierarchical/merge/vote）按 chunk 数与输出类型；size chunks conservatively（绝对 token 阈值非固定填充率）；partial failure 设计=单 chunk 重试+不完整结果优雅降级；多数团队低估合并步——三个研究摘要合并比生成更难。判据：**fan-in 合并三策略（拼接/黑板键/归约）；合并幂等；map-reduce 按块数与输出型选 reduce 策略+部分失败单块重试**。提升层：工作流/可复用 Skill。

**4. 并发隔离级按域选（SNAPSHOT/READ_COMMITTED/SERIALIZABLE）**（来源：Microsoft Agent Hypervisor spec 2026-08-15 + arXiv Position 2608.18092 实拉）：SNAPSHOT=完全隔离、agent 只见自己会话状态（低协调成本）；READ_COMMITTED=可读授权会话、写只给自己（中）；SERIALIZABLE=完整因果排序带 vector clocks+intent locks（高）；多 agent 编码系统改共享代码库需 serializability 防冲突编辑静默损坏；辩论系统（agent 操作大体不相交逻辑资源）可容忍 Read Committed 换吞吐；isolation=每 agent 执行"如同系统只有它"——不得观察他人未完成操作序列；consistency=并发操作不留冲突/矛盾状态。判据：**并发隔离级按域选（快照/读已提交/可串行化）；改共享状态需可串行化，不相交资源用弱隔离换吞吐**。提升层：工具/工作流/可复用 Skill。

**5. 事务化工具调用（工具调用当事务效果+控制永久化时机+Saga 补偿）**（来源：arXiv Atomix 2602.14849 实拉）：并行执行三类失败——speculative branches 并行计划执行真实工具调用、落选分支留残余副作用；contention 并发 agent 触同一资源、更新交错污染状态；crash recovery 重启后无法区分部分效果与已提交工作；解法=运行时把工具调用当 transactional effects、控制何时变永久、Saga 式补偿（沿用数据库原子性/隔离）；transactional boundaries 在多 agent 争用（2-8 并发×50 操作）下保正确性。判据：**并行/投机工具调用需事务边界（原子性+隔离）+Saga 补偿；落选分支副作用可回滚；重启后可区分已提交与部分效果**。提升层：工作流/可复用 Skill。

**6. 投机执行分支（并行候选分支+提交匹配分支；分支输出原子化）**（来源：Zylos speculative decoding 2026-05-31 + arXiv Second Thought 2608.13667 实拉）：speculative actions=并行化整个工作流分支而非单个工具调用——系统投机并行执行多个候选下一步、提交模型实际请求的那个分支；复杂推理任务 1.5-2.5× 加速、预测准确率合理时失败投机开销最小；Second Thought=分支与主线程动作序列化+工具执行并行解码、占满推理空闲窗口；分支输出格式化为 atomic thoughts 流（任意点中断仍有效）；observation 到达时合并=终止活跃分支+收获完成原子思维追加上下文。判据：**投机动作=并行执行候选分支+提交匹配分支；分支输出原子化（任意点中断仍有效）后合并**。提升层：工作流/可复用 Skill。

**7. 每工具并发预算（per-tool queue budget 可见压力+有界队列+共享 executor 上限）**（来源：negiadventures 2026-05-16 + moai.team 2026-07-25 + mcp-agent 2026-07-10 + CrewAI 2026-07-02 实拉）：单个全局队列隐藏哪个依赖实际过载——per-tool budgets 让压力可见+给刻意卸负载处（github: maxQueueDepth 120/maxConcurrent 8；browser: maxQueueDepth 20）；mcp-agent max_concurrent_activities 用共享 executor——上限跨整个 app；有界任务队列（Redis 1000 max pending）防单 agent 停滞时内存爆炸；FIFO 队列给用户可见流+显式优先级给运维/时限任务；ingress 队列+worker pool 解耦请求率与处理能力；Visibility Timeout 防重复处理（任务处理中锁定）。判据：**并发上限按工具分预算（每工具队列深度+并发）非单一全局；有界队列防停滞累积；FIFO 用户流+显式优先级+可见性超时**。提升层：工具/工作流/可复用 Skill。

**8. DAG 分层调度（拓扑分层：层内并行层间串行+dependsOn 就绪判据）**（来源：arXiv AdaptOrch 2602.16873 + entuit 2026-05-22 + hivemind 2026-08-11 + niteagent 2026-05-31 实拉）：DAG 划分为拓扑层 S1..Sm——层内子任务并行、层间串行；dependsOn 把 flat queue 变 DAG——任务仅在 dependsOn 全部 done 时才 ready（"review 不能在 codegen 完成前开始"）；DAG Plan & Execute=Planner 预先生成执行图/Executor 派发/Replanner 条件变化时适配——规划与执行分离使并行调用+系统化失败恢复；runTeam(team, goal)=协调 agent 分解目标、并行调度独立任务、综合结果；每波并发上限（max 4 concurrent subagents）防压垮执行环境。判据：**DAG 编排=拓扑分层（层内并行层间串行）+dependsOn 就绪判据+Planner/Executor/Replanner 分离+每波并发上限**。提升层：工作流/可复用 Skill。

**9. 共享状态工作板模式（全局可读+槽位限写+锁保护；多 agent 编程=分布式系统）**（来源：arXiv 2604.27221 2026-09-24 + 腾讯云分布式系统观 2026-04-21 实拉）：workers 经两个专用工具交互——read_workboard 观察全局进度+同伴输出、edit_workboard 追加结果到分配槽；写操作受文件锁保护且严格限于各 worker 标记区域、整个文档全局可读；读-写不对称实现动态协调；多 agent 编程本质是分布式系统问题——一致性（所有 agent 对共享状态认知一致）/可用性（随时可读写不被阻塞）/分区容错（context 天然隔离：每 agent 独立 context window 不共享内存=硬约束）。判据：**并行 agent 共享状态=工作板模式（全局可读+槽位限写+锁保护）；多 agent 编程按分布式系统三约束设计（隔离是硬约束）**。提升层：工作流/可复用 Skill。

**10. OS 式并发调度原语（条件变量计数信号量/MLFQ/僵尸回收）**（来源：arXiv HIVEMIND 2604.17111 + arXiv AgentRM 2603.13110 + 极客公园 2026-10-01 实拉）：显式计数器 A 由 asyncio.Condition 包 asyncio.Lock 保护——获取槽位等条件直到 A<Cmax、释放递减+notify(1)、Cmax 增时 notify_all() 唤醒全部 waiter 重查谓词（Cmax 减无需动作）；AgentRM=OS 式资源管理器——Agent Scheduler（MLFQ 带 zombie reaping+API 限流）/Context Lifecycle Manager（三层上下文存储+自适应压缩+休眠）；agent 请求量随任务阶段剧烈波动→推理基础设施关注冷启动/缓存/扩缩容/服务稳定性+整体成本（Cache 感知调度/KV Cache 存储/模型预热）。判据：**并发调度用 OS 原语（条件变量计数信号量/MLFQ/僵尸回收）；并发上限动态调时唤醒等待者重查谓词；agent 负载波动按基础设施治理**。提升层：工具/工作流。
