## 独点（10）

**1. Agent 认证四范式（OAuth 扩展复用/身份直通/托管身份/密码学身份）**（来源：IETF draft-klrc-aiagent-auth + draft-aap-oauth-profile + Microsoft MCP auth 2026-09-04 + IETF AAuth draft-hardt 2026-07-13 实拉）：不发明新协议——复用 WIMSE 架构+OAuth 2.0 家族扩展（AAP 为自主 agent 加结构化 claims 与验证规则，让系统能推理 agent 身份/任务上下文/操作约束/委派链/人工监督要求）；Microsoft MCP server 认证三方法——Entra 项目托管身份（无用户上下文持久化）/OAuth identity passthrough（用户交互式登录授权，用户上下文持久化）/Unauthenticated（仅当 MCP server 不需认证）；AAuth 每 agent 密码学身份（agent identifier `aauth:local@domain` 绑定签名密钥、well-known URL 发布、任何方验证——无预注册无共享秘密）。判据：**agent 认证不发明协议——OAuth 扩展（AAP claims）或托管身份或密码学身份三选；MCP server 认证三方法（托管身份/身份直通/unauth）按"用户上下文是否需要持久化"选**。提升层：工具/工作流。

**2. 连续对话式授权（JIT 替代一次性预授权）**（来源：IETF draft-chen-oauth-agent-authz-use-cases + draft-araut-transaction-tokens + draft-embesozzi-FiPA 实拉）：OAuth 模型是提前一次拿全部权限→agent 需要连续、交互式授权模型（权限按任务从高层意图演化动态 JIT 授予）；RAR（RFC 9396）——初始 consent 捕获的 authorization details 提供高保真上下文给下游 agentic enforcement，允许资源所有者授予细粒度动作权限（"Allow Agent to search only 'Research' folder"）编码进 token；FiPA 定义 H2A（Human-to-Agent）流的 JIT authorization+elicitations array 标准元数据格式描述 authenticator challenges。判据：**agent 授权=连续对话式 JIT（预授权一次拿全部→任务演化中动态授予）；RAR 细粒度动作授权（只搜 X 文件夹）编码进 token 供下游强制**。提升层：工作流/工具。

**3. one role per component per function（每组件每功能一角色）**（来源：AWS《AI agent identity and access management》2026-09-16 + Business Tech Navigator 2026-06-28 实拉）：每个 agent 组件（orchestrator、每个专家 agent、每个 MCP server）各有自己的 IAM role；role 不跨组件共享、不跨环境共享（dev/staging/prod 各自 role 集，命名约定区分+部署管线强制）；每个 role scoped 到组件特定功能所需最小权限（从零权限开始只加任务必需）；动态吊销——云 console 立即禁用 agent 身份不影响其他业务工作流（support agent 只读特定 S3 bucket+invoke 指定 Bedrock 模型、无 delete）。判据：**agent IAM=每组件每功能一角色（编排者/专家/MCP server 分开）、不跨组件不跨环境共享、从零权限加必需；吊销=禁身份即停不影响其他工作流**。提升层：工作流/工具。

**4. 委派交集原则（Effective Permissions = User ∩ Agent）**（来源：Red Hat《delegation beats impersonation》2026-05-21 + Mike Hacker 2026-05-11 + IETF attenuating tokens 2026-05-20 实拉）：委派时系统计算"用户可访问权限 ∩ agent 配置访问能力"的交集——任一方不能越界升级（delegation beats impersonation）；delegated permissions=应用可做与用户可做的交集（即使 agent 持 Files.Read 宽 scope 也受用户权限约束，agent 不能访问用户个人不能访问的）；capability-based 系统——authority 由不可伪造 token 携带 scoped 到特定操作，holder 可衰减（attenuate）但不能放大（amplify）。判据：**agent 有效权限=用户权限 ∩ agent 能力（委派优于冒充，双方都不能越界）；capability token 只可衰减不可放大**。提升层：工作流/模型。

**5. agent token 最小权限三件套（Scope+TTL+Purpose）**（来源：IETF draft-kiliram-trust-framework + Guardion 2026-07-08 + authsome 2026-05-29 实拉）：发给 agent 的 access token 必须约束三件——Scope（资源/操作集，如"读 project X 消息/调用 workflow Y"）/Validity period（短生命周期分钟到小时，限制泄露暴露窗口）/Purpose 或 task context；golden rule=绝不授予宽泛 "Read All" scope——权限绑定具体细粒度工具（server:read_status，明确拒绝 delete）；不跨 agent 复用同一身份（每 agent 每账户独立凭据，含爆炸半径+审计日志可读）。判据：**agent token 三约束=细粒度 scope（绑具体工具非 Read All）+短 TTL（分钟到小时）+任务上下文；每 agent 独立凭据，被攻破爆炸半径限 service account**。提升层：工具/工作流。

**6. 分层权限作用域（service identity / transaction / user identity 三层）**（来源：AWS Well-Architected Agentic Lens AGENTSEC03-BP03 2026-09-23 + DEV 2026-09-22 实拉）：permission scoping 按层放——broad capability limits 在 service identity（IAM role、permission boundary）；per-operation 约束在 transaction（session policy、session tags、IAM Conditions）；user-context 约束在 user identity（token-based authorization 在资源侧求值）；agent 当不可信操作者——RBAC 定粗粒度角色、ABAC 按客户账户/文件夹路径/项目 ID/环境/文档标签收窄。判据：**权限分层放——宽能力限在身份层（role/boundary）、单操作约束在事务层（session policy/tags/conditions）、用户上下文在身份层（资源侧求值）；RBAC 粗角色+ABAC 细属性（客户/路径/项目/环境/标签）**。提升层：工作流/工具。

**7. 动态凭据替代静态密钥（每请求唯一 key + lease 自动过期）**（来源：Zylos 2026-05-07 + aegis 2026-08-24 + authsome 2026-05-29 实拉）：Vault 动态凭据模式——`vault write openai/creds/my-agent-role ttl="1h" max_ttl="24h"`，每个请求产生唯一 API key+lease ID 自动过期；agent 永不持有长期凭据（被攻破=拿到几小时过期 token 而非永久可用）；JIT credential generation+dynamic capability tokens+自动化密码学轮换（企业强制 zero-trust secrets：永久 access token 换 JIT 生成）；注意 Vault 32 天默认 TTL——必须显式设置短 TTL。判据：**动态凭据——每请求唯一 key+TTL 自动过期（agent 不持长期凭据）；JIT 生成替代静态存储；Vault 默认 32 天 TTL 显式设短**。提升层：工具/工作流。

**8. 密钥生命周期（每 agent 独立 key + rotation 策略 + offboarding）**（来源：Systems Hardening 2026-04-29 + how2 2026-02-22 + JumpServer 2026-04-22 + API7 2026-05-20 实拉）：跨团队/跨 agent 归因要 per-team/per-agent keys（审计"key abc123 made a request"→立刻知道是 payments team 的）；rotation policy 三问=什么轮换/何时轮换/如何无停机替换（零停机轮换=双活切换）；offboarding——员工离开其个人签发 keys 必须枚举+轮换，hook 进 IDP；gateway 运行时从 vault 取 key（key 永不出现配置文件或版本控制）；static secrets 是负债（被静默外泄可无限复用→自动化轮换）。判据：**密钥生命周期=每团队/每 agent 独立 key（审计可归因）、rotation 策略（什么/何时/如何无停机）、offboarding 枚举轮换 hook IDP、key 不出配置文件（运行时 vault 取）**。提升层：工作流/工具。

**9. 凭据访问四纪律（集中 vault + 细粒度策略 + 审计 + 明文临解析）**（来源：JumpServer 2026-04-22 + ArchMan 2026-05-24 + granite 2026-09-22 + Truto 2026-04-29 实拉）：vault 用细粒度访问策略（每个身份只能读写特定 secret，避免宽泛 namespace 策略）+审计记录读操作；加密 at rest AES-256-GCM、加密密钥环境变量管理永不进源码；明文只在出站 API 调用瞬间内部解析（不落盘不日志）；并发 token refresh 错误模式——并发刷新触发上游 429 或 vendor 因并发刷新失效 refresh token（刷新要串行化/节流）。判据：**凭据访问=集中 vault+细粒度策略（禁宽 namespace）+审计读+明文仅出站瞬间解析；token 刷新串行化（并发刷新致 429/refresh token 失效）**。提升层：工作流/工具。

**10. Agent 服务账号模型（agent 用服务身份不用用户身份）**（来源：AgentixForce 2026-05-06 + Google Agent Registry 2026-09-24 + granite 2026-09-22 实拉）：agent 身份模型=svc-research-agent@proj.iam scopes read:search/read:docs——least privilege by design、rotation auto 90 天、audit 全动作、revoke=disable svc acct agent stops、agent 永不见用户凭据（blast radius 限 service account scope）；Google 用 Agent Identity 提供内置云认证+ADC（Application Default Credentials）或 service accounts 给 agent 自身身份；平台 env var 存储三弱点——审计记"值被改"不记改了什么/谁改的、难回溯、无细粒度权限。判据：**agent 用服务身份不用用户身份（ADC/托管身份）；账号模型=scoped 服务账号+自动轮换+全量审计+禁用即停+不见用户凭据；平台 env var 不满足审计（改了什么/谁改的不可见）**。提升层：工作流/可复用 Skill。
