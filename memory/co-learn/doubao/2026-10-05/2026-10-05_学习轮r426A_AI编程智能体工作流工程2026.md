## 落地 5 独点（每点标注提升层）

### 1. 验证循环（verification loop）=自我验证最高杠杆实践，可打包成 skill（可复用 Skill/工作流）
来源：claude.com-verification-loops / code.claude.com-best-practices / anthropic-help-center-advanced / anthropic-long-running-claude
- **给 agent 一个可运行的检查**（测试/构建/截图对比）——"Claude 在看起来完成时停止；没有可运行检查则'看起来完成'是唯一信号，**你就成了验证循环**（每个错误等你发现）"。
- **验证循环可打包成 skills**：每会话自动应用同一批检查，不靠人记得跑。
- **Ralph loop**：for 循环把声称完成的 agent 踢回上下文问"真做完了吗"——长任务 agent 会承认没达标继续干到 spec；同类 GSD 与 Claude Code 原生 /loop。
- 判据：agent 工作流必配可执行 check；把验证循环固化为 skill/自动化而非提示词叮嘱。

### 2. AGENTS.md/CLAUDE.md 工程规格：跨工具规范 + command-first + closure criteria（可复用 Skill/工具）
来源：cskwork-agents-md-cross-tool / iuriio-agents-field-guide / morphllm-agents-spec / codersera-agents-skills-guide / augmentcode-build-agents-md / nishilbhave-claude-workflow
- **AGENTS.md=vendor-neutral 跨工具规格**（OpenAI Codex/Cursor/Copilot 原生读）；**CLAUDE.md=Claude Code 自动加载**——两个都放，任何 CLI 无分叉。
- **只写 agent 无法独立发现的内容**：仓库规矩（分支命名/PR 约定）、架构决策、环境要求（env 变量）、常见坑/非显然行为；**别写逐文件代码库描述与"写干净代码"这类自明实践**。
- **command-first**：确切可执行 shell 串（`pnpm turbo run test --filter <project>` 胜过"用 monorepo 的测试运行器"）；**closure criteria**："完成=typecheck 过、pnpm test 绿、无新 any 类型"。
- **好 AGENTS.md=少 40% 后续纠正**（Anthropic 用量数据）；建议 <120 行（每会话加载）。
- 判据：AGENTS.md 只收 agent 猜不到的命令/边界/真相源/完成标准；命令写全串、完成写可验证条件。

### 3. 项目记忆分层：AGENTS.md（稳定）+ SESSION_NOTES/scratchpad（会话学习）分离（工作流/可复用 Skill）
来源：pimenov-agents-session-notes / openclawskills-agent-context / cc-bruniaux-agents
- **分层回答不同问题**：AGENTS.md=如何在此项目工作（命令/边界/真相源/安全/完成标准，提交共享）；**SESSION_NOTES.md=最近发生了什么**（变更/检查/决策/未知/下一步）。
- **OpenClaw 双文件**：`.agents.md`=真相源（提交共享、常驻 prompt、<120 行、压缩的项目知识）；`.agents.local.md`=个人 scratchpad（gitignored、每会话增长记录所学）。
- **记忆作用域三档**：user（`~/.claude/agent-memory/` 跨项目学习）/ project（`.claude/agent-memory/` 项目共享可 git）/ local（`.claude/agent-memory-local/` 不提交）。
- 判据：稳定知识进共享文件（AGENTS.md），会话学习进 gitignored scratchpad——不混层。

### 4. 多文件编辑纪律：surgical diff + prompt 公式 + 阶段间验证（工具/工作流）
来源：ismartanji-ai-coding-assistants / baeseokjae-cursor-best-practices / codex-danielvaughan-multi-file / augmentcode-multi-agent-workspace / foundrysoft-multi-file-refactor
- **Surgical diff 引擎**：5-20 文件同时生成精准 diff，**保留现有格式/import/注释**——而不是整文件重生成。
- **高绩效 prompt 公式**：①具体文件路径 ②要跟随的模式带**具体示例** ③明确**不要改什么** ④**可测试的完成条件**——"重构 auth 模块"这类模糊 prompt 因缺约束产出不稳定。
- **阶段间验证**：接口改动后先让测试过，再更新消费方（verification is needed between stages）。
- **多 agent 并行编码**：只有 spec-scoped 独立任务才可靠——git worktree 隔离每个 agent、require tests+自动门禁再合并、顺序合并分支（六种协调模式防文件碰撞/重复实现/语义漂移）。
- 判据：多文件改动用 surgical diff；prompt 带路径+示例+禁改清单+完成条件；跨阶段先验证再推进。

### 5. TDD 闭环作为 agent 工作流 + 上下文管理约束（模型/工作流）
来源：prod.cursor-agent-best-practices / kanopylabs-agentic-workflows / hasanarief-agentic-coding / dev-vidfoil-ai-coding-tricks
- **明确 TDD 序列**：先写基于期望输入/输出对的测试→跑测试**确认失败**→**明确禁止写实现**→满意后提交测试→写通过的实现——明说 TDD 避免 agent 为不存在的功能造 mock 实现。
- **测试结果是 ground truth**：失败时两选项=代码错要修 或 测试错要调——"不是生成测试文件希望它能跑"，是迭代闭环。
- **上下文管理约束**（核心约束内化后最佳实践都是推论）：指令文件保持短（每会话加载）；**研究委托子 agent**（探索消耗主会话上下文）；**任务间清上下文**（昨天失败的路径污染今天的尝试）；调查窄范围（无界"调查 X"会读几百文件）。
- **复杂重构幻觉率近零**=提供接口/签名而非完整实现文件。
- 判据：agent 写代码走 TDD 闭环（测试失败先行）；研究/探索子 agent 化；任务切换清上下文；上下文敏感内容传签名不传全文。
