## 落地 5 独点（每点标注提升层）

### 1. 三层 Span 层级 + 全消息历史 + prompt 放 event 不放 attribute（工具）
来源：mlflow-pipelines / inference-llm-tracing / cubeapm-monitor / radarai-observability / ailearningguides-observability
- **三层 span 层级**：顶部 span=agent session/user turn → reasoning spans=每个规划/思考步 → tool call spans=触发它的 reasoning span 的子节点、结果记在 span attribute 上——**分布式 parent-child span 让你重建"哪个推理步选了哪个工具+结果是什么"**；sub-agent 的 spans 也做父 agent span 的孩子（同层级贯穿）。
- **全消息历史记录**：每个消息（system/user/assistant/tool）记成索引属性（llm.input_messages.0.message.role/content，输出同构镜像）——回答最基本问题"**模型到底看到了什么**"（坏输出常因模型看到的≠你以为它看到的）。
- **prompt 放 span event 不放 attribute**：大 payload 会压垮某些 backend——content 级别数据走 event，标量元数据（model/token 数）走 attribute。
- **每 LLM 调用前后结构化日志**：prompt/output/token usage/timestamp（JSON），字段含 model version/temperature/tool-calling 参数——静默失败（HTTP 200 但输出错/偏/无依据）只有靠这些才能定位。
- 判据：一个 user turn 产出一棵树（session→reasoning→tool）；消息全文入索引属性；大 payload 走 event。

### 2. OTel GenAI 语义约定 + 五信号从 span attributes 卷取（工作流/工具）
来源：aws-agentperf / mlflow-pipelines / futureagi-monitoring / datarekha-model-monitoring / aiworkflowlab-otel
- **OTel GenAI semantic conventions（GA 2026-05）**：标准属性 gen_ai.system / gen_ai.request.model / gen_ai.usage.input_tokens / gen_ai.usage.output_tokens——**跨厂商一致**（Arize/Langfuse/Helicone/Phoenix/Honeycomb/Datadog 都消费），避免 telemetry vendor lock-in。
- **两类指标分开记**：operational metrics（latency p95/p99、error rate、cache hit rate、guardrail block rate）+ **quality metric（eval score rolling 均值）**——ops 管"系统活着吗"，quality 管"输出对吗"。
- **成本按会话/用户/路由记**：p95/p99 token 数才是月账单真凶（均值掩盖长尾）；per-route 预算超限告警。
- **五信号成熟度条（2026 门槛）**：latency/error/cost/retrieval-quality（recall@k、context_relevance 在已知 eval set 上掉=retrieval 回归）/quality——**全部从 span attributes 上卷**，告警与调试 trace 用同一数据源。
- 判据：埋点属性名用 OTel GenAI 约定；ops 与 quality 指标两套告警分开；所有监控信号同一数据源（span attributes）。

### 3. 时间旅行调试：event sourcing + durable execution + MITM 隔离重放（工具）
来源：zylos-replay / arxiv-agrepl / dev-to-time-travel / pypi-agent-strace / agentops
- **三学科合成**：event sourcing（append-only 日志作 truth）+durable execution（**memoize 副作用**做容错）+interactive debugger（任意断点状态检视/修改）——每次 agent 执行都是可回卷/分叉/从中间点重跑的事件日志。
- **工具结果 memoization 重放**：重放遇到同一工具+同一参数，**不真正执行外部工具，用记录的返回结果**（副作用免重复执行，重放才隔离）。
- **agrepl（确定性重放）**：MITM 代理在 transport 层拦截所有外部交互→序列化成结构化执行 traces→**严格隔离环境零出站网络重放**（request-key 匹配函数 K 保证请求对应）；现有观测平台能记日志但无法隔离复现 run，这补上那一环。
- **agent-strace 实用形态**：replay 会话到终端/HTML；`replay --diff` 并排会话对比（tool args+output delta）——改 prompt/模型后 A/B 复跑对比行为差异。
- 判据：可观测平台必须支持"回卷-分叉-重跑"；重放时副作用用记录值不真执行；改任何配置后 A/B 复跑对比 diff。

### 4. 四类漂移检测 + Online Shadow Eval 抓静默 drift（工作流）
来源：futureagi-glossary / tabnews-llmops / futureagi-monitoring
- **四类 drift 都要盯**：input drift（用户 prompt 分布——易测但信号最低）+output drift（响应长度/拒答率/风格——**高信号，provider refresh 先在这里显形**）+retrieval drift（向量库 reindex 改变 chunk 排名——**静默毁 RAG 质量**）+evaluator drift（groundedness rolling mean 滑动——judge 自己漂了）。
- **Online evals（shadow）是检测静默模型 drift 的唯一方式**：定时把 golden set 对生产系统跑一遍（旁路不挡流量）——drift 的判据是 golden set 通过率下降，不是人报 bug。
- **自动回滚基于质量退化**：eval score rolling 跌破阈值触发自动回滚（不是靠 HTTP 错误，因为 LLM 错误常带 200）。
- 判据：四类 drift 各设监控（input/output/retrieval/evaluator）；golden set 定时旁路跑生产；回滚触发用 eval 质量指标而非 HTTP 状态。

### 5. Golden-Set Output Drift 日常巡检（可复用 Skill）
来源：velsof-hidden-metrics
- **Metric 7（抓 model rot）**：钉 50-100 个代表输入，**每日定时跑生产系统**，输出对比基线——**embedding 语义相似度 + 几条硬规则检查**（"还引用同一个来源吗？还得到同一个数值答案吗？"）。
- 为什么有效：provider 换模型/调参后"看似正常实则退化"只有固定输入集的输出对比能抓；50-100 条足够（代表分布而非穷举）。
- 与四类 drift 的分工：drift 监控管**线上实时信号**，本条管**每日离线快照对比**——两者互补，缺一漏一半。
- 判据：固定 50-100 代表输入；每日跑；语义相似+硬规则双通道判漂移。
