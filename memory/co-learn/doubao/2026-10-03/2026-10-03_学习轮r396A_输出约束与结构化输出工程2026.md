## 落地 5 独点（每点标注提升层）

### 1. 约束解码与语法编译：token 掩码机制 + 严格条件 + refusal 程序化检测（工具）
来源：zylos / ai-tldr / devtoollab / stochasticsandbox / OpenAI 官方
- **约束解码（constrained decoding）**=生成时每步把 schema 编译成形式文法，跟踪生成位置，**掩码掉任何会让输出违反 schema 的 token**——schema 违规数学上不可能（不只是不太可能）；XGrammar（CMU）token 掩码生成 <40μs、最高 100x 加速（vocab partitioning+语法缓存，vLLM/SGLang 默认后端）。
- **strict schema 硬条件**：`strict: true` 时 OpenAPI 把 JSON Schema 编译成上下文无关文法并掩码 logits；**schema 必须满足**=每个对象层 `additionalProperties: false`、所有字段列在 `required`、只支持 JSON Schema 子集（无 anyOf/patternProperties 等）。
- **refusal 程序化检测**：OpenAI 结构化输出响应含独立 `refusal` 字符串值——程序可检测"模型拒绝了"而非"输出匹配 schema"；无 refusal 且 schema 合规才算成功，**拒绝与格式违规是两个必须分开处理的状态**。

### 2. 原生 API vs 约束解码库取舍表：100% 合规≠全覆盖，约束解码有准确率代价（工具）
来源：awesomeagents / kanopy / promptquorum / niteagent
- **原生 API（OpenAI/Gemini）**：对支持的 schema 100% 合规（数学保证），但**覆盖的 schema 类型更少**；JSONSchemaBench（10K 真实 schema）Guidance 覆盖 96%，原生 API 覆盖类型更窄。
- **约束解码库**：覆盖复杂嵌套 schema 更好，但有可测延迟成本——**Outlines 编译文法 3-8 秒 vs Guidance 近零编译时间**（选库看编译延迟是否在请求热路径）。
- **约束解码降准确率**：forcing JSON via constrained decoding 在函数调用基准上**降 2.26 个百分点**——BAML schema-aligned parsing 93.63% vs OpenAI strict 91.37%（同一 BFCL）；约束有成本，不是白拿的确定性。
- 判据：简单 schema 用原生 API（免费确定性）；复杂嵌套/本地模型用库（付编译延迟与准确率代价）；准确率敏感场景考虑 schema-aligned 解析而非纯解码。

### 3. 工具用强制模式（tool-use coercion）+ 工具调用五层可靠性栈（工作流）
来源：jatinbansal / thepromptbench / richards.ai
- **tool-use coercion**：定义单个工具（如 `submit_invoice`），其 `input_schema` 即目标输出 schema，设 `tool_choice` 强制模型调用它——**工具参数即结构化输出**；该模式在**每个**做 schema 校验工具调用的 provider 上都可用（Anthropic 主推方案：不是响应格式开关而是工具）。
- **五层可靠性栈**：① **syntactic validity**（可解析 JSON/识别工具调用格式——JSON mode+基础 parser）→ ② **schema validity**（符合声明 schema：必填字段/enum/类型/嵌套——Structured Outputs+约束解码）→ ③ **语义/值有效性**（值级正确——值验证器/业务规则）→ ④ 安全/策略 → ⑤ 下游消费；**逐层加固，别只停在"能解析"**。
- 反模式：free-form JSON 手动解析（静默损坏源头——错类型/缺字段/幻觉工具名）；只查格式不查值。

### 4. validate-and-repair：原生优先 + 解析校验 + 校验错误回喂重试 + 值验证（工作流）
来源：aiwisdom / zalt-guardrails / agentpatterns
- **原生优先**：先用 provider 原生结构化输出（OpenAI `response_format: json_schema`/Anthropic tool-use/Gemini JSON mode）——现代模型失败率 <1%，这是第一道且最高杠杆的防线。
- **validate-and-repair 兜底**：原生之后仍用 Zod/Pydantic 解析校验；**失败时把校验错误回喂给模型并重试**（`maxRetries: 2`）——不是简单重跑，是带错误信息的修复循环。
- **结构校验 ≠ 值校验**：JSON mode/Structured Outputs 只在生成期强制形状，**值级正确（类型合理/enum 合法/范围达标/无幻觉枚举）仍需生成后独立验证**——"通常返回合法 JSON"不是保证。
- 判据：任何下游代码触碰模型输出前，先过结构校验+值校验；修复循环设重试上限，超限走人工/降级路径。

### 5. Pydantic 契约驱动输出校验（structured-output-validation 模式）（可复用 Skill）
来源：lobehub（paulpas-agent-skill-router structured-output-validation）/ langchain / neuralbase
- **契约驱动**：输出声明为 Pydantic BaseModel 子类（字段带 description），用 `model_json_schema()` 生成 JSON Schema 供函数调用/API 契约——**一份模型定义双用：LLM 侧 schema + 应用侧类型**。
- **确定性解析**：`.model_validate_json()` 做确定性解析（非 json.loads 后手工校验），配合自定义 field/model validators 做语义约束。
- **自动修复循环**：校验失败把 validator 错误信息回喂 LLM 重试——校验错误成为 LLM 的下一次输入，形成闭环；声明式模式可复现（Reproducible pattern），agent 与工具间 type-safe 通信。
- 判据：凡 agent↔工具/agent↔agent 通信，输出必须声明为类型化契约（schema），解析必须走确定性 validate，失败必须回喂修复而非静默重试。
