## 落地 5 独点（每点标注提升层）

### 1. Tool calling is the new API design；Agent-ready API 契约（可复用 Skill/工具）
来源：emresavas-tool-calling / ietf-agent-friendly-http / arxiv-2605.10555-agent-first / niteagent-agent-ready
- **agent 直接消费 API——工具调用就是新 API 设计**：agent 是真实调用方，API 要为"机器读"设计，不只是为人。
- **幂等键**：每个 mutating 端点接受 `Idempotency-Key` 头（或 query 参数），定义窗口内（Stripe/Square 用 **24 小时**）重复键返回原结果无副作用——"可被任意调用任意次、副作用只发生一次"。
- **Agent-first tool APIs**：写/提交模式工具强制幂等，**键从工具声明的 idempotency_key_fields（输入参数子集）计算**，重复键在窗口内返回缓存结果。
- **IETF agent-friendly HTTP API profile**（draft-gaikwad）：有副作用的操作支持客户端提供的幂等键=官方文档化方向。
- 判据：给 agent 用的 API 先补幂等键；工具 schema 声明 idempotency_key_fields；API 评审按"agent 会重试"假设。

### 2. 幂等键的两种构造与 exactly-once 不变式（工具/工作流）
来源：tomodahinata-function-calling / tianpan-idempotency / dev-robinzzz-idempotency-gate / markaicode-agent-architecture
- **两种构造**：①`tool name + normalized arguments` 确定性哈希（基础做法）；②**业务级唯一键（order ID/request ID）优先**——**纯参数构造会吞掉两次有意订单**。
- **Invariant I1**：对任一由幂等键 k 标识的逻辑工具效应 E，**E 在现实中的副作用最多发生一次**，无论调用被投递多少次——agent 框架常把工具调用当 chat 形消息处理，缺此不变式。
- **exactly-once 语义**：跨所有 OpenAI API 调用与工具队列携带 UUID；**每 agent 步 token 预算=模型 max_tokens 的 70%**，超了返回部分状态经队列续跑。
- 判据：有业务唯一键时用它做幂等键（参数哈希兜底）；设计工具 API 先写 I1 不变式；agent 循环每步设 token 预算+续跑机制。

### 3. 流式=LLM API 设计最重要模式；最常 bug=缓冲（模型/工具）
来源：devweekends-api-design / kunalganglani-streaming / folarin-streaming-e2e / gyanbyte-streaming-production
- **没有流式用户盯 5-20 秒空白屏**；流式首 token 200-500ms——**感知延迟降 80-90%**，这是 ChatGPT 响应感的来源。
- **SSE 比 WebSocket 简单、能穿代理**（EventSource/fetch ReadableStream）；**永远备非流式 fallback**。
- **最常见的 bug=缓冲**：你的框架/代理/gzip 层把整个响应收集完再 flush——漂亮 token 流变成一块到达。修法=流 generator+响应禁缓冲。
- 判据：LLM 端点默认流式；部署后查 nginx/gzip 是否缓冲；必须有非流式降级路径。

### 4. 背压与取消：三层传播 + mid-stream 错误边界（工具/工作流）
来源：aiworkflowlab-sse-backpressure / llmversus-streaming-pipeline / nisai-streaming / codenicely-stream-react / kanopylabs-streaming / flaviocopes-streaming-sse / theneuralbase-error-mid-stream
- **背压**：写端 `await drain`（socket full 时）→for-await 暂停→上游 SDK 迭代器暂停→**OpenAI 的 HTTP/2 流停止拉取**——Web Streams 拉式 ReadableStream 原生处理；WebSocket 场景用 token bucket+最大缓冲；**有界队列**（缓冲到 Redis/S3/慢客户端时）。
- **取消必须三层传播**：浏览器 `AbortController.abort()`→后端代理**把 abort 转发到上游 LLM 调用**（把同一 abort signal 传进 SDK 调用，真关上游 HTTP 连接）——**否则关闭的标签页还在烧 token**。
- **mid-stream 错误边界**：token generator 包 try-catch→发 SSE error 事件（客户端可解析重试）→可观测 trace 以失败态完成——把隐形崩溃变成可追踪可恢复事件。
- 判据：流式管线接背压（drain/暂停/有界队列）；取消从客户端传到 provider 连接；生成器内 try-catch+错误事件+trace 失败态。

### 5. 流式事件谱系与协议标准化（工具/可复用 Skill）
来源：openresponses-spec / ietf-agentproto-llm-stream / aiworkflowlab-ssse / datallmlab-stream
- **openresponses 规范**：流式响应 `Content-Type: text/event-stream`，data 为 JSON 编码串，**终事件必须是字面量 [DONE]**，event 字段必须匹配类型。
- **IETF agentproto draft**：定义 LLM 推理流式标准线上格式——`application/llm-request+json` 请求包络+**响应事件分类学**+JSON 事件包络 schema——让中间件/编排/合规工具用**单一协议契约**处理任意符合供应商的 AI 推理流量（SSE 传输不变，只标准化内部 JSON 负载）。
- **供应商类型化事件**：Anthropic 发类型化事件（message_start/…）——比纯 token 流信息更全。
- 判据：自建流式 API 对齐 openresponses 事件谱系（[DONE] 终事件+类型化 event）；跨供应商网关用标准化线上格式；客户端按事件类型处理不只拼 token。
