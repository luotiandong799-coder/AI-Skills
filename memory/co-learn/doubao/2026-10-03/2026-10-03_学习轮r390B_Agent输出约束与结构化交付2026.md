## 落地 7 独点（每点标注提升层）

### 1. 结构化输出五层强制：从 prompt 到约束解码（工具）
来源：zylos-structured-output-constrained-decoding / kanopy-structured-output-patterns / prompt-architects-json-prompts / theneuralbase-guaranteed-schema / logic-structured-outputs-guide / channel-structured-outputs
- **五层递增**：Layer 1 prompt 说明（最弱）；Layer 2 JSON mode（保证语法不保证结构）；Layer 3 function calling/tool use（参数类型约束，仍可能类型错位如 passengers:"2" vs 2）；Layer 4 grammar-constrained decoding（推理引擎把 schema 编译成形式文法 FSM/CFG/PDA，每解码步掩码非法 token——模型物理上不能产生非法 token，这是所有 provider "100% 可靠" 声明的机制；开源=Outlines/XGrammar/llguidance/llama.cpp GBNF）；Layer 5 内容线校验（业务规则/DB 存在性/RAG 事实）。
- **平台现状**：OpenAI structured_outputs（json_schema strict，token 级约束解码，数学上不可能违例，schema 编译 +10-15ms 延迟）；Claude strict tool use + JSON outputs（output_config.format）；Gemini response schema；2026 约束解码=GPT-5 family + Gemini 2.5；Claude 用 prompt+validation+retry。
- **schema 强制≠正确性**：约束解码保证结构不保证语义；"bouncer 类比"只对真约束解码成立——很多 API 仍是 parse-then-validate，生产环境先验证模型/provider 真支持 schema 强制再删错误处理。
- **业界共识**：生产一律 strict mode/Structured Outputs；无法事先提供 schema 才用 JSON mode；自由文本当最后手段。
- 判据：先确定你拿到的是"结构保证"还是"语法保证"——决定错误处理要不要留。

### 2. 三层验证 + repair-then-retry 阶梯（工作流）
来源：supergood-validation-layer / ai-tldr-output-validation / ai-tldr-schema-validation / velsof-output-validation-patterns / agentmelt-structured-output / cadence-structured-outputs
- **三层验证**：Tier1 schema/type（结构化输出覆盖大部分）；Tier2 semantic（字段级验证器/格式检查/范围约束/跨字段逻辑）；Tier3 business logic（域规则/策略约束/人环阈值）——schema 有效但仍可能损坏数据/触发坏决策/制造责任。
- **失败处理三选一按序**：retry with error feedback → fallback value → escalate human（生产系统三件都用，按序）。
- **repair-first**：修复=启发式补丁（json_repair 补缺失逗号/未转义引号/截断结构，零模型调用）；重试=带验证错误再请求模型自纠——实际两者都做：先 repair（快、免费）再 retry。
- **实证**：parser-feedback retry 恢复 78% 畸形结构化输出 vs 盲 temperature-bumped retry 仅 31%（Anthropic Engineering 2026）；解析失败占 30-60% 生产 agent bug，validation retry 减下游崩溃 90%+。
- **重试纪律**：指数退避（2s/4s/8s）而非立即重试——相同提示常产生相同非法输出，重试必须改上下文/换措辞；max_retries=2-3，超 3 次 token 浪费（边际收益递减）。
- **type-coercion guardrails**：money/date/percentage 的默认 Python/JS 强转是隐形杀手（1500%-discount 事故）——数值型字段显式验证范围与类型。
- 判据：schema 验证通过≠安全通过——Tier2/Tier3 管"对了但错了"；修复先于重试、重试必带错误反馈。

### 3. 输出自纠错四模式：Self-Refine / Structured Reflection / CRITIC / Rubric grader（模型/工作流）
来源：selfrefine-info / arxiv-2509.18847-structured-reflection / langchain-rubrics-deepagents / yennj-self-refine-critic / ai-tldr-agent-reflection / emersonbraun-self-critique
- **Self-Refine**：单模型三阶段闭环 Generate→Feedback（同一模型当批评者多维审查：逻辑/事实/格式，给可操作修改建议）→Refine；无需监督数据/RL。
- **Structured Reflection**（arxiv 2509.18847）：把"从错误到修复"变成一等可控可训练动作——模型基于上一步证据诊断错误、提出正确可执行的 follow-up 调用；DAPO+GSPO 目标函数训练、工具调用定制奖励。
- **CRITIC 修正**：LLM 自验证硬事实不行（Self-Refine 的 catch）——verify 步必须走外部工具（搜索/代码解释器/计算器/测试运行器）；2026 默认=generate, verify (externally when possible), refine, stop when verifier passes。
- **Rubrics for DeepAgents**（LangChain）：独立 grader sub-agent 在 agent run 结束前按 rubric 评分；全过则收尾，未过则把 per-criterion 反馈注入对话再跑一轮；循环终止于 satisfied 或配置迭代上限。
- **反射循环**：critique 需要具体可测判据（"SQL 能跑吗、返回题目要的列吗"可执行；"这好吗"不可执行）——loop 是包在模型外的管道，不是模型内特性。
- 判据：自纠错的验证步默认外部化；rubric 判据必须机器可测；迭代上限与终止条件提前定。

### 4. 工具调用参数验证与修复：边界 schema + 结构化错误反馈（工具）
来源：aws-bedrock-strands-guardrails / google-adk-safety / microsoft-agent-safety / openai-agents-js-tools / zenodo-toolclad / arxiv-2605.02682-hybrid-inspection / openlegion-tool-use / autobe-function-calling-harness
- **调用前参数验证**：BeforeToolCall 检查点验证工具输入参数（不在白名单的工具跳过）；Google ADK 用户 ID 匹配校验（参数中的 user_id 与会话期望不符→返回 error 对象阻止执行）；Microsoft type/range/string length/path traversal 显式约束（文件路径解析到绝对路径检查允许目录，不查 ".." 序列）。
- **ToolClad 声明式契约**：把参数验证推到类型层——.clad.toml 声明类型化参数（path/hostname/scope-bounded string）+验证规则+命令模板+执行后端；validator 在工具派发前拒绝契约无法表达的参数——元字符注入/命令替换/path traversal/scope-target 同形 glyph **结构上不可表达**而非靠检测。
- **Parameter Integrity Enforcement**：混合检查比对出站工具调用的具体参数名/值与 LLM 指定的对照，block 不匹配调用——防应用在途篡改参数劫持合法交易（转账改收款方）。
- **工具输出也定义 schema**：空结果集/null body/200 响应里埋错误都会误导 agent——每个工具定义输出 schema，原始响应验证后以结构化错误进上下文，不把畸形输出直接传进上下文。
- **Repair 模块纪律**（OpenClaw attempt.tool-call-argument-repair.ts）：best-effort 修常见 JSON 破坏（截断字符串/缺右括号/尾逗号），不猜缺失值；修失败返回结构化错误。
- **Function calling harness 四步**：request with feedback → lenient parsing + type coercion → schema validation → 失败反馈回 LLM 继续（6.75%→100% 案例）。
- **结构化错误反馈**：验证失败不返回通用字符串错误——返回显式路径错误 payload（status/code=SCHEMA_VIOLATION/details=[{instancePath, message}]），模型可精确定位并自纠。
- 判据：工具调用验证三层（调用前参数/执行后输出/错误结构化回喂）；能推到类型层的契约（类型级拒绝）优于运行时检测。

### 5. 输出层安全：脱敏、strip 未知字段、注入残留扫描（工具/工作流）
来源：devto-zero-trust-ai-outputs / dailyaiworld-agentic-guardrails / billdx-securing-agents / stochasticsandbox-injection-prevention / botmonster-guardrails / futureagi-llm-security / openlegion-output-guardrails
- **输出层是四层攻击面的最后一层**（futureagi）：Input（用户提示→直接注入/jailbreak）/ Retrieval（chunk→间接注入/投毒文档）/ Tool-call（工具调用→沙箱逃逸/密钥外泄/confused deputy）/ Output（响应回程→PII/PHI 泄漏/有害内容/系统提示词泄漏）——逐层堆叠防御。
- **输出脱敏器**：扫描 agent 响应的 PII 模式/凭据泄漏/内部系统引用（exfiltration patterns 正则表）；PII 正则=SSN/信用卡 Luhn 校验 13-19 位/email/phone/API key 模式（sk-…）。
- **结构输出压缩攻击面**：强制结构化输出减少自由文本攻击面；交付前 schema 验证+**strip 未知字段**（响应里意外的字段删掉）+扫描 URL/代码/注入残留。
- **Zero-trust sanitizer**：独立 security validator 模型接收候选响应判定是否含注入指令/敏感泄漏，通过才放行（双模型判官，与 §Dual-LLM 同族）。
- **四层 guardrail**（neelsoumya）：Layer1 input（validate/sanitise/classify/block）→ LLM call → Layer2 output（parse/validate schema/fact-check/redact）→ Layer3 operational（rate limiting/cost caps/retry）→ Layer4 运维。
- 判据：输出不信任（zero-trust）——schema 验证+脱敏+未知字段 strip 三件套在响应到达用户/下游前全过。

### 6. 输出契约版本化：嵌入版本 + MCP versioning spec + expand-contract（可复用 Skill）
来源：supergood-output-contracts / theneuralbase-schema-versioning / theneuralbase-backward-compatible / mcp-schema-evolution / koder-schema-migrations / archman-schema-evolution / lobehub-structured-output-validation
- **输出 schema 当 API 版本对待**：agent A 改输出 schema、agent B 还等旧 shape 是最高频烧点——把 schema 版本嵌入输出（_schema_version: "1.2"）。
- **MCP versioning spec**（gRPC/OpenAPI 启发）：version 字段（major.minor）；additive-only minor bump（只加新可选字段）；major bump 条件=参数改名/删除/类型变更/响应形状变化；工具列表带 deprecated:true + sunset_date；多版本 server 同时服务 v1&v2。
- **两失败模式防护**：旧客户端发新 schema 不期望的数据；新 schema 解析旧数据（缓存/旧客户端）失败——Field() aliases、Optional+sensible defaults、代码注释记录版本变更。
- **Expand/Backfill/Switch/Contract 四步**（最可靠上线法）：expand 向后兼容引入新 schema→backfill 数据→switch 切换→contract 删旧字段——避免"all-or-nothing"部署被一个滞后消费者打爆。
- **前后向兼容双标准**：新读者可读 N-1 数据（向后）；旧读者可读 N 数据（向前）——滚动部署最低门槛。
- 判据：agent-to-agent 接口升级=API 版本管理——版本嵌入输出、只加不减、双版本并行、deprecation 走 sunset。

### 7. 输出质量评测：8 rubrics + Safety 硬门 + rubric 化 grader（可复用 Skill）
来源：futureagi-llm-evaluation-metrics / prodinit-eval-rubric / promptassay-judge-templates / microsoft-rubrics-reference / google-rubric-metrics / 42robots-llm-eval / langchain-rubrics
- **八 rubrics + 三 primitives**（futureagi）：八条=准确性/忠实度/指令遵循/…/成本（正确但 $0.5/请求=单位经济失败；per-request cost + cost per resolved task 入 CI gate，与 Groundedness 同权挡发布）——"八条之外都是厂商营销分类"。
- **Safety 硬门**：Safety 是 binary（0/1）不是连续分——有害/偏见/不当内容出现=0，任何维度分数都救不回，Safety=0 直接 block 部署。
- **LLM-as-judge 模板化**：name/inputs/scale/output/reasoning/score/criteria 结构化模板（如 structural-correctness：1-3 分=格式不符/格式对但有错/完全合规）——judge 输出带 reasoning 供审计。
- **1-5 分级语义**（Microsoft 参考）：5 Exemplary/4 Strong/3 Acceptable/2 Weak/1 Needs Improvement——rubric 分级优于通过/不通过（趋势图+边界评审需要）。
- **rubric 化 grader 循环**（LangChain DeepAgents）：独立 grader 按 rubric 评 agent 全程，未达标注入 per-criterion 反馈再跑，satisfied 或迭代上限终止。
- **四家族评测栈**（futureagi 2026）：deterministic（BLEU/ROUGE/EM/代码执行）+ LLM-as-judge（faithfulness/hallucination/task adherence/rubrics）+ RAG 特定（context relevance/recall/precision）+ agent 指标（trajectory quality/tool-call accuracy/step efficiency）——每族三处跑：离线回归套件/内联 guardrail/生产实时。
- 判据：输出质量=多家族组合评测；成本与安全进 CI 门禁；judge 结构化+带 reasoning 可审计。
