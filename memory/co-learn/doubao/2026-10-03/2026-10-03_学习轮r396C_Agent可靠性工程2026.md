## 落地 5 独点（每点标注提升层）

### 1. 熔断器生产阈值 + LLM 特殊调优 + 探针纪律（工具）
来源：zylos-degradation / openlegion-reliability / agentpatterns-circuit
- **三态熔断器**：Closed（正常计数失败）→ Open（依赖宕机，调用立即失败不触达依赖；30s 内 5 次失败触发）→ Half-Open（冷却后放一个探针请求，成功关断、失败以 2x 冷却重开 60s→120s→240s）。
- **社区生产阈值**：trip to OPEN=5 次连续失败 **或 60 秒窗口 >15% 错误率**；cooldown=60s，**LLM API 恢复慢要更长**；alert 阈值 >5% 错误率。
- **Half-Open 探针纪律**：用**轻量低风险请求**探测，**绝不重发原始失败 prompt**（重发会把昂贵调用喂给刚故障的依赖）；探针成功才关断，失败翻倍冷却。
- **熔断必须与降级成对**：状态机本身只停止浪费、不保进度——**graceful degradation（fallback 路由或用户通知）必须配套**，否则熔断只是把失败延后。
- 判据：每个外部依赖挂一个熔断器（LLM API/工具端点）；熔断触发后必须有降级路径，不能只是停止调用。

### 2. 按工具类型分档可靠性矩阵（可复用 Skill）
来源：minixium / niteagent / bestaiweb
- **同一种失败，不同工具不同对待**——按工具类型定义参数表：

| 工具类型 | 重试 | 熔断 | Fallback | 降级提示 |
|---|---|---|---|---|
| Read（get_issue） | 3 次、1s 基 | 5 失败→30s 冷却 | 缓存/有限数据 | "Live data unavailable" |
| Write（create_issue） | 2 次、2s 基 | 3 失败→60s 冷却 | 入队稍后重试 | "Try again later" |
| Search | 3 次、1s 基 | 5 失败→30s 冷却 | 简化 query | "Search unavailable" |

- **Read 可重试多于 Write**（读失败无副作用，写失败可能已生效——写更少重试+更长冷却+入队补偿）；Search 失败降级为简化 query 而非放弃。
- **重试六要素**：transient 异常类用类型匹配（非字符串匹配）/每调用最大重试数（非无限）/退避曲线指数+jitter（100ms 起步+上限封顶）/幂等（第二次执行同结果）/熔断器状态（三态+明确触发阈值）/预算耗尽后的 fallback 路径——六项全配才叫完整重试策略。

### 3. 幂等三层 + 幂等键构造 + verify-before-retry（工作流）
来源：72technologies-idempotent / openlegion-idempotency / neelmishra-deploy / arxiv-verified-tool
- **幂等三层（从外到内）**：① **run-level**（整个 agent 调用可重试——稳定 run ID+副作用日志）② **step-level**（单个 planner→tool→observation 循环可重试）③ **tool-level**（单个副作用安全调两次）——**三层缺一，重复就会漏进生产**。
- **幂等键构造**：`hash(agent_id + task_id + tool_name + call_number)`——call_number 是该工具在任务内的顺序计数：**同调用重试共享同一 key，不同调用得不同 key**；或 hash(tool name + arguments) 确定性产生。
- **verify-before-retry（非原子失败）**：不确定工具结果后，**先检查目标后置条件是否已满足**再决定——已成功则跳过重试（避免重复副作用），未成功则带更好证据重试；纯系统层 wrapper 改动、不改底层 LLM 就提升可靠性。
- 判据：每个会写外部系统的工具调用都带幂等键；重试前先 verify 后置条件而非盲目重跑。

### 4. 能力分级降级 + 健康三信号 + 自愈五循环（工作流）
来源：zylos-degraded / zylos-selfhealing / moonlight-selfhealing / csdn-fault-tolerance
- **能力分级降级（essential vs non-essential）**：服务不可用时 agent 进入降级模式而非整体失败——**显式把能力分级并预定各能力降级行为**：语言推理=essential 永远可用（本地模型兜底）/知识检索=essential 用训练知识+置信度标注/在线搜索=non-essential 降级为离线缓存。
- **健康状态三信号**：`last_heartbeat`（主循环每 N 秒更新）+`last_progress_event`（有意义状态推进时更新）+`iteration_count`（工具调用/LLM 调用总数）——调度器周期性轻量健康检查触发预定义恢复策略；LLM 调用超时未熔断/工具异常未隔离/记忆写入失败未回滚→会话状态不可逆损坏，容错是架构基底契约不是附加功能。
- **自愈五循环**：monitor→detect→diagnose→recover→verify——把可靠性当有界运行时控制问题（区别于静态工作流/简单重试/全量重规划）；每次恢复后必须 verify 才算闭环。
- 判据：agent 能力表显式标注 essential/non-essential+各降级行为；健康检查周期+恢复策略预定义；恢复闭环最后一步永远是 verify。

### 5. 混沌注入实验 + Guardian 对抗测试模式（工具/可复用 Skill）
来源：dzone-chaos / arxiv-guardian-bench / genai-club / inass-sre
- **混沌实验注入三例**：① agent handoff 延迟注入（两跳间 +800ms——测多 agent 弱通信下端到端意图保持）② 记忆投毒模拟（检索库注入一条错误文档——测 RAG 对抗数据忠实度）③ 资源耗尽/配置漂移/级联失败（Toxiproxy/Chaos Monkey/Litmus 生成）——**注入前先定义 exit criterion（SLO 式回滚条件）**，这是基础设施混沌实践同一纪律。
- **Guardian AgentBench 对抗模式**：① **Multiple Matches**（工具期望单结果却返 3-5 个相似候选——测澄清请求行为与智能上下文选择）② **Partial Data**（工具执行成功但返回不完整数据——测缺口检测、局限沟通、不完整履约承认）③ **Prompt Injection**（自然文本字段嵌指令覆盖/角色混淆/数据外渗/jailbreak——测冲突指令下指令遵循）——工具结果层不是只有失败，**"成功但不对劲"是最难测的一类**。
- **五层可靠架构**：retry budgets/fallback chains/error context/observability/chaos tests——五层齐上 agent 在底层工具坏掉时仍能干活。
- 判据：上线前跑混沌注入（exit criterion 先行）+Guardian 对抗模式（multi-match/partial-data/injection）测"成功但不对劲"路径；缺 error context 的重试只是瞎猜。
