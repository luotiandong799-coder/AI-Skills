## 落地 5 独点（每点标注提升层）

### 1. 模型路由三策略 + 三模式 + FrugalGPT 级联（工作流）
来源：redis.io / microsoft-foundry / zylos.ai（FrugalGPT）+ NVIDIA NeMo Switchyard
- **路由三策略**：rule-based（关键词/长度/头标签，决策路径显式易调试，但静态规则脆——任务分布漂移要维护，边界 case 出问题）/ semantic（嵌入分类，语义路由）/ predictive（**prefill router** 从负载数据学习预测模型成功率）；多数生产从 rule-based 起步，规则不够再上语义/预测。
- **路由模式三档**：Balanced（默认，质量成本综合最优）/ Cost（激进压价接受复杂 prompt 略降质）/ Quality（恒选最高质量不顾成本）——模式是配置不是代码，先 Balanced 再按业务调。
- **FrugalGPT 级联**（斯坦福 Chen/Zaharia/Zou）：先最便宜模型+置信度不足才升级贵模型，三组件=prompt adaptation（缩短 prompt 减成本）/ LLM approximation（缓存复用）/ 级联选择；**实测路由收益=40-85% 成本降且无可测质量损失**（Requesty/OpenRouter 等平台数据）。
- NVIDIA Switchyard 四类 router：LLM classifier / stage router / escalation router / tunable prefill router（LangChain 基准 74% 提升）。

### 2. 路由决策闭环八步 + 流量百分比 canary（工作流）
来源：llmapi.ai / truefoundry.com / dev.to shaam_ai
- **八步闭环（不需 RL day one）**：① 从路由表选第一个模型 → ② 调用 → ③ **验证输出** → ④ 失败重试或升级 → ⑤ 高风险送人审 → ⑥ 记录 model/cost/latency/result/fallback → ⑦ 基于真实结果更新路由规则 → ⑧ 循环；**生产第一步要的是 clean rules + validation + fallback + logs，不是强化学习**。
- **流量按百分比拆分**：多模型间按比例分流=新模型 A/B 测试与 canary 的基础（5% → 看指标 → 平稳再 ramp）。
- **延迟感知**：多个模型都合格时选当前健康 p95 最低的；**成本感知**：选能过关的最便宜模型；路由收益靠持续重算路由表而非一次性配置。

### 3. 工具调用失败四分类 → 对应策略（可复用 Skill）
来源：dev.to/yong_yu（retry taxonomy）+ bswen + aiagents.codeguides.io
- **盲重试危险，先分类**：① Transient（timeout/429/连接断）→系统拥有指数退避重试；② Bad arguments（4xx/schema/语义校验失败）→**错误返回模型，不盲重试**（模型修正参数再调）；③ Silent bad result（HTTP 200 但业务不可能 payload）→结果断言+标记可疑；④ Side-effecting failure（写操作部分应用）→**幂等键+补偿**，禁止 naive 重试。
- **工具永不向调用者抛异常**：内部 catch 全部失败返回结构化错误 dict，LLM 读到能智能应对（"工具从不把异常冒泡给 LLM"）；`tool_result` 带 `is_error: true`，模型同轮用修正参数重试。
- **执行与验证分离**：工具函数本身永不防御 malformed 输入（create_ticket 不校验）；校验在边界层做——Pydantic/JSON Schema 在外部数据进入 agent 处校验，抛类型化错误由运行时捕获（不是 LLM）；**每个 call ID 都必须追加 tool message（含失败）**，防模型对空回复；错误消息剥 secrets 再进上下文或日志。

### 4. 边界校验 + Output Validation Agent（可复用 Skill/工作流）
来源：bswen（tool-call-contracts）+ deepwiki（verifier agent）+ klementgunndu1 + neuralbase
- **工具契约（contracts）**：每个工具输入输出都定义严格 Pydantic/JSON Schema，**参数不匹配 schema 调用就不发生**——无幻觉参数、无静默错误执行；每个输出过结构+逻辑校验才离开 agent；Pydantic 定义工具让 schema 自生成（openai pydantic_function_tool helper）比手写 JSON schema 稳。
- **Output Validation Agent 模式**：关键工具调用（数据写/金融交易/面向用户动作）配验证 agent——它只看一件事："工具输出是否正确满足用户请求"（prompt 模板含 原 query/工具名/参数/输出）；验证失败回退/纠正，不直接放行。
- **strict 模式默认开**：SDK strict:true 时参数不校验即返回模型错误；开 fuzzy 匹配要显式且知道代价。

### 5. 并行工具执行 + tool_choice 组合矩阵 + schema 设计（工具）
来源：llmversus.com / niteagent.com / aigentlab.tech / openlegion.ai / loooop.dev
- **并行执行是最大的单点性能优化**：Promise.allSettled 而非 all（单工具失败不 abort 全部）；per-tool timeout；五数据源各 200ms：顺序 1000ms vs 并行 ~200ms = **5x 加速**；独立步骤并发执行+每个结果带**原 call id** 让模型匹配；依赖步骤序列化执行返回中间结果（Claude/OpenAI 原生支持单响应多 tool_use）。
- **tool_choice 组合矩阵**：`none`=关工具纯文本；`auto`=默认；`any`+`disable_parallel_tool_use:true`=严格单工具必用禁多；`tool`+`disable_parallel_tool_use:true`=指定工具单发；`any` 无禁用=并行跑多个——按"必须用几个工具"选组合。
- **schema 设计**：verb-noun 命名（search_web/create_ticket）；description 无歧义声明"何时用+每个参数含义"；强类型参数+**Enum 代替自由字符串**（tau-bench 衡量工具选择质量）；`required` 数组列出必填参数。
- **执行编排三模式**：LLM-orchestrated（N 轮往返高延迟高灵活，复杂分支逻辑）/ programmatic（1 轮往返线性链/批处理）/ server-side（最低延迟固定工作流）——按任务形态选，不默认 LLM-orchestrated。
