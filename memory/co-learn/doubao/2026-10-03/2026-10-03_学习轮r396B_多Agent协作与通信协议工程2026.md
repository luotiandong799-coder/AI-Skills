## 落地 5 独点（每点标注提升层）

### 1. MCP/A2A 双基座 + Agent Cards 动态发现 + 结构化消息字段（工作流）
来源：arxiv-mas-orchestration / redis-a2a / ietf-agntcy-messaging / metacto
- **双基座分工**：MCP（Model Context Protocol）管 agent↔工具/数据（同步工具调用+可选服务端流式部分结果），A2A（Agent2Agent，HTTP 基）管 agent↔agent 委托任务（orchestrator 提交任务请求给 worker，收结构化结果或进度事件流）——**MCP 管工具访问，A2A 管同级协作，两个问题别用一个协议硬扛**。
- **Agent Cards 能力广告**：每个 agent 发布简短 profile 描述它做什么——**动态发现无需预配置**（capability advertisement），跨框架协调；共享传输层同一治理上下文经 A2A/MCP/RAG 都可达。
- **结构化消息字段集**：生产系统用结构化消息格式（JSON+显式 schema）而非自然语言，**消息含 task ID（追踪）+sender/recipient 标识+message type+structured payload+相关 context**——自然语言通信缺可靠性。
- 判据：agent 间通信 = 结构化消息 + 能力发现 + 双协议分工；不要用自然语言消息做 agent↔agent 契约。

### 2. blackboard-pointer handoff + 黑板四要素 + 共享记忆治理层（可复用 Skill）
来源：openlegion-handoff / agentpatterns-blackboard / atlan-a2a / callsphere
- **blackboard-pointer handoff**：调用方把输出写到共享持久存储的命名 key（如 `output/researcher/task_abc123`），**只传 key 名给被调用方**——被调用方按需读 key 取所需字段；凭据、中间 scratchpad、调用方完整上下文**永不进交接消息**（最小暴露+上下文瘦身）。
- **黑板模式四要素**：共享黑板（结构化 key 下的可检视工作区，ACL 门控）+ 专家 agent（板状态匹配其触发条件才贡献，reader-writer）+ 可选 controller（调度谁先跑）；"读板上有什么，贡献你能贡献的"——**agent 间无直接消息**，全部经黑板（消除点对点脆弱协议）。
- **共享记忆治理层**：持久上下文存储（A2A 会话日志/长期记忆/先前任务 artifact）+ on-demand 检索（MCP/RAG）——多步工作流 agent 从共享治理层接续前一个 agent 的进度，**不在任一 agent 本地记忆里**。
- 判据：交接负载 = 指针（key）而非上下文拷贝；黑板 key 命名空间结构化+访问受控；跨 agent 状态放治理层不放本地。

### 3. 不可变状态快照 + 版本化 + append-only + 单写者原则（工作流）
来源：seanweldon-orchestration / tacnode-patterns / klementgunndu-shared-state
- **共享可变状态=竞态与丢失更新的主源**：现代数据库不显式配置（serializable 隔离+正确锁）也挡不住——架构解法=**不可变状态快照+版本化**：每个 agent 产出 sealed 不可变版本，存 **append-only 日志（insert 而非 update）**；Agent A 产 v1，后续 agent 基于 v1 产 v2，不覆盖只追加。
- **单写者原则**：关键实体（订单/支付/库存/股票）**恰好一个 agent 允许写**，其他 agent 只读或间接请求变更（走请求而非直接写）——直接消除竞态；写冲突时用锁/协商/共识（8 模式：简单锁→分布式共识）。
- **共享 vs 隔离取舍**：共享状态简单但两 agent 同时写同一 key 即竞态；隔离状态各管各的+显式 handoff payload 更安全但通信重——按实体关键度选，关键状态走单写者。
- 判据：任何 agent 写共享状态前问"这个实体允许几个 writer"——多于一个就必须单写者或版本化 append-only。

### 4. 四并发异常分类 + read-after-write staleness + Action-Message Desync（工作流/工具）
来源：arxiv-concurrency-control / agentpatterns-isolation / jamesoconnor-parallel-tool
- **MAS 失败本质是并发控制问题**：stale reads/lost updates/inconsistent outcomes——**长 LLM 推理窗口放大竞态风险**（一个 agent 推理 30 秒，另一个已改了它要读的状态）；显式并发控制=冲突检测+隔离保证+结构化资源访问。
- **四并发异常**（共享记忆/向量索引/工具注册表无隔离契约时）：① **stale-generation**（基于旧代状态生成）② **phantom-tool**（工具已被撤/换仍被调用）③ **causal-cascade**（一个异常级联污染后续）④ **tool-effect reordering**（工具效果顺序错乱）——同一类经典数据库并发异常。
- **read-after-write staleness**（同 turn 内）：agent 同 turn 发 `add_to_cart(item)` 和 `get_cart_total()` 并行执行，**get 读到 add 之前的旧值**——同 turn 并行工具调用中依赖前一个工具结果的后读必须串行或等依赖。
- **Action-Message Desync**：agent 基于消息行动，但世界状态已被改变（消息与动作不同步）——行动前复核当前状态而非只信消息。
- 判据：共享状态写入一律带隔离纪律（版本/锁/串行依赖）；同 turn 并行工具调用凡有读后写依赖必须拆串行。

### 5. 死锁/循环依赖识别 + 完成信号协议 + 双端消息校验（工作流）
来源：maxim-reliability / dev-langgraph-deadlock / agentpmt-distributed / codewithphp-protocols
- **死锁=依赖图含环**：A 等 B→B 等 C→C 等 A 即永久阻塞且无自动解决（例：代码 agent 等测试 agent 验证，测试 agent 等文档 agent 更新，文档 agent 需代码 agent 的代码）——**编排前先画依赖图查环**；非确定性 LLM 调用还带来 livelock/无界循环（分布式系统经典问题，进程是不听话的 LLM）。
- **完成信号协议（最被忽视）**：委托必须定义"工作何时算完"——轮询？被委托方 push？有无超时？**无完成协议=委托协议会被绕过**（Swarm 把委托简化成单原语 handoff function，简洁即要点）。
- **双端消息校验**：请求与响应都过 schema 校验（`validateRequest`/`validateResponse`）——enum 约束（depth: basic/detailed/comprehensive）、必填字段（findings/sources/confidence_score）双端强制；消息契约不是单端承诺。
- 判据：委托前确认①依赖无环 ②完成信号有明确定义 ③请求/响应两端都有 schema 校验。
