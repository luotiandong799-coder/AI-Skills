## 落地 7 独点（每点标注提升层）

### 1. 审计日志四层结构：单层工具调用日志不足以解释"为什么"（工作流）
来源：anomity-ai-agent-audit-trail / ins-security-audit-tool-calls / kunalganglani-otel-redaction / microsoft-structured-log-agent-decisions / ietf-verifiable-agent-conversations
- **四层日志，缺一层就断链**：LLM request/intent（系统 prompt、messages、model、finish reason——回答"为什么选这个动作"）/ Tool invocation/action（工具名、参数、结果、身份、延迟——回答"执行了什么"）/ Memory & retrieval（记忆读写、RAG 文档 ID——"召回/存储了什么上下文"）/ Identity & attribution（凭证、token、delegated vs autonomous——"谁授权了"）。
- **审计追踪每 query 记五件**：timestamp、user、retrieved context、generated output、lawful basis/refusal events——EU AI Act Art.12 record-keeping 的最小证据。
- **工具交互遥测字段**：tool name / parameter class / latency / retry count / response status / error taxonomy——随时间揭示工具选择模式与漂移（agent 突然偏好高风险 connector=prompt abuse 或 policy gap 的早期信号）。
- 判据：日志字段按"为什么-做了什么-上下文-谁授权"四问设计，工具调用日志单独不构成审计链。

### 2. Trace 采样：Tail sampling 而非 head sampling（工具·工作流）
来源：futureagi-what-is-llm-observability / theneuralbase-trace-per-request / ai-tldr-trace-sampling
- **Head sampling（发射时按比例丢）是 LLM 系统的错误默认**——失败稀有且高价值，丢了就没了。
- **Tail sampling（collector 端）四保留**：100% errors / 100% below-threshold eval scores / 100% high-cost traces（>95th 百分位）/ 1-10% clean traces（趋势基线）——Phoenix 默认 tail。
- **规模阈值**：>10K req/day 时无过滤 trace 存储 ~500GB/月；采样方案=100% errors + 10% 成功 + 0% 低价值分支；>100K req/day 必须 async tracing（不阻塞用户响应）+ 批量上传。
- 判据：采样决策发生在"收集端看到完整结果之后"，不是"发射端还不知道成败之前"。

### 3. Trace 存储成本治理：fat trace + 压缩 + 分层保留 + 容量上限（工具）
来源：spheron-clickhouse-tiered-retention / mastra-span-size-caps / beri-observability-pricing / aipromptshub-langsmith-trace-quotas / csdn-clickhouse-langfuse
- **LLM trace 是胖的**：一条 trace 可带长系统 prompt + 检索上下文 + 完整回答 + 每步工具 I/O（几 KB 到几十 KB）；存 100% 高流量应用成本可能超过 LLM 调用本身。
- **列存压缩**：ClickHouse 类列存对 prompt/completion 文本压缩约 10:1（同样数据 PG 行存 100GB vs 列存 10GB）；分层保留=hot tier 7 天全 span 带 payload（查询<1s）+ warm tier 聚合 + cold tier 长期。
- **span 容量上限默认**：cap 字符串 128KB、数组 50 项、对象 50 keys、嵌套深度 8——没有 cap 时单次大上下文 run 可写 MB 级 span（同段对话历史每步序列化一次）。
- **硬限制是静默丢弃**：LangSmith 每 trace 20MB / 每 run 10MB，超限 trace 静默 dropped 无报错——别等超限才发现没数据。
- 判据：trace 也是存储成本资产——按压缩率、分层保留、容量 cap 三件事管，缺一件就爆账单或丢数据。

### 4. 多 Agent 可观测性：parent-child span 传播 + handoff span + workflow ID（工具）
来源：braintrust-cross-agent-tracing / dzone-workflow-id / futureagi-trace-debug-multi-agent / redis-multi-agent-one-trace / sentry-failure-in-the-space-between / immersivecommons-broken-handoff
- **跨 agent 追溯靠 parent-child span 传播**：handoff payload 记在父 agent trace 上的 span，接收 agent 的 run 嵌套其下，同一 trace ID 流经两个 agent——否则调试 Agent B 的输出看不见上游根因。
- **workflow ID**：UUID 在任务入口生成、显式传播给参与任务的每个 agent（无论距起点几跳）作为每个 span 的 attribute——替代"手动交叉对照三个无共享父级的 trace 树"。
- **Broken handoff 的 tell**：A 说完成但 B 实际没跑——handoff 边界处缺失子 span 或子 span Status=Error；sub-agent tracker 显示"活跃但 3+ 小时无工具事件"是 distinct 状态（不是 running）。
- **分析单位从 prompt 变成状态转移**：不追问"模型返回了什么"，而是"为什么编排者把任务委托出去、哪里开始跑偏"。
- 判据：多 agent 系统的可观测性以"因果链"为单位；每层 agent 子轨迹带 agent 角色属性以便按角色切失败率。

### 5. 静默失败五分类 + 语义失败第三类（模型·工作流）
来源：arxiv-2606.14589-silent-failure-taxonomy / telerik-status-ok-failure / groundy-logs-never-catch / latitude-failure-mode-framework / scienx-hallucination-scoring
- **语义失败是第三类**：分布式系统传统分 crash（节点停响应）/ Byzantine（节点错响应）；AI agent 引入 semantic failures——每个组件协议层都正常但组合结果错了。HTTP 200 不代表工作。
- **五分类 taxonomy**：A 环境与平台怪癖 / B 设计假设不匹配 / C 错误吞并与稀释 / D 链式幻觉与编造（LLM 特有、最危险——不是不报错，而是主动把错误改写成看似合理的叙述）/ E 操作遗漏与取证盲点。
- **检测方法分层**：LSC（Linear Semantic Consistency，单前向 pass，84.6% AUROC，批量适用）/ Claim Decomposition（逐 claim 验证，高精度低召回）/ Real-time hooks（执行期内联拦截，取决于 judge 质量）。
- **三类隐性失败要跨轮看**：context loss（agent 忘早期约束，单轮看都正常）/ goal drift（逐步偏离原始目标，单轮不可见）——必须 LLM-judge 带全对话历史评估。
- 判据：日志只记"协议层状态"会漏掉语义失败——需要 hallucination risk / grounding / factual consistency 逐响应评分（gateway 加一层 scorer）。

### 6. Trace-linked evals：把评测分挂到产生它的 trace 上（工作流）
来源：zylos-trace-linked-evals / mlflow-evals-span-attributes / dynatrace-drift-evaluator / futureagi-llm-testing-playbook / microsoft-continuous-evaluation
- **trace-linked evals**：评测结果附加到产生它的具体 trace——LLM-judge 标出幻觉时，失败可回溯到当时的 prompt 文本、检索块、工具输出、系统 prompt；"为什么失败"可回答而非猜测。
- **采样与成本**：LLM-judge 跑 10-20% 生产流量给统计显著信号且不翻倍推理成本；span-eval 分层=100% heuristic + 5-10% judge（judge 异步）；分数作为 span attribute 与延迟/token 并列可查询。
- **Drift evaluator**：单次越界之外，比较近期分数 vs 7 天基线评测结果——渐进回归而非单次 breach。
- **三层信号栈**：continuous evaluation=宏观健康（生产样本质量分）/ monitoring=服务健康（延迟、错误率）/ tracing=解释（为什么会这样）——三件叠用。
- 判据：评测管线是运行时信号不是发布时仪式；分数必须可反查生成它的 trace。

### 7. Trace replay：从生产事故到回归测试（工具）
来源：arxiv-2609.20625-chronicle-cut-point-replay / zylos-trace-driven-debugging / microsoft-agent-replay / claudelab-deterministic-replay / codeables-live-vs-deterministic
- **Deterministic replay 原理**：记录 agent 在非确定性边界（LLM 调用、工具调用、检索、认证、外部 API）上的所有值到 append-only 日志；重放时从日志读回这些值、不调用真实 LLM/工具——run 变成可确定复现（事件溯源应用到 agent）。每个执行发唯一 runId + 单调 seq。
- **Cut-point replay**：从记录选一部分边界重放、另一部分用新代码实时执行——把记录的事故变成 CI 里跑的回归测试（记录每边界 ~23μs 开销）。
- **Live vs deterministic**：live replay 验证 bug 在 prod 已修（非确定、环境漂移风险）；deterministic replay 复现与定位（同模型版本/快照 + 同 prompts + 同配置）。
- **time-travel debugging**：agent 执行视为可回退/分叉/从任意中间点重跑的事件日志——step 12 的坏 API 响应到 step 47 才显形，此时证据已消失；重放从锚点前重建、只再生成下游轨迹。
- 判据：能重放才算可调试——重放引擎是确定性运行时，返回记录事件的精确序列并阻止任何真实外部调用。
