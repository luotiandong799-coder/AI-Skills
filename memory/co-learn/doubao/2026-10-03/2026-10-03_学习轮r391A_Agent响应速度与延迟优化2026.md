## 落地 5 独点（每点标注提升层）

### 1. 延迟预算先于架构：分阶段预算分配 + 感知延迟目标分层（工作流）
来源：fiddler-latency-budgeting / mohithg-agent-latency / kunalganglani-latency-budget / menuagentic-cost-latency / agent-works-latency-techniques / beri-latency-tax / aws-agentperf02-bp04
- **先预算后架构**：SLA 要求 <500ms 时先分配——检索 100ms / 推理 300ms / 后处理 100ms；预算决定缓存什么、并行什么、缩小什么，而不是先买硬件再测。
- **总时公式**（agent 专用）：Total Turn Time ≈ Σ(TTFT+decode)每 LLM hop + max(并行工具调用) + Σ(串行工具调用) + 编排开销；P99 估算=各组件 P50×其 P99/P50 比（云 LLM API 的 P99 TTFT=2-3×P50，外部服务工具调用可 5-10×）。
- **逐组件对账**：N steps×平均每步延迟=步时；每 case 记录工具调用时+开销；**只优化超预算的组件，不统一优化**。
- **感知延迟目标**：chat 界面 2-3s 到首 token；工具调用多步 5-8s 总时可接受、15+s 感觉坏；电商每超 100ms=约 1% 收入损失（checkout 2s=30% 会话放弃）；用户按感知延迟评判 agent，不是总处理时间——TTFT 是主导感知信号。
- **延迟 tier 分模型**：Tier1 实时语音=最快模型（Haiku/Gemini Flash）+WebSocket 流式必须；Tier2 交互聊天=fast mid-tier+强推流式；Tier3 编码助手=质量平衡（Sonnet/GPT-4.1）。每 tier 有自己的 TTFT/总时/流式/模型档组合。
- 判据：延迟优化从"预算在哪花"开始，不是从"哪个 knob"开始；组件级对账找出真凶，统一优化是浪费。

### 2. 并行工具调用编排：依赖 DAG + fan-out 经济性 + 工具输出压缩（工作流）
来源：agent-works-parallel-tool-calls / zylos-parallel-tool-calling / generalcompute-parallel-tool-execution / agentixforce-latency-pipeline / aws-agentperf02-bp03 / agenticfabriq-compress-tools / n8n-reducing-ai-workflow-latency
- **依赖 DAG 化**：把 pipeline 画成 DAG，边=数据依赖；无依赖步骤并行，工具调用是最佳并行化候选（search_web/query_db/check_calendar 独立可同时跑）。
- **收益实测**（zylos）：30s→6s（~5x）、token ~50% 少、API 成本 ~40% 低、turn 数 ~60% 少；n8n 案例：串行 2.4s 操作并行后 ~800ms。
- **fan-out 经济性**（generalcompute）：8 个并行工具调用=1 次推理决策+1 次 rejoin 调用（2 次推理而非 8 次）；推理快则 fan-out 省钱，推理慢则稀释——并行度设计与推理速度联动。
- **结构决策主导延迟**（AWS）：等待的组合结构主导总延迟>任何单依赖速度；四项=独立操作并发/复用热连接运行时/冷启动移出关键路径/单请求内重复查找去重——每项独立于模型选择，增益复合。
- **工具输出压缩=最高杠杆**：工具输出回到 prompt 并**随每个后续步骤骑乘**——一次膨胀响应每 turn 都付直到滚出上下文；压缩工具返回（截断大 JSON/日志/HTML）比压缩任何别处都值；Cursor 用"定义工具如何表现"替代 DO NOT/必须/重要长列表，系统 prompt 砍 66%。
- 判据：先画依赖图再谈并行；工具输出是逐 turn 复利成本，压缩它收益最大。

### 3. 缓存分层栈：response→semantic→prompt 逐层补漏 + 前缀稳定性规则（可复用 Skill）
来源：futureagi-prompt-caching / neuraltrust-llm-caching / kunalganglani-latency-budget / agent-works-caching / dailyaiworld-token-caching / agiflow-cost-latency / openai-gpt6-model-guide
- **四层栈**：response cache（精确重复，简单低命中近零误报）→ semantic cache（paraphrase 命中返回存储响应，FAQ 场景）→ prompt cache（前缀复用跳过 prefill）→ model call；**每层抓上层漏掉的**。
- **命中率经济学**：10,000-token 工具目录 80% 命中比 500-token 完美压缩 100% 命中省更多——**绝对 token 量×命中率**才是收益，不是压缩率。
- **前缀必须逐字节一致**：稳定内容（系统指令/工具定义/检索上下文/对话历史）放**前面**，动态内容（timestamp/用户名/会话值）放**后面**，否则整块失效；工具定义保持跨轮一致。
- **收益实测**：多轮对话 60-80% 输入 token 相同；缓存前缀 TTFT 降 40-60%；20-turn 累计省 3.2s；Anthropic 100K 缓存 prompt 2.4s vs 11.5s；OpenAI >1024 token 自动缓存；GPT-6 缓存窗口 30 分钟。
- **价格不对称**（agiflow）：cache read 0.1× 基础输入价；5 分钟 cache write 1.25×；1 小时 write 2×——写入频率与时长要算进成本模型。
- 判据：prompt 结构按"稳定在前动态在后"排；缓存是分层补漏不是单点；评估用绝对 token×命中率。

### 4. Agent 流式 UX：从 token 流升级为 agent 事件流 + 部分结果回流（可复用 Skill）
来源：ai-tldr-streaming / fiddler-streaming / max-gherman-agent-ux / langchain-token-to-agent-streams / theneuralbase-streaming-partial / openai-agents-streaming / microsoft-magentic-streaming / zylos-agui-streaming / callsphere-streaming
- **流式=最大 UX 提升**：SSE/WebSocket 逐 token 渲染，模型完成时间不变但用户百毫秒见首词（首词 200ms vs 干等 2s）；空白屏 2 秒=感觉坏，逐词 2 秒=感觉快。
- **从 token 流到 agent 事件流**（LangChain）：现代 agent 产生 message/tool call/subagent 活动/状态变更/审批请求/媒体——需要**结构化事件流**而非扁平文本；typed events+projection 简化前端（订阅消息/工具/状态/子 agent 通道，运行时处理组装排序重连）。
- **事件粒度**：token 级→条目级（RunItemStreamEvent：message generated/tool ran）→agent 变更级（AgentUpdatedStreamEvent）；非流式回复只有一个可观察时间戳，流式有几十个（首 token/工具 delta/推理块/finish-reason 翻转/工具结束标记/done）——每个都是下游提前反应的挂点。
- **部分结果流回 LLM**（theneuralbase）：工具结果增量流回 LLM，不等完整计算；在单个 tool role message 累积部分结果，工具完成（或缓冲阈值）后只调一次 LLM。
- **AG-UI 协议**（zylos）：补 MCP/A2A 故意忽略的缺口——agent 内部状态如何实时到用户屏幕；typed event vocabulary：TEXT_MESSAGE_CONTENT（部分文本块）/TOOL_CALL_START/TOOL_CALL_END（工具生命周期，UI 可显示进度）/状态变更/生命周期信号。
- **agentic 流式难点**：推理循环中途停流调工具+多 agent 最终 agent 流式而上游还在产——事件流是解，不是继续逐 token。
- 判据：交互型 agent 默认流式；工具调用进度必须有事件（TOOL_CALL_START/END），否则用户看到空白就以为坏了。

### 5. 性能回归监控：workflow 级延迟预算 + 三百分位 + 步骤预算（可复用 Skill）
来源：mlflow-monitor-agentic / belsoft-agent-observability / kunalganglani-eval-harness / aws-agentperf01-bp01 / velsof-hidden-metrics / logic-cost-attribution
- **workflow 级 p95/p99 预算**，不是单 LLM 调用级：多步 trace 超预算即告警；P50/P90/P99 三百分位全跟踪（P99 暴露均值隐藏的尾延迟——3 个外部工具串行可让 P99 暴涨而 P50 健康）。
- **性能四维成功标准**（AWS）：latency（流式=TTFT、任务型=端到端完成时间、推理管线分阶段预算）/throughput（并发会话/每秒请求/负载队列深度）/quality（完成率/工具选择参数准确/grounding）/efficiency（token per task/cost per completion/**cache hit rate**）。
- **步骤预算回归**（kunalganglani）：median+P95 step count 是真实回归信号（agent 悄悄多走步）；每次改动后对比 step count，防止"行为没坏但变慢/变啰嗦"的隐性回归。
- **真端到端延迟**（velsof）：模型延迟（request→first/last token）几乎不是用户感知值——用户感知=输入预处理+embedding+检索+prompt 组装+推理+工具+后处理全链路；监控仪表盘只显示模型延迟=最低信号。
- **成本归因挂 span**：per-agent/per-step token 用量与延迟一起跟踪，找最贵的 trace 段；spend threshold 触发告警或熔断（防跑飞循环烧光预算）；按 feature/user tier/model/prompt version/时间窗口聚合。
- 判据：延迟指标报"全链路端到端"而非模型延迟；step count 是质量不变时的隐性性能回归探测器；cache hit rate 是效率维度必须 KPI。
