## 落地 5 独点（每点标注提升层）

### 1. n8n 子工作流隔离失败域：AI Agent 节点不捕获子节点错误（工作流/工具）
来源：n8n-community-ai-agent-stop / n8n-community-tools-errors / n8n-community-error-workflow / n8n-blog-production-playbook / n8n-blog-15-practices
- **known bug**：AI Agent 节点上的 "Continue on error" 设置**不捕获工具子节点抛出的错误**——工具节点失败照样崩整个流程。
- **最可靠修法=子工作流化**：不用直接工具节点，改用 "Call n8n Workflow" 工具——把工具逻辑放进独立子工作流，对其内节点开 "Continue on Fail"，保证子工作流**总能完成并返回某种响应**给 agent，主流程不死亡。
- **结构化错误对象**：工具逻辑包 try/catch 返回 `{success:false, error:message}` 而不是 throw——结构化失败响应让父工作流可行动（agent 能根据 error 字段换路径）。
- **隔离失败域原则**：每个 agent/子工作流自己的错误处理——账单 agent 失败不级联到技术支持 agent 或崩溃编排器；每个组件返回结构化失败响应。
- **节点级错误三设置**：每节点 Settings 管 Continue on error / Retry on error / Error output（错误路由到专门处理逻辑）。
- 判据：agent 工具调用可靠性=子工作流+Continue on Fail+结构化错误对象三件套；别指望 Agent 节点自己的 Continue on error 兜住工具子节点。

### 2. LLM 输出净化前置节点：把 agent 输出当不可信输入（可复用 Skill/工作流）
来源：n8n-community-untrusted-input / n8n-community-debug-agent / n8n-blog-debug-agent
- **强制净化节点**：agent 与一切下游之间放一个小 Code 节点，顺序做三件事——①剥 fence 与 preamble ②取第一个 `{`（或 `[`）到最后一个 `}`（或 `]`）之间的子串再解析 ③解析失败给默认值/错误对象——**一步挡住凌晨 2 点执行死亡**（LLM 偶尔输出带废话前缀或截断 JSON）。
- **错误传播检查点四件套**：Structured Output Parser（坏格式立刻失败）/ IF 节点验证关键字段（步骤间校验）/ 长 agent 拆子工作流（错误在各边界停住，不滚雪球）/ Error Trigger workflow（用户在发现前先知道失败）。
- **可视化执行追踪**：n8n 单条可视化执行轨迹显示**哪个 LLM 工具调用失败、为什么、LLM 尝试传了什么参数**——生产级可靠性不需要重 DevOps 栈（查 LLM 调用问题先看执行轨迹）。
- 判据：任何 LLM/agent 节点输出进下游前先过净化节点（剥 fence+取 JSON 区间+失败兜底）；错误传播靠检查点停住不靠直觉。

### 3. Dify 知识产品面 vs Langflow 可组合组件 + Supervisor 模式（工作流）
来源：1337skills-visual-builders / agenticindex-dify-langflow / cedarops-dify-flowise-langflow / kanopy-dify-flowise-langflow / qiita-dify-flowise-langflow
- **知识管理两种哲学**：Dify 把知识当**受管产品面**（ingestion/chunking/embeddings/indexing/hybrid search/reranking 全带合理默认）——想要强检索又不想当检索专家就选它；Langflow 把检索暴露为**可组合组件**（splitters/embedding models/vector stores 直接控制）——想调优管道/做实验就选它。
- **工作流形态差异**：Langflow 图=可见链，执行=输入触发一次链式执行；Dify 工作流=应用包装器下面的一层，执行由**应用类型**决定——对话记忆/聊天界面/日志由平台管理而非显式绘制（平台托管行为 vs 自己画出来）。
- **Dify 组合形态**：workflow-as-tool + agent-as-node——一个流调用另一个流，Agent 节点是确定性 harness 内的**有界自主步骤**（与 crewai/langgraph 的对等 agent 社会是不同形状）。
- **Supervisor agent 模式**（Dify 新引入）：协调多个子 agent 复杂任务；支持**并行工具执行、工具调用重试逻辑、MCP server 连接**（agent 可连 GitHub/Slack/数据库/文件系统/浏览器）。
- 判据：选平台看形态匹配——要平台托管应用行为（记忆/UI/日志）选 Dify；要可组合管道实验选 Langflow；多 agent 协调看 Supervisor/子工作流能力。

### 4. 即时触发与语义工具搜索（工具/工作流）
来源：make-what-is-ai-automation / activepieces-changelog / activepieces-inbox-mcp / pipedream
- **Instant trigger 优于轮询**：Make 场景里 "Watch issues - instant" 类即时触发**比轮询版快且省资源**——能选 instant 就别用 polling。
- **按任务搜索工具（tool search）**：Activepieces 2026-08 AI-Ready Pieces——agent 通过 MCP server 连接后，**按任务描述（不是按名字）**在数百 pieces 中找到正确 action，再检查 schema 并运行——语义搜索替代名字记忆。
- **单连接多应用**：Activepieces Inbox MCP——连接一次 Inbox，其每个 action 变成 assistant 可调工具，**同一 server URL 下 760+ 应用单连接**（云或自托管）——agent 的工具面一次接入。
- **Pipedream 形态**：managed auth + 10,000+ tools across 3,000+ APIs + 10,000+ 预建 triggers/actions；所有集成 GitHub 上可扩展（extend any tool or write your own）——代码优先事件流。
- 判据：触发选型先问有没有 instant 变体；工具面接入按语义搜索选平台（tool search 省名字记忆）；多应用 MCP 单连接减少配置面。

### 5. 平台选型判据表：RAG 控制/多 agent 形态/集成数/许可（工作流）
来源：baeseokjae-langflow-n8n-dify / ossalt-compare / agentswarms-compare / qiita-dify-flowise-langflow
- **RAG 管道控制**：Langflow Advanced（chunking/embedding/reranking 全可调）/ Dify Intermediate（内置 Knowledge Base）/ n8n Basic（手动 HTTP 节点）——要细调检索选 Langflow。
- **多 agent 形态**：Langflow=LangGraph native / n8n=基础链式 / Dify=内置 Agent 节点+Supervisor；Dify 100+ LLM providers 原生、n8n ~15 AI 节点但 200+ 三方集成、Langflow=LangChain 全生态。
- **自定义代码能力**：Langflow=完整 Python 组件 API（最强）/ Dify=受限 Python/JS 块 / Flowise=JS 函数节点——深度定制选 Langflow。
- **许可与自托管**：Dify MIT / LangFlow MIT / Flowise Apache 2.0（均宽松可自托管）；监控分析 Dify 内置（Flowise/Langflow Limited）。
- 判据：选型五问=检索控制要多少/多 agent 什么形态/要哪些模型与集成/自定义代码深度/自托管与监控要求。
