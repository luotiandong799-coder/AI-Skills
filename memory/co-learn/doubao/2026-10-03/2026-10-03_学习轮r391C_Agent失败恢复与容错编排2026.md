## 落地 5 独点（每点标注提升层）

### 1. 错误分类学 + 工具四类注册表 + Supervisor 门控重试（可复用 Skill）
来源：openlegion-reliability / niteagent-error-handling / agent-works-recovery / xbstack-langgraph-recovery / neelmishra-retries / agentnative-idempotent-retry / dev-fault-tolerant-autonomous / aigentlab-resilience / openai-rate-limits
- **transient vs terminal 分类**：429/502/503/504/连接超时/DNS=transient→指数退避+抖动重试（cap 3-5 次）；400/401/403/校验/schema 错误=terminal→重试浪费预算每次同样失败；输入/schema 错误=模型幻觉（多余字段/缺参/类型不匹配）——重试对象是调用，不是幻觉。
- **公式**：delay=min(base×2^attempt+random(0,jitter), cap)，full jitter 防 thundering herd；429 时 Retry-After header 优先；同时限制重试次数与总时间。
- **工具级四类注册表**：read-only（自由重试）/ idempotent-by-provider（带 key 重试）/ journal-deduped（effect journal 检查后重试）/ at-most-once（绝不自动重试，升级人工）。
- **Supervisor-gated retries**（LangGraph 恢复决策分工）：Worker 只执行工具+记录标准化失败上下文（恢复逻辑的"信息提供者"）；Supervisor 是"决策者"控制全局状态，按全局预算决定 retry/fallback/ask_human/exit safely。
- **LLM 版熔断**：传统断路器 5xx/超时开闸；LLM 版应在**语义退化或成本爆炸**时也开闸（反复产 nonsense 就开闸防 token 浪费并转 fallback）。
- 判据：先分类错误再决定策略；重试决定权上收给 supervisor（全局预算视角），worker 只负责记录失败现场。

### 2. 三级重试 + Effect Journal + Transactional Outbox + Watermark（可复用 Skill）
来源：72technologies-idempotent / agentnative-idempotent-retry / claudelab-outbox / zylos-outbox / channel-idempotent-tool / dev-imversion / arxiv-exactly-once
- **三级重试缺一不可**：run-level（整 agent 调用可重试）/ step-level（planner→tool→observation 循环）/ tool-level（单副作用安全调两次）——跳过任何一级就向生产泄漏重复。
- **幂等键派生规则**：稳定 key 从 durable workflow 身份（run ID+step ID+attempt-independent operation hash）派生；**绝不从 timestamp/重试计数/LLM 输出派生**。
- **Effect journal**：副作用日志记录已执行效果，重试前查 journal 决定是否已生效——先查后调。
- **Transactional Outbox**：业务行+副作用意图**原子提交**——"if the row exists, the intent exists" 数据库不变量；dispatcher 至少一次投递+幂等消费者=effectively-once 语义，无需分布式事务；并发用 SKIP LOCKED；event id 作去重键；outbox lag 监控（未发布行>30s 告警）；N 次失败进 DLQ；TTL 清理。
- **Watermark overlay**：上游无法去重时，小元数据水印标记"此副作用已发生"，配合任何恢复策略避免重复。
- **理论边界**（arxiv）：超时请求仍在飞行中时，纯验证策略找不到结果→重试 56% 创建重复（redelivery 74%）——**验证-only 在 late commits 下不可能 exactly-once**，契约（idempotency key/effect journal）才是真保证。
- 判据：重放安全靠"意图先落库+效果可查重"两条腿；验证只是辅助，契约才是 exactly-once 的住所。

### 3. 状态检查点 + Resume + Durable Execution：执行状态的外部化（工作流）
来源：microsoft-state-checkpoints / developersdigest-reliability-cliff / aws-agentrel03 / augment-async-agent / moai-durable / zylos-durable-execution / microsoft-foundry-recover / open-multi-agent-checkpoint / langgraph-interrupt / agentnative-checkpoint-resume / aidenai-state-machine
- **长任务每大步 checkpoint**：step7 失败从 step7 前恢复不从 step1；**state 必须外部**（Postgres/Redis/JSON）——"agent memory"就是刚失败的那个；10 步链无 checkpoint 成功率 20%，checkpoint 改变数学。
- **chat-only 恢复不够**（Crab/Terminal-Bench）：仅聊天历史恢复 8-13% 正确率 vs semantics-aware checkpoint/restore 100%——聊天历史漏掉 OS 级副作用（文件系统变化）。
- **Durable execution 三原语**：checkpoint 进度 / 重放确定性控制流 / 重试失败 activity + 跨崩溃保留 wait state（Temporal/Inngest/Restate/Azure Durable Task）；orchestration 自动 checkpoint，activities 包非确定操作（LLM 调用/工具/API）。
- **恢复策略分级**（Microsoft Foundry）：naive rerun（非幂等副作用需 fence）/ framework checkpoints（persisted response snapshots）/ upstream-owned resume / watermark overlay（避免无法去重的副作用重复）。
- **Graceful shutdown ≠ terminal failure**：shutdown 时完不成的工作 exit_for_recovery 保持 in_progress，由后续 lifetime reclaim 再执行。
- **Interrupt 一等公民**：需要人工输入时 raise interrupt，run 状态已 durable——进程死/pod 重调度/过去数天，run 是 store 里的行不是活进程；resume 用同一 run id 重入。任务状态机=created→queued→running→(failed/cancelling→cancelled)→completed。
- 判据：进度存在外部存储且每步可回退；"resume from last checkpoint" 是恢复默认路径，不是"重跑一遍"。

### 4. 四类预算护栏 + onExhaustion 策略 + 预算触发频率判据（工作流）
来源：effect-agent-budgets / claude-agent-loop / vybestack-subagents / claude-cma-session-cap / forja-budget / dev-stopping-conditions / csdn-claude-maxTurns / runguard-failure-modes / agentpatternscatalog-step-budget
- **四类 bound**：maxTurns（模型请求次数）/ maxToolCalls（声明+编程工具调用）/ maxDuration（含 durable suspension 的逻辑运行时间）/ tokenBudget（累计输入输出 token）——每个 bound 命中走 onExhaustion 策略（受限终答 or fail）。
- **成本上限**：max_budget_usd（美元上限到即停）；session budget cap（平台按公开价算每 thread token 成本，达到后会话 idle，stop reason=budget_reached，**文件/工具状态/对话保留**）。
- **Step budget 返回最佳部分答案**：N 命中后终止循环，返回 best partial answer+注明"cap reached"——受限终答优于硬失败；surfaces 病态 prompt 为 cap-hit。
- **distinct exception type 防吞**（runguard）：无限循环里 max_iterations 异常被 retry wrapper 捕获吞掉→agent 在无法收敛的任务上无限跑——修复=guard 抛 retry handler 不 catch 的独立异常类型；确定性失败工具被 agent 重试 3-10 次每次读完整输出→重试级联，配 per-tool 断路器。
- **预算频繁触发判据**：step/token budget 常规触发=任务比配置大，**应拆任务不是调参**；cap 命中可能是更深 bug 的藏身处（agent 本应更早停）。
- 判据：预算=强制边界不是建议；命中后"受限部分答案>失败"；频繁撞 cap 是任务拆分信号。

### 5. 输出验证恢复：Repair-first → Parser-feedback Retry + 工具输出预验证 + 语义熔断（可复用 Skill）
来源：bestaiweb-retry-contract / machinelearningplus-self-correcting / ai-tldr-schema-validation / velsof-output-validation / channel-self-healing / misar-retries / channel-structured-outputs / zylos-structured-validation / openlegion-structured-output / agentmelt-structured-output
- **工具输出先验证再进推理链**：模型把工具响应当 ground truth——执行前用 schema（zod/pydantic）验证工具输出，验证失败不入链（自愈模式的三类静默错误之一）。
- **Repair-first**：schema 失败先启发式修复（json_repair 补逗号/引号/截断结构，免费零模型调用），修复不行再 retry——两者结合最常见。
- **Parser-feedback retry loop（cap 2-3 次）**：把验证器错误消息喂回模型作后续 turn 自纠——"Field start_date is required, got undefined" 这类具体错误模型修得极好：85% 首轮、95% 两轮累计；**cap 必须**，否则无限循环；自纠=带更好错误消息的重试。
- **受控终输出**（OpenAI error_handlers）：max_turns/model_refusal/invalid_final_output 三类错误接 handler 返回受控 final output 而非报错结束。
- **模型级 fallback chain**：结构化输出持续失败（特殊语言/对抗输入/超长文本）→ 降级到更简单输出格式/无约束模式+低置信标注；provider fallback ladder=primary→同 provider 降档→跨 provider→自托管 open-weight 兜底（标 degraded 状态）。
- 判据：验证失败的第一反应=喂错误消息让它自纠，第二反应=降级；一切 retry 都有 cap，工具输出与 LLM 输出同样要验证。
