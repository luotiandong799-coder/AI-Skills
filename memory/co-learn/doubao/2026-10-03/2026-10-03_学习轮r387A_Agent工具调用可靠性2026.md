## 落地 7 独点（每点标注提升层）

### 1. 工具目录规模退化曲线 + Tool RAG（模型·工具）
来源：zylos-tool-augmented-production / webscraft-tool-rag / vllm-sr-semantic-tool-selection / sixdegree-mcp-tool-overload / getunblocked-mcp-tool-overload / arxiv-2606.17519-scaling-routing
- **退化是非线性的**：~50 工具 84-95% 选择准确率 → 200 工具 41-83%（因模型而异）→ 740 工具趋零；机制含 "Lost in the Middle"（长上下文中间工具被忽略）+ 相似工具语义碰撞。
- **Tool RAG（按需注入）**：740 工具场景准确率 13.62%→43.13%（三倍）+ prompt 体积减半；semantic tool selection 在 100+ 工具维持 43%+（基线 13-15% 近随机）；生产经验=枚举一切进系统 prompt 的模型在几十个工具以上就崩。
- **token 成本信号**：3 个 MCP server 可在 agent 读到 prompt 前吃掉 143K/200K token；>50 工具输出质量退化、>120 崩溃——是架构信号不是配置错误。
- 判据：工具目录是稀缺上下文资源，按需检索注入（Tool RAG/语义选择）替代静态全量注入。

### 2. 选择错误 vs 调用错误分层 + BFCL v4 评测演进（模型）
来源：ai-tldr-tool-calling-best-practices / futureagi-tool-selection-accuracy / gorilla-bfcl-leaderboard / arxiv-2605.28532-feasibility-awareness / webbrain-consensus-voting
- **两类失败分治**：selection errors=选错工具/多调/漏调；invocation errors=选对但参数错——**argument correctness 对端到端成功影响大于 tool selection**（打磨 schema 胜过聪明 prompt）。
- **BFCL v4 评测口径升级**：2024 测"5 个固定工具挑一个"→2026 测"200 工具 8 个 MCP server 目录下：无匹配工具时拒绝调用、该并行时并行、调用排序有用、不幻觉目录外的工具"。
- **可行性感知（FCR）**：模型无法识别缺失能力会浪费资源做不可能任务；SR（成功完成率）与 FCR 分开测——诚实拒绝与成功执行是两个独立能力。
- 判据：评测工具调用要覆盖"该调对调/该拒时拒/该并行时并行/不幻觉"四个维度，不能只看单一准确率。

### 3. Schema 工程模式集（工具）
来源：aiworkflowlab-schema-design / dev-json-schema-validation / datarekha-tool-calling-99 / richardsai-tool-hardening / thenneuralbase-hallucinated-parameters / callsphere-schema-2026 / aaif-mcp-schema-2020-12
- **strict 化三类红利**：`additionalProperties:false` + 显式 `required` 消除约 80% 生产解析错误；enum 替代自由文本（分类字段 88%→100% 有效）；openai strict:true / anthropic strict 或 pydantic 校验工具。
- **schema 是唯一事实源**：从 schema 生成校验逻辑（ajv/jsonschema/pydantic）——后端期望变化时 schema 先变、模型再适配；不是模型先发任意串再事后猜。
- **boundary 校验在 executor 前**：pydantic ValidationError 在真正执行工具前拦截（类型/范围/枚举约束）；路径级报错修 path blindness（精确指出哪个字段错，非"某处失败"）。
- **幻觉参数监控**：过滤 schema keys 正确，但生产要**把幻觉记入监控**检测模型漂移（不止本地修）。
- 判据：schema 是工具与模型的契约边界——strict+enum+唯一事实源+boundary 校验四件套在 exec 前拦掉整类 bug。

### 4. 错误反馈三桶分类 + 结构化错误串 + 重试预算（工作流）
来源：ai-tldr-tool-errors / thenneuralbase-model-recovery / aiagents-error-handling / padiso-retry-policy / claudelab-is_error / arxiv-2601.15625-fission-grpo
- **失败三桶定模型动作**：validation/bad input（修参数重试，说清错什么期望什么："Unknown city 'Pariss'..."）/ transient（timeout/429/503，等退避重试，明示可重试）/ fatal（中止任务，不可恢复）。
- **结构化错误串替代异常**：把错误包成 user message 回会话（Anthropic tool_result is_error=true / OpenAI function_call_output）；**堆栈无用，要可行动的提示**（"price must be ≥ 0"）；每个 call id 必须回消息（含失败）。
- **重试纪律**：只重试 transient 不重试 permission；指数退避（0/1/2/4/8/16s）；硬性重试预算防无限循环；无进展循环检测→停止或升级；错误消息进上下文/日志前剥离 secrets。
- 判据：错误反馈是"给模型的可行动线索"不是"执行器日志"；三桶分类决定模型下一步；重试必须预算+退避+只 transient。

### 5. 并行工具调用判据 + Speculative Tool Calling（工具·工作流）
来源：openlegion-tool-use / aiworkflowlab-parallel / zylos-parallel-optimization / channel-parallel-5x / arxiv-2603.18897-paste / arxiv-2607.25816-speculate-while-reason / zylos-speculative-decoding
- **并行判据**：工具独立（输出互不依赖+不写同一有状态资源）才并行——40-70% 延迟削减；依赖则顺序（tool chaining）；并行结果全部单消息返回模型；同一有状态资源无事务支持并行=竞态风险。
- **ParaManager 模式**：并行编排可委派给专用小模型（agent-as-tool 范式，协议规范化+显式状态反馈）。
- **Speculative Tool Calling**：小/快模型预测下一步工具调用（名/参/顺序），主模型推理期间并行执行——无损（预测错就丢弃），55% 下一动作预测命中；PASTE 把推测结果隔离至 LLM 确认+联合调度，平均完成时间 -43.5%。
- 判据：独立才并行；推测执行=无损延迟隐藏（只读/可逆动作立即执行，写操作等验证）。

### 6. 描述工程 Description Engineering + 诚实拒绝（可复用 Skill）
来源：theneuralbase-tool-descriptions / zylos-description-engineering / jigarjoshi-descriptions-are-prompts / togetherai-best-practices / salmanq-tool-hallucination / arxiv-2406.20015-toolbehonest / arxiv-2609.14758-fabrication
- **描述是模型的唯一规格**：写清"做什么/何时用/何时不用/参数含义格式/不返回什么/限制"——反面例子 71%→96% 选择准确率（纯改描述无模型改动）；两个相似工具描述近乎相同=静默生产失败。
- **名字与描述分工**：`weather_lookup` vs `get_weather` 选择准确率相同，但描述性名字降低无关提问误触发；小模型对模糊描述更脆弱。
- **诚实拒绝（ToolBeHonest）**：无工具可解时模型应拒调用而非幻觉工具（MNT=missing necessary tools）；**no-tool test**（ICLR 2026）=移除必需工具重跑已知任务，可靠 agent 拒绝解释，幻觉 agent 发明不存在工具——每次模型升级后跑一遍（~10 分钟）。
- **工具失败后 fabrication**：工具失败时 agent 10-25% 会断言工具没返回的值——**失败必须显式声明**（"告诉它失败了，它就诚实报告；让它自己推断失败，它就编造"）。
- 判据：描述=prompt，修 registry 不修 agent；拒绝能力与执行能力分开评测；工具失败显式回传。

### 7. 工具注册表治理：同名冲突与语义近距（工具）
来源：instagit-mcp-collision / fr0ster-buildNamespacedTools / stacklok-toolhive / thenneuralbase-mcp-registry / antigravity-name-collision / aaif-mcp-schema
- **跨 server 同名冲突**：复合键 `<server-id>::<tool-name>` 保唯一（Dify 式）；冲突时仅重命名冲突者（`${prefix}__${toolName}`，fr0ster defaultToolNamespace）；priority 策略=保留高优先级后端工具丢弃重复（Stacklok ToolHive）。
- **内部注册表同名静默覆盖**：Python dict `@mcp.tool()` 装饰器同名后者静默胜出——`grep -r "@mcp.tool()" | grep -o 'def [a-z_]*' | sort | uniq -d` 查重，inspector.validate_registry() 校验。
- **语义近距工具**（read_file vs get_file_contents）：不同名近似职责，模型选哪个都行=问题——**无法自动改名，靠设计**（合并/区分职责/描述划界）；精确同名可自动重命名。
- 判据：注册表治理分两层——精确同名可机械解决（复合键/前缀/优先级），语义近距必须设计层解决。
