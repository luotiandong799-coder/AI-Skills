## 落地 5 独点（每点标注提升层）

### 1. 指令层级：System > Developer > User > Tool + 外部内容最低信任（工作流/模型）
来源：openai-instruction-hierarchy / keepmyprompts-model-spec / groundy-instruction-hierarchy / ginno-instruction-hierarchies / arxiv-hipo
- **四层信任序**：System（平台层可配置默认）> Developer（API 开发者 system message）> User（终端用户）> Tool（工具输出）——**高优先级更可信，低优先级只在不与高优先级冲突时遵循**；tool output 是不可信数据，**不覆盖指令**（工具输出里藏指令按数据处理）。
- **Model Spec 分级**：Platform（OpenAI 内建、API payload 不可见、训练/后训练烤进模型）> Developer > User > Guideline（软默认、可被隐式覆盖——样式/格式默认值属最低档）。
- **ChatGPT agent 用它做第一防御层**：system/developer 指令最高信任，用户指令中等信任，**外部拉取内容（web 页面/邮件/文档）最低信任**——指令层级本身是 prompt injection 的结构性防线。
- **HIPO（受约束 RL）**：把 system prompt 从"输入上下文"提升为"严格算法边界"——primal-dual 安全 RL 把系统提示合规当显式约束，在可行域内最大化用户效用（Qwen/Phi/Llama 跨架构验证）。
- 判据：任何 agent 提示结构按四层信任序组织；外部内容标记为"数据"非"指令"；冲突时高优先级赢。

### 2. 工具 Schema 设计：四类选择错误与修复 + 参数约束幻觉（工具/可复用 Skill）
来源：apidog-tool-schema / apifox-tool-schema / max-gherman-tools / aiworkflowlab-tool-schema / gcp-tool-design / mudassirkhan-function-calling / callsphere-tool-schemas
- **四类选择错误各配修复**：①重叠工具误选相似工具→**描述写"何时不应使用"**（each says when not to use it）；②无描述匹配任务用语→模型不选工具**凭记忆回答**→用用户常用词汇写描述；③选对工具但参数传错（参数含义模糊）→用 types/enums/units 约束；④工具链顺序错误→（顺序敏感的链）显式文档化调用顺序。
- **参数 schema 约束幻觉**：无描述的 string 参数模型填"看起来合理"的东西；**enum 把分类字段从 ~88% 有效→100% 有效**（categorical fields）；pattern 约束格式（^[A-Z]{3}$ 得到三字母代码而非乱写）——**schema 是对模型幻觉的硬约束**。
- **strict: true（OpenAI）/ Pydantic-validated（Anthropic/Gemini）**：无约束 schema 静默接受无效参数、靠模型自律不可靠。
- **明确命名参数，禁止 **kwargs**：模型靠参数名做语义映射——**kwargs 下模型不知道有哪些参数，要么传空要么编造参数名**；name+description 是模型决定是否调用的主要信号（"handles data" 无用 vs "检索客户 ID 的当前账单余额" 有效）。
- **参数面尽量窄**：注册接受多余参数的工具有害；重叠工具合并成更富参数集或明确非重叠描述。
- 判据：工具描述含"何时不用"；枚举/类型/单位约束参数；参数面=生产所需最小集；kwargs 禁用。

### 3. 约束解码机制：schema→文法→token 屏蔽（工具）
来源：zylos-constrained-decoding / devtoollab-structured-outputs / lyceum-function-calling
- **机制**：推理引擎把 JSON Schema 编译成形式文法（FSM/CFG/PDA），**每个解码步屏蔽会违反文法的 token**——模型物理上产不出非法 token——这是所有厂商"100% 可靠性"声明背后的机制（不是提示词写得好）。
- **开源引擎**：Outlines / XGrammar / llguidance / llama.cpp GBNF——开源模型要可靠 JSON 用引擎约束，别只靠 instruction following（开放权重模型靠提示词遵循 schema 不可靠，serving 运行时直接强执法则）。
- 判据：需要 100% 可解析输出的场景用约束解码引擎，不是 prompt 描述 + 祈祷。

### 4. 结构化输出工程选型：四级约束 + 同 schema 批处理（工具）
来源：vllm-constrained-decoding（acingai/lyceum）/ martinuke0-sglang / nvidia-structured-generation / claude-structured-outputs
- **四级约束**：guided_json（JSON schema）/ guided_choice（精确选项集）/ guided_regex（正则模式）/ guided_grammar（完整上下文无关文法）——按输出形状选约束类型，不是一律 JSON。
- **SGLang 生产实践**：schema 参数告诉运行时该槽位必须符合 JSON schema → **约束 token 采样只生成 JSON 合法续接**（基础场景无需外部文法引擎 guidance/outlines）+ **同 schema 的请求共享批处理加速**（schema 复用是吞吐关键）。
- **Claude structured outputs 双特性**：JSON outputs（output_config.format）+ strict tool use（约束工具参数也按 schema）。
- 判据：结构化输出先定形状（JSON/选项集/正则/文法）再选约束；高频同 schema 请求走共享批处理；工具参数同样受 schema 约束。

### 5. 显式 Prompt 缓存：90% 折扣 + 30 分钟复用 + agentic 场景价值最大（工作流）
来源：hkuspace-prompt-caching
- **显式 prompt caching（Bedrock GPT-5.6）**：精确控制缓存 prompt 的哪些部分并跨请求复用——**缓存输入 90% 折扣、30 分钟可用**（超时后失效需重缓存）。
- **agentic 工作流价值最大**：系统指令/工具定义/参考文档在多个请求间重复——缓存它们把重复成本降 90%；动态部分（用户消息/检索结果）不进缓存。
- 判据：把稳定前缀（system+tools+参考文档）与动态部分分离，稳定部分走缓存；改配置/换模型会破坏前缀缓存（上下文预算纪律同源）。
