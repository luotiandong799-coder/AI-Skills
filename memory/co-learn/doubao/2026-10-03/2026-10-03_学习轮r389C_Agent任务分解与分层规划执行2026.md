## 落地 7 独点（每点标注提升层）

### 1. 原子任务图（ATG）：递归图编译 + 接口保持 + 最小修复子图（工具）
来源：arxiv-2607.01942-atomic-task-graph / arxiv-2601.22290-six-sigma / agents.kour.me-extreme-decomposition
- **递归图编译**：从粗粒度任务图出发，递归细化非原子节点直到每个节点成为原子工具调用单元；每次细化 LLM 只允许访问当前节点直接相关的历史上下文——深度增加时每个节点注意的上下文窗越来越窄（上下文隔离）。
- **接口保持原则**：细化必须保持父节点的语义接口（外部输入-输出契约不变）——子图替换父节点后对上下游透明。
- **最小修复子图**：节点失败时以失败节点与其最低公共历史祖先构造覆盖失败节点+相关上游+受影响下游的最小修复子图；**其余 ATG 冻结以保留已验证状态、避免冗余重算**——修复完按外部接口重新集成。
- **原子三性质**（Six Sigma）：独立（无需其他子任务上下文或仅显式依赖）/可验证（输出可客观判定正确性）/聚焦（单一直白决策）；原子粒度使共识投票输出可比。
- 判据：分解是"图编译"不是"列表生成"——接口保持与最小修复区保证局部失败不污染全局已验证状态。

### 2. Goldilocks 粒度 + 四类分解失败模式（可复用 Skill）
来源：agentixforce-task-decomposition-strategies / codemia-planning-decomposition / microsoft-learn-decomposition-granularity / callsphere-decomposition-failures / aiskillcerts-narrow-decomposition
- **粒度金律**：每个子任务=能产出有意义可验证中间输出的最小单元——无法脱离周围步骤描述"怎样算做对"则太细；含多个独立可验证组件则太粗。
- **三分解模式**：Sequential（有序必序）/Parallel（独立并跑）/Hierarchical（orchestrator→manager→worker 树）；每模式失败特征不同。
- **四类失败模式**：①信息丢失（原始任务描述关键信息在传递中丢失→缓解=每个子任务显式携带原始任务规格，不只前步输出）；②错误分解（对典型实例好的分解对边缘实例错，如"研究并总结"实际需要计算步骤→缓解=执行中允许动态重分解）；③过度分解（协调开销>简化收益、上下文碎片化、LLM 丢全局目标）；④不足分解（子任务仍太复杂）；⑤窄分解（协调者切太窄→子主题未分配、输出连贯但残缺——根因永远是协调者分解、修复=拓宽分解非加子代理）。
- **经验区间**：每层 3-7 子任务、每个 1-5 次 agent 迭代完成；>5 迭代需进一步分解；8-25 叶任务是项目级合理区间。
- 判据：先判"这个子任务能否独立描述做对的标准"再定粒度；失败时按五类对号诊断，不盲目加 agent。

### 3. 分解深度自适应：倒 U 曲线与动态粒度（模型/工作流）
来源：arxiv-2510.23564-recode / arxiv-2604.23194-adaplan / microsoft-learn-adaptive-decomposition / acm-multi-turn-survey-adapt
- **深度是倒 U**：ReCode 消融（ScienceWorld，GPT-4o mini）最大深度峰值在 8（43.22%）；过浅限层次分解、过深过度分解碎片化决策——最优区间 6-12。
- **ADaPT 按能力调粒度**：根据 LLM 能力自适应调整分解粒度（capability-grounded），不是固定模板。
- **AdaPlan-H 粗→细**：先粗粒度宏计划，按任务复杂度渐进细化——模仿人类规划，缓解 overplanning 的同时提高任务成功率。
- **confidence-based 深度**：meta-agent 复杂度评估（simple/moderate/complex）驱动分解深度——简单查询 1-2 步直接执行、歧义/高价值任务详细多步分解；总创建 5 步计划的 planner 在简单查询上浪费资源。
- **递归分解深度控制**：max_depth 显式边界（3-4）+ 基例（可直解即停）；TOPO agent 的 adaptive atomic fission=运行时工具能力边界被超时把瓶颈节点动态劈成更细子原子。
- 判据：深度是设计杠杆不是默认值——按任务复杂度×模型能力×工具边界三层自适应，忌固定步数模板。

### 4. 重规划纪律：只失败触发 + 触发范围分类 + 预算护栏（工作流）
来源：zylos-adaptive-replanning / agentixforce-replanning / xbstack-planning-replanning / aura-frog-hierarchical-planning / ubc-long-horizon-agents
- **只失败触发，不逐步重规划**：重规划节点收三输入（原始目标+已完成步骤及其输出+触发步骤的具体失败细节）→ 产出剩余步骤修订计划、丢弃已判不必要的步骤——比每步全量重规划便宜且保自适应。
- **四类触发与作用域**：工具失败→单步+依赖者；前置条件违例→违例点子树；状态漂移→所有受影响步骤；上下文溢出→全计划重摘要+续跑。
- **预算护栏**：step caps（总步数上限 N）+ replan 上限（典型 3 次，之后边际收益递减→升级人或返回部分结果）+ circuit breaker（replan_thrash：per_node_budget=2 → escalate parent tier → 最终人工）。
- **失败分类驱动动作**：F3 类=局部设计失败（验收不可达、同测试连续两修复失败）→重分解（re-decompose）；重规划不是无限重试——每个 ReplanEvent 应点名触发观察、失效假设/步骤、受影响工件、不可逆效应、剩余预算、替换计划如何独立核验。
- **五类升级条件**：达 replan 上限/无可行替代（工具全试过且缺能力）/约束矛盾（升级问用户）/持续质量失败。
- 判据：重规划=受控变更不是无限重试——预算、作用域、升级路径三件套缺一，重规划就退化成重试风暴。

### 5. 验证先行 + 委托契约四要素 + decompose-until-testable（可复用 Skill）
来源：alexlavaee-delegation-framework / multi-ai-planning-verification-first / skillmd-task-refinement / agentixforce-decomposition
- **分解到能写测试为止**：为每个子任务输出可写测试（测试套件/类型检查/lint/build/人工复核）——无法程序化表达成功标准=粒度不够。
- **Verification-First**：先定义怎么验证再定义做什么——成功标准（SMART）+验证方法（自动化优先）+里程碑质量门。
- **好/坏标准示例**：好="5+ 单测通过（合法/非法/边界输入）"、"lint 无警告"、"性能 <100ms/1000 条"；坏="代码质量好"、"正常工作"、"已实现"。
- **委托契约四要素**：①子任务是什么 ②如何验证做对（test suite/type check/lint/build/human review）③允许用什么工具（scoped permissions）④失败时怎么办（回退/上报）。
- **层次规模**：Large 8-15 / Medium 3-8 / Small 1-3 / Atomic 1——每层"多少个子任务"是预算不是模板。
- 判据：验收可写测试才算分解完成；成功标准必须可机检，人工复核是最后手段不是默认。

### 6. 深研究与 Web 代理的任务分解（模型/工作流）
来源：arxiv-2606.17029-deeprubric / arxiv-2603.05294-structuredagent / arxiv-2510.06587-webdart / conductor-deep-research / supernodes-deepsearch / microsoft-corpgcn
- **分支因子 depth-aware**：DeepRubric 递归分解主题为子查询——根 6 个孩子、中间层 4 个，孩子共同覆盖父主题的独立平行面（机制/利益方/风险/量化证据/备选）——分支因子随深度衰减。
- **OR/AND 规划树**（StructuredAgent/Web）：AND 节点=必须子目标、OR 节点=替代策略——规划与执行交错，动态建树+可解释回退选项（网页任务长程稳定性）。
- **技能三分**（WebDART）：每目标动态分解为三个聚焦子任务=导航/信息提取/执行，一次聚焦一个技能；随新页面揭示持续重规划分解（利用新发现的过滤器/捷径、避免冗余探索）。
- **任务描述即规格**（AgentScope/OpAgent）：每个子任务是"要达到什么"不是"怎么做"；reflection 步可修订子任务列表；planner 把子任务封装 <task> 块委派执行器、输出插回 <result> 块继续推理。
- **统一意图规划**（Gemini Deep Research）：生成完整研究计划交用户审阅修订再执行——最高对齐、代价是用户参与。
- 判据：分解的"粒度×分支×何时重分"三问——深研究用 depth-aware 分支、网页任务用技能正交分解+页面揭示驱动重分。

### 7. 极端分解的 No-Recovery Bottleneck 与窄分解覆盖诊断（模型/工作流）
来源：arxiv-2603.06870-lead / aiskillcerts-narrow-decomposition / thenergentech-insider-diminishing-returns
- **极端分解结构性缺陷**：每步完全隔离执行的 memoryless 设计使局部错误不可逆——错误分布高度不均匀（集中在少数"hard"步骤），一旦单步持续错，即使多数投票也统计上不可能成功。
- **错误概率随步数累积**：子任务数越多、整链成功概率越低——过度分解的隐性代价=每一步都是潜在失败点；复杂指导中的额外约束可触发指令幻觉（模型优先跟随结构格式而非事实准确）。
- **窄分解诊断**：协调者切太窄→部分子主题未分配、输出连贯但残缺；根因永远是协调者的分解（不是子代理）；修复=拓宽分解而非加子代理或怪 spokes。
- **rolling-wave 原则**：近端工作细分解、远端工作留高层直到信息足够——避免过早 500 元素 WBS 把自己管死。
- 判据：分解到原子≠每步隔离执行——hard 步骤需局部恢复能力（回退/重试/上下文回流）；覆盖完整性检查=所有子主题都被分配且相加=原始目标。
