## 落地 5 独点（每点标注提升层）

### 1. Supervisor vs Orchestrator 细节与默认选型（工作流/可复用 Skill）
来源：nisai-multi-agent-guide / thinking-multi-agent-design / agdex-build-multi-agent
- **orchestrator 模式=默认**：一个 agent 拥有计划与最终答案，**worker 之间不互相说话、只对 orchestrator**——**状态与错误都只有一个明确主人**。
- **supervisor 模式**：编排 agent 分解任务→委派专家 agent→综合输出，supervisor 维护执行计划并根据中间结果调整（**工具访问=仅 agent 调用，不给直接外部工具**）。
- **分层（hierarchical）**：manager 委派+综合，workers 无全貌执行——最常用（映射管理结构），**结构性弱点=manager 成瓶颈与单点，misjudge 子任务则下游全继承错误**。
- 判据：先默认 orchestrator；需要动态调整计划用 supervisor；组织复杂度高才分层。

### 2. Router with Confidence Gating（模型/工作流）
来源：velsof-orchestration-patterns / sudoall-coordination-playbook
- **路由三模式**：**分类路由（router）最便宜最快，但 confident-but-wrong 变成生产事故**；**naive router 只选 N 类之一交接，生产级 router 必须输出类别+置信度，派发层按阈值放行**（低置信度转人工/默认路由）。
- **任务分解判据**：**子任务是否真正独立**（共享代码库/数据库行/活文档=不独立，再像也不行）——真独立才并行（orchestrator-worker），必须顺序走 pipeline。
- **成本判据**：多 agent 的产出质量提升值不值额外 token/延迟——不值就单 agent。
- 判据：router 必带置信度+阈值+兜底路由；"genuinely independent"才并行。

### 3. 通信协议四类：直接 / 共享 / 广播 / 协议驱动（工作流/可复用 Skill）
来源：techrxiv-architecting-multi-agent
- **四类通信**：①**直接通道**（点对点）；②**共享**（黑板/共享状态）；③**广播**；④**协议驱动**=把交互结构化为正式类型化交换（拍卖/讨价还价/辩论/共识——消息编码 bids/proposals/proofs+显式终止条件，**MCP 与 agent-ready API 标准背书**）。
- **协议驱动的主要工程收益=可审计性与协议规则的正式分析**——比自由对话更可验证。
- 判据：需要可审计/可形式化分析的协作（共识/竞拍/辩论）用协议驱动；简单委派用直接通道。

### 4. 失败模式四类与恢复（工作流/工具）
来源：metacto-multi-agent-systems
- **生产多智能体必须优雅处理失败，四类**：**Agent 失败**（另一实例接管/优雅降级）；**通信失败**（退避重试/换路径）；**级联失败**（**熔断器防一个失败 agent 淹没其他**）；**状态损坏**（**检查点恢复到最后已知良好状态**）。
- **成本管理**：多智能体=多倍 token 与延迟——按需扩缩容（demand-based auto-scaling），不恒定全开。
- 判据：设计时把四类失败各配恢复策略；级联用熔断、状态用检查点；成本按需伸缩。

### 5. 何时不用多 agent：决策树与单 agent 优先（工作流/可复用 Skill）
来源：sudoall-coordination-playbook / empirium-multi-agent-architecture
- **决策树三问**：①任务能拆成真正独立的子任务吗（不能→单 agent 或 pipeline）；②产出质量提升值不值得多倍成本（不值→单 agent）；③协调复杂度是否超过单体复杂度（超过→别拆）。
- **pipeline 的代价=总延迟是各 agent 延迟之和**（5 个 2 秒 agent 至少 10 秒），但每阶段输出独立可检查、天然人工复核点。
- 判据：**"大多数系统不需要多 agent"**——先问三问，默认单 agent；要拆才选模式。
