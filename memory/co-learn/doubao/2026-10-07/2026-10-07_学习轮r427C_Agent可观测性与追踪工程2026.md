## 落地 5 独点（每点标注提升层）

### 1. Trace 三层结构与全执行图（工具/可复用 Skill）
来源：langchain-llm-monitoring / langchain-agent-observability / braintrust-ai-observability-guide / sentry-ai-observability
- **trace/run/span 层级**：trace=应用从收到输入→中间处理→最终输出的**步骤序列**；run=trace 内每一步（≈OTel 的 span）；span 成树（父=用户会话，子=每次 LLM 调用/向量检索/工具执行）。
- **agent 可观测=捕获 agent 间 handoffs 与全系统执行图**（不是只有输入输出，还要暴露内部 monologue 与每步传给模型的精确参数）。
- **trace=AI 系统的 call stack**——不只显示发生了什么，还显示怎么发生为什么（决策路径完整重建）；**sessions=多轮/多步交互的分组**，把 agent 一次复杂工作流归组理解。
- 判据：agent 追迹粒度=每次 LLM call/tool 调用/handoff 都是独立 span；跨 agent 传递必须 trace 上下文延续。

### 2. OTel GenAI 语义约定 + 防孤儿 span（工具/工作流）
来源：pythondatabench-otel-genai / mlflow-measuring-latency / pypi-agentrace / aiworkflowlab-llm-observability
- **OpenTelemetry GenAI semantic conventions**：SIG 2024-04 成立，2026-05 仍标 Development，Datadog/Google 等已采用——**标准 span 属性 gen_ai.system / gen_ai.request.model / gen_ai.usage.input_tokens** 做厂商中立一致追踪。
- **token counts 不可少**：每个 LLM span 记录 ai.input_tokens / ai.output_tokens——**没有它们成本归因不可能**。
- **W3C Trace Context 全面注入**：traceparent 进 HTTP headers / queue messages / gRPC metadata——**防 orphan span**。
- **prompt capture 默认 opt-in**：默认关，只在受控环境（访问受控存储）开启。
- 判据：起点=semantic conventions（厂商中立）；token 计数每 span 必记；跨进程/队列/gRPC 都带 trace context；prompt 明文默认不落。

### 3. Trace-to-eval 链接：生产轨迹直接当评测 ground truth（工作流/可复用 Skill）
来源：futureagi-traceai / mlflow-data-flow-monitoring / databricks-eval-first-zepto / langsmith-observability
- **2026 默认模式**：给**同一批发出 prompt/completion 的 span** 打分——**trace 成为评分 ground truth，不重跑 agent**（TraceAI fi.evals）。
- **LLM-as-judge 采样 10–20% 生产流量**：平衡质量覆盖与评估成本，不是全量也不是不评。
- **traces=eval 数据集的来源**：debug 时把失败 run 标注/反馈 → 收集成 eval 集；**dual loop=生产 traces + 离线 evals 双闭环**（Zepto 客服案例）。
- 判据：生产观测与离线评估同数据源；每个失败案例都进 eval 集；评估成本用采样控制。

### 4. Agent 可观测四层 + 成本归因与硬护栏（工具/工作流）
来源：aws-agentops / traccia-docs / infoq-session-traces-cost-controls
- **四层可见性**：①agent & framework telemetry（决策/推理步骤/模型调用/工具调用/响应）②service telemetry（**framework 外**发生的 memory 读写、gateway 认证路由、identity/policy 评估、内置工具调用）③④基础设施层——**agent 依赖的服务层操作在 framework 外，单独打点**。
- **per-agent/model/tool 成本归因**：token 用量与成本按 agent/模型/工具归账；**policy guardrails=spend limits / retry caps / 自定义规则**等硬护栏。
- **agent 反复调用错工具不触发可用性告警=可观测盲区**——需要 session traces + 成本控制才能诊断这类"静默失败"。
- 判据：框架外依赖（memory/gateway/policy）单独层打点；成本按 agent/模型/工具归账；守卫=预算/重试上限硬护栏。

### 5. 观测驱动的护栏配置（guardrail 观测化）（工具/工作流）
来源：devblogs-microsoft-foundry-open-trust-stack / infoq-observability-ai-agents / langsmith-observability
- **Guided Guardrail Setup**：短问卷（audience / data access / use case）→ 针对场景的个性化 guardrail 推荐（PII 过滤 / 越狱防护 / task adherence）——**多数团队知道需要 guardrail 但不知道哪些适用**，问卷把"该配哪些"变可操作。
- **OTel-native tracing + self-hosted LLM-as-judge 同平台**（Arize Phoenix）：tracing 与评估不分离。
- **自动检测 traces 中的重复问题**：从生产 trace 自动发现反复出现的问题、诊断根因、解决（LangSmith Engine）——重复问题检测从手工翻 trace 变自动化。
- 判据：护栏按场景问卷配置而非模板堆砌；tracing 与评估同一平台闭环；重复问题检测自动化。
