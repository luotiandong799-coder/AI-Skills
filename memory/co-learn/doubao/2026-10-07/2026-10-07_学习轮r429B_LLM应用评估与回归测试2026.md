## 落地 5 独点（每点标注提升层）

### 1. 评估驱动开发（EDD）四级台阶（工作流/可复用 Skill）
来源：chiraghasija-eval-driven-dev / arxiv-MVES
- **Level 1=Golden Dataset（地基）**：固定输入集+标注期望输出（或质量判据），跑管线逐条打分——分数成为可随时间追踪、可门禁部署的数字；golden_dataset.jsonl 每行一例（id+输入+期望）。
- **Level 2+ 逐级递进**：在黄金集之上建回归基线、按失败模式扩充、接 CI 门禁——"没有数字就没有改进"。
- **MVES（Minimum Viable Evaluation Suite）=分层的评估组件集**：通用 LLM 应用 / RAG / agentic tool-use 各配最低可行评估件。
- 判据：评估驱动开发从黄金集起步；先有可追踪的数字，再谈门禁与优化。

### 2. RAGAS 五指标：RAG 管线的回归套件（工具/可复用 Skill）
来源：aitestingguide-ragas / blog-codercops-llm-evals / latitude-regression-testing / aiworkflowlab-eval-ru
- **RAGAS=开源 Python 框架，LLM-as-judge 打分评估 RAG 管线质量**；**五指标**=faithfulness（忠实度）/answer relevancy（答案相关性）/context precision（上下文精确率）/context recall（上下文召回率）/answer semantic similarity（答案语义相似度）——跨检索层与生成层。
- **多数指标无需人工标注 ground truth**——适合自动 CI/CD 管道（灵活性来源）。
- 覆盖典型 bug 面：faithfulness/answer relevance/context precision/recall/entity recall。
- 判据：RAG 功能优先用 RAGAS 五指标做回归；无 ground truth 也能自动评分是 CI 可行的关键。

### 3. LLM-as-judge：放大主观评分，但偏置是已知弱点（模型/工作流）
来源：myengineeringpath-llm-eval-guide / deepeval-llm-as-judge / dataaihub-llm-evaluation / arxiv-MVES
- **原理**：用更强 LLM 按明确判据给目标模型输出打分（输入+目标输出+评估判据+可选参考答案→结构化分数+推理）——比人工扩展性好、判据明确时与人工判断相关性高。
- **已知 judge 失败模式（必须防）**：偏置（位置/长度/自恋/格式偏好）、判据定义模糊导致相关性崩、判据不明确时相关性差——**判据要 well-defined**。
- **DeepEval 技法选择**：GEval=自定义质量判据；JevEval=可表达为有界问题+固定数学打分；DAGMetric=严格多步评分逻辑。
- **评分器按失败模式组合**：exact match/schema（结构化路径）→task validators（代码执行/API 检查）→LLM-as-judge（主观质量 pointwise/pairwise）→人工标签（校准）。
- 判据：主观质量用 LLM-as-judge 但必须过"判据是否 well-defined"关；把偏置当已知缺陷设计（对比打分/锚定示例/防位置偏置）。

### 4. 回归测试分层：三层标准栈（工具/工作流）
来源：aiworkflowlab-evals-tr / latitude-regression-testing / myengineeringpath
- **2026 三层标准**：**规则型指标**（exact match/JSON schema）→ **静态参考指标**（BLEU/ROUGE/BERTScore）→ **LLM-as-judge**（G-Eval/pairwise）。
- **回归门禁**：每次 prompt/model/管线变更都跑 golden test set（50-200 真实案例）当回归套件；**从生产失败扩充测试集**——生产翻车案例优先补进 golden set。
- **工具分工**：DeepEval=pytest 集成（LLM 应用单元测试）；Promptfoo=YAML-first CLI 工作流；RAGAS=RAG 管线评估。
- 判据：任何变更（提示/模型/管线）进生产前先过回归；生产失败案例必进测试集（不让同一个错第二次漏网）。

### 5. "更好"的提示也会伤害：评估驱动迭代防负优化（模型/工作流）
来源：arxiv-MVES-when-better-prompts-hurt
- **标题即结论**：评估驱动迭代框架 + 可复现本地实验——**"更好的"提示实际可能更差**，没有评估的提示工程是盲目优化。
- 用法：每次提示/模型/检索改动都跑同一评估集对比分数——**改动前先建立基线，改动后 diff 分数**；用本地可复现实验验证再上生产。
- 判据：提示改动必须过基线对比，不靠"感觉更好"上生产；评估集本身要随失败模式持续扩充。
