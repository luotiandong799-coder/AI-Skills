## 落地 5 独点（每点标注提升层）

### 1. 测试四层模型：单元/集成/模拟/端到端（工作流/可复用 Skill）
来源：zylos-ai-agent-testing-strategies / codex-agent-testing-frameworks / kanopylabs-ai-agent-testing / openlegion-ai-agent-testing
- **单元=验证单个工具**；**集成=验证 agent 按正确顺序、正确参数调用正确工具**（Mock MCP Server 模式：**canned responses 定义好，断言工具调用序列**——把 AI 模型从测试循环里拿出来，可复现）；**模拟=合成但逼真的场景**（见独点 2）；**端到端=全管线+真实模型**（最贵最有价值，验证最终结果正确）。
- **e2e 场景套件建立在 golden dataset 上**：精选真实用户请求+期望结果——e2e 每例含一次或多次 LLM 调用（花钱花时间），按价值排序跑。
- 判据：先 mock 断调用序列（把模型移出循环），再上真实模型场景；四层各司其职不互相替代。

### 2. 模拟环境两难：fidelity（保真）与 coverage（覆盖）同时满足（工具/工作流）
来源：zylos-ai-agent-testing-strategies / saipien-toolsimulator
- **模拟集成测试的两大工程挑战**：**fidelity=模拟环境必须够像真实，测试结论才可迁移**；**coverage=模拟必须生成压力 agent 失败模式的场景**。
- **成熟模拟 harness 标配**：**synthetic tool backends**（每个工具的真实数据假实现，可注入边界情况：空结果/异常/限流）。
- **ToolSimulator=LLM 驱动的外部工具模拟**（介于静态 mock 与真实集成之间）：**有状态、尊重契约、保护隐私**——不碰真实 API 就能规模化测 agent。
- 判据：模拟工具不是"随便 mock"，要保真（结果形态像真的）+可注入失败模式；LLM 驱动模拟可覆盖静态 mock 够不着的状态化场景。

### 3. 确定性轨迹重放（Deterministic Trace Replay）：隔离模型漂移（工具/工作流）
来源：testquality-how-to-test-ai-agents / kunalganglani-agent-eval-harness / openlegion-ai-agent-testing / aiflowreview-ai-agent-replay / moai-ai-agent-replay
- **问题**：网络延迟/限流/瞬时模型退化会让测试套件在应用代码正确时也失败——**基础设施可变性污染测试结果**。
- **解法**：首次测试运行记录 LLM 响应与工具载荷，后续 CI 重放——**隔离 agent 编排逻辑与基础设施波动、降推理成本、让失败可归因于代码变更而非模型漂移**。
- **任务重放测试**：录制生产 agent 运行（每个工具调用+参数+返回值），CI 用录制响应当 stub 重放——**高保真回归、抓纯合成 fixture 抓不到的问题**。
- **回放调试清单**：重放失败运行→diff 轨迹（工具选择/参数/中间摘要/重试）→分类根因（模型漂移/提示变更/工具契约变更/检索漂移/策略变化）→**找第一个分歧步，不看最终错误答案**。
- 判据：agent 回归测试默认录制重放；失败排查定位第一个分歧点；轨迹 diff 优先于最终答案对比。

### 4. 安全重放四步：冻结输入/恢复检查点/注入录制响应/重定向写（工作流/工具）
来源：aiflowreview-ai-agent-replay
- **Safe replay**：**冻结输入→从有效检查点恢复→注入录制响应→把写操作重定向到沙箱或 mock**——重放不产生真实副作用。
- **回放保留决策路径**：检索证据/模型输出/工具调用/策略决策/重试/状态变化全记录（不只最终响应或失败 API 调用）——append-only 事件日志供检查，快照供快速恢复，长工作流（昂贵检索/浏览器自动化/代码执行）用混合设计。
- 判据：重放必须安全（写重定向）；决策路径全量保留才能审"这个自主决定是怎么做出的"。

### 5. 编排测试的脊柱：持久 run ID + pass@k（工作流/工具）
来源：volanea-testing-ai-agent-workflows / testquality-how-to-test-ai-agents / kunalganglani
- **一个 canonical run ID 是整个工作流的脊柱**：每个日志/轨迹/内部状态迁移/外发请求/webhook/重试/补偿动作/人工介入都挂到它——**跨供应商不盲目复用同一裸值，而是从单一持久工作流身份派生稳定、目的特定的标识符**。
- **pass@k 定义**：生成 k 个候选输出，至少一个通过的占比——评估 agent 在多次尝试下的成功率。
- 判据：编排型 agent 先定 run ID 脊柱再谈测试；成功率评估用 pass@k 而非单次 pass。
