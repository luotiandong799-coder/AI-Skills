## 落地 5 独点（每点标注提升层）

### 1. 评审编排架构：Coordinator 大脑 + 上下文组装优先（工具/工作流）
来源：niteagent-ai-code-review-agent / bridgeapp-ai-code-review-pipelines
- **Coordinator（编排者）=大脑**：接收 MR 元数据、diff、历史发现、项目指令，**决定 spawn 哪些 agent、用哪些模型、何时重试或放弃**——多 agent 评审由单一协调者驱动生命周期。
- **编排者最关键职能=context assembly**：在 agent 开始评审前收集齐 git history、相关文件、CI 状态——"上下文没齐就让 agent 开工"是评审失准的头号原因。
- **JSONL=AI review 编排事实标准日志格式**：每行一个 JSON 对象事件（step_start / step_finish / error / token_usage / heartbeat）——CI 系统增量解析，断点可续。
- 判据：评审管线先设计"谁组装上下文"再设计"谁审什么"；全程 JSONL 事件流日志便于增量解析与审计。

### 2. Agentic review 部署四模式 + 审批边界（工具/工作流）
来源：msbart2-copilot-code-review-deck / github-docs-copilot-code-review / awesomecodereviews-ai-code-review-tools / morphllm-github-ai-review
- **四部署模式**：**Repository Ruleset**（Settings→Rules→Rulesets，自动审查每个 PR）/ **Organization Default**（org 级默认 effort，各仓库继承）/ **Branch Protection**（设为 required status check——**critical 发现未解决前阻塞 merge**）/ **Manual Request**（PR 评论 @github-copilot 定向聚焦分析）。
- **effort 分级**：Lite=例行变更，Balanced=复杂变更。
- **审批边界**：AI 审查留 inline 评论与 suggested changes，**不 approve / 不 request changes / 不满足 required human approval**——最终审批权与合并门禁保留给人。
- 判据：自动审查用 ruleset/required status 挂进门禁，但 AI 不参与 approve/merge 决策。

### 3. 自审循环：coding agent 开 PR 前先审自己（工作流/可复用 Skill）
来源：github-blog-copilot-coding-agent / vscode-copilot-best-practices / furybee-agentic-coding-assistants
- **开 PR 前自审**：Copilot coding agent 先用 code review 审自己的改动→反馈→迭代→改好再开 PR——**"你被 tag 时已经有人先审过一遍"**（实测抓到自己的字符串拼接过度复杂并修掉）。
- **VS Code 官方三阶段**：**Plan（先审计划再执行）→ Implement（agent 模式+把测试或预期输出写进提示让 agent 自验）→ Review（checkpoints 检查进度、跑偏回退、请求 code review）**。
- **agentic coding assistant 的本质=操作循环**：读文件→形成计划→跨代码库编辑→跑测试→读失败→再编辑——工程重点不在代码生成而在循环的可靠性。
- 判据：生成与审查同 agent 闭环；把"预期输出"写进实施提示；每阶段设 checkpoint 可回退。

### 4. 人机评审分工 + 修复工作流（工作流）
来源：techcommunity-copilot-azure-repos / aitoolsguidebook-ai-agent-review-workflow / coderabbit-agentic-sdlc
- **分工边界**：AI=早期反馈（正确性/安全/可维护性/可测试性）；**人工保留=领域知识/架构/合规/code-owner 审批**。
- **一次只修一件事**：对每条明确正确的评论只做"最小 patch、无行为改变"，**分别 commit 让修复在历史里可见**。
- **对噪音推回去**：风格类标记问"这对既定意图为什么重要"——真噪音 agent 会退让，不退让就听它的。
- **re-review 更新后的 diff**：迭代到 agent 只剩噪音为止。
- **修复路径必须内建**：10 条有用评论如果每条都要开发手动复制给 agent，评审就变成拖累——一条命令批量 remediate（CodeRabbit 模式）。
- 判据：AI 审"代码层面"、人审"业务层面"；修复逐个 commit 可回溯；remediation 有批量通道。

### 5. 安全评审是 AI 已知弱点 + severity 分级输出（工具/工作流）
来源：refacto-copilot-review-limits / github-blog-60m-copilot-reviews / dev-to-mastering-code-reviews / expertinsights-ai-code-review-tools
- **安全弱点已实证**：学术研究显示 Copilot review 常漏 SQL injection / XSS 等关键漏洞，**偏向低严重性的风格格式问题**；GitHub 官方承认可能漏安全问题、建议可能含漏洞代码——**不能替代专用安全工具**。
- **severity 分级表输出**：每条发现=Severity（Critical/High/Medium/Low）+ Location + Issue + Fix 建议（如 register.ts:45 无 rate limiting → 加 express-rate-limit 中间件）。
- **对话式修复**：Snyk Agent Fix=评论给严重性+数据路径（问题怎么到达该代码），**@snyk /fix 生成最多 5 个候选修复、@snyk /apply 提交选中的一个**——候选各自针对同一问题生成。
- 判据：AI 评审按严重性分级输出、每条带位置+修复建议；安全类问题必须叠加专用安全工具，不把 AI 当唯一防线。
