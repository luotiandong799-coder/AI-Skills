## 落地 5 独点（每点标注提升层）

### 1. OTel GenAI 语义约定：标准化 span 而非自定义日志（工具/可复用 Skill）
来源：sentry-ai-agent-observability / signoz-llm-observability
- **OTel gen_ai 语义约定=agent 系统标准化插桩**：每个 AI 操作产出带一致属性的结构化 span，替代自定义日志。
- **核心 span 操作**：`gen_ai.request`（单次模型调用：模型名/prompt/response/token 数）、`gen_ai.invoke_agent`（完整 agent 生命周期：任务开始到最终输出）；**tool span 带 `gen_ai.tool.type`/`gen_ai.tool.description`；agent span 带 `gen_ai.agent.name`/`id`/`description`**；失败统一按 `ai.error.type`（rate limit/timeout/parse failure）归类。
- 判据：插桩先按语义约定走标准 span 属性；非标属性另挂，不污染约定字段。

### 2. trace ID 是全程的"游戏"：从 API 响应一路传到值班工程师（工具/工作流）
来源：avghumans-agent-span-observability / devto-llm-observability-trace-cost-sampling
- **每个 LLM 调用、工具调用、检索各插桩为独立 span，经 OTLP 导出到 LLM 原生后端（Langfuse 推荐；已在 Datadog 生态就用 Datadog LLM Observability）**；**每个生成 span 挂 token 数与成本；trace ID 从 API 响应一路传播到值班工程师**——排查"agent 为什么走偏"的唯一抓手。
- **根 span 包裹每个用户操作，所有 LLM/检索/工具调用作为子 span**。
- 判据：没有端到端 trace ID 传播，可观测性只剩日志拼图；span 层级=用户操作(根)→LLM/工具/检索(子)。

### 3. 成本归因到 agent：没有 per-agent 归因无法定位成本尖峰（工具/工作流）
来源：zylos-agent-observability-cost-attribution / mlflow-measuring-ai-call-latency / infoq-session-traces-cost-controls
- **成本尖峰时没有 per-agent 归因=无法定位责任人/检测模型更新后的行为漂移**；**OTel GenAI SIG 提案扩展 agentic 原语集=六族约定（Tasks/Agents/Teams/Artifacts/Memory）**（issue #2664，未正式化但在设计中）。
- **指标集**：错误率（per tool/model/error type）、token 趋势（per run/feature/tenant）、成本 `ai.cost_usd`（token 数×模型价格表）、缓存命中率（检索+prompt caching）。
- **LangSmith 把异常生产 trace 转成回归测试数据集**；Arize Phoenix=OTel 原生 tracing+自托管 LLM-as-judge。
- 判据：多 agent 系统必须 per-agent 成本归因；异常 trace 反哺测试集形成闭环。

### 4. 采样与隐私：正文默认不采集（工具/工作流）
来源：devto-llm-observability-trace-cost-sampling / aliyun-ai-observability-coding-agent
- **可观测性成本与隐私要主动管**：**采样**（全量 trace 太贵——按需/按尾采样）；**隐私**（prompt/response 正文是敏感数据）。
- **编码 Agent 探针实践（阿里云 CMS LoongSuite）**：基于 OTel GenAI 标准构建调用树，全景还原推理链路/token 消耗/重试轨迹；**零代码侵入、正文默认不采集**、导出失败被隔离不影响模型调用与工具执行。
- 判据：插桩默认"元数据+摘要"，正文按需开启；采样策略先于大规模上量。

### 5. LLM 生产可观测性定义：解释"做了什么/为什么/花了多少/是否可接受"（工具/工作流）
来源：isx4-llm-observability
- **LLM 生产可观测性=端到端遥测（trace/log/metric）收集分析，解释系统做了什么、为什么、成本多少、行为是否可接受**——区分于监控（实时定量数据+看板/告警/根因）。
- **Honeycomb 类通用工具**擅长对比异常查询与成功基线分布，但**缺原生 prompt 版本管理/agent 评估库/LLM 指标**——LLM 原生后端（Langfuse/LangSmith/Phoenix）补短板。
- 判据：观测=事后解释全链路（含成本与行为可接受性），监控=实时阈值；通用工具+LLM 原生后端互补而非二选一。
