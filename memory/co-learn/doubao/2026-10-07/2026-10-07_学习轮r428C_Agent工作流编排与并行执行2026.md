## 落地 5 独点（每点标注提升层）

### 1. n8n 错误处理七模式 + 全局错误工作流（工具/工作流）
来源：workflowden-n8n-error-patterns / rajsuyash-n8n-error-handling / calmops-n8n-advanced-patterns / n8nautomation-error-handling / github-czlonkowski-n8n-skills
- **七模式清单**：①Retry On Fail（抖动 API/瞬时网络）②Error branch（单节点失败需专属路径）③Global error workflow（统一告警通道）④Error classification（不同状态码不同反应）⑤Exponential backoff loop（限流/重试需减速）⑥Idempotency check（**重跑绝不能处理同一 item 两次**）⑦（Stop and Error 显式失败）。
- **全局错误处理工作流**：建一个**专职处理其他工作流错误的工作流**，Error Trigger 节点起步，内含告警（Slack/Gmail）+日志（Sheets/Airtable）；关键参数=errorWorkflow（独立错误工作流）/continueOnFail（失败继续）/retryOnFail（启用重试）/maxTries/wait。
- **错误消息要完整**：workflow name + node name + execution ID + full error message——调试快得多；**故意制造失败测试错误处理**（HTTP Request 指向无效 URL 验证错误流真的触发）。
- 判据：错误处理全局化（一个通道收所有错）而非每个节点各自为政；告警消息带可定位四件套；重试与幂等成对设计。

### 2. AI 工作流降级阶梯（工作流/可复用 Skill）
来源：blog-n8n-production-playbook / blog-n8n-ai-agent-architecture / ai-guide-expert-state-management
- **三级降级**：**retry with simpler prompt**（响应没达 schema/质量线→更受限 prompt 缩小 agent 决策空间）→ **fall back to simpler model**（复杂 agent 链在特定输入反复失败→路由到单步 LLM 调用+窄范围 prompt，用灵活性换可靠性）→ **escalate to human**（关键流程永远保留人工审查路径）。
- **LLM 输出不确定→显式 fallback 路径建进 workflow**：高 tier 模型多次尝试仍产不出有效 tool call → 自动路由 HITL 或确定性安全路径，**防全系统停滞**。
- **错误策略按类型选**：fail-branch（错误时切另一执行路径——需替代逻辑/恢复处理时）/ retry（固定次数自动重试——瞬时错误超时/限流时）。
- 判据：每个 AI 节点背后都要有"降级链"；降级终点必须是确定性的（人审或安全路径），不许停在"再试一次"。

### 3. 自愈 agent 四通道 + 看门狗（工具/工作流）
来源：williamspurlock-self-healing-agents
- **四通道恢复**：**Retry path**（Wait 节点退避→同 jobId+attempt 计数器重新入队）/ **Compensation path**（专用子工作流撤销已知副作用）/ **Dead-letter**（失败写 agent_dead_letters 表）/ **Escalate**（Slack/Email+证据包给人工）。
- **Watchdog workflow**：每 5 分钟调度，检查积压/卡死任务——自愈系统的哨兵。
- 判据：每个失败任务都有去处（重试/补偿/死信/升级四选一），不允许"失败即消失"；副作用型操作必须有补偿路径。

### 4. 多 agent 协调五模式 + 选择判据（工具/工作流）
来源：rapidclaw-orchestration-patterns / qubittool-orchestration / tentoro-enterprise-orchestration / shogo-multi-agent-orchestration / aipromptshub-multi-agent-coordination
- **五模式**：**Sequential**（严格数据依赖，成本最低最好调试）/ **Parallel fan-out/fan-in**（独立子任务）/ **Hierarchical**（规划+执行分层）/ **Pub-Sub**（松耦合事件驱动）/ **Blackboard**（共享内存开放式）。
- **选择判据**：**agent 数量 × 任务动态性 × 容错要求**——supervisor 适合 3-8 agent 确定性流程；swarm 无单点故障（客服/动态对话）；hierarchical 15+ agent 企业级；**选错模式是多 agent 系统贵 3-5x 的最常见原因**。
- **centralized supervisor 企业默认**：所有协调走单一编排者，**通信开销与 agent 数线性**、单一可审计控制点；orchestrator 用强模型、worker 用便宜专用模型可省 **40-60% 成本**。
- 判据：按（数量×动态性×容错）三轴选模式不按喜好；成本敏感时编排者强模型+执行者弱模型分层。

### 5. 流程版本化 + 可复用组件 + 指令/知识分离（工具/工作流/可复用 Skill）
来源：community-ibm-prototype-to-production / langflow-cuga-enterprise / langchain-paid-media-agent
- **部署的是版本不是画布**：显式选择哪个版本 flow 上线——更新受控可预测；**flow 变成可复用工具**（可被不同 agent/工作流调用，不是单一 endpoint）；跑在托管环境内（安全控制/可审计）。
- **planner-executor 隔离**（Langflow CUGA）：规划者拆解跟踪整体计划与进度，**子任务隔离免被过大上下文污染**；smart coder agent 执行 glue code 处理循环/条件/数据转换。
- **可复用指令与公司知识分离**（LangChain paid media agent）：**skills 解释"怎么做"、知识库提供"事实"**——好 workspace 让 agent 自由调查新问题，**不需要为每个问题建专门 workflow**。
- 判据：流程按版本发布可回滚；重复逻辑抽成可复用 flow 组件；"怎么做"放 skills、"事实"放知识库，别混在一个 prompt。
