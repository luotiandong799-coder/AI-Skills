## 三、本轮独有点（判重净新）

- **① 收到超时码 ≠ 工作停了**：deadline 是绝对时间点、timeout 是时长，gRPC 与 .NET 双官方「默认不设＝可能永远等」；客户端 `DEADLINE_EXCEEDED` 与服务端自动 `CANCELLED` 是两侧行为，Microsoft 更明写「HTTP 请求已中止但 gRPC 调用仍跑到方法完成」。⇒ 验收断言落到「派生工作/子查询/后台任务是否停了、每个异步 DB/HTTP 调用是否接了 `CancellationToken`」，不是「调用方拿到超时错误码」；昂贵计算前先查 `IsCancelled()`，运行中周期性查。
- **② 传播的是「扣掉已耗时的 timeout」不是绝对时间点**：跨主机时钟不同步，官方算例 2s 预算花掉 0.5s 后给下游 1.5s；自动传播按语言分叉（C++ 显式启用 / Java·Go 默认 / .NET 需 `EnableCallContextPropagation()`），多 deadline 取最小，且 deadline **跨所有重试累计**、超限跳过剩余重试。⇒ 规格固定四栏（入口总预算 / 每跳已耗时 / 该跳剩余 / 子预算 < 父剩余），总预算在入口一次设定，禁止每跳各自拍 timeout；换语言/客户端工厂须重新验证「框架会传播」。
- **③ Context 是取消树，取消原因要可归因，收尾要显式脱离**：父取消→所有派生同取消；漏调 `CancelFunc` 泄漏子与定时器直到父取消（go vet 机检全路径）；context 不存 struct、作第一参数 `ctx`、不传 nil、Values 只放跨进程请求域数据；`Canceled`（人为/上游）与 `DeadlineExceeded`（时限）两类错误分开计数归因，禁止把用户取消当服务端错误报警；`Cause()` 由首次取消定、父子各自取消各保留自己 cause；**收尾/清理动作须显式 `WithoutCancel`**（无 Deadline/Err、Done=nil）并写明，否则超时连补偿、日志落盘、outbox 标记一起砍掉。
