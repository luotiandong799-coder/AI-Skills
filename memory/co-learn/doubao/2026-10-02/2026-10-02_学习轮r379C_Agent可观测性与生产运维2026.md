**2. LLM 网关加权路由与 fallback 三模式**（来源：LLM Gateway《Provider Failover》2026-04-11 + LLM Gateway《Routing》2026-09-27 + MetaCTO《Routing Guide》2026-06-16 + NerdLevelTech《Model Recall》2026-06-17 + 腾讯云《多模型路由》2026-09-30 + AI/TLDR《Failover》2026-06-12 + flatkey《Fallback Checklist》2026-07-15 实拉）：**路由不做轮询/随机：按最近 5 分钟实时指标给每个供应商加权打分（四因子加权：延迟/错误率/成本/可用性，可解释的决策）；fallback 三模式=同层异供应商（Claude 挂→GPT 接，能力近恒定、隔离单供应商事故，需 prompt 可移植）/同供应商降层（GPT-5 挂→mini，恢复快成本低能力降，任务宽容时可用）/紧急成本底线（open-weight 兜底，需求尖峰时开源定价稳）；2-3 个 fallback 够（1 主+2 备平衡可用性与控制，长链=长等待/成本跳/不一致答案）；fallback 触发边界=只对容量与可靠性问题切（错误率/限流/超时），安全错误/校验错误/上下文长度问题不切模型（换模型会行为不一致）；生产用 auto 路由（auto=成本性能平衡/smart=自选模型集）；可观测性门=能重构请求的模型/选中模型/供应商/尝试链/错误/成本（失败的成功=成功终态隐藏失败路由尝试与预算影响，阻断）；处理=会话黏性（同会话尽量同供应商保 prompt cache）/重试风暴（限流重试用指数退避+jitter）/结构化输出兼容（跨供应商 schema 行为差异）**。提升层：工具/工作流。

**3. **4. 结构化输出工程：schema-first + constrained decoding**（来源：effloow《Structured Outputs》2026-04-17 + PrecisionAI《100% Reliable JSON》2026-04-16 + nisai《JSON Mode Schemas》2026-07-14 + AWS《Schema-Compliant》2026-02-06 + TianPan《Structured Outputs in Production》2026-04-07 + FutureAGI《Evaluating Modes》2026-05-20 实拉）：**schema-first 开发=①先用 Pydantic（Py）/Zod（TS）定义数据结构 ②从定义自动生成 JSON Schema ③prompt 按 schema 建不反过来 ④LLM 输出在进业务逻辑前用同一模型验证——消除 prompt 与 parser 对形状期望不一致的整类 bug；constrained decoding/严格模式=生成层强制 schema 合规（每个 token 采样过掩码过滤），保证"若调用返回 JSON 必可解析"（OpenAI strict/Outlines/Bedrock）；工程要点=5 层嵌套/100 属性上限（深嵌套 4+ 层错误率可测升高——问嵌套反映数据层级还是组织偏好）、每个字段写 description（"ISO 8601 日期，如 2026-07-14" 远胜裸 string）、enum 激进（只允许某些值时枚举防漂移：invoice/invoice_/INVOICE）、尽量 flatten、解析后仍验证（constrained decoding 也验）；失败形=严格模式 required-by-default 静默丢可选字段/schema 过复杂拒答→retry（供应商退避）+field/model validator 声明式检查；vLLM/Ollama 本地=实现质量取决于模型/分词器/后端/schema 复杂度**。提升层：工作流/可复用 Skill。
