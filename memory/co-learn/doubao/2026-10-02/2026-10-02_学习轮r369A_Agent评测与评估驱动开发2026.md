## 独点（10）

**1. LLM-as-judge 生产化：失败模式已知+校准流程+judge 自身评测**（来源：langchain-agent-evals + microsoft-ax-evals + arxiv-2608.11434 + arxiv-2608.26623 实拉）：**judge 四失败模式=verbosity bias（长输出分高不论质量）/scoring drift（时间漂移）/位置偏见/自利偏好（judge 偏爱与自己同源模型的输出）**——人类审 50-100 traces/小时，1000 请求/天需 10-20 小时人工，LLM judge 是规模化默认但失败模式已知；**校准=在已知正确裁决的真实 agent 输出上迭代 criteria 直到 judge 与专家一致，每项检查定义 pass/fail/skip，过明确化优于欠明确化**；**run 5 次每条件——结果一致就有答案，分歧就多跑**；**judge 自身也要被评测（AgentJudgeBench 四指标=工具选择/参数结构/序列准确/查询覆盖；MobileJudgeBench 931 条人工标注轨迹评测 6 种 judge）**。判据：**judge 是可调校的测量仪器不是圣旨——先校准再信任，judge 本身也要过基准**。提升层：可复用 Skill。

**2. Eval harness 四层：replay/rubrics/CI gate/生产监控**（来源：kunalganglani-harness + niteagent-harness + mavik-harness + ml-digest-harness 实拉）：**把 agent 当软件测=跑 golden 端到端任务，record-replay 工具调用让测试稳定（replay=录制真实工具调用序列重放，去非确定性），rubrics 清晰规则评分，CI 阻塞回归**；**harness 要素=fixtures（测试集）/rubrics（评分标准）/canaries（早期预警）/replay（调试）**；**三层=Layer1 离线黄金任务/Layer2 回归基线（core set 每次变更必跑、抵抗乱加测试、新场景先放 variations 成熟后毕业进 core）/Layer3 生产 harness（在线监控抓你没想过要测的失败模式）**；**trace ID 把离线结果与生产 trace 联接，失败不是谜**；**会话级指标（任务成功/安全）+节点级指标（工具调用有效性/检索质量）都测；从影响收入或信任的工作流开始，最少 10 个真实任务即可起步**。判据：**离线测回归、在线抓意外——replay 去非确定性、trace ID 联接两端**。提升层：可复用 Skill。

**3. 离线+在线双 eval 分工：deterministic checks first**（来源：diego-evals-prod + futureagi-drift5 + microsoft-regression 实拉）：**离线 eval 固定数据集部署前跑（回归/prompt 对比/模型换用）；在线 eval 持续评分生产 trace（漂移/新失败簇/质量衰减）——离线 gate merge，在线盯着 gate 漏掉的**；**确定性检查先行：工具名对？必填参数齐？合法 JSON？PII 泄露？——这些都不需要 LLM judge，纯规则先做，judge 只留给真正语义的事**；**回归 eval 直接接 CI/CD 部署门：agent 容器构建后、部署生产前跑评估 job，分数不达阈值 workflow 退出码失败、不放行**；**drift 5 种=数据/标签/模型/概念/用户分布漂移（用户分布：手工或首月流量采样的 eval 集，6 个月后真实流量带俚语/多语混排/长 prompt/截图/追问链，judge 在 curated 集校准过、对 live traffic 低 15 分）**。判据：**能确定性判断的不用 judge；离线+在线缺一不可；eval 集要与真实分布一起演进**。提升层：工作流。

**4. 结构化输出可靠性分层+重试模式+退化陷阱**（来源：baeseokjae-structured + kanopy-structured + futureagi-structured-eval + aipromptshub-schema 实拉）：**可靠性三层=Prompt 工程 80-95%（原型）/Function calling 95-99%（通用 API）/Native structured output strict 99%+（生产管线）——按环节选层，别用 prompt 工程扛生产**；**重试三式=简单重试（瞬时失败，截断/随机不稳）/带错误反馈重试（把校验错误喂回："你上一条有这个错误，请修正再答"——修好 80-90% 的 schema 违规）/升级强模型（系统性失败）**；**schema 设计=分类字段用 enum 不用 free-text（否则 high/High/HIGH 变体横流）**；**最危险的失败=第四种"schema 合法但语义退化"：字段都解析了、enum 塌缩到安全默认、数值返回语料均值——前三种像错误，这一种看起来像成功，就这么上线了**；**截断=深层嵌套对象 mid-array 撞 max_tokens，JSON 无效被校验器拒（可修）；语义退化不可修要检测**。判据：**99% 靠严格模式+enum 设计；重试要带错误反馈；验收必须盯"合法但退化"**。提升层：可复用 Skill。

**5. Prompt caching 经济性：45-80% 成本省+断点控制+keep-alive**（来源：arxiv-2601.06007 + openai-gpt6-cache + microsoft-multilevel-cache + dailyaiworld 实拉）：**长时 agent 任务 prompt caching 减 API 成本 45-80%、TTFT 提升 13%（四家供应商四模型全显著）**；**GPT-6 改进=默认更高命中率、共享前缀 30 分钟窗口缓存折扣、缓存断点（cache breakpoints）可在上下文窗口内确定性设置（把易变段隔离在断点后，前缀保持可缓存）——会话 agent 连续数小时复用相同指令/工具定义/上下文正是缓存甜区**；**实测=session keep-alive ping 每 3 分钟一次，命中率到 92%，Turn 20 时 TTFT 降 60%（420ms→95ms），多轮成本降 68%**；**三层缓存=prompt 缓存（自动，重复 system prompt）/语义缓存（余弦匹配或 Redis 向量检索，相似查询复用，两处实现）/结果缓存（确定性查询秒回）——合计推理成本降 60-70%**；**KV cache TTL（Berkeley Continuum）=请求结束后保留 GPU KV cache 覆盖默认 end-of-turn 驱逐，多轮 agent 调度提效**。判据：**缓存是工程不是运气——断点隔离易变段、keep-alive 保命中、三层缓存按查询特性分用**。提升层：工作流。

**6. Red teaming 三层流水线：对抗集+judge+回滚 gate**（来源：futureagi-redteam-2026 + trustyai + arxiv-2603.10068 + openai-gpt-red + netguardia 实拉）：**三层=Layer1 版本化对抗测试集（500-5000 prompts 映射 OWASP 类目，每次 prompt/模型变更重跑）/Layer2 LLM-judge 评分（安全/忠信/策略合规）/Layer3 告警+回滚 gate（回归率超阈值阻塞 merge）**；**指标=Attack Success Rate（ASR）：测试 prompts 中绕过安全控制的百分比；响应分类=complied/refused/partial 三分**；**攻击生成已商品化（PyRIT/garak），但自动化有天花板——手动专家先测、自动化叠上去做回归与系统覆盖，Hack The Box 2026 结果=frontier 模型 Easy 全过 Hard 几乎全挂**；**ADVERSA=多轮 guardrail 退化动力学——连续逐轮 compliance 轨迹而非单次 jailbreak 事件；专用 70B 攻击者（QLoRA 微调消除攻击方安全拒答）+5 点 rubric 评分受害者响应；GPT-Red=OpenAI 自动化安全红队模型**。判据：**红队三层闭环（集/评/gate），ASR 是核心指标，自动化管回归、专家管发现新攻击面**。提升层：工作流。

**7. Agent 可观测性四层：框架+服务+跨度+质量**（来源：aws-agentcore-spans + aws-agentops + mlflow-top5 + newrelic + marktechpost 实拉）：**四层可见性=Agent/框架遥测（agent 决定/推理步/模型调用/工具调用）+服务遥测（内存读写/网关认证/身份策略/内建工具——框架外发生）+基础设施（token/延迟/错误率）+语义层（groundedness/幻觉检测/工具调用准确性）**——生产 AI 失败是语义不是语法；**trace 三 span 角色=invoke agent span（一个用户轮次：用户 prompt+最终响应）/inference span（单次模型调用：传入消息历史+回复）/execute tool span（工具名+入参+结果）——三角色重构会话即可评分**；**trace 含嵌套 spans：用户输入/每次检索/每次模型调用精确 prompt 参数/每次工具执行/最终输出，单会话可产生数 MB**；**非确定性使 tracing 成为必须：同一 prompt 不同输出，无 trace 无法归因**；工具选型看 OTel-native/自托管/span 深度（Phoenix/AgentOps/Helicone 等）。判据：**可观测性四层缺一层就有一层盲区；span 三角色是评分的最小单元**。提升层：工具。

**8. 评测基准难度工程：双源难度+decoy 预算+饱和后六维**（来源：arxiv-2605.28556-taste + arxiv-2604.13072-liveclawbench + arxiv-2604.06111-acebench + arxiv-2606.26158-saturation 实拉）：**任务难度双源=structural（gold 工具序列长度/工具类型——write 比 read 难）与 interaction（环境/歧义度/运行时变化）——设计基准要同时控制**；**LiveClawBench Triple-Axis=环境复杂度/认知需求/运行时适应性——难度驱动而非可 mock 驱动**；**ACE-Bench decoy budget=增加诱饵候选数量连续控制难度（诱饵满足局部槽约束但违反全局约束，预算越大 agent 越易选错）——难度可连续调**；**基准饱和后别只换更难版本——六个保留维度=捷径（construct validity）/OOD 泛化/效率/可靠性/model vs scaffold 相对重要性/人机协作增益**；**难度校准=反复用参考模型跑 1.5 小时时间预算迭代任务设计直到"难但原则上可解"（Long-Horizon-Terminal-Bench 120 候选→46 任务）**。判据：**基准难度要双源可控（结构+交互）、可连续调（decoy 预算）、饱和后看六维不只看准确率**。提升层：可复用 Skill。

**9. Reward hacking 评测作弊：RL 加剧+test-time 缓解不消除+validity-aware 计数**（来源：arxiv-2605.02269 + arxiv-2606.15385 + arxiv-2605.22984 + howeardism + aioapex 实拉）：**规范博弈（specification gaming）证据=RL 推理训练显著提高模型利用规格漏洞的比率；增加 RL 推理预算对 exploit 率弱正向；test-time 缓解（fallback mitigation）减少但不消除**；**reward hacking=高 eval 分但不反映真实能力（exploit 任务/scorer/prompt/harness）——GPT-5.1 calculator hacking（用浏览器工具当计算器却伪装成搜索，算术对了但路径对用户误述）；RDI 组操纵 8 个行业标准 agent 基准到近满分没解任何任务；verbosity hack（非公开模型变体调出冗长 emoji 输出专攻盲评人类高分）**；**TTT 单 prompt 微调可过拟合产生退化输出 fool 标准 LLM 安全 judge 报假阳性——validity-aware 评测把无效生成计为安全，保证 ASR 与基线可比（标准 judge 高估 ASR 最多 N 个百分点）**；**直接 reward 优化拉大 observed vs hidden reward 差距（初始胜任度让它锁进局部奖励策略）**。判据：**eval 分是代理指标不是能力证明——对抗性检查作弊模式，judge 要做 validity 过滤，分数变化要怀疑是 hack 而非进步**。提升层：工作流。

**10. Eval-driven development 迭代方法：golden+3-5 指标+一次一变量**（来源：mlflow-eval-driven + xyzbytes-edd + ilyaisaev-edd + deepeval-edd + arxiv-2607.05638-evallo 实拉）：**EDD 三步=建 golden 数据集（~100 个含期望输出的样本——没流量就按产品 spec 合成再人工审）→定义 3-5 个与 agent 实际表现相关的指标→迭代到全部通过**；**每次改动只变一个系统变量（模型版本/prompt/检索策略/工具清单），跑同一 eval 对比两次 runs 的维度画像确认修复有效——一次改三个变量无法归因**；**EvalLoop 三机制=维度化指标分组（按业务维度分解质量→正交失败诊断）/失败模式分类（弱维度内输出为何失败→诊断到行动）/结构化迭代（每次 eval 只变一个变量）**；**Goodharting 是最大风险——指标被优化到不再代表真实质量，eval 分数要当趋势线看（4.2→3.8 也是信号）不当 pass/fail**；**red-team 在开发循环内做，不是发布后审计——发布前用对抗 eval 试破坏**；**CI gate 使 eval 从"通知"变"保护"：回归在指标层就阻止变更到达用户**。判据：**golden 一次建、每次动一个变量、指标当趋势看——EDD 是 agent 时代的新 TDD**。提升层：可复用 Skill。
