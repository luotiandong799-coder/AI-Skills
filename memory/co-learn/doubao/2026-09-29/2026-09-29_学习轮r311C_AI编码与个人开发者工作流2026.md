## 独点（12）

1. **精确 prompt=最少修正：双厂商第一原则+Goal-Constraint-Example**（来源：Cursor《Agent Best Practices》2026-01 + dev.to《Prompt Engineering for AI Coding Assistants 2026》2026-07 + AI Bytes《9 Best Practices》2026-04 + Zero to AI Agents 2026-04）——**Anthropic 与 Cursor 独立落地同一第一原则：精确指令需更少修正——"add tests for auth.ts" vs "Write a test case for auth.ts covering the logout edge case, using the patterns in __tests__ and avoiding mocks"（成功率显著提升）**；**Goal-Constraint-Example 三段：Goal（要什么结果）/ Constraints（必须遵守：库/模式/性能）/ Example（类似代码、输入输出对、API 响应形状）**；弱 prompt="Fix the login" 强 prompt="login 端点 POST /api/auth/login 在 email 不存在时返回 500，加错误处理返回 404+JSON 错误消息"。判据：**编码 prompt 写不出 Example 段=对目标理解还不够；先给"弱→强"对照再写正式 prompt**。提升层：可复用 Skill。
2. **Plan mode 开销与跳过判据**（来源：Claude Code《Best practices》官方 2026-09 + Kunal《AI Coding Workflow 2026》2026-06）——**Plan mode 有用但加开销：范围清楚修复小（修 typo/加 log 行/重命名变量）直接做**；**规划最有用=不确定方法/改多文件/不熟悉代码；"如果一句能描述 diff 就跳过 plan"**；**多工具分工：Claude Code 自主代码库探索/bug 追查/重构；Cursor 紧 IDE 集成+快速 plan-to-implement 循环（Plan mode 起手交接云 agent）；@path imports 和 .claude/rules/ 按文件类型限定规则**。判据：**plan 是决策工具不是仪式——一句能说清 diff 就别 plan**。提升层：工作流。
3. **Spec-Driven Development：规格=超提示**（来源：arXiv 2602.00180《Spec-Driven Development》+ VSDD + shiplight.ai 2026-08 + David Lapsley 2026-01 + dev.to tamizuddin 2026-09 + 抖音 OpenSpec 精讲 2026-05）——**规格把复杂问题拆成模块化组件对齐 agent 上下文窗口；agent 从 spec 生成代码+对照 checklist 自验证需求符合性；人类精炼 spec 显著提升 LLM 代码质量——受控研究错误减少达 50%；规格使并行 agent 执行成为可能**；**SDD 在入口处约束（开发前提供细致到每个功能的规格）vs TDD 在出口处管控（成果通过严格测试）——不矛盾可结合**；**SDD 循环四步：write spec → agent 实现 → 对照 spec 验证输出 → 把验收标准提升为回归测试；循环易断点=verification handoff（"agent 写了代码但没人验证"）**；**specs 独立于代码（存 repo、在 PR 中审查、随代码演化）；versioned specs 提供永久可搜索历史**；VSDD 两原则：Spec Supremacy（spec 是最高权威仅次于开发者；测试服务 spec、代码服务测试、无 spec 溯源的不存在）+ Verification-First（形式可验证性塑造设计；pure core, effectful shell；"如果无法验证就是你架构错了——Phase 1 发现不是 Phase 5"）。判据：**SDD 与 TDD 结合（入口规格+出口测试）；验收标准必须提升为回归测试否则循环断**。提升层：工作流。
4. **TDD accelerated：人写测试套件驱动实现**（来源：The Neural Base《TDD accelerated》2026-04 + 抖音蒋老师访谈 2026-03）——**工程师写综合测试文件（每函数 10-20 用例：happy path/错误 case/边界条件）→ LLM（Cursor/Copilot）从 spec+失败测试生成实现 → 工程师审查生成代码（逻辑/性能/安全，每函数 5-10 分钟）→ 自动测试套件跑 → 失败则精炼 spec（测试揭示误解）**；**human-in-the-loop：实现质量靠测试约束+人审，不是靠模型自觉**。判据：**测试先于实现（失败测试=实现契约）；生成代码每函数过一遍人眼**。提升层：工作流。
5. **Property-Based + Mutation 测试：AI 代码的质量门**（来源：The Neural Base《Verify with tests》《Test requirements》2026-04 + Daily AI World 2026-09 + SitePoint《PR Verification Gates》2026-09 + Augment《Mutation Testing》2026-09 + AgentPatterns 2026-09 + dev.to kunal 2026-09）——**AI 训练数据偏向 happy path——property-based testing（Hypothesis/fast-check）自动生成 100+ 边界 case 抓 null dereference/边界违规/off-by-one/类型强制；Dan Luu 2026 研究 26 验证条件 2000+ agentic 会话：property-based 减缺陷率 42%，TDD 与 formal methods 反而表现不佳——property-based 和 fuzzing 对复杂协议正确率最高**；**mutation testing（mutmut/Stryker）注入小故障验证测试是否检测行为差异——AI 测试套件可高覆盖但杀死的 mutant 少得多（coverage 报告代码执行了，mutation score 报告测试是否抓注入故障）；mutation score = killed / (total − equivalent)，equivalent mutant 改语法保行为**；**阈值：AI 生成代码 mutation score >85% vs 人类代码 >75%**；**三层验证：Tier1 手写 unit（纯逻辑：parsing/mapping/validation——有分支就有测试）→ Tier2 property-based（fast-check 默认 100 随机输入）→ Tier3 mutation（Stryker 注入小改动）——每层抓上一层抓不到的**；最小测试标准：新纯逻辑 unit+每个新外部边界一个 integration（DB/queue/HTTP/file system，mocks 可以有但不能是唯一防御）。判据：**AI 代码的质量门=property（抓边界）+ mutation（验证测试真抓 bug）+ 外部边界 integration——按 blast radius 扩展**。提升层：可复用 Skill。
6. **AI 评审定位与架构一致性盲点**（来源：Kinda Technical 2026-03 + GitHub AI review workflow 2026-09 + dev.to rakbro 2026-09 + Awesome Code Reviews 2026-08 + Microsoft Copilot review）——**AI review 优势=一致性与彻底性（人类 reviewer 专业度/注意力参差）——做 first-pass reviewer 然后人类**；**评审正确性与影响而非风格——两件事让 AI review 慢而吵：花时间在格式化/命名（lint/CI 已覆盖）+一次一个调用探索 repo（checkout 分支/逐文件读/grep）**；**架构一致性=agent 盲点：agent 看到代码但不知道项目"已经知道怎么解决这个问题"——经验 reviewer 补上下文：是否引入项目已解决的第二种方式/新依赖/与周围代码不匹配的重复工具或抽象（"AI 没有发明架构不一致，它只是会引入"）**；**高 AI 采用团队：median PR review 时间涨 5 倍、每 PR 事故 3 倍、telemetry 显示 reviewer 略读而非精读——人类评审有效性在 4 分后崩溃**；从小开始迭代（先 style/基础 bug 模式逐渐扩大范围）+ HITL 必须（AI 反馈=建议不是定论）。判据：**AI 评审管正确性与影响（风格交 lint）；架构一致性必须人审；PR review 时间涨=自动化评审介入信号**。提升层：工作流。
7. **风险分级验证：自动管线/人审/强制审批**（来源：dev.to tamizuddin《Framework for Verifying AI-Generated Code》2026-09 + TestQuality《Agentic SDLC》2026-04）——**Low Risk（bug fix/refactoring/加 unit tests）→纯自动管线；Medium Risk（新功能/API 变更）→自动管线+Human code review；High Risk（DB schema/认证逻辑/基础设施代码）→自动管线+强制人工审批+同行评审**；**UC Berkeley MAST：加高层任务目标验证步骤（聚焦业务逻辑非仅编译）→+15.6% 绝对改进——现有 verifier 只做表面检查漏掉最重要失败类**；**builder-validator 链严格分离：生产代码的 agent 与测试它的 agent 分开（validator 无生成上下文访问权）**。判据：**验证深度按风险分级配；builder 与 validator 物理分离**。提升层：工作流。
8. **Verify-First 循环：gather→act→verify→repeat**（来源：The AI Operator《Verify-First Harness》2026-07 + cadence.withremote.ai 2026-05 + JasonSamuel《4-part proof system》2026-06 + XYZBytes《7-Hour Agent》2026-06 + samuelfaj 2026-06 + TestQuality）——**Anthropic 生产 agent 循环：gather context → take action → verify work → repeat；生产失败=verify 是 post-demo checklist（lint 只在 CI 跑、human review 在 merge 后、没人能…）**；**工具循环状态机：ACT（选工具 read/edit/run_shell/run_tests）→ OBSERVE（verbatim 读工具输出）→ REFLECT（观察符合计划吗）→ DECIDE（继续/重计划/升级/停止）→ VERIFY（跑测试/type-check/lint/重读 diff）**；**诚实自纠循环：agent 尝试小改动→harness 跑定义 proof→只有失败带来新信息才能迭代（错误没变就重复=烧上下文）；短期记忆（当前错误/失败命令/diff）与长期记忆（仓库…）分离**；**长时运行两护栏：Checkpoints（测试通过的安全里程碑就 commit——7 小时 run 其实是验证过状态的链）+ Reversal（定义 abort 与 clean rollback 标准）——限定 blast radius**；无人值守循环=无人值守犯错的循环，人类注意力不随 agent 输出扩展。判据：**verify 是循环内建步骤不是事后 checklist；长跑必须 checkpoint+reversal 双护栏**。提升层：工作流。
9. **增量重构纪律：Plan First, Diff Every Step**（来源：AI Tools Guidebook 2026-05 + IEEE《Refactoring Playbook》2026-07 + cadence《Ratchet Pattern》2026-05 + AnyforSoft 2026-06 + agenticskillset《Legacy Codebases》2026-08 + npm code-refactoring-skill）——**重构前：列出将做的改动（带文件路径，先不写代码）→对照一句话目标审查计划→拒绝不在路径上的——"我注意到无关 bug 想修吗"→延后（无关 bug=单独 commit 单独 diff）**；**棘轮模式：每天小重构合并+feature flag，从不回退、总是复合——周一一个重命名、周二一个提取函数、周三合并一个重复；每个 click 10 分钟可审可逆；周五代码库明显更好且没人英雄周**；**三级匹配风险：Micro（每日卫生分钟级——重命名/提取方法/简化条件/就近去重/显式不变量）/ Local（有界改进小时-天）**；**改动范围决定验证安全性——一函数可孤立测试，二十函数不能；级联效应=范围太宽的信号**；**旧代码先建 characterization tests：不测代码应该做什么，测代码现在做什么（含 bug/quirk）——目的=检测回归不是强制正确性；覆盖后可重构并信任套件抓任何行为变化**；**五阶段：Intake（读目标文件/找测试 harness）→ Diagnose（排名 code smells）→ Plan（分解原子可验证步骤）→ Execute（一次一改每改跑测试）→ Wrap-up（总结+建议后续不应用）**。判据：**一次改动=一个原子可验证步骤；重构前先有安全网（测试过+git 干净）**。提升层：可复用 Skill。
10. **上下文工程三标准+写入纪律**（来源：RockB《Context Engineering for AI Coding Agents》2026-04 + Claude 官方《Steering Claude Code》2026-06 + professionaldeveloper.net 2026-07 + Claude《New Rules of Context Engineering》2026-07 + Killer Code 2026-09 + Claude Code agent loop）——**2026 三标准：CLAUDE.md（Claude Code）/ AGENTS.md（OpenAI+多模型框架）/ .cursorrules（Cursor）**；**CLAUDE.md 两型：Always loaded（根文件：build 命令/目录布局/monorepo 结构/编码约定/团队规范）与 import 型（按需加载）**；**.claude/rules/ 按文件类型/域按需加载保持主文件简洁——上下文=当前会话 token 预算（CLAUDE.md/imported references/auto memory/history 都算）**；**完美 prompt 在臃肿无关上下文里仍产出平庸输出，平庸 prompt 在精挑上下文里常产出优秀输出**；**工具用法说明放 tool descriptions 而非 system prompt（可删重复示例）；跨 turn 不变内容（system prompt/tool definitions/CLAUDE.md）自动 prompt cached 减成本延迟**；**Sonnet 5/4.6 上下文感知：模型跟踪剩余 token budget 更有效管理上下文**。判据：**上下文文件=编码 agent 的输入质量，精简+分层+按需加载优先于堆内容**。提升层：工具。
11. **CLI agent 能力面与 /loop 循环任务**（来源：MCP Bundles《Best AI CLI Tools 2026》2026-04 + Dev Leader《Copilot CLI》2026-07 + Cursor Alternatives + aidiveforge《Grok Build》2026-09）——**/loop 命令在重复间隔跑任务——linting/test monitoring/review passes 无需人工干预**；**CLI agent=自然语言命令转 shell 脚本/CLI 动作，solo dev/多环境团队更易上手；Copilot CLI 独立 copilot 命令：读 repo/编辑文件/跑工具/委派工作/review diff（"不再只是 shell autocomplete"）**；**Grok Build 双模式：交互（键盘驱动会话）/ headless（脚本管线）——Rust Apache-2.0 自托管**；**AI Shell Agent：建议并执行 shell 命令/调试/读写信件/基于会话历史上下文化命令**。判据：**终端自动化=给重复 shell 活挂 agent 循环（/loop 类），自然语言描述动作转脚本**。提升层：工具。
12. **个人开源维护 agent fleet**（来源：santifer.io《62,000-star repo with fleet of AI agents》2026-07 + Codex CLI 维护工作流 2026-06/09 + jescalada《Auto-triage》2026-09 + GitHub Blog《Agentic Workflows》2026-02 + renezander《DraftCat》2026-03 + Claude Code Label-driven CI）——**晚间周末维护 62k star：Claude Code agent fleet 做机械活（triage/testing/review briefs/release mechanics/community metrics）；hard gates 保持诚实；每个真实失败蒸馏成规则 agent 启动加载**；**Codex 三工作流渐进路径：从 triage 开始（最高价值最低风险）→ 加 review → 治理到位后毕业到 patch drafting；scheduled triage 后台跑+有报告发收件箱+无报告自动归档**；**auto-triage 细节：对比近期开的 issue 抓重复——明确重复直接关+指向原 issue，可能重复在评论标记但保持打开；缺 steps to reproduce 或 use case→发短评论要信息；"agent 不自行关闭/不自行决定——它建议，人决定"**；**Label-driven CI：scheduled triage→过滤缺分类 label 的 issue→每个未 triage issue（每 run 最多 5 个控成本）读 issue→查代码相关部分→分类 bug/feature/chore/improvement→估 scope mini/small/medium/large**；**GitHub Agentic Workflows：plain Markdown 写 workflow 替代复杂 YAML（.github/workflows/），AI 处理 issue triage/PR review/CI 失败分析**。判据：**个人维护=渐进三工作流（triage→review→patch）+ agent 建议人决定+失败蒸馏成启动规则；成本控制=每 run 限量**。提升层：可复用 Skill。
