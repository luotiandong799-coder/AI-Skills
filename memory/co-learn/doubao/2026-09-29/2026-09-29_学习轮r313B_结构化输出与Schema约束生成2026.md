## 独点（12）

1. **Schema 约束解码机制与三层架构**（来源：thepromptbench《Reliable JSON Out of LLMs》2026-07 + jvoltci《Structured Output》2026-05 + openlegion 2026-07 + kanopylabs 2026-04）——**schema mode / grammar-constrained decoding：把 JSON Schema 交给 provider，解码被约束为只生成保持输出对 schema 有效的 token——保证可解析性与结构；OpenAI `response_format: {"type": "json_schema", "json_schema": {...}, "strict": true}`；strict 原理=幻觉 key 结构上不可能（不在 schema properties 的 key 的 token 在采样前被 mask 到 -infinity 概率）**；**三层架构：schema 定义（Pydantic/TypeBox/Zod）→ 服务端 constrained decoding（XGrammar/Outlines）→ 客户端验证+重试（Instructor/structured-outputs API）——现代栈让 100% 结构正确成默认，schema 进验证对象出无重试**；**成本：token 级 constrained decoding 使 schema 违规数学上不可能（不只不太可能），加 ~10-15ms schema 编译延迟**。判据：**结构正确靠解码约束保证，语义正确靠验证层兜底**。提升层：工具。
2. **语义可靠性 vs schema 有效性分离**（来源：arXiv 2607.18261《When JSON Is Not Enough》+ zylos 2026-04 + arXiv 2606.09395《Structured Output Control in SE》）——**GPT-OSS 120B-fast 两种模式都 100% schema 有效，但语义成功仅 83.0%（prompt-only）/81.3%（JSON-schema）；Qwen3-30B-A3B 100% schema 有效但语义仅 31.3%/30.7%——结构约束不解决语义正确**；**strict:true 管什么：必需字段都在/无额外属性（additionalProperties:false 时）/类型对/enum 有效——不管语义正确/字符串内容准确/数字范围（minimum/maximum 不强制）**；**TTMG 实证：模板驱动控制几乎消除语法错误，但大量结构性和语义错误持续——核心瓶颈在语法格式之外**。判据：**验证分三层=语法（解码保证）/结构（schema 保证）/语义（业务规则验证器保证）**。提升层：工作流。
3. **Provider 结构化输出限制矩阵**（来源：aiworkflowlab 三社对比 2026-06 + Claude docs 2026-09 + theorydelta 2026-04 + carrick 2026-05 + ExtractBench arXiv 2602.12247）——**OpenAI（gpt-5/4o）：response_format json_schema+constrained decoding 有 strict+100% 按契约+JSON Schema 受限子集；Anthropic（Claude 4.x）：tool use+tool_choice+无 constrained+≈99.7% 经验+几乎全 JSON Schema；Gemini 2.5：responseSchema+部分 constrained+≈99% 经验+OpenAPI 3.0 风格**；**Anthropic 2026 GA output_config.format：递归 schema（$ref:"#"）不支持，strict tool 合计 20 个+union 型参数 16 个上限；Anthropic 两表面=简单 prompt 形状（无 token 级约束 best effort，失败形状=near-JSON：尾随注释/缺括号）vs tool use（input_schema 成契约+验证）**；**Gemini 隐藏失败：prompt 属性顺序与 responseSchema 不同→输出属性乱序/必需值缺失或幻觉/字段名不匹配——输出有效 JSON 但不符 responseSchema（顺序型失败无文档）**；**ExtractBench：每个 provider 的 constrained 模式只支持 JSON Schema 子集；Anthropic 禁递归 schema+拒绝超内部复杂度阈值；Google"可能拒绝非常大或深嵌套 schema"——prompt 模式 62% 有效（26/42）的 resume schema 被所有 provider constrained 模式直接拒绝**；**限制绕过=schema 保持精简+额外验证放 Pydantic field_validator；Azure Databricks 只支持 json_schema（不支持 json_object）+不支持 streaming**。判据：**constrained 模式≠全 JSON Schema——先查 provider 支持子集再定 schema 复杂度**。提升层：工作流。
4. **重试实证与具体错误反馈**（来源：ai-tldr《Validate and Sanitize LLM Outputs》2026-06 + belsoftsolutions 2026-07 + kanopylabs 2026-04 + codercops 2026-05 + oneplaceforai 2026-07 + siddhantkhare 2026-09）——**生产聊天机器人约 8% 响应首过验证失败；把具体 Pydantic 错误加进重试 prompt，二过失败率降到 <1%**；**"你的响应 JSON 验证失败：缺必需属性 price"比"try again"修正效果好——具体错误消息是关键**；**重试策略三档：simple retry（同一 prompt——处理瞬时失败：截断/随机不稳定；便宜但不修系统性问题）→ retry with error feedback（把验证错误加进后续消息）→ 带重试预算**；**语义验证器（业务规则）：schema 解析通过后加领域规则——日期范围 start<end、概率分数和=1.0——捕获结构有效但语义错**；**parse-and-retry vs schema validation 分层：JSON parse 错误→修复 prompt；有效 JSON 但违反 schema（缺必需字段/错类型）→不同重试策略——显式列 schema 违规**；**Instructor 模式：Pydantic 模型输出→验证→自动带验证错误重试（Instructor 自动处理循环）**；**prompt+验证+重试用于不支持 constrained decoding 的模型（含 Claude）或需跨 provider 移植逻辑**。判据：**重试必须带错误反馈（具体错误>泛化重试）；结构有效≠业务有效（语义验证器兜底）**。提升层：可复用 Skill。
5. **引导生成框架对比与 Outlines 原理**（来源：arXiv 2606.09395 + arXiv 2501.10868 JSONSchemaBench + NVIDIA blog 2026-05 + aiwiki + davila7 skill）——**NVIDIA bash 生成实证：13 模型平均 pass rate 62.5%→75.2%（299 任务）；Qwen3-0.6B 16.7%→59.2%（最强提升）；filter/transform 任务 +17.4 百分点——语法约束减少语法错误和提前终止**；**JSONSchemaBench：constrained decoding 无论框架都比无约束更高；Guidance 全任务最佳（~3% 优于 LM-only）——归因 token-healing 实现**；**框架差异：Outlines=预构建确定性自动机表示允许 token 序列（JSON schema+regex 支持），一次性 setup 成本后高效解码，但不支持动态结构化生成；LLGuidance=每 token 动态评估语法约束（灵活无启动成本）；XGrammar 2 支持动态结构化生成**；**Outlines 四步原理：1 转 schema（JSON/Pydantic/regex）为 CFG → 2 CFG 转 FSM → 3 每步过滤无效 token → 4 只有一个有效 token 时 fast-forward——logit 层约束零开销**；**grammar-guide：speculative grammar backtracking——对任意文本生成函数（OpenAI/Anthropic 等）做 grammar-constrained decoding（不依赖内部采样接口）**；**NVIDIA NIM：EBNF 格式 CFG 用 guided_grammar 参数；Triton guided decoding 支持 None/JSON/JSON Schema/Regex/EBNF 五种 guide 类型**。判据：**本地/自托管用解码约束（Outlines/XGrammar），托管 API 用原生 structured mode**。提升层：工具。
6. **BAML Schema-Aligned Parsing 与流式结构化**（来源：nickroth《Streaming Structured Objects》2026-05 + cadence《Structured Outputs in Production》2026-05 + lobehub skill 2026-09 + parsantic pypi 2026-09）——**BAML SAP：不是希望 LLM 产有效 JSON——按 schema 解析 token 流：传统=LLM 输出→JSON.parse→希望能用（坏 JSON 失败）；BAML=LLM 输出→schema-aware parser→总是有效部分（对语法错误/幻觉有韧性）**；**部分 JSON 流式（partial-JSON parsing）：用户不愿等 8 秒结构化响应却能看到等效文本流式——读流逐 token 尝试解析不完整 JSON，字段完成就渐进显示（npm partial-json）**；**流式注意：OpenAI 支持流式结构化输出（部分 JSON chunk 到达）——不能把中间 chunk 当有效 JSON 解析；用 SDK 内建部分解析或缓冲到流完成；Anthropic tool_use blocks 在单个 content_block_stop 事件完整到达——无需部分组装**；**parsantic：native 模式验证失败自动从响应恢复原始 JSON 跑本地修复管道；流式提取暴露类型化部分对象**。判据：**流式 UI 用 schema-aware 解析器渐进渲染；API 层缓冲完整后再验证**。提升层：工具。
7. **ExtractBench/VAREX 评测方法论**（来源：arXiv 2602.12247 ExtractBench + 2607.29677 企业版 + 2603.15118 VAREX + interfaze SOB 2026-04）——**双互补指标：Valid JSON=可解析+schema 一致提取分数（必要非充分）；Pass rate=内容准确度（每个 schema 字段对照 gold 用 evaluation_config 声明指标打分——identifier 用 exact match/free text 用语义等价——字段过阈值即 pass；无效提取计零）**；**企业版：order-insensitive value F1（值准确度）+两项溯源指标 word-level F1 + page-level F1（grounding——系统能否显示每个值来自哪）**；**VAREX：exact match 主指标+ANLS（Average Normalized Levenshtein Similarity 给近似匹配部分分，区分完全失败与轻微格式差异）+数组字段 Hungarian 算法 order-invariant 匹配（按最大字段重叠最优分配）**；**SOB 成本洞察：Qwen3.5-35B/GLM-4.7/Gemini-2.5-Flash 每正确字段成本比榜单领先者低 6x-11x，值准确度只损失 ~2 百分点——top 两模型极少是生产结构化输出的默认选择**。判据：**评测=结构有效性+内容准确度+溯源三件套；选型=每正确字段成本而非榜单纯正确率**。提升层：工作流。
8. **多模态文档结构化提取：schema echo 与专项微调**（来源：arXiv 2603.15118 VAREX + 2603.01840 FireRed-OCR + ICPR survey + Qianfan + Cohere Parse 5 + OvisOCR2）——**VAREX 关键结论：<4B 参数时结构化输出合规（非提取能力）是主导瓶颈；schema echo（模型产 schema 一致结构而非提取值）压低受影响模型 45-65 pp；2B 提取专项微调 +81 pp（指令跟随缺陷无需规模可修）**；**FireRed-OCR：三阶段渐进训练（多任务预对齐→SFT→格式约束 GRPO）把通用 VLM（Qwen3-VL-2B）特化为像素级精确结构化文档解析专家；OmniDocBench v1.5 总分 92.94%（文本/公式/表格/阅读顺序）超越 DeepSeek-OCR 2 与 OCRVerse；2B 参数超越 235B**；**OCR 大模型三系统：layout-guided pipelines/end-to-end OCR VLMs/agentic OCR systems——从文本转录走向可审计、结构化、机器可行动文档知识**；**Cohere Parse 5：23 亿参数多模态 VLM 专为企业文档结构化（PDF→Markdown+视觉定位）；SigLIP 2 SO400M 编码器+2D RoPE 保留空间结构+DeepStack 多层级视觉特征注入浅层**；**OvisOCR2：0.8B 端到端解析器 OmniDocBench v1.6 SOTA**。判据：**小模型瓶颈在指令跟随不在能力——专项微调+格式约束训练可解；通用 VLM→专业结构化专家是范式**。提升层：模型。
9. **LLM 熔断器三态与成本感知回退链**（来源：balacode《Circuit Breakers for LLMs》2026-06 + ranjankumar 2026-04 + aiworkflowlab 2026-08 + belsoftsolutions 2026-07 + devopsboys 2026-06 + theneuralbase 2026-04）——**熔断器三态：Closed（正常，请求全过，计失败）/Open（端点失败，立即拒绝——停止为死端点付重试成本+停止让用户等超时）/Half-open（恢复探针——一个请求放行，成功关/失败再开）**；**无熔断后果：30 秒/请求超时×provider 停机=每次 API 调用 30 秒降级体验；熔断在毫秒级短路已知坏 provider（在抽象层实现——所有调用走同一层）**；**成本感知回退链：熔断打开时不回退到"任何可用模型"——按每 token 成本/质量要求/延迟预算排序的链（GPT-4o→Claude 3.5→Gemini 1.5 Pro）**；**5 连败→60 秒断路→直连备份；备份超时加 jitter 防同步（thundering herd）**；**LLM 特有失败模式：prompt amplification/cascading retries/semantic degradation under partial failures**。判据：**熔断保流量不保成本——回退链排序兼顾两者**。提升层：工作流。
10. **降级模式与能力问题分类**（来源：ai-tldr《Handle LLM Failures》2026-06 + theneuralbase《Incident Response for AI Failures》2026-04 + AI Wiki 2026-05）——**降级模式三层：当所有模型路径不可用时——缓存响应（按 prompt hash 键）+透明"AI 临时不可用"+人工升级路径+静态预写内容——降级模式不是失败，是故意决定提供缩减但诚实的响应而非错误页**；**能力问题 vs 故障：指标全绿但 LangSmith trace 显示模型拒绝回答（安全过滤器）或幻觉（检索上下文不支持的事实）——capability issue 不是 failure——无需重启，几分钟调 system prompt/检索参数/输出验证规则**；**监控：labels(model, fallback_to).inc()+LangSmith 每步记录哪个模型+延迟；cache 可选（Redis 故障不阻塞推理——try-except 包）**。判据：**先分能力问题还是故障再行动——能力问题调参数不重启，故障走熔断+降级**。提升层：可复用 Skill。
11. **工具调用错误六分类与主机边界捕获**（来源：latitude《Detect Tool-Call Errors》2026-07 + aiagents.codeguides《Handling Tool Errors》2026-07 + developersdigest 2026-06 + theneuralbase《Error Propagation》2026-04 + n8n 2026-07）——**六分类检测：Malformed arguments（错类型/缺必需/幻觉参数→执行前对 JSON schema 验证）；Invalid argument value（well-typed 但不存在 order ID/SKU/email→工具返回 not found 捕获分类）；Wrong tool chosen（比较工具选择与预期工具；按工具监视错误率）；Missing tool call（模型从记忆回答本应调工具→规则：某些意图必须前置工具 span）**；**主机边界捕获（不在 agent 循环内）：把工具失败转成结构化 tool observation 给模型；强制工具调用重试预算防无限循环；每个 call ID 都追加 tool message（含失败）；错误消息进上下文/日志前剥离 secrets；检测无进展循环停止或升级**；**错误传播三策略：fail_fast（关键工具立即停止链）/retry_with_backoff（瞬时错误，指数退避+全抖动）/report_to_model（错误消息回模型作 observation）；解析 Retry-After 头覆盖默认间隔**；**Claude tool use 生产事故几乎全部归因于少数模式：歧义 schema/执行端缺错误处理/失控循环/模型以为存在的工具**。判据：**错误分类决定恢复策略；执行前 schema 验证+执行后分类捕获全覆盖**。提升层：可复用 Skill。
12. **Agent 状态结构化与 IETF 格式族**（来源：IETF AAIF draft 2026-06 + aimem bundle 2026-06 + infantado agent memory 2026-07 + FAF draft 2026-06 + AEP + zhou schema + gajae session 2026-09 + MS Agent Framework 2026-07）——**AAIF v3 agent-state.schema.json：捕获/序列化/恢复运行 agent 的完整执行状态——三用例=同平台暂停恢复/跨平台实时迁移/崩溃恢复无需完整对话重放；字段 state_id（UUID 检查点标识）**；**Memory Object（IETF infantado）：持久可寻址机器可读记忆单元（稳定身份/类型化 Canonical Content/权威元数据/provenance/生命周期/可用性/保留/验证状态/版本历史）；Memory Version=不可变逻辑修订（每个权威状态变化=新版本+Event Ledger 条目）；Canonical Content=权威类型化内容（不含 embeddings 等派生表示）**；**FAF：YAML 1.2 基础语法；.faf=read-once+schema-stable；.fafm=随时间累积（条目追加/摘要/选择提升进 .faf 当成为持久事实）——生命周期区分**；**gajae session 版本化：当前版本 5，v1→v2 迁移（header version 缺失或<2：加 id/parentId 到非 header 条目；重建线性父链；compaction 字段迁移）——结构化会话有版本+迁移**；**Memory Interchange Bundle：Chunk embedding=base64 编码 little-endian float32 数组；envelope 必须声明 embedding_dim+embedding_model；MS Agent Framework：session 可序列化 JSON 存储/恢复**。判据：**agent 状态=版本化 schema+检查点+Event Ledger；跨平台可迁移需要标准交换格式**。提升层：可复用 Skill。
