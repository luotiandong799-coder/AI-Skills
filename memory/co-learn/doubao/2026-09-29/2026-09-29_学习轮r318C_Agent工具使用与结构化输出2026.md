2. **Tool Router 三种模式与工具数治理**（来源：arxiv AgentWeave 2608 + theneuralbase×2 + dev switchboard 2026-08 + dev progressive mcp 2026-09 + 51cto 2026-09 + arxiv semantic tool discovery 2603 + zylos 2026-06 + kaman 2026 + state-of-large-scale 2026-06）——**Routing Before Reasoning（AgentWeave）=deterministic pre-inference routing layer 用 eligibility/requirement/capability/routing signals 构造 bounded model-visible action space——LLM 推理前减少候选集不改下游模型**；**'dumb' routing 常胜 'smart' 全选：关键词匹配/域分类过滤层常胜过模型从全部里选——大工具空间开销（浪费 tokens/低置信/重复错误）让受限系统更快更便宜**；**Semantic tool discovery=embed 每工具描述进向量索引（registration 时）→每 turn embed 任务→cosine top-K（3-5 个）只注入 K 个——50-100+ catalog→3-5 tools，工具相关 token 降 70-90%**；**基线三步骤=Build Index→Route Query→Dynamic Injection，K=3-5 路由工具稳定准确率 >83%**；**分层 Tool Routing=统一注册表（命名空间/标签/适用场景/schema/权限/风险等级/可用状态）→硬过滤（租户/角色/环境/任务状态，无权或不可用直接隐藏）→两级召回（规则/轻量分类）→动态注入**；**kaman=session-scoped LRU caching+eviction 迭代守卫（detect+break tool-call loops）**。判据：**工具多先路由后推理；默认语义检索 top-K 注入不全量塞 schema；>20% context 工具成本即上语义检索**。提升层：工作流。
3. **工具描述四要素与 Description Engineering**（来源：zylos 2026-06 + channel.tel 2026-05 + gingerlabs 2026-06 + modelcontextprotocol + cloudstreet + aws 2026-08 + msitarzewski + sickn33 + verifymcp 2026-07 + raftlabs 2026-03）——**描述四要素（Anthropic 官方）=what it does/when to use/each parameter means/caveats，至少 3-4 句复杂工具更多**；**output-focused not behavior-focused："Returns completed orders for a verified customer" 而非 "This tool accesses our order management system to retrieve historical transaction data"**；**Triggering conditions=2-4 个显式条件用编号列表（"after identity is verified" 胜 "when you need customer data"）——具体信号胜模糊信号**；**description 是 prompt——LLM 读它决定何时用**；raftlabs：40+ 词+含 concrete example（"Search for GitHub issues by label, status, and assignee. 4. **双向 schema 验证与三类失败分类**（来源：aibuzz 2026-09 + openlegion 2026-06 + zylos 2026-04 + arxiv tool-env unreliability 2606 + llmversus 2026-04 + theneuralbase 2026-04 + lobehub 2026-09 + loooop 2026-05）——**双向验证：tool inputs（模型即使有好 schema 也可能生成无效参数，尤其边界/歧义）；tool outputs（外部 API 意外格式/错误 payload/语义无效；成功输出也随上游 API 漂移）——每 call 双向 schema 验证**；**Validation failure（模型产参不过 schema——schema 描述问题或模型能力问题）→专门 recovery path：validation error 反馈模型带清晰解释，不是 generic retry**；**Execution failure（合法调用到达但执行不稳：timeout/连接错误/异常/解析失败）→bounded retry+fallback+拒绝从部分证据完成**；**Output drift（执行成功但结果错误/意外）——tool-environment unreliability benchmark 测这三类**；**error handling：返回 structured error string 作为 tool result 不抛未处理异常——模型决定重试/fallback/告知，不 crash loop；Never skip tool result：跳过或 silent failure/None 值→模型幻觉**；**max-tool-calls guard（10/session）**。判据：**input+output 双向 schema；失败分类后走对应 recovery 路径；失败结果必须结构化返回**。提升层：工作流。
5. **工具使用失败模式五类与编排层验证**（来源：futureagi 2026-05 + swarmsignal 2026-06 + mohithg 2026-05 + mohakdeepsingh 2026-06 + sista 2026-06 + techrxiv + buildingagenticai 2026-05 + learnixo 2026-05 + arxiv 2607.05775）——**五类失败：wrong-args（参数形状不过 schema 同形状重试）/tool-hallucination（调用不存在的函数）/no-error-handling（错误路径未处理照 proceed）/tool-result misinterpretation（返回 {"status":"pending"} 读成 completed——输出格式歧义或模型读结构化数据脆弱）/context poisoning**；**parameter hallucination 最常见：结构合法但值编造（date=2025-13-45/user ID plausible nonexistent/enum 不在允许集）——JSON 能解析 API 拒绝或更糟接受返回错数据**；**Mandatory tool call verification=编排层（不是模型）确认工具调用真发生——模型输出含 tool result 但 orchestrator 无对应调用记录→视为 fabricated→强制真执行；orchestration layer 维护自己的 tool call ledger**；**Error propagation in tool selection：早期错误选择把轨迹引入 self-reinforcing loop——错误输出进 context 被当证据，后续选择显得与错误前提一致；context 越长越难 override 早期假设**；**幻觉工具调用成因=schema 歧义/description 弱/required 参数不在对话（训练目标奖励自信猜测而非校准不确定性）**。判据：**编排层持有工具调用 ledger 验证结果真实性；输出 schema 消歧；失败路径必处理**。提升层：工作流。
6. **Parallel tool calls 纪律与并行冲突检测**（来源：llmversus + loooop×2 + tryvex×2 + theneuralbase）——**独立调用并行执行（减 50-70% 延迟）、依赖调用串行；parallel_tool_calls=false 缓解 race condition（按 workload 权衡 performance vs reliability）**；**ThreadPoolExecutor max_workers=min(5, len(tool_calls)) 防耗尽 API 限制+连接池按尺寸**；**Parallel Conflict Scanner=semantic similarity clustering 识别并行工具结果冲突（两个天气 API 返回不同温度 agent 随意选）——parallel tool calls 返回逻辑上不可能的组合（Weather can't be sunny AND raining）应 flag**；**工具结果验证后再注入 context：empty result/null body/200 里埋 error message 会误导 agent**。判据：**并行只用于独立调用；冲突结果聚类检测；结果注入前验证**。提升层：工作流。
7. **Programmatic Tool Calling（PTC）与推理预算**（来源：claude programmatic tool calling 2026-09 + gpt-5.6 builder 2026-08 + arxiv HyFunc 2602 + arxiv Brief Is Better 2604 + cursuri 2026-05 + microscale 2026-07 + mech 2026-05）——**PTC=agent 写代码在 code execution container 里程序化调用工具，不每工具调用过模型往返——减延迟+减 token（agent 在数据进 context window 前 filter/process）；GPT-5.6 例：检索 100 filings 按日期过滤识别相关交易——模型不必在 context window 推理每个中间结果；BrowseComp/DeepSearchQA 上 PTC 显著提升**；**HyFunc=hybrid-model cascade：大模型把 user intent 蒸馏成单个 soft token→轻量 retriever 选函数→小 prefix-tuned model 生成最终调用——避免冗余 context 处理和全序列生成**；**Brief Is Better：function-calling agent 用固定简短推理预算 8-32 tokens/决策步（d=32 得 64.0% vs no-CoT 44.0%）；FR-CoT=zero-hallucination 保证；简短推理仅 ~10% 额外 token——函数调用场景长 CoT 反而伤**。判据：**多工具工作流用 PTC（代码内调用+上下文外处理）；函数调用决策给 8-32 token 简短预算不堆长推理**。提升层：工作流。
8. **结构化输出三厂商与 constrained decoding**（来源：claude structured outputs×3 + aiworkflowlab 2026-07 + codercops 2026-05 + thepromptbench 2026-07 + oneplaceforai 2026-07 + ag2 + aws 2026-02 + jsdelivr namch skill）——**2026 三厂商：OpenAI=json_object（仅语法）/json_schema+strict:true（全 schema 强制，<0.1% 失败 grammar-constrained token generation）；Claude=JSON outputs（output_config.format）+Strict tool use（strict:true 保证 tool names+inputs schema 验证，<0.2%）；Gemini=responseSchema（<0.3%）**；**Claude tool_choice: forced 必须（否则 Claude 可能选自然语言回应而非调工具）**；**Constrained decoding（Guidance/Outlines/XGrammar）自托管近 100% schema compliance 无显著延迟惩罚**；**经验规则：Never use json_object without schema（legacy 只保语法不保 schema conformance——模型可返回 {"result":"hello"} 当你要 {"name":str,"age":int}）→始终 json_schema+全 schema；Never assume structured output means correct output（语法合规≠语义正确——语义验证仍要）**；**Pydantic+Instructor=三厂商单一 Python 接口+验证错误自动重试**；**structured outputs 价值场景=数据提取（下游依赖无错一致格式）/多 agent 架构一致通信/复杂搜索工具，无模型性能影响**。判据：**要 schema 遵守用 strict/constrained decoding，不要 legacy json mode；语法合规不等于语义正确**。提升层：工作流。
