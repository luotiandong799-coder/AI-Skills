11. **上下文窗口管理：sub-agent 委托 vs compaction 边界**（来源：codex.danielvaughan《Context Window Management》2026-03 + cometapi《Auto Compact in Claude Code》2026-09 + subconscious GLM-5.2 2026-06 + cursor《Token Efficiency》2026-09 + NVIDIA FlexKV 2026-09）——**Sub-agent 委托不是压缩的完全替代——几百文件重构/长调试会话仍会到上限；model_auto_compact_token_limit 阈值触发自动历史压缩——理解压缩机制才能调对**；**Claude Code Auto Compact：接近上限（~200k tokens Opus 4/Sonnet 4）自动干预；hooks 文档 PreCompact 在压缩前触发（可挂自定义逻辑）**；**Subconscious Cache/TIMRUN：智能缓存层压缩时保留记忆——GLM-5.2 等前沿开源 LLM 自压缩（无手动触发无记忆抹除）——self-compact on the fly 方向**；**Cursor token 效率：agent 工作更长+步骤间带更多上下文——token 组装管理方式已变（不是简单窗口塞更多）**；**NVIDIA KVCR/FlexKV：KV Cache 卸载框架支撑更长上下文与更高吞吐（KV Cache 多层级分布式管理）**。判据：**先委托后压缩；关键里程碑前挂 PreCompact 钩子保规则；KV 层优化是服务端长上下文解法**。提升层：工具。
12. **编程上下文有效性的边界：context 注入的实证分层**（来源：arXiv 2508.08322《Context Engineering for Multi-Agent Code Assistants》+ 2607.27250 + codex 三研究汇总 2026-07 + morphllm）——**多 agent context 工程实证：Elicit/NotebookLM/ChatGPT/Claude Code 组合（多 agent 方式）成功更多任务+更少迭代——经常首次尝试就出可用方案 vs 单 agent 基线（只有 CLAUDE.md+直接用户 prompt）需后续 prompt 或开发者干预纠正**；**"injection strategy 不可测量地移动正确性"（288-run 消融，≤10-15pp 界）与"多 agent+结构化检索提升"不矛盾——差在检索机制与任务复杂度：简单任务注入策略差异无感，复杂多步任务结构化上下文工作区才显效**；**成本-收益：任何 context 注入都加推理成本（+20%），增益只有对正确信息密度才为正——context 注入是投资不是默认**；**Codex 三研究汇总：LLM 生成文件 -3% 成功率；开发者写 +4% 仅勉强抵消成本；100% 生成文件含 overview（not helpful）——content 质量>注入机制**。判据：**context 注入按任务复杂度路由：简单任务不加（省成本），复杂任务用结构化工作区+检索；文件内容宁窄勿泛**。提升层：工作流。
