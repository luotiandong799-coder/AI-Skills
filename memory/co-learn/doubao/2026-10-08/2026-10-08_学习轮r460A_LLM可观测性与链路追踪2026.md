## 落地 5 独点（每点标注提升层）

### 1. OTel GenAI 语义约定：gen_ai.* 标准 span 属性（工具/工作流/可复用 Skill）
来源：opentelemetry.cncfstack / futureagi-otel / braintrust / zylos / mlflow / openobserve
- **GenAI semantic conventions 稳定化（2026 v1.29+）定义 LLM 调用标准 span 属性：gen_ai.system（供应商）/gen_ai.request.model/gen_ai.usage.input_tokens/gen_ai.usage.output_tokens/gen_ai.response.finish_reasons——供应商无关统一 schema（OpenAI/Anthropic/自托管通用）**。
- **agent 级 span 加 gen_ai.agent.name/description；工具 span 加 gen_ai.tool.name；每 span 附 timing/input/output/token/cost（agentrace.cost.usd）——一次根 trace+子 span（llm.generate/chat、retrieval、tool.call、retries、auth、外部 API）覆盖整条 agent 流水线**。
- 提升层：工具（OTel 埋点）/ 工作流（统一观测 schema）/ 可复用 Skill（span 属性清单）。

### 2. span 树与 agent 级 trace：请求日志做不到的"为什么"（工具/工作流/可复用 Skill）
来源：inference.net / zylos / infoq-cloudflare / futureagi-tracing
- **LLM trace=服务单次请求的 span 树：每个模型调用、工具调用、检索、框架步骤带 timing/input/output/metadata——回答"不仅做了什么，而且为什么这么做"；请求日志是平的（每 HTTP 一条、无关联）做不到**。
- **每轮交互一条 trace：invoke_agent{agent class} → chat{model} → execute_tool{tool}；Agent Tracing 新增 agent 调用/模型调用/工具执行/审批等 span，模型信息+token 用量作元数据附到每个 span；工具调用/检索/推理步骤全部落在一个 trace 里可 SQL 查询**。
- 提升层：工具（trace 树）/ 工作流（按 trace 排障）/ 可复用 Skill（span 树模板）。

### 3. 生产五层并行评估与失败四桶（工作流/工具/可复用 Skill）
来源：futureagi-evaluating-genai-prod / latitude-tracking-llm-failures / tencent-cloud
- **生产 GenAI 评估五层并行：CI evals（部署前）/online evals（实时流量）/inline safety guardrails（输入输出防火墙）/drift monitoring（跨时间漂移）/trace-level observability（agent 链路）——单层不够，五层同时跑**。
- **失败四桶分桶（HTTP 200≠工作正常）：ops（timeout/rate_limit）/quality（hallucination/truncation）/structure（schema 错）/safety（PII 泄漏/越狱）——每桶各自绑 traces+live scoring+review+alerts+regression tests；完整迭代闭环=离线评测+在线观测+回归测试+人工反馈四模块打通（腾讯云）**。
- 提升层：工作流（五层评估）/ 工具（失败分桶标签）/ 可复用 Skill（失败桶模板）。

### 4. 采样评分：LLM-as-judge 只花该花的钱（工作流/工具/可复用 Skill）
来源：mlflow-observability-pipelines / latitude-realtime-eval / vibeengines
- **LLM-as-judge 打分路由：10-20% 生产 completion 采样送 judge 模型按 factual accuracy/relevance/instruction following 评分——统计显著信号够用且不双倍推理成本；分数回写 observability 平台为自定义指标或 span 属性，与 latency/token 一起可查**。
- **判据：先便宜后贵——rules 检查（schema/PII/citation）100% 流量全查；LLM judge 只用于 1%-10% trace + 100% 高风险 case；评估四步环=Curate（从生产 trace+边界 case 建版金集）→Score（程序化检查+验证过的 judge+人工标签）→Gate（每次 prompt/model/config 变更 CI 跑 eval 拦截回归）→Monitor+loop（采样打分查漂移，新失败回灌 eval case）**。
- 提升层：工作流（采样策略）/ 工具（judge 路由）/ 可复用 Skill（采样比例决策表）。

### 5. trace 聚类与异常检测：生产失败自动归因（工具/工作流/可复用 Skill）
来源：galileo-eval-framework / toolradar / alibabacloud-hermes / dev.to-kuldeep_paul
- **automated trace clustering：系统分析每条请求、分组相似模式、标出统计罕见异常、把失败链回根因——比人工翻 trace 快数量级；观测平台三件套=trace（span 全记录）+evaluation 层（输出打分/幻觉检测/回归标记）+prompt 管理（版本化/A-B）**。
- **对比失败 queries vs 成功基线分布（Honeycomb 法）；Hermes 插件把真实执行过程还原成结构化调用链：会话起点/推理轮数/工具调用/token 消耗/最耗时步骤/故障边缘区/恶意操作与敏感数据泄露——每轮 LLM/tool 调用都可查**。
- 提升层：工具（trace 聚类）/ 工作流（基线对比）/ 可复用 Skill（异常归因流程）。
