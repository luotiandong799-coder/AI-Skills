## 落地 5 独点（每点标注提升层）

### 1. 编排模式选型：选错模式是多 agent 系统贵 3-5× 的最常见原因（工作流）
来源：aipromptshub-multi-agent-coordination / rapidclaw-multi-agent-orchestration / augmentcode-swarm-vs-supervisor
- **四模式**：**supervisor**（单一控制器路由给专业 workers、收结果综合——适合清晰分解/审计需求/法律文书/代码生成/结构化抽取）；**swarm**（peer-to-peer 显式 handoff 互转——适合探索并行/独立负载，路由逻辑嵌入任务本身）；**hierarchical**（supervisor 嵌套 supervisor——大团队分层抽象，每层不同抽象级别）；**network**（完全去中心化，共享内存/消息总线通信）。
- **选型判据=任务互依性**：swarm 适合独立负载（分布式控制）；supervisor 适合动态路由/有序执行/冲突消解（中央协调）；**选错模式=最常见失败——成本 3-5×**。
- **supervisor 局限**：单一故障点+瓶颈——supervisor 挂/慢拖垮全流程；worker 相对 supervisor 无状态。
- 判据：先问"任务互依性与审计需求"再选模式；结构化/需审计→supervisor，探索/并行→swarm。

### 2. 非原子工具失败 + 验证后重试三纪律：52pp 重复副作用消除实证（工具/可复用 Skill）
来源：arxiv-2608.02645-verified-tool-calls / codex-non-atomic-tool-failures / agentnative-idempotent-retry-pattern
- **非原子工具失败**=工具已执行副作用但调用报告失败（或延迟成功后才报）——最隐蔽的失败类。
- **三纪律**：**verify-before-retry**（重试前先咨询 postcondition verifier，确认预期状态变更确实不存在才重试——绝不盲目重试）；**idempotent execution**（确需重试时带 key 使服务端去重，延迟成功到达也不产生重复效果）；**at-least-once 严格纪律**。
- **实证**：轻量验证包装器无需改模型——高故障率下重复副作用消除 **52 个百分点**，任务成功率 64%→100%。
- 判据：写工具调用先配 postcondition verifier；重试必须验证后发；副作用操作带幂等键。

### 3. 工具幂等分类注册表 + 幂等键生成规则（工作流/可复用 Skill）
来源：agentnative-idempotent-retry-pattern / google-cloud-retry-strategy / arxiv-2605.10555-agent-first-tool-apis
- **工具四档分类**：**read-only**（自由重试——list/get/token count/embeddings）；**idempotent-by-provider**（带 key 重试）；**journal-deduped**（效果日志检查后再重试）；**at-most-once**（绝不自动重试，升级人工/报警——如创建唯一资源）。
- **幂等键生成**：从**持久工作流身份**（run ID+step ID+attempt-independent 操作 hash）派生稳定键——**绝不来自时间戳/重试计数/LLM 输出**（这些每次不同，键失去意义）；agent-first 工具 API 用 idempotency_key_fields 指定键计算字段，重复键在窗口（默认 24h）内返回缓存结果。
- **LLM 应用也要幂等键**：LLM 可能同意图多次调用工具，重试导致双执行——refund/send/order 必须结构性防双扣/双发。
- 判据：每个工具入册定档；重试策略按档执行；幂等键=工作流身份派生。

### 4. 五层错误处理框架：从最便宜到最贵按序应用（工作流）
来源：alicelabs-ai-agent-orchestration / mastra-agent-swarm / microsoft-learn-ai-agent-design-patterns
- **2026 错误处理五层**：**retry（指数退避）→ fallback agent（换 agent 重派）→ escalate-to-human（升级人工）→ checkpoint and resume（检查点续跑）→ dead letter queue（死信队列）**——从最便宜到最贵按序应用，消除绝大多数级联失败。
- **workflow 状态必须持久化到 durable store**：内存中的 suspended workflow 活不过服务器重启；优雅降级=一个 agent 失败→retry/路由备份/标记人工审，不崩整个 pipeline。
- **编排者纪律**：agent 与编排者都要实现超时+重试、优雅降级、**表面错误不隐藏**（下游 agent 与编排逻辑才能响应）。
- 判据：错误处理按五层顺序叠；状态持久化；失败上抛不吞。

### 5. chat-only 恢复缺陷 + 检查点重放调试（工作流/可复用 Skill）
来源：augmentcode-async-ai-agent-workflows / dailyaiworld-multi-agent-debugging-playbook / c-sharpcorner-checkpointing
- **chat-only 恢复不可靠**：Terminal-Bench 上 chat-only 恢复仅 **8-13% 正确率** vs 语义感知 checkpoint/restore **100%**——chat-only 漏 OS 级副作用（文件系统变更等）。
- **重放调试流程**：thread_id 定位失败任务→列出该 thread 全部检查点→找失败节点前最后成功检查点→修改问题输入/工具响应→从该检查点重放→验证 agent 完成——**消除非确定性，不从头重跑**。
- **检查点四用途**：失败恢复（节点 3 挂不从头跑，从节点 3 续）；human-in-the-loop（暂停存 DB 等审批后恢复）；时间旅行（回退调试/换参数重跑）；长任务（数天等待型工作流）。
- 判据：恢复方案必须含语义状态（不止聊天历史）；调试走"检查点重放"定位隔离失败点。
