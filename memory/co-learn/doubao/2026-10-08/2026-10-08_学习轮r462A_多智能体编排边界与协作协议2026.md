## 落地 5 独点（每点标注提升层）

### 1. MCP 2026-07-28 无状态核心与网关可见面（工具/工作流）
来源：mirlohi（引 MCP 2026-07-28 规范一手）
- 协议核心转无状态：`initialize`/`initialized` 握手与 `Mcp-Session-Id` 头退役，每请求自带协议版本/客户端身份/能力；可选 `server/discover` 先探能力。
- 后果：远端 MCP server 退化为普通 HTTP 基建（请求可落轮询 LB 任意实例）；`Mcp-Method`/`Mcp-Name` 头给网关直接路由与策略面；工具/资源列表可带 cache hints（减少重复发现 + 稳定上游 prompt 缓存）。
- Multi Round-Trip Requests：工具调用中返回 `input_required` 索要确认/缺失值，客户端重试补回；Tasks 从实验性核心降为扩展；授权加 issuer 校验与更强凭证绑定，DCR 废弃改 Client ID Metadata Documents。
- 无状态传输 ≠ 无状态应用：工具可返回显式 handle 供后续引用，差别在应用状态可见、不再藏在 transport session 里。
- 提升层：工具（协议面）/ 工作流（网关策略面）。

### 2. 能力边界 vs 委托边界（可复用 Skill/工作流）
来源：mirlohi / thecaffeinatedengineer / redis
- MCP=capability boundary（调用方拥有编排）；A2A=delegation boundary（远端 agent 拥有内部计划）。
- 判据句：**"用这些参数跑这个具名操作"→tool-shaped→MCP；"对这个目标负责并汇报进度"→agent-shaped→A2A**。
- 核心问句不是"哪个协议功能多"，而是"请求跨过边界后谁拥有这份工作"。
- 两者都不保证：MCP 不保证安全参数/正确输出/最小权限/任务成功；A2A 不保证 peer 可信/artifact 正确/委托安全/策略合规。
- 单 orchestrator 控全部子 agent → 只用 MCP 即可；确定性服务间调用宁用普通 API。
- 提升层：可复用 Skill（选型判据）/ 工作流（边界划分）。

### 3. A2A v1 四对象与六条架构异味（工具/可复用 Skill）
来源：mirlohi（引 A2A v1 规范一手）/ rerun / vips
- 四对象：Agent Card（`/.well-known/agent.json`，身份/技能/接口/端点/认证）/ Message（一轮会话推进工作）/ Task（有 ID 与生命周期的有状态单元，含 HITL 暂停）/ Artifact（产出）——"conversation 推进工作、artifact 才是产出"。
- 支持 direct reply / streaming / task retrieve / cancel / subscribe / push；三绑定 JSON-RPC、gRPC、HTTP+JSON。
- 六条异味：A2A everywhere / MCP for opaque goals / Protocol as permission / One identity for every hop / Success by status string（`completed`≠通过验收）/ Unbounded delegation（无 depth/cost/time 上限）。
- 协议之后必须留 verification gate：互操作只把请求与结果送过边界，不成立"结果正确"这一结论，校验须由产出方无法自行重定义的外部检查完成。
- 提升层：工具（协议对象）/ 可复用 Skill（反模式清单）。

### 4. 编排三失效模式 + Token 经济学硬约束（工作流/工具）
来源：niteagent / traversaal / ainewshub
- Supervisor 瓶颈：orchestrator 的 LLM 调用在每轮关键路径上，失败/超时=全系统停摆 → worker 输出 schema 约束为蒸馏摘要 + orchestrator 状态 checkpoint 化 + fallback supervisor/超时走确定性路由。
- Handoff 死循环：trigger 重叠的两 agent 无限互转 → 全局 hop 上限（如 max 5）+ human handoff 逃生口。
- 路由漂移：各 agent 各自维护路由提示词，久之角色重叠/漏管 → 集中式 prompt registry + 版本化路由规则。
- Token 经济学（二手引 Anthropic）：多智能体≈单轮 chat 15×、≈单 agent+工具 4×；BrowseComp 上 token 用量解释约 80% 性能方差 → 首要优化目标是 token 效率而非"再加一个 agent"；手法=每跳只传 Delta context，禁止全量 rehydration（swarm 成本失控头号根因）。
- 二手引 MAST：多智能体失败中约 32% 来自 agent 间协调、约 79% 是系统性而非模型层（仅作趋势参考，未一手核论文原文）。
- 提升层：工作流（失效防护）/ 工具（成本判据）。

### 5. 上下文隔离三机制 + 状态外置三模式 + 直答旁路（可复用 Skill/工作流）
来源：skillmd / niteagent / traversaal / verticallabs
- 第一目的是上下文隔离：每个 sub-agent 在只装自己子任务的干净窗口里工作。
- 三机制：指令传递（默认，函数调用造指令只给所需）/ 文件系统记忆（需共享状态时才升级，延迟与一致性有代价但比消息传递更能扩）/ 全上下文委派（除非子任务真需要，否则部分违背隔离目的）。
- 状态协调三模式：shared-state 黑板（简单但易冲突）/ message-passing actor（隔离好但难调试）/ event-sourcing append-only（可审计可重放）。
- 生产教训：sub-agent 把产出写进 filesystem/artifact store，只回传轻量引用，不把完整 payload 塞进 handoff 消息。
- 转述失真：给 sub-agent 配 `forward_message` 工具，产出已定型时直答用户，不过 supervisor 再 paraphrase。
- 不确定该不该拆就别拆：任务图分解不干净、handoff 契约定义不紧时，单 agent 永远比编排得很差的多智能体好调试。
- 提升层：可复用 Skill（机制清单）/ 工作流（状态外置）。
