## 落地 5 独点（每点标注提升层）

### 1. Prompt caching 机制对比与代价表：三大提供商缓存差异（工具/工作流）
来源：aiworkflowlab-prompt-caching-2026 / novakit-prompt-engineering-2026 / genta-prompt-caching-guide / zylos-context-window-economics
- **三大提供商缓存机制**：**OpenAI 自动缓存 ≥1024 token 前缀、-50% 折扣、无需改代码、TTL 5-10 分钟**；**Anthropic 显式 cache_control 标记（最多 4 个 breakpoint）、-90% 读取折扣、TTL 5 分钟或 1 小时（extended）**；**Gemini 显式缓存**。
- **token 代价表**：**输出 3-6× 输入**（顺序生成最贵）；cache write 1.25-2× 输入；**cache read 0.1× 输入（比新鲜输入便宜 90%，长会话主导）**。
- **判据**：**缓存命中率<60% 说明 prompt 结构有问题**（重复工作负载上）；"大部分 prompt 被复用"应≈"大部分被缓存"——标稳定 system 块+稳定工具 schema 块，跨调用字节一致。

### 2. KV-cache 优化：稳定前缀前置 + 动态内容后置（工具/可复用 Skill）
来源：muratcankoylan-context-optimization / arxiv-2606.17016-tokenpilot / openai-cache-prompt-stability
- **KV-cache 复用=最便宜的优化**（运行时支持前缀缓存时）：低质量风险、立即省成本与延迟——**先做**。
- **做法**：稳定内容（system+工具定义+常检索文档）占 prompt 前缀，动态内容（用户 query/本次变体）放末尾；**工具定义/指令/顺序保持字节一致**——工具集变化时用 allowed_tools 限制可调用工具或 tool_choice=none，不动 schema 文本；canonicalization 算子保证跨轮前缀逐字节一致。
- 判据：结构 prompt 时先排稳定前缀；工具增删用 allowed_tools 而非改定义文本。

### 3. 上下文分区预算 + 三健康态 + 80% 压缩规则（工作流/可复用 Skill）
来源：lobehub-context-window-skill / asoasis-llm-context-window / aws-agentperf03-bp02
- **三区预算**：System / Skill Injection / Working-output——按组件分解并给每组件 token 预算（system 指令/工具 schema/会话历史/检索文档/用户 query 分开计）。
- **三健康态**：**ok<60% / compact 60-80% / exhausted>80%**；**80% 压缩规则=压缩在预算耗尽前触发**，不等到满。
- **压缩前协议**：commit 未提交变更 / 发 continuation signal / 更新 checkpoint / 持久化非可推导状态；安全裕度（如 10%）。
- 判据：按三区记账；80% 触发压缩；压缩前先落状态。

### 4. 任务描述钉定 + 死路清单：压缩后任务与失败路径不丢（工作流）
来源：aws-builder-ai-economics-beyond-caching / dev-nainikmehta-prompt-caching-playbook
- **钉定任务描述**：top-level objective 放动态上下文最前、**永不驱逐**——框架自动压缩上下文时，验证任务本身没被 summarize 掉。
- **显式死路清单**：总结前轮时捕获失败路径并标清 **"Do NOT retry these approaches: X, Y, Z"**——未标 failed 的失败方法会被重试（默认行为是重试失败路径）。
- 判据：压缩摘要里任务目标必须原样保留；失败路径必须显式标记，否则会重复尝试。

### 5. 缓存感知压缩：摘要请求蹭前缀缓存 + observation masking 优于 LLM 总结（工作流/可复用 Skill）
来源：aliyun-fork_prefix_messages / claude-cache-aware-rolling-buffer / agentnative-context-compaction
- **摘要请求蹭缓存**：fork_prefix_messages 场景下摘要请求=完整对话前缀+追加一句摘要指令——**开头与主对话逐字节一致→命中服务商前缀缓存，省一次全量缓存写入**。
- **缓存感知 rolling buffer**：keep_n=3、interval=25——旧截图按批换占位符，保持前缀稳定可缓存。
- **observation masking 优于 LLM summarization**：JetBrains SWE-bench 实证——掩蔽观测（mask 而非总结）**成本 -52%、solve rate +2.6%**；naive summarization 有失败模式（丢掉关键决策/状态）。
- 判据：压缩时优先 masking/截断旧观测，总结留给关键决策层；摘要调用开头与主对话一致以蹭缓存。
