## 落地 5 独点（每点标注提升层）

### 1. Spec 四段式 + 负空间规约 + Constitution 先行（工作流/可复用 Skill）
来源：blink-agentic-coding / metamindz-7rules / thebcms-sdd / softwareseni
- **spec=1-2 页结构化文档四段**：What（该功能一句话做什么）/ Why（解决的用户问题）/ Scope（含什么、显式排除什么）/ Success criteria（怎么验证成功）——**agent 每个请求都把它当上下文读，消除来回往返**。
- **Spec 负空间且保持短**：under-spec（"应该工作得很好"）无信息；over-spec（"用 Map 别用 Object"）把实现细节勒死、文档膨胀——**失败模式两边夹**。
- **Constitution 先行**：先 commit AGENTS.md/constitution.md（原则/标准/guardrail）再写第一条 spec；**一 feature 一 spec 目录 `specs/NNN-feature-name/{spec.md, plan.md, tasks.md}`**。
- **成熟模式**：vibe-code 出一个 spike → 蒸馏成 spec → spec-drive 生产版。
- 提升层：工作流（开发流程）/ 可复用 Skill（spec 模板）。

### 2. Spec 生命周期三形态：spec-first / spec-anchored / spec-as-source（工作流/可复用 Skill）
来源：dev-lu1tr0n / thebcms / javacodegeeks
- **spec-first**=规格驱动实现，代码是次要工件，spec 变了代码可再生。
- **spec-anchored**=规格与代码并行进化、往返平衡。
- **spec-as-source**=规格是系统权威来源，代码自动生成/自动验证；**agent 不发明 API 形状/错误码——从契约读；偏离立即可见（测试失败或 CI 对 OpenAPI 文档校验）**。
- 判据：选哪种看 spec 稳定性——高频变动用 anchored，规范系统用 source。
- 提升层：工作流（契约管理）/ 可复用 Skill。

### 3. TDD agent 化：红绿重构 + 测试=机器可检查规格（工作流/可复用 Skill）
来源：sureprompts-tdd / aicoderscope / developertoolkit-tdd / aitrendblend / theneuralbase-tdd
- **红**：agent 只写测试、零实现改动——跑完套件应全红；**有测试没实现就通过=测试本身写错了**；让 agent 跑套件并展示失败，证明测试瞄准真实未实现行为（不是 import 拼错"假失败"）。
- **绿**：单条窄指令"让这些测试过、别碰测试文件"写最小实现——**大而全的投机实现=范围蔓延+bug 入口**。
- **重构**：结构改进、行为不变、测试全程绿；测试+spec 双安全网防行为回归。
- **测试先写 vs 实现+测试一起**：先写测试的产出可测更好——**测试是机器可检查的规格，模型无法幻觉越过它**；每函数 10-20 测试含 happy path/错误/边界。
- 提升层：工作流（TDD 循环）/ 可复用 Skill（agent TDD prompt 模板）。

### 4. AI-native 开发循环：八步流水线 + 计划-实现上下文重置 + agent 六步循环（工作流/可复用 Skill）
来源：microsoft-devblogs / cadence / zencoder / developertoolkit-migration
- **八步流水线**：Constitution → Specify → Clarify（消歧义/依赖/边界）→ Plan → Tasks（拆成实现就绪单元）→ Implement → Validate——**每步喂下一步**。
- **agent 六步循环**：ACT（选工具 read/edit/run_shell/run_tests）→ OBSERVE（原样读工具输出）→ REFLECT（观察匹配计划吗）→ DECIDE（继续/重规划/升级/停止）→ VERIFY（测试/类型检查/lint/重读 diff）→（下一轮）。
- **计划-实现上下文重置**：计划批准后**重置会话上下文、只喂批准的计划再实现**——不依赖早期探索讨论（防探索噪声污染实现）；实现时看 diff 不看击键，改保持单逻辑单元。
- 提升层：工作流（开发循环）/ 可复用 Skill。

### 5. 结构化评审：五个风险类别 + agentic code review 多角色（工作流/可复用 Skill）
来源：developersdigest / baeseokjae-8patterns / google-adk / dailytopai
- **不逐行读，聚焦五风险类别**：安全边界（每 API 路由验认证？输入验证？数据 scope 到请求用户？）/ 数据变更（谁写库？竞态？完整性？）/ 错误处理（外部服务失败？错误捕获上报？用户见有用消息？）/ 性能 / 可测试性。
- **Agentic Code Review**：agent 顺序扮演多角色（安全审计员→性能分析→测试覆盖检查→风格执行）在人类评审前过每 PR——**系统性多视角不是"问 AI 看 diff"**；内建 /review 命令（Claude Code/Codex/Cursor）先过一遍。
- 判据：AI 先过一遍多角色评审→人只读最终 diff 当资深评审——正确性/安全/边界。
- 提升层：工作流（评审流程）/ 可复用 Skill（评审角色清单）。
