## 独点（10）

1. **任务级幂等设计是韧性地基**（来源：digeniotech + padiso）——故障容忍系统的地基=幂等：同一任务跑两次=同样结果+无副作用重复；AI 工作流最需在任务级落实——文档批处理跑到一半失败，能否安全重跑？还是会出现重复 DB 写、重复 Slack 消息、半处理记录？外部写之前用「源事件 ID + 操作名」生成幂等键并存储。判据：**重跑安全=任务级幂等，外部写必带幂等键**。提升层：工作流。
2. **DLQ 是修复面不是日志**（来源：supergood + p42.studio + dreaming.press）——DLQ=重试全部耗尽后失败任务落入的独立队列/存储；三性质=持久（任务直到显式确认/删除才消失，不蒸发）、元数据保全（原始 payload+失败原因+重试次数+时间戳）、可重放（检查 DLQ 项→修根因（改 prompt/修上游数据/调 agent 配置）→重新入队）；DLQ 深度应是受监控指标。判据：**DLQ=可检查可修复可重放的修复面，不是错误日志的别名**。提升层：工作流。
3. **DLQ 条目元数据契约**（来源：openlegion）——每条 DLQ 项必须含：原始任务 payload、agent ID、错误类型与消息（**sanitized 防系统提示词泄漏**）、重试次数与时间戳、重试期间消耗的预算、`recommended_action` 字段把失败分类为 `operator_review / context_reduction / ...`（给下游一个"接下来怎么办"的明确动作而不是裸错误）。判据：**DLQ 条目=payload+agent id+消毒错误+重试预算+recommended_action，让失败自带处置建议**。提升层：工作流/工具。
4. **五层自愈架构**（来源：aifloxium）——幂等守卫（任何副作用发生前阻断重复处理）→ 智能重试（自动吸收瞬时失败）→ 补偿动作（某步永久失败时撤销部分已完成工作）→ 死信队列（隔离无法处理的记录，主链继续流动）→ 可观测+告警（按失败预算度量）；与 r327C 三层错误处理的关系：r327C 管"失败怎么记怎么重试"，本条补"幂等守卫前置+补偿动作+失败预算"。判据：**自愈=幂等守卫→智能重试→补偿→DLQ→可观测，五层缺一不闭环**。提升层：工作流。
5. **重试五级分级**（来源：kunalganglani agent-engineering-patterns）——工具调用失败按类型分流：Transient（网络/限流）→退避重试（3 次）；Validation（参数错）→**返回错误给 LLM 让它自己纠正**（不重试）；Permission（认证）→升级人工；Logical（无结果）→返回空让 LLM 决定下一步；Catastrophic（DB 挂）→熔断中止整个任务；与 r327C"瞬时/逻辑二分"的增量=validation 返 LLM、permission 升级人工两个明确通道。判据：**失败分类决定处置：瞬时退避、参数返 LLM、认证升人工、无结果返空、灾难熔断**。提升层：工作流。
6. **自愈编排的消融证据：根因分类→定向恢复是增益来源，不是重试次数**（来源：arxiv 2606.01416）——移除根因分类器使任务成功率 99.3%→95.7%；移除定向恢复得到同样降幅——证明可靠性增益来自"失败类→恢复动作"的映射而非单纯重复尝试；移除可观测 trace 不减成功率但消除 trace 事件——可观测主要支撑可诊断性而非直接完成任务。判据：**自愈编排=根因分类+定向恢复，二者缺一即掉分；可观测价值在诊断不在完成**。提升层：工作流/工具。
7. **Saga 补偿模式：forward + compensation + ledger**（来源：moai.team）——把工作拆成步骤，每步有 forward action 和 compensation；第 N+1 步不可恢复失败时，对 1..N 步跑补偿恢复到一致业务状态；forward=建工单/写记录/发邮件，compensation=关/回退工单、删除或标记作废记录、发更正邮件；**ledger 记录哪些补偿仍有效，且补偿本身必须幂等**（补偿被重跑也不能产生新副作用）。判据：**多步外部副作用=每步配补偿+ledger 管资格+补偿自身幂等**。提升层：工作流。
8. **持久执行：确定性重放，已完成的 Activity 不重跑**（来源：temporal + aws + databricks + zylos + dev.to agdex）——Temporal 模型：工作流代码确定性、非确定性工作与副作用推入 Activities；服务存 Event History（Activity 调度与结果/timers/signals），worker 崩溃后按 Event History 重放代码重建状态——**遇到已记录步骤不物理执行、直接返回 journal 缓存结果**（信用检查保持 completed、模型响应保持原样）；wait 状态驻留 Event History 而非 RAM（杀 worker 不丢审批）；持久执行=系统保证最终达终态（成功或受控失败）无论瞬时基础设施中断。判据：**副作用进 Activity、重放只重放代码不重放副作用、wait 驻留事件历史——恢复成为运行时职责而非应用职责**。提升层：工具/工作流。
9. **检查点存储成本治理：全快照 O(N²) vs delta + 周期快照**（来源：langchain delta-channels）——LangGraph 默认全快照模型：长消息历史+文件系统上下文时检查点存储 O(N²) 增长，成为真实运营成本；DeltaChannel=每步只存 delta + 每 K 步写一次周期全快照，resume 延迟有界、存储成本随会话变长保持平坦；升级透明（既有线程继续工作）；配套=TTL 自动过期旧检查点 + gzip 压缩 + >350KB 大检查点 S3 卸载。判据：**长会话检查点=delta 存储+周期快照+TTL+压缩+大载荷卸载，别用全快照堆**。提升层：工具/工作流。
10. **n8n 集中式错误处理与恢复工作流续跑**（来源：n8n community 304713 + 300785 + n8nlogic + nex-flow + n8noneclick）——双层架构：节点级 Retry On Fail（maxTries+wait）吸收瞬时（网络/429）；Error Trigger 工作流处理剩余（告警/DLQ/记录）；**恢复工作流模式**：定时扫描 `status='failed' and retry_count<max` 的表→读 Last Successful Step→用 Switch/子工作流从该点续跑而非整链重启；On Error=Continue（错误输出分支）只在部分成功可接受时用，**且错误分支必须路由到某处**；n8n 官方 2026-07-03 指南=编排层静默管基础设施级重试、LLM 管需要上下文的推理级恢复（分工链）。判据：**失败恢复=双层（节点重试+Error Trigger）+恢复工作流从最后成功步骤续跑；错误分支必须路由到某处，不许悬空**。提升层：工作流。
