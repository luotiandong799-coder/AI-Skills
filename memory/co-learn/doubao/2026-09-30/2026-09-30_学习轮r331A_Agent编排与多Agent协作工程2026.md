## 独点（10）

1. **编排拓扑主导系统性能**（来源：arxiv 2602.16873 AdaptOrch）——多 agent 编排拓扑（如何协调/并行/综合）现在主导系统级性能、超过单模型能力（性能收敛时代）；四典型拓扑=parallel/sequential/hierarchical/hybrid，按任务依赖图+领域特征动态选择。判据：**先按任务依赖选拓扑，再选框架**。提升层：工作流。
2. **五模式坐标表：主控制点=防什么失败**（来源：augmentcode）——sequential pipeline=阶段间验证门控、防错误复合、限=跨表引用失败；parallel fan-out=聚合器综合、防竞态、限=前置顺序检查；supervisor-worker=中央主管、防单 agent 上下文坍缩、限=模糊委派；hierarchical；critic loops。判据：**按工作形态选模式，每个模式答清"控制点在哪、防什么失败、主要限制"**。提升层：工作流。
3. **handoff 六要素**（来源：loooop.dev OpenAI Agent Orchestration）——交接载荷必须含：target agent / context（或外部 store 指针/token）/ instructions（接收者聚焦点）/ metadata（路由原因、优先级、约束）/ auth（credential 或类型）/ model_hint。判据：**交接载荷=目标+上下文+指令+元数据+权限+模型提示，六项缺一交接即失真**。提升层：工作流/工具。
4. **结构化交接消息 + 边界蒸馏**（来源：aws agentcost01-bp02）——用 summary 对象替换完整对话历史（任务规格+相关事实+接收者必须遵守的约束）；版本化消息 schema 让接收者能拒绝畸形交接；交接边界加小模型调用提取"最小充分上下文"，输入 token 反映当前任务需求而非累积历史。判据：**交接=结构化摘要+版本化 schema；每个边界蒸馏一次最小上下文**。提升层：工作流。
5. **共享上下文存储：不在编排层序列化大载荷**（来源：aws agentperf05-bp04）——委托 agent 写上下文、接收 agent 读（共享 store 如 AgentCore Memory/DynamoDB），避免大上下文载荷穿过编排层；context transfer schema 定义每种委托的最小上下文（数据验证 agent 只需数据+验证规则，不需完整会话历史）。判据：**跨 agent 大上下文走共享存储按需读，不序列化搬运**。提升层：工作流。
6. **多 agent 成本爆炸是结构性失败**（来源：botonomy + channel.tel + github muratcankoylan）——五 agent 系统可烧单 agent 10-50 倍 token；多 agent 运行成本约 15x 基线——预算按 15x 估、估少即失败；成本尖峰是突发的（查询型成本 $0.03→$0.47，占 30% 流量月账单翻倍）；orchestrator 重复处理全上下文=放大点。判据：**预算按 ~15x 基线估；成本尖峰突发性，coordinator 即放大点**。提升层：工作流。
7. **何时不用多 agent**（来源：niteagent + neodrop + arxiv 2510.26585）——共享状态推理=单 agent（15x 少 token 且同等或更好准确率）；预算受限=单 agent（$0.15 vs $2.25+）；自动生成 MAS 一致劣于单 agent CoT+Self-Consistency（10x 贵+结果更差，"architectural bloat"）；SUPERVISORAGENT 用 LLM-free 自适应过滤器介入纠错可省 29.45% token 不损成功率。判据：**共享状态推理/预算敏感→单 agent；只有领域隔离或并行独立研究才上多 agent**。提升层：工作流。
8. **agent 循环无终止=最大生产事故**（来源：aiintegrator + respan）——orchestrator 完不成→重路由→worker 结果不达标→再试→循环直到成本告警；ReAct 无 max-step 会在边界情况永远循环；上线前四控制=最大迭代限制/token 上限/预算层/优雅"无法完成"返回。判据：**多 agent 必配：迭代上限+token 上限+预算层+优雅失败，四件套**。提升层：工作流。
9. **共享状态四写冲突方案**（来源：hydradb + zylos + rinet）——LWW（简单但金融/安全关键危险）→ supervisor 裁决（慢但显式可控）→ 版本化（不覆盖、新建版本、agent 引用信任版本）→ CRDT（commutative/associative/idempotent 数学保证无冲突合并；grow-only set / LWW-map）。判据：**写冲突按安全等级选：LWW<裁决<版本化<CRDT**。提升层：工具。
10. **单写者所有权 + 写时冲突检测**（来源：max-gherman + arxiv 2605.20563 STORM + agenthold）——最简单防冲突=每片状态一个写 agent（key_prefix+owner_agent_id+readable_by 分区表，串行化更新源头）；STORM 写时检测冲突立即解决而非事后 merge；乐观并发=写时带读到的版本号、版本变了拒写（ConflictError+当前值），agent 重读重算重试。判据：**先单写者分区；需并发就版本化乐观写+冲突时重读重试**。提升层：工具。
