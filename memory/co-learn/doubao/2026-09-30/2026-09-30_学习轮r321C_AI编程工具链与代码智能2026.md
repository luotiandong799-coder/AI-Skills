## 独点（10）

1. **Agentic SDLC 全阶段对照：phases survive，labor moves**（来源：arxiv 2604.26275 2026-09 + stackoverflow 2026-04 + wetheflywheel 2026-05 + augmentcode 2026-06）——**传统 SDLC 六阶段×Agentic 角色对照=Requirements（Intent specification；agent drafts spec）/Design（agents propose & critique；human selects）/Implement（coding agents execute plan；human reviews）/Testing（testing agents generate suites；sandbox）/Deploy（CI agent gates；human approves prod）/Maintain（monitor agents triage；repair agents patch）**；**人的角色从"做"转向"指明意图+审批结果"（specifying intent/reviewing diffs/arbitrating tradeoffs）**；**孤立采用在组织规模失败——review bottlenecks/fragmented workflows/trapped knowledge 会吸收掉 gains——成熟组织把 review 浓缩到更少更高价值的 checkpoints，配共享编排基建**。判据：**每阶段保留一个人类审批点（设计选择/生产发布），其余交给 agent**。提升层：工作流。
2. **四相循环与 TDD-by-Delegation**（来源：futureproofing 2026-09 + baeseokjae 2026-04 + github TDD agent 2026-09）——**Anthropic 四相循环=Explore→Plan→Implement→Commit——agent reads before writes/plans before edits/verifies before commits/human signs off before merges**；**TDD-by-Delegation=开发者写或描述测试，AI agent 写实现让它通过——强迫精确，消除"agent 猜意图"这类 AI 编码错误的最大来源**；**REQUIRED SEQUENCE=Write test→Run→Verify FAILURE→Implement→Run→Verify SUCCESS→Refactor→All PASS**；**反馈环由 agent 处理而非人**（agent 跑测试→读错误→调代码→重试直到 green）。判据：**先给测试后给实现；验证在提交前由 agent 完成、合并前由人拍板**。提升层：工作流。
3. **Spec-first 工作流与 Spec→Plan→Task 三阶段**（来源：blink 2026-05 + mr.technology 2026-07）——**写 prompt 前先写 spec：1-2 页结构化文档 4 节=What（一句）/Why（用户问题）/Scope（in/out 显式）/Success criteria（如何验证）——agent 在会话每请求读作 context，tight spec 消除往返**；**三阶段=agent 走 frozen plan top to bottom→每 plan item 变 task→每 task 后验证 postconditions（跑相关测试/查输出/读相关文件）→postcondition 失败有固定 retry budget（通常 2）→耗尽则 stop、report、等 human intervention（不继续）**。判据：**spec 冻结计划；每任务验证后置条件；重试预算 2 次封顶**。提升层：工作流。
4. **并行化收益与反信号：measure outcomes not feelings**（来源：baeseokjae 2026-05 + wetheflywheel 2026-05 + macleodlabs 2026-09）——**SDLC 转变不是打字更快而是并行性——feature development/test generation/code review/documentation 同时跑（agent 不 context-switch 不需要会）——三天 sprint→hours**；**反信号①=self-reported/anecdotal 加速估计可以错得离谱（METR 2026 教训）——measure outcomes, not feelings；反信号②=McKinsey 测 AI 约减半写新代码时间，但 DORA 2024 测 delivery stability -7.2%——收益真实且不均衡**；**GitClear 211M 变更行（2020-2024）显示 refactoring-associated lines 下降**。判据：**并行化收益以产出度量；AI 收益与稳定性成本分开核算**。提升层：模型。
5. **Dynamic Context Engineering：语义文件选择+接口骨架暴露**（来源：businesstechnavigator 2026-05 + aisrc 2026-09）——**把整个 repo 塞进 context 会降低模型推理准确度、更难找相关代码段**；**解法①Semantic File Selection=用 vector db+embeddings 检索 repo 找任务相关文件，只载最相关的；解法②Interface Skeleton Expose=依赖但不需修改的文件只暴露接口签名（class structures/function signatures）**；**Claude Code 2026 框架=memory hierarchy/rules/settings/hooks/subagents/sandboxing/cost visibility 的 terminal-first coding system（已非 CLI wrapper）**。判据：**相关文件向量检索载入；依赖文件只给接口签名**。提升层：工具。
6. **AI 代码审查智能体：从报问题到自动修**（来源：harness 2026-08 + artificialus 2026-09 + gitlab duomr 2026-04 + google codemender 2026-07 + smart-webtech 2026-06 + openhands 2026-06）——**AI code analysis 按行为而非表面语法评估代码——agent-driven 工具 act on findings 而非 filing static reports**；**Harness 三 agent=Code Review（三阶段 PR 反馈）/Code Coverage（自动测试生成）/Autofix（CI 失败自动修复）——经 PR 提交变更**；**Duo MR Reviewer=多 agent 并行专精审查（security/performance/business logic/style 各一）→cross-check 交叉验证消除假阳→severity 排序——2 分钟内**；**CodeMender=漏洞验证后自动生成 secure patch→LLM-as-judge 确保修复不破坏既有功能**；**Bugbot（Cursor 收购 Graphite 后）月审 2M+ PRs，76% 检出问题自动生成 fix PR**；**CodeRabbit 75M+ defects/6M+ repos；Change Stack（2026-05）=把大型 AI 生成 PR 重组成 ordered cohorts+layers 便于审**。判据：**审查 agent 输出修复 PR 而非评论；多 agent 交叉验证去假阳；修复过 LLM-as-judge 回归**。提升层：工具。
7. **Agent 测试失败两大源与验证环**（来源：developersdigest 2026-05 + bridgeapp 2026-08 + businesstechnavigator 2026-05）——**agent 构建功能后的测试失败主要来自两处=①agent 用了不匹配真实实现的 mock ②agent 改了函数签名没更新所有 caller——把错误输出贴回 agent 让它 trace 回根因**；**validation loop=agent edits→runs unit tests→examines failures→adjusts→repeats until green；层叠 static analysis/linters/formatters/e2e 一层层加**。判据：**失败先查 mock 与签名两源；验证环由 agent 自跑至绿**。提升层：工作流。
8. **大型重构与持久协调器：Projects 模式**（来源：dev saaswithalex 2026-09 + clickaplicaciones 2026-09 + ithome 2026-09）——**大型重构的正解=orchestration layer 接到既有 change-management infrastructure（不是 demo 级花样）**；**Cursor Projects（2026-09）=persistent coordinator 委托数千 subagents 跨 cloud+local machines，维护 shared context files，watch Slack/PR queues 无需提示——重度用户 merge 6x PRs、新用户 +30%**；**2026-02 起同一 issue 可同时 assign Claude/Codex/Copilot 并行比较方案**；**Kimi Code 四层扩展机制=Skills/Hooks/MCP/Plugins；Claude Code Auto mode 2026-08-14 成默认权限模式（动态工作流数十 agent）**。判据：**重构编排挂在既有变更管理上；持久协调器管 shared context；高价值任务可多 agent 并行对照**。提升层：工作流。
9. **IDE 原生智能接入：agent 用 IDE 自己的工具**（来源：jetbrains×2 2026-09 + ithome 2026-09 + aisrc 2026-09）——**Rider 2026.2=编码 agent 直接连 IDE 自有智能与工具（coverage data/debugger/profiler/refactoring engine/framework-specific guidance）——基于真实项目知识工作，无需从文件与终端输出重建——更快找上下文、提高更改安全性**；**Copilot 四 surface（2026）=Inline Completion/Chat/Workspace（cloud-side agentic 多文件）/Coding Agent（类 Cursor Background Agents）——每种 surface 对应不同工作流形态，优势=四者+GitHub 生态整合**；**Claude Code 1M token context（Opus 4.6）+Agent Teams 并行**。判据：**优先让 agent 走 IDE 结构化工具（覆盖率/调试器/重构引擎）而非裸文件读写**。提升层：工具。
10. **AI 编程工具选型 2026：按工作流契合度选**（来源：dev akaranjkar08 2026-07 + aibuzz 2026-05 + toolchase 2026-09 + botmonster 2026-04 + tech-insider 2026-09 + feng 2026-09 + anthropic 2026-02）——**无单一工具四维全胜——Claude Code=raw capability 胜（SWE-bench 74-87.6%/1M context/deepest architectural reasoning，terminal-first 多步+多文件+Agent Teams 并行）；Cursor=开发者日常体验与团队工作流胜（AI-native IDE，背景 agents+云自动化）；Copilot=企业广度与组织默认位胜（$10/mo 最宽 IDE 支持 VS Code/JetBrains/Neovim/VS/Xcode）**；**Windsurf/Devin=well-defined 任务自治执行**；**模型面=Opus 4.6 更仔细规划/更长 agentic 任务/更大代码库/更好自纠（catch own mistakes）；Sonnet 5.5 Terminal-Bench 4.0 70.6% vs Sonnet 5 的 10.3%（智能体编程评测飞跃，一半价格）**；**建议=从契合当前工作流的工具开始（企业用 Copilot，IDE 深度用 Cursor，终端/大型重构用 Claude Code），多工具并存按任务分工**。判据：**选型按任务形态分工而非"最好的"单点**。提升层：工具。
