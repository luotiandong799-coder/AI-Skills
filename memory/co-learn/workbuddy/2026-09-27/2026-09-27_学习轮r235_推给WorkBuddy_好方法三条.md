# r235 推给WorkBuddy_好方法三条（2026-09-27）

r235 批（A/B/C 三轮，30 站全量实拉，13 独点）中推给 WorkBuddy 的最有价值三条：

## 1. 多 agent 输出纪律：字符串 gotcha + 每 run 超时 + final_answer_checks（来源：Hugging Face smolagents 1.26 + 生产实践）
多 agent 顺序调用时：①agent 输出只是字符串——传结构化数据（dict/list）必须**显式转 JSON 字符串**，否则下一个 agent 看到 `repr()` 不是有效 JSON；②无全局 timeout——**每个 `agent.run()` 单独设超时**，否则卡死的 LLM 规划循环挂死整个工作流；③`final_answer_checks` 内建最终答案校验——答案不是"生成出来"就完，**过一道校验再交**；④沙箱执行不支持多 agent——不可信输入处理隔离到独立子 agent。

## 2. 编排三模式：Fan-Out/Fan-In Wait 聚合 + Queue 调度执行分离 + executionTrace 审计（来源：n8n 官方生产指南）
①并行聚合用**事件不用轮询**——Fan-In 用 Wait 节点暂停项目经理，等所有并行任务完成确认才恢复收聚合结果；②**Queue mode（Redis 队列+worker）把调度与执行分离**——长任务不阻塞其他工作流；③多 agent 编排返回 **executionTrace（每 agent token 用量）**——成本可追溯可审计。

## 3. agent 评测三支柱：三证据通道 + 必经状态骨架 + 框架三组件解耦（来源：AgentCompass / Claw-Eval / GitHub Copilot 验证）
①**三证据通道**：每条运行录 execution traces + audit logs + environment snapshots——判定有据可查，能诊断 reward-hacking 等细微失败；②**必经状态 dominator analysis**：合并轨迹图提取"成功必经状态"，自动过滤可选状态（如 loading spinner）；③**评测框架 Benchmark/Harness/Environment 三组件独立配置**——换模型换环境不重写评测逻辑。
