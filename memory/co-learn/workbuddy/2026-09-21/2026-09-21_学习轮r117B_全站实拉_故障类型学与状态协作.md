## 独点：3 条
**D30：工具环境故障类型学+可恢复注入（来源：arXiv 2606.25819《Beyond Function Calling》2026 实拉）**
- 机制：工具环境不可靠性的故障类型学——Specification Drift（规格漂移：工具行为与文档不符）/Invocation Errors（调用错误）/Execution Failures（执行失败）/Output Drift（输出漂移）/Cross-Source Conflict（跨源冲突）；注入失败须"既破坏又可恢复"，每个注入任务至少保留一条恢复路径：retry（重试）/fallback（回退）/cross-checking（交叉核对）/normalization（归一化）/evidence verification（证据验证）。
- 判据：**测试工具可靠性时，故障注入必须有恢复路径，且恢复路径本身是可枚举的**——只破坏不可恢复的任务测不出"恢复能力"；故障分五类，处置先归类。
- 与 §工具失败 2×2 分类学（D22）分工：D22 管"失败性质（显式/隐式×瞬时/永久）决定处置策略"，本条管"调用侧五类具体故障+恢复路径五选"——性质决定要不要重试，类型决定怎么修。
- 提升层：工具/工作流（故障注入与恢复路径设计）。

**D31：结构化错误恢复优于纯英语（来源：arXiv 2606.05037 REVISE + Codex KB 2026-08-12 实拉）**
- 机制：270 次尝试三种错误响应模式对比（相同验证逻辑）：结构化机器可读错误（含错误码/字段/恢复建议）比纯英语描述恢复成功率更高；错误反馈要带"下一步能做什么"。
- 判据：**工具报错给模型的格式要结构化，不是写得长**——错误码+失败字段+恢复建议（机器可读）优先于一段自然语言描述；agent 在结构化反馈下恢复成功率显著更高。
- 与 §重试分类 分工：那条管"什么时候重试"，本条管"错误信息本身长什么样"——错误信息是 agent 恢复的输入，结构化输入才有结构化输出。
- 提升层：工具（错误反馈格式）/工作流。

**D32：多 Agent 协作用 schema 验证的状态变更，不用对话（来源：arXiv 2605.29313 PatchBoard 2026 实拉）**
- 机制：用经验证的 JSON Patch 变更替代 agent 间自由对话——Architect agent 构造任务特定 schema+工作流规则，确定性内核在提交前验证每个状态变更（schema 约束/角色写契约/运行时不变量），事务性提交；ALFWorld 84.6% vs 30.8%。
- 判据：**agent 间"说"不如"改"——协作通过共享状态的可验证变更完成，而不是自由文本对话**；每个变更过 schema/写契约/不变量三重验证再提交；对话只留规划与评审，落地全走结构化状态。
- 与 §多 Agent 协作纪律·接口契约 分工：那条管"输入输出格式固定"，本条管"状态变更是唯一落地通道且必须 schema 验证"——契约管形状，本管管通道与验证。
- 提升层：工作流（多 Agent 协作机制）/可复用 Skill。
