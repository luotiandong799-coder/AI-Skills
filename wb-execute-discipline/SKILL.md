# wb-execute-discipline（执行纪律：覆盖零省略，失败不放弃，错不过三）

来源：用户 2026-09-13 三条原话指令（当日学习循环实测提炼）：
1. **"我让你打开的都必须全部学完 一个都不能少"**
2. **"失败了你要继续进去学习 不能失败了就放弃"**
3. **"如果失败2次以上要思考为什么错 不能一直错误的方式进行下去 然后纠错改正优化以后不再一样错"**

## 〇、先查 GitHub 再动手：现成优先，能改就不从零写（用户 2026-09-16 规则）
**任何工作任务开始前**，先做一步 GitHub 复用检查（用户原话："工作任务先看 GitHub 有没有现成的或者差不多拿来可以改的"）：
- 搜索关键词 = 任务的核心动作 + 领域（如"agent skill document summarize"、repo 名 + 能力词），用 general_search / GitHub Search 代拉，找：**现成实现**（正好是这个功能）或**相近实现**（差不多的，可改造成本低）。
- **判定优先级**：有现成的直接复用 → 有差不多的 clone 下来改 → 都没有才从零写。复用优先于重写，和"重复功能不重复投入"同一原则。
- 复用检查结果留痕一行：找到什么（repo 链接）/ 判不判可改（为什么）/ 最终选择（复用 / 改造 / 自写）。找不到也留痕"已查无复用"，不跳过这一步。

## 一、覆盖零省略（原则一）
- 用户点名过的**每一个**目标（站点 / 仓库 / 文件 / 清单项），本轮都必须**真实执行、真实评估**：
  - 不得用"每轮抽 N 个轮换"代替全表
  - 不得用"上轮已做过 / 已评估过"代替本轮实做（结论必须来自本轮）
  - 不得以"预计无价值"为理由预跳过——判定必须来自实做后的证据
- **"完成"的判定** = 真实执行 → 逐条评估 → 有产出就落地 / 无产出记录判据。三项缺一不算完成。
- 目标清单要**显式列出并逐项打勾留痕**，不靠脑子记；漏项 = 违规。

## 二、失败持续攻坚（原则二）
失败（访问失败 / 超时 / 被拦 / 报错）**不等于放弃**，按路径阶梯逐级换路：
1. **直连**（WebFetch / curl 默认路径）
2. **换端点**：镜像站、备用域名、API/JSON 端点、无 www 域名
3. **浏览器渲染**（agent-browser / playwright，可过部分 bot 检查）
4. **替代入口**：站点官方镜像、缓存页、聚合页
- 每级试过仍失败才可标注"本轮未达"；**只要还有一级路没试，就不许写"放弃 / 跳过 / 略过"**。
- 失败必须**如实留痕**（哪级、什么错误、何时），失败项不算完成，下轮优先补。

### 换路之前先辨错误类型（决定"重试有没有意义"）
来源：Make Help Center `exponential-backoff` / `error-handlers`（2026-09-14 经代理实访）+ 本轮实测样本。

**别把三类失败混成一类处理**——同一路径原样重试只对其中一类有意义：

| 类型 | 特征 | 正解 |
|---|---|---|
| **瞬时（transient）** | 连接超时、5xx、限流、DNS 抖 | **退避后重试有意义**：逐次拉长间隔（1m→2m→10m→30m…），并设**次数/总时长上限**，到顶停手 |
| **确定性（deterministic）** | 403 / 404 / 认证失败 / bot 拦截 / 域名停放 | **重试无意义**（同样是 403，重试一万次还是 403）→ 直接换路（换端点 / 代理 / 认证）或判"本轮未达" |
| **空壳（empty shell）** | **HTTP 200 但正文为空 / 只有 JS 壳 / 停放页** | 也属"没有内容"：**判据要看内容，不只看状态码** |

- **状态码不是全部证据**：本轮实测 `fullstackskills.com` 返回 **200 但正文只有 114 字节**（GoDaddy 停放页）；`chatgpt.com/gpts` 200 / 528KB 但剥掉 script 后正文 **39 字符**（纯 JS 渲染壳）。**只看 200 就记"已实访"是假完成**——要落地一次正文提取（长度 / 关键词 / RSC payload）再判。
- 反过来，**403 也可能只是"路径不对"而不是"内容不存在"**：本轮 `help.make.com` 直连 403 → 换代理后 200 且捞到真方法论。所以 403 的正确反应是**换路**，不是"判死"也不是"原样重试"。
- 判定顺序：**先辨类型 → 再选动作**。瞬时才重试；确定性换路；空壳换提取方式或判无内容。
- **第四种混淆：把"失败"当"合法的空"**（来源 trailofbits second-opinion v2 重写，2026-09-15 实拉）：*preserve Git errors instead of interpreting them as an empty diff*——命令非零退出 / 报错时，产物是"没拿到"，不是"拿到了空结果"。"git diff 为空"是有效结论（没改动），"git diff 执行失败"是证据缺失——两者动作完全不同（前者收工，后者修采集）。判据：**空结果要有"采集过程本身成功"的证据支撑；没有，就按失败走换路，不许按空走收工。**

### 重试前重播种干净骨架：不许在毒化产物上续跑（来源：william-london/ownframework-loop `reseed poisoned semantic retries`，2026-09-15 实拉）

语义校验失败（格式错 / schema mismatch / 结构毒化）后的重试，**不从失败产物上修补，也不把失败产物当起点**：

1. **先归档毒化产物**（可诊断、可追责），再重试——直接覆盖 = 丢证据
2. **用带固定字段的原始模板重播种（reseed）**：schema、run_id、身份、哈希等 fixed fields 由框架预填，重试方不得重写
3. **禁止模型编造替代身份值**：固定字段在进程启动时就畸形 → 停下上报**传输损坏**，不是"帮忙补一个看着合理的"
4. **顶层键集封闭（fail closed）**：出现模型自创的顶层键 = 整体判无效，不是忽略多余键
5. **信封校验 ≠ 就绪校验，分两步**：干净的空骨架**有意**留空语义行——"信封合法"（结构/身份对）与"就绪可交付"（内容填满）是两个独立判定；混成一步会把"合法的半成品"误判为"无效"，或把"没填的骨架"误判为"就绪"
- 与重放幂等配套：重放沿用原产物路径，重播种**必须换新产物**（旧产物已毒化归档）——先判是重放还是重试，再选沿用还是重播种。

### 重试的幂等纪律：重放是同一动作，不是新的一次

来源：GitHub `william-london/ownframework-loop` `docs/STATE_MACHINE.md` + `.agents/skills/of-loop-build`（2026-09-14 增量）：*"A replayed claim is the same pass and MUST NOT increment budget."*

**崩溃后重放的（replay）动作，是同一个动作，不得二次计数 / 二次扣预算 / 二次写证据。** 区分三种情况，别混为一谈：

| 情况 | 是不是同一次 | 处理 |
|---|---|---|
| **重放**（崩溃恢复、同一 pass 重新认领） | 是 | **沿用原路径与计数**，不新增一轮、不重复扣额度 |
| **重试**（动作确实失败、要再做一遍） | 否 | 计一次新的，纳入重试预算 |
| **新一轮**（收到新输入 / 上一轮有产出） | 否 | 正常推进 |

- **判定问一句：这次执行有没有产生新的"东西"？** 没有（只是把上次没跑完的补完）→ 是重放，不计数。
- 重放必须**沿用同一结果路径**，不另开目录——另开目录会让"哪份是最新的"变成悬案。
- 反模式：崩溃恢复后重新认领，预算计数 +1（额度被崩溃吃光）；重放时生成 `result_v2.json` 而不是写回原位。

## 二·五、失败处理是独立构件，不是散落的 try/catch

来源：n8n Docs《Handle errors gracefully》（2026-09-14 实访 Markdown 原文）。

**把失败处理外置成一条可复用的一等通道**（独立的错误处理流程，多个任务共用），而不是在每个步骤里各写一份兜底：

- 每份内联兜底都是"只在这里有效"的一次性代码，**改起来要改 N 处、验证起来一处都没验证过**；外置后只写一次、只测一次、处处生效。
- **同一个错误通道服务多个任务**——失败模式往往相似，重复实现没有收益。

**错误负载必须自带定位信息**，最小四项：
1. **哪个环节失败了**（节点 / 步骤 / 子任务名）
2. **可回访的执行标识**（执行 URL / 运行 ID）——没有它，事后无法还原现场
3. **这是否是一次重试**（`retryOf`）——重试掩盖原发错误是定位失败的头号原因
4. **原始错误与堆栈**，不做美化裁剪

**不同阶段的失败，能拿到的信息不一样**：起步阶段（触发器 / 初始化）失败时，执行上下文尚未建立，只有触发侧信息；后续步骤失败时才有完整执行上下文。**先判断失败发生在哪个阶段，再决定能从错误里问出什么**——用后段的信息结构去解读前段的失败，只会得到"字段缺失"的假象。

## 二·六、限流要预防，不要只靠重试；循环必须有显式终止条件

来源：n8n Docs《Loop》（2026-09-14 实访 Markdown 原文）。

**退避重试是补救，分批是预防——两者都要，但预防更便宜。** 明知道下游有速率限制还一次性全量灌进去，等于故意制造失败再慢慢重试。

- **主动分批**：大批任务切成批（可调批大小）逐批处理。批大小是**效率与被打回概率之间的旋钮**：批太大撞限流，批太小程序开销占比高。
- **按目标调参**：外部 API 按它的限流窗口定批大小；本地批量操作按内存/时间定。
- **别把"重试成功"当成"做对了"**：靠重试扛过去的流程，耗时和不确定性都被隐藏了，一遇更严的限流就整体雪崩。

**循环必须写清终止条件**：
- 两类循环分开看——**计数循环**（处理完所有项就停，天然有界）与**条件循环**（直到满足某条件才停）。
- **条件循环必须有显式终止判据**，且判据要能被验证（"跑 X 次还没满足就停手上报"）。没有上界的条件循环 = 潜在的无限执行。
- 与 §五「重试预算」（`wb-spec-driven`）同源：**任何"再来一次"的结构都要有次数/时长上界**。

## 二·七、缺信息要"结构化索取"，不要猜也不要直接失败

来源：MCP 官方《Understanding MCP clients》Elicitation（2026-09-14 实访）：服务端可以在执行中**反过来向用户请求特定信息**（例如订票前询问座位偏好、房型、联系电话）。

- **执行方不是只能被调用，它可以回问。** 但回问必须是**结构化的**（明确要哪个字段、什么格式、为什么需要），不是"你再说说"。
- **三种劣质替代**：① 猜一个默认值往下跑（把猜测固化进结果）② 直接报错退出（其实只差一个字段）③ 把所有可能的信息预先全部要一遍（把成本转嫁给每次调用）。
- 判据：**这一步缺的是"必需且只有对方知道"的信息吗？** 是 → 停下来问这一项；不是 → 用默认值并记录，或直接失败。
- 与 §一「覆盖零省略」不冲突：缺信息停下来问**一项**，不等于跳过目标；**问完必须继续把事情做完**。

### 补齐信息后重试原请求：必须回显状态令牌（requestState）
- 来源：同页 Elicitation 的 MRTR（Multi Round-Trip Requests）模式（2026-09-15 实访）：服务端因缺信息暂停时，响应里带 `InputRequiredResult`（含索取项 + **`requestState` 状态令牌**）；客户端收集完输入后**重试的是原请求**，且必须**附上收集到的回答并原样回显 `requestState`**——服务端靠它确认"这次重试续的是哪一次暂停"，而不是当作全新请求。
- 迁移到长链路任务：因缺信息/外部事件暂停的步骤，恢复时**把暂停时服务端/上游给出的状态带回**（任务 ID、断点令牌、上一轮的中间状态哈希），不要只把"补充的信息"带回去就当续上了。
- **不回显状态的两种事故**：① 上游把它当新请求从头再跑（重复扣款/重复发信/重复计数）；② 上下文串台（把 A 暂停的输入续到 B 的会话里）。
- 与「重放幂等」的关系：重放幂等管"同一动作重复执行只算一次"（读侧防护），本条管"恢复执行时主动证明续接正确"（写侧协议）——两者配套，缺一不可。

## 二·八、检查工具要支持"连一次、查一项、退出"

来源：MCP 官方《Inspector CLI client》（2026-09-15 实访）：CLI 模式每次运行**连上服务器 → 执行你点名的那一个方法 → 打印结果 → 退出**。

- **这个形态才能进 CI**。一个必须保持会话、需要交互才能得出结论的检查工具，永远只能被人手动跑。
- 落到本地的验证脚本：**接受一个明确的目标（"查哪一项"）作为入参，跑完输出结果并退出**，不要做成"进去之后选菜单"的交互程序。
- 判据：**这条检查能不能写成一行命令放进管道？** 不能 → 它不会被经常跑，等于没有。
- 与 `wb-artifact-verification`「验证要能脚本化」同源：那条讲**为什么需要**，本条讲**接口长什么样**（单次、单目标、可退出）。

## 三、失败 ≥2 次必根因诊断（原则三）
同一目标失败 **2 次及以上 → 立即停手，禁止第三次原样重试**：
1. **写假设**：为什么错？（缺依赖？子进程被杀？目标本身不可达？参数/顺序错？前一步污染？）
2. **最小探针验证假设**：查安装态 / 查进程残留 / 单独测可达性 / 退最小参数——用证据否掉或证实假设，不靠猜
3. **纠正后走新路径**：改的是根因（缺 Chromium 就先装，不是延长超时硬冲）；验证新路径通了再继续
4. **根因 = 环境结构性限制**（如沙箱禁 GUI、需 VPN、需人工装依赖）→ 留痕标注"非重试可解 + 解法归属（用户 / 手动步骤）"，不无限重试烧上下文
- 纠错后把教训写进相关技能（如浏览器技能补"前置检查"），**保证同类错不再犯**——这是原则三的终点，不是修完就完。

## 与相邻技能的分工（防抢触发）
| 场景 | 走谁 |
|---|---|
| 单个 bug / 报错的技术诊断循环（重现→最小化→假设→验证→修复→回归） | `wb-debug-loop` |
| **任务级执行纪律：点名目标全量覆盖 + 失败换路攻坚 + 失败≥2次根因诊断 + 重放幂等（重放不二次计数）** | **本技能** |

## 反模式

## 非交互驱动交互式 CLI 的显式契约（来源：github/gh-stack）

很多 CLI 靠 **stdout 是否为 TTY** 切换行为：管道下正常返回，PTY 下弹菜单/全屏 TUI **永久阻塞**。agent 宿主的 TTY 检测各不相同——所以**永远显式传 flag，不赌自动探测**。驱动一个交互式 CLI 前，先建立三列契约表：**必跑（带 flag 的安全形态）｜裸跑禁令（会阻塞/逐项要标题/只在 TTY 可用的命令）｜为什么**。模式速记：
- 取数用 `--json`（`--short` 等人类格式别解析）；提交用 `--auto`/`--yes` 类免确认 flag。
- **菜单专用命令（TUI-only）= 能力缺口**：没有非交互路径的命令不硬调、不挂超时重试，找重构路径绕行（如用"先 unstack 再 init"替代不可脚本化的 reorder）。
- 遇"换分支/换上下文"类操作可能撞**不可强制的守护**（报错即终态，不 force 重试）——按提示先做前置清理动作再重试原操作。
- 状态读取：JSON 走 stdout 供解析；状态性提示走 stderr——**靠退出码分支，不解析 stderr 文案**。

## 失败路径三分律：每个 catch 要么响，要么类型化，要么显式降级（2026-09-15 来源 principal-engineer handling-failures）
每个失败路径只许三选一，且三者**都要响**：① 记 WARN/ERROR 日志后重抛；② 记日志后返回**调用方必须处理**的类型化失败（结果类型/sealed error/编译器强迫下游确认的状态）；③ 记日志后进入**有名字、有文档、有可观测信号**的降级模式。禁止：裸 catch-continue；catch 后返回默认值（空列表/null/0/缓存副本）掩盖失败；`?? fallback` 把主路径失败藏起来（fallback 合法的唯一前提是"缺失本身在别处响亮地暴露"）。**记 DEBUG 级日志然后当作已处理 = 多走一步的吞没**——生产里没人看见就等于没记。

- **降级模式必须有界**：跳过-继续类降级要有**命名、可调的阈值常量**（降级到什么程度升格为中止），阈值定值是和 owner 的判断题，但守卫本身必须在。"无界降级 = 慢动作吞没"。
- **修/标既有吞没**：改到的代码里已有吞没 → 顺手修掉，或显式标记"欠账+它藏了什么"；留着不动 = 背书它。新引入的静默吞没是一级阻塞项。

## 幂等校验比对记录值，不比现算值（同源 ownframework-loop d5c724b5 回执驱动重播种）
检测"重复执行/重放"时，用**回执里记录的** digest/状态比对当前产物是否漂移，而不是每次现场重算——现算值永远和期望一致，是自证，检测不出真漂移。回执本身要校验格式（如 64 位十六进制），无效回执报错而不是当不存在。

## 自动续跑门控：五个条件全满足才拦，且拦截自带护栏（来源：othmanadi/planning-with-files v3 completion gate，2026-09-15 实拉）
"没做完就不许停"的自动续跑门（goal/loop 驱动的 stop 拦截）按这套护栏设计，缺一条就放行：
- **未完成是正常态不是错误**（issue #178 教训）：条件里只认"存在 in_progress 阶段"，不认"完成数<总数"这种把空计划也拦下来的口径；误拦用户比放过一次续跑更糟。
- **拦截理由只写状态描述，不写命令式指令**（PR #180 教训）：reason 字段里"还有 3 个阶段未完成"是描述，"继续完成第 2 阶段"会变成模型执行的续跑命令——措辞分級要显式。
- **连续拦截有上限**（默认 20 次，到顶放行）+ **停滞放行**：上次拦截后台账没有新进展 = 模型没在推进，允许停——死循环续跑比提前停止浪费大。
- **防跨轮污染**：拦截计数器每轮任务初始化时清零；宿主自己的 stop 标志（已在强制续跑中）为真时直接放行。
- 门控的判据是**落盘产物**（计划/台账文件的实际状态），不是对话转录——转录可以被幻觉，盘上的状态不会。

## 预览不是计划：`--dry-run` 的语义边界（来源：OpenClaw 官方 docs.openclaw.ai·concepts/memory-provenance，2026-09-15 实拉）
带预演（`--dry-run`）的执行入口要写清三件事，否则"我先看看"会悄悄变成"我以为已经存了"：

- **预览是按当前状态现算的，不是被保存下来的执行计划**——看预览与真执行之间状态可能已经变了，两者之间没有任何绑定关系。
- **"无二次确认"本身就是一条必须告知的事实**：某些工具看预览后直接执行、没有额外确认步骤，**使用者必须知道这一点**（写进调用前的提示，不靠猜）。反过来，若我设计了这样的入口，就要把"预览 → 执行"的绑定显式做出来。
- **失败后是"解错 + 重跑同一条命令"，不是手改状态**：先解决报出的存储 / 文件系统错误 → 重跑原命令 → **再跑一次预览核对残留**（失败可能留下部分清理，这是合法中间态；收尾判据见 `wb-debug-loop` §二·八）。**不可逆操作不提供"自动收尾"**——清干净的判据是"再预览时无残留"，不是"我觉得清完了"。

## 精确选择器：ID 大小写敏感，缩写不得匹配更长的 ID（同源）
批量操作的选择器（会话 ID / 记录键 / 路径清单）必须**精确匹配**：大小写敏感、**缩写不得命中更长的 ID**（前缀匹配 = 静默选中了别的对象，而选错对象往往到最后的清理 / 删除步骤才暴露）。
配套：执行前把解析出的**实际目标清单**打印出来核对——与 `wb-spec-driven` §七·14「先展示真实目标再可复查」同源，那条管跳转与提交，这条管批量操作的选择器。

## 保留 / 清理策略要写清"在哪几处触发"，不是一个"定期清理"（同源）
数据保留策略必须显式列出**触发点**（启动时 / 周期维护 / 每次写入顺带）并写出**上限**（时间上限如"查询排除 30 天前记录"、容量上限如"台账 10 万条，超限按时间淘汰"）。只写"会清理"而不写触发点与上限 = 实际不知道什么时候清、清多少——策略等于不存在。

## 从阻断中恢复：续跑是需授权的协议动作，且只发一次有界预算（来源：william-london/ownframework-loop `feat(supervisor): continue blocked program checkpoints safely` 312cf82b，2026-09-15 实拉）

"被阻断之后接着跑"不是"再跑一遍原命令"，而是一次**需要显式授权、需要证明续的是同一个东西**的协议动作：

- **必须声明"我续的是哪一个"**：续跑入口要求传**预期候选标识**（完整 SHA，如 40 位十六进制），并与状态文件里已绑定的候选**逐字比对**；不一致**直接拒**——**防在已经漂移的基线上续跑**（"上次停在哪"和"这次从哪起跑"必须是同一个对象）。
  - 与 `wb-spec-driven` §七·17「审批绑定具体内容」分工：那条管**批准**那一刻的绑定，本条管**续跑**那一刻的绑定。两次都要绑，不存在"批过一次就一直有效"。
- **前置形态校验防伪造**：续跑标识走**严格格式**校验（SHA 必须 `[0-9a-f]{40}`、continuation id 必须 32–64 位十六进制一类），**不接受"看起来像"的值**——宽松匹配等于允许伪造续跑身份。
- **一次有界修复资金，不是无限重试**：阻断状态的逃生口只**发放一次**修复预算；花完就真停。与 §二·六"任何'再来一次'都要有上界"同源，本条是"给一次配额"的具体形态。
- **事务提交后的重复调用 = 幂等观察，不重复消耗配额**：已有事务提交成功后再调同一次续跑 → 返回 `continued: false / idempotent: true`，**不扣第二次预算**。与「重放幂等」同源，落到"预算"这个可数对象上。
- **计数器镜像漂移必须对账**：同一事实记在两处（顶层镜像 `repair_round` + 累积计数器 `cumulative_repair_round_count`）时，**不等即报错，不许取其一继续**。判据：**同一事实的第二份记录是校验对象，不是备用来源。**
- **协议状态与跨系统回执责任分离**：状态层只拥有**协议状态**（本系统的状态迁移与计数），**跨系统回执与台账（ledger）迁移归上层**。两层混写 = 两边都不完整，且失败时无法定位是哪一层的账错了。
- **恢复前重校冻结契约**：续跑前重新校验**冻结契约**（冻结图 / 冻结配置一类）与"是否还有未完成单元"，无未完成单元即拒——**不因为"已经批了续跑"就跳过这道校验**。
- **迁移历史要显式**：每次续跑写一条带 from / to / 时间 / actor / 理由的迁移记录 + before / after 计数。失败恢复最怕"状态变了但没人知道为什么"。

## 覆盖账本：没有哪一次遍历是穷尽的（来源：cloudflare/security-audit-skill SKILL.md，2026-09-15 实拉）
批量目标（站点 / 文件 / 仓库 / 接口）必须**先建一份确定性覆盖计划**，每拿到一个结果就更新；账本只由一个角色写。
- **没有历史账本时，要在最终覆盖声明里明说"没有历史账本"**；**绝不暗示"跑过一遍 = 全覆盖"**。
- **范围外记 `out_of_scope`，绝不记为已覆盖**；局部运行必须自称局部覆盖。
- 历史结果的继承规则：
  - **只有源与条件都未变、且证据仍满足当前契约**的已确认记录才可继承；**仅凭一个 source ref / 版本号不足以证明路径未变**。
  - **源变了 → 必须重新验证**，不得因为"以前确认过"就继续当结论用。
  - **历史"已驳回"只压制那一条失败主张，不压制对该单元的覆盖**；证据变了就是新工作。
  - **历史"快速跑 / 局部跑"只贡献它的证据与缺口**，绝不隐含"其余没问题"。
- 与 §一覆盖零省略 配套：那条要求**一个都别少**，这条要求**少做了要说得出来**。

## 预算不够就停并声明，不许静默减少覆盖（同源）
- 分配顺序：**先预留复核与验证，再分配产出**；预留不足 → **一个都不启动**，记为未完成并写清原因（`预算不足以支撑最低限度的复核与验证` 一类具体原因）。
- 判据：**宁可交付一份写明"没跑完"的结果，也不要交付一份悄悄少跑了几项却自称完整的结果**——后者无法被信任，前者至少可以补。
- **降档只降广度与冗余，不降证据门槛**：可以缩小范围、减少复核轮次，**不许降低"这项算不算通过"的标准**，也不许跳过独立验证。
- 中途发现预算被吃掉 → **停止新增，按优先级把已启动的验证做完**，并列出未验证项；**绝不为了凑"跑完了"而把未验证项标成通过**。

## 写隔离：每个执行者一个独立根，且不用临时目录兜底（同源）
- 共享结果文件**只有一个写者**（协调方）；每个执行者拿到**自己唯一的根目录**，`scratch/`（可写、不留存）与 `artifacts/`（留存、由协调方提升）分开。
- **`artifacts/` 不暴露给执行环境**；执行者不得改共享文件、不得改他人目录。
- **不得把 `/tmp` 或宿主 home 目录当可写回退**——它们是共享面，且清理策略不在你手里。
- **执行者 ID 用小写受限字符集**（`^[a-z0-9][a-z0-9_-]{0,63}$`）且**排除 Windows 设备名**（`con` / `prn` / `aux` / `nul` / `com1`–`com9` / `lpt1`–`lpt9`）：小写防大小写折叠碰撞，设备名在 Windows 上会直接变成一个设备而不是目录。

## 依赖探测失败要分三型：不存在 / 不可用 / 运行时故障（来源：GitHub `simota/agent-skills` 的 `judge` 引擎预检段，2026-09-16 实拉）
判断"某个能力/工具在不在"时，**探测失败不等于能力不存在**，把两者混为一谈会造成两种方向相反的错。
- 三型：**① 不存在**（探测明确返回无）→ 走降级/替代路径，可以；**② 可用性探测失败**（探测本身没跑完）→ **不许按"不存在"处理**；**③ 运行时故障**（凭据过期/鉴权失败、网络不通、配额用尽）→ **是故障，不是能力缺失**，先修故障或上报，**绝不静默降级**。
- 判据：**降级是有代价的动作，只有"确定不存在"才配触发它**。凭据过期被当成"没装这个工具"，结果是悄悄用了个更弱的方案，问题被埋进产物里。
- 实操：**探测要在主上下文里做**（子 agent / 子进程的 PATH 与环境更窄，探测结论不可靠），且探测结果要写进执行记录，供后续对账。

## 自动修复的成熟度阶梯与护栏（来源：同源 `mend`，2026-09-16 实拉）
让 agent 自动修问题时，**自治程度不是开关，是有前置条件的阶梯**，跳级等于把不可逆风险交给运气。
- 四档，逐级放行：**① 只出洞察（只读）→ ② 出建议（人来执行）→ ③ 按批准执行 → ④ 带护栏自治**。上一档在真实场景里稳定，才允许进下一档；**任何一档出事就退回上一档**，不靠"下次小心"恢复。
- **成熟度阶梯配套三条硬护栏**：
  1. **同一失败模式的自动修复设次数上限（建议 3 次）并指数退避**——无上限重试会从"自愈"变成**重试风暴**，把瞬时故障放大成雪崩；
  2. **runbook 新鲜度门槛**：自动执行前检查最后复核时间（如 <90 天）与**基础设施是否漂移**（拓扑/版本/配置变了没）——**过期的剧本在新环境上执行，修的是旧问题、造的是新故障**；
  3. **分级验证 + 自动回滚**：健康检 → 冒烟 → SLO 检 → 恢复确认，四步任一失败即触发回滚，且**回滚路径本身要预先验证过**（没验证过的回滚等于没有回滚）。
- **超出目录的失败模式不许自动修**：不在已知模式库里的、或属最高危险级的，一律带上完整现场上下文转人工/转专项，**不许"试一把看看"**。

## 并行派发：一条响应里多个派发才真并行，且子 agent 不继承你的上下文（来源：GitHub `obra/superpowers`·`dispatching-parallel-agents`，2026-09-16 实拉）
把多个独立故障分给多个子 agent 是提速手段，但**派发方式错了会变成"看起来并行、实际串行"，或者更糟——几个 agent 互相踩**。
- **机制事实**：**同一条响应里发出多个派发 = 并行执行；一条响应只发一个 = 串行**。想并行就必须挤在同一轮里发完，否则等回来再发下一个，时间就是相加的。
- **能不能并行按三问判**：① 多个故障点？② **互相独立**（修好一个不会顺带修好另一个）？③ **无共享状态**（不会改同一批文件/争同一资源）？三问全过才并行，任一不过就串行或合并成一个 agent。
- **探索性调试不派发**：**还不知道坏在哪的时候不要并行派发**——连问题域都没划出来，派出去的只能是"你去看看"，结果是几个 agent 做同一件事或各猜各的。
- **子 agent 的上下文由你构造，不继承你的会话**：不要让它"接着我们的上下文继续"——**你精确打包它需要的东西**；这也顺带保住你自己的上下文留给协调用。子 agent 的 PATH/环境更窄，**探测类动作要在主上下文做**（与 §探测 同源）。
- **提示词四要素**：① **单一问题域**（"修 agent-tool-abort.test.ts"，不是"修完所有测试"）；② **自包含**（贴错误、贴用例名，别让它猜位置）；③ **明确"不要改什么"**（"只改测试，不动生产代码"——没约束它会重构一切）；④ **明确返回什么**（"返回根因与改了什么"，不是"修一下"）。
- **回收四步**：读各份摘要 → **查冲突**（有没有改到同一处）→ **跑全量**（各自通过的改动放在一起未必通过）→ **抽查**（**子 agent 会犯系统性错误**，同一类错误会同时出现在好几份结果里）。

## 子代理编排纪律：静默 + 角色成本分层（来源：Microsoft Copilot Studio multi-agent patterns 2026-09-09 + 掘金《Sub-agent 技术笔记》2026-08-10 + 博客园《多 Agent 协作实战》2026-07-09 实拉）
- **静默纪律：子代理不直接回用户，主代理统一汇总**——委派任务时显式带"禁止直接回复用户"指令（"收集完把结果交回给我，不要直接答复"）；所有子代理结果由主代理合并成**单一答案**，否则用户收到多份互相对不齐的碎片。
- **角色分型：读密集与写执行分开**——explorer（只读、不改动、扫代码/查文档/收集信息）vs worker（带写权限、落地改动）。**读密集子代理可配便宜模型**（Claude Code Explore 默认 Haiku 且只读）；写执行才配主力模型。**并行分工三角色：探索、实现、验证一起跑**（来源：Claude Code 自动化 Skill·Agent Swarm，用户提供文章 2026-09-17）——大改动用 explorer 探明现状、worker 落地实现、**独立的 verifier 验证产出**（跑测试/查 diff/对照验收），三者并行，不是做完再验；验证角色独立于实现者，避免"自己写自己验"的盲区。
- **心智单一**：每个子代理只做一件事做到极致（researcher 只调研、writer 只写作），别在一个子代理里塞多职责——塞多了就退回单 Agent。
- **契约明确**：子代理的输入/输出/边界写进委派（贴错误、限定改动范围、明确返回物），不靠"接着聊"。

## 多 Agent 架构先按决策树选型，再谈编排（来源：Anthropic 多 Agent 协作模式指南·博客园 2026-04-20 + 腾讯云《多 Agent 协作》2026-06-30 实拉）
不是"上了多 Agent 就一定好"——先回答三个问题选架构：
- **任务有没有可程序化验证的质量标准？** 有 → **生成器-验证器**（一个生成、一个校验，质量闸门自动化）
- **能不能清晰拆成短且有界的子任务？** 能 → **协调器-子智能体**（生产环境绝对主流：中央编排者拆解分配汇总，工作者各自执行）
- **子任务是长时间、多步骤的独立工作？** 是 → **智能体团队**（成员可主动反馈、按规则直接通信）；步骤序列固定可预测 → **顺序流水线**（上一个的输出是下一个的输入）
判据：**选型顺序由"任务性质"决定，不是由"想用几个 Agent"决定**；拆不开、验不了就退回单 Agent + 顺序步骤。

**Agent 间通信三模式按耦合度选**（来源：腾讯云《多 Agent 协作》2026-06-30 实拉）：
- **黑板（Blackboard）**：共享 workspace，各 Agent 读写同一块——任务耦合紧时用，**必须配 ownership + 版本追踪**（谁写的、哪一版，否则互相覆盖）
- **消息传递（Message Passing）**：Agent 间显式发消息——解耦好，事件驱动/接力场景用
- **共享内存（Shared Memory）**：同进程内多 Agent 的底层方案
判据：**串行流水线用黑板/共享内存，并行独立任务用消息传递**；通信不设防的多 Agent 比单 Agent 更容易互相污染产出。

## 清理被拒时永不强删；绿色只对跑过的那棵树成立（来源：GitHub `obra/superpowers`·`finishing-a-development-branch`，2026-09-16 实拉）
收尾阶段（合并 / 清理工作树 / 删分支 / 删中间产物）是**不可逆动作密度最高**的一段，这里的默认动作必须是"停下来问"。
- **清理被拒 = 里面有别处没有的东西**：`git worktree remove` 因 `contains modified or untracked files` 被拒时，**永不自行加 `--force`**。先 `git -C <path> status --porcelain -uall` 列全清单，再给三条路让用户选：**提交进分支 / 移到主仓库根 / 删除（不可恢复）**。判据：**拒绝理由是"还有内容"，强删等于替用户决定这些内容不值钱。**
- **绿色只对跑过的那棵树成立**：`A green run only proves the tree it ran on`。合并、rebase、切分支、重排提交之后，**必须在结果树上重跑一遍**；"这一轮早些时候测过""功能分支上是绿的"都不算。**验证结论绑定被测快照，不绑定"这个项目"。**
- **集成决策权在用户，不在执行者**：收尾只呈现选项（本地合并 / 推上去开 PR / 保持原样），**等选择**；"他们显然想合并"是原文明列的合理化借口。**丢弃分支只在用户明确要求时、且键入指定确认词后才执行**——"嗯，删了吧"不算确认（与全局规则「破坏性操作必须先列清单再确认」同源，这条补的是**确认词的精确性**）。
- **PR 已开不等于工作树是垃圾**：评审意见要回到同一个工作树里改，**PR 落地前不要清掉它**。判据：**清理的触发点是"工作已落地"，不是"我觉得用不上了"。**
- 与 §保留/清理策略 的分工：那条讲**何时触发清理**，这条讲**触发之后被拒绝 / 需要确认时怎么办**。

## 验证的触发条件是"候选物变了"，不是"到了新阶段"（来源：GitHub `warpdotdev/common-skills`·`create-pr` / `fix-errors`，09-15 提交 `82d2bd9`，2026-09-16 经 gh API 实拉）
上一节说"绿只对跑过的那棵树成立"（**变了就必须重跑**），本节是它的反面：**没变就不许重跑**。两条合起来才是完整的重跑判据。
- **开 PR / 提评审 / 交任务不是验证边界**：原文 `PR creation is not a validation boundary`。若前面的实现流程已跑完测试、lint、格式化，**且候选物没有变化**，就**不要重跑**——阶段切换本身不构成重跑理由。
- **什么算"候选物变了"**：合并了基底分支、或动了源码 / 测试 / manifest / 生成代码 / 配置。只有这些发生时才按顺序重跑：**测试 → lint/类型/构建 → 格式化（放在最后且只跑一次）**。
- **格式化之后不重跑测试**：格式化不改语义，**在它之后再跑一遍测试/ lint 是把成本花在没有信息的动作上**。同理，**改完测试若没有实质改变行为，不回头重跑受影响的测试**。
- **定点修复不升级为全量验证**：`Fix the reported failure with the narrowest useful command. Do not turn a targeted repair into repeated full-workspace validation.` 判据：**跑的范围要匹配"这次改动能影响到的范围"**，不是匹配"我有多不放心"。
- **罕见失败交给流水线，不在本地全量兜**：`CI owns uncommon failures outside targeted local coverage.` 本地只覆盖**目标范围内的检查**；为罕见失败在本地跑全量，是把长尾成本搬到每次迭代上。
- **顺序固定且有理由**：先测试再 lint 再格式化，是因为**后面两步可能改代码**，改完要回到受影响的测试；而格式化放在最后是因为它只改排版。
- 与 §绿色只对跑过的那棵树成立 合并成一条总判据：**重跑的充要条件是"被测对象自上次验证后发生了变化"，既不因阶段推进而补跑，也不因"刚测过"而跳过。**

## 派发的切分维度、团队规模与依赖图：并行度不等于人数（来源：GitHub `wshobson/agents` 的 `plugins/agent-teams/skills/team-composition-patterns` + `task-coordination-strategies`，2026-09-16 实拉）
与 §并行派发（三问判并行、提示词四要素、回收四步）配套：那条管"能不能并行、怎么派"，这条管**按什么切、派几个、依赖怎么摆**。
- **切分维度必须与"冲突面"一致**，四种切法各有适用场景：
  | 切法 | 适用 | 不适用于 |
  |---|---|---|
  | **按层**（前端 / 后端 / DB / 测试） | 全栈特性、垂直切片 | — |
  | **按组件**（认证 / 用户 / 通知） | 微服务、模块化 | — |
  | **按关注点**（安全 / 性能 / 架构） | **评审、审计** | 实现（会在同一处改） |
  | **按文件所有权**（`src/api/` 归某人） | **并行实现、避冲突** | 评审（会漏掉跨文件问题） |
  → 判据：**评审类按关注点切（同一份材料看不同维度），实现类按文件所有权切（不同材料各改各的）**。切错维度 = 要么互相踩、要么重复劳动。
- **团队规模按"维度覆盖"定，不按"任务数"定**：原文判据 "Start with the smallest team that covers all required dimensions"；反例是 **4 人做 6 个独立任务，不如 3 人各领 2 个**。→ 每多一人就多一份协调开销，**加人的收益必须超过这份开销**。
- **调试场景按"竞争假设"切，不按"同一件事再查一遍"切**：给每个调查者一条**互相竞争的根因假设**（3 条竞争假设），而不是都去查同一个方向——后者只会得到三份一样的结论。
- **依赖图宁宽勿深**：优先"宽而浅"而不是长链；**关键路径长度 = 最短完成时间**，所以先解关键路径上的阻塞；`blockedBy` 只加真正必需的（多加一条就把并行度降一格）；**成环即死锁**，派发前先查。
- **只读角色不接实现任务**：判据是"这个角色有没有完成任务所需的工具"——读-only 的子 agent 派去改文件，失败是配置错误不是执行不力（与 §子 agent 的 PATH/环境更窄 同源）。

## 并行实现的真实冲突源与解阻塞（相邻扩展：同源 `wshobson/agents`·`parallel-feature-development` + `team-communication-protocols`，2026-09-16 实拉）
> 查重留痕（sa §查重双键检索）：`wshobson/agents` 已在上一段消费（`team-composition-patterns` / `task-coordination-strategies`）。本段只取上一段**没有的判据**——冲突来自哪里、怎么解阻塞，不重写切分维度。
- **一文件一主（cardinal rule）**：任何文件不得同时归两个执行者。必须共享时二选一：① 指定唯一 owner，其他人**提请求、由 owner 顺序应用**；② **抽接口契约文件**（由 lead 所有、实现者只读 import），双方对它编程但都不改它。
- **barrel / index 文件是隐形冲突源**：`index.ts`、`__init__.py` 这类"自动导入一切"的文件**必然被双方改**——要么指定唯一 owner，要么由 lead 最后统一合并。所有权表没覆盖它 = 规则形同虚设。
- **契约变更必须广播**：改了接口签名不通知，别人写的测试会挂，而且挂得莫名其妙。→ **广播只留给"共享资源变了"这类人人都受影响的事**；日常进度用点对点消息——**广播成本是 O(人数)**，拿它做日常同步等于按人头烧轮次。
- **互等死锁用桩解**：两方各等对方先完成 → 由 lead 给其中一方**一份 stub / 部分结果**，让它先跑起来，集成时再换真实现（原文：finished implementer writes a stub or mock of the downstream dependency）。**先完成的一方有义务解下游的阻塞**，而不是"我做完就等着"。
- **子 agent 不回消息，先分状态再处置**：`idle`（做完了在等派活/等关闭）与 `active`（执行中，当前操作结束才处理消息）**处置完全不同**——前者该派新活或关闭，后者只需等。不判状态就重发，只会叠消息。
- **切分错了就停**：停新工作 → lead 重分 → 广播变更。**已写代码的沉没成本可接受，带着错的切分继续更糟**（与 `wb-spec-driven` §四 中途重新对齐 同源，这里给的是并行场景的具体三步）。

## 并行是稀缺资源设计问题，协调者只能在 lane 契约之后引入（来源：OpenClaw 官方 docs.openclaw.ai·concepts/parallel-specialist-lanes，2026-09-16 实拉）
加 agent 不等于提吞吐——只有在能减少**真实瓶颈**竞争时才加，且协调层必须最后才上。
- **先枚举真实瓶颈，再决定加不加 lane**：瓶颈通常是这几类——① session 锁（同一 session 同时只许一个 run 改）；② 全局模型容量（所有可见 run 共享 provider 限额）；③ 工具容量（shell/浏览器/网络/仓库可能比模型本身慢）；④ 上下文预算（长 transcript 让每轮更慢更散）；⑤ 归属歧义（重复 agent 干同一件活 = 纯浪费）。**某个 lane 只有在这五类里至少命中一类竞争、且它能缓解那类时，才值得存在**；否则只是把串行阻塞换成协调开销。
- **协调者只能在 lane 契约之后引入**：每个 lane 先有书面契约（Owns 归属 / Does-not-own 非目标 / Chat-budget 快答留聊天长任务后台 / Handoff 交接摘要格式 / Tool-posture 最小工具面），才加 coordinator 去跨 lane 追踪 owner、去重、路由交接。**没有 lane 契约就加协调者 = 协调混乱**（原文：A coordinator without lane contracts just coordinates chaos）。
- 与 §并行派发三问 / §切分维度 的分工：那些管"这次能不能并行、怎么切"，这条管"**长期多 lane 架构的引入顺序与存在判据**"——前者是单轮决策，后者是结构性纪律；两者都过了，多 agent 才真提吞吐而不是制造新瓶颈。

## 自治程序契约与 Execute-Verify-Report（来源：OpenClaw `automation/standing-orders`，2026-09-16 实拉）
把"周期性 / 常驻的自主权"交给 agent 时，用**程序契约**框死边界，而不是一句"你看着办"。
- **四段式程序契约**：每个自治程序写明 ① **Scope**（授权做什么）② **Triggers**（何时跑：定时 / 事件 / 条件）③ **Approval gates**（哪些动作必须人审）④ **Escalation**（何时停下求助）。四段缺一 = 边界不清 = 迟早越权或摆烂。
- **Execute-Verify-Report**："我来做"不是执行，"Done"没有验证不算完成——**先真做、再证结果（文件存在 / 消息送达 / 数据解析）、最后汇报做了什么验证了什么**；执行失败重试一次换思路，仍失败就报故障诊断，**绝不静默失败**；**不无限重试，最多 3 次就升级**。→ 这直接防住 agent 最常见的失败模式：口头确认但不落地。
- **权限从窄起步，随信任扩展**：第一天就给"你看着办"的宽泛授权 = 把不可逆风险交给运气；先窄后宽。
- **"不要做什么"和"能做什么"同样重要**：显式写 What-NOT-to-do 段，边界靠否定约束兜底。
- **没有触发器的 standing order 只是建议**：授权若不被 automation / cron 真正驱动，就退化成"你该记得做"——而 agent 不会记得口头指令。→ 自治权必须绑定一个真实触发器，否则不叫授权。
- 与 §自治程度阶梯 的分工：那条管"**自动修复的成熟度分级**"（洞察→建议→按批准执行→带护栏自治），这条管"**常驻自主程序的契约结构**"——前者是单点修复的放权梯度，后者是长期授权的边界框架，两者叠加才既敢放权又不出格。

## 周期循环的三条编排护栏：限在制品、先能手工跑、别造不存在的分离（来源：GitHub `humanlayer/skills`·`plugins/design-control-loop`，skills.sh /hot 榜单 2026-09-16 实拉）
把周期性自主任务当**控制回路**设计：被驱动的属性与**目标值（set point）** → **测量（sensor）** → **选下一小步（controller）** → **执行（actuator）**，外加识别**扰动（disturbance）**（同事提交、依赖升级、生成代码、flaky 测试）。编排它时有三条硬护栏：

- **护栏一 · 在制品上限（flow control）**：**默认一个循环同时只允许一个未合并产物**——调度触发时若本循环已有未合并产物，本次 **no-op**；**人工显式派发可绕过**上限。
  - 判据：**产出速度快于消费（评审）速度时，先限流，不要继续堆**。没有这条，每日循环会堆出一串互相冲突的 PR，而没人来得及看（原文：a daily loop can stack up duplicate or conflicting PRs while no one is reviewing）。
  - 与 §自动续跑门控 的分工（**两条相反，别混**）：那条管"**不许停**"（goal/loop 驱动时，没做完要拦住停止），这条管"**不许再开新的**"（产物已积压时，新触发要让位）。一个是保推进，一个是保可评审，缺哪条都会走极端。
- **护栏二 · 每个部件必须先能手工单跑，才允许接进编排**：接进定时/CI 之前，先分别手工跑一遍并读到输出——① 测量：跑一次，确认输出稳定、可重复、能当控制器的输入；② 选步：拿真实测量输出跑一次，确认选中的下一小步合理；③ 执行：在选中的目标上跑一次，确认改得对、验证过得去。
  - 判据：**编排层只能编排"用户已经能手工跑通"的东西**（原文：The workflow should only orchestrate pieces the user can already run by hand）。任一步不能脱离编排独立运行 = 还没到接编排的时候——否则一出问题只能整条重跑，无法定位。
- **护栏三 · 部件可以融合，不造不存在的分离**：测量与选步常常就是同一个工具（既报问题又按影响排序）；选步与执行也常常是同一个 agent（既挑目标又改）。**融合了就把它折叠成一个步骤**，不要为了凑"标准三段式"硬拆（原文：do not invent separation the design does not have）。
  - 判据：**拆分的唯一理由是"两部分的失败模式或调参节奏不同"**，不是"架构图上应该有三个框"。

**人工在环的两条通道**（循环不打方向就会漂）：① **长期反馈文件**——版本化的 markdown，每轮**确定性装载**进执行器上下文，只写会改变未来选择的内容（永久排除范围、已知误报区、评审偏好），**不写单次日志与一次性指令**；② **在产物上直接反馈**（如 PR 评论触发改写），反馈要**同时更新反馈文件**，否则只改了这一个产物、下一轮照旧。
- 与 §自治程序契约 的分工：那条给"**授权边界**"（Scope/Triggers/Gates/Escalation 四段），这条给"**循环结构与节流**"（目标值、测量、限流、反馈通道）——前者回答"能做什么"，后者回答"每一轮怎么走一小步且不失控"。

## 同一条信息的每一份镜像都要同步：漏改是静默的，且专挑"只被部分消费者读到的那份"（来源：GitHub `FrancyJGLisboa/agent-skills-platform`·`LEARNINGS.md`，gh search repos 2026-09-16 实拉）
新增一个产物、校验器或流程步骤时，**同一条信息往往已经以镜像形式存在于多处**（正文 + 清单 + 报告模板 + 索引）。原文记录：加新校验器时，**显眼的触点每次都改了，漏的永远是同一类"次要镜像"——而且连续两次犯同一个盲点。**

- **机制**：不同消费者读不同的文件——**有的只读清单/索引，不读正文**。对这类消费者来说，**那份镜像就是它的全部信息来源**，漏改 = 对它们完全不可见，**且不报任何错**（原文：silently incomplete）。
- 判据：**凡"会被某个消费者独立读取"的副本，都要按主副本的完整度来维护**；"它是次要的/派生的"不是少维护的理由。
- **收尾动作（可机械执行）**：宣布这类改动完成前，先 **grep 出这条信息的全部出现位置**并逐个核对，而不是只改记得住的那几处。**容易漏的位置建议固化成一条 grep 命令**（原文就留了一条现成的 grep 作为 checklist 项）。
- **别只靠"上次记得"**：同一个盲点会重复犯——原文两次都是 review 抓到的。**把它写成清单项，不写进记忆。**
- 与 §计数器镜像漂移必须对账 的分工：那条管**同一事实的两份数值必须相等、不等即报错**（对账/校验）；本条管**同一信息在多处存在副本时，新增内容要把每一份都补上**（同步/覆盖）。前者是运行时一致性，后者是变更时完整性。

## 失败恢复是有序阶梯：同体恢复 → 换凭据 → 换实现；超时/熔断是终态不是换路信号（来源：OpenClaw 官方 docs.openclaw.ai·`concepts/model-failover`，2026-09-17 实拉）
原文：故障分两级处理 `1. Auth-profile rotation within the current provider. 2. Model fallback to the next model`，且在此之前先做 `bounded same-model recovery ... It continues the existing transcript, preserving partial output and completed work`。

- **阶梯（顺序不许跳）**：① **同体有界恢复**（同一模型 / 同一命令 / 同一路径，退避重试，**保留已完成的工作与部分输出**）→ ② **换凭据 / 换身份**（同一 provider 内轮换 profile）→ ③ **换实现**（换模型 / 换工具 / 换路径）。**一失败就直接跳到第 ③ 层 = 把已经做完的部分白扔掉**，还顺手掩盖了真实故障类型。
- **恢复后先查断点，再决定重做**：`The agent is instructed to inspect interrupted actions before deciding whether to repeat them.` → 恢复 ≠ 从头重跑：先确认**中断点已经做到哪、哪些副作用已经发生**，再决定是补做还是重做。
- **超时 / 成本熔断是终态，不是换路信号**：原文把 `agent_run_terminal_timeout`、`idle_timeout_circuit_breaker` 记为 `model_fallback_chain_stopped` 的原因，并写明 `These are terminal stops, not provider failures or requests to try another model`。
  - 与 §换路前先辨错误类型 的分工：那条的三类是**瞬时 / 确定性 / 空壳**，本条补**第四类：终态**——整体超时、成本熔断、预算耗尽这一类**既不重试也不换路，直接失败上报**；换路只会把同一个超时在另一个候选上再付一遍。
- **失败恢复可以换路径，不可以偷偷降标准**：原文 thinking-level recovery `applies only when the provider identifies a reasoning or thinking parameter`；没被指认的（模型/账号限制、无关的 unsupported option）**保持原失败分类**，`does not retry them with thinking disabled`。→ 判据：**"把 thinking / 校验 / 精度关掉再试一次"只有在错误被明确归因到该参数时才允许**，否则就是靠降低能力让失败消失。
- **自动降级不得覆盖显式的人为决策，也不得持久化**：原文 `Explicit user session selections are strict`（不参与自动 fallback），且 fallback `does not persist the fallback as the next turn's model selection`。→ 两条判据：① **用户显式指定的东西（模型 / 工具 / 路径），自动降级不许接管**；② **降级只作用于本次**，不许写回配置或默认项让下一次静默沿用。
- **失败摘要要能指导"下次什么时候再试"**：原文 exhaustion summary 带 `structured per-attempt details and the soonest cooldown expiry when one is known`。→ 报失败时给齐：**每次尝试的明细 + 最早可重试时间**；缺这两样，重试只能靠猜时机。
- 反模式：一出错就换模型（丢已完成工作）；超时后换一条路再撞一次超时；为了跑通悄悄关掉校验；把本次的降级写进配置当默认。
- **提升层**：工作流 / 执行纪律。

## 改向 ≠ 中止：编排层要分清"已开始的工作"和"已请求的工作"（来源：OpenClaw 官方 docs.openclaw.ai·`concepts/queue-steering`，2026-09-17 实拉）
原文：`Stopping already-running work is a different intent from redirecting future work.`，并把运行时行为拆成两类对象——`OpenClaw distinguishes started work from requested work`：已启动的调用跑完，未启动的调用才被跳过。

- **两种意图必须分开表达**：① **改向（steer）**＝别改已经跑起来的，只改接下来做什么；② **中止（interrupt）**＝最新消息要顶掉当前这轮。**用一个动作同时承担两者 = 语义不明**，下游既不知道要不要收尾，也不知道该不该重跑。判据：**停止正在跑的**和**改变接下来要做的**，必须能分别下达。
- **改向只在边界生效，不打断已跨过检查点的调用**：顺序模式下每个调用启动前检查一次；并行批次有**一个原子启动检查点**——检查点之前的改向压住整批，之后的改向一个也召回不了。→ 判据：**"我发了新指令"不等于"正在跑的会停下来"**，改向生效点必须写清楚是下一次调用前、还是下一轮模型前。
- **被跳过的调用必须留下成对的、结构化的"未执行"结果**：原文 `Every skipped call receives paired tool start/end events and a synthetic result`，且 transcript 保持**追加且结构成对**。→ 判据：**取消不是消失**——每个被取消的单元都要有一条"它没跑、为什么没跑"的记录，而且位置和它原本该出的结果一致；否则模型会把"没有结果"读成"结果为空"。
- **可见的发送/确认 ≠ 已被消费**：原文 `A visible message or send acknowledgment does not mean the active runtime has consumed it.` → 修正 §Execute-Verify-Report 的"消息送达"判据：**送达确认不是消费证据**。要证明执行过，得拿到消费侧的信号（已处理 / 已落库 / 已产生副作用），只有"发出去了/界面显示了"只到送达层。
- **投递有生命周期窗口**：原文 `Append messages before the handler's promise settles; detached work that pushes later can miss the producer's delivery step.` → **脱离窗口的异步补写会被静默丢弃**：要回传的东西必须在承诺结算前落定，事后补推不算数。
- 与 §周期循环三条编排护栏 的分工：那条管**循环本身怎么设计**（在制品上限 / 先单跑 / 不造不存在的分离）；本条管**循环已经在跑时怎么干预**（改向 vs 中止、跳过怎么留痕、什么叫真的被消费）。
- 反模式：一句"停一下"既要它收尾又要它改方向；以为发了新指令旧任务就会停；把被取消的任务直接从记录里删掉；拿"已发送/已显示"当执行完成的证据。
- **提升层**：工作流（编排 / 周期任务干预）。

## 后台维护工作与前台容量分开预算；调度器不许占它等待的槽（来源：OpenClaw 官方 docs.openclaw.ai·`concepts/queue`，2026-09-17 实拉）
原文：`Skill Workshop reviews and plugin background completions ... share a separate budget of three concurrent runs ... keeps maintenance work out of foreground reply capacity while bounding its total concurrency`；`Schedulers that await background work do not occupy this budget themselves. Only the dispatched work holds a slot ... so a scheduler cannot block the child it is waiting for`；`This preserves input, not execution permissions ... requires an explicit resend. The in-memory queue is not replayed`。

- **维护类工作走独立池，且独立池也要有上限**：评审 / 整理 / 索引重建 / 记忆固化这类"不做也不会立刻坏"的工作，**不许和前台交互抢同一份并发**，否则一次后台整理就能把响应拖垮；但独立不等于无限——原文同样给三并发的硬上限。→ 判据：**分离的是资源池，不是取消配额**。
- **等待子任务的调度器，不许占用它等待的那类资源**：只有被派发出去的工作持槽，调度器自己不持。→ 判据：**"我在等它"不能变成"我占着它要用的东西"**；编排层占有执行槽 = 自锁。
- **队列满时丢谁，必须是显式配置**：原文 `cap: 20` + `drop: summarize|old|new`（默认保留压缩后的摘要再丢）。→ 判据：**"满了怎么办"要写在明面上**，三种丢弃语义差别很大：留摘要 / 直接丢最旧 / 拒最新；**静默丢弃 = 把输入当成已处理**。
- **"已入队 / 已持久化"≠"会执行"**：输入先落库再确认，但网关在它进入 transcript 前停掉 → 重启后它是"被中断的输入"，**需要显式重发，内存队列不重放**。→ 判据：**记录与执行是两个状态**，恢复路径不许假设队列会替你补跑。
- **可能已生效但确认丢失 → 报不确定，不重放**：原文 `If the answer may have committed but confirmation is lost, OpenClaw reports that uncertainty and does not resend it`，且 `A later delivery or source-cleanup failure does not make the answer replayable`。→ 判据：提交态分**三档**（确定未提交 / 确定已提交 / 不确定），**不确定一律不重放**，只报不确定并让人查；重放的代价是重复副作用，比"没做成"更贵。

## 无人值守自动化分型 + 工作流状态三文件（来源：51CTO《想让 Agent 在你睡觉时继续干活》2026-07-02 + 阿里云《零重型框架》2026-05-15 实拉）
- **无人值守任务先过安全分型**：只生成草稿不自动发布（扫描/日报周报→可无人值守，但产物止步草稿）；外发类只准备草稿、发送前人工确认（邮件/客服回复）；生产变更/删库/付款/产品战略→**不适合自动执行**，人工审批+审计；代码重构谨慎适合（范围小、测试足、能回滚）。
- **工作流状态三文件**（让任何一步断点续跑/失败回退/去重执行）：`run_state.json`（当前 DAG 进度：当前节点、各任务状态、已用 token、执行时间）+ `last_success.json`（最近一次成功执行的完整状态快照，失败时回退到它）+ `dedupe_index.json`（基于幂等键的去重索引，防同一步重复执行）。
- **规划范式按任务形态选，不默认一种**（来源：Best AI Web《Planning Agents in Practice》2026-05-07 实拉）：**Plan-and-Execute**（步骤可预先枚举、成本比延迟重要、要可审计）——规划一次、执行逐步、过程可预测；**ReAct**（步骤无法预先枚举、需要每步对观测反应）——单发式迭代工具调用；**ReWOO**（token 预算紧、步骤可知但观测贵）——计划里不塞观测结果。判据：**能枚举步骤且要可审计 → P&E；动态场景 → ReAct；省 token 场景 → ReWOO**；步骤中途发现大前提变了 = P&E 的已知弱点，此时切观察触发重规划而不是咬着执行完。
- **重规划触发四策略，按成本/适配度选**（来源：CSDN《如何提升 AI Agent 规划能力》2026-05-04 实拉）：**失败触发**（单步报错/前置不满足/结果不符预期才局部重规划，日常按原计划走，资源消耗最低）；**观察触发**（每完成一步观测结果实时微调后续计划，适配最强，适合动态场景）；**定期触发**（固定节奏检查）；**全量重规划**（每步都重算，成本最高）。默认失败触发，动态多变场景升观察触发。
  - 与 §重放幂等 的分工：那条管**重放怎么计数**（同一动作不二次计数，读侧防护）；本条管**什么情况下根本不许重放**（不确定态，写侧禁令）。
- 反模式：后台整理和前台回复共用一个并发池；调度器占满执行槽导致它派发的任务永远排队；队列满了静默丢输入并在报告里写"已收到"；恢复后以为入过队的东西会自己跑；"可能已提交"时重发一遍求稳。
- **提升层**：工作流（编排 / 周期任务容量）。

## 批量扫描只能用来"挑谁"，不能用来"判定它是什么"——取证深度不许静默降级（来源：mattpocock/skills·`docs/engineering/triage.md`，2026-09-17 实拉，★263k）
原文：`The "show what needs attention" pass is a cheap listing meant for *selection* ... Run it across twenty issues at once and an agent can quietly fall back to that cheap listing as its evidence base, which returns issue bodies but not comments. A user hit exactly this: three issues already carried a comment saying "already fixed, recommend closing", and all three got fresh agent briefs instead. If you want a bulk pass, say explicitly that comments must be read per issue.`

- **同一份数据有两种用途，各有一种取证深度**：**选择**（这批里先动哪个）用浅层扫描就够了；**判定**（它属于哪一类、要不要做）必须取到完整上下文（主体 + 评论/历史/关联记录）。→ 判据：**浅层扫描合法，但只能产出候选名单；一旦拿它当判定的证据，就是降级**。
- **批量会诱发静默降级**：一次要处理 N 个目标时，agent 倾向于把"廉价的列表"当成证据基础继续往下走，而且不报错、不说一声。原文的实际后果是——三个早已有人写下"已修复、建议关闭"结论的条目，全部被重新做了一遍 brief。→ 判据：**重复劳动 + 覆盖已有结论，是取证降级的典型症状**，不是"多做了点无用功"。
- **批量任务的指令里必须显式写取证深度**：原文给的原话是 `say explicitly that comments must be read per issue`。→ 判据：**"全部处理"不等于"每一项读全"**，后者要单独说；说"全部"时默认会被理解成"全部各扫一眼"。
- **自检问句**：我刚才对这 N 项下的结论，是我**看过完整上下文**得出的，还是从**同一份浅列表**里顺手推出来的？如果是后者，结论不成立。
  - 与 §依赖探测失败三型 的分工：那条管**能力探测的结果不能当"不存在"**（探测域）；本条管**已取到的数据不能越权当判定证据**（取证深度域）。
  - 与 §改向≠中止 的分工：那条管**意图语义**（停 vs 转向）；本条管**证据充分性**。
- 反模式：一句"把这一批都处理了"就开跑；用列表页的摘要字段判定条目性质；批量跑完发现对同一批条目重复产出了早已有结论的产物；发现重复后怪"数据变了"而不查取证深度。
- **提升层**：工作流（批量任务 / 零省略执行）。


## 派活给子 agent 要传"目的"，不只传查询——返回后迭代取回，不要一次收货（来源：ECC《The Longform Guide to Everything Claude Code》，2026-09-17 实拉，★260k）
原文：`Sub-agents exist to save context by returning summaries instead of dumping everything. But the orchestrator has semantic context the sub-agent lacks. The sub-agent only knows the literal query, not the PURPOSE behind the request.` / `Iterative Retrieval Pattern: 1. Orchestrator evaluates every sub-agent return 2. Ask follow-up questions before accepting it 3. Sub-agent goes back to source, gets answers, returns 4. Loop until sufficient (max 3 cycles)` / `Key: Pass objective context, not just the query.`

- **省上下文的机制本身制造了信息缺口**：子 agent 靠"只回摘要"省窗口，代价是它只拿到字面查询，拿不到编排者脑里的目的。→ 判据：**摘要省的是 token，不是语义**；把被省掉的理解成本留在编排者这一侧，等于没省。
- **派活必须带"为什么派这一趟"**：除了查什么，还要写清这条结果**要支撑哪个决定、命中什么判据、不合用时该往哪查**。→ 判据：子 agent 的指令里只有"查什么"没有"查来干什么"，它的取舍标准就和你的不一样——它会按自己的理解挑重点。
- **返回先评估再接受，硬上限 3 轮**：原文给了 `max 3 cycles`。→ 判据：**第一次返回是候选不是结论**，先追问再决定收货；不给上限会退化成无限追问，而**超过 3 轮说明派活时目的没传清楚**——该回去改指令，不是继续追问。
- **一个 agent 一进一出，中间产物落文件，阶段间清上下文**（原文 sequential phases 规则）：阶段之间用文件传递（`research-summary.md` → `plan.md` → `review-comments.md`），**不靠对话记忆接力**。→ 判据：**文件是阶段间唯一合法接口**；用上下文传，上一阶段的噪声会一起带进下一阶段的判断。
- 与 §等待子任务的调度器不许占用它等待的那类资源 的分工：那条管**资源占用**（别自锁）；本条管**语义传递**（别让它瞎猜）。
- 反模式：把用户原话原样转给子 agent；子 agent 返回什么收什么；追问到第 6 轮还觉得"再问一次就清楚了"；阶段之间靠"上一轮我说过"传递结论。
- **提升层**：工作流（子 agent 编排 / 委派）。

## 自动化动作的挂载点按"频率 × 延迟预算"选——高频事件点会把成本摊到每一次交互（来源：ECC《The Longform Guide》，2026-09-17 实拉）
原文：`The key design decision is using a Stop hook instead of UserPromptSubmit. UserPromptSubmit runs on every single message - adds latency to every prompt. Stop runs once at session end - lightweight, doesn't slow you down during the session.`

- **同一个动作挂在哪个事件上，决定它付成本的次数**：每消息触发 = 每一次交互都付一次（原文：给每个提示加延迟）；会话边界触发（Stop / PreCompact / SessionStart）= 一次会话只付一次。→ 判据：挂载点的选择不是"能不能做"，而是**这件事该摊到每次交互，还是该在边界一次付清**。
- **抽取 / 固化 / 落盘类动作一律挂边界**：把会话里的模式抽成技能、把状态写进记忆、压缩前保存现场——都是事后整理，不需要实时。→ 判据：**动作的价值在结果、不在及时性** → 挂低频点；只有"不做就立刻出错"的拦截类动作才配挂高频点。
- 自检问句：这个自动化**晚 10 分钟做**有区别吗？没区别就挂边界点；有区别才挂每消息点，并接受它给每次交互带来的固定成本。
- 反模式：为了"实时"把记忆固化挂在每消息钩子上，然后抱怨每轮都变慢；反过来把拦截类校验挂到会话结束点（那时副作用已经发生）。
- **提升层**：工作流（自动化挂载点 / 钩子设计）。

## 改名 / 改格式时，第二副本体藏在字符串里：它不报错，只是持续教错（来源：GitHub `edonadei/caliper`·`docs/MIGRATING-to-skills.md`，2026-09-17 实拉）
原文：`Step 1 only rewrites a YAML key. If your spec is an eval of a skill that writes caliper specs, the dead format is also sitting inside your strings, where no schema migration can see it`；`a line like "the spec must have a top-level skill block with skill.path" now instructs the agent to produce a spec caliper rejects. The task fails, and worse, it teaches the wrong format.`

- **结构变更有两层副本：字段名层（解析器看得到）与自然语言层（解析器看不到）**。改动提示词、验收标准、示例、断言文本、heredoc 里嵌的样例，都属于第二层。→ 判据：**schema 校验只会告诉你字段名错了，不会告诉你示例还在教旧格式**；这类副本的失效是静默的。
- **它的失效模式是"教错"，比"读不到"更糟**：一份残留旧格式的示例，会持续产出按旧格式写的新产物——**它不是一处孤立故障，是一个污染源**。→ 判据：**修一处漏改只救已经生成的那一份；漏在示例里，后面每一份都会错**。
- **验收标准里的过期判据会让评委判错东西**：`expect:` 写的是旧口径，评委就照旧口径打分，产物按新口径做对了反而判不过。→ 判据：**改了做法没改验收标准 = 用旧尺子量新东西**，报错位置会在产物上，根因却在标准里。
- **grep 范围必须显式包含正文字符串，不能只 grep 标识符**：`grep -rn '旧字段名\|旧写法' 目标文件` 要覆盖 prompt / expect / assert / setup / 文档示例。→ 判据：**find-replace 按"键"匹配，正文按"意思"写着同一个东西**，两者不匹配就会漏。
- 与 §同一信息的每一份镜像都要同步 的分工：那条管**文件级镜像**（同一信息抄在正文 + 清单 + 索引里，有的消费者只读其中一份）；本条管**字符串内嵌副本**（同一格式写在提示词 / 示例 / 断言文本里，没有任何消费者会把它当"需要同步的镜像"）。前者漏改的表现是"那一侧看不到"，后者是"那一侧照着错的教下去"。
- 反模式：只跑 schema 校验就说迁移完成；改了字段名没改示例；验收标准还写着旧口径就去查产物为什么不过。
- **提升层**：工作流（变更完整性 / 迁移纪律）。

## 工具结果断言层：可疑结果打标交还模型，不硬拦截（来源：博客园《AI Agent 工具调用可靠性的工程实践》2026-06-11 实拉）
- **关键工具加结果合理性断言**：用业务规则检查返回值——"查询历史已有数据的月份却返回空，大概率是参数错了而非真没数据"、"金额字段不应出现负值"。→ 判据：**参数校验管"调用前"，结果断言管"调用后"**，两层都要，缺一层就漏一半。
- **可疑结果打 `_suspicious` 标记连同提示语交还模型，而不是硬拦截**：断言规则不可能穷尽业务情况，硬拦会误杀正常边界；标记 + 提示语让模型自己判断，保留决策权。→ 判据：**断言层是哨兵不是法官**，它负责"提示这不对劲"，不负责"替模型下结论"。
- **工具失败返回结构化错误对象，不抛异常**（来源：CSDN《OpenAI Function Calling 完全指南》2026-09-05 + AI/TLDR Tool Calling 2026-06-12 实拉）：失败时返回 `{ok:false, error:{code, message, retryable}}` 给模型——**模型据此决定重试/换 fallback/告知用户**，而不是崩溃循环。错误对象三字段定死：`code`（机器可判）、`message`（模型可读）、`retryable`（该不该重试）。
- **工具循环必须查终止条件，防无限循环**（来源：The Neural Base Function Calling Cheat Sheet 2026-04-12 实拉）：**每次工具调用后检查 stop_reason**——只有其为 tool_calls/tool_use 才继续循环，否则立即停止返回结果；不看 stop_reason 会让工具循环无限跑（服务端执行了但 LLM 永远在等下一轮结果）。
- **重试分两类管：transport 与 tool 分开**（来源：Elser AI《GPT-6 Astra Function Calling Guide》2026-09-07 实拉）：transport 重试管 API 超时/429/瞬时 5xx（指数退避+抖动）；tool 重试管自己依赖的失败。**写操作必须幂等**：连接断后先查"这次操作是否已生效"再决定重调（create_refund 断了 → 先查退款存在否，不盲目再调一次），配幂等键。

## AI 生成代码收 diff 五连查 + 约束块显式化（来源：AI Bytes《AI Coding 9 Best Practices》2026-04-16 + aisrc《Промпты для coding agents 2026》2026-09-13 实拉，与 §修复验证互补——那条管"改完怎么验"，本条管"AI 交的活收之前怎么查"）
**别批准一个 200 行的改动因为它"看起来对"**——AI 写代码看起来对、细节微妙错是常态。
- **收每个 diff 前五连查**：①import 真实存在吗（**幻觉导入仍常见**）；②函数签名跟调用处一致吗；③有没有发明不存在的 helper；④有没有改没让改的代码（越权改动）；⑤测试跑过了吗、代码真跑了吗。
- **约束块显式写进 coding prompt**（最被低估的一块）：不改 public API / 不加新依赖除非万不得已 / 不碰无关模块 / 遵循项目现有规则——不写，AI 默认全都能改。
- 判据：**AI 代码 = 新来的 junior 写的**——必须过正常评审流程，安全点单独看；三级测试栈（unit → integration → e2e）逐层过，不跳过。

## 轻量自动化三模式：Scheduled Batch / Webhook 端点化 / 事件触发（来源：DEV《AI Automation Pipelines 2026》2026-08-19 + cronhooks《Schedule AI Workflows》2026-04-27 + n8nautomation《Webhook Response Mode》2026-06-29 + Tutorials Dojo《Cursor Automations》2026-08-27 实拉，与 §定时任务记账判据互补——那条管"排期怎么写对"，本条管"自动化用什么形态搭"）
- **Scheduled Batch 模式（最省）**：cron + 脚本 + 一次 API 调用，$6/月 VPS 就能跑"每早爬竞品价格 / 日报摘要 / 审计成本异常 / 跑测试并总结失败"——**别为批量任务上重基建**，重编排平台是给复杂多步流程的。
- **Webhook 端点化模式**：把 AI workflow 暴露成 HTTP POST 端点（响应模式设 **Last Node**——返回末节点输出），加 shared secret 头保护，外部定时器/事件源来触发——**触发与执行解耦**，换调度器不用动 workflow 本体。
- **GitHub 事件触发清单**：PR opened / PR merged / push 到分支 / issue comment / PR review / workflow 完成——**团队自动化的标准起点**，比轮询省。
- 判据：先问"这活需不需要近实时"——不需要就 Scheduled Batch；需要就 Webhook 端点化；事件来自 GitHub 就用事件触发。

## 视觉提取三纪律：置信度标注 / 锚定描述 / 宽表裁剪（来源：Claudexia《Claude Vision 2026》2026-04-08 + Google《Image Understanding》2026-09-12 实拉，与 wb-ui-visual-qa 分工——那个管"看界面找问题"，本条管"从图里提取文字/数据"）
- **逐值标置信度**：提取每个值旁标注 `confidence: low|medium|high`——**低置信度行转人工复核**，不让模型静默输出可能错的数字。
- **图前锚定描述**：每张图前写一行说明（"这是德国税表第 3 页"）——**先锚定再识别**，能提升语言特定字形的 OCR 准确率。
- **宽表裁剪**：20+ 列的大表先裁剪/分块再提取，别整张塞给模型。
- **文字图顺序**：单张含文字图时，文字提示放图片前面（image 数组里 prompt 在前）；分辨率越高细节越准但 token 和延迟越高——按需选，不无脑最高清。

## 多 Agent 协作纪律：按技能建 / 共享层先建 / 接口契约 / 质检-回退（来源：AgDex《Multi-Agent 2026》2026-04-29 + Levelop《Practical Guide 2026》2026-08-12 + DynamicsCon《AI Workforce 2026》2026-05 + 腾讯云《Multi-Agent 实战》2026-04-02 + Tencent Cloud《LightVela》2026-07-31 + NovaKit《Orchestration 2026》2026-04-19 实拉，与 §多Agent决策树互补——那条管"什么时候拆"，本条管"拆了之后怎么协作"）
- **按技能建 agent，不按步骤建**：agent 按"它擅长什么"划分（研究/分析/写作），不按"流程第几步"划分；**"大多数多 agent 系统其实不需要多 agent"**——单 agent 能干的别拆，多 agent 慢、贵、被过度使用。
- **五种编排模式**：orchestrator-worker（一个编排者拆任务收结果）/ supervisor 路由（决策者分发）/ hierarchical（嵌套 supervisor，大系统）/ swarm 对等 / pipeline 顺序流水线（线性确定、好调试）——先选模式再动手。
- **共享知识层先建再拆**：多 agent 的可维护性来自类型化工具的共享知识层——**先把这个层做对，再拆 agent**；业务逻辑下沉到工具层，专家 agent 保持单车道，编排者只编排不干专家活。
- **Agent 间接口契约**：每个 agent 输入格式固定、输出结构化易解析（下游能准确理解上游）；责任边界清晰，避免重叠冲突；防止"后一个 agent 覆盖前一个 agent 数据"的 bug（交接用不可变中间产物）。
- **步骤间质检-回退函数**：agent 完成后不直接进下一步，先过质检函数——**结果太少就重试、分析太浅就要求修订**（"检查-回退"机制），把质检员当一等公民放进编排。

## 定时与后台任务的三条记账判据：排期语义 · 触发窗口 · 执行态与交付态分开（来源：OpenClaw 官方 docs.openclaw.ai·`automation/cron-jobs/schedules` + `automation/tasks`，2026-09-17 实拉）

- **cron 的"日"与"周"是 OR 不是 AND**：day-of-month 与 day-of-week 同时非通配时，匹配**任一**字段（Vixie cron 标准行为）。`0 9 15 * 1` 本意"15 号且是周一"，实际是"每月 15 号 **或** 每个周一"——一月触发 5–6 次而不是 0–1 次。要 AND 必须用 day-of-week 修饰符（`0 9 15 * +1`），或在任务内部自己守卫另一个字段。
  - 判据：排期写完后回读一遍"这一段到底是或还是且"。频率错一个数量级是**静默**的——它不会报错，只是多跑或少跑。
- **"整点"不保证整点执行**：顶小时表达式（分钟固定、小时通配）会被自动错峰最多 5 分钟削峰；要精确必须显式 `--exact`，或自己给 `--stagger 30s`。
  - 判据：对外的定时承诺按**窗口**写，不按**时刻**写。把内建错峰当故障去排查是白费力气。
- **执行终态与交付终态是两套状态，必须分开记**：子任务可以执行结果为 `succeeded` 而 `deliveryStatus` 仍是 `session_queued` / `blocked`。**"活干完了但结果没交回去"不能记成执行失败**——那样既丢掉已完成的结果，又会让重试去重复一份已完成的工作。
  - 判据：结论里执行结果与交付结果各占一槽，交不回去就写"已执行·未交付"，不许合并成"失败"。
- **等待完成靠通知，不靠轮询**：脱离子会话的完成是 push-driven 的，原文说"status polling loops are usually the wrong shape"。需要结果时挂完成通知，不要写 sleep-check 循环（它也顺带违反 §等待者不许占它等待的那类资源）。
- **与相邻条目分工**：§重放幂等 管"失败了能不能重来"，这条管"没失败但没交回去该怎么记"；§"已入队/已持久化 ≠ 会执行" 管入口，这条管出口。

## agent 恢复与控制流：检查点 / 错误分类→恢复状态机 / 有界重试 / 防失控（来源：DEV《AI Agent Control Flow Patterns 2026》2026-08-26 + Microsoft Foundry《When AI Agents Fail》2026-08-13 + agentnative《Checkpoint and Resume》2026-07-26 + 人人都是产品经理《让 AI 做研究》2026-09-17 实拉，与 §重试分两类管 互补——那条管"transport/tool 怎么重试"，本条管"整个 agent 运行怎么恢复"）
- **错误先分类，再决定恢复动作**：瞬时超时 / 未知状态 / 授权失败 / 重复风险 / 部分完成——**Retry / Recover / Escalate 是显式选择，Retry 不是默认**；恢复是受控状态机的一环，不是无脑重来。
- **重试仅当工具幂等**：不幂等的重试会把副作用翻倍；**tool receipt（工具调用凭证）存入 checkpoint**，断了先查"是否已生效"再决定（与 §写操作必须幂等 同一根）。
- **防失控用机制不用提示词**：max steps / 预算上限 / circuit breaker（熔断），**不是"更优的提示词"**——提示词拦不住失控循环。
- **检查点恢复陷阱：中断点之前的代码 resume 时会重跑**——副作用要么放在 interrupt 之后、要么做成幂等；checkpoint 按步提交（事件日志作安全返回点），失败只重试该步不全量重跑；checkpoint 历史要修剪（保留审计所需，热存储有界）。
- **HITL（人在环）是一等状态**：带超时、SLA、审计轨迹，不是临时插一句"要确认吗"。
- **pilot 先行**：全量跑之前先小规模验证可行性——目标是"跑对"不是"跑完"；发现不对就改计划或停。
- 判据：**恢复设计做在运行前**——崩溃后才想"怎么接着跑"等于没有恢复设计。

## AI 编码测试强化：变异测试自动化 / 变更前影响分析 / 测试写法规格化（来源：Codex Knowledge Base《Agent Testing Lifecycle》2026-06-19 + arXiv《TDAD》2603.17973 + ailinklab《Matt Pocock TDD Method》2026-06-10 实拉，与 §TDD/修复验证 互补——那条管"红绿循环与验收"，本条管"测试本身的质量与范围"）
- **变异测试 hook 自动化（存活突变 = 测试套件盲区）**：实现编辑后由 hook（如 PostToolUse）自动跑 mutation——注入故障进生产代码、看测试是否抓住；**存活突变意味着测试套件有盲区**，把存活突变喂回再修。判据：**AI 生成的测试会撒谎**——看起来全覆盖，变异一跑就露馅。
- **变更前影响分析（只跑受影响的测试）**：构建 **源码↔测试依赖图**，commit 前 agent 先查"这次改动会影响哪些测试"再决定跑哪些——不跑全套、不漏关键；依赖图做成**轻量静态 skill 文件**供 agent 查询（同 §TDAD）。
- **测试写法规格化（验行为不验实现）**：测试经**公共接口**验证行为，不钉死内部函数名——好测试读起来像域语言规格（"user can checkout with valid cart"），坏测试像实现走查（"checkout calls paymentService.process"）；代码可整体重写，测试不该跟着内部结构改。
- **烂测试 = agent 优化去通过烂测试**：测试定义"正确"，测试烂则 agent 的优化方向错——测试设计（TDD/属性测试/集成测试）是 agent 编码的上游质量闸。
- 判据：**先让测试可执行（澄清预期行为），再实现**；实现后变异验证，收工前影响分析——三者合起来才闭环。

## 可靠自动化编排：持久执行 / workflow-activity 分离 / per-state 重试 / Saga 补偿（来源：Google《Gemini + Temporal 持久 Agent》2026-09-12 + freeCodeCamp《Durable Autoscaling AI Agent》2026-06-23 + agentnative《Idempotent Retry Pattern》2026-07-25 + moai《Durable Execution》2026-07-02 + Cloudflare《Run Workflows》2026-06-26 实拉，与 §定时任务记账判据/重试分类 互补——那条管"排期语义与重试分类"，本条管"长任务怎么做到可恢复"）
- **持久执行（Temporal 语义）**：每步 LLM 调用/工具调用/循环由运行时持久保存——崩溃自动重试并**从上次完成步骤继续**：不丢对话历史、不错误重复工具调用；**停用 SDK 内置重试**防双重重试（运行时重试 + 应用重试叠加=重复副作用）。
- **workflow 与 activity 分离**：workflow 只描述顺序、**不做实际工作**（无网络调用）→ 崩溃后可安全重放重建状态；网络/LLM/工具等副作用全放 activity，**独立失败独立重试，不影响 workflow 状态**。
- **per-state 重试配置**：每个步骤单独配退避倍数/最大次数/jitter——限流类 API 指数退避、Lambda 类瞬时失败立即重试，不一套参数套全程。
- **Saga 补偿模式**：长事务拆成正向动作 + 补偿动作（发邮件→发更正邮件 / 建记录→删除或标记作废）；第 N+1 步不可恢复失败时，对 1..N 跑补偿恢复一致状态；**ledger 记录哪些补偿仍有效，补偿自身必须幂等**。
- **幂等键规范**：日期+记录 ID / 源事件 ID / slug / 内容哈希做稳定键——重试应确认或完成同一结果，不制造第二个结果。
- **按复杂度路由**：<30 秒的聊天/快速调用用 Agent 裸跑；>30 秒、多步、人审流程用持久 Workflow（自动重试+失败恢复+等外部事件）。
- 判据：**自动化可靠性的第一问永远是"它重复执行会发生什么"**——补 Prompt 之前先补幂等与恢复。

## MCP 工具工程纪律：isError 优先 / 错误六要素 / stdio 纪律 / 工具工程清单（来源：ChatForest《MCP Error Handling & Resilience》2026-03-28 + blueman82《mcp-server-enhancement》SKILL + GroovyWeb《MCP Server Development Guide》2026-05-02 + RaftLabs《MCP server development》2026-01-22 实拉，与 §工具循环/重试分类 互补——那条管"调用与重试"，本条管"工具本身怎么造、错误怎么回"）
- **isError: true 是最高影响改动**：工具失败返回**工具错误**（isError）而非协议错误——协议错误意味着"请求本身没法处理"，工具错误才是"业务逻辑失败"，分错层级最误导排障。
- **LLM 友好错误消息六要素**（好错误让 LLM 能自我恢复）：①失败类别 ②是否可恢复 ③哪个参数/假设失败 ④涉及哪个策略/系统约束 ⑤重试有没有意义 ⑥下一步该试哪个工具/流程——测试问：**"LLM 读到这条消息，知道下一步试什么吗？"** 不知道 = 重写。返回错误对象不抛异常（机器可读 code + LLM 可读 message + 建议修复）。
- **stdio 纪律（stdout 只走协议）**：MCP stdio 模式下 stdout 保留给协议 JSON——**一个 stray console.log（你自己的或依赖的）会注入协议流，客户端死于指向错误的 JSON parse 崩溃**；日志一律走 stderr 或文件。判据：凡是会往 stdout 写东西的依赖都要防，不只是自己不写。
- **工具工程清单**：输入进业务逻辑前先验证（Pydantic/Zod）；所有出站调用加超时（默认 5s、复杂查询 15s）；写操作全部配幂等键；返回结构化、带明确标签的响应。
- 判据：**工具是"learned 与 programmed 行为的边界"**——工具契约烂，模型再聪明也恢复不了。

## AI 编程工作流：spec 四步循环 / 任务型最小权限 / TDD 阶段化 handoff / ground truth 显式化（来源：shiplight《Spec-Driven Development》2026-08-10 + VS Code《TDD flow》官方文档 2026-09-11 + futureproofing《Agentic Coding Workflow 2026》2026-07-20 + SuperDev《Safe Workflow》2026-09-14 + Augment《Spec+TDD》2026-06-23 实拉，与 §规格驱动流水线/AI 代码收 diff 互补——那条管「整体流水线」，本条管「每阶段的交接与验证依据」）
- **spec 四步循环**：写 spec → agent 实现 → 按 spec 验证输出 → **把验收标准提升为回归测试**（每个工件喂下一个；验证交接是最易断点，专门盯）。
- **spec 只精确两件事**：Intent（为什么、解决什么问题——人和 agent 做局部决策的依据）+ Constraints（性能预算、安全边界）；spec 不预测全系统，小阶段迭代。
- **spec 作重构安全网**：重构后测试保持绿 = 行为与 spec 对齐；**边界用例只在失败测试指定时才进实现**，不让 agent 自由发挥边界。
- **任务→工具面最小权限映射**：文档任务只给读+编辑（无 shell）；测试修复只给测试命令（无网络、无部署凭据）——按任务类型配工具面，不用一把万能钥匙。
- **TDD 阶段化 agent 分工与 handoff**：Red agent 写失败测试 → 显式交接 Green agent 实现 → 交接 Refactor agent 重构——每阶段一个专用 agent，完成后必须显式 handoff 到下一阶段，不混职责。
- **ground truth 显式化**：每阶段写清 agent 读什么当完成依据——Build 读计划与现有代码模式、Test 读测试套件/构建退出码、Ship 读 diff 与 PR 清单——**不靠「感觉完成了」判断，靠指定依据**。
- 判据：**编程工作流的质量在交接处**——spec 是否落到回归测试、工具权限是否按任务收窄、阶段是否显式 handoff、完成依据是否可指认；四处都松，循环就散。

## Agent 规划与执行分离：ReWOO 三分离 / 计划自检门 / 计划可重放 / 省上下文 40-60%（来源：BestAIWeb《Planning Agents 2026》2026-05-07 + arXiv《MIRROR》2505.20670 + openlegion《Agentic Design Patterns》2026-06-01 + Ranjan《Orchestration in Agentic AI》2026-03-08 + Microsoft《Agent Reflection Planning》2026-09-17 实拉，与 §可靠编排/多 Agent 协作 互补——那条管「拆了怎么跑」，本条管「计划本身怎么产、怎么检」）
- **ReWOO 三分离**：Planner 先出完整计划（每步带占位证据）→ Workers 填观察 → Solver 综合——比 ReAct 显著省 token（planner 能出合理计划时不需要中间观察来回喂）。
- **计划自检门（MIRROR）**：分解出计划后先自评四维（完整性/效率/连贯性/子任务可否再优化），评分超阈值 θp 才交给执行，否则迭代修订——**计划也有质量门，不是执行才把关**。
- **计划可重放**：计划是可检查、可记录、可重放的离散工件——出错时先定位是**规划层错还是执行层错**，两层修法不同。
- **Plan-and-Execute 省上下文 40-60%**（长任务）：executor 上下文限定当前步，不背全计划——代价是需计划质量门兜底（与上面配合）。
- **计划=策略预检工件**：任何工具调用前对计划做禁止项自动审（被禁操作/越权动作），不靠执行中拦截。
- **迭代精炼 3-5 遍封顶**：不确定解空间才用 iterative refinement，明确 3-5 遍上限——无上限的自评循环会烧光预算。
- 判据：**规划的产出是「可检查的计划」不是「会执行的念头」**——自检门+策略预检+可重放三项齐，plan 层才可信。

## 多智能体协作强化：编排层 checkpoint / 结构化 handoff / 委托循环防护 / partial failure 预案（来源：AINinza《Multi-Agent Orchestration 2026》2026-04-06 + Stochastic Sandbox《Orchestration Patterns 2026》2026-04-21 + NovaKit《Multi-Agent Guide》2026-04-19 + Kalvium《When One Agent Isn't Enough》2026-04-23 实拉，与 §多 Agent 协作纪律 互补——那条管「拆了怎么建」，本条管「跑起来怎么防崩」）
- **编排层 checkpoint**：每成功一步存 state，失败从最后 checkpoint 恢复而不是重启整个 workflow——长跑没 checkpoint = 网络抖动白费 30 分钟。
- **supervisor/worker 省 40-60%**：orchestrator 分解→路由 specialist（worker 用小模型 tuned 域）→组装——比全程 frontier 模型省近半。
- **pipeline 重试/超时放管线层，不放进单节点**：单节点内自己做重试会重复执行且难统一；每节点后打日志，质量退化点可定位。
- **结构化 handoff 最可靠**：固定交接格式防上下文膨胀、让 agent 间契约显式可测——比自由摘要交接稳。
- **委托循环防护**：A→B→A 的循环用委托深度计数器或 no-backsies 规则（不能委托给委托给自己的 agent）——防死循环。
- **partial failure 预案三选**：worker 3/5 崩了——重试该 worker / 重启编排器 / 降级计划（少一个 worker 的简化版）——提前定好选哪个，不现场即兴。
- 判据：**多智能体系统的死法大多是「一个 worker 崩了拖垮全局」**——checkpoint 恢复、管线层重试、委托防环、partial failure 预案四项齐，编排才扛得住。

## Agent 循环工程：loop spec 五元组 / plan-act-verify vs review-gated / 原子文件级任务 / 每阶段 fresh context（来源：arXiv 2607.00038《Stop Hand-Holding Your Coding Agent》+ datallmlab《Loop Engineering》2026-07-07 + SitePoint《Run AI Coding Agents for Days》2026-04-17 + Kunal Ganglani《Agent Loops 2026》2026-06-22 实拉，与 §规划执行分离 互补——那条管「计划与执行怎么分」，本条管「循环本身怎么定义怎么收」）
- **loop spec 五元组**：trigger（人/排程/事件）+ goal（尽量可验证）+ execution（调用已验证的命名 skill，不用步骤提示）+ verification（真检查）+ stopping rule——循环是可复用的有界工件，不是逐句提示。
- **两种验证形态**：plan-act-verify（一次编程检查 tests/build/lint，pass 即停）适合「把 CI 修绿」类可检查任务；review-gated（程序检查 + 第二重 gate：judge 模型或人工批准）适合任何要交付的东西——gate 挡住的后果是 escalation failure（没人被 paged），必须配升级路径。
- **原子文件级任务**：markdown 任务文件 + 显式验收标准 + 约 30-60 分钟工作量 + 明确文件边界——不给 agent 宏大目标。
- **每阶段 fresh context**：主上下文只放主任务，不直接推进的步骤丢 subagent；每阶段用干净上下文起步（链 subagent），响应变不连贯时策略性压缩。
- **agentic context layer**：版本化文件（ADR/项目记忆/规则）给所有 agent 同一 ground truth——防平行 agent 漂移、互相矛盾、重议已定决策。
- 判据：**循环可靠 = 可验证目标 × 命名 skill × 真验证 × 明确停止**——四项齐就是 loop，缺一项就是碰运气。
