## r690B 下沉：证据匹配主张类型——数字、缺席、改名与示例的四类硬约束

来源：GitHub `vercel-labs/agent-browser`·`.agents/skills/technical-writer/references/technical-verification.md`（2026-11-07 实拉 API 9,688B）。提升层：可复用 Skill（文档取证）。

- **按主张类型配证据，不用"看起来合理"代证**：实现行为→相关代码 + 测试 + 版本/commit；公开接口→目标版本的公开导出与类型，并对照官方 API 文档；发布状态→官方 changelog 与可用性文档；计划中的行为→**明确标为提案**的工程规格；性能/规模→原始测量 + 方法学 + 工作负载 + 条件；别家能力→**该厂商自己维护的文档**。
- **测试的证明力有边界**：测试只在其覆盖范围内支持结论；**缺测试不等于功能不存在**；**mock 不能证明外部服务的行为**。判据：把"测过"与"外部真的这样"分开写。
- **数字纪律**：不得用任意的数值精度让文字显得权威——「最高到」「大约」都**救不回一个编造的数**；测量类必须保留 metric / baseline / 单位 / 工作负载 / 是否厂商自报；延迟≠吞吐、平均≠分位、相对提升≠百分点。
- **缺席主张也要证据**：搜不到不能证明不存在。给**窄结论**（"在该版本文档的公开接口里没有找到"），并写下"什么情况下需要复查"。
- **改名不等于等价**：产品换了名字，不代表行为相同；**不得把新名字直接替换进旧 API、旧迁移路径或旧运行时解释**——历史名可能正是用户检索旧报错所需要的，要标时期/版本并解释已验证的替代关系。
- **代码示例六查**（收进文档前）：①包/API/flags/imports/配置键在该版本真实存在；②片段用的是正确机制、放在正确文件或执行上下文；③前置依赖/凭据/权限已说明或链接；④占位符可识别、一致、替换后仍合法（避免被 shell 当重定向）；⑤错误处理与清理够用且不喧宾夺主；⑥周边文字准确描述它做了什么、**没证明什么**。完整示例须能在所述环境直接跑；**部分示例必须写明改哪个文件、假定什么既有上下文**；不得把伪代码标成可运行。
- **最小验证 + 诚实标注**：优先语法校验/编译/相关测试/链接检查，而不是整仓跑一遍；**没跑就写"未运行"**，不得编造成功结果；不得为验证文字去执行破坏性动作、产生费用或发布内容。
## r693A 下沉：交给执行者的说明要"耐久"不要"精确"——写契约不写路径

来源：GitHub `mattpocock/skills`·`docs/engineering/triage.md`（12,893B，2026-11-08 实拉 API 原文）。提升层：工作流 / 可复用 Skill（文档）。

- **brief 的寿命比代码位置长，所以只写稳定的东西**：一份等执行的说明可能在队列里躺几周，期间代码早已移位。判据：**只写类型、签名、行为契约、验收条件；不写文件路径、不写行号**——路径会腐烂，契约不会。
- **已复现的 brief 远比猜的强**：动笔前先验一次（复现步骤 / 检出分支跑相关测试），结论只有三种：已确认并附代码路径 / 复现失败 / 细节不足到无法尝试。**"细节不足"是最强的"需要补充信息"信号**，不要硬写成一份看似完整的说明。
- **两条通道不要混**：外部进来的报单（别人写的、形状各异）要先分流再执行；**自己规划产出的票已经是可执行态，再分诊一遍纯属浪费**——两条通道在"可执行"这一点汇合，不在此之前。
- **批量看清单时，清单通常只有正文没有评论**：靠它做判断会把"评论里已写已修复"的条目重新派活。判据：**批量处置必须显式要求读每条评论**，否则"便宜的一遍过"就是错误证据源。
- 反模式：把 brief 写成一份"什么都说一点"的长文（执行者仍不知道从哪下手）；用关键词去重历史决定（应按概念匹配，命中后先引用旧决定问"现在还成立吗"）。
## r693B 下沉（增量）：术语表的跨引用范围、加载自检与"值钱的位置"

来源：GitHub `mattpocock/skills`·`docs/engineering/domain-modeling.md`（10,337B，2026-11-08 实拉 API 原文；与 §十一 术语表与决策记录 互补——那条管"文件装什么/膨胀怎么修"，本条管"它跟谁对齐、怎么判断它真的在起作用"）。提升层：可复用 Skill（文档）。

- **跨引用只对代码、术语表与 ADR，不查工单**：别人三个月前在一条已关闭的 issue 里吵定的命名，它不知道，会当新问题再提一遍。判据：**跨引用范围决定它会不会重复辩论**——要补，就把"已定命名去查哪里"写进项目自己的 agent 文档，别指望工具自己知道。
- **"自动加载"是这类技能最弱的一环，必须有可观察的自检**：技能说"在对话中顺手维护术语表"，模型常只加载上层对话、跳过术语维护。判据：**会话结束时术语表一个字没变，就是没加载**；要它就**按名字显式调用**，不要等它自己触发。
- **值钱的位置只有命名边界**：模块名、表名、状态枚举、issue 标题、命令名、接口字段——同义词控制在这些地方才产生价值；普通叙述里纠结用词是净亏。
  - 推论：**一天就能做完的项目跳过术语表**；未评审、由 agent 自己撰写的术语表**比没有更糟**（后续会话会把它当事实读）。
- **术语表不该随手增长**：它的正确状态是"有时变短"；只增不减说明它又在吸收实现细节了。
## r694B 下沉：改别人的既有文档——外部输入先当不可信、不许重排版、红线要验"有没有漏包"

来源：Anthropic 官方 `anthropics/skills`·`skills/docx/SKILL.md`（6,897B，2026-11-08 实拉 API 原文）。提升层：工作流 + 工具。

- **外部来源的文档先当不可信**：解包后先删掉符号链接条目（`find unpacked -type l -delete`），再做任何读写。判据：**"这份文件是谁给的"决定要不要做这一步，而不是"看起来是个 docx"**。
- **改 XML 前后都不许重排版**：就地改，不格式化、不美化缩进——重排版会造出一份 diff 比实际改动大几十倍的产物，评审没法看。
- **可见的短语在 XML 里常常不是连续字符串**：Word 会把文本拆进许多 run（修订号、拼写标记），所以改之前先合并同格式相邻 run（不改变内容与渲染），否则你会"搜不到那段话"。判据：**先合并再改，不是先改再想办法**。
- **红线（修订模式）要验"有没有漏包"**：用 `--author` 校验，任何被你改了却没有被插入/删除标记包住的文本都会被报出来——这在"接受全部修订"的视图里完全看不见，是最容易犯又最难发现的错。
- **删除整个段落 = 删掉每个 run + 删掉段落标记**；被删掉的段落标记含义是"与本段合并到下一段"，所以全删的段落才会整段消失。
- **判"缺陷"前先分清是文档的还是查看器的**：主流两个接受修订的工具都不合并被删段落标记，会留下一个空条目——空 bullet 是视图产物，不是文档缺陷。判据：**真正的段落删除要去 XML 里看，不要看渲染结果下结论**。
- **验收 = 渲染成图再看**：转 PDF → 逐页转 JPEG → Read 看图（页码按总页数补零）。判据：**没看过渲染结果的"改好了"不算改好**；纯文本 diff 看不出字体、分页、表格错位。
## r694C 下沉：改既有文档的结构纪律——结构先于内容、槽位≠条目、打包要去残留

来源：Anthropic 官方 `anthropics/skills`·`skills/pptx/SKILL.md`（20,782B，2026-11-08 实拉 API 原文）。提升层：工作流 + 工具。

- **所有结构动作（增、删、调序）必须在编辑任何一页的内容之前做完**。原因有两条，都是"顺序错了就白做"：复制页是**逐字复制**当前文件，先改内容再复制会把改动一起克隆出去；清理脚本会**删掉不在页序清单里的页**，包括你刚写的那一页。判据：**先定骨架，再填字**。
- **模板槽位 ≠ 源条目**：模板画了 4 个成员位而你只有 3 个 → **删掉第 4 个的整组元素（图 + 全部文本框）**，不是只清空文字；删完还要专门查一遍"孤儿视觉"（留下的框、线、图标）。判据：**"内容清空"不等于"版面清干净"**。
- **打包要先删旧产物再打**：目录里已有上一版输出时，先删再 zip，否则**已删除的部件会残留在新包里**——文件看起来能开，里面却带着你以为删掉的东西。
- **模板来源的产物验收要基线化**：模板自身可能就带 schema 错误，直接跑校验会把它的错报成你的；带 `--original` 跑，把模板已有的错压掉，只留你引入的。但**结构类检查（关系、内容类型、图表）不吃基线**，模板带的问题照样要单独看。
- **占位符残留用 grep 兜底**：`xxx`、`lorem`、`ipsum`、`TODO`、`[insert`、"this page/slide layout" 这类字符串，肉眼翻页容易漏；一条命令扫全文，命中就必须先修再宣布完成。
- **改完必须全量重渲染**：编辑后的源文件要重新导出一遍再转图，直接对旧图判断等于没验。
## r695B 下沉：文档共创的顺序纪律——骨架先立、未知最多先写、摘要最后写、三轮无改动才转删

来源：Anthropic 官方 `anthropics/skills`·`skills/doc-coauthoring/SKILL.md`（15,815B，2026-11-08 实拉原文）。提升层：工作流 + 可复用 Skill。

- **先立占位骨架再填内容**：结构一旦同意，立刻把**所有章节标题 + `[待写]` 占位**建出来（有 artifact 用 `create_file`，没有就建 md 文件）。判据：**先有骨架，用户才能看见"还差哪几块"**；逐节即兴写会丢掉章节之间的配重。
- **从"未知最多"的章节开始，摘要最后写**：决策文档从核心提案起，技术规格从技术路线起；**摘要/概述留到最后一节**——先写摘要等于在信息最少的时候定调，后面必然反复改。
- **每节六步，不许跳**：① 5–10 个针对本节目的的澄清问题 → ② 头脑风暴 5–20 条候选项（含"用户说过但忘了的"和"没人提到的角度"）→ ③ 用户 keep/remove/combine，**并要求一句理由**（理由是用来学他的优先级，供后面章节复用）→ ④ 缺口检查（"这节还缺什么"）→ ⑤ 起草 → ⑥ 精准编辑。
- **编辑只用局部替换，绝不重打全文**：`str_replace` 逐处改；重打全文会让未被提及的段落悄悄漂移（与 §一「编辑即诊断」同源：只改点名的那处）。
- **什么时候转"删"**：**连续 3 轮没有实质修改之后**，才问"有没有可以在不丢信息的前提下删掉的"。判据：`3` 是"增补期结束"的信号，早于此问删会误删还没长出来的内容。
- **80% 时通读一遍查三样**：跨节流与一致性、重复与矛盾、**"slop"式的通用填充**——每句都要能说清它承担什么。
- **有图必查 alt 文本**：文档里无 alt 的图，别人（或模型）读文档时等于看不见；交付前先补。
## r695B 下沉：读者测试——用"无上下文的读者"验收文档，而不是用作者的自洽感

来源：同上（`doc-coauthoring/SKILL.md` Stage 3，2026-11-08 实拉原文）。提升层：工作流 + 可复用 Skill。

- **做法**：交付前**预测 5–10 个读者真会问的问题**（"他要在文档里找什么就会这么问"），然后把这些**只给问题 + 文档正文、不给任何上下文**，交给独立会话/子 agent 回答。
- **必跑三条探针**（比正确率更能暴露缺陷）：
  1. 这份文档哪里含糊、不清楚？
  2. 它默认读者已经知道什么？（**未言明的前置知识是最高频的读者卡点**）
  3. 内部有没有自相矛盾或不一致？
- **通过条件**：读者**连续答对、且不再冒出新缺口或新歧义**——才算文档就绪；只答对一两题不算。
- **失败就回到对应章节改，再测**：不要整篇重写——问题定位在哪节就改哪节（与 §十一「先删到 lean 再谈拆」同构：定点修，不整篇重做）。
- **最后一步仍是作者自己终读**：读者测试通过 ≠ 可以交；作者要事实复核（链接、数字、技术细节）并确认"读的人会因此做什么"。附录用来承载深度，不靠正文堆。
## r696C 下沉：结论分级四档锚点 + 强弱判别问句——严重度上限是"已证明的影响"（来源：同上 `security-audit`·Separate priority from certainty）

- **四档锚点各对应一种"打穿程度"**：critical＝未认证就拿到代码执行/整库访问/任意账号接管；high＝**完整击穿**某条显式控制且有真实后果（认证绕过、跨租户读写、存储型脚本影响他人、认证后代码执行、未认证远程停服）；medium＝真实越界但爆炸半径有限/前置条件罕见；low＝非机密内部信息泄露或需长期投入才得微小收益；informational＝确证但近乎无影响，通常只作为更大结论的前置。
- **强弱判别问句（high vs medium）**：**"它完全击穿了某条显式控制并造成真实后果，还是只削弱了它？"**——答不出具体损害，等级就该低于直觉。
- **上限规则**：等级**不得超过已证明的影响**；`needs_validation` 一类"被阻断的假设"**不给等级**（与 av r689B 三态字段纪律同源，本条补的是等级怎么定）。
- **反模式清单可直接借用**：把清单偏差当漏洞、纵深防御建议但无可达越界、拿"最佳实践缺失"当结论、把自影响当跨边界结果、按猜测的部署行为定性。
## r697B 下沉：知识记录默认"扩展既有 owner"，新建前必须证明既有 owner 装不下（来源：同上 `AGENTS.md`·Authority / Judgment boundary / Validation 三节）

- **写之前先搜四个坐标**：拟用的 canonical owner/id、受影响路径、导出符号、行为的语义词——同时搜**现有记录**与**在途 PR**。默认动作是"扩展或投影既有 canonical owner"，不是新开一份。
  - 判据：**新文档的成本不在写它，而在以后每次都要读它**——所以先证"既有 owner 装不下"，再新建。
- **新建的唯一正当理由：不同的事实边界**，且必须在记录里写明"为什么既有 owner 装不了它"。反面清单同样明确：**不为已完成、已有主、已被取代的工作再立新政策**。
- **authority 三态**：`draft`（尚无权威，可能还缺证据或 owner 复核）/ `current`（明确批准、有权威）/ `archived`（仅作上下文，须带 `superseded`/`withdrawn`/`historical` 之类原因与替代链接）。**只有 `current` 治理实现与评审**。
  - 判据：**批准不能从"代码已合并、没人反对、旧评审、wiki 上早就有"推断出来**——沉默不是批准，合并也不是。
- **记录用现在时描述系统**：提案、历史、PR、研究都不进记录；模板形状大改要升 schema 版本并迁移活跃记录，只改模板指引不动已接受的历史。
  - 判据：**记录答"系统现在是什么样"，不答"我们讨论过什么"**——混进去，三个月后就分不清哪句是现状、哪句是旧提案。
## r699A 下沉：模型味文案的三级判据——一个 tell 不算证据，簇与重复才算；每条禁令必须配一条正面动作（来源：同上 `references/copy-tells.md` 9,612B，2026-11-08 实拉）

- **病因先说清**：模型倾向挑"适配最多页面"的措辞，调优又把它推向安全、正面、密集的表达——**具体事实被"适配任何业务"的说法替换掉**。所以**具体只能来自输入（brief、客户原话）**，不能来自风格规则；风格规则给不出具体。
- **三级严重度，不要一刀切**：`ban`（出现一次即为 tell，如 "delve/tapestry/testament to/seamless/robust" 这类占位形容词、`[Company Name]`、`{{tokens}}`、页面上残留 markdown 星号或 `##`）、`cap`（一次尚可、重复即 tell）、`context`（只有与其他 tell 并列时才计入）。**单个 tell 证明力很弱，簇与重复才是信号**——按密度判，不按键名判。
- **每条禁令必须配一条正面动作**：只写"别用 X"会让模型抓最近的替代品（禁了 "seamless" 就换 "effortless"）；**禁令 + 该位置该写什么（具体数字、步骤、失败情形）才算闭环**。
- **residue 是最强的单条证据**：会话残留（"Certainly!"、"I hope this helps"）、模板占位（"[Company Name]"、lorem ipsum、`{{token}}`、`[NEED]`）——**等于把对话或模板直接粘进了成品**。
- **例外要写明**：行业里字面成立的用法（攀岩 harness、定制 bespoke、无缝针织）与客户自己的品牌名保留；否则清洗会把真实信息一起洗掉。
- 判据：**去模型味不是换同义词，是把被形容词盖住的事实补回去**。
