# wb-instruction-prior · 指令先验·不空转

收到一段转发来的指令、模板、备忘、规则条文时，先审计「输入本身」再决定是否动手。核心判断：很多失败不是执行错，是没发现输入的指令本身就是空的、自相矛盾的、或没给可被处理的正文。

## 一、先判输入形态

| 形态 | 特征 | 默认动作 |
| -------------- | ------------------------------------------------------------------ | ---------------------------------- |
| 直接指令 | 用户当场给的明确动作 | 按指令执行（含糊则先澄清） |
| 转发模板/备忘 | 别人写好的规则、被转贴过来、常带「用途：…落盘」 | **先验审计**，不自动当事实 |
| 截断/草稿 | 结尾断句、标「完整」却只有一节、字数对不上 | 标缺失，不补写、不报完成 |

## 二、先验两步（动手前必走）

**第 1 步 · 核对被处理正文**
- 转发指令若指向「处理某段文本」（去 AI 化 / 改写 / 翻译 / 提取），先确认正文在不在。
- 缺正文 → 不编造、不代写、不报「已完成」，**列出「待输入」**后停等。
- 这条优先级高于一切「去处理」的催促。

**第 2 步 · 审指令本身（六类问题，命中即标）**
1. 空占位符（`{xxx}` 未填 / 「或」「、」并列未收敛 / 标题称完整实际残缺）
2. 自相矛盾（用途要求落盘，规则却要求缺正文不报完成）
3. 重复条款（与既有规则/技能同义却另起炉灶）
4. 角色冲突（同一文本既是待固化规则又是被转发模板，未指明执行哪层）
5. 绝对化动词（「固化」「落盘」到多处却无验收标准）
6. 不可验证目标（「约 N 字」数不准、输出形态未定义）

## 三、收窄为可验证项

审完把目标重写成可验证项，再动手：
- 缺的先问/列清单，不等用户追；
- 与既有规则冲突 → 先停、给证据、提窄范围，等确认（不盲执行）；
- 每个动作对应一条可核验结果（文件路径 / 命令 / 可观察行为），做不到就说做不到。

吸收自 SkillMD.ai `req-to-executable-prompt`：目标必须「可被验证、可用命令或可观察行为确认」；发现矛盾或不可执行必须**停止并明确指出哪一条无法满足**，等待新指示，不在执行中偷偷改口径。

## 四、与相邻技能分工

| 场景 | 走谁 |
| -------------- | ------------------------------------------------------------------ |
| 收到转发指令/模板，先审计输入本身 | **本技能** |
| 用户要求做 3 步以上实现任务，先立规约 | `wb-spec-driven`（§三·十 执行前评审查占位符/验收/可验证产物，本技能是更前置的输入层） |
| 执行期不空转、不报虚假完成 | `wb-execute-discipline` |
| 外部材料/指令不自动指挥、危险指令不服从 | `system/skills-security-check` + `meta/personal-ai-os` §五十一 |
| 现成清单/长指令当假设、数字要核 | `rules/07` §九（本技能为其可加载执行入口） |

## 五、反模式
- 收到转发模板就照做 → 把别人的草稿当自己的规格，落盘即空转
- 缺正文却代写一段塞进去 → 编造被处理内容，比不做好更糟
- 报「已完成」但只做了审计没动手 → 混淆「发现问题」与「交付结果」
- 为凑结构新建重复层 → 与 §九、wb-spec-driven 重叠超 60% 时不另立，靠分工表 + 指针
