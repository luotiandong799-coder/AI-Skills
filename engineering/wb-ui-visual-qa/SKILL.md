# wb-ui-visual-qa（界面视觉检查：截图说话，不靠描述）

## 核心原则

**界面问题要靠截图定位，不靠模型脑补布局**。打开页面 → 截图 → 看渲染结果 → 指出问题位置，比"我猜这里可能有问题"可靠得多。

## 与 browser-automation 的分工

| 场景 | 用谁 |
|---|---|
| 打开网页、填表、登录、抓数据、点按钮 | browser-automation |
| **验证页面长什么样、截图找 UI 问题、双端视觉回归** | 本技能 |

判断标准：**任务是"操作"还是"检查"**——操作走 browser-automation，检查走本技能；视觉检查发现异常后要改页面再操作，两个技能配合。

## 执行流程

1. **明确检查面**：桌面端、移动端、还是双端？关键页面/路由清单是什么？改动点是哪块（有 diff/变更列表时按改动点聚焦检查，不整站漫游）。
2. **打开并截图**：逐个页面打开、等渲染完成（JS 内容至少等 2-3 秒或等关键元素出现）、截图保存。
3. **逐张看图定位问题**：对每张截图检查——
   - **布局**：元素重叠、溢出、错位、空白异常、滚动条异常
   - **样式**：颜色/字号/间距不一致、圆角/阴影异常、字体加载失败（豆腐块）
   - **文案**：错别字、截断（...）、换行错乱、中英文混排问题
   - **响应式**：移动端窄屏是否单列换行、触控目标是否过小、是否横向溢出
4. **改动前后对比**：有改动前截图就并排对比；没有就凭页面预期检查。对比时先看"改动影响区"再看全局。
5. **输出问题清单**：每条问题带——位置（哪个页面/哪个区块）、现象（看到什么）、证据（截图）、严重度（阻断/明显/轻微）、修复建议。

## 双端检查要点

**桌面端**：宽屏布局、hover 态（如果可触发）、多列是否正常。
**移动端**：320-390px 窄屏、触控目标 ≥44px、文本不溢出、图片自适应、不依赖 hover。

## 判定纪律

- **截图是证据，描述不是**：没截图不写"看起来没问题"——没看就是没看，标注"未检查"。
- **改动区优先，全局兜底**：有变更时先查改动影响区，再扫全局；无变更时按清单过关键页。
- **分清视觉问题与功能问题**：布局/样式/文案归本技能；点击无响应、接口报错归功能测试，转 browser-automation 或调试流程。
- **不脑补修复**：只定位问题+给建议，具体改法交给开发流程，不越权直接改页面。

## r695A 下沉：AI 生成设计的指纹清单与两遍法（来源：Anthropic 官方 `anthropics/skills`·`skills/frontend-design/SKILL.md` 9,390B，2026-11-08 实拉原文）

**为什么归本技能**：界面"看起来没问题"和"看起来像 AI 批量生产"是两件事，后者同样是用户可见缺陷——布局全对、审美仍扣分。检查清单要能指名说出"这条像模板"。

- **五组已被观察到的生成痕迹**（原文按审美聚类，检查时逐条比对）：
  1. **奶油底 + 高对比衬线标题 + 陶土色**（底接近 `#F4F1EA`，强调色接近 `#D97757`，恰好是 Claude 交互强调色）——在用户 brief 上出现即读作"AI 味"；
  2. **近黑底 + 单一荧光绿/朱红**；
  3. **报纸式**：发丝分隔线、零圆角、密集分栏；
  4. **SaaS 卡片套件**：内容切成一模一样的圆角卡片、不分层级全用同一个圆角、每张卡同一个 `rgba(0,0,0,.1)` 软阴影、渐变当装饰；
  5. **模板装饰条款**：每个标题上方一层 letter-spaced 全大写 eyebrow 标签、用中点拼元信息（`A · B · C`）、`WORD — fragment` 式带空格 em dash、用 `#0B0B0B`/`#111` 假装黑、小字号数据用等宽体、链接与按钮文本末尾挂一个 `→`。
- **与 wb-visual-gen §三·五 分工**：那张表管网页硬禁（AI 紫渐变/三等分卡片/Inter/假截图/编号 eyebrow），本条管设计层指纹与出稿流程；两边重叠的项（eyebrow、em dash）以那边口径为准，本条只补差异。
- **判据：这些不是"错"，是"默认"**——某些 brief 下完全成立；但当 brief 没有指定时，把自由度花在这些默认上就是缺陷。**brief 的明确指定永远优先**，包括它就是要这种风格。
- **两遍法（写码之前必须先过一遍）**：① 先出一份紧凑 token 计划——4–6 个命名 hex 的基色、字体与各自角色、布局概念（一句话 + ASCII 线框，含对齐方式）、三条"这页为何独特"的原则；② **对着 brief 复核这份计划**：把它放进任何同类页面是否同样成立？成立就说明是默认，改掉并写明改了什么、为什么；③ 复核通过再写代码。
- **克制**：大胆只花在一处（一个记忆点），其余保持安静；质量地板不宣传也要达到——移动端响应式、可见键盘焦点、尊重 `prefers-reduced-motion`、对比度可访问、配色和谐。
- **自评用截图**：一图胜千 token，改完自己先看图再交付。
- **顺手要查的代码坑**：`.section`（类选择器）与 `.cta`（元素选择器）这类特异度混用会把 padding/margin 互相抵消，表现为"间距怎么调都不对"。
- **文案也是设计**：CTA 说清会发生什么（`Save changes` 而不是 `Submit`）；同一个动作全流程同名（按钮 `Publish` → 提示 `Published`）；错误不道歉、不模糊，只说发生了什么和怎么修；空态是行动邀请而不是情绪。
## r695C 下沉：主题套件——先看全量样张再选，选定后一次性套用到全部产物

来源：Anthropic 官方 `anthropics/skills`·`skills/theme-factory/SKILL.md`（3,124B，2026-11-08 实拉原文）。提升层：可复用 Skill（视觉一致性）。

- **一个"主题"是三件套**：**色板（带 hex）+ 标题/正文字体配对 + 一个能说清的视觉身份**（给谁看、什么气质）。判据：只有配色没有字体角色的，不算主题，只是换了个颜色。
- **流程固定四步**：① **先给全量样张让用户看**（不要改样张、不要只描述）；② 问选哪套；③ **等显式确认**；④ 才把该主题套到产物上。
  判据：**"看着不错就先用"是最贵的返工**——主题一旦铺开，改一次等于全篇重排；样张阶段改的成本是一句话。
- **没有合适的就现造，但造完仍要过一遍确认**：按同样的结构（色板/字体/身份）新造一套，命名说清它代表什么，**先展示复审，再套用**——自造主题同样不能跳过"看样张"这一步。
- **一致性优先于单页好看**：选定后所有页面/所有产物同一套色与字体；某页"单独调一下更好看"就是破窗（与 §三·五 同页只锁一个主题、§r695A 大胆只花一处同源）。
## r696A 下沉：改现成产物先读模板——固定段一字节不动，只换标注出来的变量段

来源：Anthropic 官方 `anthropics/skills`·`skills/algorithmic-art/SKILL.md`（19,769B，2026-11-08 实拉原文，STEP 0: READ THE TEMPLATE FIRST）。提升层：工作流（视觉产物改动）。

- **动任何现成产物前，第一步是把模板原文读完**（不是"扫一眼"，是用 Read 读全），然后**把它当字面起点**：原文原话是 "Use that file as the LITERAL STARTING POINT - not just inspiration"、"Build on it, don't rebuild it"。
- **固定段 / 变量段先分清再动手**：模板里标注为 FIXED 的（页头、侧栏结构、品牌字体与配色、种子控件、动作按钮）**一字节不动**；只替换标注为 VARIABLE 的（算法本体、参数控件）。判据：**"我觉得这样更好看"不是改动理由**——那是把模板的已决事项重新决策一遍。
- **五类禁止项各对应一种偷懒**：从零重写 HTML / 自创配色与样式 / 换系统字体或深色主题 / 改侧栏结构 / 只把这模板当"灵感"。
- 与 §r695C 主题套件、§r695A 两遍法的分工：那两处管"选什么风格、怎么出稿"；本条管**"已经有模板时，不许再造一个模板"**。
## r696B 下沉：平台规格先数字化，交付前用校验器机检，优化只在被要求时做（来源：Anthropic 官方 `anthropics/skills`·`skills/slack-gif-creator/SKILL.md`，7,841B，2026-11-08 实拉原文）

- **把平台的硬限制先写成一张数字表，再动手**：尺寸（emoji 128×128 / 消息 480×480）、帧率 10–30、色数 48–128、时长 <3 秒。判据：**规格是常量不是品味**——先落表，代码里所有默认值都从表里取，别边做边猜。
- **配一个"能不能交"的校验器，而不是靠肉眼**：原文自带 `validate_gif(file, is_emoji=True)` 与 `is_slack_ready(file)` 两级——**交付前跑一次，返回 pass/fail + 明细**。判据：**能机器判的规格绝不靠目测**（尺寸/帧率/色数/体积都是可判的）。
- **优化是条件动作，不是默认动作**："Only when asked to make the file size smaller" 才降帧率/降色数/缩尺寸/去重帧。判据：**没被要求就把清晰度换成体积，是在替用户做他没提的取舍**。
- **别用跨平台不可靠的渲染手段**：emoji 字体在平台间不一致 → 宁可自绘；同理，交付物里任何"本机有、对方不一定有"的字体/图标/资源都要先问一句。
## r696B 下沉：动效质感的四条硬手法——粗描边、渐变底、分层细节、缓动不用线性（来源：同上 `slack-gif-creator` 的 Making Graphics Look Good + Animation Concepts）

- **描边/线条宽度 ≥2px**：1px 线在任何缩放下都毛糙，成品像占位图。判据：**"细=精致"是错的，细=没做完**。
- **背景用渐变、形状要分层**：纯色底 + 单个平面形状 = 素材感；叠一层半透明外发光、内嵌小一号同形、加高光弧，立刻从"图标"变"作品"。
- **动作必须带缓动曲线**：linear 位移看起来像机械滑轨；原文给了现成档位 `ease_in / ease_out / ease_in_out / bounce_out / elastic_out / back_out`——下落用 ease_in、落地用 bounce_out、停下用 ease_out，过冲用 back_out。
- **复合动作优于单一动作**：弹跳+旋转、脉动+滑入；粒子要给重力与透明度衰减。判据：**一个动作说清一件事，两个动作才像"设计过"**。
- 与 §r695A 两遍法、§r696B 平台规格的分工：那两处管"流程与硬规格"，本条管**动效与图形的质感水位**。
## r699A 下沉：收尾门禁——只要检查器还能修出一个 FAIL，这个页面就不算完工（来源：GitHub `Leonxlnx/taste-skill`·`references/gate.md` 13,183B + `skills/taste-skill/SKILL.md` 30,970B，2026-11-08 实拉，1663 文件全树）

- **完工的定义是机检清零，不是"我看着挺好"**：一个 build 在 checker 仍能列出可修的 FAIL 时**不算结束**；门禁脚本把未关闭项列出来，并**记轮次**——这样迭代是真的在收敛，而且**会结束**（有轮次上限，默认 3 轮）。
- **轮次预算是"防止无限打磨"的装置，不是质量指标**：每轮跑完必须留下"这一轮修掉了哪几条 FAIL"，下一轮从剩余清单继续；轮次用尽仍未清零 → 交回人工并附剩余清单，不许静默延长，也不许把未清零当已完工。
- **每项检查独立进程 + 新鲜 profile**：同一页面在各自 headless 实例里跑，互不继承 Cookie/缓存/已登录态——**检查之间不能共享状态**，否则第二次检查拿到的是第一次改过的世界。
- **门禁必须在"真实浏览器 + 真实构建"上跑**：框架站点要指到 dev server 或 dist 产物，**产物每次先重构建再门禁**，否则这一轮修的是旧构建。
- **"改过的 kit 要能被检出"**：页面从素材目录加载的文件若与技能自带副本不一致（忽略空格/引号/分号/逗号这类格式化差异），判为 kit-edited——把"偷偷改了基础件"从观感问题变成可判定项。
- 判据：**没有 FAIL 清单和轮次计数的"再改改"，是打磨的幻觉**——它既不收敛也不结束。
## r699A 下沉：把"太空/溢出"变成数值判据——空区 35%/50% 两档、320 宽查越界、无脚本再加载一次（来源：同上 `references/gate.md` 检查清单段，2026-11-08 实拉）

- **空区（empty-area）用占容器比例分两档**：**>35% 记 WARN、>50% 记 FAIL**——"这一屏看着空"从审美判断变成可复算的数字，且阈值分档让告警不淹没真故障。
- **越界（off-viewport）要在最窄宽度上走一遍**：除了常规 390，另在 **320** 走一遍，任何超出屏幕的元素都记——**溢出在窄屏才暴露**，只看 1440/390 会漏掉窄机。
- **无脚本复检（hidden-content）**：**关掉脚本再加载一次页面**，检查依赖 JS 才出现的内容——脚本失败时的降级形态本身是交付质量的一部分。
- **移动端两条硬判据**：元素相互碰撞（collide）与触控目标尺寸（tap-size ≥44×44）由 390 宽那趟直接量，不靠肉眼。
- 判据：**能被量出来的缺陷，不要写成形容词**——"有点挤"没法验收，"390 宽下 tap-size 38px"可以。
