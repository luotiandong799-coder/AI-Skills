# wb-execute-discipline（执行纪律：覆盖零省略，失败不放弃，错不过三）

来源：用户 2026-09-13 三条原话指令（当日学习循环实测提炼）：
1. **"我让你打开的都必须全部学完 一个都不能少"**
2. **"失败了你要继续进去学习 不能失败了就放弃"**
3. **"如果失败2次以上要思考为什么错 不能一直错误的方式进行下去 然后纠错改正优化以后不再一样错"**

## 〇、先查 GitHub 再动手：现成优先，能改就不从零写（用户 2026-09-16 规则）
**任何工作任务开始前**，先做一步 GitHub 复用检查（用户原话："工作任务先看 GitHub 有没有现成的或者差不多拿来可以改的"）：
- 搜索关键词 = 任务的核心动作 + 领域（如"agent skill document summarize"、repo 名 + 能力词），用 general_search / GitHub Search 代拉，找：**现成实现**（正好是这个功能）或**相近实现**（差不多的，可改造成本低）。
- **判定优先级**：有现成的直接复用 → 有差不多的 clone 下来改 → 都没有才从零写。复用优先于重写，和"重复功能不重复投入"同一原则。
- 复用检查结果留痕一行：找到什么（repo 链接）/ 判不判可改（为什么）/ 最终选择（复用 / 改造 / 自写）。找不到也留痕"已查无复用"，不跳过这一步。

## 一、覆盖零省略（原则一）
- 用户点名过的**每一个**目标（站点 / 仓库 / 文件 / 清单项），本轮都必须**真实执行、真实评估**：
  - 不得用"每轮抽 N 个轮换"代替全表
  - 不得用"上轮已做过 / 已评估过"代替本轮实做（结论必须来自本轮）
  - 不得以"预计无价值"为理由预跳过——判定必须来自实做后的证据
- **"完成"的判定** = 真实执行 → 逐条评估 → 有产出就落地 / 无产出记录判据。三项缺一不算完成。
- 目标清单要**显式列出并逐项打勾留痕**，不靠脑子记；漏项 = 违规。

## 二、失败持续攻坚（原则二）
失败（访问失败 / 超时 / 被拦 / 报错）**不等于放弃**，按路径阶梯逐级换路：
1. **直连**（WebFetch / curl 默认路径）
2. **换端点**：镜像站、备用域名、API/JSON 端点、无 www 域名
3. **浏览器渲染**（agent-browser / playwright，可过部分 bot 检查）
4. **替代入口**：站点官方镜像、缓存页、聚合页
- 每级试过仍失败才可标注"本轮未达"；**只要还有一级路没试，就不许写"放弃 / 跳过 / 略过"**。
- 失败必须**如实留痕**（哪级、什么错误、何时），失败项不算完成，下轮优先补。

### 换路之前先辨错误类型（决定"重试有没有意义"）
来源：Make Help Center `exponential-backoff` / `error-handlers`（2026-09-14 经代理实访）+ 本轮实测样本。

**别把三类失败混成一类处理**——同一路径原样重试只对其中一类有意义：

| 类型 | 特征 | 正解 |
|---|---|---|
| **瞬时（transient）** | 连接超时、5xx、限流、DNS 抖 | **退避后重试有意义**：逐次拉长间隔（1m→2m→10m→30m…），并设**次数/总时长上限**，到顶停手 |
| **确定性（deterministic）** | 403 / 404 / 认证失败 / bot 拦截 / 域名停放 | **重试无意义**（同样是 403，重试一万次还是 403）→ 直接换路（换端点 / 代理 / 认证）或判"本轮未达" |
| **空壳（empty shell）** | **HTTP 200 但正文为空 / 只有 JS 壳 / 停放页** | 也属"没有内容"：**判据要看内容，不只看状态码** |

- **状态码不是全部证据**：本轮实测 `fullstackskills.com` 返回 **200 但正文只有 114 字节**（GoDaddy 停放页）；`chatgpt.com/gpts` 200 / 528KB 但剥掉 script 后正文 **39 字符**（纯 JS 渲染壳）。**只看 200 就记"已实访"是假完成**——要落地一次正文提取（长度 / 关键词 / RSC payload）再判。
- 反过来，**403 也可能只是"路径不对"而不是"内容不存在"**：本轮 `help.make.com` 直连 403 → 换代理后 200 且捞到真方法论。所以 403 的正确反应是**换路**，不是"判死"也不是"原样重试"。
- 判定顺序：**先辨类型 → 再选动作**。瞬时才重试；确定性换路；空壳换提取方式或判无内容。
- **第四种混淆：把"失败"当"合法的空"**（来源 trailofbits second-opinion v2 重写，2026-09-15 实拉）：*preserve Git errors instead of interpreting them as an empty diff*——命令非零退出 / 报错时，产物是"没拿到"，不是"拿到了空结果"。"git diff 为空"是有效结论（没改动），"git diff 执行失败"是证据缺失——两者动作完全不同（前者收工，后者修采集）。判据：**空结果要有"采集过程本身成功"的证据支撑；没有，就按失败走换路，不许按空走收工。**

### 重试前重播种干净骨架：不许在毒化产物上续跑（来源：william-london/ownframework-loop `reseed poisoned semantic retries`，2026-09-15 实拉）

语义校验失败（格式错 / schema mismatch / 结构毒化）后的重试，**不从失败产物上修补，也不把失败产物当起点**：

1. **先归档毒化产物**（可诊断、可追责），再重试——直接覆盖 = 丢证据
2. **用带固定字段的原始模板重播种（reseed）**：schema、run_id、身份、哈希等 fixed fields 由框架预填，重试方不得重写
3. **禁止模型编造替代身份值**：固定字段在进程启动时就畸形 → 停下上报**传输损坏**，不是"帮忙补一个看着合理的"
4. **顶层键集封闭（fail closed）**：出现模型自创的顶层键 = 整体判无效，不是忽略多余键
5. **信封校验 ≠ 就绪校验，分两步**：干净的空骨架**有意**留空语义行——"信封合法"（结构/身份对）与"就绪可交付"（内容填满）是两个独立判定；混成一步会把"合法的半成品"误判为"无效"，或把"没填的骨架"误判为"就绪"
- 与重放幂等配套：重放沿用原产物路径，重播种**必须换新产物**（旧产物已毒化归档）——先判是重放还是重试，再选沿用还是重播种。

### 重试的幂等纪律：重放是同一动作，不是新的一次

来源：GitHub `william-london/ownframework-loop` `docs/STATE_MACHINE.md` + `.agents/skills/of-loop-build`（2026-09-14 增量）：*"A replayed claim is the same pass and MUST NOT increment budget."*

**崩溃后重放的（replay）动作，是同一个动作，不得二次计数 / 二次扣预算 / 二次写证据。** 区分三种情况，别混为一谈：

| 情况 | 是不是同一次 | 处理 |
|---|---|---|
| **重放**（崩溃恢复、同一 pass 重新认领） | 是 | **沿用原路径与计数**，不新增一轮、不重复扣额度 |
| **重试**（动作确实失败、要再做一遍） | 否 | 计一次新的，纳入重试预算 |
| **新一轮**（收到新输入 / 上一轮有产出） | 否 | 正常推进 |

- **判定问一句：这次执行有没有产生新的"东西"？** 没有（只是把上次没跑完的补完）→ 是重放，不计数。
- 重放必须**沿用同一结果路径**，不另开目录——另开目录会让"哪份是最新的"变成悬案。
- 反模式：崩溃恢复后重新认领，预算计数 +1（额度被崩溃吃光）；重放时生成 `result_v2.json` 而不是写回原位。

## 二·五、失败处理是独立构件，不是散落的 try/catch

来源：n8n Docs《Handle errors gracefully》（2026-09-14 实访 Markdown 原文）。

**把失败处理外置成一条可复用的一等通道**（独立的错误处理流程，多个任务共用），而不是在每个步骤里各写一份兜底：

- 每份内联兜底都是"只在这里有效"的一次性代码，**改起来要改 N 处、验证起来一处都没验证过**；外置后只写一次、只测一次、处处生效。
- **同一个错误通道服务多个任务**——失败模式往往相似，重复实现没有收益。

**错误负载必须自带定位信息**，最小四项：
1. **哪个环节失败了**（节点 / 步骤 / 子任务名）
2. **可回访的执行标识**（执行 URL / 运行 ID）——没有它，事后无法还原现场
3. **这是否是一次重试**（`retryOf`）——重试掩盖原发错误是定位失败的头号原因
4. **原始错误与堆栈**，不做美化裁剪

**不同阶段的失败，能拿到的信息不一样**：起步阶段（触发器 / 初始化）失败时，执行上下文尚未建立，只有触发侧信息；后续步骤失败时才有完整执行上下文。**先判断失败发生在哪个阶段，再决定能从错误里问出什么**——用后段的信息结构去解读前段的失败，只会得到"字段缺失"的假象。

## 二·六、限流要预防，不要只靠重试；循环必须有显式终止条件

来源：n8n Docs《Loop》（2026-09-14 实访 Markdown 原文）。

**退避重试是补救，分批是预防——两者都要，但预防更便宜。** 明知道下游有速率限制还一次性全量灌进去，等于故意制造失败再慢慢重试。

- **主动分批**：大批任务切成批（可调批大小）逐批处理。批大小是**效率与被打回概率之间的旋钮**：批太大撞限流，批太小程序开销占比高。
- **按目标调参**：外部 API 按它的限流窗口定批大小；本地批量操作按内存/时间定。
- **别把"重试成功"当成"做对了"**：靠重试扛过去的流程，耗时和不确定性都被隐藏了，一遇更严的限流就整体雪崩。

**循环必须写清终止条件**：
- 两类循环分开看——**计数循环**（处理完所有项就停，天然有界）与**条件循环**（直到满足某条件才停）。
- **条件循环必须有显式终止判据**，且判据要能被验证（"跑 X 次还没满足就停手上报"）。没有上界的条件循环 = 潜在的无限执行。
- 与 §五「重试预算」（`wb-spec-driven`）同源：**任何"再来一次"的结构都要有次数/时长上界**。

## 二·七、缺信息要"结构化索取"，不要猜也不要直接失败

来源：MCP 官方《Understanding MCP clients》Elicitation（2026-09-14 实访）：服务端可以在执行中**反过来向用户请求特定信息**（例如订票前询问座位偏好、房型、联系电话）。

- **执行方不是只能被调用，它可以回问。** 但回问必须是**结构化的**（明确要哪个字段、什么格式、为什么需要），不是"你再说说"。
- **三种劣质替代**：① 猜一个默认值往下跑（把猜测固化进结果）② 直接报错退出（其实只差一个字段）③ 把所有可能的信息预先全部要一遍（把成本转嫁给每次调用）。
- 判据：**这一步缺的是"必需且只有对方知道"的信息吗？** 是 → 停下来问这一项；不是 → 用默认值并记录，或直接失败。
- 与 §一「覆盖零省略」不冲突：缺信息停下来问**一项**，不等于跳过目标；**问完必须继续把事情做完**。

### 补齐信息后重试原请求：必须回显状态令牌（requestState）
- 来源：同页 Elicitation 的 MRTR（Multi Round-Trip Requests）模式（2026-09-15 实访）：服务端因缺信息暂停时，响应里带 `InputRequiredResult`（含索取项 + **`requestState` 状态令牌**）；客户端收集完输入后**重试的是原请求**，且必须**附上收集到的回答并原样回显 `requestState`**——服务端靠它确认"这次重试续的是哪一次暂停"，而不是当作全新请求。
- 迁移到长链路任务：因缺信息/外部事件暂停的步骤，恢复时**把暂停时服务端/上游给出的状态带回**（任务 ID、断点令牌、上一轮的中间状态哈希），不要只把"补充的信息"带回去就当续上了。
- **不回显状态的两种事故**：① 上游把它当新请求从头再跑（重复扣款/重复发信/重复计数）；② 上下文串台（把 A 暂停的输入续到 B 的会话里）。
- 与「重放幂等」的关系：重放幂等管"同一动作重复执行只算一次"（读侧防护），本条管"恢复执行时主动证明续接正确"（写侧协议）——两者配套，缺一不可。

## 二·八、检查工具要支持"连一次、查一项、退出"

来源：MCP 官方《Inspector CLI client》（2026-09-15 实访）：CLI 模式每次运行**连上服务器 → 执行你点名的那一个方法 → 打印结果 → 退出**。

- **这个形态才能进 CI**。一个必须保持会话、需要交互才能得出结论的检查工具，永远只能被人手动跑。
- 落到本地的验证脚本：**接受一个明确的目标（"查哪一项"）作为入参，跑完输出结果并退出**，不要做成"进去之后选菜单"的交互程序。
- 判据：**这条检查能不能写成一行命令放进管道？** 不能 → 它不会被经常跑，等于没有。
- 与 `wb-artifact-verification`「验证要能脚本化」同源：那条讲**为什么需要**，本条讲**接口长什么样**（单次、单目标、可退出）。

## 二·九、Agent 是一等实体：define once, use anywhere（来源：n8n 官方 blog《Introducing n8n Agents》2026-09-25 + Activepieces Changelog 2026-09 双源印证实拉）

n8n 把 agent 从"工作流步骤里的一个设置包"升级为独立可命名实体：定义一次，即可在聊天界面、工作流节点、Slack 消息、定时任务里复用同一个实例；Activepieces 同期发布同形态（agent 可命名 / 简报 / 对话 / 一句文字创建）。与"工作流内嵌 AI Agent 节点"是两种东西：

- **实体 vs 节点**：节点是"流程中的一步"，实体是"可跨入口调用的独立能力单元"。同一个 agent 定义一次，在 chat / 定时 / 消息平台 / 其他工作流节点都能挂载。
- **判据**：要复用的"人设 + 工具集 + 简报"是否跨多个入口出现？是 → 提升为独立 agent 实体，不复制配置；配置复制是这类重复最常见的来源。
- **提升层**：工作流 / 可复用 Skill。触发词：agent 一等实体、define once use anywhere、agent 复用、跨入口挂载、实体 vs 节点。

## 二·十、Harness 层管执行治理，MCP 层管连接：先分两层再谈编排（来源：36氪《DeepSeek 的 Harness，为何是一头黑色鲸鱼？》2026-08-14 + 七牛云《DeepSeek Harness + MCP 开源部署指南》2026-09-21 实拉）

MCP 与 Harness 不在同一层：MCP 是"连接"标准（统一 AI 应用与外部数据 / 工具 / 工作流的接法），Harness 负责更上层的**执行治理**——何时把工具交给模型、调用前是否需要审批、结果如何写入会话、失败后是否重试、Agent 何时派出子任务、在什么条件下停止。把执行治理误放进连接层（或反之），编排就退化成"在工具里硬塞流程"。

- **治理清单**：工具交接时机 / 调用前审批 / 结果写会话 / 失败重试 / 子任务派发 / 停止条件——六项都属于 Harness 层职责，不属于 MCP 协议。
- **判据**：新增"该不该执行 / 何时执行 / 失败怎么处理"的规则时，落点应在执行治理层（编排、钩子、审批门），不要塞进工具描述或协议参数。
- **提升层**：工作流 / 架构。触发词：Harness、执行治理层、MCP 只管连接、工具交接时机、停止条件、调用前审批。

## 二·十一、gated tool：工具级人工审批闸门，用确定性控制替代提示词护栏（来源：n8n HITL for AI tool calls 文档 2026-09-30 实拉）

把高风险工具声明为 gated：AI 可以发起调用意图，但**未经人工显式批准不执行**；批准动作在工具层强制，不依赖模型的提示词遵守。与"提示里写'这个工具要小心'"是两种安全模型：

- **提示词护栏 vs 物理闸门**：前者靠模型记住规则（可被注入 / 遗忘绕过），后者在执行链路上设卡（批准前不触发副作用）。
- **判据**：这个工具一旦误调用的代价是否不可逆 / 不可撤回？是 → 上 gated（人工批准才能执行），而不是在提示词里叮嘱；提示词叮嘱只作为闸门之外的补充说明。
- **提升层**：工具 / 工作流。触发词：gated tool、HITL 工具审批、执行前批准、确定性控制替代提示词护栏、不可逆工具。

## 三、失败 ≥2 次必根因诊断（原则三）
同一目标失败 **2 次及以上 → 立即停手，禁止第三次原样重试**：
1. **写假设**：为什么错？（缺依赖？子进程被杀？目标本身不可达？参数/顺序错？前一步污染？）
2. **最小探针验证假设**：查安装态 / 查进程残留 / 单独测可达性 / 退最小参数——用证据否掉或证实假设，不靠猜
3. **纠正后走新路径**：改的是根因（缺 Chromium 就先装，不是延长超时硬冲）；验证新路径通了再继续
4. **根因 = 环境结构性限制**（如沙箱禁 GUI、需 VPN、需人工装依赖）→ 留痕标注"非重试可解 + 解法归属（用户 / 手动步骤）"，不无限重试烧上下文
- 纠错后把教训写进相关技能（如浏览器技能补"前置检查"），**保证同类错不再犯**——这是原则三的终点，不是修完就完。

## 子 agent 上下文切片（scope context per agent）：每个子 agent 只拿任务相关切片，不给全量对话历史（来源：n8n Production AI Playbook《Complex agent patterns》2026-09-25 实拉，r540B 落地）

多 agent 编排的最大浪费不是工具费，是**把整份对话历史喂给每个子 agent**。正确做法是按角色裁剪上下文：billing 专家只拿账务相关切片，不给全量会话记录；同时**按任务选模型**（分类/路由/简单提取用轻量模型）——模型选择是配置决策，不是架构变更。

- **判据**：① 派发子任务时先问"它需要知道哪些，不需要知道哪些"——上下文切片按**任务边界**切，不按"方便"切；子 agent 的 prompt 自含其任务所需的全部事实，其余一概不给。② 工具描述要同时写清**负责什么 + 不负责什么**——"不负责什么"决定路由边界，缺了它子 agent 会把不属于自己的请求也接走。③ 模型选型跟着任务难度走：路由/分类/提取这类低难度动作是配置项，换模型不改架构。
- **提升层**：工作流 / 上下文治理。触发词：scope context per agent、上下文切片、按任务选模型、工具描述不负责什么、子 agent 只拿任务相关。

## 工具数量阈值 15-20：一 agent 工具超过 20 个选得比 5 个差；语义工具记忆用检索替代全量常驻（来源：n8n.it《n8n AI Agent 实践》+ wearetandem《Créer un agent IA avec n8n》+ Oracle×DeepLearning.AI《Agent Memory》课程，2026 实拉，r540B 落地）

两个独立来源印证同一实证：**15-20 个工具以上，模型开始混淆工具选择**；"一 agent 20 个工具选得比 5 个工具差"——每多一条工具描述，选择决策被稀释一分。解法不是少装，是两条：① 超过阈值就**拆 agent**（orchestrator 快模型 + specialist 强模型分割工具面）；② 工具当**程序性记忆**用——向量索引、推理时**语义检索只取上下文相关工具**，而不是全量常驻选择面。

- **判据**：① 工具清单超过 15-20 条且选择开始失误 → 拆 agent 或上语义工具检索，别在提示词里强调"认真选工具"（提示词护栏治不了选择稀释）。② 工具描述写"什么时候用"优于写"它是什么"——描述质量第一参数，每条描述都参与稀释，短的、边界清楚的描述最省。③ 工具数量治理与上下文预算联动：可见工具越多，schema 隐性成本越高——两条账一起算。
- **提升层**：工具 / Agent 编排。触发词：15-20 工具阈值、工具选择稀释、一 agent 20 工具比 5 个差、语义工具记忆、工具当程序性记忆、推理时检索相关工具、拆 agent 分工具面。

## 权限档谱 permissions presets：按场景预置六档权限档位，替代逐工具写 scope（来源：Dify Marketplace Better E2B Sandbox 插件 2026-09 实拉，r540B 落地）

沙箱/工具面的权限不该每次逐工具配，而是预置**按场景选档**的档位谱：`allow_all`（完全放行）/ `dev_standard`（接受编辑）/ `dev_webfetch_allowlist`（web 取指白名单）/ `ci_build_test`（构建测试不问）/ `review_readonly`（评审只读）/ `plan_mode`（规划不执行）。选档在**调用前**做，档位即权限契约。

- **判据**：① 同一工具面在不同场景（开发/评审/CI/规划）需要的权限档不同——预置档位让"选档"成为配置决策，而不是每次运行临时授信。② 档位是**默认值不是上限**：plan_mode 只读规划、review_readonly 评审只读，写动作必须升档；档位描述写进工具面文档，拒绝"默认最高档"的惰性。③ 与 §per-tool 最小权限 的分工：那条管"单个工具给多少权"（粒度），本条管"整个运行场景用哪个档"（形态）——档位选错时逐工具权限救不了，先对档再谈工具。
- **提升层**：工具 / 安全。触发词：permissions presets、权限档谱、allow_all、dev_standard、ci_build_test、review_readonly、plan_mode、按场景选档、档位默认值不是上限。

## 缓存变量注入调试：改中间变量只跑下游，不重跑昂贵上游（来源：Dify Variable Inspector / Dify 1.5.0 官方博客 + deepwiki 文档 2026 实拉，r540C 落地）

调试工作流/多步管道时，**测试边界 case 不必重跑昂贵的上游**（LLM 调用/API/数据库查询）。Dify 的 Variable Inspector 模式：执行到目标节点 → 打开变量面板 → 直接修改缓存变量值（支持 JSON 编辑复杂类型）→ 只运行下游节点验证，下游用改过的值继续执行。

- **判据**：① **断点注入**——"执行到 N → 改中间值 → 只跑 N 之后"，与整条重跑是两套成本；LLM/API/DB 是贵节点，反复整条重跑测边界 = 为一次假设付全程成本。② 变量命名纪律：**小写下划线、无空格、case-sensitive**——`UserName` 与 `user_name` 路径引用不匹配是静默失败；引用上游变量走**变量选择器**插入，不手打路径。③ 与 §工具结果断言层 的分工：那条管"调用后结果不对劲怎么处理"，本条管"调试时如何最小成本复现下游行为"——怀疑下游逻辑时先注入中间值隔离上游变量，而不是带着上游整条重跑。
- **提升层**：工作流（调试效率）。触发词：Variable Inspector、缓存变量注入、断点注入、只跑下游节点、不重跑昂贵上游、变量名小写下划线、case-sensitive、变量选择器插入、边界 case 测试。

## eager_input_streaming：工具参数边生成边流入，大 payload 少一轮往返（来源：anthropics/skills 官方 claude-api SKILL.md + Claude Agent SDK 文档 2026-10-12 实拉，r540C 落地）

流式请求中，自定义（client-defined）工具设 `eager_input_streaming: true`，**工具输入还在生成时就边生成边流入**——大工具 payload 不必等模型把完整 JSON 写完后端才收到，减少长输入请求的往返等待。配套事实：`content_block_start` 事件在工具块开始时即携带 tool 的 `name` 和唯一 `id`，用于后续拼回 `tool_result`；工具输入 JSON 是分段到达的（partial JSON），不能假设一次拿全。

- **判据**：① **长输入工具默认开 eager 流式**——payload 大时等完整输入再传输是纯浪费；用户工具与平台工具的区别在 SDK 里明确（client tools 才配）。② 分段 JSON 是常态：流式工具调用要按块累积解析（content_block_delta 累积到 block_stop），**先记 name+id 再等块完成**，不要假设单事件即完整。③ 与 §重试分两类管 的分工：那条管"失败后怎么办"，本条管"传输阶段怎么省"——流式省的是延迟，不是正确性；拼错 tool_result 比慢更糟。
- **提升层**：工具 / 工作流（流式延迟治理）。触发词：eager_input_streaming、工具输入边生成边流入、client tools、partial JSON、content_block_start name id、分段累积解析、长输入防超时、流式工具调用。

## 失败分类决定重试策略：瞬时型自动重试 / 资源型不重试 / 逻辑型不盲重试（来源：n8n community 官方错误处理 + Pipedream 官方 settings/mech.app 运行时 + n8nlab 成本量化 2026 实拉，r540C 落地，与 §重试分两类管互补——那条管"transport 与 tool 分开重试"，本条管"按失败类型决定要不要重试"）

重试不是默认动作，**失败类型决定重试策略**，三类分治：

- **瞬时型**（网络 blip/429/503）：自动重试，指数退避+jitter；平台级实证是 step 级 3 次（1s/2s/4s）后错误传播——**重试边界在 step 级，全失败则下游不执行**（n8n node 级 Retry On Fail 管这类，workflow 级 Error Trigger 管剩余：告警/DLQ/记录，两层分治不是一层）。
- **资源型**（OOM/超时）：**不自动重试**——重试=再烧一遍资源，先调配置（加内存/加超时）而不是重跑（Pipedream 官方明确 OOM/timeout 不自动重试）。
- **逻辑型**（schema 变更/业务错误/参数错）：**不盲重试**——Retry On Fail 是盲的，不分析失败原因；API 改了响应 schema 重试 3 次只会烧钱（$0.01/调用 × 1000 条 × 激进重试 = 快速烧完预算），先查失败原因再决定修什么。
- **重试前先查幂等**：前 8/10 步已触发时 naive retry 会发重复邮件/建重复 CRM 记录（n8n 实证）——先确认"这次操作是否已生效"再决定是否重调。
- **判据**：① 接到失败先**分类**（瞬时/资源/逻辑）再决定动作——分类错了重试策略就错了。② 资源型失败的修复动作是调配置不是重跑；逻辑型失败的修复动作是查根因不是重试。③ 自定义退避循环：端点不返回 Retry-After 或需更保守退避时，用 Set/If/Wait 自建循环，不受平台默认 5 次/5 秒限制。
- **提升层**：工作流（重试策略）。触发词：失败分类、瞬时型重试、资源型不重试、OOM 不自动重试、逻辑型不盲重试、盲重试烧钱、Retry On Fail 是盲的、两层错误处理、node 级 vs workflow 级、step 级重试边界、重试前查幂等、自定义退避循环。

## 错误处理器五指令语义 + Incomplete Executions 常开 + 连续错误禁用阈值：错误不是"重试或放弃"二选一，而是五动作谱（来源：help.make.com/fix-errors-and-warnings + academy-content.make.com/intermediate-errors 2026-10-12 实拉，r541A 落地，与 §失败分类决定重试策略互补——那条管"要不要重试"，本条管"错误命中的 bundle 怎么处置"）

- **五条错误处理指令语义**：**Resume**（以替代值继续）/ **Ignore**（跳过该 bundle 继续处理其余）/ **Rollback**（撤销）/ **Commit**（确认已做）/ **Break**（停当前 bundle 继续下一个）。**Ignore 最常用**：10 个数据 1 个错，其余 9 个照常处理，错的那个单独记录后手工——不要因为 1 个坏数据把整批停在原地。
- **连续错误达到阈值才禁用调度**：普通错误累积 N 次才停用场景，**致命错误（InconsistencyError）即时禁用**——致命错误重试无意义，直接停发防污染。
- **Retry handler 参数**：自动同 action 重试最多 3 次、延迟 5/10/15 分钟递增，仍失败落 Incomplete Executions。**Incomplete Executions 建议常开**——像安全带：保存失败 run 的 blueprint+数据+日志，改好模块设置后可**从失败模块重放**，不用整条重跑。
- **死信模式**：每个错误路径加"记录行"（错误信息+时间戳+原始输入落表），错误不静默消失；指数退避 + jitter（0-30% 随机）防重试风暴。
- **判据**：① 错误处理先选指令再写逻辑——五个指令是处置谱系，默认不是"整条失败"，是 Ignore 让其余数据继续。② Incomplete Executions 是重放入口——失败 run 的蓝图/数据/日志被保存，修复后可定点重放；关掉它等于把失败现场扔了。③ 致命错误用阈值外的即时禁用——连续计数只防"偶发噪声刷屏"，InconsistencyError 一票停发。
- **提升层**：工作流（错误处理）。触发词：Resume Ignore Rollback Commit Break、错误处理器五指令、Ignore 最常用、坏数据不阻塞整批、连续错误禁用阈值、InconsistencyError 即时禁用、Retry 5/10/15、Incomplete Executions 常开、从失败模块重放、死信记录行、jitter 防重试风暴。

## Pipedream 组合约束三件套：dedup 三策略优先 + trace_id 跨重试稳定 + platform axios 调试性（来源：pipedream.com/docs + downloads.flaviocopes.com/practical-debugging.pdf 2026-10-12 实拉，r541A 落地）

- **每执行 trace_id 跨自动重试稳定**：同一原始事件的重试共享同一 trace_id——排障先按 trace_id 聚合重试序列（哪次触发、每次结果），再谈修复；无 trace_id 关联的多次重试在日志里是孤岛。
- **内置 dedup 策略 unique/greatest/last 优先于自定义**：轮询 source 用 `$.service.db` 缓存最近处理 ID/timestamp、增量扫描（scanDeltaItems 生成器）；**有内置去重就别写自定义去重**——内置按事件 ID 去重是平台保证，自定义去重是自担正确性。
- **HTTP 一律用 `@pipedream/platform` 的 axios**：标准 axios 对 4XX/5XX **不返回可调试数据**；platform axios 保留状态码+响应体，调试时能看失败响应。
- **调试器 vs 打印判别**：打印调试每问一次=一次编辑+重跑循环；调试器可停在"扩散前冻结时刻"。**条件断点**：500 次跑 1 次失败时设 `item.price===undefined` 只在可疑处停。回归测试拿最小失败输入永久保留——"无测试的修复是临时修复"。日志禁记整对象/凭据（记 error.message+identifier）。
- **判据**：① 重试排障先聚合 trace_id 再下结论——把多次重试当独立事件排查会重复归因。② 去重优先信任平台内建——unique/greatest/last 是声明式去重，自定义去重逻辑出错时没人替你兜底。③ 调试优先选断点而非打印——"改代码-重跑-看输出"循环在长任务里成本高，断点冻结时刻更早暴露状态。④ 与 §失败分类决定重试策略 的分工：那条管"按失败类型决定动作"，本条管"重试之间如何关联、错误如何被观察"。
- **提升层**：工具 / 工作流（可观测性）。触发词：trace_id 跨重试、重试序列聚合、dedup unique greatest last、scanDeltaItems、platform axios、4XX 5XX 可调试、条件断点、最小失败输入回归测试、无测试的修复是临时修复、日志禁记整对象凭据。

## Dify 异常处理三选项 + Partial success 局部成功 + 重试优先于异常分支：节点级兜底策略要显式选，不能留默认（来源：legacy-docs.dify.ai/zh-hans/guides/workflow/error-handling + dify.ai/blog/dify-1-5-0 + agenticindex.io/change-log/dify 2026-10-12 实拉，r541B 落地，与 §错误处理器五指令互补——那条管"错误命中的 bundle 怎么处置"，本条管"节点自身配置哪层兜底、流程状态怎么记"）

- **异常处理三选项必须显式选择**：每个节点可配**无**（异常即失败，走流程终止）/ **默认值**（预定义异常信息替代输出，流程继续）/ **异常分支**（失败走备用路径，如降级模型/缓存兜底）。判据：不配 = 选了"无"——异常直接杀死整条流程；写文档/部署流程时把"每个易错节点的兜底选项"列成检查表，不许留默认。
- **Partial success 是独立状态**：节点异常但启用异常机制、整体流程仍正常完成时，流程状态记 **partial success**——不是 success 也不是 failed。判据：按"部分成功"而非"成功"统计成功率——把 partial 当 success 会掩盖"一直靠兜底在撑"的真相；把 partial 当 failed 会误报系统故障。
- **重试优先于异常处理**：同节点同时开启重试与异常分支时，**先重试、重试耗尽才走异常机制**。判据：兜底是最后防线不是第一选择——先给瞬时失败一次机会，再降级；顺序写反会让兜底路径成为常态路径。
- **Workflow Node Locator（Dify 1.16.1）**：运行日志里的错误直接连线到画布对应节点——日志定位问题从"人工对照节点 ID"升级为"错误即跳转"。判据：日志与拓扑的联动是调试效率杠杆——有跳转能力的平台，排查从点击开始而不是从搜索开始。
- **提升层**：工作流（错误处理）/ 工具（平台调试能力）。触发词：异常处理三选项、默认值兜底、异常分支、Partial success、局部成功、重试优先于异常分支、Node Locator、错误连线画布节点、兜底是最后防线。

## Incomplete Executions 机制补充：不开就静默丢 bundle，自动重试是 scenario 级不是模块级（来源：help.make.com/manage-incomplete-executions + academy-content.make.com 03 + automatelab.tech 2026-10-12 实拉，r541C 落地，与 §错误处理器五指令互补——那条管"错误命中的 bundle 怎么处置"，本条管"重试队列的开关后果与粒度边界"）

- **不开 Incomplete Executions 时 Break 静默丢 bundle**：原文「Without this flag the Break handler has nowhere to queue the retry and silently drops the bundle」——Break 重试指令的落点是 Incomplete Executions 队列，**关掉存储=重试无处排队=静默丢弃**；错误看起来"处理了"实际 bundle 蒸发。
- **自动重试作用于整个 scenario，不是单个模块**：scenario 设置的自动重试对整条流程生效；**要模块级粒度必须用 error handler + router 在流程内部自己实现**（error handler 处理单个模块，router 分流）。判据：按"要重试的粒度"选实现——整条重试用 scenario 设置，单模块重试用 error handler，别指望 scenario 设置做模块级。
- **Break 的 retry 参数是开关**：retry=true 才进重试队列；false 时直接报错停止。**Rate Limit 场景**：Break 模块可指定等待时间后重试（60 秒等待通常可解除限流）。
- **重试成功标记 Resolved 并停止**：Incomplete Executions 自动重试成功 → 标记 Resolved 停止重试；仍失败 → 保留在 Incomplete 供人工 Retry selected（批量重试选中项，状态 Scheduled→In Progress）。判据：重试队列不是无限循环——成功即收敛，失败留人工。
- **判据**：① 重试指令的落点必须先存在——配 Break/Retry 前先确认 Incomplete Executions 已开，否则指令是空转。② 粒度按层选——scenario 级设置覆盖整条，模块级靠 handler+router，两层各管各的。③ 与 §错误处理器五指令的分工：那条管"五动作选哪个"，本条管"重试队列本身怎么配、粒度到哪"。
- **提升层**：工作流（错误处理）。触发词：不开就静默丢 bundle、重试无处排队、scenario 级重试、模块级粒度、error handler router、Break retry 开关、Rate Limit 等待重试、Resolved 停止重试、Retry selected 批量重试。

## handoff 交接点双端哈希：内容哈希校验交接、diff 定位发散（来源：jdforsythe.github.io/10-principles observability + techdailyshot.com 2026-10-12 实拉，r541C 落地，与 §重放幂等互补——那条管"失败重来"，本条管"交接本身是否无损"）

- **每个交接点 hash 两端产物**：Agent A 输出 → Agent B 消费前，A 端与 B 端各算一次内容哈希——**哈希一致=交接干净；不一致=消息丢失/被改写**。判据：交接的完整性校验不能靠"B 收到了"（收到≠无损），哈希对比把"交接是否无损"变成可断言。
- **哈希使 diff 定位发散点**：两条 pipeline 跑出不同结果时，按阶段比对各交接点哈希——**第一个哈希不一致的阶段就是发散点**，不用整条重查。判据：多阶段链路排障从"逐阶段哈希对比"开始，先把发散范围缩到一个交接点，再查该点内部。
- **结构化日志 JSON 而非 printf**：非结构化文本日志无法按字段检索/聚合；结构化字段（trace_id/request_id/session/step/event）让日志可按交接点查询。判据：可观测性的前提是字段化——没有字段的日志是死数据。
- **判据**：① 交接点=校验点——每个 agent 间的产物传递处放一个哈希断言，泄漏/改写/乱序都会被当场抓住。② 发散点定位用哈希阶梯——先找到第一个不匹配的交接点，再深入该点，别在整条链上瞎猜。③ 与 §trace_id 跨重试 的分工：那条管"一次执行的多重试怎么关联"，本条管"两个环节之间产物是否无损"。
- **提升层**：工作流（可观测性）。触发词：handoff 哈希、交接点校验、双端哈希、消息丢失断言、diff 定位发散、哈希阶梯、结构化日志 JSON、交接点即校验点。
