## 失败恢复有两条硬边界：回滚资格按「是否事务模块」封闭枚举，且重试耗尽可级联改变自动化生命周期（来源：help.make.com/rollback-error-handler.md 8,865B + exponential-backoff.md 2,779B + docs.n8n.io/.../executions.md，2026-10-01 r348A 独立 curl 实拉）
- 原文：①「Modules that support transactions are labeled with the 'ACID' label.」②「Auto-commit enabled — Only the module that produced the error can revert its changes.」③「Auto-commit disabled — All changes made during the bundle's execution across every transaction-supported module can be reverted.」④「If the 8th attempt fails, Make disables scheduling of the scenario.」⑤第二证 `N8N_WORKFLOW_AUTODEACTIVATION_MAX_LAST_EXECUTIONS=3`。
- 判据：① **回滚范围不是「尽量回滚」，而是按模块是否事务（ACID 标签）封闭枚举** —— 非事务模块的改动失败后仍然留着。⇒ 任何「出错就回滚」的承诺都必须先回答哪些改动真的可回滚；把不可回滚的算进去，验收时会得到「回滚成功了但状态还是脏的」。② **提交模式反转回滚粒度**：Auto-commit 开=只有出错模块回滚；关=整个 bundle 跨全部事务模块回滚。粒度更粗的那一档不是更好，而是失败时影响面更大，要与业务的原子性需求对表。③ **重试耗尽不止是这次失败**：它可以直接改自动化本身（停用调度）。⇒ 排障「这条自动化怎么不跑了」时，先看是不是先前的重试耗尽把它关掉了，而不是查触发器与权限。
- 提升层：工作流。触发词：ACID 标签回滚资格、Auto-commit 反转回滚粒度、只有出错模块可回滚、重试耗尽停用调度、AUTODEACTIVATION。

## 同一个错误的默认处置会随调度形态分岔；重试资格要按错误类别封闭列举，不靠「看起来可重试」（来源：help.make.com/fix-rate-limit-errors.md 9,275B + docs.dify.ai/en/api-reference/guides/errors.md 3,157B，2026-10-01 r348A 独立 curl 实拉）
- 原文：①同一 `RateLimitError`（429）无 handler 时：定时触发=「pauses the next scenario run for 20 minutes」；即时触发=「reruns the incomplete execution from its start with exponential backoff」。②Dify：「Retry with backoff: `too_many_requests`, `500`, and network failures」vs「Don't retry as-is: validation errors (fix the request first), authorization failures, or quota errors (they won't clear until the quota does)」；`code` 是稳定分支键，`status` 只镜像 HTTP。
- 判据：① **跨调度形态的默认值不可假设一致**：同一个 429 在定时/即时两条路径上的默认动作完全不同（暂停 20 分钟 vs 从头指数退避）。⇒ 写重试/兜底策略时先问这条路径的调度形态是什么，否则同一种错误会得到两种完全不同的用户体验。② **重试资格要写成两张封闭清单**（可重试 vs 不可原样重试），而不是一个「是否重试」布尔：配额类错误在配额刷新前重试纯属浪费，鉴权/校验类不改请求重试必然重复失败。③ **分支键取稳定字段**：用业务 `code` 分支，不要用镜像 HTTP 的 `status` —— 后者会随传输层重映射漂移。
- 提升层：工具/工作流。触发词：429 定时暂停 20 分钟、即时指数退避、同错误分岔、重试白名单黑名单、配额错误不重试、code 稳定分支键、status 只镜像 HTTP。

## 背压要先分「丢弃式 / 阻塞式」两档并显式写出；限流的作用面按触发类型分轨（来源：pipedream.com/docs/concurrency-and-throttling.md + docs.n8n.io `/scaling/control-concurrency.md`，2026-10-01 r348A 独立实拉）
- 原文：①「fixed window throttling」、`limit=0` 即关队列、「exceeds the queue size, events will be lost」。②队列仅对 event-driven 生效，「excluding native HTTP or cron types」。③第二证：n8n 并发上限「applies only to production executions」，显式不含 manual / sub-workflow / error / CLI。
- 判据：① **背压有两档且代价相反**：丢弃式（队列满即丢事件，吞吐让位于内存）与阻塞式（反压上游，延迟换不丢）。⇒ 选型时先声明是哪一档；混着用会出现「既延迟又丢事件」的最坏组合，而日志上两者都只是「慢」。② **`limit=0` 这种取值要显式识别** —— 它不是队列无限，而是队列不存在，溢出直接丢。③ **限流/并发上限必须点名覆盖哪些触发类型**：只覆盖事件驱动、不覆盖 HTTP/cron/子工作流/手动/错误工作流是默认形态。⇒ 排「限流没生效」时先核对触发类型在不在作用域内；恰好漏掉兜底错误工作流与被复用子工作流，是最常见的失效面。
- 提升层：工作流。触发词：丢弃式背压、阻塞式背压、events will be lost、limit=0 关队列、限流按触发类型分轨、生产执行才限流、子工作流不在并发上限内。

## 「我在改的东西会不会被在途同步覆盖」要按锁的覆盖范围判，不按我的操作意图判（来源：docs.openclaw.ai/gateway/openshell.md 25,346B，2026-10-01 r348A 独立 curl 实拉）
- 原文：①「External editors and other Gateway processes do not participate in that lock」—— mirror 模式的锁只覆盖同一 Gateway 进程内的 upload→command→download。②「symlinks, FIFOs, or Unix sockets, into either workspace」永不复制。③清理失败须保留 runtime registry 条目供 recreate/prune 重试，明令勿靠删 registry 或切 workspace 隐藏失败。④`timeoutSeconds:120` 但 sandbox 创建保底 ≥300s。
- 判据：① **锁的作用域不等于「所有会碰这个文件的人」**：进程外的编辑器与宿主进程不参与锁，因此运行中的镜像命令在 download 阶段可以覆盖外部编辑。⇒ 「我刚改的怎么没了」这类问题的判据是谁参与这把锁，不是我改的时候有没有人看着。② **清理失败要留下可重试的把柄**：删沙箱失败时保留 registry 条目，是为了让 recreate/prune 还能找到它；靠删记录或切工作区让错误消失，等于把可重试故障变成不可见孤儿。③ **超时分档要按阶段看**：执行超时与创建保底是两个数值，用执行超时去估创建等待会误判卡死。
- 提升层：工作流。触发词：锁不覆盖外部编辑器、download 覆盖外部编辑、清理失败保留 registry、勿隐藏失败、symlink 不跨同步、创建保底超时。

## 分叉结构的「并行性」与「可合并性」都不对称，不能按图形外观推断（来源：help.make.com/router.md 6,347B + if-else-and-merge.md 19,001B，2026-10-01 r348B 独立 curl 实拉）
- 原文：①「modules connected to a router run **sequentially, not in parallel**」；②同页对照表：`can be merged back together with a Merge module` vs `Routes can't be merged back together`。
- 判据：① **看到扇出就假设并行，是「跑得挺快但结果对不上」类 bug 的误判源头**：同一种图形，在一种节点类型下是顺序执行。⇒ 排障前先确认分叉节点类型，再谈并行；性能预期与正确性预期都要按节点语义而非连线形状来定。② **两种分叉的合并能力不对称是结构事实**：router 分支不可在下游合并，if-else 分支可以。⇒ 不能把一种分叉的收束手法迁移到另一种；「聚合」这个词在同一系统里至少三种语义（顺序聚合 / 按到达顺序收带上限 / 任一分支为空即不产出），引用时必须点名是哪一种。

## 观测面可损、重放面必精：「看不见」不等于「没存」（来源：docs.n8n.io `/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions.md` 13,422B，2026-10-01 r348C 独立 curl 实拉）

## 挂起态是双字段：状态位只回答「态」，原因与恢复入口在独立实体；恢复去重的正确原语是存储唯一约束（来源：www.activepieces.com/docs/install/architecture/waitpoints.md 7,102B，2026-10-01 r349B 独立 curl 实拉，`only carries status` / `the *why* lives on the waitpoint` / `never processes a resume twice` / `10 000 is also the ceiling` 逐串命中；经 Qoder r367-Q-B 提名）

## 调度面「防惊群」与「漏扫记账」是两件相反极性的事：默认抖峰，漏扫按已完成记账不补跑（来源：docs.openclaw.ai/automation/cron-jobs/schedules.md 15,917B，2026-10-01 r349C 独立 curl 实拉，`stagger` ×5 / `catch-up` / `fire: true` ×3 逐串命中；经 Qoder r371-Q-C 提名）

## r351B · 扩展点是"观察者"不是"拦截器"：写入成功 ≠ 投递成功（来源：docs.openclaw.ai `automation/hooks/writing-hooks.md` 10,721B，2026-10-02 r351B 独立 curl 实拉逐串命中）

- **★返回值三不：不阻塞、不取消、不改写**：原文 "Returned values **do not block, cancel, or rewrite** the operation."。判据：排障时别把事件钩子当成熔断/拦截点——想在钩子里"返回 false 掐掉这次操作"是无效设计；真要拦截必须走宿主提供的专用否决通道。**这条决定了"为什么我的钩子没生效"的第一类答案：生效了，但它本来就没有阻断权。**
- **★context 是观测快照，唯一可写例外要显式点名**：原文 "Treat context as an **observation, not a live state-editing API**... **patch events carry cloned snapshots**. The **explicit mutable exception** is `agent:bootstrap`'s `context.bootstrapFiles`."。判据：**往 context 里改字段默认不产生任何效果**（且 patch 类事件给的是克隆副本），只有被点名的那一个例外可写。排查"改了没反应"时，先确认写的是不是那个唯一例外。
- **★同一个写入点，投递语义按生产者分档**：`event.messages` 原文 "is **not a general send-message API**"——表列四档：chat 命令会 await 并尝试回复；Gateway 会话 reset/create 的 RPC "messages are **not routed as chat replies**"；压缩事件交给调用方的回调投递；**其余核心事件（含 `/stop`、自动 reset、bootstrap、patch、Gateway 生命周期）"Ignored as replies"**。判据：**推送成功不等于送达**；且"缺失收件人/不支持的路由/发送策略/投递失败"任一都能让回复静默消失。
- **★时序早于 settle 才算数**：原文 "Append messages **before the handler's promise settles**; detached work that pushes later can **miss the producer's delivery step**."。判据：异步尾巴里补写的消息会静默丢失——这类丢失无任何报错，是典型的"偶发不发"根因。
- **★禁用 ≠ 移除，放置 ≠ 生效**：原文 "**Disabling leaves the files in place**"；放 workspace 目录的钩子须显式启用，且 "Workspace placement is **not an agent sandbox or a guarantee that the Gateway will load** that workspace's hooks"。判据：排查残留行为时，被禁用的钩子文件仍在磁盘上（可能被别的机制重新发现）；排查"没加载"时，先查放置位置是否被宿主承认，而不是查代码逻辑。
- 排障顺序：① 该扩展点是否有阻断权 → ② 写的是否为唯一可写例外 → ③ 该生产者是否把这次写入计入投递 → ④ 写入发生在 settle 前还是后 → ⑤ 文件是否被宿主发现（放置位）与被启用（禁用留文件）。

## r352B · 重放的两副面孔：它跑的是「旧输入 + 当前版本」，且变量取当下值不是当时值（来源：help.make.com `scenario-run-replay.md` 9,556B，2026-10-02 r352B 独立 curl 实拉逐串命中；与 §数据钉定 / §局部执行 互补——那两条管"把输入钉住、把范围收窄"，本条管"拿历史真实输入重跑时到底复现了什么"）

- **★重放能力要附「不可重放清单」与分场景入口**：原文 "**Run cannot be replayed**" 因两类 run 不入库——**Check run**（轮询触发器无新数据的检查运行）与 **Single module run**。入口分两个：Builder 内 *Run with existing data* 用于边建边测，History / Run details 里 *Replay run* 用于错误恢复与数据回填（不需要进 Builder）。判据：**声明"哪些运行没有存"与"从哪进"是重放功能的一部分**；排查"为什么这条不能重放"时，第一件事是核它是不是那两类不入库的运行，而不是查权限。

## r353A · 确认不是一个动作：ack ≠ transcript commit ≠ 被模型读到（来源：docs.openclaw.ai `plugins/codex-harness-runtime/queue-and-feedback` 4,065B，2026-10-02 r353A 实拉）

- **★三段确认语义互不蕴含**：`turn/steer` 的 acknowledgment **不代表 transcript commitment**；"A message sent to Codex without a confirmed transcript commit is **not replayed automatically**"；而 commit 只证明输入**进入了历史**，"does not prove that a subsequent model request has read it"。判据：**收到 ack 只能说"送达了"，说不了"存下了"，更说不了"生效了"**——排查"我明明发了但没执行"要按这三段分别取证，不能停在 ack。
- **★观测面降级只投运维通道，不回落给用户**：Codex 保存诊断日志失败时，只在 **Gateway logs 记 warning**；每条 native notice **收到即记一次**，不按共享该 app-server 的每个会话重复广播；operator-only，**不回落 chat**；"a logging failure never interrupts the native connection"，且该告警**既不修复原生日志故障，也不代表会话状态丢失**。判据：**日志系统自身的故障是"静默降级"而非"抛错"**——看不到日志 ≠ 没有故障；同时它保证不影响主链路，所以不能靠"业务还在跑"反推日志健康。
- 排障顺序（确认相关）：① 有没有 ack → ② 有没有 transcript commit（无 commit 则不会自动 replay）→ ③ 是否有后续模型请求真的读了它 → ④ 若怀疑日志缺失，先去运维通道查 warning，不要以 chat 无提示为证据。
- 提升层：工具 / 工作流。触发词：确认语义、ack、transcript commit、自动重放、诊断日志失败、operator-only。

## r353B · 日志落点会回退、低级别日志结构性降质、"跳过"不等于有人在等（来源：docs.openclaw.ai `gateway/logging` 23,470B + `concepts/queue-steering` 12,731B，2026-10-02 r353B 实拉）

- **★日志路径不保证稳定**：默认滚动日志在 `/tmp/openclaw/`（每天一个、按网关主机本地时区命名，命名 profile 另加前缀）；**若该目录不安全或不可写（属主错误 / world-writable / 是 symlink）则回退到用户级 `os.tmpdir()` 路径**，且"On Windows it **always** uses that OS-tmpdir fallback"。判据：**取证不能硬编码日志路径**——先解析实际落点；Windows 上默认就在 tmpdir，清理临时目录会直接清掉日志。
- **★低级别日志为省开销主动降质**：`trace` / `debug` / `info` / `warn` 记录**省略调用点元数据 `_meta.path`**（避免每条常规消息都抓取并解析栈），只有 `error` / `fatal` 保留；开启 diagnostics 且有内部消费者订阅时**所有级别都保留**。判据：**warn 级记录天然缺少定位信息，这是设计而非缺陷**——要靠 warn 定位必须临时开 diagnostics，不能指望常规日志自带调用点。
- **★"工具被跳过"不等于"有用户消息在等"**：被跳过的调用仍会收到配对的 start/end 事件与合成结果（`Skipped to process an incoming message.`），但**内部更新（如子 agent 完成报告）走同一个转向边界**，它们"can be hidden from the chat transcript and do not appear in the user message queue"。判据：**看到 Skipped 只能推出"有内部更新进来"，推不出"用户在催"**；把它当作用户行为信号会误判排队原因。
- 排障顺序（日志/信号相关）：① 日志实际落点（是否回退到 tmpdir）→ ② 该条记录的级别是否自带调用点（warn 以下没有）→ ③ Skipped 事件先按内部更新解释，再按用户消息解释。
- 提升层：工具 / 工作流。触发词：日志回退、tmpdir、_meta.path、warn 降质、Skipped 合成结果、内部更新走同一边界。

## r354B · 重试解决瞬时故障、熔断解决持续故障：两者必须成对配置，且熔断默认关（来源：docs.n8n.io `use-environment-variables/executions.md` 独立 curl 取 `.md` 原文，2026-10-02 r354B 实拉）

- **★"反复崩溃自动停用"是一个有默认关闭的熔断开关**：`N8N_WORKFLOW_AUTODEACTIVATION_ENABLED` 默认 `false`，`N8N_WORKFLOW_AUTODEACTIVATION_MAX_LAST_EXECUTIONS` 默认 `3`（"Number of crashed executions before unpublishing a workflow"）。判据：**重试与熔断方向相反且必须成对**——重试把失败再试一次（适合瞬时抖动），熔断在连续失败 N 次后停止投喂（适合持续故障）；只配重试，持续故障会被变成"持续压力 + 持续产生垃圾执行"。
- **★熔断的判据是"最近 N 次"而非"累计 N 次"**：变量名 `MAX_LAST_EXECUTIONS` 指向最近窗口。判据：**连续性与累计性是两种不同的触发语义**——累计计数会让"偶发失败的老工作流"在时间拉长后必然被熔断；连续/最近窗口才对应当下的健康度。
- **★熔断动作是"下线（unpublish）"不是"删除"**：触发后工作流被取消发布而非移除。判据：**自动处置的默认动作应是可逆的停用**；让自动化拥有删除权，等于把误判的代价从"暂停"抬到"数据丢失"。
- **★阈值可配说明熔断强度是策略不是常量**：3 次是默认值而非固定值。判据：**把熔断阈值写死在代码里，等于让运维在"太敏感"和"太迟钝"之间没有调节余地**；阈值、开关、动作三者都应该是配置项。
- 提升层：工作流 / 可复用 Skill。触发词：重试与熔断成对、autodeactivation、最近 N 次、连续 vs 累计、熔断即下线、熔断阈值可配。

## 限流要补问「副本语义」与「成功计不计入」；超时时钟只走活跃段；同步调用要分清「答错了」与「没回答」（来源：pipedream.com/docs/conduit/deploy/hardening.md 7,011B + www.activepieces.com/docs/install/reference/limits.md 6,779B，2026-10-03 r393A 独立 curl 取 `.md` 原文实拉；与 §限流排查先看作用域再看数值 互补——那条管"限的是谁"，本条管"多副本会不会放大"与"什么才写进计数器"）

- 限流器要问第四件事：计数器是共享还是 per-replica。认证失败类（登录、OAuth、MCP、SCIM）在 PostgreSQL tier **跨副本共享** ⇒ 跑 N 副本不会让凭据猜测者拿到 N 倍速率；其余限流器**故意 per-replica**（集群总速率≈N×单实例）⇒ 扩容前必须确认目标限流器属于哪一类，否则横向扩容等于放大攻击面。
- 只有失败写计数器，成功登录不写 ⇒ 护栏不该给正常行为制造状态，也不该让攻击者用成功请求探测计数；被限的认证失败会以 `rate_limited` 出现在指标里，是观测信号不是普通错误。
- 超时只计活跃执行时间：被 Wait for Approval / Delay 暂停的时段**不计入** run timeout ⇒ 人类审批挂在流程里不会烧掉执行预算；但"暂停生命周期"另有独立上限，是另一条时钟，两条都要声明。
- 同步 webhook 的状态码语义：流程跑失败**立刻** 500；只有超时窗口内从未产生任何响应才 408（仍在运行，或流程没有 Return Response 步骤）⇒ 500 是"答了但错了"，408 是"根本没答"，排障方向不同。

## 同一个超时状态码下有两种命运；「提交成功」不等于「会单独跑一次」；404 与 204 指向两处不同配置（来源：docs.openclaw.ai `gateway/config-hooks.md` 36,853B，2026-10-03 r393C 独立 curl 取 `.md` 原文实拉；经 llms.txt/索引页定位；与 §有错误不等于有可重试记录 互补——那条管哪些错误根本没进重试体系，本条管已经拿到回执之后怎么解读）

- 503 不能一概读作"没跑成"：单跑模式下 15 秒内未准入，**那段排队工作被取消**；fan-out 模式下待处理工作**继续在后台执行**；网关暂停/重启也会返回 `503 gateway_unavailable` ⇒ 同一个码、三种后果，先分清提交模式再决定要不要重提。
- wake 回执的 `eventOutcome` 有两个值：`queued`（队列接受了这次唤醒）与 `coalesced`（同样的唤醒已经是队列里最近的待处理事件，被合并了）⇒ **"我提交成功了"不等于"它会单独执行一次"**，重复提交被合并是设计行为，验收时要读这个字段而不是只看 200。
- 404 与 204 是两种"什么都没发生"：404 = 没有任何 mapping 匹配到这个 hook；204 = 匹配到了但没产生任何动作 ⇒ 前者去查匹配条件，后者去查动作定义，方向完全不同。
- 重试前先分类：400 是 JSON/载荷/路由或投递选择不合法，**原文要求先读 `error` 字段再重试**；401 是 hook 鉴权失败；429 必须遵守 `Retry-After`；500 是 mapping/transform 抛异常（查网关日志）；502 是准入前的 agent 准备失败。

## 观测的陈旧窗口要写明秒数，且「负面结果不缓存」是独立设计；凭据状态要报「配置不可用」而非回落到正常态（来源：docs.openclaw.ai `gateway/config-secrets-env.md` 10,309B + `gateway/config-tools.md` 7,517B 索引页 + `gateway/config-tools/github-identity.md` 17,020B，2026-10-03 r395A 独立 curl 取 `.md` 原文实拉）

## 进度标记与产出分两次落库就是失步窗口；超时放弃的语义是「当没发生过」，且放弃阈值必须小于接管租约（来源：docs.n8n.io deploy/host-n8n/configure-n8n/durable-scheduler.md 30,546B，2026-10-04 r417A 独立 curl 取 .md 原文实拉；真页经 llms.txt 287,049B 重新定位，此前 Qoder 引用的 hosting/scaling/durable-scheduler 系 1,930B 404 壳）
- 进度与产出是两个写入就存在失步窗口：轮询光标默认存 workflow static data 并与执行分开保存，崩溃落在两次保存之间时二者错位，症状是「跳过条目」或「重复处理」。修法是把光标与执行放进同一张表的同一事务，使一轮轮询要么完全发生要么完全没发生。判据：写入次数即窗口数。
- 超时放弃必须让标记原地不动：poll 超过阈值被放弃时平台什么都不记、光标不动，下一次覆盖同一段，因此不丢数据。「放弃」的正确语义是「当作没发生过」，若写成「推进到下一处」就会静默丢数据。
- 两个超时必须有偏序：放弃阈值（poll timeout）须严格小于接管租约（lease duration），否则被放弃的工作仍在跑而另一实例已接管同一 run，放弃形同虚设；平台在 timeout 达到 lease 时启动告警。
- 积压补跑是形状选择且没有任何策略逐条重放：丢弃全部 / 坍缩为最新一次 / 每条触发规则各一次，三种策略下时钟一律跨过积压；一次性触发没有「下一次」可恢复，故 catch-up 策略下仍会晚跑，skip 则永久丢弃。与部分失败三形状互补——那条管同批内失败条目的形状，本条管跨批积压的形状。
- 调度实体有所有者：owner reconciliation 周期回收所有者已消失的 schedule，否则留下无人认领的孤儿定时任务。

## 隔离强度是可以被性能问题悄悄降级的安全属性：强隔离方案（每 token 一个独立子进程）会因内存/时延被回退成共享沙箱，且共享会话会跟着一起退（来源：api.github.com/repos/activepieces/activepieces/releases?per_page=3 22,912B，2026-10-12 r527A 一手 curl 200 逐串命中 `0.92.2` / `chore(engine): evaluate template-expression scripts with the legacy sandbox (#16189)` / `chore(engine): use the legacy sandbox for the shared script session too (#16190)` / `This routes {{ }} template-expression evaluation through the legacy sandbox instead of spawning a Deno process per token`；r527A 落地）
- **实证**：Activepieces 0.92.2 把 `{{ }}` 模板表达式求值从「每个 token 起一个 Deno 进程」改回 legacy sandbox，理由是「relieving the memory pressure and slowdowns on flows that map many expressions over large step outputs」；**第二个 commit 把 shared script session 也一并改回 legacy**。
- **判据**：① **隔离方案是一个可运维回退的档位，不是平台的固有属性**——既然能被一次 chore 提交整体改回去，就不能在任何审计结论里把"跑在沙箱里"当作常量；要问的是"当前这一版跑在哪一档隔离上"。② **性能回退与安全降级是同一个动作的两面**：把 per-token 独占进程换成共享沙箱，换来的是内存与时延，付出的是**不同 token 之间的执行上下文不再互相隔离** ⇒ 评审这类变更时不能只算性能账。③ **会话面会随引擎面同步退**：#16190 说明共享脚本会话也走 legacy ⇒ 只盯着"引擎改了"会漏掉"会话复用面也一起退了"，两个面要各自确认。④ **回退要能被机检发现**：这类变更出现在 `chore`/`Maintenance` 段而非 `Breaking Changes` 段，读 breaking-changes 页看不到 ⇒ 排障"为什么隔离行为变了"要直接读发布说明的维护段，而不是只看破坏性变更清单。⑤ **回退是可逆的设计选择，不是 bug**：原实现存在过说明强隔离可行，选型时要记录"曾因什么指标退回去"，否则下一次评估会重复踩同一个性能点。
- 提升层：工具（隔离档位）/ 工作流（变更评审）。触发词：legacy sandbox、per-token Deno process、隔离降级、共享沙箱、shared script session、chore 段安全回退。

## 「重启」不是免费的排障动作：重启频率本身是一档限流面，且该档通常不可配（来源：docs.openclaw.ai/gateway/security/rate-limiting.md 13,490B，2026-10-12 r527C 一手 curl 200 逐串命中 `Gateway restart cycles` / `30s cooldown between restarts` / `Keyed by: process` / `Configurable: no`；同页 `They protect different boundaries, key on different identities, and fail with different error shapes`；r527C 落地）
- **实证**：网关把限流做成七张独立表，除常见的认证失败（10 次/60s + 5 分钟 lockout）与 webhook（20 次/60s）外，**`Gateway restart cycles` 也占一行：30 秒冷却、按进程计、不可配**；同表还有未认证 WebSocket 握手 128 并发槽（按解析后的客户端 IP，NAT 后同源共享、loopback 不豁免）、控制面写 RPC 30 次/60s per method+device+IP（不可配）、ACP 会话 120/10s（internal）。
- **判据**：① **"重启一下试试"有物理下限**：冷却是进程级的硬间隔，连续快速重启会被挡在冷却里，表现为"重启命令没报错但服务没起来" ⇒ 排障手册里的重启步骤必须写明最小间隔，否则自愈循环会自己把自己限死。② **限流要按"面"记账而不是按"有没有限流"记账**：七个面的键（IP / IP+凭据域 / method+device+IP / 进程 / translator 实例）、失败形态（503 且无 Retry-After、lockout、内部）、可配性（仅前两面可配）全不同 ⇒ 报"被限流了"而不说是哪个面，等于没报。③ **不可配的面要单列**：webhook、控制面写、ACP、重启冷却四档明确 `Configurable: no` ⇒ 出现"我改了 `gateway.auth.rateLimit` 却没生效"是设计如此，不是配置没落盘；排查前先分清目标面在不在可配集合里。④ **NAT 与 loopback 都要按共享主体算**：同一 NAT 出口共享 preauth 预算，浏览器源 WS 认证失败明确「loopback **not** exempt」⇒ 本地调试环境和多租户出口都会被同一份预算打到，压测结论不能直接外推到单客户端场景。

## 流式回答的「完成」必须由协议自己的终态事件定义：无终态事件的干净关闭跨客户端口径相反，截断曾被计为成功；重试窗口只开在「输出尚未到达读者」之前（来源：api.github.com/repos/windmill-labs/windmill/pulls/11623 一手 curl 200 逐串命中，2026-10-12 r528B 实拉；`retry transient AI provider failures before output reaches readers` / `The call is retried only while none of its output has been shown to anyone. Once tokens are on screen, a failure surfaces as an error instead of a restarted answer` / `some readers of the stream can't take back text they already showed` / `a stream that failed part way used to count as a finished answer` / `Request timeouts are not retried, because the request timeout is the job's own. Connect timeouts are.`；r528B 落地）
- **实证**：Windmill PR #11623 给出两套此前互不统属的事实。① **流终止判定**：`parse_events` 在传输错误、以及**在收到终态事件之前流就关闭**时判失败；终态事件逐协议具名——`[DONE]` / `finish_reason`（chat completions）、`message_stop` 或带 `stop_reason` 的 `message_delta`（Anthropic）、`response.completed` / `response.incomplete` / `response.done`（Responses）、`finishReason`（Gemini）、`MessageStop`（Bedrock）；**终态事件之后的传输错误被忽略**，已完成答案保留。对"干净关闭但无终态事件"，各客户端口径相反：Vercel AI SDK 的 OpenAI-compatible（`Response stream ended without a finish reason`）、openai-python 的 Responses helper、gemini-cli（`NO_FINISH_REASON`，重试）、langchain-aws **判失败**；Anthropic SDK、openai-python 的 chat stream、Vercel 一厂各家 **接受并以 unknown reason 结束**。本 PR 取失败一侧，`so a truncated answer is never taken for a complete one`。② **重试边界**：只在"没有任何输出被展示给任何人"时重试；一旦 token 上屏，失败表现为错误而不是重开答案。重试集合为 408/409/429/5xx（先看 `x-should-retry`），但 **OpenAI `insufficient_quota` 的 429 与 Gemini 429 中 `QuotaFailure` 名为 `PerDay`/`Daily` 的不重试**；等待取 `retry-after-ms` → `retry-after` → Gemini body 的 `RetryInfo.retryDelay`，**最多尊重到 60s，超过就失败**；最多 3 次、抖动指数退避约 1s/2s/4s、上限 10s。
- **判据**：① **"连接正常关闭"不等于"回答完整"**：流的完成判据是**该协议自己的终态事件**，不是 TCP 干净关闭 ⇒ 验收流式输出时要断言"收到了哪一个终态事件"，只断言"没有异常/没有报错"会把截断回答判成成功（原文即承认这是既有 bug：`used to count as a finished answer ... completed with truncated or empty output`）。② **跨 SDK 迁移会让同一个流静默改变成败结论**：同一段"无 finish reason 的干净关闭"，在 A 客户端是错误、在 B 客户端是成功 ⇒ 换 SDK / 换 provider 封装后，成功率指标变差不一定是模型退步，可能是终止判定变严；比对指标前先对齐终态判据。③ **终态事件之后的错误要忽略**：已完成答案之后的传输错误不应把结果打成失败 ⇒ 判定顺序是"先找终态，再看错误"，反过来实现会把已成功的请求批量误判。④ **重试的前提是"可撤销"，不只是"可重试"**：同一个 429，在输出到达读者之前可以重来，之后不行——因为流是 append-only，读者**拿不回**已经显示的文本 ⇒ 设计重试时的第一问是"这次失败能不能被无损撤销"，答不出来的重试只能放在产生可见输出之前。⑤ **同一状态码内部要按 body 子类型分叉**：429 里 `insufficient_quota` 与日配额类**明确不重试** ⇒ "429 就重试"是错的，可重试性要下沉到错误体的具体原因字段。⑥ **远端给的等待时长要有上界**：`retry-after` 系列被尊重但封顶 60s，超出直接失败 ⇒ 盲从远端重试提示会把一次调用拖成不可控的长尾。⑦ **超时要分连接超时与请求超时**：连接超时可重试，**请求超时不可重试**（`the request timeout is the job's own`）⇒ 把两者混为一类做重试，会让已经跑满预算的作业被再跑一遍。

## 用 CAS 对账的并发写入，陈旧 base 必须硬失败而不是重放或 rebase：重放会把已付费输出再算一遍（来源：docs.openclaw.ai/gateway/cloud-workers/security-model.md 7,592B，2026-10-12 r529C 一手 curl 200 逐串命中 `Durable, exactly-once worker transcripts.` / `the worker commits transcript batches through a compare-and-swap protocol against the session's leaf` / `a stale base fail-stops the run instead of duplicating or rebasing paid output`；r529C 落地）
- **实证**：OpenClaw 云 worker 的转录提交不是"写进去"，而是**对会话 leaf 做 compare-and-swap**：worker 成批提交转录，base 陈旧时**整个 run fail-stop**，官方明确写它这么做是为了**不复制、不 rebase 已付费的输出**（`duplicating or rebasing paid output`）。同页相邻的另两处同源事实：每次派发 mint 一份 worker 凭据且网关只存哈希，凭据轮换 + owner-epoch fencing 保证同一会话至多一个 live owner，**重连的陈旧 worker 被 fence 而不是合并**；GitHub 发布路径走 tree / commit / **compare-and-swap ref** API。
- **判据**：① **并发对账发现"我落后了"时，默认处置是硬失败而不是追上**：落后就重放，在有计费副作用的一侧等于把已完成的工作**再买一次** ⇒ 选处置动作前先问"重跑一次的代价是不是零"，非零就选 fail-stop。② **"rebase"在产出侧是危险词**：把别人的新进展垫在自己下面再提交，会让同一段付费输出以新的名义出现两次 ⇒ 只有"纯函数、可重算、无副作用"的产出才允许 rebase；带成本或外部副作用的产出只允许 fail-stop + 人工裁决。③ **对账的锚要是"我读到的那个版本"，不是"最新的那个版本"**：CAS 的价值全在 base 上 ⇒ 报"提交失败"必须带上 base 与当前 leaf 两个值，只报失败无法区分"我落后"与"系统坏了"。④ **陈旧执行者的正确处置是隔离不是合并**：重连的旧 worker 被 fence ⇒ 排障"两个进程在改同一份东西"时，先确认有没有 fencing/epoch 机制，以及它是否真的挡住了旧的一方；"看起来还在写"往往是 fence 没生效，而不是并发设计允许。⑤ **同一套 CAS 语义要贯穿所有写入通道**：转录走 CAS、Git 发布走 compare-and-swap ref ⇒ 只在一个通道做对账，其余通道仍会静默覆盖；审计时逐个写入面问"这一路的 base 是什么"。⑥ 与 §多资源加锁取稳定全序（dl 1.180.0）、§跨 yield 结算三件套（dl 1.178.0）分工：那条管**加锁顺序**防互锁、那条管**归属冻结与幂等结算**，本条管**对账失败的处置方向**（fail-stop 而非重放/rebase）及其计费理由。
- 提升层：工具（并发对账）/ 工作流（失败处置）。触发词：compare-and-swap、stale base、fail-stop 不重放、不 rebase 付费输出、会话 leaf、owner-epoch fencing、陈旧 worker 被 fence、CAS ref 发布。

## 换认证模式会连带换掉 TLS 严格性：IAM 模式强制主机名与证书校验，口令模式保持原行为——排查连接类失败必须先判认证模式再判 TLS（来源：api.github.com/repos/zenml-io/zenml/releases?per_page=3 24,428B，2026-10-12 r531B 一手 curl 200 逐串命中 `AWS RDS IAM authentication for MySQL stores` / `ZenML generates fresh IAM tokens for database connections and enforces TLS hostname and certificate verification in IAM mode` / `while preserving the existing password-based behavior` / `giving AWS users a passwordless database authentication option`；r531B 落地）

## 健康检查的时间基准必须排除依赖方的维护窗口：上游返回 503 + 维护头时，本服务的探针仍应报健康；未初始化状态（首次轮询前）不得让健康检查自己抛 500（来源：api.github.com/repos/PrefectHQ/prefect/pulls/23325 5,320B，2026-10-12 r531C 一手 curl 200 逐串命中 `PREFECT_RUNNER_SERVER_MISSED_POLLS_TOLERANCE` / `Prefect-Maintenance` / `Retry-After` / `polling_window_start(last_polled)` / `liveness probe` / `Restarting a runner also stops the flow runs it is executing.` / `500 Internal Server Error`；同批 PR #23230 已对 worker 做过同样修改；r531C 落地）
- **实证**：Prefect runner 的 `/health` 用「最后一次轮询距今不超过 `PREFECT_RUNNER_SERVER_MISSED_POLLS_TOLERANCE × PREFECT_RUNNER_POLL_FREQUENCY`（默认 20s）」判存活。维护窗口内 API 返回 `503` 并带 `Prefect-Maintenance: true` 与 `Retry-After`，客户端按 `Retry-After` 等待后才重试 ⇒ 任何维护窗口开始约 20 秒后，liveness probe 就把它判死并重启，而 **重启 runner 会连它正在执行的 flow run 一起停掉**。修法是把时间基准改成共享函数 `polling_window_start(last_polled)`，取「最后一次轮询」与「最近一次维护退避结束时刻」的**较晚者**。同一处还有第二个 bug：`runner.last_polled` 在首次轮询完成前是 `None`，而检查无条件做减法 ⇒ webserver 启动到首次轮询之间 `/health` 一直返回 `500 Internal Server Error`；平时很短，但若首次轮询正撞上维护窗口，这段 500 会持续整个窗口。
- **判据**：① **健康检查量的必须是「我自己是否在正常工作」，不是「我的依赖是否可用」**：依赖进入计划内维护并被明确告知（`Prefect-Maintenance` + `Retry-After`）时，本服务正在**按设计退避**，此时判死是误判 ⇒ 探针的时间窗口要把「被告知的等待期」从「失联时长」里扣掉。② **误判的代价被下游放大**：本例不是「多重启一次」，而是 `Restarting a runner also stops the flow runs it is executing` ⇒ 评估健康检查误报时，必须沿「重启会连带终止什么」往下追一层，否则会低估一个 20 秒阈值的破坏力。③ **退避信号必须可机读且被探针消费**：维护状态通过响应头与 `Retry-After` 显式传达，修法正是让探针去读它 ⇒ 只把 `Retry-After` 当重试建议、不当健康基准，等于把已经拿到的信息丢掉。④ **「还没开始」不是「已经坏了」**：`last_polled is None` 属于未初始化而非失败 ⇒ 任何以「上次成功时间」为输入的判活逻辑，都要为 `None` 单独分支（报健康或报 starting），不能让空值进入算术后抛出 500。⑤ **同一逻辑要在所有同类组件上对齐**：本 PR 是 runner 侧对 worker 侧 PR #23230 的跟进 ⇒ 有一致性要求的健康检查，改一处要回扫同类组件，否则「为什么 worker 没重启、runner 重启了」会成为新的疑难问题。⑥ 与 §健康检查分存活与就绪两级（KB:1562/2860，就绪须含下游依赖）**看似相反、实则互补**：那条要求**就绪**面把依赖算进来，本条要求**存活**面把依赖的计划内不可用排除掉 ⇒ 正确形态是「存活看自己（排除被告知的等待）、就绪看依赖（含下游连通）」，两者混用会一边误重启、一边漏报。
- 提升层：工具（健康检查与探针设计）/ 工作流（变更影响评估）。触发词：健康检查时间基准、维护窗口误判、Prefect-Maintenance、Retry-After 作为健康基准、last_polled 为 None、liveness probe 误重启、重启连带终止运行中任务、存活 vs 就绪。

## 「同一借用者已持有令牌」是幂等去重信号，不是致命错误：限流器的溢出异常要按语义分叉捕获，只捕 WouldBlock 会把重复提交打成服务级崩溃（来源：api.github.com/repos/PrefectHQ/prefect/pulls/23341 2,296B，2026-10-12 r531C 一手 curl 200 逐串命中 `already holding one of this CapacityLimiter's tokens` / `_submitting_flow_run_ids` / `the limiter token stays held until the run exits` / `only catches anyio.WouldBlock` / `critical_service_loop treats the error as fatal` / `logs a warning, and continues to the next run in the batch` / `Other RuntimeErrors are re-raised`；r531C 落地）
- **实证**：带 `--limit` 的 worker 在轮询返回「自己正在执行的那个 flow run」时会停摆。成因链：`_submit_run` 在基础设施启动后把 run id 从 `_submitting_flow_run_ids` 移除，但**限流令牌一直持有到 run 退出**；后续轮询再拿到同一 run 时 `acquire_on_behalf_of_nowait` 抛 `RuntimeError: this borrower is already holding one of this CapacityLimiter's tokens`。而 `_submit_scheduled_flow_runs` **只捕获 `anyio.WouldBlock`**，于是 `critical_service_loop` 把这个错误当致命错误处理。修法：捕获「already holding」这一类 RuntimeError → 记 warning → 继续处理同一批次里的下一个 run；**其余 RuntimeError 仍然重抛**。回归测试 `test_worker_skips_duplicate_submission_of_run_holding_limit_slot` 在修复前失败、修复后通过，并额外断言「同批次的新 run 仍被提交、令牌计数正确」。
- **判据**：① **异常的类型是语义，不是实现细节**：同一类 `RuntimeError` 里，「容量已满」（WouldBlock）与「你已经持有了」（already holding）含义相反——前者要等，后者**什么都不用做** ⇒ 用异常类型做控制流时，必须按语义分叉而不是按类捕获；把「已持有」当错误上报，会把幂等情形误报成故障。② **「令牌持有期」与「业务完成期」要对齐**：本例令牌持有到 run 退出，而 bookkeeping 集合在启动后即移除 ⇒ 两个生命周期记账不一致时，中间窗口的重复请求必然打到限流器；设计限流面要显式写清「令牌何时归还」。③ **吞掉整个异常类会制造静默故障**：反方向同样成立——本 PR 明确 `Other RuntimeErrors are re-raised` ⇒ 修「重复提交」时不能顺手把同类异常全捕了，否则真正的容量/状态错误会变成一条 warning 溜走。④ **回归测试要断言三件事而不只是「不报错」**：本例断言「重复 run 被跳过」+「同批次新 run 仍提交」+「令牌计数正确」 ⇒ 幂等修复的验收必须包含「该做的没被顺带跳过」与「资源账目没漂」，只测「不崩」会漏掉过度去重。⑤ **限流与去重是同一个机制的两个出口**：容量限制器既产生「满了」也产生「重复了」 ⇒ 设计限流面时要同时定义这两种返回该怎么被上层解释，只定义其中一种，另一种就会落到默认的致命分支。⑥ 与 §重启频率是限流面（dl 1.184.0）、§CAS 陈旧 base 必须 fail-stop（dl 1.186.0）分工：那条管**限流分面与不可配档**、那条管**并发对账失败的处置方向**，本条管**限流器异常语义的分叉处理**，落点是「哪一类溢出信号应该被当作无操作」。
- 提升层：工具（限流与幂等）/ 工作流（异常处理分叉）。触发词：already holding token、CapacityLimiter 重复借用、只捕 WouldBlock、critical_service_loop fatal、令牌持有到退出、重复提交幂等、其余 RuntimeError 重抛。

## 嵌套执行上下文的继承语义必须逐原语显式定义：未定义的调用会静默挂起而非报错，且作用域要用 AsyncLocalStorage 不是布尔 flag（来源：api.github.com/repos/windmill-labs/windmill/pulls/11699，2026-10-12 merged 16:47Z，一手 gh api 逐串命中）
- **实证**：workflow-as-code 里"任务体内调用任务/步骤"永久挂起：任务体跑在**重放工作流以到达其步骤**的子 job 里，那一轮中除正被执行的步骤外每个步骤都停在**永不 resolve 的 promise**上——这对工作流体自身的其余步骤是对的，却**连带抓住了任务体自己发出的调用**（`step()`/`sleep()`/`taskScript()`/`taskFlow()`/`waitForApproval()` 与 Python 客户端同病）。表现是"子 job 永久等待，无报错、无内层 job"。而任务是单个 job、没有自己的轮次，**本就无法派发或检查点一个步骤**。修复后逐原语定义语义：任务体内 `task()`/`@task` 与 `step()` **就地（in place）在同 job 运行、结果 JSON 往返**（`step()` 不做检查点；任务的 task options 不适用），`sleep()` 在 job 内等待，而 `taskScript()`/`taskFlow()`/`waitForApproval()` **显式抛出指向工作流体的错误**。机制选择：TS 用 `AsyncLocalStorage` 作用域、Python 用 `ContextVar`——**布尔 flag 不行**：在 `Promise.all([a(), b()])` 下工作流体与任务体并行重放，flag 会让工作流体的调用误走"就地执行"而在本 job 跑出一个兄弟任务。取舍写明：**嵌套任务就地运行而非报错**，因为那与任务在工作流外本来的行为一致。测试：两客户端新增回归（嵌套 task/step、工作流体兄弟不被跑、从任务体派发须报错）——**无修复时全部以超时失败**。
- **判据**：① **上下文继承规则的空档表现为静默挂起，不是报错**：未定义的调用若落在"等待永不兑现的承诺"上，系统给不出任何信号——**嵌套/派发类 API 的语义表必须逐原语填满，空档的默认行为必须是显式错误**。② **就地执行 vs 派发 vs 报错是三种不同语义，要按原语分别裁定**：能安全就地跑的（纯计算/等待）就地跑并声明"不检查点、task options 不适用"；必须报错的要指向正确位置（"该在工作流体里调"）——笼统地"都支持"或"都禁止"都会留空档。③ **作用域机制要在并发下检验**：`Promise.all` 下工作流体重放与任务体并行，布尔 flag 无法区分调用来源 ⇒ 用 `AsyncLocalStorage`/`ContextVar` 这类随异步调用链传播的作用域；选型判据是"**兄弟分支并存时它还能不能指认调用方**"。④ **"无修复即超时失败"是这类 bug 的标准回归形态**：静默挂起的修复必须有能在修复前挂住的测试，否则测试通过只证明没崩。⑤ 与 dl 1.197.0（同一未应答请求只问一次）分工：那条管**交互层的重复提示**，本条管**执行层的嵌套语义空档导致永久等待**。
- 提升层：工具（执行上下文与派发语义）/ 工作流（嵌套任务的排查面）。触发词：任务体内调用静默挂起、嵌套执行上下文、in place 就地运行、永不 resolve 的 promise、逐原语定义语义、AsyncLocalStorage 作用域、ContextVar、布尔 flag 在并发下失效、Promise.all 并行重放、无修复即超时失败、taskScript 须报错。


## 技能/规则修订前先把执行证据锚到具体条目：跨重复运行比失败与成功的抽象轨迹定位「可疑动作」，再定编辑点（来源：arxiv.org/abs/2610.11858v1（SkillMorph）一手 export.arxiv.org 2026-10-13 r547B 实拉摘要逐串命中）
- **实证**：技能提供可复用指引，但"**incomplete or unsuitable guidance can impair task execution**"。已有做法用 LLM 从执行反馈生成修订，但"**grounding these revisions in explicit behavioral evidence remains challenging**"。SkillMorph 的核心："**link execution evidence to specific skill contents before generating revisions**"——具体是"**compares failure and success evidence in abstracted trajectories across repeated runs and tasks, incorporating changes between evolution loops to identify suspicious actions**"，再用这些可疑动作"**localize edit sites in the skills and generate corresponding revisions**"。SWE-Skills-Bench 与 CannBot 上，其演化的技能在 trial-level accuracy 与 execution consistency 上均优于原技能与四种既有技能演化方法；并已用于自动 kernel generation（AI 算子开发团队接受了 6 个技能修订 PR）。
- **判据**：① **"这次失败了所以改技能"是未定位的修订**：执行反馈与技能内容之间缺一条因果链，直接让模型生成修订等于让它猜改哪里——**修订前必须先建立"证据 → 具体条目"的锚点**。② **定位靠失败与成功的对照，不靠失败单独**：只在失败轨迹里找可疑动作会把"成功跑也做了的动作"误判为嫌疑；跨重复运行与多任务比对**两类轨迹**，差异面才是定位信号。③ **轨迹要抽象化再比**：原始轨迹噪声淹没结构差异，比对的是抽象后的动作序列——定位精度取决于抽象层选得对不对。④ **把"演化循环之间的变化"也算进证据**：上一轮改了什么会改变本轮的可疑动作集，忽略它会在同一处反复修订（与 dl 1.197.0「按询问内容去重」同构：都要记住已做过什么）。⑤ **编辑点是局部的**：定位输出是 edit sites（条目级），不是"重写这份技能"——整篇重写会把没问题的部分一并换掉且无从非回归（与 sa 1.139.0 Skill-V「修订须保受保护约束 + 历史回放非回归」配套：一个给定位，一个给验收）。⑥ 与 dl KB:507「定位阶段只产出失败点矩阵、不许同时提修复」分工：那条管**角色边界**（不许边定位边改），本条管**定位方法**（用什么证据、怎么比、怎么落到编辑点）。
- 提升层：工作流（技能/规则修订的故障定位）/ 工具（轨迹抽象与对照）。触发词：修订前先锚定证据、SkillMorph、可疑动作 suspicious actions、失败与成功轨迹对照、抽象轨迹、跨重复运行比对、演化循环间的变化、edit sites 条目级定位、整篇重写是未定位修订、execution consistency、SWE-Skills-Bench。


## 错误处理路径自身的崩溃会抹掉真实错误：跨边界序列化按原始类型白名单抽取，且 name/message/stack 必须显式置为可枚举可配置可写（来源：api.github.com/repos/n8n-io/n8n/pulls/33503，2026-10-13 r551B 一手 gh api 200 逐串命中 `the database driver throws an error object that often contains the raw query buffer (which can be massive)` / `attempts to serialize it over IPC via JSON.stringify, it crashes with a fatal JavaScript heap out of memory exception, masking the actual DB error` / `act as a strict primitive whitelist instead of mutating the error in-place` / `Object.create(Object.getPrototypeOf(error)) ... without triggering non-configurable descriptor traps` / `Explicitly enforces enumerable: true, configurable: true, and writable: true via Object.defineProperties on name, message, and stack` / `simulate a 50MB Buffer injection alongside non-configurable properties` / `JSON.parse(JSON.stringify(safeErr))`；r551B 落地）
- **实证**：节点执行 DB 查询违反约束（如 PostgreSQL duplicate key）时，驱动抛出的错误对象常携带**原始查询 buffer（可能极大）**；JS Task Runner 捕获后经 IPC 用 `JSON.stringify` 序列化，直接 fatal `JavaScript heap out of memory` 崩溃，**真实 DB 错误被掩盖**。修法：`makeSerializable` 改为严格的**原始类型白名单**（`string`/`number`/`boolean`），不再原地改错误对象；用 `Object.create(Object.getPrototypeOf(error))` 动态克隆原型以保留类身份（`UnsupportedFunctionError` 等）且不触发 non-configurable 描述符陷阱；对 `name`/`message`/`stack` 显式 `Object.defineProperties` 设 `enumerable/configurable/writable = true` 使其存活于 IPC 序列化边界。测试注入 50MB Buffer + non-configurable 属性，并用 `JSON.parse(JSON.stringify(safeErr))` 显式模拟 IPC 边界。
- **判据**：① **错误处理路径自己是故障高发区，且失败形态最坏**：它一崩，用户拿到的是崩溃而不是根因 ⇒ 设计错误通道时要问「处理错误的代码本身会不会因为这份错误而崩」。② **错误对象的载荷大小是外部可控量**：原始查询 buffer、结果集、附件都可能被故障或对手放大 ⇒ 把不可控载荷带进序列化边界等于自埋 OOM，跨边界前必须先裁剪。③ **裁剪方式是白名单抽取，不是原地删除字段**：白名单默认丢弃未知（新加的大字段自动被挡），黑名单默认放行未知（下一次新增字段又炸）。④ **保类身份要靠克隆原型，不要复制属性**：直接赋值属性会碰到 non-configurable 描述符抛错，而 `Object.create(getPrototypeOf(e))` 绕开了这个陷阱。⑤ **可枚举性是跨 `JSON.stringify` 的生死线**：`message`/`stack` 若不可枚举，过边界后静默变空壳，`error.message` 变成 `undefined` ⇒ 「错误有值」与「错误能被传过去」是两件事，验收要在边界后断言。⑥ **测试必须模拟边界本身**：`JSON.parse(JSON.stringify(safeErr))` 而不是断言对象结构，同时注入极端载荷与描述符陷阱 ⇒ 序列化契约的回归测试要跑真实编解码。
- 提升层：工具（错误通道与跨进程序列化）/ 工作流（故障可观测性）。触发词：错误处理路径崩溃、掩盖真实错误、50MB buffer、JSON.stringify OOM、原始类型白名单、Object.create 克隆原型、不可枚举字段过边界消失、JSON.parse(JSON.stringify()) 模拟 IPC。

## r559A · 悬空态最常见的成因是「终止路径上留下了一个只有将死的进程才会兑现的承诺」（来源：api.github.com/repos/PrefectHQ/prefect/pulls/23284，2026-10-14 r559A 一手 gh api 200 逐串命中 `retry_type = "in_process"` / `Workers explicitly skip in-process retries in their polling query` / `The k8s Job reports Succeeded (the runner exits 0)` / `flip it to "reschedule"`）
- **实证**：k8s 工作池的 pod 被驱逐、SIGTERM 落下后，flow run 会停在 `AwaitingRetry` 且没有 worker 认领。链路：引擎把 SIGTERM 转成 Failed 状态提案 → `RetryFailedFlows` 把它拒成一次 retry；但这次转换同时给 run 的 policy 盖上 `retry_type = "in_process"`，语义是「**我的进程会处理这次重试**」——然而这个进程正在被杀。runner 按预期提出 `AwaitingRetry`，而 `in_process` 标记留了下来；**worker 的轮询查询显式跳过 in-process 重试**，于是 run 就一直坐着；同时 **k8s Job 报 Succeeded（runner 退出码 0）**，基础设施层的崩溃检测也不会触发。修法：在 SIGTERM 重排路径提出 `AwaitingRetry` 之后**回读**该 run，若 `retry_type` 仍是 `in_process` 就翻成 `reschedule`（意为「该由某个 worker 接手」——当前进程即将退出，这恰好正确）。取舍说明：作者考虑过在服务端对任何非 Failed 状态进入 AwaitingRetry 的转换统一清除 `retry_type`，但认为**过宽**——可能存在服务端确实设置 in_process 并期望它留存的合法场景；故把改动限定在「已知进程将死」的 SIGTERM 重排路径内。已知代价：读 + 改是两次 API 调用，不是一次原子操作。
- **判据**：① **承诺与兑现者要绑定生命周期**：`in_process` 是「我负责」的声明，一旦声明者即将消失，该声明就必须一并改写 ⇒ 排查悬空态先问「这个对象身上有没有一个只有已死/将死的主体才会兑现的承诺」（重试、续跑、回调、锁续期都属此类）。② **两层观测同时报成功时问题最隐形**：应用层 run 停在合法状态 `AwaitingRetry`（不是错误态），基础设施层 Job 报 Succeeded（退出码 0）⇒ 任何一层单独看都"没坏"；**排障清单要显式包含「两边都说没事」的组合**，与 r558A「成功状态码 ≠ 成功」互补——那条是**单次响应**被误读，本条是**两层状态机各自合法**却整体卡死。③ **修复范围要收窄到「你知道前提成立的那条路径」**：服务端统一清除被认为太宽（可能破坏合法 in_process 语义），故只改 SIGTERM 重排 ⇒ 宁可留一个窄修复 + 明确未覆盖清单，也不要一个"看起来更彻底"的宽改。④ **非原子的读改写要显式登记为已知代价**：作者自己点出这是两次调用 ⇒ 承认并写清残留竞态，好过假装原子。⑤ **「跳过」规则是悬空的高发地**：worker 轮询显式跳过 in-process ⇒ 凡有"轮询/扫描会排除某类对象"的设计，都要反查"有没有路径能把对象变成被排除的类别却没人再把它变回来"。
- 提升层：工作流（悬空态与终止语义）/ 可观测性（双层静默）。触发词：in_process retry、SIGTERM 重排、AwaitingRetry 无人认领、worker 跳过 in-process、Job 报 Succeeded 但 run 悬空、两层都报正常、回读再翻标记、窄修复优于宽修复。

## r559C · 「缺数据」被当成错误处理时，默认后果量级会与原因不匹配（来源：help.make.com/fix-missing-data-errors.md 5,862B，2026-10-14 r559C 一手 curl HTTP 200 逐串命中 `BundleValidationError` / `if the input bundle is missing the required data` / `Your main goal is to avoid disabling your scenario`；**形态更正**：help.make.com/llms.txt 实测 200 / 73,053B / 420 页可达，此前「Make 403」结论仅适用于 make.com 主站与社区面，须按面记账）

## r574B 下沉条目：**恢复能力不是「失败后重试」的副产品，必须显式训练并带独立恢复样本**——ReTerm（arXiv 2610.18484，2026-10-15 abs 一手 https 200 逐串命中）指出终端 agent 在长程执行中难以从命令错误/错误实现中恢复，最终任务失败；做法是从 agent 自身失败态分叉出多条独立自我恢复轨迹做在线 RL（ReTerm-GRPO），并构造 10K 恢复示范做冷启动。判据：① 恢复是独立能力面，验收要单列「从失败态继续并最终完成」的用例，不能只用「首次就成功」的通过率代表；② 恢复样本必须从真实失败态分叉，用合成错误注入替代会漏掉真实失败分布；③ 与「失败分诊/自愈条目」分工：那条管失败被记录成可追踪条目，本条管恢复行为本身要被训练与验收（全文见 references/knowledge-base.md）。
- **提升层**：模型（恢复能力）/ 工作流（失败态利用）。
- 触发词：恢复训练、从失败态分叉、ReTerm-GRPO、恢复示范冷启动、长程恢复失败、恢复不是重试副产品。

## r574C 下沉条目：**错误处理开关必须覆盖连接/设置阶段，不只覆盖运行阶段**——`Continue On Fail` 在连接建立（connection setup）阶段被忽略：握手失败直接抛出，节点级容错声明在这里不生效，同一个开关在两个阶段语义不一致。判据：① 容错声明是横切契约，必须枚举它应当生效的全部阶段（连接/认证/运行/收尾），逐阶段断言；② 阶段间语义分叉本身就是缺陷信号（同一配置在 A 阶段生效、B 阶段不生效）；③ 与「错误处理分支不得改变数据路径语义」分工：那条管启用后输出形态变化，本条管开关根本没覆盖到该阶段（全文见 references/knowledge-base.md，2026-10-15 r574C，来源 n8n #41118）。

## 挂起、等待与取消的四类静默故障：选主后定时器不重挂 / 审批等待无取消入口 / 兄弟任务失败不传播 / 经暂停的计量值只能当近似（来源：api.github.com n8n-io/n8n issue #39896 + langgenius/dify release v1.18.0 + openai/codex issue #57477 + crewAIInc/crewAI issue #8667，2026-10-27 r631C 一手 api/releases JSON 200 逐串命中）
- **实证**：①n8n #39896 标题即修复项 `fix(core): Re-arm waiting executions after leader takeover`（state=closed）。②Dify v1.18.0 release 原文「**Nested usage and step totals can still be approximate, particularly after a pause or stop.** Console drilldown and external trace export have different scopes」。③openai/codex #57477 state=open，标题「Task awaiting approval with no controls to cancel it」（版本 26.1016.62342，附截图为证）。④crewAI #8667 state=open 原文「`Crew.kickoff()` runs each `async_execution=True` task in a daemon thread … When one of them fails, the exception goes straight out of `kickoff()` and **the sibling threads keep running to completion: they spend the rest of their model calls, fire user callbacks, write output…**」。
- **判据**：① **等待态的定时器必须能被"换了个谁来管"这件事重新挂上**——HA 选主切换后若不显式 re-arm，等待中的执行会永久挂起且不报错：它不是失败也不是成功，是**第三种静默结局** ⇒ 排查"卡住不动"时，先问"它的等待由谁在守、守的人换过没有"，与既有「挂起占 exit 0」不同轴（那条管退出码语义，本条管等待的持有者）。② **审批/人工等待必须有取消入口与超时迁移**——等待审批的任务没有任何控件可以取消它，等于把"放弃"这一动作从系统里删掉了 ⇒ 凡引入人工等待，必须同时给出取消路径与超时去向，否则用户只能关掉整个会话（与 §审批语义族分工：既有条目管"谁能批/何时批"，本条管"不批了怎么办"）。③ **兄弟任务的失败要级联停止并抑制完成事件**——一个异步任务失败后其余兄弟线程继续跑完、照常触发用户回调并写产物，于是上层收到成功的完成事件而这次运行其实已经失败 ⇒ **并发分支的收敛逻辑必须包含"任一失败即停其余并抑制其完成事件"**，只看 `future.result()` 的取回顺序会让失败之后的产物与回调照常落地。④ **经 pause/stop 的执行，其 usage/步数聚合只能当近似值**——官方原文给出"can still be approximate, particularly after a pause or stop"，且控制台下钻与导出 trace 的口径不同 ⇒ **凡拿 token/步数做结算、归因或评测证据的，必须先确认这次执行有没有被暂停过**；被暂停过的数值要显式标"近似"，不能进精确账单。⑤ 四条的共同形状：**都不是崩溃，都是"看起来还在/看起来完成了"**——排查清单里要给"静默非结果"单列一档（等待未重挂 / 无取消入口 / 完成事件与失败并存 / 计量值失去精确性），只查错误与超时会全部漏掉。
- 提升层：工作流（挂起与取消语义）/ 可观测性（计量归因口径）。触发词：re-arm、leader takeover、等待执行永挂、审批无取消入口、兄弟任务取消传播、TaskCompletedEvent 假完成、usage 近似值、pause or stop、暂停后计量不可作精确账单、静默非结果。
