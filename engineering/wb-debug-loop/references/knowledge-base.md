## 技能级记忆：per-skill 经验跨任务积累，创建与使用同循环（来源：arXiv MemSkill 2602.02474 + MUSE-Autoskill 2605.27366 2026-08 实拉，与 §轨迹→技能自进化 分工——那条管"从轨迹提炼技能"，本条管"技能自己的经验怎么存、怎么被下次调用用上"）
- **技能级记忆（skill-level memory）**：每个技能单独积累"这技能上次在哪类任务上栽过/哪步最花时间/哪个参数最容易传错"——下次调用时喂回给技能。判据：**技能经验存在技能自己的命名空间里，不混进会话记忆**——会话结束技能经验不丢。
- **创建-使用同循环（eliminate creation-usage mismatch）**：把 skill_create 内建进运行时循环，agent 干活时直接调用创建，不用跳出去另开流程——**建完立刻用，用的时候顺手建**。
- **设计器周期性回看难例**：定期把"选中技能产出差"的硬案例拿给设计器，驱动技能演进（不是等出问题才改）。判据：**难例是技能迭代的燃料，按周期主动收集而非被动等报错**。
- 反模式：技能经验写进会话记忆随会话丢；创建技能和用技能分成两套流程；难例攒到压垮才处理。
- **提升层**：可复用 Skill（技能生命周期）。

## Harness 工程：把运行环境当被优化对象，深度遥测驱动演进（来源：harn.app AHE 2026-09 + EveryDev《Agentic Harness Engineering》2026-09-18 实拉，与 §轨迹→技能自进化 分工——那条管"技能内容怎么长出来"，本条管"harness 配置（工具 schema/检索策略/沙箱/记忆规则）本身怎么被优化"）
- **harness 是研究对象不是固定底座**：tool schemas、retrieval policies、sandbox config、memory rules——这些"环境配置"是**可以被自动提议修改**的对象，由一个 Evolution Agent 持续提修订案。判据：**当 prompt 和技能都改不动了，往 harness 层找空间**（改 schema 描述、改检索策略、改沙箱权限）。
- **深度遥测（deep telemetry）**：记录 prompts、检索到的上下文、工具参数、编辑操作、快照——**不只看"结果对不对"，看"每一步给模型喂了什么"**。判据：**遥测维度覆盖"模型看到了什么"，而不只是"模型输出了什么"**；工具参数和检索上下文是诊断重灾区。
- 判据：**harness 修订要能 A/B：同一批任务，旧 harness vs 新 harness 的可复现对比**——没有基线就谈不上优化。
- 反模式：prompt 调不动就放弃；只记录最终结果不记录喂给模型的上下文；harness 配置改一次就不再回看。
- **提升层**：可复用 Skill（harness 优化 / 遥测纪律）。

## Harness 自改进三阶段：聚类失败 → 定向修改 → 留出验证（来源：arXiv Self-Harness 2606.09498 + explainx 2026-06-10 + Llama Stack 2026-03-01 实拉，与 §Harness 工程 分工——那条管"运行环境当优化对象+遥测"，本条管"自改进的流程与放行门槛"）
- **三阶段闭环**：①**弱点挖掘**——把失败轨迹聚类，找出**模型特有**的失败模式（不是通用 bug）：重复错误类型/缺失错误处理/工具使用低效/上下文管理失败/卡死循环；②**harness 提案**——每条修改**绑定一个具体失败机制**，小集合、多样且最小（防止过度泛化的大改）；③**提案验证**——回归测试 + held-out 任务上无退化才提升。判据：**没有 held-out 对比的 harness 修改不发布**——修了 A 例毁了 B 例是最常见翻车。
- **确定性自改进序列**：固定"每 N 次调用触发一次 evaluate_self()+improve_self()"（对测试集基准→重写自己的 system prompt）——不靠 LLM 自己决定何时改。判据：**触发是固定序列不是模型心情**；模型决定"要不要改自己"等于让考试者决定何时改考卷。
- 反模式：把失败当孤立个案逐个修；一次提交涵盖多个失败机制的大改；改了不跑 held-out 直接上线。
- **提升层**：可复用 Skill（自改进流程）。

## 后台 review fork：答案交付后静默复盘，只许动记忆和技能（来源：Hermes Agent Self-Improvement 深度分析 2026-05-29 + DeepSeek《Integrate with Hermes》实拉，与 §轨迹→技能自进化 分工——那条管"从轨迹提炼技能"，本条管"复盘进程怎么隔离"）
- **后台 review fork 五件套**：①**前台指导**——复杂工作流成功时告诉主 agent"该存/该补 skill"；②**迭代计数器**——跟踪距上次技能评审的工具密集工作量，到阈值触发；③**后台 review fork**——用户可见答案交付后，静默启动一个复盘 agent 带对话转录；④**窄工具白名单**——复盘 fork 只能调记忆和技能工具，**不能任意 shell/文件/网络**；⑤**不打扰用户**——复盘在后台跑，交付不阻塞。
- 判据：**复盘进程的权限 = "看得见对话，动得了技能库，碰不了别的"**——复盘 agent 被注入时爆炸半径只有技能库；白名单是复盘与主 agent 的本质区别。
- 反模式：复盘和主 agent 同权限；复盘结果直接改生产配置不经审查；复盘把完整转录再写回主上下文。
- **提升层**：可复用 Skill（自改进进程隔离）。

## 视觉双扩展模式：主动调用视觉工具 + 开放搜索补知识（来源：arXiv Agentic-MME 2604.03016 2026-04-03 实拉，与 §符号级导航 分工——那条管"符号定位"，本条管"图像输入怎么被主动加工"）
- **Visual Expansion（视觉扩展）**：模型主动调用视觉工具变换图像（裁剪/放大/增强/检测），不只用原图一次——**对模糊/局部/低对比度图，先加工再理解**。判据：**"看不清楚"时先想"哪个视觉工具能把它变清楚"**，不是直接放弃或猜。
- **Knowledge Expansion（知识扩展）**：现实任务常缺视觉内容之外的信息——主动走开放网络搜索补齐，视觉理解+检索知识组合。判据：**视觉输入只回答"图上是什么"，图外的事实（背景/来源/上下文）走搜索**。
- 判据：**视觉代理的调试对象是"工具调用链"（用了哪个视觉工具、搜了什么），不只是模型的视觉回答**。
- 反模式：原图看不清直接猜；视觉任务死等模型硬读，不调用增强工具。
- **提升层**：工作流（多模态调试）。

## trace 暴露的失败模式清单：四类日志指标看不出来的错（来源：Zylos《Agent Observability in Production》2026-05-29 + Zylos《Trace-Driven Debugging》2026-04-30 实拉，与 §深度遥测 分工——那条管"怎么记 trace"，本条管"trace 里专门找哪几类错"）
- **四类 trace 专属失败**：①**工具调用幻觉**（调真实工具但参数是编的——tool call span 显示模型生成的参数，执行前就能告警"参数含 schema 没有的字段"）②**静默失败**（工具返回了但结果是错的，无异常信号）③**方向错误**（任务完成、无报错，但输出整体错位——系统性错分类/漏记录/编造引用）④**幻觉上下文**（输出与检索上下文不符）。判据：**这几类错从日志/指标看不见，只能在 trace 里找**——调试时专门按这四类扫。
- **方向错误的 trace 特征**：所有 span 都显示成功、延迟 token 正常、失败只有"把输出和真值对比"才能发现。判据：**"看起来全对"是最难抓的失败——必须对照期望输出，不能只看执行成功**。
- 反模式：只看工具成功/失败信号；执行成功就认为结果正确；幻觉参数在 trace 里躺着不设告警。
- **提升层**：可复用 Skill（trace 调试）。

## trace→evaluator 引导：从生产失败直接生成评测器（来源：Datadog《Bits Evals》2026-06-09 实拉，与 §自改进三阶段 分工——那条管"失败聚类→最小修改→验证"，本条管"失败怎么变成评测器"）
- **失败样例是评测器的原料**：从生产 trace 和根因分析报告**生成 evaluator 候选**（对齐观测到的失败模式）——不是抽象地"写个评测器"，是从真实失败反推"什么样的评测器能抓住这类错"。判据：**评测器应由失败模式驱动生成**，而不是从通用模板抄。
- **产物形态多样**：可生成 LLMJudge（Python）、prompt 级、schema 级等不同格式，适配已有评测框架。判据：**生成物要能直接跑**，不是论文式的建议。
- 与 §held-out 验证 的衔接：生成的评测器先在 held-out 失败集上验证"能不能抓住它该抓的错"，再进回归。
- 反模式：评测器从零手写不看失败样本；生成后不验证抓错能力；评测器覆盖不到线上真实失败模式。
- **提升层**：工作流（评测治理）。

## harness 演进三问：定期问"哪些脚手架能拆"（来源：Claude《Agent Harness Design: 3 Patterns》2026-04-02 实拉，与 §Harness 工程 分工——那条管"harness 建什么"，本条管"harness 怎么随模型变强而精简"）
- **①lean on the model**：优先用模型已经会的能力，**别把模型能力复制进 harness**——harness 里的每一条指令/工具/规则都要问"模型自己会不会"。判据：**模型越强，harness 该越薄**；把模型已会的写进 harness 是重复劳动还增加出错面。
- **②ask what you can stop doing**：定期盘点"哪些脚手架现在可以拆掉"——早期为兜底加的 prompt 段/校验/回退，模型变强后可能成了噪音。判据：**"删掉试试"是合理的实验**，不是冒险——拆掉后跑回归确认没退化。
- **③carefully set boundaries**：边界仍然要设（工具范围/权限/安全），只是边界要跟着能力重新校准。判据：**harness 演进 = 增删平衡**：能力侧做减法，边界侧做校准。
- 反模式：模型升级后 harness 一字不改；把模型已会的能力写进 prompt 造成冗余；只加不拆，harness 越来越胖。
- **提升层**：工作流（harness 演进）。

## 二·五·六、修复不能由"容错装置"构成：先问它纠正根因，还是安排活下去（来源：GitHub `thedotmack/claude-mem`·`docs/merge-rubric.md`，2026-09-16 实拉）

> 判重留痕（sa 双键检索）：`thedotmack/claude-mem` 与 `merge-rubric` 全库零命中，新源；概念词「兜底 / fallback / 重试掩盖」命中 `wb-execute-discipline` §失败路径三选一——**那条管"写代码时失败怎么处理"**，本条管**"评审一个修复时，它到底是不是修复"**，场景与判据不同，按相邻扩展落地并写明分工。

**先判"这算不算 bug"**：bug = **今天确实存在的错误行为**（错输出 / 丢数据 / 崩 / 错状态码 / 路径从没匹配上 / 参数从没传下去）。以下**都不是 bug 修复**，混进来会稀释评审注意力：
- **新功能 / 新开关 / 新模式**；**加固**——"让它更鲁棒"但**没有任何行为今天是错的**，原文判词 `armor for a wound nobody has`；**性能与成本调优**（限流/批处理/缓存，本来没坏）；**可观测性**——`logging a failure is not fixing it`，把失败记下来不等于修了它；**已被修掉的 bug 的二次修复**（`superseded fixes`：当前 main 上已不存在 = 穿着 `fix:` 前缀的 no-op）。

**再判"这个修复是不是由容错装置搭出来的"**——对 diff 里**每一个新条件**问一句：
> **它是在根因上纠正逻辑，还是在发现失败后安排活下去？** 前者是修复，后者一律打回。

会伪装成修复的七种：
| 伪装 | 识别特征 | 原文判词 |
|---|---|---|
| 守卫 | `try/catch` 记日志继续跑、永不抛出的包装、`best-effort by design` | 守卫触发后，**失败依然存在，只是更安静了** |
| 熔断器 | 失败预算、冷却状态、隔离台账、持久化的重启额度 | 这些状态的唯一职责是记住"有多坏" |
| 兜底 | try X 失败转 Y；主数据为空时用合成占位内容 | `The fallback's existence is an admission that X is broken and nobody fixed X.` |
| 重试 | 把重试当韧性加上去 | 重试**确定性失败**= 慢一点的失败；重试**瞬时失败**= 把缺陷藏起来 |
| fail-open / fail-soft | "优雅降级""绝不阻塞编辑器"、吞掉并警告 | 错误必须响亮地冒出来，否则下一次排障要付利息 |
| 自愈 / 看门狗 / 回收器 | 孤儿清扫、内存轮询重启进程、卡死自重启 | 这些系统**在生产里管理 bug，而不是把 bug 从代码里删掉** |
| 截断 | 裁剪 / 切片 / 静默丢弃，让症状看起来装得下 | 输出太大/错/重复 → **去修生产者，别拿剪刀对付结果**（正确位置执行用户显式要求的 `limit` 是语义，不算截断） |

**反向鼓励的三类**：① **删掉**上面任何一种（删一个重试、删一条兜底、删一个静默 catch 是最好的 diff）；② **fail-fast 转换**——把静默容忍在它该在的边界换成响亮、即时、有类型的错误；③ **朴素的正确性**——对的顺序、对的路径展开、对的引号、对的 flag、对的调用机制、WHERE 里对的列。**一个 `if` 本身没错，错的是它站在错误逻辑前面当 bouncer。**

**规模 check**：修复的体积要与错误体积成比例——**一行错，大约就是一行改动 + 测试**。一个单行缺陷躺在 400 行 diff 里，多出的 399 行必是上表某种伪装，先认出是哪一种再打回。原文：`A wrong comparison does not need 350 lines of ledger to become a right comparison.`

- **不许部分给分**：任一节不过 = 整个打回（`no partial credit`）；**只有一半 diff 合格，就只提那一半**重新提交。
- 与既有条目的分工：§二·五 管"补丁修得真不真"（变体来自根因 + 基线两边验）；§二·五·五 管"补丁打在哪"（收敛到调用方共享处）；**本条管"这个 diff 配不配叫修复"**——三道关卡顺序是：是 bug → 是修复不是容错 → 位置对 → 才谈验证。
- 与 `wb-execute-discipline` §每个失败路径三选一 的分工：**那条是写代码时的错误处理纪律**（失败路径必须回响、禁止 `?? fallback` 藏主路径失败）；**本条是评审/自审修复时的判据**（这个"修复"是不是只是给它穿了盔甲）。同一枚硬币的两面，不互相替代。

## 二·五、修复验证：补丁是待验证假设

来源：GitHub `trailofbits/skills` 的 `post-patch-validation`（Trail of Bits 安全技能库，2026-09-14 新合入；与本地 §一·3「修复必须配回归」、§二 六步循环互补——那条管"有没有回归"，这条管"这个修复是不是真的修好了"）。

**核心判断：修复存在 ≠ 问题解决。** 修完之后，**补丁是待验证假设，不是结论**。

1. **四样东西都不是证据**：diff 很小 / 作者可信 / 与上游官方补丁一致 / 原 PoC 不再复现。它们是背景信息。**原 PoC 失效只说明这一条路径堵上了，不说明根因堵上了。**
2. **变体必须来自根因，不是原 payload 的表面变异**：同一个根因往往有多条触发路径。枚举被修复点触及的——**兄弟调用点**（同样的坏模式在别处复制过）、**备选回调与输出通道**、**错误路径与清理/回滚路径**、**边界值**。至少测一条独立于原始复现的根因变体。
3. **每个验证用例必须两边都成立才算数**：断言的是"安全/正确行为"，它**必须在有问题的旧基线上失败**、在修复后通过。两个版本都通过的测试什么也没证明。旧基线那次失败要**确认是我写的断言挂了**，不是 harness 根本没跑起来（见 `wb-artifact-verification` 的到达标记）。
4. **先钉不可变基线**：优先精确 commit / 版本号；未提交的改动**先导出 patch 文件**，不在用户的工作树里做验证。
5. **验证期间不得改补丁**：失败退回给改的人，重新钉一次再跑。**偶发重跑通过了也不能采信**——保留第一次钉住的结果，先修不确定性再重跑。改测试让它变绿同理（§四）。
6. **别把无关失败算在补丁头上**：修复后新出现的失败，**先在旧基线上跑同一个检查**——旧基线也失败 = 本来就有，不是这个补丁引入的。分不清因果就报"不确定"，不要编一个因果。
7. **新旧两边都失败 ≠ 同一个失败（#304 更新，2026-09-15 实拉）**：归因未解决时**两边日志都保留**、明说"归因未解决"——**退出码相同不代表失败原因相同**（typo 和真 bug 可以都退出 1）。逐条比对失败内容，比不出就报未解决，不猜。
8. **超时单独记为缺口，不作废整体（#304 更新）**：一个检查超时 = 该检查证据缺失，**不是"回归"也不是"通过"**，也不因此作废其他检查的发现——无关超时不应隐藏已证实的失败（与 `wb-artifact-verification` findings+gaps 双通道配套）。

### 合理化借口 → 必须的回应

| 借口 | 回应 |
|---|---|
| "原复现路径已经不复现了" | 再测至少一条独立的根因变体 |
| "全量测试都过了" | 基线复现 + 目标行为仍要单独证明 |
| "和官方/上游补丁一致" | 出处是背景，不是证据 |
| "diff 就几行" | 调用方、失败路径、清理路径照样要跑 |
| "重跑一次就过了" | 保留第一次钉住的结果，先修不确定性 |
| "没有别的变体了" | 去查兄弟调用点与边界；查不出就**如实说没覆盖到**，别默认通过 |

## §〇·五、第三类失败：情境错误——代码对、模型也没坏，错在被喂进去的东西（来源：GitHub `footprintjs/agentfootprint` README，2026-09-18 实拉，★20 新源）（自 SKILL.md 正文下沉 2026-09-28 r212，原文零删减）

## 〇·五、第三类失败：情境错误——代码对、模型也没坏，错在被喂进去的东西（来源：GitHub `footprintjs/agentfootprint` README，2026-09-18 实拉，★20 新源）
§〇 的二分（模型行为 vs 代码）漏了一类：**代码没有报错、基建健康、答案读起来也通顺，但结论是错的**——因为**模型被给的东西**里有某一条影响了它。经典日志**只记录代码做了什么，从不记录上下文做了什么**，所以这类失败在日志里完全干净。

| 错误类 | 根因在哪 | 传统排查手段 |
|---|---|---|
| 基建（崩溃 / 超时 / 500） | 系统 | 日志、监控 |
| 业务逻辑（分支错 / 算法错） | 代码 | 栈回溯、断点 |
| **情境（选错工具 / 信了错事实 / 跟了错指令 / 用旧信息作答）** | **喂给模型的东西** | **以前没有** |

- **四种典型失效形态**：① **选错工具**——两个工具描述读起来几乎一样（"孪生工具"），模型在它们之间瞎选；② **信了错的事实**——某个工具返回了它，或被注入的一条事实落地了；③ **跟了错指令**——错误的技能/引导被触发，或**早触发了一轮**；④ **用过去作答**——上一轮的内容或过期记忆渗进了本轮。
- **判定判据**：`无报错` + `输出读起来合理` + `结论确实错`，且**固定种子重跑结果一致**（不是随机飘）→ 不是模型随机性，是上下文里有一条是决定性的。**分型错了，你会在代码里找一个根本不在代码里的 bug。**
- **定位手段是对"上下文条目"做消融，不是对代码行做二分**：逐条摘掉可疑的上下文（某条事实 / 某个技能 / 某几轮历史），用**固定种子重跑多次**，看结论是否翻转。判据：**要"多次全部翻转"才算定位到**（如 3/3 seeded reruns 翻转）；只翻转一次不够，那可能只是采样噪声。与 §二 六步循环的最小复现分工：那条缩小**代码与输入**的范围，本条缩小**上下文条目**的范围。
- **结论必须留因果边，不能事后叙述**：每个结论要能回溯成 `结论 ← 规则 ← 派生数据 ← 原始字段`，**每一跳都是当时真实记录下来的边**。事后口头叙述出来的因果链没有定位价值——它和被它解释的错误一样不可核查。
- **孪生工具在目录层静态 lint，别等跑完看 trace 猜**：把"描述近乎相同"的工具对在**运行前**标出来（相似度 margin 过窄即告警），这是静态检查，成本远低于事后从 trace 里反推为什么选错。与 `wb-ponytail` §相似命名的工具靠示例区分 互补：**那条给示例让模型分得清，本条在目录层先把这对找出来**。

## §二·七、失败永不阻塞主回复：回复路径上每一步都要 等 5 节（自 SKILL.md 正文下沉 2026-09-28 r212，原文零删减）

## 二·七、失败永不阻塞主回复：回复路径上每一步都要有超时或回退（来源：OpenClaw 官方 docs.openclaw.ai·concepts/memory-architecture，2026-09-15 实拉）
把"辅助子系统"接进主流程时（记忆检索、召回、日志、打分、外部查询、埋点），**每一步都必须有超时或回退，最好两者都有**。硬判据：**子系统挂掉只能降低质量，不能吃掉这一轮**——用户拿不到回答、而原因是"某个辅助服务连不上"，那是设计错误，不是偶发故障。

排查 / 评审时的落地动作：画一遍回复路径，对每个依赖问"**它挂了会怎样**"。答不出来，就是这里缺超时或回退。同理，新加一个外部调用却不带超时，是引入阻塞面的改动。

## 二·八、部分完成是合法的失败态：先解错、重跑同命令、再核对残留（来源：OpenClaw·concepts/memory-provenance，2026-09-15 实拉）
清理 / 迁移 / 批量删除类操作失败时，按顺序做三件事，**不许跳步**：

1. **不手改状态、不手删残留**。尤其**不许为了消除报错而删证据**（语料行、来源行、审计行）：证据要保留到依赖它的产物清理完为止——提前删证据，会把"可诊断的失败"变成"查不出的损坏"。
2. 先解决报出的错误 → **重跑同一条命令**（不是换个变体、不是手工补做）→ **再跑一次预演核对残留**。
3. **失败留下部分清理是预期内的**：判据是"再核对时无残留"，不是"我觉得清完了"。

## 二·九、回收条件由"是否仍被引用"决定，不由"多久没动"决定（来源：OpenClaw·concepts/memory-provenance，2026-09-15 实拉）
清理中间产物 / 来源行 / 镜像 / 缓存时用**引用计数式**判据：只有在**存活条目、留存的前像、日记摘录、索引快照都不再引用它**时才回收。

用"多久没被访问 / mtime 多久没动"当回收判据，会在"长期没人碰但仍有引用"的对象上误删——典型受害者正是让失败可被溯源的那批来源行与审计行（**清理工具删掉诊断依据，下一次失败就查不出根因**）。配套：清理前先问"谁还在引用它"，答不出就不删。

## 三、卡住时（超过 3 轮无进展就换打法）

- **换假设方向**：挑那个"最不可能、但一旦成立就解释全部现象"的假设试一次
- **二分定位**：版本回退、注释掉一半、换输入、上游/下游各切一半
- **写出来**：把从输入到失败点的完整链路用文字写一遍（写到第三行常常自己就发现了）
- **查边界现场**：空值 / 并发时序 / 编码 / 时区 / 缓存 / 权限 / 环境变量 / 相对路径
- **环境差异**：本地复现不了 → 逐项对比 版本、依赖锁定、配置、数据、运行用户
- **看首个异常**：栈底那个通常是被包装后的噪声，根因常在上游第一个异常

## 四、反模式

- 一次改好几处 → 不知道是谁修好的，还埋了新坑
- 靠重启 / 清缓存 / 再试一次过关 → 根因没找到，必然复发
- 只看报错最后一行 → 漏掉首个异常
- 改测试让它通过 → 测试是裁判，不是被告
- 无回归就收工 → 同一个 bug 回来第二次
- "我读了一遍代码，应该是这里" → 假设当结论用，跳到第 5 步
- 滑窗规避反模式（来源 Qoder r265-C 审计落地，arXiv 2609.30217 EvasionBench，2026-09-26 实拉）：重试循环会把"相关上下文"推出监控/评审窗口，让同一操作在第 N 次重试时"看不见地"通过——监控须锚定操作序列而非近期窗口，跨轮拆分的动作也计入同一意图链。

## 归因排名的三个诚实边界：主题混淆 / 平顶 / 缺席者（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/contrastive-influence.md`+`ranking-confidence.md`+`missing-context.md`，2026-09-18 实拉）

与 §〇·五 上下文消融分工：**那条确立"消融才是因果层"，本条管排序器（ranker）在给出因果之前有哪些必须自曝的盲区**——排序只负责收窄，永远不负责定罪。

- **因果确认有三条接口，对象不同、动作不同**：① **排序**（`scoreInfluence` 类）只给**在场**嫌疑一个先后；② **消融**——**移除**在场的嫌疑，看结果是否翻转；③ **缺失上下文**——**恢复**缺席的嫌疑（加回去重跑），翻转才是因果。判据：**你无法消融一个不在场的东西**（`You cannot ablate what isn't there`），"不知道为什么错"时先问是"在场的有问题"还是"该在的没来"，选错接口就永远查不到。
- **相似度排序有内置的混淆项：主题中心的无辜者会排到真凶前面**。按"更像模型的最终答案"排序时，**决策所关于的那个主题**天然像任何答案——对的答案和错的答案都像。退款决策引用了退款政策，于是无论模型判"批准"还是"拒绝"，政策文本都高分；答案错了时它依然高居榜首，把真正的元凶压在下面。判据：**"和主题高度相关"≠"导致了这个结论"**，纯输出相似度分不开这两者。
- **消混淆的办法是拿一个参考输出做差**：`contrastive(e) = sim(e, 实际输出) − sim(e, 参考输出)`。两边都像的（主题无辜者）两项抵消趋零；**只对错误输出像的**才凸显。判据与适用边界：**只在有参考输出时成立**——回归 / 评测调试场景（上次的正确结果、golden answer、测试用例的期望输出）用它；冷启动定位没有参考对照，用了也没信号（`answer == reference` 时全部为 0，这是设计而非故障）。
- **"没有明显第一名"比"分数低"更是信号**：缺席 / 挤占类错误（历史被截断、上下文稀释、lost-in-the-middle）的真凶是靠**挤走**关键内容起作用的，它自己完全不必像答案，于是排名必然很低——**常常低于一个答案恰好提到过的无辜来源**。此时排序器照样会交出一个自信的 rank-1，而它是错的。判据：**症状不是低分，是"平顶"（flat top）**——没有任何来源明显领先时，不要把 rank-1 当答案，改为对整个短名单做消融覆盖。
- **"有明确领先"只是"排名有领先"的代理，不是"它是原因"的代理**：一个答案反复援引的高相似无辜者照样能赢。**两个分支都要消融确认**（有明确领先时确认领先者，没有时覆盖短名单）——`clearWinner` 只决定你消融几个，不决定你消不消融。
- **判"是否领先"的门槛要选能跨尺度迁移的口径**：绝对差 `s0 − s1 ≥ t` 在不同打分尺度下对**同一个相对差距**给出不同判定（`[0.10, 0.09]` 判"不明显"、`[1.00, 0.90]` 判"明显"，两者其实都是 10%）；相对比率 `(s0 − s1)/|s0| ≥ t` 跨尺度一致。判据：**换 embedder / 换答案长度 / 换评分实现后结论就变的阈值，是没校准过的阈值**——阈值常量要标清它是相对量还是绝对量，不确定时先扫一遍再定。
- **缺失上下文靠"集合差"定位，不靠语义比对**：把上下文当**带稳定 id 的单元**（每次注入、每条记忆、每个工具结果都有 id），则"丢了什么"是一个 id 上的集合差 `dropped = available − sent`（候选集 = 窗口化/截断之前为该轮装配的单元；sent = 最终真进了 prompt 的）。这是 O(n)、精确、确定性的，**不需要 embedding、不需要 LLM，也不用语义比较大块文本**——记忆总量多大都无所谓，你 diff 的是那一轮的**有界候选集**。
- **被丢掉 ≠ 有问题**：大多数被丢弃的上下文是**被正确丢弃的**，所以 dropped 列表只是候选，不是原因；确认方式与消融镜像——**把它加回去重跑，结果翻转才是证据**。速度优化（按与任务的相关性排序后再逐个恢复测试）只是可选层，**核心查找必须保持纯集合差**。
- **两类"没拿到"要分开治**：集合差只抓**截断 / 稀释**（曾可用但掉出窗口）；**从未可用**（相关记忆检索根本没捞出来）是另一回事，它需要**相关性信号**而不是差集。判据：先分清"它没进来"和"它从来就没到过候选池"，两者用错工具都查不出东西。

## 消融只取一个读数就漏掉一类 bug：质量翻转之外还有成本读数（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/two-score-localization.md`，2026-09-18 实拉）

与 §归因排名的三个诚实边界 分工：**那条管"排序器在定罪之前有哪些必须自曝的盲区"，本条管"消融只测答案对不对时，会漏掉哪一类真 bug"**。

- **答案对了不等于没坏——还有一类"静默决策 bug"：绕了远路，但照样答对**。一条误导性的上下文可以让 agent 在早期选错工具、多绕几圈，随后模型自己修正、最终答案正确。此时 `verdict`（质量）读数是"无变化"，而 `cost`（圈数 / token）实打实多付了。判据：**正确性基准和 token 仪表板都看不见它**——前者只看最终答案，后者只看总量、不做归因；只有"逐条消融 + 同时读成本"能把它捞出来。
- **一次消融取两个读数，不要开两套实验**：消融本来就要摘掉嫌疑项重跑，只要 runner 返回 `{ output, cost }` 而不是一个裸字符串，同一批重跑就同时给出质量分与成本分，**零额外运行**。判据：**另开一套成本实验 = 两份噪声 + 一次额外的对齐**，两个读数不落在同一次重跑上就不能相减。
- **2×2 分型，四个格子四种处置**：答案翻转 × 成本稳定下降 → `both`；只翻转 → `content-bug`；**只降成本 → `cost-cause`，即静默决策 bug**（最该被抓、最难被抓）；都不变 → `no-detected-effect`。
- **成本读数必须过安慰剂对照才成立**：移除任何东西都可能因为良性路径波动而少跑一圈，所以"成本原因"必须**比"移除那些并不改变答案的条目"带来的下降更多**（用留一法算出安慰剂带）。判据：**没有对照的成本差只是噪声**；只省了一圈（`+1` loop）尤其脆——**确定性 ≠ 鲁棒性**。
- **"稳定"的口径是符号一致 + 没有任何一次更贵**：跨多个种子符号一致，且**没有任何一次消融重跑比基线用得更多**。一次更贵就否定稳定性，不是取平均。
- **"移除它成本下降"是必要性，不是浪费**：那条可能是承重脚手架（摘掉后走了捷径、省了圈数，但也没干它该干的事），所以只能写 `reducedCostOnRemoval`，**永远不写"浪费"**。判据：**成本读数不判好坏，只判"它是不是这笔开销的相关项"**——值不值得删是另一个决定。
- **没有检出效应 ≠ 无辜**：过度决定（overdetermination：两条不同路径都能到同一个答案、圈数也一样）会让质量与成本两个轴都读不出东西。结论一律记 `no-detected-effect`，**不记 `innocent`**。与 §被丢掉 ≠ 有问题 同向但对象不同：那条管 dropped 候选，本条管**已经测过的嫌疑**。

## 诊断装置自身的可信度：绿色由计数挣得，"没查过"永不读成"没问题"（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/trace-debugging.md`，2026-09-18 实拉）

与 §消融只取一个读数 分工：**那条管"消融要测哪几个量"，本条管"把结果报告出来的那一环自己有没有撒谎"**——一个从没跑过的检查和一条查完没发现的记录，在多数报告里长得一模一样。

- **"检查跑过、它覆盖的都没被违反"与"这个缝根本没注册检查器"是两种状态，报告必须分开写**：前者是证据，后者是空缺。检查器行（哪几个检查、各跑几次、几次出结论、几次不适用）**要作为答案的一部分一起给出**，不能只给结论条数。判据：**只读结论数的报告无法区分"查过了没有"和"查了没查到"**，而这两种情况的下一步动作完全相反。
- **绿色头条由计数挣得，不由沉默挣得**：只有 `checked` 遭遇之和 ≥ 1 才许打印"检查跑过，无违反"，并且要**写出这个数字**；全是 `unreachable` / 出作用域 / 注册了却没遇到对象的运行，一律读 `⚠ NOTHING WAS CHECKED` 并给出原因。判据：**沉默不是健康——默认输出"0 条发现"是最省事也最会骗人的写法**。
- **注册了却 0 次遭遇 = 接线腐烂（wiring rot），不是干净**：检查器装上了却从没碰到它该查的东西，说明 seam 装错位置、或结构变了而检查没跟着走。判据：**"装了"和"生效了"要分别计数**，装了不生效比没装更危险，因为它占位了你的注意力。
- **三种缺席各有各的句子，永不合并成"无问题"**：① 产物根本没有事件尾 → `no finding evidence`（这份东西没带证据通道）；② 尾在但通道是空的 → 说明**为什么**空；③ 报告过发现、但尾已不再携带 → `evidence missing`。判据：**"没找到证据" ≠ "没有错误"**，两句话分开写；与 §被丢掉 ≠ 有问题 同向，对象从"上下文条目"换成了"缺陷记录本身"。
- **只答检查器真能产出的缺陷类，其余回"答不了"而不是空列表**：缺陷类枚举里没有检查器的那一类（如"重复执行"），被问到时明确回 `⚠ UNANSWERABLE`。判据：**关于某一类缺陷的沉默，不是该类不存在的证据**；给空列表等于让读报告的人自己补上"看来没问题"。
- **关掉采集开关不会让运行变干净，只会让读它的工具报告"证据通道缺失"，并指名是哪个开关关的**：`events: false` 不是"少记一点"，而是下游必须说"这个通道没有数据，打开 X 才能回答这个问题"；干脆不下订阅（no wildcard subscription）也好过下完再忽略。判据：**省成本的开关必须换成一个诚实的缺口，不能换成一片空白**——空白会被当成通过。
- **"模型提出的参数"与"实际执行的参数"必须分两栏看**：治理 / 中间件规则在 before-tool 改写参数时，这件事**在对话里完全不可见**——模型在历史里读到的是自己提的那一份，工具真正跑的是另一份。一次工具调用的事实散在四处（assistant turn / 中间件台账 / tool turn / 事件流），要 join 成一行，前提是先承认它们是四份。判据：**凡是"我明明传了 X，它却按 Y 跑"的幽灵 bug，先比对这两栏，不要去改业务代码**。
- **长得一样的 id 不代表同一个命名空间**：工具自己记录的内层运行 step id 与外层运行 id 同形但不同域，外层的 `trace_node` / `get_value` 不接受内层 id；越界要明确标记（"这是内层 id"），不能静默返回查不到。判据：**同形 id 混域时，"查不到"会被误读成"这个步骤没执行"**。


## 能力"装了不生效"的静默失败分型：四级台阶 + 双验证通道 + 残留注册（来源：dsh-plugin.org DSH 插件诊断教程族 develop-plugin-errors / plugin-not-loading / plugin-not-activate / plugin-runtime-crash / fix-service-already-registered / develop-plugin-debug，2026-09-18 实拉，新信源首轮）

能力注册类故障绝大多数**不抛异常**：没有语法错、编译器不警告、日志一片安静。判据——把"装了不生效"当**症状**处理，先建 symptom → cause → fix 表，别干等栈回溯。DSH 的九条静默陷阱（现象/根因）：完全不识别（导出形式不符）/ 停在 PENDING（缺 `inject` 声明）/ 变 FAILED（`apply` 里有阻塞或一次性副作用）/ 有输出但调用方拿不到字段（返回散文而非符合 schema 的值）/ 重放时崩（presenter 不纯，掺了 I/O 与时钟）/ 装完没反应（包缺 patch 清单）/ 装完宿主崩（产物没带构建输出）/ 卸载后定时器还在跑（资源没交给 effect 拿 disposer）。

- **生效四级台阶：声明 → 安装 → 加载 → 生效。逐级分型，别跳级猜**：
  - 没**声明** → 装了也白装：缺清单（`dsh.bundle`）会被当"普通依赖"装进去、永不加载；缺依赖声明（`inject`）则服务永远不到。两者都归为 "installed but useless"。
  - 没**装载**（没重启 / profile 错 / 包不全）→ 走固定四步清单「重启 → 列插件 → 验 profile → 读启动日志」，按序修「重装 → 换正式构建 → 回滚」。
  - 装载了却**不生效** = 本技能 §诊断装置可信度 的 wiring rot（注册了 0 次遭遇）。**四级台阶的价值：先钉住断在哪一级，再动手**——把"从没加载"当"代码坏了"去改代码，是最常见的时间浪费。
- **声明先于使用（declare-then-use）**：能力必须先显式声明它依赖什么，否则依赖永远不到，且以**误导性的"缺某属性"**形式报错——**报错指向缺失的属性，根因是缺失的声明**。判据：见 `cannot get property X without inject` 式报错，先查声明、别去查 X。迁移到技能系统：技能要显式声明所需工具（allowed-tools），否则"装了但用不上"。
- **两条验证通道验证不同的事，混用会把"根本没装上"看成"代码坏了"**：判据问题是"你在验证**加载**还是验证**安装**"——加载验证用最短反馈环（源码挂载 + 重启），安装验证用产物装入（打包后重装）。**"它不加载"与"它装不上"是两个失败面**，别用"装不上"掩盖"不加载"。
- **症状指向的"对象坏了"未必是数据问题**：进程级全局单例被**先注册者永久占用**，之后所有相关操作都失败，直到重启进程；而"**挂载期失败 ≠ 数据损坏**"（会话数据其实是完好的）。同一根因还会分成**显式失败**与**静默闪烁**两种形态。判据：先问"这是挂载期还是数据期"，再问"是谁先占了那个 id"。
- **残留注册要算进嫌疑**：异常拆除的资源没释放，之后会和**自己上一次的残留**冲突（"its own leftover registration"）。排"重复注册"时，把**自己上一轮的残留**列进嫌疑名单，别只怀疑别人。

## 幻影字段与结构性归因：声明存在 ≠ 会被写入 / 补盲点别拿两个代理相乘（来源：`footprintjs/agentfootprint`·`docs/proposals/003-per-loop-influence-credit.md`（2026-09-18 实拉，A 轮未取的新设计提案），与 §诊断装置自身的可信度、§三种缺席、§静默失败分型 互补——那三条管"报告怎么写 / 缺席怎么分 / 装了为什么不生效"，本条管"**拿来做判定与分组的那个字段本身是不是真的有值**"与"**补一个归因盲点该用哪种形状的解**"）

- **幻影字段（phantom field）：声明了、但从来没人往里写**：源文档的引擎字段 `loopIteration` **已声明**，却被实测证实**引擎从未填充**——只在一个叙事渲染器里被算出来过，且**不在提交记录里**。任何按它分桶的设计或排查，都是建在一个幻影字段上。判据：**用一个字段做分组 / 判定 / 统计之前，先验证"它由谁写入、在哪条落盘记录里能读到"**；能从可观测信号派生时，**优先用派生**（源文档改用"重复的 stage id + 递增执行序号 + 父链接"派生循环计数）。验证方式要落在磁盘证据上：grep 写入方、在真实记录里读出非空值，**不靠类型声明与文档**。
- **补盲点要找结构事实，不要拿两个代理指标相乘**：源文档要修"只看后向链"的盲点，正解是**前向可达性闸门**（该来源的前向可达能不能触达后续环节，触达不到就闸到 ~0）；被否决的方案是把 forward × backward 两个相似度代理相乘——**那只会放大主题相似项**，等于把"长得像"当成"有影响"。判据：**想补一个归因 / 评分盲点时，先问有没有一个结构事实能直接判它（真被读过 / 真可达 / 真被调用过）；有就别用相似度代理叠加**。代理相乘不会变成证据，只会让噪声更自信。
- **代理就是代理，要在产物里留标记**：注入的锚点（把用户问题当作参考节点接进图）是**代理，不是真实的依赖边**，源文档要求给每个消费该锚点的节点打 `incompleteSources` 与 `forward-anchor:injected` 标记。判据：**凡是为了算得出来而人为接进去的节点 / 边，必须在结果里显式留痕**，不许让它和真实依赖混在一个字段里。

## 降级还是通道断：先看骨架在不在 / 迟到订阅者一条都收不到（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/streaming.md` + `CLAUDE.md` §Invariants，2026-09-19 实拉，A 轮主源；与 §诊断装置自身的可信度、§证据通道缺失 互补——那两条管"检查器有没有遭遇、开关被谁关了"，本条管"**通道还在不在，以及它从哪一刻起才存在**"）

- **降级运行下骨架必须照发**：没有 `stream()` 的 provider 不发逐 token 事件，但 `llm_start` / `llm_end` / `tool_start` / `tool_end` 与轮次 / 迭代框架**照发不误**。判据：**先数骨架事件在不在——骨架在、细节少 ＝ 降级；骨架也没了 ＝ 通道断，不是降级**。把降级当成断链，会去修一个没坏的通道；把断链当成降级，会一直等一个永远不会来的细节。
- **事件流没有回放：迟到的观察者不是少收几条，是一条都收不到**：listener 在场判定是**丢弃而不是排队**（源文档原话 drops, not queues）。判据：**探针 / 记录器必须在被观测对象启动之前挂上**；挂晚了不报错、不补发，只表现为"这一轮什么都没记到"。与 §三种缺席 分工：那条管"查完没发现"与"压根没查"要分开写，本条给出零命中一个具体来源（**订阅时点晚于运行时点**）。
- **没有缓冲的通道，"可用性"是一个时点不是一个状态**：判据：**问"它现在开着吗"之前，先问"它是先于被观测的东西打开的吗"**。
- **匹配器零命中，先查它匹配的是不是真实形式**：源文档 landmine——分支 stage id 的真实形式是 **BARE**（`'final'` / `'tool-calls'`），而文档常量里写的是前缀形式；**按文档常量写的 matcher 在真实运行里一条都匹配不到，且静默**。判据：**匹配规则要按运行时实际出现的形式校验，并把"这个匹配器到底会认几种形式"显式写出来**；与 §检查器不许与路由器矛盾 分工——那条管两套规则不一致，本条管**同一事物的两种书写形式**。

## 观测是遍历期内的被动旁路，不是事后批处理（来源：GitHub `footprintjs/agentfootprint`·`docs/guides/recorders.md`「An agent that can't be measured can't be improved」「Observation ... is passive — it watches agent execution without changing behavior ... all during traversal, never as a post-processing step」（2026-09-19 B轮独立实拉，此前未读），与 §降级还是断链 / §迟到订阅 互补——那两条管"订阅时点与通道存活"，本条管"测量该长在哪条时间线上"）

- **测量必须挂在遍历期内的旁路，不要做成事后重读**：源文档把记录器 / 事件流明确为"traversal 期间的被动观察者，绝不做 post-processing"。判据：**要度量一个 agent，就在它跑的时候顺手记，不要在跑完之后去重新读一遍会被重读 / 老化的结果**——你事后量到的，可能已经不是它当时决策时看到的那个窗口。
- **每条观测事件自带执行坐标，才能回溯到精确步骤**：源文档的事件信封 `meta` 携带 `runtimeStageId` / `subflowPath` / `turnIndex` / `iterIndex` / `runId` / timing——任何一条度量 / 错误都能指回"它发生在哪一步"。判据：**一个观测点若不能回答"它属于哪一次迭代 / 哪一个子流程"，就是一条丢了上下文的孤立数字**，归因时既证不了因果也排不了序。
- **跨边界的错误信息要脱敏，异常原文不外传**：源文档在托管适配器里把"handler 抛出的异常文本"洗成 sanitized 消息，**未捕获异常的原文永不越过边界**。判据：**要把一个错误告诉另一个进程 / 用户时，传的是"发生了哪类失败 + 怎么修"，不是堆栈原文**——原文里藏着路径 / 内部状态 / 第三方线索，跨边界就是泄露。

## 先切轮再归因：重复结构的数据要按单元切分再测量（来源：GitHub `footprintjs/agentfootprint`·`docs/proposals/005-trajectory-assembler.md`「The localizer saw the whole run as one flattened bag … a ReAct agent thinks in rounds … slice into iterations first」, 2026-09-19 实拉，学习轮 r111）
- 当被观测对象有「重复结构」（迭代/轮次/批次）时，必须先按单元切分再测量与归因，否则把整段运行的因果抹平成一个平均数：既找不到「这一轮真正引入的坏来源」，也走不回「哪个决策导致错答案」。
- 判据＝如果一份数据天然是 N 个同样结构的单元，却只有一个跨全部的汇总指标，那个指标在说谎——它把「第 3 轮才进来的坏事实」均摊到了每一轮。
- 与 §归因排名的诚实边界（平顶/缺席者）、§消融只取一个读数、§固定种子重跑 互补——那些管「排名怎么排才不被平顶误导/一个读数漏掉一类/基线要稳」，本条管「**被测对象本身是不是该先被切成轮**」。


## 操作顺序有承载：某变换必须在会拒绝未变换输入的闸门之前完成（同来源 trajectory-assembler.md 关联 `findings-ledger-spec.md`「the peel is the FIRST read of tc.args … before validateToolArgs, or a strict schema loops outputRetry on a correct answer」, 2026-09-19 实拉，学习轮 r111）
- 当一个字段的「剥离/转换」必须在「校验/拒绝」之前发生，这个顺序不是风格而是正确性——把剥离放到校验之后，正确输入会被严格 schema 当成非法而拒绝，甚至陷入重试死循环。
- 判据＝凡是有「先 X 再 Y」且 Y 会拒绝未 X 的输入，X 必须发生在 Y 之前一行，且 Y 读的是 X 之后的结果，不是 X 之前的原值。
- 与 §生效四级台阶、§接线腐烂、§匹配器零命中（真实形式）互补——那条管「能力怎么才算生效/接线怎么腐烂/匹配器要匹配真实形式」，本条管「**两个操作谁先谁后的顺序本身就是一项正确性约束**」。

## 二·五·五、修在调用方收敛处：只修被报告的路径 = 修好了报告，没修好 bug（来源：riekelt/principal-engineer·grounding-before-coding，2026-09-15 实拉）

- bug 报告只点名**一条症状、一条路径**；动手前先找齐通往你要改的代码的**每条路线**（grep 调用点 / 引用链）
- 缺陷长在**共享物**上时，守卫放共享处：**diff 更小，且覆盖工单从没提过的兄弟路径**。补丁只打在被报告的那条路径上，等于替报告打了补丁
- 与 §二·五 互补：那边管"补丁修得真不真"（变体来自根因），这边管"补丁该打在哪"（位置选收敛点）——**位置选错，后面的变体验证再严也只是在错误的修复上空转**
- 修复前把"这个改动不能破坏的不变量"列成清单：以旧 bug 命名的测试、带解释性注释的守卫、编码了血泪阈值的常量——它们标记着历史上出过的事故

## 二·六·五、日志即线索：报错先翻译成可行动清单，不整段读日志（来源：Claude Code 自动化 Skill·Terminal Sense + CI Fixer，用户提供文章 2026-09-17）

- **提取信号行**：错误类型 + 关键栈帧 + 首个异常行（不是整段日志）→ 映射到最可能的根因类别（缺依赖/权限/网络/数据格式/状态过期/竞态）

判据：**报错信息是输入，行动清单是输出**；翻译不出来就补测（缩小到最小复现），不靠重跑碰运气。

## 并发度不是越低越稳：低并发 × 多实例会耗尽下游连接池（来源：docs.n8n.io《Enable queue mode》2026-09-29 r318B 独立实拉；与 §批量失败/单条失败 互补——那条管"失败怎么归"，本条管"把并发调低反而制造新故障"）

## 失败先分两类，恢复方向相反：平台失败前向重试，应用失败后向补偿（来源：Temporal 官方《Application failures》`docs.temporal.io/encyclopedia/application-failures` 2026-09-23 r144-C 独立重拉首读，此前未读）

- **原文事实**：官方按"在哪被检测到、由谁缓解"把失败切成两类。**平台失败**（服务中断、网络中断、Worker 崩溃、环境问题）由持久化执行**透明兜住**，"Your application code does not need to account for these failures"，恢复方式是 **forward recovery**：重试该操作，成功就从失败点继续，**不撤销已完成的工作**。**应用失败**（无效输入、业务规则违反、外部服务调用失败）由你的代码产生，"**do not resolve on their own through retries alone**"，恢复往往是 **backward recovery**：**撤销一部分已完成的工作**回到先前状态（例：扣款失败时要释放已锁定的库存）。
- **判据**：
  - **收到失败先判"再跑一次会不会自己变好"**：会（环境抖、节点崩、网络断）→ 前向恢复，重试即可，**别动已完成的部分**；不会（输入非法、规则违反、外部返回错误）→ 重试只是重复同一个错误，必须走后向恢复或改输入/改代码。
  - **后向恢复的代价是"已经做过的要撤回"**：所以每做一步对外有副作用的事，都要提前想好它的反操作；**没有反操作的步骤不要随便重试**。
  - **别把平台问题当成逻辑 bug 去改代码**：环境类失败改代码通常无效且会引入新问题；先证明它是应用失败再动代码。
  - **别把应用失败交给重试兜**：重试一个必然失败的调用只会放大延迟与日志噪声，且会让"到底失败在哪一步"更难定位。
- 与 §重试策略三型（抛错方声明 NonRetriable/RetryAfter/默认退避）分工：那条管"**抛错的一方怎么声明**"，本条管"**收到失败的一方往哪个方向恢复**"——重试还是补偿，两者配合才完整。
- 与 §回退到已知好点 分工：那条管"撤销到某个点并保留痕迹"，本条管"**什么时候该撤销而不是重试**"。
- 反模式：一律重试；对非法输入做指数退避；平台抖动时去改业务逻辑；补偿动作本身没做幂等导致越补越乱。
- **提升层**：工作流（失败处理路径）+ 工具（恢复动作）。
- 触发词：重试还是补偿、前向恢复、后向恢复、平台失败、应用失败、环境还是逻辑、再跑一次会不会好、要不要回滚、撤销已做的、没有反操作

## §r321B — 重试的作用域是单请求不是复合流；「发出后无应答」是歧义态不重放；内层重试与外层预算分开计数；不可重试类直接走降级不耗预算（来源：docs.openclaw.ai/concepts/retry，2026-09-30 r321B 独立 curl 实拉 9,854B 原文核验）

- 原文/要点：① "Retries apply per request (message send, media upload, reaction, poll, sticker)."→"Composite flows do not retry completed steps."；② "A reset, timeout, or lost response after sending remains ambiguous and is not replayed."；"`push` and `pull` are not replayed by this runner: a failed connection can follow an accepted write, so publication keeps its existing remote-outcome reconciliation."；③ "Native harnesses may retry individual requests internally before returning a terminal failure to OpenClaw; **those internal retries are separate from** OpenClaw's continuation budget."；"When that wait is longer than 60 seconds, OpenClaw injects `x-should-retry: false` so the SDK returns control promptly."；④ "Billing failures, authentication errors, and provider refusals do not use this transient retry budget."；"Exhausted subscription, daily, weekly, or monthly usage windows go directly to eligible auth-profile or model fallback."；⑤ "A completed successful model response clears the outage window, so useful model and tool work between failures does not consume it. Partial streams, failed responses, and tool activity alone do not clear it."；"Cancellation and the run deadline still stop recovery."
- 判据：① **重试的最小单位必须显式钉在"单个请求"上**——写成"重试这个流程"会把已完成且有副作用的步骤重放一遍；复合流的正确形态是**只重试当前步、已完成步不重放**；② **"发出去但没收到应答"是第三态，不是失败也不是成功**：网络重置/超时/丢响应后重发，等于把一个可能已生效的写操作再做一次；正确处置是**先对账（reconciliation）再决定**，而不是无条件 replay——尤其写类操作（push/pull/发消息）；③ **内层的重试不能吃掉外层预算**：下层库自己重试 N 次再返回一个失败，外层看到的是"一次失败"，实际消耗远大于账目；两者必须分开计数，且外层要有**掐断内层长等待的手段**（如注入 `x-should-retry: false`），否则一个 60s+ 的 `Retry-After` 会让整条运行被单点拖死；④ **不该重试的错误不进重试预算**：鉴权失败、计费失败、提供方拒答重试一万次也不会变成功，正确路径是**直接落到降级/换身份/换模型**，把它们塞进瞬态预算只会延后真正的切换并耗尽额度；⑤ **故障窗口的清除条件要写成"有实际进展"**：一次成功的完整响应才清零，部分流/工具活动不清零——否则"看起来在动"会无限续命一个实际已故障的窗口。
- 与已落 §幂等（会被重跑的东西必须幂等）分工：那条管"重跑后世界不变"的设计要求；本条管"**什么该被重跑、由哪一层计数、什么情况不许重跑**"。与 §判死前先回查真实执行状态 分工：那条管判死结论要先验证；本条管**已发出未确认的写操作如何处置**。
- 提升层：工作流 / 工具。触发词：per request 重试、复合流不重放、歧义态、先对账再重放、内层重试独立计数、x-should-retry、不可重试类直落降级、故障窗口清除条件。

  2. **先验数据形状，再动逻辑**。改查询之前先看"这条 join 的语义承载了哪条业务规则"——`outer join` 不是实现细节，它等价于"过期促销也参与计算"。判据：**跨系统 bug（DB join / 异步队列 / 第三方 API 响应）先追数据流、再追应用状态**；原文前两条假设（前端取整、Redis 缓存竞态）都死在应用状态层，第三条转向"把 ORM 实际发出的 SQL 打出来"才命中。
  3. **定位阶段让 AI 只产出"失败点矩阵"，不许它同时提修复**。原文关键动作："I asked the system to generate a test matrix instead of suggesting fixes."——一旦允许它建议改法，会话立刻滑回"先改一版看看"的冲动。判据：**把 AI 在定位阶段的许可动作限制成"列举可证伪的失败点 + 各自一条判别命令"，修复请求单独下一轮再发**。与 §无回路不假设 / §假设必须带预测 分工：那两条管假设本身的质量，本条管**给 AI 的角色边界**。
- 提升层级：工作流（定位阶段的输入核准与角色边界）+ 可复用 Skill。
触发词：schema 漂移、幻影列、迁移缺失、先对齐环境、数据形状、join 语义、业务规则住在实现里、失败点矩阵、只许列举不许改、跨系统 bug、数据流先于应用状态、按设计排障不是碰运气。


## 转圈不用等超时：同一个动作连续重复就是卡死信号；迭代上限按任务复杂度定档（来源：Inngest 官方 `inngest.com/docs-markdown/ai-patterns/agent-tool-loops`，2026-09-22 r132-B 独立重拉首读，此前未读）

- **卡死检测判据是"在重复"不是"跑得久"**：官方示例是 `iterations > 3 && 最近三次工具都相同` 就直接跳出。判据：**是不是在反复做同一个动作**——重复本身就是信号，不需要等超时、也不需要等预算耗尽。与 §自纠循环硬上限 分工：那条管"最多转几圈"，本条管"**怎么判定它已经在原地打转**"。
- **迭代上限按任务复杂度定档，不统一拍一个数**：官方给的是简单问答 2–3 轮，会读文件、会改代码、会跑测试的编码 agent 15–20 轮。判据：**这个 agent 完成一件事正常要几步**——先估计步数再定上限，反过来写上限等于拿一个数约束所有任务。
- **每次模型调用与每个工具执行各成一个可重试单元**，换回三样东西：①**独立重试**——工具挂了不重跑模型调用；②**细粒度可观测**——能直接指名是哪一个工具挂的，而不是只知道"这一步失败了"；③**互不依赖的工具可以并行**。判据：**失败时能不能只补最后那一段，以及能不能指名是谁挂的**。与 §重试策略三型 分工：那条管"抛错方怎么声明重试语义"，本条管"**重试的粒度切在哪一层**"。
- **并行工具的单元 id 必须带序号保证唯一**：同名单元在并行时会互相覆盖、事后无法分辨是哪一路。判据：**并行的每一路有没有一个不会撞名的标识**。
- **预算按累计输入 token 卡，不按轮数卡**：每轮把 `usage.input_tokens` 累加，超阈值即停并返回明确终态。判据：**轮数与花费不是线性关系**——一轮可能读进十万 token，也可能只有几百，用轮数当预算等于没设预算。
- **上下文随循环增长要修剪**：保留最初的用户消息 + 最近若干条，丢掉中间。判据：**原始意图与当前进展不能丢，中间过程可以丢**。

## 错误处置先分四档再决定接不接：接不住的就让它冒上去（来源：LangChain 官方 `docs.langchain.com/oss/python/deepagents/fault-tolerance` + `/langgraph/thinking-in-langgraph`，2026-09-21 r128-B 独立实拉，新增源页）
- **四档**（原文口径）：①**瞬时失败**（网络超时、限流）→ 自动重试 + 指数退避；②**模型能自愈的错误**（工具输出不对、解析失败）→ 转成错误消息喂回模型，让它改输入再试；③**需要人拍板的错误** → 暂停、等输入；④**意外错误** → **让它冒泡**（"Let them bubble up for debugging. Do not catch what you cannot handle."）。
- 判据：**先问"接住它之后我能改变什么结果"，答不出来就不要捕获**——捕获一个你处理不了的错误，唯一的实际效果是把一次可诊断的崩溃换成一次静默失败（对应 §能力装了不生效的静默失败分型：这类错误最难查，因为它根本不报错）。
- **重试按调用对象收窄，不做全局重试**（同源 `fault-tolerance` 原文：Scope retry middleware to specific tools rather than retrying everything —— 文件系统 `read_file` 失败重试没有收益，超时的 web 搜索才值得）。判据：**确定性失败（文件不存在 / 参数非法 / 权限不足）重试只是拖长故障时间**；只有"可能瞬时"的调用才配重试策略，且退避要指数。
- 与 §六步循环「没有稳定复现之前不改产品代码」分工：那条管**什么时候动手改**，本条管**错误冒出来那一刻怎么分类处置**。
- 提升层级：工作流（错误处理分档）+ 可复用 Skill。
触发词：错误分档、接不住就冒泡、不要捕获处理不了的异常、瞬时失败、模型可自愈、暂停等人、重试收窄、指数退避。


## 回退到已知好点：被回退的那段不许从日志里消失，且回滚的作用域要分层声明（来源：Google ADK 官方 `adk.dev/sessions/session/rewind`，2026-09-22 r129-C 独立重拉实读，新信源首读）

- **原文事实**：*`rewind`* 指定要撤销的那次 invocation，系统撤销它**及其之后**的全部请求（有 A/B/C 三次请求，想回到 A 之后的形态就指定 B，于是 B 与 C 一起被撤销）。两个关键约束：① *"all requests, including rewound requests, are preserved in the log for later debugging, analysis, or auditing"*；② *"all ADK managed session-level resources are restored... However, global resources, such as app-level or user-level state and artifacts, are not restored."*
- **判据**：
  - **"回到某个点"要留痕，不是抹掉**：被回退的那段仍要留在日志里。判据：**回滚恢复的是状态，不是历史**——把试错的痕迹一起删掉，等于把"为什么这条路走不通"也删了，下一轮会原样再走一遍。与 `wb-ponytail` §重来不是解法（abort 丢掉的不只是 merge state）分工：那条管**别轻易归零**，本条管**归零之后那段历史怎么处理**。
  - **回滚的作用域必须显式分层**：会话级能回滚的，全局级（已发的消息、已写入外部系统的记录、用户级状态）回滚不了。判据：**做"撤销到 X"之前，先列出"哪些层会跟着回去、哪些层不会"**；回滚不了的那部分要在结论里点名，而不是等用户以为全撤干净了。
  - **重试的起点是"已知好点"，不是"最开始"**。判据：**发现走错了先定位最后一个确认正确的状态，从那里换一条路**，从零开始会把已经确认对的判断也一起丢掉。
- 提升层级：工作流（失败回退与重试起点）+ 工具（回滚作用域声明）。
- 触发词：回退到已知好点、rewind、回滚留痕、回滚作用域、会话级与全局级、撤销不抹历史、重试起点。


## 旁路挂件的失败必须显式选策略并留痕：默认“降级继续”，可选“冒泡为失败”，但两种都要可被程序检出（来源：Mastra 官方 `mastra.ai/docs/subagents`（Delegation hooks → Hook errors 段），2026-09-22 r130-A 独立实拉首读，新信源首读）

- **原文事实**：委派钩子（`onDelegationStart` / `messageFilter` / `onDelegationComplete`）抛错时，*"the delegation continues by default: `onDelegationStart` proceeds with the original prompt, `messageFilter` falls back to the unfiltered context, and `onDelegationComplete` keeps the subagent's original result. Set `hookErrorStrategy: 'throw'` to fail the delegation instead."* 无论选哪种：*"every hook failure is recorded on the run's request context under `__mastra_delegationHookErrors` as a list of `{ hook, primitiveId, toolCallId, runId, name, message }` entries, so you can detect a hook failure programmatically."* 另有两条细节：*"If `onDelegationComplete` throws while handling a failed delegation, the original delegation error remains the surfaced error. The hook isn't invoked again for its own failure."*
- **判据**：
  - **旁路的失败只有两种合法处置，且必须显式选，不能吃实现默认**：`continue`（主链路照走，用原始输入/未过滤上下文/原始结果）或 `throw`（把委派判失败）。判据：**先声明这条挂件是"必须有"还是"有了更好"**——必须有就配成 throw，有了更好才配成 continue；不声明等于让框架替你决定主链路的语义。
  - **选了"降级继续"就必须留痕**：降级的表现是"原样放行"，行为变了但表面无异常。判据：**没有痕的降级 = 既改变行为又不可见**，事后回答不了"这次是不是走了降级路径"。留痕要落到**可程序检出的位置**（请求上下文里的结构列表），不能只写进日志给人看。
  - **后发的次要错误不得顶替第一个真因**：主链路已经失败时，钩子在处理这个失败时又抛错，对外仍报原来的错误。判据：**保真顺序是先到先得**，排障时第一个真因比"处理失败时又失败"更有价值。
  - **钩子不为自己的失败再跑一次**（*"The hook isn't invoked again for its own failure."*）：判据：**给旁路写错误处理时，先排除"错误来自旁路自身"这条路径**，否则一次失败变一串。
- **与 §错误处置四档 分工**：那条管**主链路上冒出来的错误**怎么分档（瞬时/自愈/需人/意外），本条管**观测、通知、过滤这类挂件**的错误——它们不在主链路上，但会静默改变主链路的输入与结论。
- 提升层级：工作流（旁路失败的处置与留痕）+ 工具（可检出的降级记录）。
- 触发词：钩子失败、旁路失败、hookErrorStrategy、降级继续、降级要留痕、不自递归、不顶替原错误、观测挂件失败、静默降级。


## 自纠循环必须有“执行前检查”的硬上限；失败要自动留下可续跑的现场快照（来源：Haystack 官方 `docs.haystack.deepset.ai`（`concepts/pipelines/pipeline-loops` → Loop Termination and Safety Limits + `pipeline-breakpoints` → Error Recovery with Snapshots），2026-09-22 r130-C 独立重拉实读，新信源首读）

- **原文事实**：① 循环上限：*"Every pipeline has a per-component run limit, controlled by the `max_runs_per_component` parameter of the `Pipeline` constructor, which is `100` by default. If any component exceeds this limit, Haystack raises a `PipelineMaxComponentRuns` error."* 且 *"The limit is checked **before each execution**, so a component with a limit of 3 will complete 3 runs successfully before the error is raised on the 4th attempt."* 官方给的理由：*"If your loop condition is wrong or never satisfied, the error prevents the pipeline from running indefinitely."* ② 失败快照：*"Pipelines automatically create a snapshot of the last valid state if a run fails. The snapshot contains inputs, visit counts, and intermediate outputs up to the failure. You can inspect it, fix the issue, and resume execution from that checkpoint instead of restarting the whole run."* 快照可从异常对象取（`e.pipeline_snapshot`）、可落盘、可再装载续跑。③ 循环里的组件会跑多次，但 *"For each component that ran, the pipeline returns **only the last-produced output**"*，要留中间产物必须显式传 `include_outputs_from`。
- **判据**：
  - **凡是"让它自己重试/自纠"的循环，都要有次数上限，且上限必须在执行前判断**：执行后才判断，等于多跑了一次不该跑的动作（那一次可能有副作用）。判据：**写 while/loop 时先写 `max_runs`，再写循环体**；超限要抛**明确的错误类型**，不能静默跳出——静默跳出会把"没做完"伪装成"做完了"。
  - **上限的作用是兜住"条件永远不满足"，不是调优**：*"If your loop condition is wrong or never satisfied..."*。判据：**调低上限是排障手段（快速暴露死循环），不是性能参数**；新写的自纠/路由逻辑先用很小的上限跑，确认会收敛再放开。
  - **失败现场要自动留、可检查、可续跑**：快照里要有输入、访问计数、以及失败前的中间产物。判据：**一次跑砸的流水线，恢复成本不该等于重跑成本**；没有现场快照，就只能"改一点、从头再跑一遍"，既慢又可能因为随机性换了个失败方式。
  - **循环里的中间产物默认只留最后一次，要留必须显式声明**：判据：**自纠过程的每一轮结论默认是过程量不是结果**，需要审计/复盘时显式打开中间输出（对应 `include_outputs_from`）——“默认全留”会污染输出，“默认全丢”会让复盘无从下手。
- **与 §回退到已知好点、§错误处置四档 分工**：那两条管**错误出现后怎么回退、怎么分档**，本条管**循环本身的护栏与失败现场的保存**。
- 提升层级：工作流（自纠循环的护栏）+ 工具（失败快照与续跑）。
- 触发词：循环硬上限、max_runs_per_component、执行前检查、自纠循环护栏、死循环兜底、失败快照、可续跑现场、从快照恢复、只留最后一次输出、include_outputs_from。

## 重试策略要由抛错方显式声明：分「不再重试」「到点再试」「默认退避」三型，别让所有错误走同一条退避（来源：Inngest 官方 `inngest.com/docs-markdown/features/inngest-functions/error-retries/inngest-errors` + `/retries` + `/rollbacks`，2026-09-22 r131-A 独立实拉，新信源首读）

- **三型分错**：`NonRetriableError`（无效输入、重试必然重犯 → 立即停）、`RetryAfterError`（限流 / 竞态 / 429 → 指定延迟）与默认指数退避（其余瞬时故障）。判据是「**再跑一次会不会不同**」：答不会就别退避重试——那会把一次可诊断的失败摊成 N 次无意义重试，日志被同一条错误刷满，真正的新错误反而被埋掉。
- **单步耗尽力后抛的是可被捕获的 StepError**：这一步可以自己接住降级（换工具 / 换数据源 / 换模型），接不住才冒泡成整任务失败。与 §错误处置四档 分工：那条管「接不接」，本条管「**接住之后由谁声明重试时机、以及失败是在步内层降级还是升级成整任务失败**」。
- **尝试计数成功即重置**：`attempt` 在每一步成功后归零，不跨步累计。与 §自纠循环硬上限 分工：那条管「条件永不满足时的护栏」，本条管「**计数以哪个成功为界重置**」。
- **每步配一个小回滚**：失败不只是「停止」，还包括把这一步已经造成的部分效果撤掉；步数变多时，只有逐步回滚才能保证任意长度都安全。与 §回退到已知好点 分工：那条管整体回退与留痕，本条管**每个动作各自带的那份撤销**。



## 工具调用故障先分三段：选没选对 / 调没调对 / 结果用没用对（来源：Arize Phoenix 官方 `arize.com/docs/phoenix/evaluation/pre-built-metrics/{tool-selection,tool-invocation,tool-response-handling}`，2026-09-22 实拉，与 §模型答错四形态、§幻影字段 互补——那两条管“模型被给的东西带偏了它”与“字段有没有被写入”，本条管“工具管线本身在哪一段断的”）
- **三段有各自的输入、各自的失败表征，捕获的错误类型不重叠**：①**选择段**——选了根本不存在的工具、该用却没用、复杂任务该选多个只选了一个；②**调用段**——必填参数缺或值错、JSON 结构坏、凭空造 schema 里没有的字段、参数里夹带 PII / 敏感数据；③**结果段**——工具返回里没有的数据被当成有、日期数字解析错、瞬时错误该重试没重试 / 参数错该改参却去重试、工具结果里的凭据与内部 URL 被说给用户、多工具结果只用了一部分。官方原话：三者 “complementary — …catches wrong-tool errors while …catches malformed-call errors — and are best run together for complete tool-calling coverage”。
- 判据：**“工具相关的结果不对”先问是选错、调错、还是用错**。三段修法完全不同（改工具清单 / 改 schema 与描述 / 改结果处理逻辑），不先分段就动手，等于在没断的那一段上打补丁——补丁会堆在错误的位置，症状还在。
- **喂给判定的字段要人类可读，不要原样丢 JSON**：官方明确 “human-readable formats typically produce more accurate evaluations”（工具清单写成 `book_flight: 预订两城之间的航班。需要出发地、目的地、日期`，而不是整坨 JSON Schema）。判据：**这段内容是给模型读还是给程序读**——给模型读的先翻成人话，给程序读的才保留原结构。与 mts §同一结果两种形状 同向：那边管输出给谁看，这边管喂进判定的输入长什么样。
- **同一个指标要声明它量的是哪一层**：Phoenix 的 evaluator 明确标注支持 span（单次调用）/ trace（完整链路）/ session（整个会话），层级不同结论不同。判据：**报一个数字之前先说清它是哪一层的**——跨层比数是把“这一轮不好”误读成“这个能力不好”。
- 提升层级：工具 + 工作流（排障）。


## 人工在环/延迟步骤要"暂停续跑"而非"终止运行"（来源：Pydantic AI deferred tools / HandleDeferredToolCalls，2026-09-27 实拉）
- **需要人批/外部处理的步骤，运行要暂停等待而不是整段结束**：把工具调用**移交给前端或后台 worker** 处理，外部（人或后台）完成后用结果**恢复（resume）运行**——核心是 "human-in-the-loop approval does not end the run"。
- **审批在运行内部 handler 里完成，运行继续**：通过 `HandleDeferredToolCalls` 在 run 内的 handler 批准/解决延迟的工具调用，运行不终止、后续步骤照常走。
- 判据：**凡有"等外部确认"的环节，先问"这次等待是要挂起还是要从头杀掉"**——要挂起就设计成可 resume 的暂停，别让一次审批把前面所有进度清零（与 §失败自动留可续跑现场 同向：那条管失败后的快照续跑，本条管"人批期间"的暂停续跑，二者都要求"恢复成本 ≠ 重跑成本"）。
- 提升层：工作流（暂停续跑）/ 工具（延迟工具审批）。

## 验证证据要让没跟过过程的人自己下结论；开始前先找仓库里已有的规程（来源：Devin 官方 `docs.devin.ai/work-with-devin/testing-and-recordings`，2026-09-22 r133-B 实拉，与 §修复验证、§自纠循环必须保留可续跑现场 互补——那两条管“证明补丁真的修好了要测什么”与“失败要留下可续跑的现场”，本条管“证据以什么形态交付、流程以哪份规程为准”）
- **证据的合格线是读者不需要补上下文**：官方对测试录屏的目标是 “a short recording that a code reviewer watches and immediately thinks ‘yep, it works’ — then merges the PR”。判据：**把这份证据交给一个没参与过程的人，他能不能独立下结论**——需要你在旁边口头补充才能看懂的证据，等于没有证据。
- **四段式，顺序不能省**：① 环境就绪（装依赖、起服务、登好账号）② 读 diff 与代码库拟出**最小的、聚焦的**测试计划 ③ 执行并在关键节点做标注 ④ 把结果作为交付的一部分发出去。判据：**测试计划是从这次改动推出来的，还是从“把所有功能跑一遍”抄来的**——后者产出的长录屏没人看。
- **进入验证前先找仓库里有没有已约定的规程**：官方 Phase 1 明确包含 “Checks for relevant skills in the repo (under `.agents/skills/`) and follows them if found”。判据：**这个仓库里是不是已经有人写下了“这类改动该怎么验”**——有就按它走，没读完就自创流程，等于把团队约定降级成个人习惯。
- 提升层级：工作流（验证交付）。

## bug 报告规格是修复上限：轨迹证据富化报告 + gold standard prompt（来源：Al Fahim 等《Bug Report Specification Refinement with Trajectory Guidance》2026-07 + saram.io《Why Your LLM Keeps Fixing the Same Bug》2026-07-17 + The Neural Base《SWE-Bench》2026-04-22 实拉，与 §模型答错四形态互补——那条管“模型被什么带偏”，本条管“喂给修复的规格本身是不是约束瓶颈”）
- **bug 报告规格质量是修复的主导约束，不是模型**：TrajSpec 用轨迹派生证据富化稀疏 bug 报告，SWE-bench Lite Pass@1 从 41% 提到 72%——同一模型，报告变好修复翻倍。判据：**修复成功率上不去，先查报告里有多少可行动证据（复现步骤/相关文件/失败路径），再怪模型**。
- **gold standard prompt 结构**：失败测试 + traceback → 先写一段根因解释 → 给最小补丁（修根因不修症状）→ 只展示改动的行（diff 不全文件）→ 不改函数签名。判据：**这条 prompt 同时逼出“诊断”和“最小改动”**，两条都缺的“修一下”提示词换不回稳定修复。
- **生成 3-5 个独立候选（不同 prompt）+ 全测试套件隔离验证 + 只把通过的给人审**（附 diff/哪些新测试过/覆盖率）——多候选提升命中，全量回归防修 A 坏 B。
- 提升层级：工作流（排障）。

## 符号级导航：language server 问定义/调用者，替代扫文件（来源：13labs《AI Coding Agent in a Codebase Too Big to Explain》2026-08-11 实拉 + Anthropic《Claude Code at Scale》2026-05-14 实拉，与 §失败经验签名索引互补——那条管“错误怎么索引”，本条管“大仓里怎么找代码”）
- **grep 是默认，符号级导航是升级**：装代码智能插件，agent 直接问 language server“这个符号的定义/调用者列表”，替代自己扫描文件找。判据：**问语言服务器一次拿到精确答案，胜过多次推测性文件读取**——语言服务器插件和委派搜索干掉了最多无效读文件。
- 与 §定位路径的分工：那条管“报错怎么走到根因”，本条管“定位时问谁”——问语言服务器比扫文件准且省。
- 提升层级：工作流（定位）。

## 轨迹→技能自进化：步骤级归因 + 重复失败压成 SoP（来源：arXiv SkillAdaptor 2606.01311 2026-09-01 + Trace2Skill 2026-07 + LifeSkill 2606.04815 2026-08 实拉，与 §失败经验记忆 分工——那条管"同类错误召回历史修复路径"（记忆层），本条管"从轨迹定位技能缺陷并更新技能本体"（技能层））
- **失败归因到步骤，不是到整段轨迹**：SkillAdaptor 从执行轨迹定位**第一个可行动 fault**（first actionable fault），诊断它对应的技能缺陷，然后**只精修那一个技能，无关技能不动**。判据：**"这轮失败了"太粗，要能说出"第几步、哪个技能、缺什么"**——轨迹级反思会把无关技能一起改，污染好技能。
- **重复失败 + workaround 压缩成 SoP（标准操作程序）**：Trace2Skill 把反复出现的失败与绕行办法蒸馏成可迁移技能，无需参数更新、无需测试时检索即可复用。判据：**同类失败出现 ≥2 次就升级成 SoP 技能**——一次怪错记情景，重复的才配进技能库。
- **技能的价值由验证器说了算，不由文本合理性**：LifeSkill 用验证器成功率给候选技能打分（多个 rollout 平均），鼓励"解决任务有用"而非"看起来合理"的技能。判据：**新技能落地前先跑验证器，能通过验证的技能才保留**——"读着像那么回事"不是保留理由。
- 反模式：失败后整段反思把所有技能重写一遍；把一次性怪错蒸馏进技能库；凭感觉判断新技能好不好不跑验证。
- **提升层**：可复用 Skill（自进化 / 调试归因）。

## 诊断通道要与被诊断通道物理分离；观测按请求 opt-in，默认不发（来源：MCP 官方《Debugging》+《server/utilities/logging》规范页 2026-09-22 r138-A 首读深拉，此前未读）
- **日志禁止写进协议正在用的那条通道**：stdio 服务器往 stdout 打日志 = 把诊断信息灌进被诊断的报文流，症状是"连上了但解析莫名出错"。诊断走 stderr（stdio）或 OTel（HTTP）。判据：**这条输出会不会被对端当成协议内容解析**——会就必须换通道。
- **观测开关由调用方按请求显式声明**（请求元数据里带 `logLevel`），没声明就不发日志通知。判据：**观测是"这次要查"才开，不是常开**——常开的观测会改变被测对象的时序与体积，你看到的是"加了观测之后的行为"，不是原行为。
- **与 §最小化复现 分工**：那条管"把问题缩小到哪一步"，本条管"**别让观测本身把问题变掉**"。
- 反模式：排查时把 debug 日志打到主输出流；开着全量日志测延迟/时序；把诊断信息混进准备喂给模型的返回结果里。
- **提升层**：工具 / 工作流（诊断设施）。

## 可观测采集默认全采；脱敏要显式打开，且用 allowlist 而不是 blocklist（来源：OpenAI Agents SDK 官方《Configuration》+《Tracing》2026-09-22 r138-B 独立重拉首读，此前未读）
- **默认采集敏感数据**：生成 span 存模型的输入输出、函数 span 存调用参数与返回值——默认开关是**开**的。判据：**"我加了 trace"等于"我把这些字段送进了存储"**，先决定采集边界，再加观测。
- **脱敏用 allowlist，不用 blocklist**：官方脱敏示例的允许清单里**不含名称 / 元数据 / 错误 / span 数据**，只放行事件类别与链路 ID。判据：**靠"猜哪些字段敏感"去删，一定会漏；只放行确定可以留的才不漏**。
- **关掉采集要留关联 ID**：脱敏后的 span 仍保留响应 ID 一类关联元数据，否则"这条 trace 对应哪次调用"断掉，可观测性直接归零。判据：**脱敏不能顺手把可追踪性一起脱掉**。
- 与 §跨边界错误信息脱敏 分工：那条管"错误文本越过进程边界"，本条管"**观测数据落进存储与看板之后归谁看**"。
- 反模式：开着全量 trace 上生产；按"把已知敏感字段删掉"做脱敏；为脱敏把链路 ID 一起删了，出事时无法回溯。
- **提升层**：工具 / 工作流（可观测性治理）。

## 会挂死的用法要设计成显式错误；复用的对象会把它上一轮的隐性状态一起带过来（来源：Pydantic AI 官方《Troubleshooting》2026-09-22 r138-C 独立重拉首读，此前未读）
- **"这样用会死锁"要抛错，不要让它卡住**：在同步工具里再调同步运行入口——父流程还在等这个函数、子流程又把线程占住——框架直接抛 `UserError`，而不是挂在那里。判据：**一种用法的结果是"卡住/超时"而不是"失败"，它就该是一个显式错误**；挂住没有堆栈、没有上下文，是所有失败形态里最难查的一种。
- **复用实例 = 继承它的隐性状态**：事件循环被关掉之后，只重建外层对象而不重建它里面的连接层，会接着用绑在已死循环上的连接池，报错出现在完全不相干的位置。判据：**一个对象除了接口之外还持有连接 / 缓存 / 会话 / 句柄时，"能不能复用"要连同这些一起判断**；要重建就整条重建，别只换最外面那层。
- 与 §卡死检测 分工：那条管"运行中怎么发现它在原地打转"，本条管"**在设计与选型阶段就把会打转的用法堵掉，以及换对象时别带来看不见的旧状态**"。
- 反模式：靠超时兜底一个已知会死锁的用法；换 agent 不换它持有的连接层；把"卡住了"当成"只是慢"。
- **提升层**：工具 / 工作流（失败形态设计）。

## 挂在关键路径上的旁路代码，四条可靠性约束：别占主循环、必须幂等、自己兜错、一次只干一件事（来源：Google ADK 官方《Design Patterns and Best Practices for Callbacks》，2026-09-23 r142-A 独立重拉首读，此前未读）
- **旁路是内联执行的，主循环在等它**：回调/守卫/校验这类代码跑在 agent 处理循环内部，循环会等每一个跑完。判据：**这段代码里有没有网络请求、重计算、大文件读写**——有就是把它放错了位置，卡住的是整条主链路，不是它自己。要卸载就得接受由此带来的复杂度，别默认"反正只是个小检查"。
- **会被重跑的东西必须幂等**：框架侧可能发生重试，凡是带外部副作用的旁路（自增外部计数器、发通知、写远端）都要设计成"同样输入跑多次结果一样"。判据：**它跑第二遍，世界会不会变**。
- **旁路里的错误要自己兜住**：用 try/catch 包住、记录、并明确决定"这次调用是停还是继续"——**不能让旁路的异常把整个进程带崩**。判据：**这个检查挂了，主任务该失败还是该降级继续**，没答案就是缺错误处理。
- **一次只干一件事**：把日志、校验、改状态、缓存塞进同一个回调，任何一处改动都会牵动其余；排查时也无法判断是哪一段造成的。判据：**能不能一句话说清这个回调的用途**——说不清就该拆。
- **写状态用具体键，不要改大结构**：`state['quota_exceeded'] = True` 这种细粒度写入可追踪、不会误伤同结构里的其他字段；整体替换大字典会让无关字段被悄悄回滚。变更应尽量落在可追踪的 delta 上而不是就地改本体。
- 与 §钩子失败（钩子抛错后默认继续、错误要留痕、钩子不为自己的失败再跑一次）分工：那条管"**旁路已经失败了怎么降级**"，本条管"**旁路怎么写才不容易失败、失败时不拖垮主链路**"。
- 反模式：在回调里发 HTTP 请求；把四个职责塞进一个 before 钩子；依赖"框架只调一次"所以不写幂等；回调抛异常导致整轮崩；整体覆盖写大状态对象。
- **提升层**：工具（旁路/钩子设计）。

## 断点设在"第 N 次访问这个环节"上；失败要自动留下一个能接着跑的状态（来源：Haystack 官方《Pipeline Breakpoints》，2026-09-23 r142-B 独立重拉首读，此前未读）
- **断点的坐标是"环节 + 第几次访问"，不是位置也不是时间**：带循环的流程里，能精确停在第 N 次经过某个环节，前 N-1 次照常跑完。判据：**我关心的是第几次经过这里**——答得出次数就用访问计数，答不出才退而用位置。
- **停下来时拿到的是完整现场，不是一句报错**：被停环节的输入、到此刻为止已产出的中间结果、访问计数，三者一起给。判据：**只拿到"失败了"三个字时，能不能不重跑就看出错在哪**。
- **失败时自动保存最后一个有效状态**（输入 + 访问计数 + 中间输出），可以从那里续跑，而不是整条重来。判据：**这条流程重跑一次的代价**——代价高就必须保留可续跑的中间态，代价低才适合整条重跑。
- **快照落盘默认关闭，要写盘必须显式打开**；改用自定义回调接管时不再写文件。判据：**这份快照里有没有不能落盘的内容**——有就走回调，不要为了调试把全局落盘打开。
- 与 §回退到已知好点（回退的作用域分层 + 被回退内容不下日志）分工：那条管"**往回退**"，本条管"**停在哪、存下什么、怎么从存下的状态接着往前跑**"。
- 反模式：一失败就整条重跑；断点只按位置设导致循环里每次都停；默认开着快照落盘，把中间态和原始输入一起写进磁盘。
- **提升层**：工作流（可恢复性）。

## 失败先分两类，恢复方向相反：平台失败前向重试，应用失败后向补偿（来源：Temporal 官方《Application failures》`docs.temporal.io/encyclopedia/application-failures` 2026-09-23 r144-C 独立重拉首读，此前未读）（细则见 KB，2026-09-30 r320C 下沉）
## 重试的粒度是「步骤」不是「整段」：journal 让重试跳过已完成的步骤（来源：Restate 官方 `docs.restate.dev/foundations/key-concepts` + `/develop/ts/error-handling` + `/develop/ts/durable-steps`，2026-09-23 r145-B 独立重拉首读，新信源首读，此前未读）

- **每一步的调用与结果都进 journal**；崩溃后重放时**跳过已完成的步骤、从中断处续跑**，而不是从头再来。判据：**重试之所以能"不重复副作用"，是因为每一步都有记录与可复现的结果**——没记的步骤，重试就等于重做（与 §平台失败前向重试 分工：那条管"**该重试还是该撤销**"，本条管"**重试到底重跑多少**"）。
- **幂等键让重复请求返回同一结果**：请求头带 idempotency key，平台自动去重，重复请求拿回原结果。判据：**一个动作可能被发两次时，问"第二次靠什么认出自己是同一次"**——答不出就是没做幂等（与 §幂等是快捷路径硬门票 分工：那条管"能不能走快捷路径"，本条管"**重复到达时怎么收敛成一次**"）。
- **状态更新与执行步骤一起 journal → 状态永远不与执行不同步**：Restate 官方把"state is never out of sync with the execution"当作一致性保证。判据：**改状态和记状态必须是同一个动作**——先改后记（或先记后改）都会出现"执行到哪了"与"状态是什么"对不上。
- **服务与 Server 之间断连时是"停手 + 换实例续跑"，不是原地傻等**：SDK 写不进 journal 就中止本次执行，由服务端在另一个实例上重放。判据：**续跑的前提从来不是"这个进程活着"，而是"进度在进程外"**。

## 回滚有两个维度（产物 / 对话），要分开退；快照放进影子仓，别污染主历史（来源：Cline 官方 `docs.cline.bot/core-workflows/checkpoints`，2026-09-23 r145-C 独立重拉首读，新信源首读，此前未读）

- **先分清坏的是哪一维**：官方给的三档正是两个维度的组合——**只退产物**（代码坏了，但讨论出来的上下文还有用，留着换个实现再来）、**只退对话**（产物是好的，只是跑题了，留着文件换引导）、**两个都退**（彻底从已知好状态重来）。判据：**退之前先回答"坏的是做出来的东西，还是达成它的那串对话"**——默认"全退"等于把还能用的那一半也扔了（与 §回退到已知好点 分工：那条管"**退到哪个点**"，本条管"**退哪一维、退多少**"）。
- **快照粒度 = 一次工具调用**，每改一次就存一份；连改三个文件就有三个点，可分别退。判据：**快照点必须能对应到"某个具体动作"**，否则退的时候说不清退掉了什么。
- **影子仓与主版本仓物理隔离**：官方用一个独立于项目 git 的影子仓库存快照——主历史保持干净归用户管，且**连未被 git 跟踪的文件也能被快照到**。判据：**回滚用的存储不能复用交付用的存储**——共用会让"回滚"变成"改历史"（与本项目 §落地序列 的"改 repo → 推 → 回灌 live"同源：两仓分离）。
- **回滚成本决定能放多少手**：官方原话——有了 checkpoint，"the cost of a mistake drops to nearly zero"，才敢开 auto-approve 让 agent 自己往前冲。判据：**在问"要不要给它自主权"之前，先问"错了退得回来吗"**（与 `wb-spec-driven` §实习生判据 分工：那条管"**给多少自主权**"，本条管"**自主权的前提条件**"）。

## 失败要"声明原因"，不是"描述症状"：报什么、不报什么（来源：n8n 官方 `docs.n8n.io/connect/create-nodes/build-your-node/reference/error-handling` + `/build/flow-logic/handle-errors-gracefully`，2026-09-23 r146-A 独立实拉首读，此前未读）

- **官方把"为什么失败"做成一等字段**：错误带 `failure: { cause: ... }`，`cause` 取六值，**前三类自己会好**（`rate-limited` 服务在限流 / `quota-exhausted` 配额到点就回来 / `temporarily-unavailable` 服务当前降级），**后三类必须有人动手**（`credential-invalid` 凭证失效要重连 / `configuration-invalid` 指向的目标没了或不再被允许 / `node-defect` 是节点自己的 bug，凭证与配置都没问题）。判据：**分类的第一刀是"再等等会不会自己好"**——这一刀决定是排重试还是排队等人。
- **抛出方只陈述原因，不陈述对策**：官方原话 "The node states the cause, never what to do about it: n8n owns any behavior derived from the declaration"（例如轮询触发该怎么退避，由平台从 cause 派生，不由抛错方写死）。判据：**原因与对策分离，对策归调用方**——在错误里夹"该怎么办"，等于把策略写死在最不了解上下文的那一层，且会随环境过期。
- **只声明响应能证明的原因**：原话 "Only declare a cause the response proves. If you can't classify an error with confidence, throw it unchanged: an error without a declaration is still valid."。判据：**分类不出就原样抛，不猜一个 cause**——猜错的分类比没有分类更坏，它会让上层按错误的自愈路径去重试一件等人动手才可能好的事。
- **等待提示只属于可自愈的那三类**：`retryAfterMs`（服务要求的最小等待）/ `resetsAtEpochMs`（服务说什么时候回来）；另外三类官方明确不接受，"there's nothing to wait for"。判据：**给"需人动手"的失败配等待 = 死等**。
- **错误负载要写明哪些字段必然缺失**：`execution.id` / `execution.url` 依赖执行已入库，主工作流触发节点就出错时没有；`execution.retryOf` 只在是重试时出现；**触发点不同，负载结构就不同**——触发节点出错时 `execution{}` 变少、`trigger{}` 变多。判据：**上报结构必须声明缺省条件**，否则消费方会把"这个字段没有"当成"又出错了"，排障时多追一层假故障。
- 与 §平台失败 / 应用失败 分工：那条管**恢复方向**（前向重试还是后向补偿）；本条管**失败怎么被结构化声明**——声明是恢复决策的输入，没有声明就只能猜方向。
- 与 §新旧两边都失败 ≠ 同一个失败 分工：那条管"归因没解决时别合并"；本条管"归因清楚了要写成机器可读的 cause"。
- 触发词：失败声明、failure cause、只报原因不报对策、分类不出就原样抛、等待提示、错误负载缺省字段、配额耗尽、凭证失效、限流退避。
## 回滚挂在「事务」上而非「步骤」上；提交时机决定回滚保护范围（来源：Prefect 官方 `docs.prefect.io/v3/advanced/transactions` 2026-09-23 r147-A 独立实拉首读，清单外新信源）
- 回滚钩子（on_rollback）在「事务」失败时触发，不只是本任务失败时：同事务内某步成功、但兄弟步失败，成功那步的回滚钩子照样跑 → 清理副作用要挂事务上，不能只挂本步。
- 回滚只在「已暂存（staged）」之后才发生：任务跑完还没 stage，失败时无回滚可跑；已 commit 的不能再回滚（EAGER 提交后外部失败也救不回）。
- 提交时机三态：LAZY（块退出才提交，失败前都还可回滚）/ EAGER（各自即时提交，结果更早可用但失去组内保护）/ OFF（手动 commit，否则退出即回滚）；嵌套继承父模式，显式覆盖。
- 框架只跑你的回滚钩子，不会自动撤销外部副作用（文件 / API / DB 写入）——钩子里必须自己实现清理。
- 触发词：事务回滚、副作用清理、提交时机、staged、on_rollback、LAZY / EAGER / OFF。
- 提升层：工作流（多步改动失败后的现场还原）。
## 失败先按「靠换什么能救」分两类，恢复入口不同：截断加 token，校验失败改契约（来源：Instructor 官方 `python.useinstructor.com/concepts/error-handling` 2026-09-23 r147-B 独立实拉首读，清单外新信源）
- 输出截断（`IncompleteOutputException`，撞 token 上限）→ 加 `max_tokens` 重跑，不碰契约。
- 校验失败（`ValidationError`，模型没给出合规结构）→ 改契约 / 改数据 / 加示例，不是加 token；拿 token 救校验失败只会空转。
- 判据：两类恢复入口混为一谈，会把「判据写错」当成「模型不行」，越改越偏。先问「这一轮是哪种失败」再决定改哪。
- 与 §严格解码畸形拒绝不回退 分工：那条管「畸形结构化结果绝不静默回退到文本」（硬规则），本条管「分类之后各自的恢复动作从哪下手」。
- 触发词：截断重跑、校验失败恢复、两类失败、max_tokens、先分类再改。
- 提升层：工作流（失败恢复路径分诊）。
## 把操作显式命名成「step」：父子层级从嵌套自动解析，不靠事后埋点（来源：Chainlit 官方 `docs.chainlit.io/api-reference/step-decorator` + `/step-class` 2026-09-23 r147-C 独立实拉首读，清单外新信源）
- 每个 step 必有名：默认取被装饰函数名（可覆盖）；`type` 字段用于监控 / 调试分类（llm / tool / ...）；`input`+`output` 自动从函数签名取，不用手写。
- `parent_id` 从装饰函数的嵌套调用自动解析：调了谁、谁就是爹，层级天然形成——可观测性来自「给代码块贴名 + 嵌套结构」，不是额外插埋点。
- `metadata` / `tags` 随 step 持久化，用于过滤与分类；`current_step` 运行时可覆盖 input/output。
- 触发词：step 命名、父子层级、type 分类、current_step、parent_id 自动解析。
- 提升层：工作流（执行可观测 / 排障路径）。

## 熔断 / 配额必须自带一条「窄自救通道」，且恢复要留释放余量（来源：Qdrant 官方 `qdrant.tech/documentation/common-errors`（Insufficient storage / quotas）2026-09-23 r150-A 独立实拉首读，清单外新信源）

- **触顶后不是"用度一降就恢复"**：必须降到阈值下方一个余量（官方默认 5 个百分点）才清除熔断。判据：**任何"超限 → 恢复"的机制要给两个阈值而不是一个**（迟滞），否则会在阈值线上反复抖动。
- **限流状态下必须保证"能自救的操作"不被限流本身挡住**：官方在配额下**始终允许删点/删集合**（好腾空间），但**拒绝删除单个向量或 payload 键**（防止用"打洞"的方式变相绕过配额）。判据：**设计熔断时先列出"退出熔断必须执行哪些动作"，显式放行这些动作，同时把放行面收窄到只能自救、不能退化成绕过。**
- 报错要连着治理动作一起给：官方 507 报错正文同时给出"减磁盘 / 加容量 / 调阈值"三条路并标出释放余量 —— 与 §失败要声明原因 分工（那条管报什么不报什么，本条管报错里必须带上"怎么退出来"）。

## 「收尾的超时」和「干活的超时」是两个旋钮，默认值取向相反（来源：CAMEL-AI 官方 `docs.camel-ai.org/key_modules/workforce`（`graceful_shutdown_timeout: float = 15.0` / `task_timeout_seconds: Optional[float] = None`），2026-09-23 r150-C 独立实拉首读，清单外新信源）

- **关停宽限默认给一个具体值（官方 15 秒）**：不给值就可能出现"永远等不到优雅退出"，进程只能被强杀。判据：**收尾动作自己也要有上界，否则"优雅"变成"无限期"。**
- **干活超时默认是"不限"（`None`）**：因为任务时长分布极长尾，给一个拍脑袋的默认值会误杀正常的大任务。判据：**超时默认值要按"误杀代价"取向** —— 误杀长任务代价高 → 默认不限、按需显式设；卡住不退代价高 → 默认给值。
- 两者要能分别设（官方一个是 workforce 级、一个是 task 级），共用一个超时会把"整体收尾"和"单个任务执行"绑成同一个数。
- 与 §活性判定用心跳 + 期待进展事件对 分工：那条管"运行中怎么判活"，本条管"两类超时的默认值该怎么取、能不能分开设"。

## 外部依赖韧性——用回退路由兜底，不差时让路由器决策（来源：OpenRouter 官方 `openrouter.ai` 概览 + `docs/guides/routing/routers/free-router.md`，2026-09-23 r151-A 独立实拉首读，清单外新信源）

- **单一外部依赖（某家的某个模型）是整个 run 的脆弱点**：官方「route around provider outages and rate limits with automatic fallbacks」——把「调不通时换一个」做成路由层的一等能力，而不是在业务代码里散落 try/except。
- **当你对「用哪个」无所谓时，让路由器决定，不要写死**：`openrouter/free` 这种 free-router「picks one for you」，把「任意可用模型」交给路由，省掉 brittle 的硬编码选择，也避免单家 outage 拖垮整体。
- 判据：**fallback 链是「依赖层」的事，不是「调用点」的事**；调用处只声明「我需要能聊天的模型」，路由负责在 outage / 限流时换人。
- 与 §熔断 / 配额必须自带窄自救通道 分工：那条管「命中上限后怎么退出来」；本条管「在还没命中上限时，先靠路由把单点依赖拆成多候选」。

## 重试前先按错误语义分类：可重试的才退避，永久错误去修别循环（来源：Fireworks 官方 `docs.fireworks.ai/guides/reliability.md` + `guides/inference-error-codes.md`，2026-09-23 r151-C 独立实拉首读，清单外新信源）

- **不是所有失败都该重试**：官方明确 429/500/502/503/504 = 可重试（带退避）；400/401/404/422 = 不可重试——是请求本身错了，重试只会放大流量、永远失败。
- 判据：**重试循环里先判状态码语义，再决定退避还是改请求**；把 400 当瞬态去重试，等于用更多请求确认同一个 bug。
- 与 §失败按「换 token / 改契约」分两类恢复入口 分工：那条管「模型侧失败怎么恢复」；本条管「传输/协议层错误按语义分流，可重试才退避、不可重试立刻改请求」。

## 超时是「每次尝试」的度量、是下界不是上界；抢占是默认状态，不是异常（来源：Modal 官方 `modal.com/docs/guide/timeouts.md` + `/guide/retries.md` + `/guide/preemption.md`，2026-09-23 r153-B 独立实拉首读，清单外新信源）
- **超时按「每次尝试」计，不是任务总预算**：官方写明超时是 `per execution attempt`，配置了重试的函数 **`will start new execution timeouts on each retry`**，并给了算式——一个死循环函数设 100 秒超时、允许 3 次重试，**在平台里至少跑 400 秒**。→ 判据：**算「最坏总时长」必须做 per-attempt × (1 + 重试次数)**；把平台超时当总预算是**成倍低估**，而这个低估在监控上看不出来（每次尝试都「没超时」）。
- **超时不含排队，而且是「至少」不是「至多」**：官方写明超时**不包括调度时间**；又说 `Functions will run for at least as long as their timeout allows, but they may run a handful of seconds longer`，要精确时长必须**自己在用户代码里实现超时逻辑**。→ 判据：**平台超时是保险丝，不是计量器**——凡是要拿超时值做「多长时间算失败 / 多少预算够用」这类推算的地方，都要按「至少」处理并留余量。
- **启动超时与执行超时是两个旋钮**：`startup_timeout` 独立配置容器**启动**时间（载大数据 / 初始化大模型 / 导入大量包），官方记录在引入该参数之前，`timeout` 同时管启动与执行。→ 判据：**启动慢与干得慢是两类问题**，混在一个旋钮里会出现「为了迁就启动而把执行超时也放大」这种误修。
- **「被打断」是默认状态，不是例外**：官方写明所有函数**默认可被抢占**（`subject to preemption by default`），抢占发生后平台**优雅终止该函数并以同一输入重启**；且**运行时长越长被抢占概率越高**，长任务官方建议是**拆成小块 + 用检查点频繁保存 + 保证操作幂等可安全重试**。→ 判据：**长任务的正确设计前提是「随时会断」，不是「别断我」**；`重启用同一输入`这条同时意味着**幂等是前置条件**——不幂等的任务重启会重复副作用。
- **「不被中断」是买来的，有价格，而且有买不到的场景**：想要不可抢占必须显式把 `nonpreemptible` 置真，代价是 CPU / 内存**按标价乘 3 倍**，**且 GPU 函数不支持这个参数**（官方给出的原因是可用性与调度延迟约束）。→ 判据：**把「稳定性」当配置项时，要同时问三件事：默认值是什么、要花多少代价改、哪些场景改不了**；只答第一件的方案，会在 GPU 这类买不到的场景上直接失效。
- 与 §收尾超时与干活超时是两个旋钮 分工：那条管**同一次执行内两类超时的默认取向为什么相反**；本条管**超时的计量口径（per-attempt / 不含调度 / 只是下界）与「中断是默认态」**——前者算的是「一段有多长」，后者算的是「一次有多长、会重复几次」。
- **提升层**：可复用 Skill / 工作流（超时与中断的建模纪律）。

## 心跳要靠「让出执行权」才发得出去；越限终止会跳过收尾钩子；「暂停」不等于「中止」（来源：trigger.dev 官方 `trigger.dev/docs/runs/heartbeats.md` + `/runs/max-duration.md` + `/queue-concurrency.md`，2026-09-23 r153-C 独立实拉首读，清单外新信源）
- **心跳机制会被「不让出执行权的代码」饿死，于是「健康的任务」被判成卡死**：官方机制是任务每 30 秒向平台发一次心跳，**5 分钟收不到就把这次运行标记为 stalled 并停机**（报 `TASK_RUN_STALLED_EXECUTING`）；官方同时点明病因——**在事件循环上长时间阻塞的代码（例如对大表做同步紧循环）会让心跳根本发不出去**。官方给的修正动作不是调大判停窗口，而是**在长循环里插显式让步**（`heartbeats.yield()`），且说明「可以每轮都调，实现只在需要时才真让步」。→ 判据：**心跳不是「进程还活着」的证明，而是「进程肯把控制权交出来」的证明**；出现 stalled 类误杀，先查是不是有紧循环没让步，而不是先放宽超时——放宽只是把误杀推迟，同时把真卡死的发现延后。
- **越限终止会跳过收尾钩子，所以「收尾一定会跑」是个错假设**：官方写明任务超过 `maxDuration` 时，`cleanup`、`onSuccess`、`onFailure` **都不会被调用**。→ 判据：**任何「无论如何都要执行」的清理动作，不能挂在正常收尾钩子上**（那恰恰是异常路径最不可靠的位置）；要么做成幂等的可重入清理，要么由外部看门狗补做。
- **计量口径：`maxDuration` 比的是 CPU 时间，不是墙上时间**：官方说明它按「自本次尝试开始以来任务在 CPU 上活跃运行的时间」计，**不包含在 `wait.for` / `triggerAndWait` / `batchTriggerAndWait` 上等待的时间**。→ 判据：**「等」不算「跑」**——一个长期在等外部回调的任务不会因为总时长很长而越限；反过来，一个几乎不等待的 CPU 密集任务会以远超直觉的速度撞上限。用墙上时间去预估 CPU 上限，两个方向都会算错。
- **「暂停」的语义边界是「不启动新的」，不是「停掉现有的」**：官方写明暂停队列后「正在执行的运行会继续跑完」。→ 判据：**要「止血」和要「清场」是两个不同动作**：暂停只止血（新流量不进来，存量照跑）；期望「一暂停就全部停下」会导致对存量的误判——你以为已经停了，其实还在写。
- **并发上限有「基线 / 覆盖」双层，且覆盖是显式可重置的**：官方队列对象同时给出 `concurrency.base`（代码里定义的默认值）、`concurrency.override`（临时覆盖值）与 `concurrency.current`（有效值），覆盖操作记录 `overriddenAt` / `overriddenBy`，并单独提供「重置回基线」的动作。→ 判据：**临时调参必须留痕（谁、什么时候）并保留一键回到基线的动作**；只有「当前值」没有「基线值」的系统，调完就回不去了。
- 与 §活性判定用心跳 + 期待进展事件对 分工：那条管**用哪两类信号判活、窗口怎么容忍丢包**；本条管**心跳为什么发不出去（执行权没让出）以及它是可以靠改代码修好的**。与 §收尾超时与干活超时是两个旋钮 分工：那条管**超时默认值取向**；本条管**越限之后收尾钩子压根不跑**。
- **提升层**：可复用 Skill / 工作流（长任务活性与终止语义）。

## 被环境杀死的进程，恢复靠「完成标记做游标」而不是靠业务方幂等表；且只有这一类失败才配自动重试（来源：Trigger.dev 官方 `trigger.dev/docs/ai-chat/patterns/oom-resilience.md` 与 `patterns/recovery-boot.md`、`patterns/persistence-and-replay.md`，2026-09-23 r154-A 独立实拉首读）
- **恢复不必业务方自建去重**：官方明写 `The recovery doesn't need any customer-side persistence to avoid duplicate processing`——它用平台本就为每个会话维护的两份持久状态：`session.out`（每轮**成功结束**都写一个 `trigger:turn-complete` 标记）与 `session.in`（每条用户消息带服务端时间戳）。重试启动时：① 流式扫 `session.out` 取**最后一条 turn-complete 的时间戳** `T_last_complete`；② 在 `session.in` 上加过滤 `timestamp > T_last_complete` → **已完成的轮次被滤掉，只重跑崩掉的那一轮**（官方原话 `skips records belonging to turns that already completed`）。→ 判据：**游标要锚在「完成时写入的标记」上，绝不能锚在「读过哪里」**——已读位在半途崩溃时会把没做完的活标成做完了；完成标记天然表达"这一段真的做完了"。扫 `session.out` 是流式且有界的（逐块检查后即丢），只有重试路径才付这份带宽。
- **不是所有失败都该重试，官方把这条写成了硬约束**：`chat.agent` **不暴露通用 retry 选项**（`does not expose generic retry options`），OOM 恢复是**唯一的重试路径**，内部就是把 `retry.maxAttempts` 固定为 2（一次 OOM 重试）。官方给的理由，原文：`retrying an LLM-driven loop on non-OOM errors tends to be expensive and side-effecting`（对非 OOM 错误重试一个 LLM 驱动的循环，既贵又带副作用）。→ 判据：**重试的准入面越窄越好**——只把「进程被环境杀死」这类**不改语义的**失败放进自动重试；逻辑与语义类失败重试只会**重复付费并重复副作用**。需要更丰富的语义就明确降级到原始原语自己写，不要偷偷把自动重试的口子放宽。
- **恢复要把「被杀死时正在做的那一轮」留在链上**，天真的两种做法都错：取消或崩溃时那一轮**从没写过 turn-complete**，于是「天真续跑」要么**把用户已经主动取消的活重做一遍**，要么**把上下文全丢掉**。官方恢复启动读三份东西——最后成功落盘的**快照**、快照游标之后的 `session.out` 尾部（含 `partialAssistant`，即那个没收 `finish` 的半成品，`cleanupAbortedParts` 已剥掉仍在流式中的碎片）、以及最后一个 turn-complete 游标之后的 `session.in` 尾部（死掉的 run 没来得及确认的用户消息）。当**同时**存在半成品与两条以上在途用户消息时，把 `[第一条在途用户消息, 半成品]` 接进链上，其余在途消息当作全新轮次派发——模型看到的是 `[...已结算消息, 被打断那轮的提问, 它的半成品回答, 新的追问]`。→ 判据：**「取消」不等于「丢弃」**；保留半成品并让新指令自带上下文，后续无论是「接着写」「改成别的」还是「不相关的提问」都能被正确处理（现代指令跟随模型以最新一条用户消息为准）。
- **半成品必须显式标记为未完成**：快照里每条消息带 `final` 字段，**失败轮次捕获的部分答案是 `final: false`**；`state` 另存运行时无法从消息重建的东西（如压缩摘要）。→ 判据：**部分产出必须带「我没做完」的标记**；不标的话，恢复后的链路会把半成品当成完整答案继续往下推。
- 与 §重试的粒度是「步骤」不是「整段」 分工：那条管**有了 journal 之后重试怎么跳过已完成的步骤**；本条管**没有业务方日志时，怎么用平台自带的完成标记做出等价的跳过**，以及**哪些失败才配进这个自动重试口**。与 §平台失败前向重试 分工：那条管**该重试还是该撤销**；本条管**重试从哪里接、被打断的那轮怎么处置**。
- **提升层**：工作流 / 可复用 Skill（中断恢复与重试准入）。
- 触发词：OOM 恢复、进程被杀、中断恢复、recovery boot、取消不等于丢弃、半成品保留、完成标记游标、重试准入、只重试一类失败、final false、partial assistant、被杀死的进程怎么续。

## 配了不等于会跑：参数之间的硬约束会让重试静默失效；兜底处理器的管辖范围由它所在的容器决定（来源：Kestra 官方 `kestra.io/docs/workflow-components/retries.md` 与 `workflow-components/errors.md`，2026-09-23 r154-B 独立实拉首读，新信源首读）
- **★参数之间有一致性约束，不满足时不是报错而是「永远不触发」**：官方在重试文档里放了一条 warning——`Ensure retry.interval is smaller than maxDuration, or retries may never run.`（重试间隔必须小于任务总时长上限，否则**重试可能永远不会跑**）。→ 判据：**「我配了重试」不等于「重试会发生」**；写进配置的参数之间要过一遍**两两一致性检查**（尤其是「间隔」与「总预算」、「单次上限」与「总上限」这类同量纲不同刻度的对子）。这类失效的共同长相是：**语法合法、加载成功、日志干净、行为与没配一样**——所以只能靠**主动的一致性校验**抓，不可能靠报错抓。
- **同一个词在不同的刻度上指不同的事，必须显式命名是哪一层**：官方把两个旋钮分开定义——`timeout` 是**单次任务尝试**（初次或任何一次重试）的最大时长，超了这次尝试失败；`retry.maxDuration` 是**该任务的总时长上限**，**包含所有尝试与它们之间的等待**，超了就不再重试。官方给的算例很清楚：`timeout: 10m` 配 `maxDuration: 30m` ＝每次最多 10 分钟、**总共最多磨 30 分钟**。→ 判据：**「单次多久算超时」与「总共允许磨多久」是两个刻度，必须分别设置并各自有值**；只配一个，另一个要么无界要么被误解。
- **「重试发生过」本身是一个应该留痕的状态，别让它静默**：官方提供 `warningOnRetry`——**只要发生过重试，整个执行的状态就被标成 WARNING**（默认关闭）。→ 判据：**靠重试扛过去的一次成功，和一次就成功的成功不是一回事**；不给「重试过」留痕，等于把不稳定的信号洗成绿灯，下一次更严的抖动就会直接崩。（与 §别把「重试成功」当成「做对了」 互补：那条讲**归因**，本条讲**把这件事变成可观测状态**。）
- **兜底处理器的管辖范围＝它挂在哪个容器上，不是全局**：官方把两种错误处理拆开——`errors` 是**执行生命周期内**的失败处理（任务或流程出错时触发，适合「只在失败时告警」「只在某个可组合任务的子树里处理错误」）；`afterExecution` 是**执行已经结束之后**按最终状态触发（适合「按 SUCCESS / FAILED / WARNING 分别做不同的事」）。并且官方强调：**局部错误处理器只作用于定义它的那个可组合任务的子树**——官方例子里挂在 `t2` 上的处理器**捕获不到 `t1` 的错误**。→ 判据：**兜底放在哪一层，就只兜住那一层**；写兜底前先问「我要兜的是这一个子树、还是整条流程的收尾」，选错层级＝最需要兜的那块没被兜住，而不报任何错。
- 与 §重试的准入面越窄越好（r154-A 落）分工：那条管**哪些失败才配自动重试**；本条管**重试参数组合会不会让它压根不跑、以及怎么让「跑过重试」看得见**。
- **提升层**：工作流 / 可复用 Skill（重试配置的一致性校验与失败处理分层）。
- 触发词：重试不生效、配了没跑、参数冲突、interval 大于 maxDuration、单次超时与总时长、warningOnRetry、重试留痕、兜底范围、局部错误处理、errors 与 afterExecution、处理层级。


## 端到端超时由最严的那一层决定，不是由你设的那一层决定（来源：Modal 官方 `modal.com/docs/guide/webhook-timeouts` + `/docs/guide/timeouts`，2026-09-24 r156-C 独立实拉首读，清单内信源此前未深拉）
- 实测刻度链：Web 函数 **HTTP 请求上限 150 秒**（硬限制），底层函数**可以有更长的超时**，超 150 秒时服务端返回 **303 重定向到 result URL** 续等；而**客户端**的重定向次数又是一道闸（浏览器约 20 跳 ≈ 50 分钟；Python `urllib` 默认单 URL 最多 **4 跳 ≈ 12.5 分钟**）。判据：**同一条链路上每层的超时都要单独数一遍**，实际能等多久＝最短的那一段，跟你给函数设了多长无关。
- **★长任务别赌"等得住"，改成轮询**：让入口 `spawn()` 后**立刻返回 call_id**，另一个端点用 `FunctionCall.from_id(call_id).get(timeout=0)` 查，未完成就回 **202**。判据：**需要超过 HTTP 层上限的任务，架构上就该拆成"提交 + 查结果"，而不是把超时一路调大**。
- 判据补充：**超时不是唯一的等待上限**——重定向次数、客户端库默认值、是否需要 CORS（CORS 场景拿不到 result URL 的头部）都是同一类"隐式上限"，排查等待类失败时逐个排除。
- 与 §超时是 per-attempt 度量 分工：那条管单次尝试的计时口径；**本条管跨层链路的合成上限**。


## 多因并存时先修主因，并把每条修复写成「四要素配方」（来源：AWS Strands Evals 2026-06-15 + FutureAGI 2026-05-14 + IETF draft-pei-opsawg-agentops 2026-07-21，2026-09-24 豆包 r157-B 实拉取证，同轮 WB 审计独点属实后落地）
- **★先修 PRIMARY，次级与三级常常随主因消失**：一次评测里同时报出的多个失败往往有因果链，先啃主因而不是按数量排序。判据：**按"报了几次"排序会让你先修十个衍生症状**；先问"哪些是原因、哪些是结果"。
- **★按修复类型分组批量改**：同一类修复（工具描述类 / 系统提示类）攒在一起一次改完，而不是逐条来回迭代。判据：**同类改动的验证成本可以摊薄**，逐条改等于每改一次都重跑一遍全量。
- **★每条修复写成四要素**：根因 / 长期结构性建议 / 立即修复的具体改动（提示 or schema）/ 验证脚本或评测模板。判据：**只有"改了什么"没有"怎么证明改对了"的修复，下一轮回归时无法判断它是否还生效**。
- **★事件模型要把「因果起源」和「传播症状」分开记**：观测事件分事件/异常/断言/诊断四类，记录时必须区分"这是起点"还是"这是被传导出来的表现"。判据：**把症状当起源修，会出现"修好一个又冒出下一个"的无限排障**。

## 排障前先要「决策出处」：否则分不清是坏输入还是坏推理（来源：Adaline 2026-05-27 + cordum.io 2026-04-01，2026-09-24 豆包 r157-B 实拉取证，同轮 WB 审计独点属实后落地）
- **★每个决策点要能回溯"当时它看到了什么"**：这一步检索到了哪些文档、作用域内有哪些先前输出、收到过哪些用户信号。判据：**结论错了但证据是对的 → 改推理；证据本身就是错的 → 改检索/输入**；没有决策出处，这两条路根本分不开，只能瞎试。
- **★用同一个追踪标识把"工具选择 / 策略规则 / 审批 / 执行结果"串起来**：意图与结果之间要有一条可查的连线。判据：**断掉的链路会让"为什么选了它"变成不可回答的问题**。


## "设置没生效"的四类分诊：先查映射，别当 bug 修（来源：Pydantic AI 官方 pydantic.dev/docs/ai/capabilities/thinking，2026-09-24 r160-C 独立重拉首读）
- **① 后端根本不支持 → 静默忽略**：没有报错、没有告警，参数像没写一样。判据：**先查"这个能力在这个后端上是不是常开/不可关"，再查调用链**。
- **② 档位被就近吸附 → 语义漂移**：请求发出去了、值也变了，只是**不是你要的那个**。判据：**现象是"效果不对"而不是"没生效"，去比对档位映射表**。
- **③ 被更具体的设置覆盖**：统一设置与厂商原生设置同时存在时后者赢，且可能只给一条 warning。判据：**全局搜一遍同名能力的所有配置位**。
- **④ 根因在上游、报错在下游**：历史被加工 → 厂商侧部件配对被破坏 → 报错出现在下一次请求。判据：**报错点与根因点分离时，优先回溯"最近一次对中间产物的加工"**。
- **★"字段为空"不等于"没有"**：兼容 API 不返回推理摘要时，`content` 是空的，**原始内容被放在 `provider_details` 里**（遵循"原始推理不直接展示给用户"的约定）。判据：**先看旁路字段再下"没返回"的结论**。


## 可复现调试靠确定性替身与结构预检（来源：Haystack 官方 components/agents/agent.py + converters/output_adapter.py + about-pipelines，2026-09-24 r161-C 独立实拉首读）
- 用确定性 mock 复现：把外部依赖（embedder / generator）换成同接口、同输入同输出、不联网的替身，bug 才能稳定复现而非偶发。
- 结构先可视化再信任：pipeline 建好后先画成图确认组件连接符合预期，再跑；边接错（输出类型不匹配、连错分支）是常见无声故障。
- 判据：调试复杂流前先核对"结构 / 接线"这一层，很多失败不在逻辑而在连线。
- 兜底只在底层真抛错时才生效：fallback 依赖底层组件正确实现超时并抛异常；若底层吞错，兜底永远不触发。
- 判据：验证"错误处理是否真有效"，要确认底层确实会 fail-fast 抛错，而不是假设框架会兜底。
- Agent 退出靠显式终止原因：空响应且无识别出的终止原因不触发退出，保留对畸形工具调用的恢复行为 —— 验证 agent 收敛时要看它有没有明确的停止条件。

## 「设置没生效」第五类：配置挂错了层 —— 上层不认识实例、后端其实自动做（来源：Strands Agents 官方 harness/configure/context-and-caching 2026-09-25 实拉；与 §四类分诊 合并为五类）
- **同一开关在两类 provider 上含义不同**：Bedrock / Anthropic 直连由框架显式配置 cache point 与缓存的工具定义；OpenAI / Google 等**在服务端自动缓存，框架没什么可配**——**在这些后端上把缓存关掉没有任何效果**。
- **预构造实例上的配置被忽略并警告**：把缓存开关传给一个已经建好的 Model 实例时，框架**不知道这个实例的 provider 是谁**，于是忽略并给一条 warning；要配就得配在实例自己身上。
- → 判据（新分型）：**看到「配了没效果」先问这个配置归哪一层** —— ①上层封装是否根本不掌握下层实例的真实类型（→ 忽略 + warning）②这项能力在后端是不是自动完成的（→ 开关无效果）。与已有四类（后端不支持／档位吸附／被更具体设置覆盖／根因在下游）并列，**这一类专治「配置挂在错误的层」**。
- 提升层：工具 / 工作流。

## 「卡住」的三问分型：在排队 / 在跑 / 整体超期，三者处置完全不同（来源：Temporal 官方 docs 2026-09-25 独立实拉 —— encyclopedia/detecting-activity-failures、retry-policies、task-queue/naming）
- **三种超时测的是三件不同的事**：①**Schedule-To-Start**＝从「排进队列」到「被 worker 领走」的时间，测的是**排队时长／worker 够不够**；②**Start-To-Close**＝**单次执行**的时长，测的是这一步跑多久；③**Schedule-To-Close**＝从第一次排期到全部完成的**整体时长**（一次执行只算一次，不随重试重置）。→ 判据：**先分清「它在等」还是「它在跑」**——等待类的失败重试没有意义，执行类的失败才是重试对象。
- **排队类超时是设计上不可重试的**：Schedule-To-Start 超时**无论重试策略是什么都不触发重试**，因为重试会把任务放回同一个队列。官方给的出路是**改用指标监控排队延迟**（`schedule_to_start_latency`）＋**准备把流量改道到另一个队列**的具体方案。→ 判据：**「重试能改变什么」是重试的前置题**——重试会把请求放回同一个失败位置时，重试就是空转，正确动作是换路或扩容。
- **服务端不负责发现 worker 挂了**：worker 失联或崩溃时服务端**检测不到失败**，只能靠 Start-To-Close 超时兜底把任务重新排队。→ 判据：**没有超时就没有失败**——长耗时步骤必须显式配单次执行超时，否则一个 worker 崩掉会让这一步永远「在运行中」；跑得更久的步骤要配心跳（heartbeat）＋心跳超时，让「活着但没进度」也能被发现。
- **名字错配是静默分叉**：任务队列是**首次使用时动态创建**的，名字写错不会报「队列不存在」，而是**新建一个空队列**——worker 永远收不到任务、流程原地卡住且没有任何错误。→ 判据：**凡是按名字动态创建的中介（队列／通道／主题／技能名／钩子名），拼错的表现都是「什么都没发生」而不是报错**；排查顺序上先对名字常量，再查逻辑。与 dl §结构先于逻辑 同源。
- 提升层：工具 / 排障。

## 每一步都落检查点，调试从任意一步重跑（来源：r188 批内化内容 + 我独立复核）
- **长工作流的每一步都落检查点，支持从任意一步 `run_from` 重跑**：排查某一步的问题时不必从头跑一遍。→ 判据：**可重放的粒度决定调试成本**——只能整体重跑的工作流，改一个参数要付整条链的时间；与 dl §确定性替身 分工：那条管"用替身把外部依赖固定住"，本条管"把中间状态固定住，让重跑从中间开始"。
- 提升层：排障 / 工作流。

## 主动提前终止要写原因，且原因要能在事后查到（来源：Pipedream 官方 pipedream.com/docs/workflows/building-workflows/control-flow/end-workflow，2026-09-25 r179-B 独立实拉）
- **提前结束工作流（`$.flow.exit()` 或预置 End Workflow 动作）时可以配一个 reason**，官方明写 "This reason will be surfaced when inspecting the event execution"。
- 判据：**"没走到最后一步"有两种成因——被前面挡住了，和跑到了但主动退出**，留痕上不写原因就分不开，事后只能靠猜。与 dl §Agent 退出靠显式终止原因 分工：那条管**模型侧**有没有给出终止信号，本条管**人工/编排侧**的提前退出要不要把原因写进执行记录。
- 提升层：可观测性 / 排障。
## 环境重置成本决定"容忍污染"的程度：重建越贵，越容易把排查成本转嫁给模型（来源：Activepieces《What Is Harness Engineering》2026-09-27 实拉）
- **原文要点**：`When a sandbox takes 30 seconds to refresh, DevOps teams tend to let agents struggle in "dirty" environments to save time, whereas a 100ms refresh rate makes a clean-slate strategy the most efficient path for the model.` —— 同一批人、同一个 agent，只因**沙箱重建延迟从 30s 降到 100ms**，最优策略就从"在脏环境里继续"翻转成"推倒重来"。
- 判据：**"要不要从干净环境重来"不是品味问题，是一个由重置成本决定的策略变量**。重置便宜 → 干净重来（模型面对的是已知初始态，症状可复现）；重置昂贵 → 人会不自觉地容忍污染环境，于是 agent 的失败里混进"环境里残留了什么"这个额外未知数，排查难度按未知数个数增长。
- 实操含义：报告一个 agent 失败时，**先回答"它是从什么状态开始的"**——如果答案是"不确定，环境被前面的尝试改过"，那么这条失败记录的诊断价值接近零。判据：**便宜的重置是"最小化"这一步能不能做的前提**；没有便宜重置，"最小化"就只能靠推理，不靠复现。
- 与 §失败现场要自动留、可检查、可续跑 分工：**那条管"现场要留下来"，本条管"留下来之后，什么时候该丢弃现场推倒重来"**——留现场是为了不复现不出的 bug，重建便宜则是为了不让现场变成污染源。
- 提升层：工作流 / 工具。

## 参数微变的循环抓不住：按"同一工具在同一执行内的调用次数"计数，而不是按参数签名去重（来源：Activepieces《Building a Reliable Harness for Multi-Agent AI Systems》2026-09-27 实拉）
- **原文要点**：`the highest financial risk lies in "semantic loops," where an agent attempts to solve a task by repeatedly calling the same tool with slightly different parameters`；`When an LLM receives a "Tool Error" response, its default behavior is to hallucinate a new parameter, leading to a cascade of tokens that provides zero utility.`；排查手法是 `filtering logs for identical tool calls occurring within a single execution ID`，从而找出 `which specific prompts lack the exit conditions`。
- 判据：**"换了个参数再试一次"是循环，不是进展**。签名去重（同参数同工具才计数）会在参数每次微变时全部漏判——agent 看起来一直在"尝试新办法"，实际是在同一个死胡同里抖动。
- 因此循环检测要**按工具计数**（同一 execution 内同一工具被调用 N 次即告警/终止），并且**告警的落点是 prompt 缺退出条件**，不是"这个工具坏了"。判据：**计数命中说明写 prompt 时没回答"什么时候该放弃"，补的是退出条件；只加调用上限而不补退出条件，agent 会在上限处静默终止并交出一份残缺结果**。
- 反模式：把语义循环当"模型不够聪明"去换模型；或对同一个工具设两个不同名字绕开计数（等于主动拆掉自己的护栏）。
- 与 `wb-execute-discipline` §4xx 签名防重发闸 分工：**那条管"确定性失败（4xx）的重复调用要在发出前短路"，本条管"非确定性失败下参数微变的抖动循环"**——前者按签名拦得住，后者必须按次数才拦得住。
- 提升层：可观测性 / 工作流。

## 重试前先归因到层：错误要标"它发生在哪一层"，且归因器必须自曝 best-effort（来源：Pipedream `pipedream.com/docs/connect/components/actions.md`「Error responses」，2026-09-27 实拉）
- **原文要点**：失败响应里除 `error.name` / `error.message` 外还有一个 `attribution` 对象，用 `origin` 把错误归到四层之一：**`component_code`**（工具/组件自身代码错，发生在发出任何网络调用之前）→ 不可重试，要改组件代码或入参；**`upstream_api`**（第三方 API 返回 4xx/5xx）→ 有时可重试（5xx 常为瞬时，4xx 通常指向入参或请求本身，重试多半无效）；**`network_io`**（DNS 失败、连接被拒、超时）→ 最可能瞬时、值得重试；**`response_parsing`**（2xx 但解析失败）→ 不可重试。同时附 `network_calls_count` 与 `last_call{client, method, host, status, duration_ms}`。
- 判据：**"该不该重试"的答案不由错误类型给，而由"错误发生在哪一层"给**。同一个 `AxiosError: Request failed with status code 500`，归到 `upstream_api` 是"可以试一次"，归到 `component_code` 就是"重试一万次也一样"——只看消息文本，这两种情况长得一模一样。
- **★归因本身是 best-effort，必须自曝**：原文明确 `Error attribution is best-effort`，并列出两种已知误判情形——**上游 SDK 在真正失败之后又发了 telemetry / logging 调用**（于是"最后一次调用"并不是真正失败的那次），以及**对同一个 host 发了多次调用**（分不清是哪一次）。判据：**把 best-effort 的归因当事实写进结论，等于把概率判断伪装成确定性证据**；引用归因结果时必须带上"这是推断"的标记，并在上述两种情形下显式降级为"归因未定"，不能据此直接下重试或定责结论。
- 反模式：只看 `error.message` 里的状态码就决定重试次数；或把归因字段当作权威事实直接写进给用户的故障结论里。
- 与 §重试策略三型（错误四档 / 重试按调用对象收窄）分工：**那条管"抛错方该怎么声明自己的重试语义"，本条管"抛错方没声明时，观测方如何从调用痕迹反推它属于哪一层，以及反推错了怎么办"**。
- 提升层：可观测性 / 工作流。

## 重试 / 轮询耗尽之后往哪走：默认出口的方向要先问清楚（来源：Pipedream 官方 `docs/workflows/building-workflows/code/nodejs/rerun`，2026-09-27 r199-A 实拉 9,640B；同源 `errors.md` 8,995B）
- **★次数用完之后的平台默认是"继续往下走"，不是失败**：原文「When you exceed `maxRetries`, the workflow proceeds to the next step. If you need to handle this case with an exception, `throw` an error from the step」。也就是说重试 / 轮询机制的**默认出口朝向"成功"**，失败会以"一份没拿到的输入"的身份继续被下游加工。**排查时不能把"整条链路没报错"读成"重试成功过"**——要看重跑计数（该平台的 `$.context.run.runs` 从 1 起算）。
- **★想要失败必须自己声明**：想让"重试耗尽 = 失败"，得在计数分支里显式 `throw`；指望框架替你判定有没有成功，拿到的就是静默通过。**判据：写完重试 / 轮询后先回答一句"次数耗尽时，出口是报错还是放过"，答不上来说明这条路径还没定义完。**
- **★测试态与生产态跑的不是同一条路径**：挂起 / 重跑在测试执行时**不生效**（原文「Workflow execution canceled — this may be due to `$.flow.suspend()` usage (not supported in test)」）；测试期的未处理错误也**不发通知、不进自定义错误流**（`errors.md`「Error notifications are only sent when a deployed workflow encounters an error on a live event」）。→ **在测试态"跑通了"证明不了生产路径可用**；凡是依赖挂起、回调、告警的行为，必须在已部署的真实触发下再验一次。
- **★挂起要自带超时，且睡醒是一次新的执行**：默认 24 小时后自动取消，可自定义毫秒值；平台在恢复时**重置计费计数**，每次唤醒按一次全新执行算。写"等外部回调"的逻辑时，必须显式设超时，并知道每次醒来面对的是新的执行上下文而不是原上下文的延续。
- 与 §部分完成是合法的失败态、§修复不能由容错装置构成 的分工：那两条讲"不许伪装成功"的原则与"容错不等于修复"；本条指出**伪装成功最常见的那个具体开关就长在重试计数上**。
- 提升层：可观测性 / 工作流。

## 入队四态语义；显式命令覆盖持久设置；降级会剥离语义标签（来源：docs.openclaw.ai/tools/steer.md 3,228B，2026-10-01 r342A 独立 curl 实拉逐串命中）

- **原文**：①「`/queue steer` makes normal inbound messages try to steer the active run ... `/queue collect` or `/queue followup` when future normal messages should **wait for a later turn** instead of steering the active run. `/queue interrupt` when the **newest message should replace the active run** instead of steering it.」；②「`/steer <message>` is an explicit command that tries to inject that command's message into the active run ... **regardless of the stored `/queue` setting**.」；③「When that injection is not available, **the command prefix is stripped** and `<message>` continues as a normal prompt.」
- **判据**：① **新输入与在途运行的关系是四档显式语义（改向在途 / 本轮后跟随 / 排队等后续轮 / 替换在途），不是一个「要不要中断」的二值开关**⇒ 排障「我新发的指令怎么没生效」先确认当前落在哪一档；把「排队跟随」当「改向」是最常见误读——它本来就设计成不打断本轮。② **一次性显式命令独立于持久设置**⇒ 「设置是什么」与「这次实际走哪条路径」要分开看，显式指令会临时覆盖默认档位。③ **降级会剥离语义标签**：注入不可用时命令前缀被去掉、消息按普通提示继续——内容还在，但「这是一条改向指令」这层语义没了。⇒ 排查「指令被当普通问题回答了」时不是消息丢了，而是它被降级成了另一类输入；设计降级链路时必须回显原语义标签，否则调用方永远无法自证自己发的指令变成了什么。
- **提升层**：工具/工作流。触发词：入队四态、steer/collect/followup/interrupt、显式命令覆盖持久设置、降级剥离语义标签。

## 续期只认真实执行；环境变量常常只是初值（来源：docs.openclaw.ai/concepts/session.md 22,390B + www.activepieces.com/docs/install/configure-operate/telemetry.md 2,830B，2026-10-01 r342B 独立 curl 实拉逐串命中）

- **原文**：①「Three attempts that fail to start a backend turn exhaust the recovery budget. Once a real backend turn starts, the budget refreshes ... **Accepting, queueing, or preparing a resume request alone does not refresh it.**」；②「CLI backends that do not report turn acceptance refresh the budget **only after observed assistant output or tool activity; silent startup does not refresh it.**」；③（遥测）「`AP_TELEMETRY_ENABLED=false` still works as a **starting value**: each platform's setting is created the first time it is read and takes the variable's value ... **Once the setting exists, the toggle governs it and changing the variable has no further effect.**」；④（遥测）「**Deployment setup** is a separate switch ... Unlike product analytics it **does not read `AP_TELEMETRY_ENABLED`** — switch it off in the UI to stop the daily snapshot.」
- **判据**：① **意图不算活动**：接受、排队、准备恢复请求都不刷新配额，只有真正启动后端回合才刷新。⇒ 查「预算怎么突然耗尽了」时，别数发起了多少次恢复，要数真正跑起来几次；把排队中的请求当成已消费是常见误算。② **静默启动不算证据**：不上报 turn acceptance 的后端，只有在观测到实际输出或工具活动后才认为它活着。⇒ 判断某个环节是否真的在跑，不能用「没报错」当证据，要找它的可观测产物。③ **环境变量常常只是初值，不是终值**：设置首次被读时落库，之后由 UI 开关掌管，再改环境变量无效。⇒ 排查「我明明改了环境变量怎么没生效」的标准答案是——先查这个设置是不是已经被创建过一次；这是配置类故障的高频根因。④ **一个总开关不等于所有外发都关了**：产品分析与部署快照是两个独立开关，且后者根本不读那个环境变量，只能在 UI 关。⇒ 关外发时要按通道逐个枚举并逐个验证关闭机制，不能假设「关了总闸」。
- **提升层**：工具/工作流。触发词：续期只认真实执行、排队不刷新预算、静默启动不算证据、环境变量只是初值、设置落库后变量失效、外发逐通道开关。

## 按「调用方身份」计数的闸门必须自证生效：反向代理会让它整体失效（来源：Flowise rate-limit 本机实拉，r326B）
- **原文**：「The rate limitation is **tracked by IP-address**. If you have deployed Flowise on cloud service, you'll have to set `NUMBER_OF_PROXIES`」；「most likely you are behind a proxy/load balancer. **Therefore, the rate limit might not be able to work.**」；官方校验闭环=逐档 +1 直到 `{{hosted_url}}/api/v1/ip` 回显的 IP 与你的实际 IP 一致。
- **判据**：① **「按身份计数」的闸门（IP / 租户 / 客户端）上线验收必须做一次身份回显比对**，否则测的是没被限流的那条路径而全绿；失效形态是**完全不工作**（不是变宽），最危险。② 平台应自带「回显我看到的客户端身份」端点——没有自证端点的限流 = 不可验证的限流。③ 修复方向是让平台认识真实拓扑（代理档数），而不是放宽阈值。
- **提升层**：工具/安全边界。触发词：限流按 IP、NUMBER_OF_PROXIES、代理后限流失效、身份回显自证、闸门可验证性。

## 脱敏的正确形态是「保留可观测骨架、替换载荷」，且错误详情必须在脱敏清单内（来源：docs.n8n.io/deploy/host-n8n/configure-n8n/security/redact-execution-data.md 17,934B，2026-09-30 r338C 独立实拉）
- **原文**：「Before execution data redaction, the only option was to disable execution history entirely... which removed all visibility into workflow success or failure status. **Execution data redaction preserves execution monitoring while hiding the sensitive data payload.**」保留 = 节点名 / 执行状态 / 耗时 / 工作流结构；替换 = `item.json` → 空对象、`item.binary` 移除。
- **判据**：① **隐私开关不该以「关掉观测」为代价**——正确形态是**降级观测粒度**：元数据骨架保留、载荷替换。设计任何隐藏数据开关时先问：关掉之后还能不能判断成功/失败/耗时/走到哪个节点？答不出来就是关错了对象。② **错误通道必须在脱敏面内**：原文「it also redacts error details... Only the error type and HTTP status code remain」——只脱敏正常 payload 而保留错误原文，脱敏形同虚设（错误是载荷最大的旁路，一次异常即可把未导出字段带进留痕）；最小可诊断集 = 错误类型 + 状态码。③ **敏感字段的声明权在作者侧且高于查看者权限**：节点作者用 `sensitiveOutputFields` 标记的字段「always redacted... even for users with reveal access」——不能靠有权限就能看覆盖作者声明。
- 提升层：工具/可观测性。触发词：脱敏保留骨架、降级观测粒度、错误详情脱敏、sensitiveOutputFields、作者声明高于权限、关掉执行历史。

## 定时器恢复的默认动作是「重排未来时点」而不是「补跑历史欠账」：合并错过的滴答，且用运行身份而非起始时间认领（来源：docs.openclaw.ai/automation/cron-jobs/how-it-works.md 9,877B，2026-10-01 r339A 独立 curl 实拉逐串命中）
- **原文**：①「On Gateway startup, overdue agent-turn jobs and jobs that await a heartbeat are **rescheduled instead of replayed immediately**, keeping model/tool execution out of scheduler startup.」②「When a running Gateway wakes after a deadline, the scheduler **coalesces missed timer ticks**. Cron rechecks eligible jobs using its **stored deadlines and run receipts**。」③「Restart recovery matches finalized results to the **run identity**, never just a coincident start time.」④「If a foreign process exists but its **start identity cannot be verified**, its receipt becomes recoverable **after more than two hours** from the queued or running start. Recovery revokes that receipt before admitting another run; it **cannot undo external side effects already in flight**.」⑤「Catch-up limits and delays **pace recovery; they do not expire it**.」⑥「Setup/startup stalls get a **phase-specific timeout** … and are **capped independently of long `timeoutSeconds` values** so cold-start/auth/context failures surface quickly.」
- **判据**：① **追赶（catch-up）的正确默认动作是 reschedule 而非 replay**——重排把欠下的次数折进未来的下一次判定；补跑则会在整个系统刚起来、最脆弱的那几十秒里把停机期间积压的全部工作一次性倾泻下去，等于用重启给自己做一次压测。② 追赶的计量单位是**合并**（coalesce）而非队列：错过的时钟滴答合成一次判定，且只根据**已落库的 deadline 与 run receipt** 重新检查资格，不按墙上时钟现猜——「我睡了多久」不是可恢复依据，「我存下来的到期记录」才是。③ **恢复/bragging-rights 的匹配键必须是运行身份，不是启动时刻**：同一时间戳启动的进程不等于同一个 run；只有身份能对上才能认领已终态的结果。身份无法自证的孤儿进程，要过保守阈值才可收回其收据——宁可慢，不可错领。④ **恢复算子有边界：能撤销资格，不能撤销已在途的外部副作用**。写「自动接管/自动重试」前必须分清这两个 Domain：内部记账可以回滚，已经发出去的外部调用回不来。⑤ **限速与延迟只调节追赶的节奏，不消灭追赶的义务**（"pace recovery; they do not expire it"）——别把限流当成静默丢弃。⑥ 长任务 timeout 之上还要有**独立的相位看门狗**：把设置/冷启动/鉴权/上下文构建单独计时并封顶，否则这些早期失败会被一个 48 小时的总超时掩盖到几小时后人才发现。
- **提升层**：工具/工作流。触发词：追赶重排不补跑、reschedule not replay、coalesce missed ticks、按运行身份认领、孤儿进程阈值、副作用不可回滚、pace not expire、相位看门狗、启动停滞快速失败。


## 远端执行的「权威副本（canonical）」唯一且会随模式改变；自动修复不得顺带放宽安全面；危险能力用 break-glass 显式命名（来源：docs.openclaw.ai/gateway/config-agents/sandbox.md 11,028B + concepts/agent.md 8,025B，2026-10-01 r346B 独立 curl 实拉逐串命中）
- **原文**：①「seeds the remote workspace once after create or recreate；then **keeps the remote SSH workspace canonical**；**does not sync remote changes back to the host automatically**」；「In `remote` mode, **host-local edits made outside OpenClaw are not synced into the sandbox automatically after the seed step**.」；②「Containers default to `network: "none"` ... **`"host"` is blocked**. `"container:<id>"` is blocked by default unless you explicitly set `sandbox.docker.dangerouslyAllowContainerNamespaceJoin: true` (**break-glass**).」；③「On upgrade, `openclaw doctor --fix` disables sidecars affected by a persisted `"none"` value and restores the dedicated network **without silently enabling egress**.」；④「After a workspace has been observed, OpenClaw stores its setup state and attestation in the shared SQLite database ... If a **recently attested workspace disappears or is wiped, startup refuses to silently reseed** `BOOTSTRAP.md`.」。
- **判据**：① **远端执行必须显式声明"谁是 canonical"，且非权威侧的写入不保证生效**：SSH/OpenShell 后端在 seed 之后把远端工作区定为唯一权威副本，**既不会自动把远端改动同步回宿主，也不会把宿主此后的本地编辑同步进去**。⇒ 于是出现一类极难自查的故障：「我在本地改了，远端跑的还是旧的」和「远端跑出来的结果，本地看不到」——两者的根因是同一个：**这一侧不是 canonical**。排查"改了没生效"类问题，先问三件事：当前 canonical 在哪一侧、我改的是哪一侧、两者之间有没有同步步骤。② **安全默认值是"无出口"，且高危形态要靠显式 break-glass 开关放行**：容器网络默认 `none`；`host` 直接阻断；"加入别的容器命名空间"更是需要把开关命名为 `dangerously...` 才可用。⇒ 两层设计值得照搬：一是**默认闭**而不是默认开，需要出网是例外；二是**把危险写进名字里**——让调用方在敲下这个配置时就读到警告，比文档里写一段"请谨慎"有效得多；同时"可放行"不等于"默认可放行"，break-glass 开关仍应出现在审计清单里。③ **自动修复可以修"坏配置"，但不得顺手放宽安全面**：升级时修复器会禁用被持久化坏值影响的组件并恢复专用网络，但明确**不静默开启出口**。⇒ 自愈工具的权限边界要写在工具里：修复的目标是"回到一个正确的状态"，不是"让功能跑起来"；凡是会让攻击面变大的改动（开网、提权、放宽松绑）都必须停下来交人确认，哪怕它是让报错消失的最短路径。④ **"目录空了"不等于"全新开始"**：工作区一旦被 attested，其状态记在共享数据库里；若该工作区消失或被清空，启动会**拒绝静默重新播种初始文件**。⇒ 这条防的是"状态与实体不一致时自动重建"造成的历史抹除：看起来是初始化，实际是把"曾经存在过"这个事实删掉。恢复路径必须显式要求"工作区与其数据库状态一起清理"，而不是让系统自己猜。
- **提升层**：工具/工作流/安全边界。触发词：canonical 权威副本、远端不同步回宿主、非权威侧写入不生效、网络默认 none、host 阻断、break-glass 显式命名、dangerously 前缀、自动修复不放宽安全面、不静默开启出口、attested 工作区消失拒绝重播种。


## 「没生效」必须拆成三分支（未发现 / 不合格 / 未执行）；静态资格报告只覆盖它检查过的项（来源：docs.openclaw.ai/automation/hooks/troubleshooting.md 2,683B，2026-10-01 r346C 独立 curl 实拉逐串命中）
- **原文**：①「Check the report's `workspaceDir` and `managedHooksDir` with `openclaw hooks list --json`. **Confirm you are inspecting the intended host, profile, and agent.**」「Each hook needs `HOOK.md` and one supported handler file; **a metadata file alone is insufficient**」「**Collection locations inspect immediate children** ... nested packs and collections are not followed, and **rejected entries do not cause unlisted children to be scanned**」；②「**Reports can pass requirements without proving that its module imports successfully.**」「A **`ready`** report **does not override the master switch or name selection** and **does not mean another agent's workspace was loaded**」；③「**Ordinary chat text does not trigger `command:new`**; `/stop` does not send hook replies; **a metadata subscription does not invent a custom trigger**.」「If the marker appears but the chat reply does not, **check the producer and route, not just enablement**」。
- **判据**：① **"它没生效"不是一个症状，而是三种互斥状态，排查路径完全不同**：**未发现**（根本没被收进清单：检查你在看的宿主/profile/agent 是不是你以为的那个、必需的成套文件齐不齐、发现只扫直接子级）、**不合格**（找到了但被判定不可用：看 `blockedReason`、缺失的二进制、环境、配置路径、OS、是否被显式启用、有没有声明事件）、**未执行**（合格了但没跑：查总开关、名称选择、重载模式、真实事件是否重放）。⇒ 一上来就问"为什么没生效"会同时在三条路上乱撞；**先确定它停在哪一态**，才能把检查项收敛到该看的那一份证据上。② **静态资格检查的作用域必须写成"它不证明什么"**：报告可以逐项通过 requirements，却**不证明模块真能 import**；`ready` 状态**不覆盖总开关、不覆盖名称选择、也不意味着别的 agent 的工作区被加载过**。⇒ 验收/健康类输出最危险的形态是"绿灯但只查了一半"——它让下游把"这份报告没报错"当成"这个东西能用"。凡是产出合格结论的检查，都要同时声明**它不覆盖的范围**，否则绿灯会被当成全局通行证。③ **发现过程不递归、也不因拒绝而降级**：集合位置只检查直接子级，嵌套的包与集合不被跟随，且被拒条目**不会**导致系统转而去扫描未列出的子级。⇒ 这条防的是"宽容退化"——一种常见的错误容错是：正规路径失败就自动放宽规则去别处找。**不跟随嵌套、拒绝后不放宽**保证了"能被找到"这件事是可预测的；若实现成"找不到就再往下挖一层"，加载面会随失败而扩大，且没人能说出最终到底加载了什么。④ **触发面必须与声明严格一致**：普通聊天文本不会触发 `command:new`，`/stop` 不发 hook 回复，元数据订阅**不会凭空发明一个自定义触发器**。⇒ 事件系统的订阅清单是**封闭枚举**而不是模式匹配；把"看起来像"当成"会触发"，是"我明明说了为什么没反应"类问题的根源。⑤ **标记出现但回复没出现时，查的是生产与路由，不是启用状态**：执行侧已经产生了可观测标记，说明"跑没跑"这个问题已结案，剩下的是**投递链路**的问题。⇒ 复用同一句话：**执行成功与送达成功是两个独立结论**，混在一起查会把"已执行"反复验证三遍而始终没碰真正的断点。
- **提升层**：工具/工作流。触发词：没生效三分支、未发现/不合格/未执行、blockedReason、ready 报告不覆盖总开关、静态检查不证明可 import、发现只扫直接子级、拒绝后不放宽、触发面封闭枚举、标记出现但回复没到、执行与投递分离。

## §六步循环下沉（2026-10-03 r408A 自 SKILL.md 下沉）
## 二、六步循环

| 步 | 做什么 | 判据（做到什么算这步结束） |
|---|---|---|
| 1 重现 | 用固定的输入/环境/命令拿到**确定性**的失败；记录命令与输出**原文**（不转述） | 我能重复触发它三次 |
| 2 最小化 | 剥掉无关输入、依赖、代码路径，直到最小失败用例 | 能把失败压成一小段片段或一条命令 |
| 3 假设 | 写 1–3 条**可证伪**的假设，按"验证代价"排序（先排最便宜的） | 每条假设都能说出"什么观察结果会否掉它" |
| 4 验证 | 用日志 / 断点 / 单测 / 二分 / 版本回退**直接观测** | 拿到一手证据（打印的值、返回码、trace），不是"读代码觉得应该是" |
| 5 修复 | 改最小必要处，说明**根因**（不是症状） | 能一句话说清"为什么之前会错" |
| 6 回归 | 跑最小复现（现在通过）+ 相关既有测试/路径（没挂） | 两边都跑过，输出留着 |

1–4 步才是排障，5–6 步是顺手完成的事。**卡住 90% 是跳过了 2 或 4。**


## §复现率低时的发力方向下沉（2026-10-03 r408C 自 SKILL.md 下沉）
## 复现不了就先把发生率抬高：1% 追不到，50% 就能二分（来源：topaiskills.com「diagnosing-bugs-skill-faq」（Matt Pocock `diagnosing-bugs`，mattpocock/skills 工程族）2026-09-21 实拉，与 §六步循环「没有稳定复现之前不改产品代码」互补——那条管"没有复现不许动手"，本条管"**复现率低到不可用时该往哪个方向使劲**"）

- **原文事实**：技能要求先有一条 **red-capable 命令**（已跑过至少一次、走真实 bug 路径、断言用户确切症状，且确定性 / 秒级 / agent 可无人跑）；原文判词 "*if you catch yourself reading code to build a theory before a red-capable command exists, stop*"。对 flaky 的处理不是追干净复现，而是**抬高发生率**：把触发循环一百次、并行化、加压、压缩时间窗、注入 sleep。原文阈值直白 —— **"a 50%-flake bug is debuggable, a 1% bug is not"**，一直抬到可调试为止。30 秒的 flaky 回路比没有回路好不了多少；2 秒的确定性回路是超能力。
- **判据**：
  1. **flaky 的方向是"抬高发生率"，不是"等它自己再出现一次"**。判据：**先量化当前发生率，然后逐档抬高（循环次数 / 并发 / 压力 / 时序干预），每档记录命中率**；只写"偶现"两个字等于把这个 bug 判了无期。
  2. **没有回路就禁止假设，且要大声说出"我没有回路"**。判据：**假设之前必须有一条已经跑过、能在该 bug 上变红的命令**；建不出来就停下列出试过什么，并点名要三样之一——能复现的环境、脱敏的捕获产物（HAR / 日志转储 / core dump / 带时间戳录屏）、或加临时生产埋点的授权。
  3. **假设必须自带预测，且成组并列**：生成 **3–5 条可证伪假设**，每条写清"**如果 X 是原因，改 Y 会让 bug 消失或变糟**"，**先给用户看排序再动手测**（单条假设会锚定在第一个想得通的解释上）。判据：**一条没有预测语句的假设不是假设，是一个名词**。
- 提升层级：工作流（排障循环的执行顺序）+ 工具（回路与探针的构造）。
- 触发词：复现率、抬高发生率、flaky 阈值、red-capable、red-capable 命令、无回路不假设、假设带预测、3–5 条假设、锚定。



## 数据钉定与局部执行下沉（2026-10-04 r409A）
## 数据钉定（input pinning）隔离待测单元：dev-only 钉子、生产忽略（来源：docs.n8n.io types-of-executions 6,643B，2026-09-30 r327B 独立实拉）
- **原文**：`On future runs, instead of executing the pinned node, n8n will substitute the pinned data and continue following the flow logic... Production executions ignore all pinned data.`
- **判据**：① 迭代调试时把上游节点输出**钉死为固定样本**，下游只在这一固定输入上反复试错 → 把「单元待测」与「上游可变性/外部调用成本」解耦，避免每次改一行都要重打整条链路或重复打外部服务。② 钉子是**开发态构造物**，生产执行必须全部忽略（否则测试夹具污染真实数据 + 跳过本应执行的真实逻辑）。③ 与「局部执行」配合：钉输入 + 只跑待测节点 = 最小可复现调试闭包。提升层：工具/工作流。触发词：数据钉定、input pinning、确定性迭代、dev-only 夹具、生产忽略 pin。

## 局部执行（partial execution）：重跑范围可靶向，不整流产跑（来源：docs.n8n.io types-of-executions 6,643B，2026-09-30 r327B 独立实拉）
- **原文**：`Partial executions are manual executions that only run a subset of your workflow nodes... executes the specific node and any preceding nodes required to fill in its input data.`
- **判据**：① 重跑/复现应**只跑待测节点 + 喂它所需的最小前驱**，而非把整条工作流从头跑一遍——降低复现成本、避免重触发副作用节点。② 局部执行仍需触发拓扑（须有一条 trigger 描述「何时执行」），不是任意节点都能起跑 ⇒ 靶向重跑要在「最小前驱」与「拓扑合法性」之间取平衡。③ 与「数据钉定」是同一调试哲学的两面：一个控输入、一个控范围。提升层：工具/工作流。触发词：局部执行、partial execution、靶向重跑、只跑待测节点、最小前驱。

## 等待/轮询/卡住运行处置（来源：OpenClaw `ci/watching-runs.md`，2026-09-30 实拉）

1. **终态用不同退出码区分，超时携带诊断载荷**：GREEN=0 / FAILING=15 / TIMEOUT=16 —— 成功、失败、超时是可区分信号而非笼统「未完成」；TIMEOUT 须附带最后聚合 + 待处理计数诊断载荷。判据：有等待/轮询的环节，失败与超时必须分码返回、超时码带诊断上下文。
2. **失败/不确定状态绝不自动触发二次变更（幂等护栏）**：不确定态禁止自动重试/二次写入，否则放大副作用；恢复须是显式人工/批准动作。判据：不确定态默认不自愈，恢复动作显式且可审计。
3. **轮询分批拉取 + 超额缓存续拉**：每轮最多读 32 条缺失记录，超额保持 pending 从缓存 resume，不一次性拉全量压垮下游。判据：长列表轮询设每轮上限，超出走增量续拉。

## 读侧先行的灰度升级律：旧版读侧会把引用当正文返给客户端，且不报错（来源：docs.n8n.io/hosting/scaling/queue-mode/，2026-09-28 r210-B 独立实拉）

## 超时不是一个数：默认值随触发类型分档、可调上限随套餐分档，且超时后只保留「已成功步骤」的日志（来源：pipedream.com/docs/workflows/limits 2026-09-29 r296-C 独立 curl 取 .md 原文核验；与 §2.41.0 容量上限二分 互补——那条管"能不能提升"，本条管"同一平台里超时有几套默认值"）

- 判据：① **同步入口与定时入口的超时预算本就不同**——HTTP/Email 是有人（或有系统）在等响应，默认 30 秒；Cron 没人等，默认 60 秒；把定时任务的预算套到 webhook 上，或者反过来，都会拿到不该有的超时；排查超时先确认**这个工作流的触发类型决定了它拿的是哪一套默认值**；② **"默认值"与"可调上限"是两个参数**——默认值能改，但天花板由套餐决定；用户说"我已经调到最大了还是超时"，要先问是哪个套餐，因为"最大"对免费档是 5 分钟、对付费档是 12.5 分钟；③ **超时不等于日志全丢，但丢的恰好是最需要的那一块**：已成功 cell 的日志会被附到事件上，而**正在跑的那一步的中间态拿不到**——所以超时类故障能确认"跑到哪一步"，不能确认"那一步内部卡在哪"；需要后者就得自己写中间检查点（与 §每一步都落检查点 同向）。
- 提升层：工具/工作流。触发词：超时默认值、30s vs 60s、触发类型决定超时、套餐决定超时上限、超时后部分日志、/tmp 2GB 不可提升。

## 事件流的「实时」与「历史」是两个集合：SSE live-only 不回放、恢复须 gte 补拉并按 id 去重、补齐字段不得用 null 覆盖；会话状态含 rescheduling/terminated 两态，不能一律读成卡住或失败（来源：docs.bigmodel.cn `cn/managed-agents/{events,session-operations}.md` 15,944B / 5,798B，2026-10-04 r409B 独立 curl 取 `.md` 原文实拉；与 §落盘后转发的缓冲层前提是单写者 / §判死前先回查真实执行状态 互补——那两条管"转发层并发"与"判死要验证"，本条管"断线后怎么把两个集合拼回一个真相"与"中间状态的语义"）
- **原文**：`live-only：流只转发连接建立后的实时事件，不回放历史`；`断线后先建立新的 SSE 连接并缓存新事件，再从最后一个非空 processed_at 开始补拉历史。使用 gte 而不是 gt，避免漏掉时间戳相同的事件；重复事件按 id 去重`；`如果响应的 next_page 非空……同一 id 只处理一次，但后续补齐的 processed_at 等字段仍要合并，不能用 null 覆盖已有值`；`建立 HTTP 连接不等于服务端订阅已经完成，单次补拉仍可能遇到极短的注册窗口`；`processed_at 在事件被平台处理时写入，不保证唯一`；`event_start 与 event_delta 是实时预览帧，没有自身的 id / processed_at，也不会写入事件历史`；会话状态表含 `rescheduling（平台正在重新调度会话的沙箱（恢复或迁移），随后自动回到执行）` 与 `terminated（会话已终止，不再接受交互（例如所引用的 Environment 被归档后触发的准入终止））`。
- **判据**：① **实时流不是历史的超集也不是子集而是另一条通道**：预览帧只在实时流出现且不落历史，结束状态只在历史/SSE 的持久化事件里 ⇒ 「我在流里看到了」与「我在历史里查得到」不能互相替代，验收要指明依据哪一侧。② **恢复补拉用 gte 不用 gt**：时间戳不唯一，`gt` 会把同一时刻的兄弟事件整批漏掉；去重键是 id 不是时间戳。③ **合并是字段级合并而非覆盖**：后补到的记录里 `processed_at` 可能为 null，直接覆盖会抹掉已有值 ⇒ 补历史的第一原则是"只填空、不改写"。④ **连接建立 ≠ 订阅完成**：存在注册窗口，恢复中的一轮必须继续用历史接口核对直到看到结束事件，单次补拉不足以判定本轮结束。⑤ **`rescheduling` 是"还在工作"**：重新调度沙箱随后自动回到执行，把它当卡死会触发错误的重启/判死；`terminated` 常常是**上游资源被归档的连带结果**（不是本会话出错），根因要往引用链上找。⑥ `processed_at` 不唯一意味着**不能拿它当游标主键**，游标必须是 id + 时间戳组合。
- 提升层：工具/工作流。触发词：SSE live-only、断线恢复 gte、按 id 去重、补齐不得 null 覆盖、连接建立不等于订阅完成、预览帧不落历史、processed_at 不唯一、rescheduling、terminated 由上游归档触发。

## r350B · 保序的唯一手段是并发=1；限速窗口与并发是两个独立旋钮（来源：pipedream.com/docs/workflows/building-workflows/settings/concurrency-and-throttling，2026-10-02 r350B 实拉 441,983B）

- **★不限并发 = 不保证按接收顺序处理**；要保序必须把并发限到单个 worker，未处理事件进队列按序执行。判据：**"顺序正确"是并发控制的结果，不是队列的赠品**——进了队列不等于保序。
- **★限速是固定窗口（fixed window）不是滑动窗口**：设为 5 秒 1 次，意思是每个固定 5 秒时间盒内最多触发一次。判据：**固定窗口在边界会突发（盒尾+盒头连发 2 次）**，压测与容量估算要按最坏突发算，不是按平均速率。
- **★并发与限速解决不同问题**：并发防竞态与保序，限速防上游 API 限流。判据：**被上游 429 时应调限速，被竞态咬到时应调并发**，调错旋钮问题不消失。

## r350C · 限流是"多组独立预算"，不是单一 RPM：先定位是哪一类预算、被拒发生在哪一层（来源：docs.openclaw.ai/gateway/security/rate-limiting，2026-10-02 r350C 实拉 248,732B）

- **★Gateway 同时执行多组互相独立的限流**：握手并发预算（concurrent handshake budget）**既不是每分钟请求数上限，也不是已认证客户端上限**；握手超时、pre-auth 帧大小与队列上限、origin 校验、失败认证限制各自独立生效。判据：**"被限流了"必须先翻译成"哪一类预算被打满"**，否则调错旋钮（加大 QPS 配额救不了握手并发）。
- **★超预算返 503 + `Too many unauthenticated sockets`，且不带 Retry-After**。判据：**没有 Retry-After 时客户端不能依赖标准退避协议**，必须自带抖动重连策略（文档建议错开重连突发，让在途握手先完成）。
- **★代理形态且无有效归属的请求在"获取槽位之前"就被拒**，不会回落到共享代理 IP 预算。判据：**被拒发生的位置（取槽前 / 取槽后）决定它算哪一类失败**，也会影响日志里看不看得见。
- **★限流键的选择本身是安全属性**：计数按凭据类别分域（共享 token / 设备 token / 节点配对 / 重审批 / bootstrap token / watchOS challenge 各自独立），一个面被打洪不影响另一个；来自 loopback 的失败按**规范化页面 origin**（如 `browser-origin:https://evil.example`）分桶而非共享 IP，非 loopback 才按客户端 IP。判据：**loopback 不能当单一信任主体**，否则一个页面能打满所有本地来源的额度。
- 提升层：工具 / 工作流。

## r350C · 重试的粒度是"每个 HTTP 请求"，不是"每个多步流程"；且不同失败类别各有独立预算（来源：docs.openclaw.ai/concepts/retry，2026-10-02 r350C 实拉 233,233B）

- **★Per-request 而非 per-flow**：按 HTTP 请求重试，且**只重试当前步以保序**。判据：**重试粒度选错会同时破坏顺序与幂等**——整流重试会重跑已成功的副作用，逐步重试不会。
- **★预算按失败类别分域**：限流最多 10 次总尝试；其他瞬时失败是 90 秒窗口内 8 次重试；整个 run 的重试总数有上界。判据：**"重试 8 次"不是全局常量**，先给失败分类才知道它有多少次机会。
- **★provider pacing 可以压过本地退避上限**：`retry-after` / `retry-after-ms` / "Please try again in …" 提示设的是**最小等待**，即使超过本地 30 秒退避上限也以它为准；退避从约 1 秒起指数增长并加抖动。判据：**服务端给的时间是下限不是建议**。
- **★不进瞬时重试预算的类别**：billing 失败、认证错误、供应商拒绝（refusal）都不使用这套预算；**空错误体不会让一个确定性 HTTP 客户端错误变成可重试**。判据：**4xx 是终态分类，不能因为响应体为空就升级成重试**。
- **★已恢复的尝试不留持久错误，只有终态失败保留一条错误**。判据：**日志里看不到错误 ≠ 没发生过重试**；排障要单独看重试计数与等待指示，不能只看错误条数。
- 提升层：工具 / 工作流。

## 故障分类按「文本像不像」而不是状态码：跨厂商没有统一协议语义，周期用量窗口与瞬时限流同桶会让冷却时长失去意义（来源：docs.openclaw.ai `concepts/model-failover.md` 39,408B，2026-10-04 r413B 独立 curl 取 `.md` 原文实拉；与 §fallback 两种相反语义 / §循环上限计量 互补——那两条管"备用在哪个阶段顶上""上限以什么为单位"，本条管"什么叫一次限流、冷却到什么时候为止"）
- **原文**：「That rate-limit bucket is **broader than plain 429**: it also includes provider messages such as `Too many concurrent requests`, `ThrottlingException`, `concurrency limit reached`, `workers_ai ... quota limit exceeded`, `throttled`, `resource exhausted`, and **periodic usage-window limits** such as `weekly limit reached` or `monthly limit exhausted`.」「A timeout that **looks like** rate limiting counts as such a failure.」「Thrown exhaustion summaries include structured per-attempt details and the **soonest cooldown expiry** when one is known.」「A terminal credential failure cools down **the exact selected profile** before model fallback.」「Transcript, format, context, pre-provider timeout, and ambient CLI failures **without a selected profile do not change shared profile health**.」
- **判据**：① **分类规则必须写成文本枚举而非状态码匹配**——同一类处置（冷却 + 换下一个）由"消息像不像"触发；跨厂商没有统一状态语义，只认 429 会把大半真实限流漏成普通错误。⇒ 排障时"为什么它没走降级"的第一查点是**匹配表是否覆盖该厂商的措辞**，不是网络/凭据。② **瞬时与周期窗口不能共用同一个冷却值**——`429` 的恢复单位是秒，`weekly limit reached` 的恢复单位是天；两者进同一个桶 ⇒ 冷却值无论取哪个都是错的。⇒ 分类桶必须携带**恢复量级**，或者干脆把周期窗口单列；否则重试风暴（短冷却打在周限额上）与假死（长冷却打在瞬时抖动上）二选一。③ **耗尽报告的价值在"最早可重试时刻"而不是"失败原因列表"**——终态失败要给出 soonest cooldown expiry；只列每次失败原因，运维拿到的是"为什么不行"而拿不到"什么时候再试"。④ **归因必须有门槛：没有选定目标的失败不该记到任何目标头上**——发生在选定之前的失败（pre-provider timeout / 环境级 / 无 profile 的 CLI 失败）不改变共享健康度；把所有失败都用来惩罚候选，会让一次环境问题把全部凭据依次冷却掉。⑤ **归因粒度要精确到"被选中的那一个"**——终端凭据失败只冷却那个具体 profile，不是整个 provider；粗粒度惩罚会把"一个 key 坏了"放大成"一家厂商不可用"。
- 提升层：工具 / 工作流 / 可复用 Skill。触发词：限流桶文本枚举、周期用量窗口、soonest cooldown expiry、冷却量级、归因门槛、精确到被选中的凭据。

## 取消不是回滚、超时降级不得串联更多超时、失败类别决定重试资格：清理预算与操作预算必须分离，且「信号被拒」须靠进程普查证明才算清理完成（来源：docs.openclaw.ai `concepts/compaction.md` 20,148B + `ci/checkout.md` 21,314B，2026-10-04 r416A 独立 curl 取 `.md` 原文实拉；与 §fallback 两种相反语义 / §限流桶文本枚举 互补——那两条管"备用在哪个阶段顶上""什么叫一次限流"，本条管"取消/超时之后现场是什么状态、什么才配重试"）
- **原文**：「Cancellation is not rollback: a compaction that already completed remains in the transcript and is still counted, without sending a late reply.」「The built-in OpenClaw runtime does not start further recovery hooks, maintenance, transcript truncation, or retries after cancellation.」「OpenClaw commits that compaction without a summary instead of ending the turn … A timed-out summary does not move to the model fallback chain, because each extra model could add another full timeout window to the wait.」「Such a replacement must strictly reduce history; unchanged or larger results are rejected.」「Cleanup has a ten-second allowance, separate from the operation deadline.」「A denied group signal can be accepted only when that census proves there are no live members; live or unknown state still fails closed.」「Only ordinary Git failure or `FetchTimeout` permits retry after verified cleanup.」「After a failed or terminated fetch and verified process-tree extinction, the owner removes newly created locks in physical Git metadata; pre-existing locks and linked metadata remain untouched.」「Once cleanup succeeds, cancellation takes precedence over timeout or ordinary Git failure.」
- **判据**：① **取消只保证"不再向前"，不保证"回到之前"**：已完成的副作用（已写入的压缩条目）留在转录里并参与计数，只是不补发迟到的回复；取消后不再启动任何后续 recovery / 维护 / 截断 / 重试 ⇒ 把取消当回滚，会在"看起来干净"的现场上继续跑，而实际已经留下了一半的变更。② **超时降级不得串联更多超时**：摘要超时就提交一个"无摘要"的压缩让回合继续，刻意**不**转模型 fallback 链——每多一个候选模型就多一个完整超时窗口 ⇒ 用"换一个更慢的东西再试一次"来救超时，本质是把 N 倍等待塞给用户；降级路径必须显式声明它不再引入新的等待源。③ **优化类操作要有单调性校验**：压缩结果必须严格小于原历史，等于或更大则拒绝 ⇒ 没有单调性校验的"优化"可能只是复制甚至放大，而且不会报错。④ **失败类别决定重试资格，不是所有失败都该重试**：只有「普通失败 / 取数超时」在**进程树抽干经验证之后**才放行重试，取消与所有权失败是终态 ⇒ 不分类的重试会把终态失败也拖进重试风暴，还会掩盖真正的终态原因。⑤ **清理预算与操作预算必须分离**：清理有独立的固定额度（10 秒），不吃操作 deadline ⇒ 共用一份预算时，要么收尾没时间做完留下脏状态，要么主操作被清理挤掉。⑥ **"发了终止信号"不等于"它停了"**：信号被拒时须做进程普查证明无存活成员才接受，live 或 unknown 一律 fail closed ⇒ 这是清理假象的头号来源；同理"等 leader 退出"不够，要观察整个进程组消失。⑦ **清理只动自己新建的东西**：锁回收只移除本次新创建的锁，既有锁与链接元数据保持不动 ⇒ 清理必须区分所有权，否则会顺手破坏别人的状态。⑧ **取消优先于超时与普通失败**：清理成功后若同时存在取消，归类为取消 ⇒ 终态归类要有优先级，否则同一现场会被记成三种不同的失败。
- 提升层：工作流 / 诊断 / 可复用 Skill。触发词：取消不是回滚、超时降级不串联超时、单调性校验、失败类别决定重试资格、清理预算独立、进程普查 fail closed、只清理自己新建的、取消优先于超时。

## §下沉 2026-10-08 · 多进程共享事件日志（原 wb-debug-loop 正文，因 500 行预算下沉）
## 为「不丢数据」而加的持久化兜底层，在多进程共享时会自己变成丢数据的故障源；显式配置会取消平台的自动保护并把唯一性责任转移给编排方（来源：docs.n8n.io `administer/observe-and-log/stream-logs-to-external-systems.md` 26,482B，2026-10-06 r427-B 独立 curl 取 `.md` 原文实拉逐串命中；真路径经 docs.n8n.io/llms.txt 287,049B 定位——`administer/observe-and-log.md` 959B 与 RBAC 父页 2,500B 均为导航桩已判壳）
- **实证**：官方原文「n8n persists each emitted event to a local log file before forwarding it to streaming destinations. The file survives restarts and lets n8n re-emit events that weren't yet delivered.」；警告块原文「If multiple n8n processes share one writable volume … they must not write to the same event log file. **Concurrent appends from multiple processes can interleave or corrupt the file, leading to recovery failures and lost events.**」；责任转移原文「n8n uses the configured path verbatim and **doesn't append a process-type suffix**, so **your orchestrator owns uniqueness across processes**.」
- **判据**：① **兜底层要单独过一遍"N 个实例并发"这一问**——先落盘再转发本是为了重启后能重发未投递事件，但多进程共享同一可写卷时并发追加会交错甚至损坏文件，结果是恢复失败与事件丢失 ⇒ 遇到"明明加了可靠层却仍在丢数据"，优先查这个可靠层自身在并发下的行为；单实例下成立的可靠性设计不是多实例下成立的证据。② **显式配置会取消平台的自动保护，且责任被显式转移**——默认路径按进程类型自动加 `-worker` / `-webhook-processor` 后缀，一旦显式配置 `N8N_EVENTBUS_LOGWRITER_LOGFULLPATH`，后缀不再自动加，唯一性归编排方 ⇒ 看到"平台不再自动做 X"要立刻追问"那现在谁做"；文档里明写 "your orchestrator owns uniqueness" 就是在声明责任转移，接管默认值等于接管它背后那件事。③ **兜底层的失败模式要有独立预算，且历史遗留不自动清理**——`N8N_EVENTBUS_LOGWRITER_MAXTOTALMESSAGESPERFILE` 限制恢复时从单个文件解析的行数（"so a corrupted file can't exhaust process memory"）；已存在的旧共享文件需人工隔离，平台不自动删 ⇒ 给兜底层设恢复/解析上界，并把迁移期遗留文件列为显式人工动作，别指望升级顺带清掉。
- 提升层：工作流 / 可观测性。触发词：多进程共享日志、并发追加损坏、兜底层自伤、唯一性归编排方、显式配置取消自动后缀、恢复解析行数上界、先落盘再转发。

### §下沉·wb-debug-loop·r439·探针要能一次撤干净seam太浅本身就是结论同来源di
## 探针要能一次撤干净，seam 太浅本身就是结论（同来源 `diagnosing-bugs` 技能正文，与 §诊断装置自身的可信度、§接线腐烂 互补——那两条管"检查器有没有遭遇"与"装了为什不生效"，本条管"**临时探针的回收**"与"**回归测试挂点选错时该怎么报告**"）

- **原文事实**：调试日志只允许打在**能区分假设的边界**上，绝不"log everything and grep"；每条调试日志带**唯一前缀**（如 `[DEBUG-a4f2]`），收尾一条 grep 全清；原文判词 "**one breakpoint beats ten log statements**"。性能回归不用日志查——**先建基线测量，再二分**。回归测试**在修复之前写，但前提是存在正确的 seam**（该测试在真实调用点上复现该 bug 形态）；**seam 太浅的测试给的是虚假信心**；**若根本不存在正确 seam，那本身就是发现**——代码库架构在阻止这个 bug 被锁定，要作为结论报出来。收尾六条清单：原 repro 不再复现（重跑第一轮循环）、回归测试通过、按前缀 grep 清掉全部 `[DEBUG-...]`、一次性原型删除或移到标记位置、**把被证实正确的那条假设写进 commit / PR 说明**。
- **判据**：
  1. **每条临时探针都要有可回收的标识**。判据：**写第一行调试代码前先定前缀，收尾时用同一个前缀 grep 并确认命中 0**；没有回收手段的探针不该落地（与 §观测是被动旁路 分工：那条管测量挂在哪条时间线，本条管临时测量怎么撤）。
  2. **"测不到"要分两种并分别报告**：seam 太浅 → **给的是假信心，必须标注**；没有 seam → **是架构结论，不是失败**。判据：**写回归测试前先回答"这个测试能不能在真实调用链上复现该形态"，答不出就别写，把答案当发现报**。
  3. **把"哪条假设是对的"写进提交信息**。判据：**下一次排障的人应该能从 commit 里读到这次的因果，而不是从代码里反推**。
- 提升层级：工作流（探针生命周期）+ 可复用 Skill（结论的写法）。
- 触发词：唯一前缀、[DEBUG-a4f2]、一次 grep 清理、一个断点胜十行日志、基线再二分、seam 太浅、没有 seam 是发现、假设写进 commit。

### 下沉·wb-debug-loop·已处理的失败是独立可见状态Warning态不是消失了重试有固定序列且超限会熔断关
## 已处理的失败是「独立可见状态」（Warning 态），不是消失了；重试有固定序列且超限会熔断关停调度（来源：help.make.com《Introduction to errors and warnings》+《Exponential backoff》2026-09-29 r337-Q-A 实拉核验；与 §重试掩盖 互补——那条管"别用重试糊过去"，本条管"重试本身有几条纪律"）

### 下沉·wb-debug-loop·自述成功不构成幂等证据重复执行中九成agent仍自报成功引量化结论前先确认分子分
## 自述成功不构成幂等证据：重复执行中九成 agent 仍自报成功；引量化结论前先确认分子分母（来源：arxiv.org/abs/2609.29095，2026-09-30 r323B 独立实拉 44,254B）
- 原文：「the same frontier models duplicate in **56% and 74%** of episodes」（在途未返回 / 传输重复两种情形）；「lowers the duplicate rate from **28% to 4%**」（契约化后）；「agents **reported success in 90% of the episodes in which they had duplicated an effect**」；「the contract explains **81%**」= 契约能解释的**方差占比**，不是重复率（**口径纠偏**：不得把 81% 引成“81% 的请求会重复”）。
- 判据：① **“恢复后重跑成功”与“只执行过一次”是两件事**：重复执行里九成自带成功自述，因此验收幂等只能靠外部痕迹（执行痕迹计数、副作用唯一键、服务端去重日志），**不能靠 agent 汇报**——自述成功是“我觉得成了”，不是“只发生了一次”；② **引量化结论前先确认分子分母**：同一篇里 56/74%（重复率）、28%→4%（干预前后）、81%（方差解释度）属于三个不同量，混引会造出不存在的事实；③ 把“待补”复核成“已核”时，条目里要**写下核到的原句**（不是只写“已复核”），否则下一个人仍无法判断。
- 提升层：工具/工作流。触发词：自述成功、幂等证据、重复率、方差解释度、口径纠偏、痕迹计数。

### 下沉·异步入口的丢失窗回执与落库之间那一段已应答的请求不会有人重试有重建路径的子系统陈旧备份严格劣于空
## 异步入口的丢失窗 =「回执与落库之间」那一段：已应答的请求不会有人重试；有重建路径的子系统，陈旧备份严格劣于空库（来源：www.activepieces.com/docs/install/guarantees/disaster-recovery.md，2026-09-30 r325A 独立 curl 实拉 7,611B 逐串命中；经 Qoder r357-Q-A 提名）
- 原文：①「Activepieces returns `200` with an `x-webhook-id` header after the job is enqueued to Redis, **before** any Postgres record exists. If Redis loses its dataset in that window, those requests vanish without a trace, and the sender — having received a `200` — **will not retry**. Your async-webhook RPO **is** your Redis persistence window」；同步路径「the run is recorded in Postgres **before** execution」不受此窗影响；②「A **stale** Redis backup is **strictly worse** than an empty Redis plus the refill on restart」；③ runbook「Restore or replace Redis (an **empty** Redis is fine) → Restart the app containers. The refill machinery rebuilds schedules, renewals, and paused-run timers from Postgres → filter runs still in `QUEUED`/`RUNNING` … resumes from the last checkpoint and **never re-runs completed steps**」；④ 三 store 分册：Postgres=flows/runs/schedules/waitpoints/connections（System of record）、S3=执行历史（SOR）、Redis=除队列本身外全部可由 Postgres 重建；⑤「Recovery targets are stated as **formulas**…they are properties of *your* Postgres/Redis/S3 setup, not of Activepieces」；⑥ 队列重试「starts at 8 minutes — **longer than a typical failover**」；⑦「Database connection pools are **not guaranteed to re-establish cleanly** through a failover's DNS flip; a restart is cheap and **always correct**」。
- 判据：① **「已返回 200」不等于「已持久化」**——凡回执时点与落库时点不一致的入口（先入队、后异步落库），其暴露窗等于队列的持久化窗，且这扇窗内的丢失**不可自愈**，因为发送方拿到成功确认后不会重试；设计异步接收链路必须先回答「回执那一刻数据落在哪一层」，并把这个窗**单独**计量成 RPO，不能用整体可用性数字代替；② **RPO/RTO 是推导量不是产品属性**——官方把恢复目标写成公式，理由是自托管下它取决于你自己的存储档位；引用任何一个 RPO 数字前先问「它背后是哪个 store 的哪档持久化」；③ **有权威源 + 自动重建器的子系统不该备份**：陈旧副本会把已完成进度倒退回过去，比空副本更糟——空 + 回填是幂等收敛，旧副本是状态回退；判断「要不要备份」的标准是**有没有回填通道**，不是「数据重不重要」；④ **恢复程序必须自带人工收尾动作**：清空 → 回填 → 按最后检查点批量重试滞留态，且明确不重跑已完成步 ⇒ 恢复脚本自身必须幂等并能按检查点续；⑤ **恢复后重启优于「优雅重连」**——连接池不保证跨 DNS 切换自愈，宁可付一次便宜且永远正确的重启；⑥ **重试首延要大于典型故障切换时长**，否则所有重试都落在故障窗内，白烧预算还放大下游压力。
- 提升层：工作流/工具。触发词：异步暴露窗、回执先于落库、x-webhook-id、RPO=队列持久化窗、陈旧备份劣于空库、重建优先于备份、批量重试滞留态、DNS flip 后重启。


### 下沉·慢的外部依赖不得阻塞冷启动连接与刷新各给一个独立上界超时只降级不阻塞启动期对未就绪依赖fail-
## 慢的外部依赖不得阻塞冷启动：连接与刷新各给一个独立上界，超时只降级不阻塞；启动期对未就绪依赖 fail-closed，刷新期旧值继续供给（来源：docs.n8n.io `/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/external-secrets.md` 4,588B，2026-09-30 r325B 独立 curl 实拉逐串命中，**通道更正**：Qoder 给的 `docs.n8n.io/use-environment-variables/external-secrets.md` 实际返回「Page Not Found」壳，真实前缀须经 `docs.n8n.io/llms.txt`(286,271B) 定位；经 Qoder r358-Q-B 提名）
- 原文：「`N8N_EXTERNAL_SECRETS_CONNECT_TIMEOUT`…`20`…If the vault doesn't answer in time, n8n **marks it as errored**, retries the connection in the background with **increasing delays**, and **startup continues without its secrets**.」「`N8N_EXTERNAL_SECRETS_REFRESH_TIMEOUT`…`20`…If the fetch takes longer, n8n **stops waiting** and the fetch **keeps running in the background**. When it completes, n8n stores the secrets. **At startup, workflows that use secrets from that vault fail until the first fetch completes. On an update interval, the previously fetched secrets stay available.**」「For HashiCorp Vault and Infisical, n8n also **cancels each single HTTP request after the larger of the two timeouts**.」（均 Available from n8n 2.41.0）
- 判据：① **冷启动不能被最慢的那个依赖绑架**——对不可达/慢的外部凭据源设**两个独立上界**（connect / refresh），到点即标记 errored 或停止等待，主流程继续；「配了但拉不到」不应等于「系统起不来」；② **降级方向按阶段分叉，不是一刀切**：启动期没有旧值可用 ⇒ **fail-closed 直到首次拉取成功**（依赖它的执行直接失败，不拿空值蒙混）；周期性刷新已有旧值 ⇒ **旧值继续供给不中断**（"取新的别把已有的掐了"）；同一个超时在两个阶段给出相反动作，是设计不是矛盾；③ **后台续跑 + 递增延时重试**是让"慢依赖"与"主流程"解耦的标准形态：等待被截断，但工作不丢弃，成功即入库；④ **单个 HTTP 请求的上界要由两个超时中的较大者兜底**，否则会出现"整体超时已过、单次请求还在挂着"的悬挂连接。
- 提升层：工具/架构。触发词：冷启动不阻塞、connect/refresh 双超时、启动期 fail-closed、刷新期旧值继续、后台续跑、递增延时重连、单次请求上界。


### 下沉·并发闸门有作用域已开限流全链路受控且队列项不可重试来源n8ncontrol-concurrenc
## 并发闸门有作用域：「已开限流」≠「全链路受控」，且队列项不可重试（来源：n8n control-concurrency 本机实拉，r326B）
- **原文**：①「Concurrency control applies **only to production executions**: those started from a webhook or trigger node. It doesn't apply to any other kinds, such as **manual executions, sub-workflow executions, error executions, or started from CLI**」；②「**You can't retry queued executions.** Cancelling or deleting a queued execution also removes it from the queue」；③「On instance startup, n8n **resumes queued executions up to the concurrency limit** and re-enqueues the rest」。
- **判据**：① **设限后必须逐执行形态验证是否真被管住**——守压力的闸门恰恰不管「兜底用的错误工作流」与「被复用的子工作流」这两条最容易失控的路径；「我开了限流」只证明主路径被管。② 排队 ≠ 可重试：入队即失去重试权 ⇒ 队列不是「稍后重试的备份」，重试责任在调用方。③ 重启策略=「按上限恢复 + 其余重新排队」⇒ 重启后的在途量由闸门决定，不是全量洪峰。
- **提升层**：工作流/工具。触发词：限流作用域、only production executions、manual/子流程/错误流程绕过、队列不可重试、重启按上限恢复。

- **按「调用方身份」计数的闸门必须自证生效：反向代理会让它整体失效（来源：Flowise rate-limit 本机实拉，r326B）**：本章已下沉 `references/knowledge-base.md`（r326B）。
