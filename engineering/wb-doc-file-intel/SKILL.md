# 文档/文件智能路由（认类型 → 选处理器 → 提取/分析/转换）

## 核心判断
来了一个文件 / 一批文件，先**认类型**再决定怎么处理；本技能只做**路由与编排**，各类型的真本事下沉到已有技能，不重造——契合 AGENTS §0.7「功能相近合并、不重复创建」与 `personal-ai-employees` 的"只取独特点"。

## 类型识别（扩展名 + 内容嗅探双保险）
扩展名不可信（可能错标 / 无扩展名）时，用 magic bytes / 前几行内容嗅探兜底。

| 类型 | 路由落点（现有技能 / MCP） |
|---|---|
| PDF | `pdf` / `pdfkit-py`（读、抽取、转） |
| DOCX / WPS文字 | `tencent-docx`（生成/美化）、`tencent-local-office-edit`（就地编辑） |
| XLSX / XLS / CSV / TSV | `tencent-docs-sheetagent`（编辑分析）、`tencent-docs-sheet-generation`（从零生成） |
| PPTX | `tencent-pptx` |
| TXT / JSON / 代码 | Read 直接读；JSON 用结构化解析，不靠肉眼 |
| 网页 URL | `web-scrape`（干净抽取）；需登录 / 反爬 → `browser-automation` |
| 云文档（docs.qq.com 等） | `library` / `tencent-docs` / `tencent-saas-docs` |
| 图片 / 音视频里的信息 | `wb-media-forensics`（取证抽帧读图） |

## 处理决策（先问要什么，再选动作）
1. **提取**（只要内容）→ 优先结构化抽取：表格 / 字段 / 段落 / 元数据，保留来源与页码 / 行列定位。
2. **分析**（内容 + 结论）→ 抽取后做分析，区分事实 / 假设 / 不确定（见 AGENTS §6 三层标注）。
3. **转换**（A 格式 → B）→ 路由到对应生成技能，不手写转换器。
4. **整理 / 生成**（多源 → 新产物）→ 先抽取各源结构化信息，再去重 / 合并，最后生成。

## 多文件规则
- **去重**：同源多版本只留最新 / 最全；按内容哈希或关键字段判重，不盲目全并。
- **合并**：建立文件间对应关系（如"同一主题的 v1/v2"），合并时标注来源。
- **不丢上下文**：保留每个字段出自哪个文件、哪页 / 哪行，便于回查。

## 与现有技能分工
- 本技能**不实现**任何抽取 / 转换，只认类型 + 派活 + 编排多文件 + 完整性兜底。
- 具体能力 100% 复用上表落点；无对应落点才考虑新增（并先走 `wb-skill-authoring` 评估，确认非重复再建）。
- 与 `library`（云文档路由）分工：本技能管**本地 / 任意来源文件**的类型识别与编排；`library` 管云端资料库的存取与协作。

## 输出前检查（完整性）
- 文件能打开、结构完整、关键内容无缺失、格式可用（表格可编辑 / 文档可打开）。
- 抽取结果核对：关键字段 / 表格是否齐全，不把"读到了一部分"当"读全了"。

## 失败处理
- 文件损坏 / 不可读 → 明确报告"哪份、为什么"，**不猜测内容、不编造数据**。
- 类型识别失败 → 先内容嗅探，仍不行就问用户或报"不确定"，不硬套处理器。
- 多文件冲突 → 在交付物里并列呈现差异，不擅自选边；标注"以 X 为准"须说明理由。

## 识别顺序第三层：结构化声明 > 内容嗅探 > 名称启发式（来源：Pipedream `docs/connect/components/files.md` 的 `format: "file-ref"` 与 `stash: required|optional`，2026-09-27 r198-A 实拉）
- **★类型 / 能力的判断优先级固定为三层**：①结构化声明字段（元数据里明确写出的 type / format / 能力标记）②内容嗅探（magic bytes、前几行）③名称启发式（文件名、字段名里出现的关键字）。**只有前一层拿不到才下降到下一层**。
- **★名称启发式是末位手段且必须显式标注为"猜测"**：它命中率低且会双向漏（该命中没命中 = 漏处理；不该命中命中了 = 误处理）。判据：**靠名字认类型，等于把识别正确性押在对方命名习惯上**。
- **★声明缺失不等于能力缺失**：元数据字段可能没写全，此时走下一层，不要把"没声明"当成"没有该能力"直接跳过。判据：**漏声明和真的不支持是两回事，混为一谈会静默丢掉可用能力**。
- 与 §类型识别（扩展名 + 内容嗅探双保险）的分工：那条管"文件本体是什么"；本条管"某个字段 / 能力承担什么角色"，并把三层的先后顺序钉死。
## r702C 下沉：结构化文本先正则、只对低置信项上 LLM（来源：GitHub `affaan-m/ECC`·`skills/regex-vs-llm-structured-text/SKILL.md` 6,749B，2026-11-08 实拉）

- **先判格式是否稳定重复**：>90% 的段落遵循同一模式（题目、表单、发票、表格）→ 先写正则；正则覆盖 ≥95% 就**到此为止，不上 LLM**；只有 <95% 时才引入 LLM，且**只校验低置信项**，不复跑全量。
- **四段管线**：正则解析（抽结构）→ 清洗（去页码/标记/artifact 噪声）→ 置信分（字段级打分，≥0.95 直出，<0.95 才送校验）→ LLM 校验只修边角。
- **必用 LLM 的场景要在判据里写清**：自由格式、版式高度可变、字段语义需要推理——不是"看着复杂就上 LLM"。
- 判据：对结构化文本全量调 LLM＝用 20 倍成本换 1–2 个点准确率，**而且不可复现**（同一输入两次结果不同）；正则的确定性本身就是可用性。

## r705B 下沉：文件处理按内容哈希缓存——路径无关、内容变更自动失效（来源：GitHub `affaan-m/ECC`·`skills/content-hash-cache-pattern/SKILL.md` 5,732B，2026-11-08 实拉）

- **缓存键用内容，不用路径**：`SHA-256(文件内容)` 做 key（大文件按 64KB 分块流式算）。**文件改名/移动后仍命中**；内容一变 key 就变，**自动失效**，不需要手工清理。
- **路径键的三个通病**：改名即失效、同内容不同路径重复算、内容变了却因 mtime 精度/复制保留时间而误命中。判据：**缓存要跟"内容"绑定，才配得上"结果只依赖内容"的纯函数**。
- **服务层分离**：`process(path) -> result` 保持纯函数；缓存读写放在外层 wrapper（查 key → 命中直接返回 → 未命中计算后写入）。**不要把缓存逻辑塞进业务函数**，否则以后想关缓存就得改业务代码。
- **必须能关**：提供 `--cache / --no-cache` 开关；调试与首次验证走 no-cache，确认结果正确后再开。
- **写入要原子**：先写临时文件再 `os.replace` 落位，避免半截缓存被下次当成有效结果读走；缓存目录按 key 前缀分桶，避免单目录几万文件。
- 判据：**缓存的价值 = 省下的重复计算 − 失效错误带来的返工**；无法保证"内容变了必失效"的缓存，是负资产。
