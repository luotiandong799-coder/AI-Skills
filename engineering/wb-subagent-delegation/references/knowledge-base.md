

## 并发去重从「选 leader」改为「共享队列 + 认领」：两机制失效形态不同；内层超时必须短于外层租约；必须一致的状态对分开落盘即失步窗口；放弃的正确语义是「状态不推进」（来源：docs.n8n.io/deploy/host-n8n/configure-n8n/durable-scheduler.md 30,546B，2026-10-01 r346C 独立 curl 实拉逐串命中）
- **原文**：①「In a multi-main setup, **only the leader fires schedules. If leadership changes at the wrong moment, timing can slip**.」「**Each run executes once across instances.** Every main instance shares the same queue and **claims runs** from it. Only one instance picks up each run, so the work spreads across your mains **instead of depending on a single leader**.」「If an instance claims a run but stops before finishing ... the **reaper** releases the run so another instance can pick it up.」；②「**Keep the timeout below `N8N_SCHEDULER_LEASE_DURATION`, so an abandoned poll can't still be running when another instance takes its run over.** n8n warns at startup when the timeout reaches the lease duration.」；③「n8n stores the cursor in the workflow's static data and **saves it separately from the execution the poll produced**. If the instance crashes between the two saves ... **the cursor and the execution fall out of step, and the workflow either skips items or processes them twice**.」；④「A poll that runs too long is **abandoned** ... n8n stops waiting for it and **records nothing: the cursor stays put**, so the next poll covers the same ground and no data goes missing.」；⑤「n8n scans every active workflow's published version for **duplicate or missing trigger node ids**. If it finds any ... it **turns off durable poll cursors, keeps poll triggers on the in-memory scheduler for the whole instance**, and logs an error naming the affected workflows.」。
- **判据**：① **"避免同一件事做两次"有两种机制，选错机制就换了一种失效形态**：**单点 leader** 的失效是**时序滑移与单点依赖**（领导权在错的时刻变更，该跑的时刻就漂了；leader 挂了全体停摆）；**共享队列 + 认领**的失效则是**租约与接管**（认领者崩溃后由 reaper 释放、他人接手，风险转移到"前任是否真的停了"）。⇒ 别把"有 leader"当成唯一解：要的是**每个工作单元只被执行一次**，达成方式可以是"只有一个执行者"，也可以是"多个执行者抢同一份带租约的工作"；后者的额外收益是负载自动分散，额外义务是必须有接管语义与租约边界。② **嵌套超时的次序是硬约束，不是调优建议**：内层（poll 超时）必须**短于**外层（租约时长），否则被放弃的那次仍在运行，而另一个实例已经接管了同一份工作——于是"放弃"与"接管"重叠，产生真正的并发双跑。⇒ 凡是"超时后交给别人"的设计，都要把**两层超时的大小关系**写成不变量，并在启动时校验（原文即启动告警）。只看单个超时数值是否"够长"，看不出这个错误。③ **必须保持一致的两个状态若分开落盘，中间就是失步窗口**：游标与它产生的执行分别保存，崩在两次保存之间则二者失步，后果是**跳过条目或重复处理**——注意这是**同一故障的两种相反表现**，取决于崩在哪一半。⇒ 判断一对状态是否需要原子更新，标准是**它们共同定义了"做到哪了"**；分开写就等于承认有一段时间内"做到哪了"没有正确答案。修法不是加重试，而是让二者落在同一个提交边界内（原文的 durable cursor 即此）。④ **放弃的正确语义是「状态不推进」，而不是「记录一次失败」**：超长轮询被放弃时系统**什么都不记录**，游标原地不动，下次重跑覆盖同一范围。⇒ 这是**放弃与失败的关键区别**：记录成失败会推进/污染状态机，而"当作没发生过"让下一轮天然重做且不会丢数据。设计可放弃的操作时，先定义它**不应该留下什么痕迹**。⑤ **预检失败时整体降级并点名受影响对象，而不是部分启用**：启动扫描发现重复/缺失 trigger id，就关闭持久游标、把整个实例的 poll 触发器退回内存调度，并**在日志里点名具体是哪些工作流**。⇒ 与"资格未知则保持启用"相反的一种正当处置——当**一致性前提**被破坏（而非能力不确定）时，退回已知的旧路径并**明确说出影响面**，比带着坏前提继续跑更安全；两条纪律的边界在于：不确定的是**能力**就保持并推迟终判，不确定的是**前提**就降级并报出影响面。
- **提升层**：工具/工作流/安全边界。触发词：leader 选举 vs 共享队列认领、claim 去重、reaper 释放接管、租约 lease duration、内层超时短于外层租约、游标与执行分开落盘、状态对失步窗口、放弃不推进状态、预检失败整体降级并点名。
