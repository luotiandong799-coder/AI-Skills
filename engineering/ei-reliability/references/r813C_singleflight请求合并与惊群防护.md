## 一、stampede 的成因与量级：过期瞬间所有请求同时回源

- **原文**（System Design In Depth《Cache concurrency control》WebFetch 200 全文逐字）："A popular bakery runs out of croissants. If every customer in the queue walks into the kitchen to bake their own, the kitchen collapses. That is a cache stampede. The fix is for one person to bake while everyone else waits a moment or takes yesterday's croissant. The subtler bug: a slow baker who started before the recipe changed can put an old-recipe batch on the shelf after the new one went out."
- **原文**（同上逐字）："**Mental model:** on a miss, make sure only one worker rebuilds each key, and make sure an old rebuild can never overwrite a newer value."
- **原文**（同上 worked example 逐字）："A catalogue key takes 200 ms to rebuild from the database and receives 10,000 reads per second across 100 app servers. With no protection, when it expires every request in the 200 ms window misses, which is about 2,000 concurrent identical DB queries." "**Per-process singleflight:** at most one load per server, so 100 concurrent loads. That is 20 times better, but still 100." "**Distributed rebuild lock** (`SET lock:key token NX PX 3000`): one load cluster-wide. The other callers either serve the stale value or poll briefly." "**Probabilistic early refresh (XFetch):** each reader refreshes early with a probability that rises as expiry approaches, weighted by rebuild cost. Typically one reader refreshes shortly before expiry, and nobody ever sees a miss."
- **俄文一手交叉**（vikulin-va.ru《Cache stampede в Go》WebSearch 逐字）："Cache stampede — параллельные запросы на истёкший ключ: каждый видит cache miss, все уходят в БД одновременно, DB получает N одинаковых тяжёлых запросов." "singleflight ... коллапсирует параллельные вызовы с одним ключом: первый идёт в БД, остальные получают тот же результат." "sync.Mutex / sync.Map для защиты Redis-кеша бесполезны: lock виден только внутри одного пода. Distributed lock через Redis SetNX — единственный способ защитить multi-instance деплой без сторонних зависимостей." 算例："Нагрузка 200 RPS и TTL 30 секунд — после рестарта Redis за первые 300ms БД получает ~60 идентичных тяжёлых запросов."
- **判据**：① 算例必须先报量级再选方案：200ms 重建 × 10,000 RPS ⇒ 约 2,000 并发相同查询；进程内 singleflight 降到每进程 1 次（100 台⇒100 次，改善 20× 但仍 100）；分布式锁才降到全集群 1 次。② 「本地 mutex 够了」是最常见误判——200 台服务用进程内合并仍有最多 200 个并发 DB 加载。③ stampede 的典型触发点是 Redis 重启 / FLUSHDB / 服务首次部署（hot key 同时冷），不是缓慢增长流量。

## 二、singleflight 的正确语义：不是缓存、不是限流、进程内有效

- **原文**（gerryyang.com《Singleflight:并发请求合并原理与实践》WebFetch 逐字）："singleflight 提供的是一种重复函数调用抑制机制：在高并发下，多个 goroutine 同时请求相同资源(同一个 key)时，把并发请求合并成一次执行，让其它调用方等待并共享结果，从而缓解『缓存击穿/惊群』。" "核心 API：Group 的 Do / DoChan / Forget。Do(key, fn)：同步阻塞。对同一个 key，第一个调用执行 fn，后续调用阻塞等待并共享结果。返回值里的 shared=true 表示『这一轮结果被多个调用方共享』,不代表缓存命中。"
- **原文**（同上逐字）："错误也会被『共享』：同一轮合并执行如果返回 error，等待者会一起收到这个 error。如果你的业务希望『失败后立刻允许重试』，可以在失败场景 Forget(key)，避免后续调用继续复用/等待同一轮失败结果。" "别把不可重入的副作用塞进 fn：singleflight 更适合『纯读』或『幂等』的昂贵操作(读 DB、请求第三方、生成可缓存结果)。像扣库存/发短信这种副作用，会因为『只执行一次』而改变语义。" "局限性：进程内有效 + key 高基数会占内存 —— singleflight 的合并只在单进程内生效；分布式场景要靠分布式锁/一致性哈希/集中缓存来做跨节点合并。"
- **原文**（StackOverflow q/73253115 WebSearch 逐字，Go 官方包注释）："// Do executes and returns the results of the given function, making // sure that only one execution is in-flight for a given key at a // time. If a duplicate comes in, the duplicate caller waits for the // original to complete and receives the same results. // The return value shared indicates whether v was given to multiple callers."
- **原文**（17golang.com WebSearch 逐字）："它不是缓存，也不是限流器，它做的事情很窄：把同一个 key 上同时发生的重复函数调用合并起来，让真正回源的调用只执行一次，其他请求等结果并共享。" "这个字段很适合打指标：如果 shared 比例突然升高，通常说明热点 key、缓存失效或者下游变慢正在出现。"
- **判据**：① shared=true 表示「结果被多个调用方共享」，**不等于缓存命中**——别把它混进缓存命中率指标；反过来它是热点/失效/下游变慢的告警信号。② singleflight 只合并「正在飞行中」的调用；一旦该轮完成，新请求仍会回源——它不是缓存、不设 TTL、不判新不新。③ 失败结果也被共享，须在错误分支 Forget(key) 让后续调用能立即重试，否则所有等待者一起吞同一轮失败。④ fn 只能放幂等纯读；扣库存/发短信这类副作用被合并会改变业务语义。⑤ 高基数 key 会占内存（每个 in-flight key 一条记录），须评估 key 空间。

## 三、陈旧写竞态（stale set）与租约：合并还不够，旧结果不能覆盖新结果

- **原文**（System Design In Depth WebFetch 200 逐字）："An old reader can load the database, race with an update-and-delete, then repopulate stale data. A refresh owner can crash, waiters can pile up, and a distributed lease can expire while work continues." "Facebook's memcache issues a lease token on a miss. A delete invalidates outstanding leases, so the late set of v1 is rejected. The same token also rate-limits rebuilds: memcache hands out at most one token per key every 10 seconds, and other clients briefly wait and retry."
- **原文**（同上「Technique comparison」表逐字，逐行）：Local singleflight — Stops stampede「Per process only」/ Stops stale set「No」/ Cost「Trivial」；Distributed lock with TTL —「Yes」/「No」/「Extra round trip. Stale lock holder」；Leases (memcache) —「Yes」/「Yes」/「Needs cache support」；Versioned compare-and-set —「No」/「Yes」/「Needs version from the DB row」；Stale-while-revalidate —「Yes, readers never wait」/「No」/「Serves bounded staleness」；XFetch early refresh —「Mostly」/「No」/「Tiny. Probabilistic」；Delayed double delete —「No」/「Reduces the window」/「Heuristic. The delay is a guess」。
- **原文**（同上「Thinking」段逐字）："**The delete-then-stale-set race.** Reader loads the old row, writer updates the DB and deletes the key, then the reader sets the old value. Use leases or versioned sets." "**Locks without timeouts.** If the lock holder dies, waiters hang. Every rebuild lock needs a TTL and a fallback (serve stale data or fail fast)." "Probabilistic early refresh such as XFetch reduces synchronized expiry probability but does not guarantee permanent residency."
- **原文**（gerryyang.com 逐字）："这可以减少『局部超时 → 全局误取消 → 下一波又重新回源』的抖动与放大效应。" "在缓存回源场景里，一个常见的工程优化是：只有 shared=false 的那次负责写缓存/打点，避免同一轮里重复写入或重复统计。"
- **判据**：① 两件事必须分别设计、缺一不可——「只让一个 worker 重建」（stampede）与「旧重建永不覆盖新值」（stale set）；singleflight 只解决前者，进程内且挡不住陈旧写。② 分布式重建锁必须带 TTL + 失败回退（serve stale 或 fail fast），否则持锁者死亡⇒等待者永久挂起。③ 防止陈旧写的可选机制各有代价：租约（delete 使 lease 失效，迟到 set 被拒，memcache 每 key 每 10s 至多一个 token）、版本化 CAS（需 DB 行带版本号）、stale-while-revalidate（读者永不等待但服务有界陈旧）。④ XFetch 只是降低同步过期概率，不保证 key 永久驻留，别当「永不过期」。⑤ 指标打点只由 shared=false 的那次负责，避免同一轮重复写缓存/重复统计。
