## 一、过载为什么会整体崩（AWS Builder Center 逐字）

作者 David Yanacek，标题《Using load shedding to avoid overload》，Published Dec 5, 2019。

- 「not only is throughput bounded by a system's resources, throughput typically degrades when the system is overloaded. When a system is given more work than its resources support, it becomes slow. Computers take on work even when they're overloaded, but they spend increasing amounts of their time context switching and become too slow to be useful.」
- 「When a server gets so overloaded that its latency exceeds its client's timeout, requests start to fail. This is where a latency increase transforms a latency problem into an availability problem.」
- 「The insidious part of an overload situation is how it amplifies itself in a feedback loop.」+「if each layer performs a number of retries, an overload in the bottom layer causes cascading retries that amplify the offered load exponentially.」+「When these factors are combined, an overload creates its own feedback loop that results in overload as a steady state.」——即 metastable failure 的官方描述。
- goodput vs throughput 逐字：「Throughput is the total number of requests per second that is being sent to the server. Goodput is the subset of the throughput that is handled without errors and with low enough latency for the client to make use of the response.」「The ideal load test result is for goodput to plateau when the service is close to being fully utilized, and to remain flat even when more throughput is applied.」
- 目标逐字：「When a server approaches overload, it should start rejecting excess requests so that it can focus on the requests it decides to let in. The goal of load shedding is to keep latency low for the requests that the server decides to accept so that the service replies before the client times out.」

## 二、worked example 与策略表（System Design In Depth 逐字）

vedgupta.in《Load shedding》Updated Sep 17, 2026。

- 「A service has 100 worker slots, each request needs 50 ms of work, and clients time out at 1 s. Capacity is therefore 100 / 0.05 = 2,000 requests per second.」
- 无 shedding 无界队列：「Offered 3,000 per second... the queue grows by 1,000 per second. After a few seconds, queueing delay passes 1 s, so requests are served only after their client has already given up. The server stays 100% busy but goodput (successful, in-time responses) can fall toward zero. This is congestion collapse.」（10 万 QPS 容量收 15 万 QPS ⇒ 近 15 万全超时，不只是超出的 5 万）
- 加 queue-time limit：「reject any request that has waited more than, say, 200 ms, or cap in-flight plus queued work at about 400. Now roughly 2,000 per second succeed within the deadline and 1,000 per second get a fast 503. Goodput stays at capacity.」
- 加优先级：「if 30% of traffic is batch or prefetch requests, shedding those first means user-facing requests (2,100 per second) are almost all served.」
- Little's Law 落地：「in-flight requests = throughput x latency. At 2,000 per second and a 50 ms target, only about 100 requests should be in flight. A concurrency limit near that number is a direct way to protect latency.」
- 自适应并发（Netflix concurrency-limits / TCP Vegas）：「tracks the minimum observed latency as the no-queue baseline, and when measured latency rises above it, queueing has started and the limit is reduced; when latency is at the baseline, the limit probes upward.」
- 策略表七行：per-client rate limiting（护公平、不反映真实容量）/ static concurrency limit（护 worker pool、需随服务重调）/ adaptive concurrency limit（护无排队延迟基线、需好延迟信号）/ queue time deadline（省废弃工作、需到达时间戳）/ LIFO 或 CoDel（过载时新请求仍成、老请求饿死）/ criticality-based（护业务关键、需每请求打标）/ degraded responses 缓存或部分（护体验、数据陈旧）。
- 失败模式：「Health checks shed too: if health checks are rejected, the load balancer marks nodes unhealthy and sends even more traffic to the survivors. Exempt them.」「Metastable states: retries and cold caches can keep the system overloaded after the trigger ends; combine shedding with retry budgets.」
- 恢复惊群（ESB1995 逐字）：「When a shed load is lifted and the system returns to normal, all the clients that received 503 will retry simultaneously... Always include a Retry-After header with a randomised delay (e.g., 5–30 seconds with jitter) in shed responses, and implement exponential backoff on the client side.」

## 三、判据（三条独点）

### 独点1：过载时整体 goodput 崩塌，不是「只丢超额部分」；早丢才省资源
- 判据：① 容量 C、到达 λ>C、客户端超时 T 三者同时给定时，不 shedding 的结论是「几乎全部请求超时」而非「只 λ−C 超时」——验收要看 goodput 曲线是否随 offered load  plateau。② 丢弃点尽可能早（edge / load balancer / iptables / 反序列化与鉴权之前）：AWS 逐字「Early rejection is important because it's the cheapest place to drop excess traffic, but it comes at a cost to visibility」，故须分层+记录丢弃了什么。③ 反向边界：极少数场景「quickly dropping a request can be more expensive than holding on to the request」（AWS 逐字），需实测而非教条早丢。

### 独点2：丢弃要按关键度分层，健康检查必须豁免；优先级只能降不能升
- Netflix Zuul（Analytics India Magazine / System Overflow 逐字）：三桶 NON_CRITICAL（日志/后台，高吞吐不影响播放）/ DEGRADED_EXPERIENCE（暂停标记/语言/历史，影响体验不影响播放）/ CRITICAL（影响能否播放）；每请求 priority score 1–100，后端异常时按最低优先级渐进丢弃，cubic 函数使阈值随 overload 缓升后陡降；service throttling（按错误率/并发）与 global throttling（CPU/连接数）两级。QCon SF 2025 版把决策下移到单个微服务，「services can only maintain or decrease priority, never escalate it」防低优先级请求沿途提权。
- AWS 优先级反直觉例（逐字）：「start()/end() 两 API 必须都可调才能完成工作 ⇒ prioritize end() over start()」；分页「first-page requests should be prioritized behind subsequent-page pagination requests」，否则第 N−1 页失败会浪费前 N−2 次调用；健康检查 ping 是「most important request」，被丢会让 LB 判不健康进一步减少容量。
- 判据：① 优先级标签在请求生命周期早期打、全程传递且只降不升。② 健康检查/控制面流量显式豁免。③ 完成类请求优先于启动类、后续页优先于首页——按「已完成工作的沉没成本」定优先级而非按到达顺序。

### 独点3：队列要设 TTL 与上限；静态 QPS 限不住动态容量；重试预算与 shedding 是两条独立机制
- 队列 TTL（AWS 逐字）：「place an upper bound on the amount of time that an incoming request sits on a queue, and we throw it out if it's too old. This frees up the server to work on newer requests that have a greater chance of succeeding.」+「As an extreme version... use a last in, first out (LIFO) queue... (HTTP/1.1 pipelining doesn't support LIFO, but HTTP/2 generally does.)」
- surge queue 反例（AWS 逐字）：Classic Load Balancer 用 surge queue 导致 brownout（服务端拿到请求时不知排了多久），Application Load Balancer 改为直接拒绝超额流量——「A generally safe default is to use a spillover configuration, which fast-fails instead of queueing excess requests.」
- 静态失效（vedgupta 逐字）：「a fixed 10,000 requests per second limit is wrong after a deploy that halves per-request cost or a cache flush that doubles it; adaptive concurrency limits track real capacity.」——GC / cache hit ratio / 网络时延让容量动态变化。
- 判据：① 队列三件事同时写：大小上限 + 停留 TTL + 超时提示传递（client timeout hints「apply them transitively」，下游知道剩余时间）。② 自适应并发以 minRTT 为无排队基线，延迟超基线即收紧；与 §16 token bucket 限流、§12 deadline 传播、§15 熔断、§22 背压有界队列各管不同面，不可互相顶替。③ 丢弃响应带 `Retry-After` + jitter（5–30s）且客户端指数退避，否则 shedding 反过来制造重试风暴；与 retry budget 联合才打破 metastable 稳态。
