# 生成物验证（独立 oracle + 差分 + 变异测试）

三层检查清单
### A. 生成层（结构/契约）
- 存在性 + sha256 + 行数（可溯源）
- `ast.parse` 通过；`python -m py_compile` 真过编译
- 必需函数/接口齐备，**参数名与顺序**符合约定
- 反退化扫描：`TODO`/`FIXME`/`...`/空 `pass` 函数体/占位符
- 自包含性：只 import 标准库（`sys.stdlib_module_names`）
- CLI/接口契约：`--help` exit 0；非法子命令/非法入参 → 非 0 退出
- 以模块方式导入并直接调用 API（不止测 CLI）

### B. 执行层（取值正确性）
每个用例：exit code + 输出可解析 + **schema 键集合完全一致** + **值 == 至少一个 oracle** + **边界值**（0 / 1 / 空 / 负数 / 极值）+ **确定性**（同命令跑两次字节一致）。
- 差分模糊测试：随机输入 × 2 个以上独立 oracle，全量比对（记录 seed 保证可复现）
- 内部一致性：若产物输出"结果 + 过程/证据"（如编辑脚本、对齐、trace），必须**重放过程验证能推出结果**，且过程代价 == 结果值

### C. 检出能力层（变异测试）
- 至少 5 个变异体，覆盖不同失败族：**数值 off-by-one / 过滤条件弱化 / 语义静默归零 / 契约字段改名 / 边界判断翻转**
- **每个检查必须先证明自己跑到了**（到达标记，见「验证完整性三查」1）——变异体"失败"若没打标记，可能是它自己 import/构建挂了，不是被抓住
- **等价变异体必须先识别再排除**：若变异后语义与原实现完全等价（例：删掉 `sorted(key=(-count, first_pos))` 里的 tie-break —— Python dict 插入序本就等于首次出现序），它**必然逃逸**。这不是验证器失明，必须显式标注为"等价变异体，不计入检出率"，否则会误判验证失败、也会掩盖真正的盲点。
- 每个变异体**独立目录 + 原始文件名 + 随机目录名**（见坑 4 与"侧盲"），`caught = 打完到达标记后存在任一 FAIL`
- 报告里记录 `caught_by`，用于确认是"真实的取值检查"抓到它，而不是无关路径错误

## r385A · 导出/迁移产物必须自带机读验收面：清单要含「没导出什么」，截断要自证，跳过的要给原因（来源：pipedream.com/docs/workflows/export-workflows.md 6,591B 独立 curl 取 .md 原文，2026-10-02 实拉；经 Qoder r388-Q-C 提名）
- **★验收清单的价值在「未导出项」而不是「已导出项」**：原文「`manifest.json` lists **every workflow in the project, including workflows that were not exported**, so **nothing is left out without a record**」。判据：**只列成功项的清单无法回答"漏了什么"**——迁移/导出/批量操作的产物必须把失败与跳过项一并登记，且逐项带 `status` 枚举（`exported` / `skipped_never_deployed` / `skipped_export_limit`），让"跳过"本身成为可判状态而不是沉默。
- **★产物要自带截断与限额自证**：manifest 同时给出 `schema: "project-export/2026.01"`、`truncated: false`、`truncated_reason: null`、`limits: {workflows: 500, bytes: 268435456}`。判据：**完整性不是"看起来齐"，而是产物自己声明自己是否被截断、按什么限额截的**——验收方不读这套自证字段，就无法区分"确实只有 3 项"与"到第 4 项被限额掐断"。
- **★需人工重填的部分必须逐条点名到 step 与 prop**：`warnings[]` 给出「step send_message: secret prop api_key was omitted from the export and **must be re-entered after import**」。判据：**"导入后需要重新配置"这种话没有验收价值**——点名到具体步骤与字段才能机检；warnings 为空才是真的无需人工介入。
- **★迁移/导出只搬结构不搬凭证，这条边界要写进验收而不是使用说明**：secret props 一律 `<redacted>`、App props 只保留 `authProvisionId` 且「Tokens and other credentials are removed」、私有组件「includes the component key, **but not its code**」。判据：**导入后"能装上"不等于"能跑"**——凭证与私有代码是结构化缺口，验收必须把它们列为显式待补项，与 §r383A「迁移工具只搬被引用资源」分工：那条管**资源覆盖面**，本条管**产物自带的验收面字段**。

## 归因会被反向代理改写；公开写入的报告通道要做信息量过滤；存储有没有卸载通道决定限额是不是同一回事（来源：pipedream.com/docs/conduit/deploy/hardening.md 7,011B + www.activepieces.com/docs/install/reference/limits.md 6,779B，2026-10-03 r393A 独立 curl 取 `.md` 原文实拉；与 §留痕两种缺口 / §影响边界声明 互补——那两条管账本入口与改动连带面，本条管账本里"是谁"这一栏会不会被基础设施改写）

- 反向代理前置会改写身份归因：不设 `CONDUIT_TRUSTED_PROXIES`，审计记录与 per-IP 限额全部算到代理头上，真实客户端消失 ⇒ 验收归因面之前先确认链路里有没有代理，这是**配置前置条件**而不是运行时故障，现象看起来却像"没记录"。
- 未鉴权的报告端点是一块公开写入面，必须做信息量过滤而不是照单全收：Conduit 丢弃两类 CSP 报告——浏览器扩展注入的内容（任何策略都管不了）、页面不在 `CONDUIT_BASE_URL` 内的报告（否则任何人可提交）⇒ **噪声与伪造是同一道门**，不记录比记录错误的东西更安全。
- 安全头作用域要克制：HSTS 是 host-only，不替无关子域 opt-in，也不申请 preload；纯 HTTP 开发地址不发 HSTS ⇒ 作用域越宽，误伤与不可回退性越大（preload 基本不可撤）。
- 同为"存储"，有没有卸载通道是两回事：KV store 的键值直接进 Postgres `jsonb`，**没有对象存储卸载通道、每次访问全量读写、计入数据库大小**；只有文件与运行日志才有卸载 ⇒ 容量验收要按存储面分开算，不能拿"日志 25MB 上限"推出 KV 也有同等余量。


## 验证结论必须声明「证明了什么的上界」，失败要分三类不可合并；同一份托管身份在不同执行面保证不同，验收须按执行面分别写（来源：docs.openclaw.ai `gateway/config-secrets-env.md` 10,309B + `gateway/config-tools.md` 7,517B 索引页 + `gateway/config-tools/github-identity.md` 17,020B，2026-10-03 r395A 独立 curl 取 `.md` 原文实拉）

- **验证证明的是上界不是全体**：官方明确「验证证明的是哪个账号应答了 GitHub API 请求」，而 `/user` 端点**不证明写权限**；仓库级授权要等一次精确仓库操作成功才算已知 ⇒ 验收报告要写「这次验证证明了 A，不证明 B」，只写「校验通过」会让人以为写权限也验过了。
- **失败三分类不可合并**：状态区分区分 missing credentials（缺凭据）/ unverified transport failure（未验证的传输失败）/ rate limiting（限流）三类，且不返回底层 `gh` 诊断 ⇒ 「拿不到结果」至少要分成「没凭据」「网络不可信」「被限流」，三者改的地方完全不同，合成一个「验证失败」就没法处置。
- **同一托管身份在不同执行面保证不同**：本地 gateway-owned exec 每次启动前读取并校验 profile，把 token 只放进私有子进程环境并清掉 `GITHUB_TOKEN`；Codex-native shell 只拿到非密 overlay（`GH_CONFIG_DIR`），**不隔离 OS keyring**，profile 消失时 gh 可回落到原生 keyring；沙箱、node-host exec、remote-exec **根本收不到**托管凭据，只有 `github_publish` 记录一个不含凭据与仓库权限的有界发布请求 ⇒ 验收必须先问「这次跑在哪个执行面」，再说「用了托管身份」保证了什么。
- **要强保证必须换执行面而不是加配置**：官方写明「需要启动绑定的托管身份保证时，用 `gateway_exec`」；native shell 的那套保证明确不覆盖 ⇒ 当能力声明与实际需求差一档时，正确处置是换通道，不是在同一通道里加参数。

- **看得见通知不等于拿得到内容**：ambient 群组监听会向主会话排队活动通知并告知「发生了什么」，但官方明确**不授予访问权限** ⇒ 「我收到了通知」与「我能读那份上下文」是两件事，验收要分开问。
- **附件的暂存位置是硬约束**：子 agent 附件一律暂存在网关自有状态里并带 `.manifest.json`，**永不穿过子工作区**；沙箱子进程只在 `/openclaw/attachments/<uuid>/` 拿到**只读投影**；共享作用域沙箱与不支持只读资源投影的后端会在 staging **之前**就拒绝这次 spawn ⇒ 能力前置检查发生在落盘之前，不是先落盘再判。
- **正文脱敏与路径存续是两件事**：附件内容会自动从 transcript 持久化中脱敏，但文件本身仍以 `0700`/`0600` 权限存在；`cleanup=delete` 总是删除附件，`cleanup=keep` **只有在 `retainOnSessionKeep=true` 时**才保留 ⇒ 「已脱敏」不等于「已删除」，验收要分别确认两条路径。
- **退役的遗留路径不删也不遍历**：升级前暂存在子工作区 `.openclaw/attachments/<uuid>/` 的遗留附件，其 registry 记录退役时**既不删除也不遍历**那些文件；回执里的 `relDir` 是**保留下来的标识符，不是可用路径，不得解析** ⇒ 迁移类产物里那些看起来像路径的字段，要显式标注「不可解析」，否则下游会拿着它去读一个已经不存在的位置。

## 审计事件目录是「能发出」的全集而非「已发生」的集合；归因空值多义；有 trace id 不等于可回溯也不等于可信身份（来源：pipedream.com/docs `conduit/use/api-reference/audit-log/get-audit-event-catalog.md` 9,011B + `.../list-org-audit-log.md` 11,642B + www.activepieces.com/docs `admin-guide/security/audit-logs/overview.md` 4,198B，2026-10-03 r396A 独立 curl 取 `.md` 原文实拉）

- **目录列的是能力，不是事实**：Pipedream 的审计事件目录返回的是**本构建能发出的事件命名空间树**，官方写明是让过滤 UI 能列出**「甚至尚未被记录过的事件」** ⇒ 「目录里有这个事件」不能证明它发生过，反过来「目录里没有」才是唯一能证明「不会被记录」的证据。覆盖面验收要拿代码里的 event schema 当真源，不能拿目录当台账。

## 验收要报「通过率」与「通过但偏离率」双轴并带 Wilson 置信区间；检查项数≠根因数；拦截器双指标验收（拒断率 + 授权供给无损）（来源：Qoder r400-Q/r401-Q 审计净新，2026-10-03；对应 pipedream.com/docs `get-audit-event-catalog.md` 9,011B 本轮回拉印证「目录含未发生事件」）

- **通过率单轴会虚高，必须并报「通过但偏离规范」率**：评测/扫描器只报"通过率"会掩盖"形式上过了但偏离规范"的占比，小样本下尤其危险；两率都带 Wilson 置信区间，样本少时间隔宽、不拿点估计当结论。
- **检查项数≠根因数**：报"检查了 N 项"不代表覆盖了 N 个根因维度——检查项计数（如 6.34）和根因数（如 2.65）是两套数，覆盖面验收要标清"查了几项"与"对应几个根因"的区别，避免用项数冒充维度覆盖。

## 验证一条「拒绝」是否生效，必须先有一个「若规则失效则必然成功」的反证探针；拿不到反证时阻断与不可达不可区分（来源：docs.openclaw.ai security/network-proxy.md 21,937B，2026-10-04 r417B 独立 curl 取 .md 原文实拉）
- 阻断的验证比放行的验证难一个量级：放行只要看到成功即可，阻断必须证明「要不是被拦，这次本来会成功」。做法是发一个**只有规则失效才会返回成功**的探针（内置 loopback canary 带 per-run token），于是「拿到匹配 token 的响应」直接证明代理转发了本该拒绝的目标。
- 反证探针的判定必须写成四态而不是布尔：传输失败算通过（被挡）；非 2xx 且缺少探针 token 算通过；**2xx 却缺 token 算失败**（有别的东西意外成功了）；**任何带匹配 token 的响应算失败**（证明规则确实没生效）。
- 没有反证探针时就只能 fail-closed：自定义拒绝目标不带 token，于是任何 HTTP 响应都判为「可达」，连传输错误也算检查失败——因为无法区分「代理挡了一个可达源」与「别处出了故障」。**只有内置探针才允许把传输错误当作阻断的证据，这条豁免必须写进文档，否则会被当成通用规则误用。**
- 可达性的另一种证明是「可预期的确定性失败」：故意发一个无效 provider token，收到对端特有的 `403 InvalidProviderToken` 即证明隧道真的到达了对端——正向成功可能来自中间层缓存，而只有真实对端才产得出的错误码不可伪造。
- 验证通道自身的日志只记 destination / decision / status / reason，绝不记请求体、authorization 头、cookie 或其它秘密。校验用的 URL 凭据在文本与 JSON 两种输出里都要脱敏。
- 校验项要分清「通道级」与「进程全局」：`proxy.tls.caFile` 只作用于受管代理路由，而 `NODE_EXTRA_CA_CERTS` 是进程全局且必须在 Node 启动前设置，平台无法在运行中补加。**声明信任时必须同时声明作用域与注入时点**，否则「配了就该生效」的期待会落空。
- 校验探针本身失败不应阻断主流程：探针在预算内不回答时记 warning 并附下一步排查指引，主更新继续 best effort。探针是观测件不是准入件。

## 跨审计方对账的主键是内容哈希不是名称版本，且「没发现恶意」要拆成四档计数才可读（来源：skills.sh/audits 333,759B 一手 curl 实拉，2026-10-06 r432-B 逐串命中 `skillFolderHash` 75 处 / `purl` 25 处 / `summary` 四计数；与 §聚合目录剔除是逻辑与 互补——那条管聚合结论的方向，本条管聚合的对账键与计数口径）
- 原文事实：多家审计结果（含 `partner":"Socket"`）统一挂在 `skillFolderHash` 上（`"skillFolderHash":"0ca4cfe5…96e6"`）；第三方坐标写成 `"purl":"pkg:socket/skills-sh/<owner>%2F<repo>%2F<skillpath>%2F@<hash>"`——**`@` 后面是哈希不是版本号**；每份审计带 `summary:{"total_urls_checked":2,"malicious":0,"clean":0,"unknown":2,"errors":0}` 四计数分列。
- 判据：① **对账键必须是内容哈希**：多家的结论挂在目录内容哈希上，改名、改版本、换托管位置都不会让历史审计与对象脱钩；用名称或语义版本做键，改一次名就把结论与对象断开，表面上"审计还在"、实际已指向别的产物。② **外部坐标也用内容坐标**：`purl` 里 `@` 后是哈希而非版本 ⇒ 版本相同而内容不同的情况在其模型里根本不存在；引用第三方扫描结论时先确认它用的是内容坐标还是版本坐标，后者无法证明"你手里这份"被扫过。③ **`unknown` 与 `errors` 必须与 `clean` 分列**：上例 `total_urls_checked:2` 而 `clean:0 / unknown:2 / errors:0` —— 一个"零恶意"的审计完全可能由 100% `unknown` 撑起，**零 clean 不等于零风险，也不等于查过**；把 `malicious:0` 读成"通过"是误读。⇒ 引用审计结论时固定问两个数：`clean` 占 `total` 多少、`unknown+errors` 占多少。④ **同名字段可能混用哈希算法**：本次 75 处 `skillFolderHash` 中 **74 处 64-hex（SHA-256）、1 处 40-hex（SHA-1）** ⇒ 跨条对账前必须先声明算法并按长度机检，否则同一个字段名下的值不可比，对账会在静默中失效。

## SSRF 验收要区分「重解析绕过」与「混合应答」：一次 DNS 应答里同时含被封地址与放行地址时，必须整体拒绝而不是取并集放行（来源：api.github.com/repos/langflow-ai/langflow/releases?per_page=3 31,882B，2026-10-12 r527A 一手 curl 200 逐串命中 `v1.12.4` / `fix: reject mixed blocked DNS answers with IP allowlists by @erichare in .../pull/15334` / 同批 `fix(ssrf): pin direct Requests helper connections by @erichare in .../pull/15340`；r527A 落地）
- **实证**：Langflow v1.12.4 的安全修复条目不是"加一条 DNS 校验"，而是**拒绝混合型的被封 DNS 应答**（`reject mixed blocked DNS answers with IP allowlists`），即判定单元是「这一次解析返回的整个地址集合」，不是逐个地址。
- **判据**：① **两种绕过形态要分别建用例**：DNS rebinding 是**时间维度**——先给好地址过校验、再解析成坏地址；混合应答是**空间维度**——同一次应答里好地址坏地址并存。只测前者会把后者整条漏掉。② **放行的主语必须是"整个应答"而非"某个地址"**：一旦按地址逐个判，攻击者只要在同一域名下混入一个放行 IP 就能让整次解析通过 ⇒ 校验函数的返回类型应是"这次解析是否整体可信"，不是"哪些地址可用"。③ **IP 允许清单与 DNS 阻断必须联合判定**：修复标题把两者写在一起（`mixed blocked DNS answers` **with** `IP allowlists`）⇒ 只有 DNS 侧阻断、没有 IP 侧清单时，"该不该放行"没有确定答案；两套机制要同一处求值。④ **直连通道是绕过面**：同批 `pin direct Requests helper connections` 说明绕过不止发生在解析器上，还在"直连不走代理的 HTTP helper" ⇒ 审计出网路径时要穷举所有发请求的封装，而不是只审主客户端。

- **实证**：Langflow v1.12.5 PR #15529 的修复不是"把敏感值从响应里删掉"，而是**在保留服务端可执行真值的前提下返回掩码**——原文 `Return masks for these values while preserving decrypted configs for server execution`；并配套四条写回规则：按 `map key or header name and occurrence` 回填最新存储的凭据、替换与删除仍可用、模糊/新引入掩码 `return 422` 而不是存占位符、保存 flow 时 `Restore only the originally masked graph fields on every retry, leaving other nodes' explicit references intact`；另有 `Encrypt new header arguments at rest and retain compatibility with legacy plaintext configs` 与 `reject masks without an existing value owned by the caller before staging writes`。自述 76 条聚焦后端测试 + 52 条后续套件测试通过。
- **判据**：① **脱敏的验收对象是"双向协议"而不是"单向隐藏"**：读侧给掩码只是半个协议，写侧必须能把掩码映射回真值，否则用户一保存就把占位符当成新密码写进去——**"保存成功"在掩码系统里是危险信号，正确行为是显式 422**。② **回填的定位键是"位置"而非"值"**：按 map key / header name + 出现序号定位 ⇒ 改名、重排、增删同名字段都会让回填错位，回填方案必须先声明"以什么为键"。③ **恢复范围要收敛到被掩码集合**：原文 `only the originally masked graph fields` ⇒ 重试不是全量重放，恢复范围超出掩码集合就会覆盖别处的显式引用，制造"我没改这个字段却被改了"的故障。④ **加密面与兼容面必须同时声明**：新 header 参数 at rest 加密，同时 `retain compatibility with legacy plaintext configs` ⇒ "已加密"只对新建成立，存量明文仍在库里，审计要按新旧两段分别算覆盖率。⑤ **掩码的所有权要可判定**：`without an existing value owned by the caller` ⇒ 掩码不能凭空产生，提交方必须对该值有既有所有权；无主的掩码在 staging 写入前拒绝。⑥ **落地验收动作**：取一次管理接口响应 → 把掩码**原样**回写 → 检查真值未被占位符覆盖。只验"响应里没有明文"只覆盖了半个协议。⑦ 与 §脱敏是返回面的承诺不是存储面的承诺（KB:2752）互补：那条管"返回不吐 ≠ 服务端没有"，本条管"返回吐了掩码之后，写回这条路径会不会把真值弄丢"。
- 提升层：工具（凭据掩码协议）/ 工作流（安全验收）。触发词：mask 回写、422 拒绝占位符、按 map key 回填真值、脱敏双向协议、重试只恢复掩码字段、legacy 明文兼容、掩码所有权。

## 权限的签发面与执行面是分离的：非管理员也能给自己签上 admin scope，令牌自带的 scope 清单不能当权限证据，必须在执行侧用响应码探测（来源：developers.make.com/api-documentation/authentication/api-scopes-overview.md 11,643B，2026-10-12 r528B 一手 curl 200 逐串命中 `Even if you are not the administrator, you can assign to your token the scopes meant for administrators. - **实证**：Make API 的作用域只有 `:read` / `:write` 两型，且**签发时不校验角色**——不是管理员也能把 `admin:read` / `admin:write` 勾到自己的令牌上；校验发生在访问那一刻，普通用户访问管理资源返回 `403 Access denied`。原文还写明 `Some resources require more than one scope`，以及管理端点的可达性本身还随平台形态变化（云版普通用户进不了管理界面，本地版带 platform administration 角色的用户可以）。
- **判据**：① **令牌上写着什么，与这个令牌能做什么，是两件必须分别取证的事**：签发面不校验角色 ⇒ 拿到一枚含 `admin:write` 的令牌，**不能**推出持有者是管理员，也不能推出他能动管理资源。审计权限时的正确动作是**执行侧探测**（发一个真实请求看响应码），而不是读令牌声明。② **失效方向要写清楚**：本例是"**过授予、实际受限**"——授予面比执行面宽。与 §签名≠行为符合声明（av 2.197.0 / sa KB:2680）**方向相反**：那条是声明强于实际（说得到做不到），本条是授予强于实际（签得到用不了）。两者都要报，但补救动作不同——前者要补运行时验证，后者要补签发侧校验或明确"签发不校验"是设计选择。③ **"签发不校验"本身要被显式声明**：既然 403 只在访问时出现，系统必须在文档里写明"scope 可在签发时任意选择"，否则使用者会把"我能勾上"误读成"我有这个权限"，进而把 403 当 bug 上报。④ **作用域的类型数与资源的所需数是两个独立维度**：两型（read/write）× 单资源多 scope ⇒ 建模权限时不能假设"一个资源一个 scope"，要有"所需 scope 集合"这种一对多结构。⑤ **同一 scope 在不同平台形态下可达性不同**（云版 vs 本地版）⇒ 权限矩阵的行列里要带上"部署形态"这一维，否则跨环境验收会得出相反结论。
- 提升层：工具（权限取证）/ 工作流（安全验收）。触发词：签发面 vs 执行面、scope 不是权限证据、403 在访问时、过授予实际受限、admin scope 非管理员可签、单资源多 scope。

## 对「共享对象」做的运算必须是无副作用的：原地扩展（+=）会顺着图引擎污染兄弟节点的输入，验收要断言操作数不变且重复运算结果不累积（来源：api.github.com/repos/langflow-ai/langflow/pulls/15514 25,803B，2026-10-12 r529A 一手 curl 200 逐串命中 `fix(lfx): stop Data addition from mutating the left operand's lists` / `Adding two Data/JSON objects that share a list-valued key changed the left operand` / `Reusing that operand in another addition then piled up duplicates, and adding an object to itself changed the original` / `the graph engine hands the same Data object to every downstream node, so a component doing incoming + extra corrupted the input its sibling nodes saw` / `JSON.__add__ shallow-copies self.data and then used += on overlapping keys, which extends a list in place`；r529A 落地）
- **实证**：Langflow PR #15514 的最小复现是 `left = Data(data={"items":[1]})`、`right = Data(data={"items":[2]})`：`(left + right).data` 得 `{"items":[1,2]}`，但 `left.data` **也变成** `{"items":[1,2]}`（应为 `{"items":[1]}`），再算一次变成 `{"items":[1,2,2]}`。成因是 `JSON.__add__` 只做了浅拷贝（`shallow-copies self.data`）却在重叠键上用 `+=`，`+=` 对 list 是原地扩展。危害面由执行模型放大：图引擎把同一个 `Data` 对象交给**每一个下游节点**，所以任一组件写 `incoming + extra`，被污染的 `incoming` 就是它的**兄弟节点**正在读的那一份。
- **判据**：① **"看起来是纯函数"的运算要按纯函数验收**：加/合并/拼接这类命名的操作，验收必须包含"操作数在运算后是否不变"这一断言，只断言返回值正确会漏掉整条污染路径。② **浅拷贝不足以构成无副作用**：复制了顶层容器但内层仍共享引用，`+=`/`append`/`extend` 一类原地操作照样改到原对象 ⇒ 判断安全性的单位是"最深那层被写到的对象是否独占"，不是"是不是新建了一个容器"。③ **验收要重复跑同一运算**：单次运行 `(left+right)` 看不出问题，第二次才暴露 `{"items":[1,2,2]}` ⇒ 对有状态的合并运算，最少跑两遍并比对两次结果是否一致。④ **自运算（a + a）是必测用例**：原文专门点出 `adding an object to itself changed the original` ⇒ 左右操作数同一对象的情形要在测试矩阵里单独占一格。⑤ **共享即传播面**：把同一对象分发给多个消费者时，任一消费者的"读"都可能被另一消费者的"写"改变 ⇒ 排障"某个节点拿到了不该有的数据"时，先查上游是否有组件在原对象上做过原地修改，而不是先怀疑调度顺序。⑥ 与 §变异契约（KB:410）、§只加不改+纯函数派生（KB:578）分工：那两条管"断言是否真的读了它声明的字段 / 派生过程不得改原文"，本条管**二元运算对共享操作数的原地污染及其跨节点传播**，落点是可执行的最小复现（重复两次 + 自运算）。
- 提升层：工具（数据结构语义）/ 工作流（验收用例设计）。触发词：原地扩展、+= 污染左操作数、浅拷贝不等于无副作用、共享 Data 对象、兄弟节点输入被改、重复运算结果累积、a+a 自运算、图引擎共享引用。

## 密钥的「已设置」与「拿得到」是两个字段：创建时一次性披露的密钥事后无法回读，更新接口不重新披露（来源：pipedream.com/docs/connect/api-reference/set-project-environment-webhook.md 8,298B，2026-10-12 r529C 一手 curl 200 逐串命中 `Creating a webhook returns signing_key; updating an existing webhook does not.` / `The signing key is returned when a webhook is created, but omitted when an existing webhook` / 字段 `signing_key_set` 描述 `Whether a signing key has been set for this webhook`；r529C 落地）
- **实证**：Pipedream 的项目级 webhook 接口在同一端点上合并 create/update：摘要行即写明**创建时返回 `signing_key`、更新已有 webhook 时不返回**；响应体描述重申 `The signing key is returned when a webhook is created, but omitted when an existing webhook`；schema 里另有独立布尔字段 `signing_key_set`，释义是"这个 webhook 是否已经设过签名密钥"。同族端点 `/connect/api-reference/update-trigger-webhooks.md` 进一步限定 `signing_key` **仅对 OAuth 认证的请求返回**，并单列 `Regenerate ... signing key` 作为重新获取的唯一途径。
- **判据**：① **"存在"与"可得"必须拆成两个字段建模**：`signing_key_set: true` 只回答"有没有配过"，不回答"我现在能不能验签" ⇒ 把"已设置"当"我能用"是这类接口最典型的误判，且它不报错——你只是拿不到值。② **一次性披露的密钥，验收动作前移到创建时刻**：既然事后回读不到，"我持有该密钥"的证据只能是创建响应里的那一份留存 ⇒ 交付/交接清单里必须显式包含"创建响应的密钥是否归档"，不能假设随时可再取。③ **更新接口不是重新披露的时机**：同端点承担 create/update 两职却只在 create 返回值 ⇒ 用 update 去"顺便拿一下密钥"必然落空；判断"这次调用会不会给我"要看它是不是创建路径，而不是看端点叫什么。④ **可见性还受认证方式约束**：`signing_key` 仅在 OAuth 认证请求下返回 ⇒ 同一个"有没有密钥"的事实，随调用凭据类型给出不同答案；审计要固定凭据类型后再比对。⑤ **轮换是独立端点不是副作用**：官方把 `Regenerate ... signing key` 单列 ⇒ 想换密钥必须显式走轮换，"更新一下 webhook"不会也不应该顺带把旧密钥吐出来；轮换完成后旧值即不可恢复，交接面要同步。⑥ 与 §掩码是双向写回协议（av 2.201.0）、§权限签发面与执行面分离（av 2.202.0）分工：那条管"掩码值怎么回填真值"、那条管"签到的 scope 能不能用"，本条管**密钥值本身的披露时机与"已设置"字段的语义边界**——三者共同点是"响应里看得到的东西，不等于你拥有它"。
- 提升层：工具（凭据披露面）/ 工作流（交付与交接验收）。触发词：signing_key_set、创建时返回密钥、更新不返回密钥、一次性披露、存在不等于可得、OAuth 才返回、regenerate signing key。

## 数据的读取形状属于发布契约：物化路径按类型分叉（非字符串键字典不再走 JSON 路径），日志从「整块 blob」改为分页可过滤的条目 API——二者都会让读侧工具静默断链（来源：同上 ZenML 0.97.0 发布说明，2026-10-12 r531A 一手 curl 200 逐串命中 `Dictionary outputs with non-string keys are no longer materialized through the JSON path.` / `If you relied on reading such artifacts back as JSON-compatible data with keys converted to strings` / `Log retrieval now uses a paginated/filterable entries API instead of assuming a single full log blob` / `update your code to preserve original key types or change outputs to use string keys for JSON interoperability`；r531A 落地）
- **实证**：同一版 ZenML 的破坏性变更里有两条读侧形状变更。① **物化路径按 key 类型分叉**：非字符串键的字典输出**不再**经 JSON 路径物化，官方给出的迁移动作是二选一——「preserve original key types」或「change outputs to use string keys for JSON interoperability」；被点名的受影响假设是"读回来时键已被转成字符串"。② **日志 API 形状变更**：`Log retrieval now uses a paginated/filterable entries API instead of assuming a single full log blob`，并特别说明 `especially for external log stores`，官方要求直接消费日志 API 或围绕旧响应形状建过工具的调用方改用新的 entries endpoint 加分页/过滤参数。
- **判据**：① **"能写进去"不等于"能按原形状读回来"**：物化器会按类型选路径，所选路径决定读回时的类型保真度 ⇒ 验收产出物时必须断言"读回来的类型 == 写进去的类型"，只断言"能读回来"会把静默的类型转换判成通过。② **类型转换一旦被当作既定行为就会被写进下游**：本例官方明确承认"键被转成字符串"曾是可依赖行为 ⇒ 凡是"框架帮你做的隐式转换"，都要在发布说明里显式声明它是不是契约；是契约就必须在移除时列进破坏性变更（本例正是这么做的）。③ **"整块"到"分页"是响应形状变更，不是性能优化**：`instead of assuming a single full log blob` ⇒ 下游若假设"一次拿全"，改成 entries API 后不会报错，只会**少拿**——这类变更的故障形态是数据不全而非异常，必须在验收里加"条数与总量是否一致"的断言。④ **外部存储是这类差异的高发面**：原文限定 `especially for external log stores` ⇒ 同一套 API 在本地存储与外部存储下的形状/完整性可能不同，验收矩阵要带上"存储后端"这一维。⑤ **迁移动作给了两条且互不兼容**：保真 key 类型 vs 改成字符串 key ⇒ 二选一意味着"兼容 JSON"与"保真类型"在此处是互斥目标，选型时要先判下游消费者更需要哪一个，不能两边都要。⑥ 与 §共享对象运算无副作用（av 2.203.0）、§密钥已设置≠拿得到（av 2.204.0）分工：那两条管**写侧污染**与**披露时机**，本条管**读侧形状在版本间变更**，落点是"读回来的东西是不是我以为的那个形状"。
- 提升层：工具（产出物读取契约）/ 工作流（升级验收）。触发词：non-string keys 物化、JSON path 不再物化、key 类型保真、日志 entries API、single full log blob、分页导致少拿、external log stores 形状差异。

## 同一个外部服务在自动化里占两个方向相反的面：入向触发（webhook provider）与出向通知（alerter）必须分别建模；签名算法按 provider 定，触发条件是 typed 的而不是通用事件流（来源：api.github.com/repos/zenml-io/zenml/releases?per_page=3 24,428B，2026-10-12 r531B 一手 curl 200 逐串命中 `separate from the existing Slack alerter that sends notifications to Slack` / `inbound Slack Events API callbacks as a first-class webhook provider` / `typed GitHub filters for merged pull requests, completed workflow runs, pushes, and published releases` / `authenticates deliveries with ClickUp's raw hex HMAC signature` / `supports string-based filters` / `project-scoped`；r531B 落地）
- **实证**：ZenML 0.96.4 把 webhook 做成一等自动化能力，同一版里出现三处面分离事实。① **Slack 出现两次且方向相反**：新增的是 `inbound Slack Events API callbacks as a first-class webhook provider`（入向：Slack 事件触发流水线），官方同时写明它 `separate from the existing Slack alerter that sends notifications to Slack`（出向：流水线结果通知到 Slack）——同一个 Slack 集成，一个是源一个是汇。② **触发条件是有类型的**：`typed GitHub filters for merged pull requests, completed workflow runs, pushes, and published releases`，即事件在平台侧已被切成具名子类型，而不是给下游一整条原始事件流自行判断。③ **签名算法随 provider 变**：ClickUp provider 用 `ClickUp's raw hex HMAC signature` 验签，并 `supports string-based filters`；作用域被限定为 `secure, project-scoped integrations`。
- **判据**：① **"集成了 Slack"是一个不完整的陈述，必须补方向**：入向触发与出向通知的凭据、端点、权限、故障形态全不同 ⇒ 集成清单里同一服务可能要占两行；说"已接入"而不说方向，验收时会对错面（配了 alerter 却去测能否触发流水线）。② **"一等 provider"意味着它是受管身份而非自建胶水**：官方把 inbound 回调提到 first-class，等于由平台承担验签与投递语义 ⇒ 自建一个"收 webhook 再转发"的中间件时，要先确认平台是否已有一等 provider，重复实现会多出一个必须自己维护的验签面。③ **typed filter 的价值在于把判断前移**：`merged pull requests` / `published releases` 是平台已解析的语义子类型 ⇒ 若拿到的是原始事件流，判断"这次 push 是不是一次 release"的逻辑会散落在每个下游；选型时优先选给 typed filter 的那一侧，否则要在自己的过滤层复刻平台已实现过的解析。④ **"有类型"同时意味着"类型之外不触发"**：typed 列表是白名单 ⇒ 需求里出现列表外的事件（如 issue comment）时，它不会静默降级为通用事件，而是根本不触发；排障"配了却没触发"的第一问是"这个子类型在不在 typed 列表里"。⑤ **验签算法不是通用 HMAC，是 provider 特定的**：ClickUp 用 raw hex HMAC ⇒ 不能把"A 平台的验签代码"复制到 B 平台；provider 文档里"签名用什么编码/什么键"必须逐家记录（本例键名与编码都是 ClickUp 私有约定）。⑥ 与 §回调通道认证推荐 HMAC（KB:1067）分工：那条管**选型**（在 API key / Bearer / HMAC 中选哪个），本条管**落地形态**（同一服务的入/出两面要分开建、签名按 provider 定、过滤优先用 typed），落点是集成台账的建模方式。
- 提升层：工作流（集成建模）/ 工具（webhook 验签）。触发词：入向触发 vs 出向通知、webhook provider vs alerter、typed GitHub filters、raw hex HMAC、project-scoped webhook、一等 provider、事件子类型白名单。

## 自述文档与实际行为必须同源：发现文档声明 PS256 而令牌实签 RS256，严格按发现文档校验算法的一方会拒掉全部合法令牌；客户端权限判定也必须与服务端授权路径同源（superadmin 是隐含成员）（来源：api.github.com/repos/windmill-labs/windmill/pulls/11637 2,873B + /pulls/11653 4,292B，2026-10-12 r531C 一手 curl 200 逐串命中 `advertised PS256 in id_token_signing_alg_values_supported, while every token is signed with RS256` / `A verifier that reads the algorithm from discovery and enforces it rejects valid tokens` / `signing_algs(), which returns the same constant the signing call uses, so the two cannot drift apart again` / `buildPermissionedAsContext counts user.is_super_admin alongside is_admin` / `whoami returns a member's own usr row, so a superadmin with a non-admin membership in the workspace reports is_admin: false` / `The backend, though, treats a superadmin as admin on every auth path`；r531C 落地）
- **实证**：两个 PR 是同一类缺陷的两例。① **Windmill #11637**：OIDC 发现文档 `/api/oidc/.well-known/openid-configuration` 在 `id_token_signing_alg_values_supported` 里宣告 `PS256`，而**每一个令牌都是用 `RS256` 签的**；任何「从发现文档读算法并强制校验」的校验方会**拒掉合法令牌**。修法不是改文档里的字符串，而是让发现文档取 `signing_algs()`——**与签名调用使用同一个常量**，`so the two cannot drift apart again`；令牌、密钥、JWKS 全部不变。② **Windmill #11653**：`syncBehavior: v1` 下 CLI 判断「能否在 push 时保留 ownership」只看 `whoami` 的 `is_admin`；但 `whoami` 返回的是成员自己的 `usr` 行，一个在工作区里持非管理员成员的 superadmin 会报 `is_admin: false`，而**后端在会话 / 用户 / 作业令牌三条认证路径上都把 superadmin 当 admin**，`can_preserve_on_behalf_of` 也会为他们保留原属主 ⇒ CLI 拦下了一批「根本不会改变任何属主」的 push，故障在 git sync 自动 pull 到 fork 时暴露（pull 以父项目上启用自动 pull 的 superadmin 身份运行）。
- **判据**：① **「文档说什么」与「代码做什么」是两个可漂移的值，修法是消除两个来源**：本例没有「把文档改成 RS256」就算完，而是让发现文档取签名的同一个常量 ⇒ 遇到「自述与实际不符」，先问能不能让二者**共用一个定义**；只改其中一处，下一次改签名算法时会再次漂移。② **发现/元数据文档是被消费的契约，不是说明文字**：校验方会 `reads the algorithm from discovery and enforces it` ⇒ 元数据面写错不是「文档小错」，其后果是**合法调用被全量拒绝**；验收这类接口要跑一次「按文档所声明的方式去校验」的端到端用例。③ **故障面在严格的一方**：宽容校验方无感，严格校验方全拒 ⇒ 排查「只有某一批客户端验签失败」时，先比对它们是不是真的按发现文档强制执行，而不是先怀疑 JWKS/密钥。④ **修这类 bug 不改变产物**：`No change to tokens, keys or the JWKS` ⇒ 可以单独评估风险与回滚面；发布说明里要写明「改的是声明面不是产物面」，否则运维会误以为需要轮换密钥。⑤ **客户端的权限判定必须复刻服务端的授权路径**：CLI 只看 `is_admin`，后端却把 `is_super_admin` 也算进去 ⇒ 凡是「客户端先判一次能不能做、服务端再判一次」的结构，两处判据必须同源；出现「我明明有权限却被本地拦下」时，优先怀疑客户端少算了一类隐含成员（superadmin / 服务账号 / 组继承）。⑥ **隐含成员要在自述里点名**：`whoami` 返回的 `is_admin` 不含 superadmin 语义 ⇒ 身份接口要说明「这个字段是否包含平台级超管」，否则下游会把它当完整的权限答案。⑦ 与 §权限签发面与执行面分离（av 2.202.0）互补：那条是**签发宽、执行严**（过授予），本例是**客户端严、服务端宽**（本地误拦）；两者都源于「两个地方各判一次且判据不同源」，补救方向相反——前者补执行侧取证，后者补判定同源。
- 提升层：工具（元数据与身份契约）/ 工作流（权限判定一致性）。触发词：discovery 宣告算法与实际不符、PS256 vs RS256、signing_algs 同源、按发现文档严格校验、superadmin 隐含管理员、is_admin 不含超管、whoami 自身行、CLI 与后端判据不同源。


## 部署态产物与预览态构造是两条路径：预览通过不构成部署产物正确的证据；物化时漏写的字段不会在运行时补齐，修复生效面是「重新物化」而不是「重启」（来源：api.github.com/repos/windmill-labs/windmill/pulls/11660 27,088B，2026-10-12 r532A 一手 curl 200 逐串命中 `keep preserve_step_tags on saved branch and loop flow nodes` / `copied same_worker into that value but not preserve_step_tags` / `Previews were unaffected because they build the nested value at runtime, which already carries the flag` / `Flow nodes are written at deploy time, so flows deployed before this fix keep their nodes without the flag until they are redeployed` / `the flag is part of the node hash, so new nodes are written` / `No runtime fallback is added`；r532A 落地）
- **实证**：Windmill #11660 修复的是「流部署后嵌套节点的标签丢失」。部署一条流时，每个多步分支 / 循环体会被存成一个自带 `FlowValue` 的 flow node；依赖作业只把 `same_worker` 拷进该值，**没拷 `preserve_step_tags`**，于是被保存的分支/循环里每个步骤都继承了流的标签——一个打了 `bun` 标签的步骤落到了只跑原生任务的 worker 上，报 `Worker is in native mode and cannot execute non-native job with language 'bun'`。关键三条边界：① **预览不受影响**，因为预览在运行时构造嵌套值，那条路径本来就带着该 flag；② 修复作用点是 `reduce_flow` / `insert_flow_modules`，把 `preserve_step_tags` 写进每一个被存储的节点（for / while / branch-one / branch-all 全覆盖）；③ **升级需要重新部署**——flow node 在部署时写入，旧部署的节点不带该 flag，**内容不变地重新部署一次就够**，因为该 flag 参与 node hash，会写出新节点；官方明确 `No runtime fallback is added`。
- **判据**：① **「预览能跑」与「部署后能跑」验证的不是同一个对象**：本例两条构造路径不同（运行时构造 vs 部署时物化），只有物化那条漏了字段 ⇒ 验收必须打在**部署后的真实产物**上，用预览 / 试运行结果当通过证据，等于只验了没问题的那条路径。② **物化漏字段是静默故障**：没有任何报错，只是标签被继承 ⇒ 凡是「把配置展开 / 扁平化后存起来」的结构（快照、编译产物、序列化节点、缓存条目），都要断言「存进去的字段集合 == 需要的字段集合」，只断言「能取出来」测不出漏字段。③ **修复生效面要写进发布说明**：`flows deployed before this fix keep their nodes ... until they are redeployed` ⇒ 这类修复不是「升级即生效」，发布说明必须写「需重新部署 / 重新生成」并给出判定方法（本例：内容不变重部署即可，因 flag 进 hash）。④ **「不做运行时兜底」是必须显式声明的取舍**：官方选择不加 fallback ⇒ 验收时要确认自己不依赖那条不存在的兜底；反过来，若你的系统依赖「运行时补齐」，就要把它当契约来测，而不是当巧合。⑤ **内容不变的重部署也能生效，前提是版本标识覆盖了变化字段**：`the flag is part of the node hash` ⇒ 设计产物 hash / 缓存键时把「会影响行为的配置」纳进键；否则会出现「改了配置但产物被判定为未变」的假命中。⑥ 与 §读侧形状是发布契约（av 2.205.0）、§自述与实际必须同源（av 2.207.0）分工：那两条管**读回来的形状**与**声明面与行为面**，本条管**写出去的产物在两条构造路径下不一致**，落点是「验证对象必须是部署后的真实产物」。
- 提升层：工具（部署产物验收）/ 工作流（修复生效面声明）。触发词：preview unaffected、deploy time 写入、preserve_step_tags 丢失、物化漏字段、重新部署才生效、node hash 含 flag、no runtime fallback、预览与部署两条构造路径。

## 数值零是合法取值，不是「空/缺失」的 falsy 哨兵：读侧与校验形状必须把 numeric 0 与 missing/empty 区分开，否则 falsy 强制会让 0 被当成未填而丢失（来源：api.github.com/repos/langgenius/dify/pulls/43243，2026-10-12 r535A 一手 curl 200 逐串命中 `used truthiness checks for Number inputs, so numeric 0 could be mistaken for an empty value` / `Preserve 0 from URL parameters and Number defaults instead of falling back to another default.` / `Keep 0 in the new-conversation input snapshot.` / `Accept 0 in required-field validation.` / `Render numeric 0 as 0, not as an empty field.` / `Prevent the embedded chatbot and chat-with-history disabled-state guards from treating 0 as missing.` / `Preserve existing normalization for empty-string defaults by converting them to null.`；r535A 落地）- **实证**：Dify 的嵌入式聊天机器人与 chat-with-history 两条输入流对 Number 输入用了 truthiness 检查，导致 numeric `0` 被误判为空值。修复覆盖六处同源事实：① 从 URL 参数 / Number 默认值里**保留 0**，不再回退到另一个默认；② 新会话输入快照里**保留 0**；③ 必填校验**接受 0**；④ 渲染层把 0 显示为 `0` 而不是空字段；⑤ 禁用态守卫不再把 0 当 missing；⑥ 空字符串默认仍归一为 `null`，与 0 明确分两条规则。两条路径共享同一输入语义，只修一条会留下另一条同样的 bug，所以必须同源修。- **判据**：① **数值 0 是合法值，falsy 强制是缺陷类**：任何「取值是否为空 / 未填」的判定不能把 0 当作假 ⇒ 读取与校验形状要把 numeric 0 与 missing/empty/null 显式区分（用 `== null` 而非 `!value` 或 falsy 判断）。② **类型化输入的 default 不是「空缺回退」**：Number 默认 0 是真实值，不应在读取时被回退到另一个默认 ⇒ 默认值与空缺是两种语义，校验要分别处理。③ **序列化往返要保真 0**：从 URL 参数 / JSON 读到的 0 必须原样保留进快照，不能因「空」判定被吞掉。④ **必填校验的「已填」判定要含 0**：required Number 输入填了 0 应算已填，falsy 判定会误拒合法输入。⑤ **渲染层与校验层语义一致**：显示 0 而非空、disabled 守卫不把 0 当 missing ⇒ 同一份「0 是否缺失」语义要在读 / 校验 / 渲染 / 禁用态四处一致，否则一处漏改就静默丢值。⑥ **空字符串默认归一 null 与 0 共存**：本例明确「空串默认→null、0 保留」，证明空值与 0 必须分两条规则，不能统一成「空」。⑦ **同源双路径要同修同测**：嵌入聊天与 chat-with-history 共享输入语义，只改一处留另一处同 bug ⇒ 共享语义的多个入口要一起改一起测。⑧ 与 §读侧形状是发布契约（av 2.205.0）、§部署态与预览态构造分叉（av 2.208.0）分工：那两条管「读回类型 / 构造路径不同」，本条管「数值零的语义保真」，落点是数据形状的零值处理。- 提升层：工具（读侧 / 校验形状契约）/ 工作流（零值回归用例）。触发词：numeric 0 mistaken for empty、truthiness check Number、preserve 0 from URL params、required validation accept 0、render 0 not empty、disabled guard treats 0 as missing、empty-string→null、零值保真。

## 验证流水线的顺序本身是安全属性：先扫描、再填卡、然后对「实际发布的那一份目录」签名；签名只证明「装的就是被签的那份」，不证明技能无害（来源：raw.githubusercontent.com/nvidia/skills/main/docs/signing-agent-skills.mdx 3,330B，2026-10-12 r541A 一手 curl 200 逐串命中 `directory tree` / `unsigned files` / `does not prove a skill is safe` / `ignore-unsigned-files`；提名 Qoder r540-Q-C ③）
- **实证**：NVIDIA skills 仓的签名文档给出一条完整发布流水线：`SkillEvaluator`（对 release-checklist#tier-1 范围跑 SkillSpector）→ 处置 findings → **填完技能卡** → **签「实际发布的那份目录」** → 发布 `.sig` → 安装/CI 时校验。签名格式「extends Sigstore-style bundles so verification can cover a **directory tree** instead of only a single file」，默认覆盖范围内全部文件与目录、**排除签名自身**；「**签名后加入的未签名文件，严格校验应当失败**」，唯一降级位是显式 flag `--ignore-unsigned-files`；文档尾段免责原文「Signing does not prove a skill is safe. It proves the released skill is the one that was signed」。
- **判据**：① **顺序错置会让签名对不上被发布物**：先签后改卡片、或签完再补文件，签名覆盖的就不再是最终发布态 ⇒ 验收断言必须是「签名的对象 == 实际发布的对象」，把流水线顺序写进发布门控清单。② **完整性声明的覆盖面必须与可校验覆盖面逐项对账**：目录树签名默认「除签名自身外全量覆盖」，新增未签名文件必须让严格校验失败 ⇒ 设计验签规则时先枚举「哪些文件在覆盖范围内」，再把「范围外文件出现」当失败态；降级只能是显式 flag，不能是默认宽容。③ **验签结论的落栏有硬约束**：签名证明的是来源与完整性，不是安全性 ⇒ 审计报告里「已验证签名」只能进「完整性/来源」栏，进「安全性」栏即越界（与 §权限签发面与执行面分离 av 2.202.0 同族：拿得到的 scope 不一定能用，签得了的名不一定无害）。④ 与 §签名粒度=目录内每个文件 detached signature（KB r347A）分工：那条管**签多细**（文件级粒度 + verified 指针可机检），本条管**何时签、签哪一份、结论写在哪**（时序、覆盖面、语义落栏）。
- 提升层：工具（验签流水线设计）/ 工作流（发布门控顺序）。触发词：签名时序、签被发布的那一份、directory tree 签名、签名后新增未签名文件、ignore-unsigned-files、签名不证明安全。

## 目录内容哈希的三态语义：`hash: string | null` 的规范释义是「无快照」而非「内容未变」——把 null 读成未变，等于把无证据当通过（来源：www.skills.sh/docs/api 138,514B，2026-10-12 r541A 一手 curl 200 逐串命中 `SHA-256 hash of the skill's file contents. Use for cache invalidation or detecting changes without re-fetching files. - **实证**：skills.sh 注册表详情端点 `GET /api/v1/skills/{source}/{skill}` 返回整目录文件内容的 SHA-256 与文件列表两个字段，用途写明「cache invalidation or detecting changes without re-fetching files」，但两个字段都允许 null，释义逐字为「Null if no snapshot exists」——**拿不到摘要与内容没变是两种不同状态，API 用 null 显式区分**。

## 提示前缀的缓存契约包含键序：schema 属性顺序跨作业漂移会让每个作业的首个模型调用必丢前缀缓存，序列化容器随机序是隐形根因（来源：api.github.com/repos/windmill-labs/windmill/pulls/11687，2026-10-12 r542A 一手 curl 200 逐串命中 `An AI agent step's JSON schemas (the structured output_schema and each script tool's parameters) are part of the prompt prefix a provider caches on` / `Their property order changed from one job to the next, so the first model call of every job missed the prompt cache; only later calls inside the same job hit it` / `OpenAPISchema kept properties, $defs and definitions in a std::collections::HashMap, whose iteration order is randomised per process and per map` / `filter_schema_by_input_transforms removed a tool's preset inputs with Map::remove while iterating a HashSet` / `With serde_json's preserve_order, remove swaps the last entry into the freed slot` / `Six separate preview jobs sent byte-identical request bodies`；r542A 落地）

## 有效期校验的形状：无效形态要枚举到上界（错类型/NaN/0/负/非有限/超 JS Date 上限），间接引用不绕过被引字段自身的校验，引用名永远不作为凭据发送（来源：docs.openclaw.ai/auth-credential-semantics.md 29,070B，2026-10-12 r542B 一手 curl 200 逐串命中 `expires is optional. ## 可重试性按责任来源分四档而非按状态码；归因本身须申报为尽力推断并附可复核证据（来源：Qoder r542-Q-A 提名，WB 审计一手复核 pipedream.com/docs/connect/components/actions，2026-10-12 逐串命中）
- **实证**：Pipedream Connect 行动失败按 `origin` 四分类：`component_code`（自有码缺陷→不可重试）/ `upstream_api`（上游 API 4xx/5xx，仅 5xx 可重试）/ `network_io`（网络 I/O→最可重试）/ `response_parsing`（2xx 但解析失败→重试无益）；文档明言归因是 best-effort（靠观测到的 HTTP 调用与抛出点关联），并附 `last_call{client,method,host,status,duration_ms}` 可复核证据。
- **判据**：① 重试决策问「责任在谁」不问「什么码」——同一 500 来自上游抖动可重试、来自自家代码缺陷重试纯浪费；2xx 解析失败是第四态（不是成功也不是失败），重试无益；② 归因是推断不是事实——未声明 best-effort 的归因会被下游当确定事实用，须附证据槽（最后一次调用的客户端/方法/主机/状态/耗时），取不到证据的归因降级为未知；③ 分类表与重试矩阵同源维护，分档变了矩阵必须跟着变。

## 多步变更的最后一公里：完成判据、启用动作、前置就绪必须明示，否则操作员被锁在「已就绪但未启用」状态外（来源：api.github.com/repos/langflow-ai/langflow/pulls/15679，2026-10-11 merged，一手 curl + 逐串命中）

## 检索与选择面的排序必须纳入执行期可靠性：语义 MRR 高≠选得对，验收指标是故障场景错选率（来源：arxiv.org/abs/2610.13889，2026-10-09 一手实拉摘要逐串命中）
- **实证**：RATED（Reliability-Aware Tool Retrieval via Execution Dynamics）：现有工具检索方法优化语义相关性，但 largely ignore tool availability during execution——静态语义排序会把已失效/高失败的工具排在前面。RATED = frozen dual-encoder + contrastive fine-tuning 做语义匹配 + lightweight contextual bandit 模块按实时执行反馈重排候选，不重训模型即可快速适应运行时工具失败。EcoAgent 基准：5,172 个真实工具、210,000+ query-tool pairs。结果：真实查询上相对 ToolLLM API retriever MRR +52.2%；30% API 失败率的严重 outage 场景下 fault selection rate 从 86.2% 降到 2.9%；重排延迟开销 <1ms。
- **判据**：① **语义相关性与执行可用性是两个轴**——「选得相关」不等于「选得能跑」；选择面（检索/匹配/推荐/技能装载）必须把实时成败反馈纳入候选重排，轻量 bandit 类机制即可，不必重训模型；② **验收指标必须含故障面错选率**（outage 场景下选中故障工具的比例），只报 offline MRR 会把整个失效面漏掉——86.2% 的错选率在 MRR 曲线上完全看不见；③ **重排开销要有预算线**（本例亚毫秒级），用可靠性换延迟要明码标价；④ 对技能系统的直接映射：技能/工具按 description 语义匹配装载时，历史执行成败（工具真实可跑率）应作为重排信号；选择器的验收 = 故障场景错选率 + MRR 双指标，单指标不过验收。
- 提升层：工具（选择器/检索器设计）/ 工作流（评测指标设计）。触发词：执行期可靠性重排、语义 MRR 不够、fault selection rate、outage 错选率、RATED、contextual bandit、实时执行反馈进排序、EcoAgent、工具可用性轴、双指标验收、状态绑定凭据、适用性由状态定不定时、绑定粒度匹配等待粒度、派生令牌不存储、恢复 URL 控制面、flake 修复等就绪信号、repeat-each 量化flake率、4/12 到 25/25。

## 恢复类凭据按状态绑定而非时间绑定：绑定粒度必须匹配消费方的等待粒度，派生令牌不落盘（来源：api.github.com/repos/n8n-io/n8n/pulls/39089，2026-10-12 merged，一手 curl + 逐串命中）
- **实证**：n8n engine v2 用一份 ADR 记录「派生令牌授权恢复请求」的设计：三种令牌——execution-bound resume URL、step-bound resume URL、approval callback——**一个 wait 只接受同方式绑定的令牌**；令牌**不过期**，请求是否仍适用由 step 状态决定；data plane 自行派生令牌且**不存储任何东西**（engine v1 的存储随机令牌与 encryption-key HMAC 两种机制，在 data plane 独立进程拿不到 control plane 加密密钥时都失效）；密钥管理（secret source/轮换/拒启）显式划到后续 ADR。
- **判据**：① **适用性边界有两个坐标系——时间与状态**：交互类票按时间绑定（av 2.215.0 寿命匹配会话），恢复/等待类凭据按状态绑定（step 终态即失效）——用错坐标系表现为两种坏味：时间绑定的恢复票在长流程中途过期作废，或状态绑定的票在状态已变后仍被接受。② **绑定粒度必须匹配消费方的等待粒度**：按执行绑定、按步骤绑定、按审批回调绑定是三种粒度，wait 只收同粒度令牌——粗粒度令牌被细粒度等待接受=一个恢复点能授权整条流程。③ **凭据的可得性路径要与运行时的密钥可达性匹配**：派生-不存储让无密钥方也能造票（只有 data plane 运行时能构建），存储式令牌在跨进程/跨面部署下拿不到密钥即全瘫——设计凭据先问「哪个面在什么时刻能接触到什么秘密」。④ 与 av 2.216.0（有效期形状：上界/间接引用不豁免）分工：那条管时间字段的校验形状，本条管「要不要用时间」这个坐标系选择与绑定粒度匹配。
- 提升层：工具（凭据设计）/ 工作流（恢复与等待授权）。触发词：状态绑定凭据、applicability by state not expiry、绑定粒度匹配等待粒度、execution-bound/step-bound/approval callback、派生令牌不存储、derived not stored、恢复 URL 是暂停工作流与未知调用者之间唯一的控制、密钥管理范围外显式声明。
